#### 1) **Compilation failures of generated tests (E2029 Declaration expected but end of file found)**

- **Likely causes:**

  - **Peer output formatting artifacts**: The debug log shows peers returning strings like `delphiCopyDownloadprogram HelloWorld;` or `Delphiprogram HelloWorld;` — these are concatenated tokens (site labels, "CopyDownload", or filename headers) that were not stripped before writing to the compiler input.

The agent's parser that extracts code from peer responses likely failed to robustly extract only the code block content.
  - **Temporary file naming/extension mismatch**: The test harness wrote files with `.txt` extension (see `grisp_test_... .txt`) instead of `.dpr` or `.pas`, which may confuse the Delphi compiler or the registry logic that expects `.pas`/`.dpr`. The compiler error referencing `.txt` suggests the file content or extension was wrong.

#### 2) **Peer output normalization/parsing is brittle**
- **Symptom:** Peer responses include site-specific prefixes, capitalization differences, or appended tokens (e.g., `delphiCopyDownload`, `Delphiprogram`), and the agent still wrote them to disk for compilation.
- **Likely causes:**
  - **Insufficient sanitization**: The agent's code that extracts code from peer responses does not robustly strip non-code text, code fences, or site-specific artifacts.
  - **Overly strict prompt format**: The agent required a filename header in the markdown block; peers sometimes prepend site labels or other UI tokens. The agent's parser should be tolerant to such variations.

#### 3) **Test harness and compiler registry fragility**
- **Symptom:** The `TGrispCompilerRegistry.GetCompilerForLanguage` and `TGrispTestAdapterImpl.ExecuteInternalTest` rely on file naming and language mapping that can fail when inputs are unexpected.
- **Likely causes:**
  - **Language vs. file extension mismatch**: `ExecuteInternalTest` chooses file extension based on `Language.ToLower = 'c'` or `'pascal'/'delphi'` string comparisons, but the `Compiler` is selected using `FConfig.PreferredLanguage` (an enum) — mismatch between the textual `Language` parameter and the configured enum can cause wrong compiler selection or exceptions (note: registry raises for Python).
  - **Temporary file extension `.txt` used**: The debug output shows `.txt` files being compiled; Delphi expects `.dpr` or `.pas`. The registry/adapter should ensure correct extension and file content before invoking compiler.
  - **RunProcess and CreateProcess handling**: The `RunProcess` implementation is complex and platform-dependent; timeouts or partial reads could mask errors. But primary issue is malformed source.

#### 4) **Prompt engineering and peer instruction leakage**
- **Symptom:** The debug prompts include `<!-- DEBUG: ... -->` tags and explicit instructions to output only code blocks with filename headers. Peers still returned extraneous tokens.
- **Likely causes:**
  - **Peers (web LLMs) sometimes include UI artifacts** (e.g., "CopyDownload", site labels) or ignore strict formatting constraints. The agent should not assume perfect compliance.
  - **Prompt-tagging enabled**: The agent inserted debug comments into prompts (`EnablePromptTagging := PromptTag`), which may have influenced peer outputs or introduced tokens that peers echoed back.

#### 5) **Agent decision despite failing tests**
- **Symptom:** The agent selected a final solution and wrote `/workspace/program.txt` even though generated tests failed repeatedly.
- **Likely causes:**
  - **Scoring logic tolerates test failures**: The agent's selection criteria appear to weigh peer reliability and repairs and may accept a repaired candidate even if tests failed, or the final "chosen" solution may be the repaired code produced by peers (not the compiled test).
  - **False-positive success reporting**: The agent reports "Plan committed and persisted" and writes files even when the test harness failed to compile the temporary test files. This can mislead users.

### Concrete code sketch (sanitizer pseudocode in Pascal/Delphi)
Add a function near the peer-response handling code:

```pascal
function ExtractDelphiCode(const Raw: string; out FileName, Code: string): Boolean;
var
  FenceStart, FenceEnd: Integer;
  Candidate: string;
begin
  // 1) Remove HTML-style debug tags
  Candidate := RegexReplace(Raw, '<!--.*?-->', '', [roIgnoreCase, roSingleLine]);

  // 2) Find first triple-backtick fenced block
  FenceStart := Pos('```', Candidate);
  if FenceStart > 0 then
  begin
    FenceEnd := PosEx('```', Candidate, FenceStart + 3);
    if FenceEnd > FenceStart then
      Candidate := Copy(Candidate, FenceStart + 3, FenceEnd - (FenceStart + 3));
  end;

  // 3) Strip common UI tokens (e.g., 'delphiCopyDownload', 'Delphiprogram')
  Candidate := RegexReplace(Candidate, '^(delphiCopyDownload|Delphiprogram|Pascal/Delphi:\w+)', '', [roIgnoreCase]);

  // 4) Trim and ensure it looks like Delphi source
  Candidate := Trim(Candidate);
  if (Pos('program', LowerCase(Candidate)) = 1) or (Pos('unit', LowerCase(Candidate)) = 1) then
  begin
    Code := Candidate;
    FileName := 'HelloWorld.dpr'; // or parse from fence header if present
    Result := True;
  end
  else
    Result := False;
end;
```

Use this function to produce the sanitized `Code` and ensure the temp file uses `.dpr` extension before calling the compiler.
