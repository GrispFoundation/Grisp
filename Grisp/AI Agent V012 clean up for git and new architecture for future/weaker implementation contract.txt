# GRISP v1.0

# Protocol & Implementation Design

**Status:** NORMATIVE IMPLEMENTATION DESIGN
**Derived from:** GRISP Agent Specification v1.0
**Primary implementation:** Delphi / Windows
**Browser gateway:** Firefox
**AI transport protocol:** GARP/1.0
**AI semantic protocol:** GAI/1.0
**Artifact identity:** SHA-256 based
**Default execution policy:** fail-closed

---

# 1. Purpose

GRISP v1.0 is a deterministic, evidence-driven AI engineering runtime.

Its purpose is not merely to obtain an answer from an LLM.

Its purpose is to produce, verify, and, when authorized, commit an engineering artifact whose exact identity, provenance, validation evidence, and acceptance decision are reconstructable.

The fundamental model is:

```text
AI       = reasoning worker
GRISP    = authority
TOOLS    = measurement
POLICY   = authorization
EVIDENCE = proof record
FIREFOX  = AI transport and interaction substrate
```

No external AI system is authoritative.

An AI worker may:

```text
analyze
plan
generate
criticize
repair
design tests
review
rank
explain
```

An AI worker may not by itself establish:

```text
correctness
authorization
security
successful compilation
successful execution
successful testing
final acceptance
```

The architecture therefore follows:

```text
USER REQUEST
    ↓
TASK
    ↓
AI REASONING
    ↓
CANDIDATE ARTIFACT
    ↓
DETERMINISTIC VALIDATION
    ↓
OBJECTIVE EVIDENCE
    ↓
HARD ACCEPTANCE GATES
    ↓
FINAL VERIFICATION
    ↓
TRANSACTIONAL COMMIT
```

The core invariant is:

```text
NO UNVERIFIED ARTIFACT MAY BECOME
AN ACCEPTED GRISP RESULT.
```

This is consistent with the normative architecture and its explicit non-negotiable invariants.

---

# 2. Normative hierarchy

GRISP implementations shall interpret specifications in this priority order:

```text
1. GRISP semantic invariants
2. acceptance and security rules
3. artifact identity rules
4. evidence rules
5. state-machine rules
6. GAI semantic protocol
7. GARP transport protocol
8. implementation-specific storage/transport details
9. optimization
```

An implementation detail SHALL NOT weaken a higher-level requirement.

For example:

```text
PostgreSQL limitation
    SHALL NOT weaken evidence immutability.

Firefox limitation
    SHALL NOT turn an unknown response into a valid response.

LLM confidence
    SHALL NOT override compiler failure.

Performance optimization
    SHALL NOT eliminate final verification.
```

---

# 3. Separation of specifications

GRISP shall not collapse all protocols into one specification.

The system shall be divided into four explicit contracts:

```text
GRISP SEMANTICS
    Task
    Artifact
    Evidence
    Policy
    Decision
    State
    Acceptance

GAI/1.0
    AI worker request/response semantics

GARP/1.0
    GRISP ↔ Firefox transport/session protocol

IMPLEMENTATION
    Delphi classes
    storage
    processes
    Firefox actors
    provider adapters
```

This separation is important.

GARP transports data.

GAI describes what the AI worker is being asked to produce.

GRISP interprets and verifies the result.

Firefox does not become part of GRISP's semantic authority.

The architecture explicitly establishes this boundary.

# 5. Task

A task is the normalized representation of a user request.

```text
TGrispTask

task_id
user_prompt
target_language
target_platform
requested_artifact_kind
constraints
acceptance_tests
risk_level
required_capabilities
policy_profile
created_at
metadata
```

`requested_artifact_kind` shall distinguish at least:

```text
EXECUTABLE
LIBRARY
UNIT
PROJECT
SCRIPT
PATCH
DOCUMENTATION
ANALYSIS
```

The artifact kind determines which objective validations are applicable.

For example:

```text
EXECUTABLE
    compile
    runtime
    tests

UNIT
    compile
    harness/tests

DOCUMENTATION
    syntax/schema validation
    policy
```

GRISP shall never silently replace one artifact contract with another.

# 6. Risk classification

Every task shall have a deterministic risk classification:

```text
R0  informational
R1  ordinary generation
R2  system/file state
R3  privileged/security/network
R4  destructive/high impact
```

Risk classification shall affect:

```text
allowed capabilities
sandbox restrictions
validation requirements
verification depth
human approval requirements
```

Keyword detection may provide hints.

It SHALL NOT be the security authority.

The identity hierarchy shall distinguish:

```text
provider
```

Two providers shall not automatically be considered statistically independent merely because their names differ.

# 9. GAI/1.0 semantic worker protocol

AI responses shall be treated as protocol data rather than arbitrary prose.

Preferred form:

```json
{
  "protocol": "GAI/1.0",
  "operation": "generate",
  "result": "ok",
  "artifacts": [
    {
      "filename": "HelloWorld.dpr",
      "language": "delphi",
      "kind": "source",
      "content_encoding": "utf-8",
      "content": "program HelloWorld;..."
    }
  ]
}
```

A provider does not need to natively implement GAI/1.0.

The worker adapter may translate the provider's response into GAI-compatible raw semantics.

The critical rule is:

```text
provider response
    ↓
strict parse
    ↓
ArtifactBundle
```

not:

```text
provider response
    ↓
heuristic cleanup
    ↓
maybe artifact
```

---

# 10. Artifact response states

An AI response is not automatically an artifact.

The semantic boundary is:

```text
RAW_RESPONSE
    ↓
RESPONSE_PARSED
    ↓
ARTIFACT_BUNDLE_CREATED
```

The following are distinct:

```text
RAW_RESPONSE
PARSED_RESPONSE
ARTIFACT_BUNDLE
ARTIFACT
ACCEPTED_ARTIFACT
COMMITTED_ARTIFACT
```

Each represents a stronger guarantee.

Therefore:

```text
UNPARSED DATA CANNOT BECOME AN ARTIFACT.
```

# 11. ArtifactBundle

The canonical internal representation is:

```text
TGrispArtifactBundle

artifact_id
task_id
parent_artifact_id
revision
files[]
artifact_kind
language
provenance
metadata
```

Each file contains:

```text
TGrispArtifactFile

filename
language
kind
content
content_encoding
content_sha256
size_bytes
```

The file content itself is authoritative.

The supplied hash is metadata that must be independently verified.

---

# 12. Artifact identity

The implementation shall distinguish two concepts:

```text
FILE CONTENT HASH
ARTIFACT MANIFEST HASH
```

The file content hash is:

```text
SHA256(exact canonical file bytes)
```

The artifact identity is:

```text
artifact_id =
sha256:
SHA256(
    canonical artifact manifest
)
```

The canonical manifest contains the exact hashes of all files.

This means the artifact identity is a deterministic identity of the complete bundle.

It shall NOT be based on:

```text
filename alone
array index
memory address
database row number
provider message ID
```

---

# 13. Exact-content rule

For an artifact whose bytes are to be compiled, executed, tested, or committed:

```text
THE BYTES USED FOR VERIFICATION
MUST BE THE BYTES IDENTIFIED BY THE ARTIFACT.
```

The system shall not silently transform:

```text
CRLF → LF
encoding
whitespace
Unicode normalization
source text
```

between artifact creation and verification.

A normalization operation is itself a transformation.

Therefore:

```text
Artifact A
   ↓ normalize
Artifact B
```

creates a new artifact identity.

This is necessary to preserve the final invariant:

```text
FINAL COMMITTED BYTES
=
FINAL VERIFIED BYTES
```

---

# 14. Canonical artifact manifest

The canonical manifest shall contain:

```text
task_id
parent_artifact_id
revision
artifact_kind
language
files
provenance
metadata
```

`artifact_id` is excluded from the manifest being hashed.

Files shall be sorted by:

```text
UTF-8 bytewise filename order
```

If filenames are identical, sort by:

```text
content_sha256
```

Each file record shall contain:

```text
filename
language
kind
content_encoding
content_sha256
size_bytes
```

Raw file content shall NOT be included in the manifest hash payload.

The manifest therefore remains compact, while the file hashes retain content identity.

---

# 15. Canonical JSON

Canonical JSON serialization shall be explicitly defined.

Rules:

```text
UTF-8
no insignificant whitespace
exact key ordering where specified
UTF-8 bytewise ordering for dynamically sorted metadata keys
stable escaping
no implementation-defined number representation
```

Because Delphi's JSON implementation and other runtimes may serialize JSON differently, GRISP SHALL NOT rely blindly on library `ToJSON` behavior for a cross-language artifact identity.

A dedicated canonical serializer shall be used.

The canonical serializer shall have test vectors.


It shall additionally reference:


The provenance model exists to make reconstruction possible.

# 17. Artifact parser

The parser is a security boundary.

It shall implement three modes:

```text
STRICT_STRUCTURED
COMPATIBILITY_MARKDOWN
RAW_TEXT
```

`RAW_TEXT` is permitted only when the task explicitly requests raw textual output.

The default for engineering artifacts is:

```text
STRICT_STRUCTURED
```

---

# 18. Strict structured parsing

A structured response shall be accepted only if:

```text
schema valid
required fields present
field types valid
filenames valid
content encoding valid
file hashes valid
bundle hash valid
artifact kind valid
language valid
```

The parser shall recompute:

```text
content_sha256
artifact_id
```

and compare them against any supplied values.

A mismatch is:

```text
ARTIFACT_HASH_MISMATCH
```

not an invitation to silently replace the incoming identity.

---

# 19. Markdown compatibility parsing

Markdown is compatibility mode only.

The parser shall inspect the entire response.

It shall not simply take:

```text
first code block
```

and ignore everything else.

Instead:

```text
response
 ↓
discover all candidate blocks
 ↓
classify headers
 ↓
associate filenames
 ↓
validate language
 ↓
detect conflicts
 ↓
determine whether interpretation is unique
```

Exactly one valid interpretation:

```text
ACCEPT
```

No valid interpretation:

```text
PARSE_ERROR
```

Multiple plausible interpretations:

```text
PARSE_AMBIGUOUS
```

---

# 20. No repair-by-cleanup

The parser SHALL NOT silently remove strings such as:

```text
CopyDownload
Delphiprogram
Pascalprogram
```

or other provider/UI contamination.

Unexpected tokens shall be diagnostics.

Example:

```text
UNEXPECTED_TOKEN
position = ...
token = "delphiCopyDownload"
context = artifact content
```

The purpose of the parser is to identify malformed data, not to guess what the provider intended.

The architecture explicitly rejects the previous string-cleaning approach.

---

# 21. Filename rules

Filenames shall be explicit.

A parser shall NOT invent:

```text
HelloWorld.dpr
program.pas
main.py
```

merely because they seem plausible.

Missing required filename metadata shall result in:

```text
PARSE_ERROR
```

A transformation that supplies a filename is not parsing; it is inference.

Inference may be performed by an AI worker.

It must not silently occur in the artifact parser.

---

# 22. Static artifact validation

Before expensive compilation:

```text
encoding
NUL
filename syntax
path traversal
absolute paths
duplicate filenames
maximum size
maximum file count
language consistency
extension consistency
artifact kind consistency
```

For Delphi:

```text
program/unit/library structural form
filename/extension compatibility
obvious framing contamination
```

This stage is deterministic.

# 24. Evidence categories

Evidence should explicitly distinguish:

```text
PARSE_EVIDENCE
STATIC_VALIDATION_EVIDENCE
OBJECTIVE_BUILD_EVIDENCE
OBJECTIVE_RUNTIME_EVIDENCE
OBJECTIVE_TEST_EVIDENCE
POLICY_EVIDENCE
HASH_EVIDENCE
COMMIT_EVIDENCE
SUBJECTIVE_AI_EVIDENCE
```

An AI opinion shall never masquerade as objective evidence.

For example:

```text
LLM: "This code looks correct."
```

is:

```text
SUBJECTIVE_AI_EVIDENCE
```

while:

```text
dcc64 exit code = 0
```

is:

```text
OBJECTIVE_BUILD_EVIDENCE
```

```text

 ↓

 ↓
executable
 ↓
process runner
```

# 28. Test architecture

Tests must target the actual artifact.

For executables:

```text
artifact
 ↓
process
 ↓
observable output
 ↓
oracle
```

For units:

```text
artifact
+
test harness
 ↓
compile
 ↓
run
 ↓
oracle
```

For projects:

```text
project graph
 ↓
materialized files
 ↓
build
 ↓
runtime
 ↓
tests
```

The generated test shall not invent a function merely to make the candidate testable.

That exact failure mode is explicitly prohibited by the architecture.

---

# 29. Test descriptor

Every test shall declare:

```text
test_target
test_type
oracle
coverage_intent
```

Examples of oracle types:

```text
stdout_exact
stdout_contains
exit_code
file_exists
file_hash
structured_output
exception
property
```

A test that cannot demonstrate that it exercises the real artifact is:

```text
TEST_INVALID
```

and contributes no acceptance evidence.

# 30. Policy engine

The policy engine is an enforcement boundary.

Capabilities shall be explicit:

```text
compile
run
read_workspace
write_workspace
delete_workspace
network
browser_ai
process_spawn
debug
```

A worker may request a capability.

The policy engine decides whether the capability is authorized.

The request is not the authorization.

# 31. State machine

The orchestrator shall use an explicit state machine.

Recommended states:

```text
TASK_ACCEPTED
TASK_NORMALIZED
WORKER_PLAN
CANDIDATE_GENERATION
ARTIFACT_PARSE
STATIC_VALIDATION
COMPILE_PENDING
COMPILED
RUNTIME_PENDING
RUNTIME_VERIFIED
TEST_PENDING
TEST_VERIFIED
ADVERSARIAL_REVIEW
CANDIDATE_RANKING
FINAL_VERIFICATION
COMMIT_PENDING
COMMITTED
REPORT
```

Failure states:

```text
NORMALIZATION_FAILED
PARSE_FAILED
STATIC_FAILED
POLICY_REJECTED
COMPILE_FAILED
RUNTIME_FAILED
TEST_FAILED
TIMEOUT
CANCELLED
VERIFICATION_FAILED
COMMIT_FAILED
```

There is no generic:

```text
failure → success
```

transition.

---

# 32. State transitions

A state transition must have:

```text
current state
event
guard
new state
reason
```

Example:

```text
COMPILE_PENDING
    + CompileCompleted(status=ok)
    + applicable runtime contract
    ↓
COMPILED
```

Failure:

```text
COMPILE_PENDING
    + CompileCompleted(status=failed)
    ↓
COMPILE_FAILED
```

No other implicit transition exists.

---

# 33. Candidate state versus task state

The implementation shall distinguish:

```text
TASK STATE
```

from:

```text
CANDIDATE STATE
```

because multiple candidates may exist simultaneously.

For example:

```text
Task T1
 ├── Candidate A → COMPILE_FAILED
 ├── Candidate B → TEST_VERIFIED
 └── Candidate C → POLICY_REJECTED
```

The task remains active while eligible candidates exist.

Only candidates that pass the applicable hard gates may enter ranking.

---

# 34. Acceptance predicate

Define acceptance as a deterministic predicate:

```text
ACCEPTABLE(T, A) iff

    ArtifactParsed(A)
AND StaticValidationPassed(A)
AND PolicyPassed(T, A)
AND AllRequiredObjectiveChecksPassed(T, A)
AND FinalVerificationPassed(T, A)
AND ProvenanceComplete(A)
AND ArtifactIdentityValid(A)
```

For applicable checks:

```text
CompileRequired → CompilePass
RuntimeRequired  → RuntimePass
TestsRequired    → TestsPass
```

A missing required check is failure.

It is not equivalent to success.

---

# 35. Objective gates precede subjective ranking

The candidate pool is partitioned:

```text
ALL CANDIDATES
      ↓
PARSE VALID
      ↓
POLICY VALID
      ↓
BUILD VALID
      ↓
RUNTIME VALID
      ↓
TEST VALID
      ↓
ELIGIBLE SET
```

Only then may subjective ranking occur.

Therefore:

```text
compile = false
```

means:

```text
eligible = false
```

regardless of:

```text
AI score
peer confidence
provider reputation
number of approving reviewers
```

This is one of the central principles of the specification.

---

# 36. Subjective scoring

Subjective quality remains useful.

After hard validation:

```text
quality_score
reviewer_confidence
reliability_factor
```

may be used to rank eligible candidates.

Example:

```text
ranking_score =
    quality_score
    × reviewer_confidence
    × reliability_factor
```

The score has no authority over acceptance.

It chooses among candidates that are already valid.

---

# 37. Adversarial review

Before final ranking, GRISP may ask a worker to attack a candidate.

The purpose is defect discovery.

The reviewer should be instructed to find:

```text
smallest failing input
compiler edge case
runtime failure
security issue
contract violation
environment dependency
```

Findings shall be classified:

```text
BUG
SECURITY
CONTRACT_VIOLATION
PORTABILITY
PERFORMANCE
ROBUSTNESS
STYLE
OPTIONAL_IMPROVEMENT
FALSE_POSITIVE
```

Normally only:

```text
BUG
SECURITY
CONTRACT_VIOLATION
```

trigger automatic repair.

---

# 38. Repair model

Repairs create new immutable candidates.

```text
Candidate A
    │
    ├── evidence
    ├── critique
    └── repair request
              │
              ▼
         Candidate B
```

Candidate A is never mutated in place.

Therefore provenance remains:

```text
parent_artifact_id
```

and the candidate graph remains reconstructable.

---

# 39. Parser repair versus AI repair

When failure originates in artifact framing:

```text
provider output
    ↓
malformed framing
```

GRISP should repair the parser/extraction process first.

Only when the source itself is invalid should the system request the LLM to rewrite the implementation.

Correct:

```text
bad framing
    ↓
strict extraction retry
    ↓
same source
```

Not:

```text
bad framing
    ↓
generate an entirely new program
```

The architecture explicitly establishes this recovery strategy.

---

# 40. Final verification

The selected candidate is not automatically trusted.

GRISP shall verify the exact final candidate again.

Required sequence:

```text
1. obtain exact final bytes
2. recompute artifact identity
3. verify artifact identity
4. parse final artifact
5. static validate
6. compile exact bytes
7. run exact bytes
8. execute mandatory tests
9. execute policy checks
10. record final evidence
11. compare expected artifact identity
12. only then prepare commit
```

No prior evidence is substituted for final verification.

---

# 41. Transactional commit

Commit shall be treated as a separate verified stage.

```text
FINAL_VERIFIED
      ↓
COMMIT_PENDING
      ↓
prepare
      ↓
stage exact bytes
      ↓
write atomically
      ↓
re-read committed bytes
      ↓
hash committed bytes
      ↓
compare with verified identity
      ↓
record commit evidence
      ↓
COMMITTED
```

The following must be impossible:

```text
verified artifact A
        ↓
write artifact B
        ↓
report artifact A as committed
```

The critical invariant is:

```text
FINAL COMMITTED BYTES
=
FINAL VERIFIED BYTES
```

The original specification explicitly requires verification of committed bytes.

---

# 42. No force-commit bypass

GRISP shall not provide a mechanism equivalent to:

```text
--force-commit
```

that turns a failed artifact into an accepted artifact.

A developer may request:

```text
DRAFT OUTPUT
```

but this shall be a different storage class:

```text
/workspace/draft/
```

not:

```text
/workspace/final/
```

A failed or unverified artifact remains unaccepted.

---

# 43. Workspace

The workspace shall distinguish:

```text
/workspace/
    input/
    candidates/
    tests/
    build/
    runtime/
    final/
    evidence/
    logs/
    draft/
```

Semantics:

```text
input     = task material
candidates= immutable candidates
tests     = test definitions
build     = compiler outputs
runtime   = execution outputs
final     = accepted artifact only
evidence  = immutable evidence
logs      = operational logs
draft     = explicitly unverified developer output
```

Only `/final` represents an accepted artifact.

---

# 44. Storage abstraction

The GRISP core shall not depend directly on PostgreSQL.

Define:

```pascal
IGrispArtifactStore
IGrispEvidenceStore
IGrispTaskStore
IGrispDecisionStore
```

The first implementation may use local deterministic storage.

Later implementations may use:

```text
SQLite
PostgreSQL
embedded storage
distributed storage
```

without changing the semantic core.

The database is an implementation detail.

The evidence contract is normative.

---

# 45. Evidence immutability

Evidence is append-only.

The application shall expose:

```text
record evidence
read evidence
query evidence
```

but not:

```text
modify evidence
delete evidence
```

An implementation may enforce this using:

```text
database permissions
append-only tables
hash chaining
signed records
```

The chosen mechanism does not alter the semantic rule.

---

# 46. Evidence querying

The minimum query dimensions shall be:

```text
task_id
artifact_id
operation
worker_id
evidence_id
created_at
status
```

Common reconstruction query:

# 59. GARP idempotency

`request_id` is also the idempotency key.

A repeated:

```text

```

must not submit the prompt twice.

The gateway shall return the existing request state when the same request is retried.

This directly prevents duplicate browser submissions.

# 60. GARP cancellation

```json

  "protocol": "GARP/1.0",
  "type": "cancel_prompt",
  "request_id": "uuid",
  "session_id": "uuid",
  "payload": {
    "reason": "task_timeout"
  }

```

The gateway shall terminate or stop observing the provider operation.

The resulting state must be explicit:

```text
CANCELLED
```

or:

```text

```

Cancellation cannot mean success.

# 72. Reliability model



# 73. Reliability mathematics

A Bayesian model such as Beta distributions may be used:

```text
Beta(
    prior_alpha + successes,
    prior_beta  + failures
)
```

Store:

```text
mean
lower_confidence_bound
upper_confidence_bound
sample_count
recent_performance
```

Selection may use lower confidence bounds rather than naive historical averages.

This belongs after the deterministic core is stable.

# 92. Final architecture

The completed system can therefore be summarized as:

```text
                    GRISP
                      │
          ┌───────────┼───────────┐
          │           │           │
          ▼           ▼           ▼
       AI WORKERS   TOOLS      POLICY
          │           │           │
          ▼           │           │
       AI RESPONSE    │           │
          │           │           │
          ▼           ▼           ▼
       ARTIFACT ─── EVIDENCE ─── AUTHORIZATION
          │
          ▼
    HARD ACCEPTANCE
          │
          ▼
    FINAL VERIFICATION
          │
          ▼
      TRANSACTION
          │
          ▼
        /final
```

and:

```text
GRISP
  │
  │ GARP/1.0
  ▼
Firefox AI Gateway
  │
  ├── DeepSeekAdapter
  ├── ChatGPTAdapter
  ├── GeminiAdapter
  ├── ClaudeAdapter
  ├── GrokAdapter
  └── future adapters
```

The result is not fundamentally a voting system.

It is:

```text
DETERMINISTIC ENGINEERING VERIFICATION
        +
UNTRUSTED AI REASONING
        +
CONTROLLED EXECUTION
        +
EXPLICIT POLICY
        +
CRYPTOGRAPHIC IDENTITY
        +
TRACEABLE EVIDENCE
        +
STATEFUL AI TRANSPORT
```

The central question at the end of every task becomes:

```text
Can GRISP prove that this exact artifact
was parsed,
authorized,
built,
executed,
tested,
verified,
and committed
without violating any acceptance invariant?
```

Only when the answer is deterministically **yes** does GRISP report:

```text
ACCEPTED
```

Anything else is:

```text
REJECTED
```

or an explicitly unverified draft outside `/final`.

That is the implementation design I would now use as the bridge between the existing architecture specification and the actual Delphi/Firefox codebase.
