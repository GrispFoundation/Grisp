## Sandbox Execution for Test Programs – Design and Implementation

The test adapter needs to execute arbitrary code – either compiled from test programs or directly run (if `--allow-llm-commands` is enabled). Without proper isolation, this code could delete files, access sensitive data, or compromise the host. We must implement a **sandbox** to mitigate these risks.

Below is a comprehensive plan, balancing security with practicality.

---

### 1. Principles of Sandboxing

- **Least Privilege** – The test process should run with the minimal permissions required.
- **Resource Limits** – Prevent DoS (CPU, memory, disk, network).
- **Temporary Workspace** – All files are ephemeral and disposed of after execution.
- **Network Isolation** – No external network access (unless explicitly required).
- **No Persistence** – All changes are discarded.

---

### 2. Sandbox Architecture Overview

The sandbox is implemented in `TGrispTestAdapterImpl.RunProcess` (the low‑level process launcher). It adds security layers before creating the child process.

```
┌─────────────────────────────────────────────────────┐
│                GRISP Agent Process                  │
│                                                     │
│  ┌─────────────────────────────────────────────┐    │
│  │        TGrispTestAdapterImpl                │    │
│  │  ┌──────────────────────────────────────┐   │    │
│  │  │         RunProcess                   │   │    │
│  │  │  - Create temp workspace             │   │    │
│  │  │  - Apply OS-level restrictions       │   │    │
│  │  │  - Launch process with low privilege │   │    │
│  │  │  - Monitor and enforce limits        │   │    │
│  │  └──────────────────────────────────────┘   │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

### 3. Implementation Options by Platform

#### **Windows** (Delphi)
- **Job Objects** – Create a job that limits CPU usage, process memory, and can terminate the process tree.  
- **User Account** – Run the process as a limited, non‑administrator user (e.g., `NETWORK SERVICE` or a dedicated local user).  
- **Desktop/Window Station** – Isolate the process from the interactive desktop (use `CREATE_NO_WINDOW`).  
- **File System** – Use a temporary directory under `%TEMP%` with restrictive ACLs (grant only the limited user).  
- **Network** – Use Windows Firewall or the `lpDesktop` parameter to deny network; simpler: use a local loopback‑only policy via `CreateProcess` with `CREATE_NO_WINDOW` and no network privileges (most child processes inherit the agent’s network access, so we need to restrict at the OS level; we can use a low‑integrity token with `SECURITY_MANDATORY_LOW_RID`).

**Windows Specifics:**  
- Use `CreateRestrictedToken` to strip administrative privileges.  
- Use `SetInformationJobObject` to set CPU and memory limits.  
- Example (pseudo‑code):
```pascal
// Create job object
hJob := CreateJobObject(nil, nil);
var limits: JOBOBJECT_EXTENDED_LIMIT_INFORMATION;
limits.BasicLimitInformation.LimitFlags := JOB_OBJECT_LIMIT_PROCESS_MEMORY or JOB_OBJECT_LIMIT_JOB_MEMORY or JOB_OBJECT_LIMIT_CPU_RATE;
limits.ProcessMemoryLimit := 512 * 1024 * 1024; // 512 MB
limits.JobMemoryLimit := 1 * 1024 * 1024 * 1024; // 1 GB
SetInformationJobObject(hJob, JobObjectExtendedLimitInformation, @limits, SizeOf(limits));
// Assign the process to the job
AssignProcessToJobObject(hJob, PI.hProcess);
```

---

#### **Linux / Unix** (FPC)
- **setrlimit** – Limit CPU time, memory, file size, number of processes.  
- **chroot** – Change root to a temporary, empty directory with only essential files (e.g., `/bin`, `/usr/lib` for compiler).  
- **User Namespace** – Use unprivileged user namespaces to map the process to a non‑root user.  
- **seccomp‑bpF** – Restrict syscalls to a safe subset (open, read, write, close, exit, etc.; block `execve`, `fork`, `socket`).  
- **Network** – Use `unshare(CLONE_NEWNET)` to create a private network namespace with only the loopback interface.  
- **Isolated Temp** – Create a temporary directory with `mkdtemp`, `chroot` into it, and drop privileges.

**Linux Example (FPC):**
```pascal
uses Unix;
// After fork, before exec:
// 1. Create temporary directory
DirName := '/tmp/grisp_' + IntToStr(GetPID);
mkdir(DirName, 0700);
// 2. chroot into it
if chroot(PChar(DirName)) <> 0 then ...
// 3. Set resource limits
rlim: TRLimit;
rlim.rlim_cur := 5;   // 5 seconds CPU
rlim.rlim_max := 5;
setrlimit(RLIMIT_CPU, @rlim);
// 4. Drop privileges (setuid to nobody)
setgid(65534);
setuid(65534);
// 5. Execute
execvp(...);
```

### 5. File System Isolation and Cleanup

- **Temporary Directory**: Always create a fresh, randomly‑named subdirectory under `%TEMP%` (Windows) or `/tmp` (Linux).  
- **Compiler/Interpreter Availability**: For the registry mode, we need the compiler executable inside the sandbox. We can either:
  - Copy the compiler into the sandbox (expensive) or
  - Mount/bind‑mount the compiler directory (Linux) or
  - Use the same executable path but ensure the process runs with limited privileges; the compiler itself might access files outside the sandbox but will be confined by the user’s permissions.
- **Cleanup**: Always delete the temporary directory (and its contents) after execution, using `try..finally` and ignoring errors.

---

### 6. Command Whitelist and Argument Sanitisation (LLM Mode)

When `--allow-llm-commands` is on, we must still prevent obvious attacks. In `ExecuteLLMCommand`, we already validate the executable against a whitelist and reject dangerous characters. Add additional checks:

- **Path Resolution**: Ensure the executable is an absolute path to a known safe location (e.g., `/usr/bin/gcc`, `C:\Program Files\...`).  
- **Argument Restriction**: Reject arguments that contain `..`, `|`, `>` or that try to access system directories.  
- **Timeouts**: Hard‑limit execution time (already in `RunProcess`).  
- **Input/Output**: Capture stdout/stderr; do not allow interactive input.

---

### 7. Default Policy

- **Sandboxing is optional** – By default, the agent runs with only basic process isolation (limited user) but **not** full chroot/container.  
- The user can enable `--sandbox` or `--container` (e.g., `--sandbox docker`) to use a Docker container or systemd‑nspawn for strong isolation.  
- For maximum security, the agent can be run inside its own container by the system administrator.

---

### 8. Implementation Roadmap

| **Phase** | **Feature** | **Platform** |
|-----------|-------------|--------------|
| 1 | Basic resource limits (CPU, memory) via Job Objects / setrlimit | Windows, Linux |
| 2 | Run as low‑privilege user (dedicated account) | Both |
| 3 | Temporary directory isolation and cleanup | Both |
| 4 | Command whitelist and argument sanitisation | Both |
| 5 | Chroot / network namespace (Linux) | Linux |
| 6 | Docker integration (optional) | Linux, Windows (WSL2) |
| 7 | Full containerisation with `systemd-nspawn` or `podman` | Linux |

---

### 9. Limitations and Risks

- **Kernel Exploits**: If the host kernel is vulnerable, a sufficiently sophisticated test could escape even a chroot.  
- **Compiler‑induced Risks**: The compiler itself might have vulnerabilities that could be exploited.  
- **Performance Overhead**: Containerisation adds startup latency.  
- **User‑mode Sandboxing** (Windows Job Objects, Linux `setrlimit`) is weaker than full containerisation; use only for trusted code.

---

### 10. Final Recommendation

- **Default**: Use OS‑level process isolation (Job Objects / setrlimit) with limited privileges and resource limits. This provides decent safety without extra dependencies.  
- **Optional**: Enable full containerisation (e.g., Docker) via a CLI flag. For example, `--sandbox docker` would invoke the test within a Docker container that has a minimal base image, no network, and a read‑only filesystem except the temp workspace.  
- **LLM Commands**: When `--allow-llm-commands` is used, force sandboxing on (i.e., ignore the flag if sandboxing is disabled). The user must explicitly enable both.

### Code Example: Sandboxing in `RunProcess` (Linux)

```pascal
{$IFDEF LINUX}
function RunProcessSandboxed(const CmdLine: string; var Output, Errors: string; var ExitCode: Integer): Boolean;
var
  PID: TProcessID;
  Dir: string;
begin
  // Create temporary directory
  Dir := '/tmp/grisp_' + IntToStr(GetTickCount64);
  mkdir(PChar(Dir), 0700);
  // Fork
  PID := fork;
  if PID = 0 then
  begin
    // Child
    // 1. chroot
    if chroot(PChar(Dir)) <> 0 then Halt(1);
    chdir('/');
    // 2. Drop privileges
    setgid(65534);
    setuid(65534);
    // 3. Set resource limits
    var rlim: TRLimit;
    rlim.rlim_cur := FConfig.TimeoutMs div 1000 + 1;
    rlim.rlim_max := rlim.rlim_cur;
    setrlimit(RLIMIT_CPU, @rlim);
    // 4. Execute
    execl('/bin/sh', 'sh', '-c', PChar(CmdLine), nil);
    Halt(1);
  end
  else
  begin
    // Parent: wait, read output from pipes, etc.
  end;
  // Cleanup
  rmdir(PChar(Dir));
end;
{$ENDIF}
```

*(Note: This is a simplified illustration; real code would need to handle pipes for I/O and error reporting.)*

### 11. Conclusion

The sandbox design provides a layered defence:  
1. **Resource limits** – prevents denial‑of‑service.  
2. **Privilege reduction** – limits file system access.  
3. **Filesystem isolation** – uses temporary workspaces.  
4. **Command validation** – in LLM mode, prevents dangerous commands.  
5. **Optional containerisation** – for ultimate isolation.

By implementing these measures, the agent can safely execute untrusted test programs while still allowing advanced flexibility when explicitly enabled. The risk of system compromise is significantly reduced, and the default (safe) mode ensures that even if a vulnerability exists, the impact is contained.

Windows Sandbox is an excellent choice for secure test execution. It provides a lightweight, disposable virtual machine that’s perfect for running untrusted code, and it’s built right into Windows 11 Pro and Enterprise editions.

## What Windows Sandbox Offers

Windows Sandbox creates a **clean, temporary Windows environment** that’s isolated from your host system. When you close it, everything is discarded – no traces remain on your machine.

The key features relevant to your agent are:

- **Folder sharing**: Map host directories into the sandbox with read or write permissions
- **Automated startup**: Run scripts or executables immediately when the sandbox launches
- **Programmatic control**: Launch and control sandboxes via command line
- **Network isolation**: Optionally disable network access for complete air-gapping

## How It Works

### 1. Configuration via `.wsb` Files

Windows Sandbox uses XML configuration files with a `.wsb` extension. Here’s a template that shares a folder and runs a test automatically:

```xml
<Configuration>
  <!-- Disable networking for maximum security -->
  <Networking>Disable</Networking>
  
  <!-- Share a folder from the host -->
  <MappedFolders>
    <MappedFolder>
      <HostFolder>C:\GRISP_Sandbox_Share</HostFolder>
      <ReadOnly>false</ReadOnly>
    </MappedFolder>
  </MappedFolders>
  
  <!-- Run the test program automatically on startup -->
  <LogonCommand>
    <Command>C:\GRISP_Sandbox_Share\run_test.bat</Command>
  </LogonCommand>
</Configuration>
```

You can also share folders **at runtime** through the Sandbox UI by clicking the three dots (⋮) icon and selecting "Share folder".

### 2. Programmatic Control via CLI

Windows Sandbox includes a command-line interface (`wsb.exe`) that allows full automation:

```cmd
:: Start a sandbox with a configuration file
wsb.exe start --config "C:\path\to\test.wsb"

:: List running sandboxes
wsb.exe list

:: Execute a command inside a running sandbox
wsb.exe exec --id <sandbox-id> --command "test.exe --verbose"

:: Stop a sandbox
wsb.exe stop --id <sandbox-id>
```

### 3. Integration with Your Agent

**Step 1: Prepare the Test Environment**

The agent creates a temporary workspace on the host:

```
C:\GRISP_Sandbox_Share\
├── test.exe          (compiled test program)
├── test.pas          (source code, for reference)
└── run_test.bat      (launcher script)
```

The `run_test.bat` script executes the test and captures output:

```batch
@echo off
test.exe > output.txt 2>&1
echo %ERRORLEVEL% > exitcode.txt
```

**Step 2: Generate a `.wsb` File Dynamically**

The agent writes a temporary `.wsb` file with the sandbox configuration, including the shared folder path and the logon command.

**Step 3: Launch and Monitor**

The agent launches the sandbox, waits for the test to complete, then reads the output files from the shared folder before cleaning up.

## Security Considerations

Folder sharing is the **primary security concern** – it creates a bridge between the sandbox and your host. Here’s how to stay safe:

| **Risk** | **Mitigation** |
|----------|----------------|
| Malware escapes via shared folder | Use **read‑only** sharing where possible; write results to a dedicated output folder with restricted permissions |
| Malware modifies shared files | Use `ReadOnly>true</ReadOnly>` in the `.wsb` for the source folder |
| Network-based attacks | Disable networking with `<Networking>Disable</Networking>` |
| Clipboard data leakage | Disable clipboard sharing with `<ClipboardRedirection>Disable</ClipboardRedirection>` |
| Host compromise via printer redirection | Disable printer redirection with `<PrinterRedirection>Disable</PrinterRedirection>` |

### Best Practice: Two-Folder Strategy

Create two shared folders:
1. **Read‑only input folder**: Contains the test executable and any input files
2. **Write‑only output folder**: Where the sandbox writes results (logs, exit codes)

This prevents the sandbox from modifying the test program itself while still allowing result capture.

```pascal
function TGrispTestAdapterImpl.ExecuteInWindowsSandbox(
  const TestProgram: TTestProgram; 
  out Feedback: TDebugFeedback): Boolean;
var
  WorkspaceDir, WsbPath, BatPath: string;
  WsbContent: TStringList;
  Output, Errors: string;
  ExitCode: Integer;
begin
  // 1. Create workspace on host
  WorkspaceDir := 'C:\GRISP_Sandbox_Share\' + GUIDToString(CreateGUID);
  CreateDir(WorkspaceDir);
  
  // 2. Write test executable and launcher script
  WriteTestFiles(WorkspaceDir, TestProgram);
  
  // 3. Generate .wsb configuration
  WsbContent := TStringList.Create;
  try
    WsbContent.Add('<Configuration>');
    WsbContent.Add('  <Networking>Disable</Networking>');
    WsbContent.Add('  <MappedFolders>');
    WsbContent.Add('    <MappedFolder>');
    WsbContent.Add('      <HostFolder>' + WorkspaceDir + '</HostFolder>');
    WsbContent.Add('      <ReadOnly>false</ReadOnly>');
    WsbContent.Add('    </MappedFolder>');
    WsbContent.Add('  </MappedFolders>');
    WsbContent.Add('  <LogonCommand>');
    WsbContent.Add('    <Command>' + WorkspaceDir + '\run_test.bat</Command>');
    WsbContent.Add('  </LogonCommand>');
    WsbContent.Add('</Configuration>');
    WsbPath := WorkspaceDir + '\test.wsb';
    WsbContent.SaveToFile(WsbPath);
  finally
    WsbContent.Free;
  end;
  
  // 4. Launch sandbox and wait for completion
  //    (Use CreateProcess with wsb.exe start --config "..." and monitor)
  if not LaunchSandboxAndWait(WsbPath, FConfig.TimeoutMs) then
  begin
    Feedback := TDebugFeedback.MakeFailure('Sandbox execution timed out');
    Exit(False);
  end;
  
  // 5. Read results from shared folder
  ReadTestResults(WorkspaceDir, Output, Errors, ExitCode);
  
  // 6. Clean up
  DeleteDirectory(WorkspaceDir);
  
  // 7. Build feedback
  Feedback := TDebugFeedback.MakeSuccess('Test executed in Windows Sandbox');
  Feedback.TestOutput := Output;
  Feedback.TestExitCode := ExitCode;
  Feedback.TestPassed := (ExitCode = 0);
  Result := True;
end;
```

## Windows Sandbox Reuse and AI Risk Assessment – Recommendations & Implementation

### 1. Reusing a Running Windows Sandbox

**Yes, reusing a sandbox is highly advisable** – it avoids the overhead of creating a new VM for each test, reduces SSD wear, and speeds up test execution.

Windows Sandbox **does not natively support** persistent reuse. However, we can **work around it** by:

- Starting a sandbox with a **long‑running listener** inside (a simple script that waits for commands from the host).
- Using a **shared folder** as a communication channel:
  - The host writes a command file (e.g., `cmd.txt`) into the shared folder.
  - The sandbox has a loop that checks for new commands, executes them, and writes the results to a result file.
- The sandbox remains alive indefinitely (or until the agent exits).

#### Implementation Strategy

1. **Create a persistent sandbox configuration** (`.wsb`):
   - Shares a **dedicated host folder** (e.g., `C:\GRISP_Sandbox_Workspace`).
   - Runs a **listener script** (`listener.bat`) on startup.

2. **Listener Script (`listener.bat`)** inside the sandbox:
   ```batch
   @echo off
   :loop
   if exist C:\GRISP_Share\cmd.txt (
       set /p cmd=<C:\GRISP_Share\cmd.txt
       %cmd% > C:\GRISP_Share\stdout.txt 2> C:\GRISP_Share\stderr.txt
       echo %ERRORLEVEL% > C:\GRISP_Share\exitcode.txt
       del C:\GRISP_Share\cmd.txt
   )
   timeout /t 1 /nobreak >nul
   goto loop
   ```

3. **Host‑side manager** (`TWindowsSandboxManager`):
   - Starts the sandbox once (via `wsb.exe start --config "sandbox.wsb"`).
   - For each test, writes the command (e.g., `test.exe`) to `cmd.txt`, waits for the result files to appear, reads them, and returns the output.
   - Keeps the sandbox running for the entire agent session.
   - On agent shutdown, stops the sandbox (`wsb.exe stop`).

#### Benefits
- **No repeated VM creation** – only one sandbox per agent session.
- **Fast execution** – command turnaround is near‑instant (just file I/O).
- **Resource‑efficient** – memory/CPU usage is constant.

#### Risks & Mitigations
- **Command injection** – the host writes commands; we must sanitize them.
- **Stale commands** – implement a time‑out mechanism to detect hangs.
- **Sandbox crash** – the manager should detect if the sandbox dies and restart it.

### 2. AI Risk Assessment – To Use or Not to Use?

Your idea – **ask the AI how risky it is** – is creative but **not recommended** as a primary security control.

#### Why It’s Problematic

| **Issue** | **Explanation** |
|-----------|-----------------|
| **AI is not a security oracle** | LLMs have no direct understanding of system vulnerability; they can be easily fooled or give false confidence. |
| **Adversarial prompts** | An attacker could craft a test that the AI mistakenly deems safe. |
| **Decision fatigue** | The user still must trust the AI’s judgment, which undermines the purpose of having explicit security controls. |
| **No audit trail** | An AI’s “low risk” assessment is not a defensible security policy. |

#### A Better Approach: **User‑Controlled Policy**

Provide clear, user‑set flags:

| **Flag** | **Behaviour** |
|----------|---------------|
| `--sandbox never` | Run tests directly on host (fastest, least secure). |
| `--sandbox always` | Always use the reusable Windows Sandbox. |
| `--sandbox auto` | Use sandbox only if `--allow-llm-commands` is enabled (default). |

This puts control in the hands of the user, where it belongs.

#### Optional – AI‑Assisted Recommendation (Not Enforcement)

We could *display* an AI‑generated risk assessment in the log for informational purposes, but **not** use it to make a security decision. For example:

```
[INFO] AI risk assessment: This test uses file I/O and network calls. Consider using --sandbox always.
```

The user still decides.

### The Core Limitation

The `.wsb` configuration file **does not** support changing this path. There is no `VhdxPath` or `ImagePath` element in the XML schema.

### Workarounds

#### 1. Symbolic Link (Most Practical)

Redirect the VHDX file to a RAM disk or another drive using a directory junction:

```powershell
# Stop any running sandbox first
# Move the original VHDX
move C:\Windows\System32\WindowsSandbox.vhdx D:\SandboxCache\

mklink C:\Windows\System32\WindowsSandbox.vhdx D:\SandboxCache\WindowsSandbox.vhdx
```

Then mount `D:\SandboxCache` on a RAM disk (using ImDisk, OSFMount, etc.). The sandbox will use the VHDX from the RAM disk location.

---

Instead of moving the entire sandbox image, place only the **shared test workspace** on a RAM disk:

```xml
<Configuration>
  <MappedFolders>
    <MappedFolder>
      <HostFolder>R:\SandboxWorkspace</HostFolder>   <!-- R: is RAM disk -->
      <ReadOnly>false</ReadOnly>
    </MappedFolder>
  </MappedFolders>
</Configuration>
```

**Benefits**:
- All test files (source code, executables, outputs) live in RAM – extremely fast I/O
- Zero SSD wear from test execution
- No risk of breaking Windows Sandbox itself

**Trade-off**: The sandbox OS image still resides on the SSD, but that's a one-time ~500 MB read. The heavy write activity (test compilation, logs, outputs) goes to the RAM disk.

---

Create the sandbox VHDX on a RAM disk, then use it as a custom VM in Hyper-V Manager:

```powershell
New-VM -Name "SandboxVM" -MemoryStartupBytes 4GB -Generation 2 `
  -NewVHDPath "R:\SandboxVM.vhdx" -NewVHDSizeBytes 50GB
```

Then launch it with:
```powershell
Start-VM -Name "SandboxVM"
```

**Limitation**: This is a full Hyper-V VM, not a Windows Sandbox instance. It lacks the "wipe on close" convenience and dynamic memory features.

- **Share folders** with a running sandbox: `wsb share --id <id> -f <host-folder> -s <sandbox-folder>`

This would allow you to **reuse a single sandbox** across multiple tests – exactly what you wanted to avoid SSD wear.

## The Dealbreakers

### 1. **No Process I/O** – The Big One

> *"Currently, there is no support for process I/O meaning that there is no way to retrieve the output of a command run in Sandbox."*

This means `wsb exec` **cannot capture stdout or stderr**. You only get the exit code. For an AI agent that needs to know whether tests passed, what errors occurred, or what the test output was, this is a non‑starter.

### 2. **Requires an Active User Session**

> *"An active user session is required to execute a command in the context of the currently logged on user. Therefore, before running this command a remote desktop connection should be established."*

You'd need to connect via RDP first (`wsb connect`), which complicates headless automation.

### 3. **Headless Execution is "Attack‑Like"**

According to security research, running `wsb exec -r System` without an interactive RDP session creates a "server‑without‑remote‑session" state that is considered a high‑signal indicator of headless abuse. While not a technical blocker, it suggests this path may be restricted or monitored in enterprise environments.

## Alternatives That Actually Work

### Option A: Shared Folder + Listener (What We Discussed Previously)

This remains the **most reliable** approach:

1. Start the sandbox once with a shared folder mapped
2. Place a listener script (`listener.bat`) that runs via `<LogonCommand>`
3. The host writes commands to `cmd.txt` in the shared folder
4. The listener executes them and writes results back to `stdout.txt` / `stderr.txt`
5. The host reads the results

This **works today**, captures full stdout/stderr, and requires no RDP session. The only downside is the ~1‑2 second polling delay.

### Option B: `wsb.exe` + Shared Folder (Hybrid)

You could use `wsb exec` to **trigger** the listener (e.g., `wsb exec -r System -c "listener.exe"`) but still rely on the shared folder for I/O. This avoids the polling loop inside the sandbox but doesn't solve the output capture problem.

### Option C: Third‑Party Tools

Several projects wrap `wsb.exe` with better APIs:
- **[wsbx](https://github.com/gifnksm/wsbx)** – A type‑safe Rust API for controlling Windows Sandbox
- **[pywinsandbox](https://github.com/karkason/pywinsandbox)** – Python utilities for Windows Sandbox
- **Windows Sandbox MCP** – An experimental .NET tool for programmatic management

These may offer better I/O handling, but they are third‑party and not officially supported.

## Recommendation for Your Agent

| **Approach** | **Pros** | **Cons** |
|--------------|----------|----------|
| **Shared folder + listener** | Works today, full I/O, no RDP | 1‑2s polling delay |
| **`wsb exec`** | Direct command execution | **No I/O capture**, requires RDP session |
| **Third‑party wrappers** | Potentially cleaner API | Unsupported, may break with Windows updates |

If you really want to use `wsb exec`, you could combine it with shared folders: use `wsb exec` to launch the test (avoiding the listener loop), but still write output to the shared folder for the host to read. This reduces the polling requirement inside the sandbox but still relies on the shared folder for I/O.

When you start a Windows Sandbox, it does not write directly to `C:\Windows\System32\WindowsSandbox.vhdx`. Instead, it uses that file as a **read‑only base image** and creates a new **writeable differencing disk** (a child VHDX) in your temporary folder. ### The Real Source of SSD Wear

- **Base Image**: Read once during boot. Negligible wear.
- **Differencing Disk**: Created on every sandbox launch. **This is the heavy write operation** that causes SSD wear, because every byte written inside the sandbox is actually written to this differencing disk (which lives on your physical SSD by default).

### Where Does This Differencing Disk Live?

By default, Windows Sandbox places the differencing disk in:

```
%USERPROFILE%\AppData\Local\Temp
```

or the system‑wide `%TEMP%` folder (usually `C:\Windows\Temp` or `C:\Users\[User]\AppData\Local\Temp`).

If you redirect the `%TEMP%` environment variable to a RAM disk, the differencing disk will be created **entirely in RAM**, eliminating all write‑wear from sandbox launches and test executions.

### How to Move the Differencing Disk to a RAM Disk (Properly)

This is the **correct** way to solve the wear problem. It is safe, reversible, and doesn't involve moving or replacing system files.

#### Step 1: Create a RAM Disk (e.g., `R:`)

Use ImDisk Toolkit, OSFMount, or your preferred RAM disk tool. Assign it a drive letter, e.g., `R:`. Create a folder for temporary files:
```cmd
mkdir R:\Temp
```

1. Open **System Properties** → **Advanced** → **Environment Variables**.
2. Under **User variables**, find `TEMP` and `TMP`. If they exist, edit them to `R:\Temp`. If not, create new ones.
3. Log off and log back in (or restart the GRISP Agent process).

**Option B: Set it via Command Prompt (Temporary, for the current session):**
```cmd

```

If the sandbox still creates the differencing disk on `C:`, you may need to change the **system‑wide** TEMP variable. This affects all applications, so be cautious.

1. Open Command Prompt **as Administrator**.
2. Set the system TEMP variables:
   ```cmd
   setx /M TEMP R:\Temp
   setx /M TMP R:\Temp
   ```
3. **Restart your computer** for the changes to take effect.

2. While it's running, open Task Manager → Performance → Open Resource Monitor → Disk tab.

### ❓ Why `%TEMP%` Doesn't Work Anymore

The older versions of Windows Sandbox used a single VHDX file that was created and discarded, which is why redirecting `%TEMP%` was a valid solution. In Windows 11 23H2, the architecture changed to use Windows Containers technology. The sandbox now runs as a containerized instance, and its files are stored in the `Containers` system folder instead of a temporary user folder.

### ❌ Why Solution 1 (Windows Sandbox Symlink) is a Bad Idea

**1. It will likely fail on modern Windows 11 anyway**
The guide even mentions this: *"if Windows 11's vmcompute service rejects the symlink due to hardcoded ACL security checks."* In current Windows 11 builds (especially 24H2 and later), Microsoft has hardened `vmcompute.exe` precisely to prevent this kind of tampering. When you try to start the service, it will likely throw an `Access Denied` or `Element not found` error, and the Sandbox simply won't boot. 

**2. It will break Windows Updates and Feature Updates**
The `C:\ProgramData\Microsoft\Windows\Containers` folder is not just for the Sandbox—it stores the base OS images used by *all* container features (WSL2, Docker, Defender Application Guard, etc.). Windows Update expects this path to be a stable system directory on an NTFS drive. Redirecting it to a RAM disk will cause cumulative updates or major feature updates to fail mid-installation, potentially leaving your OS in a corrupted, unpatched state.

**3. The "Reboot Hazard" is a nightmare**
The guide warns about this, but understates the risk. If your PC crashes, bluescreens, or loses power, your RAM disk (`R:`) disappears. On the next boot, `vmcompute` will try to start and see that `C:\ProgramData\Microsoft\Windows\Containers` points to a drive that doesn't exist. **This will prevent Hyper-V, WSL2, and Windows Sandbox from starting at all.** Fixing this requires booting into Windows Recovery Environment (WinRE) via a USB stick to manually delete the broken symlink—a massive hassle for the average user.

**4. It defeats the purpose (RAM vs. SSD)**
The container base layer is roughly **5–8 GB**. To hold this, your RAM disk must be at least that large, permanently eating up that much system RAM. If you have 16 GB of RAM total, you'll only have ~8 GB left for Windows and the actual running VM. When that runs out, Windows will aggressively page memory to your SSD's pagefile.sys—**causing even more SSD writes than if you had just left the Sandbox alone.**

Here is why this is **completely safe and recommended** compared to the Windows Sandbox hack:

- **No kernel services touched**: Sandboxie runs at the user-mode file system level. Moving its root folder to a RAM disk does not affect Windows system services, Hyper-V, or WSL2. 
- **Zero reboot risk**: If your RAM disk disappears on reboot, Sandboxie simply throws a "Folder not found" error when you try to launch a box. It **will not** crash your host OS or prevent your computer from booting. You just recreate the RAM disk and carry on.
- **Granular control**: You don't need to move the entire 8 GB base image. You only move the *differencing layers* (the changes made during that session), which are typically a few hundred MBs at most. This achieves your goal (eliminating SSD writes for temporary sandbox data) without consuming massive amounts of physical RAM.
