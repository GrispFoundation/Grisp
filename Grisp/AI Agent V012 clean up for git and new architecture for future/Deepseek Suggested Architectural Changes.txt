## Architectural Changes to Improve the AI Agent

### The Core Problems
- **Language agnosticism** – no language preference is stored or propagated, so all peers default to C.
- **Tests not derived from actual code** – peers generate generic division tests regardless of repair content.
- **Fake test execution** – the test adapter only simulates compilation/runtime, no real compiler integration.
- **Capability negotiation** is rudimentary and does not consider language or code complexity.
- **Resource leaks** and fragile ownership make the codebase error‑prone.

These issues require architectural shifts – not just tactical fixes.

---

## Proposed Architectural Improvements

### 1. Introduce a `TAgentConfiguration` Object
Centralize all runtime settings in a single, immutable configuration record passed to the agent and its components.

```pascal
type
  TAgentLanguage = (alPascal, alDelphi, alC, alPython, alUnknown);

  TAgentConfiguration = record
    PreferredLanguage: TAgentLanguage;
    PreferredCompiler: string;          // e.g., 'fpc', 'dcc32', 'gcc'
    CompilerPath: string;
    RunSandboxed: Boolean;
    MaxTestRuns: Integer;
    GenerateTests: Boolean;
    TraceLevel: Integer;
  end;
```

**Benefits:**
- Clean separation of concerns – the CLI parses flags into this config, then passes it to the agent.
- All peers and adapters can query the config to make language‑aware decisions.
- Future extensions (e.g., timeouts, resource limits) are straightforward.

---

### 2. Redesign the Peer Interfaces to Be Language‑Aware
Currently `IWebLLMPeer` has methods without language parameters. Change them to accept the configuration or a language hint.

```pascal
type
  IWebLLMPeer = interface
    ['{...}']
    function GetName: string;
    function GenerateCandidate(const UserPrompt: string; const Config: TAgentConfiguration): TCandidate;
    function CritiqueCandidate(const UserPrompt: string; const Candidate: TCandidate; const Config: TAgentConfiguration): TCritique;
    function RepairCandidate(const UserPrompt: string; const Candidate: TCandidate; const Critiques: TArray<TCritique>; const Config: TAgentConfiguration): TRepair;
    function RequestCapabilities(const UserPrompt: string; const Repairs: TArray<TRepair>; const Config: TAgentConfiguration): TArray<TCapabilityRequest>;
    function ProposeTestProgram(const UserPrompt: string; const Repair: TRepair; const Config: TAgentConfiguration): TTestProgram;
    function ScoreRepairs(const UserPrompt: string; const Candidates: TArray<TCandidate>;
      const Repairs: TArray<TRepair>; const Debugs: TArray<TDebugFeedback>; const Config: TAgentConfiguration): TArray<TScore>;
  end;
```

**Consequences:**
- Each peer can adapt its prompts to the target language and compiler.
- The heuristic peer can generate language‑specific code templates.
- The Firefox peer can instruct the LLM to output code in the specified language.

---

### 3. Replace the Stub Test Adapter with a Real, Compiler‑Integrated Harness
The `IGrispTestAdapter` should actually compile and run tests using the system compiler. This requires **capability‑controlled access** to the host environment.

**New architecture:**
- Introduce a `TGrispCompilerRegistry` that knows how to invoke each compiler (FPC, Delphi, GCC, Python, etc.) with appropriate flags.
- The adapter receives the target language and the test code, writes it to a temporary file in the VFS (or physical sandbox), invokes the compiler, captures output, runs the executable, and returns detailed feedback.

```pascal
type
  TCompilerKind = (ckFreePascal, ckDelphi, ckGCC, ckPython);

  ICompiler = interface
    function Compile(const SourcePath, OutputPath: string; var Errors: string): Boolean;
    function Run(const ExePath: string; var StdOut, StdErr: string; var ExitCode: Integer): Boolean;
  end;

  TGrispCompilerRegistry = class
    function GetCompilerForLanguage(Lang: TAgentLanguage; const Config: TAgentConfiguration): ICompiler;
  end;

  TGrispRealTestAdapter = class(TInterfacedObject, IGrispTestAdapter)
  private
    FRegistry: TGrispCompilerRegistry;
    FVfs: IGrispVfs;
    FConfig: TAgentConfiguration;
  public
    function CompileAndRunTest(const RealPath, Language: string; out Feedback: TDebugFeedback): Boolean;
    function RunQuickCheck(const RealPath, Language: string; out Feedback: TDebugFeedback): Boolean;
  end;
```

**Why this matters:**
- Real errors (syntax, linker, runtime) are captured and used to adjust peer reliability.
- The agent can iterate repairs based on actual compilation failures.
- The “external score” in the scoring algorithm becomes trustworthy.

---

### 4. Refactor Test Generation to Be Code‑Aware
Instead of peers generating generic tests, they should analyse the repair code to extract **function signatures, potential edge cases, and invariants**.

**Architectural addition:**
- A lightweight static analyser component (`TGrispCodeAnalyzer`) that inspects the repair’s Abstract Syntax Tree (or uses regex heuristics) to identify:
  - Function names, parameter types, return types.
  - Arithmetic operations, array accesses, pointer dereferences.
  - Conditional branches that could throw exceptions.
- The analysis results are serialised and injected into the test‑generation prompt.

```pascal
type
  TFunctionSignature = record
    Name: string;
    Params: TArray<string>;
    ReturnType: string;
  end;

  TCodeAnalysis = record
    Functions: TArray<TFunctionSignature>;
    HasDivision: Boolean;
    HasArrayAccess: Boolean;
    HasPointerDeref: Boolean;
  end;

  IGrispCodeAnalyzer = interface
    function Analyze(const Code, Language: string): TCodeAnalysis;
  end;
```

Then `ProposeTestProgram` is called with the analysis:

```pascal
function ProposeTestProgram(const UserPrompt: string; const Repair: TRepair;
  const Analysis: TCodeAnalysis; const Config: TAgentConfiguration): TTestProgram;
```

This yields **tests that actually exercise the specific functions** in the repair, not just division‑by‑zero.

---

### 5. Enhance Capability Negotiation with Language and Complexity
`NegotiateCapabilities` should consider:
- The **target language** – some compilers need specific capabilities (e.g., `test_execute` may require a runtime environment).
- The **complexity** of the repair – simple fixes may not warrant deep debugging; complex ones do.
- The **risk profile** – if the code contains low‑level operations, demand `stack_trace` and `debug` capabilities.

**Change the signature:**
```pascal
function NegotiateCapabilities(const Requests: TArray<TCapabilityRequest>;
  const Config: TAgentConfiguration; const Analysis: TCodeAnalysis): TArray<string>;
```

This allows the negotiation to be dynamic and context‑aware.

---

### 6. Introduce a Centralised Logger and Trace Store
The current `TProtocolTrace` stores everything, but it’s only created after execution. For debugging and auditing, it’s better to have a **logging service** that records all phases incrementally, with configurable verbosity.

```pascal
type
  IAgentLogger = interface
    procedure LogPhase(Phase: Integer; const Data: string);
    procedure LogEvent(const EventName: string; const Payload: TArray<string>);
    function GetTraceJSON: string;
  end;
```

The agent and its components can inject log entries at each step, making it easier to diagnose why tests are C‑based or why compilation failed.

---

### 7. Refactor Memory Ownership with Managed Containers
The current `TAction.Params` leaks because the parser owns the `TStringList` but the caller never frees it. Adopt a **single ownership rule** with a helper `FreeRuleArray` that recursively frees all nested objects.

Better yet, use **interfaces for collections** (e.g., `IInterfaceList`) or **record‑based dynamic arrays** with automatic cleanup using `TArray` and `TList<T>` (which can be freed). However, Pascal’s record semantics require explicit cleanup. The simplest architectural change is to **encapsulate actions in a class** that owns its `Params` and provides a `Free` method, or to use the `FreeRuleArray` pattern consistently.

**Recommended:** Define `TAction` as a class instead of a record. Then the parser creates instances, and the caller has a `TList<TAction>` that can be freed. This simplifies ownership and makes it clear that every `TAction` must be freed.

---

### 8. Make the VFS Compiler‑Aware
The VFS currently stores files and MIME types. Add a metadata field for **language** or **compiler flags**. When a test is written, the adapter can later query the VFS to know how to compile it without relying on the extension alone.

```pascal
TGrispVfsEntry = record
  ...
  Language: string;  // 'pascal', 'c', 'python'
  CompilerFlags: string;
end;
```

The test adapter can then pass these flags to the compiler registry.

---

### 9. Support Multiple Compilers and Versions
The registry should be able to handle different compiler paths and versions. For example, Free Pascal (fpc) vs. Delphi (dcc32) have different command‑line options. The configuration can specify the compiler executable and any default flags.

---

### 10. Integrate with the GRISP Graph for Test Results
Currently, test results are only stored in `TProtocolTrace`. To enable long‑term learning, store test outcomes as **nodes/edges** in the GRISP graph. For example, create a `TestResult` node for each test run, linked to the repair and the peer that generated it. This allows the agent to later query past performance and adapt peer reliability more accurately.

---

## Summary of Architectural Changes

| **Component**                | **Current Issue**                                   | **Architectural Change**                                                            |
|------------------------------|-----------------------------------------------------|-------------------------------------------------------------------------------------|
| **Configuration**            | No language/compiler settings                       | Introduce `TAgentConfiguration` passed to all components                            |
| **Peer Interface**           | Language‑agnostic methods                           | Add `Config` parameter to all methods                                               |
| **Test Adapter**             | Simulated compilation                               | Replace with real `ICompiler` registry and execution                                |
| **Test Generation**          | Generic C division tests                            | Use static analyser to extract function signatures; pass analysis to peers          |
| **Capability Negotiation**   | Fixed threshold, no language/complexity             | Include `Config` and `Analysis`; make decision dynamic                             |
| **Logging**                  | Only final trace                                    | Introduce incremental logging service                                               |
| **Memory Management**        | Leaks due to manual `TStringList` ownership         | Use classes with explicit `Free` or `FreeRuleArray`; consider `TList<TAction>`     |
| **VFS**                      | Only MIME, no compiler metadata                     | Add `Language` and `CompilerFlags` fields                                           |
| **Graph**                    | Only used for runtime state                         | Store test results as graph nodes for learning                                     |

## Implementation Roadmap (Phased)

1. **Phase 1 – Foundation** (2–3 days)  
   - Implement `TAgentConfiguration` and CLI parsing.  
   - Update all peer interfaces and implementations to accept `Config`.  
   - Add `TGrispCodeAnalyzer` with simple regex‑based analysis.

2. **Phase 2 – Real Test Harness** (3–4 days)  
   - Implement `TGrispCompilerRegistry` and `ICompiler` for FPC and GCC.  
   - Replace the test adapter with the real one.  
   - Integrate compilation/runtime feedback into scoring.

3. **Phase 3 – Language‑Aware Test Generation** (2–3 days)  
   - Modify `ProposeTestProgram` to use the analysis results.  
   - Update `THeuristicPeer` and `TFirefoxChatAIPeer` to generate language‑specific tests.

4. **Phase 4 – Enhanced Capability Negotiation** (1 day)  
   - Modify `NegotiateCapabilities` to consider language and analysis.

5. **Phase 5 – Observability and Memory** (1 day)  
   - Add `IAgentLogger`.  
   - Refactor action ownership with `FreeRuleArray` or classes.

6. **Phase 6 – Graph Integration** (1–2 days)  
   - Store test results in the graph for future learning.

---

## Expected Outcomes
- The agent will produce **tests in the correct language** (Delphi/Pascal) that **exercise the actual functions** in the repair.
- Compilation and runtime errors will be detected **accurately**, leading to **more reliable peer reliability updates**.
- The agent becomes **extensible** to new languages and compilers with minimal effort.
- Memory leaks and fragile resource handling are eliminated.

These changes turn the agent from a proof‑of‑concept into a production‑ready tool for multi‑language software repair and testing.
