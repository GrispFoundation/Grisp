### Short verdict
You *can* start by asking an AI model alone, and that will yield quick, often useful tests. But for **reliable, repeatable, language‑correct** test generation—especially for Delphi/Pascal in a multi‑LLM repair loop—the **hybrid** approach (syntactic extraction via Tree‑sitter plus targeted LLM prompting) gives the best tradeoff between engineering effort and quality. It reduces hallucination, ensures tests call the actual functions, and still leverages LLM creativity for test design.

---

### Why AI only is tempting and where it fails
- **Pros**
  - Very fast to get working: just craft prompts and call the model.
  - Flexible: model can invent test styles, harnesses, and edge cases.
- **Cons**
  - **Hallucination risk**: LLMs may invent function names, wrong signatures, or produce tests in the wrong language.
  - **Non‑deterministic**: different runs may produce inconsistent tests.
  - **Hard to validate automatically**: you need extra checks to ensure the test compiles and actually exercises the repair.

---

### Why Tree‑sitter/LSP (or at least Tree‑sitter) helps
- **Deterministic facts**: extract exact function/procedure names, parameter lists, and locations of risky ops (division, array access).
- **Better prompts**: include concrete signatures and risky sites so the LLM writes tests that call the real code.
- **Lower hallucination**: the LLM is constrained by real code facts rather than inventing them.

---

### Practical hybrid workflow I recommend
1. **Extract syntactic facts** with Tree‑sitter (or a simple regex fallback if you must): function names, params, return types, risky operators, public vs private markers.  
2. **Build a compact code summary** (2–6 bullets) and a small table of signatures.  
3. **Send a structured prompt** to the LLM that includes the summary, signatures, target language, and desired test harness (DUnit or simple assertions).  
4. **Compile and run** the generated test in a sandboxed adapter; capture diagnostics.  
5. **Feed back** compiler/runtime output to the LLM for iterative repair/test refinement.

---

### Minimal structured prompt you can use right away
```text
Language: Pascal (Free Pascal)
Code summary:
- Functions: safe_divide(a: Integer; b: Integer): Integer
- Risky ops: division at line 42; no explicit null checks
- Public functions to test: safe_divide

Requirements:
- Produce a single self-contained Pascal test file compilable with fpc.
- Include normal and edge cases (e.g., b = 0, negative values).
- Use simple assertions or print PASS/FAIL lines.
- Keep the test minimal and runnable without external libraries.

Provide only the test source code in your reply.
```

---

### When AI only is acceptable
- Small, exploratory tasks where speed matters and occasional hallucination is tolerable.
- Human‑in‑the‑loop workflows where a developer will inspect and adapt tests manually.
- Prototyping or when you lack parser/LSP resources for the language.

---

### When hybrid is essential
- Automated repair pipelines where tests gate acceptance and must be machine‑verifiable.
- Multi‑LLM cross‑repair where peers must agree on concrete, language‑correct tests.
- Environments requiring reproducibility and auditability (CI, safety‑critical code).

### Quick implementation plan (practical, low friction)
