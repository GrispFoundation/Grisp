# 🧱 GRISP Virtual Filesystem Design  
The GRISP VFS is built around one core idea:

> **The AI never sees the real filesystem.  
> It only sees a graph of nodes it has explicit capabilities for.**

This eliminates the exact problems you saw in DeepSeek Harness:  
path confusion, sandbox bypass, privilege escalation, hallucinated tool calls.

---

## 🧩 1. **Graph‑Native Structure (G‑Blocks as Files)**
Instead of directories and files, GRISP uses **G‑Blocks**:

- A file is a G‑Block  
- A directory is a G‑Block  
- A workspace is a G‑Block  
- A capability envelope is a G‑Block  

Each block has:

- **type** (file, dir, capability, rule, etc.)
- **edges** (contains, parent, allowed‑write, allowed‑read)
- **metadata** (size, MIME, permissions)
- **content** (byte array or structured graph)

This means the filesystem is **not hierarchical** — it is **graph‑structured**.

This prevents:

- `..` traversal  
- drive‑letter confusion  
- absolute path escapes  
- POSIX vs Windows mismatch  

---

## 🔐 2. **Capability‑Bound Access**
Every operation requires a **capability token**.

A capability token contains:

- allowed operations: read, write, list, delete  
- allowed block types: file, dir  
- allowed path roots: `/workspace`, `/sandbox`  
- allowed size limits  
- allowed MIME types  
- allowed rewrite rules  

If the model tries:

```
write("/workspace/../secret.txt")
```

GRISP checks:

- Does the capability allow traversal? → No  
- Does the path normalize inside workspace? → No  
- Does the block exist? → No  
- Is the operation allowed? → No  

→ **Operation rejected. No escalation possible.**

---

## 📁 3. **Canonical Path Normalization**
GRISP normalizes all paths into a canonical form:

- No drive letters  
- No UNC paths  
- No absolute roots  
- No backslashes  
- No mixed separators  
- No symbolic links  
- No `..`  
- No `.`  

Example:

User gives:  
`G:\workspace\test.txt`

Model gives:  
`/workspace/test.txt`

GRISP normalizes both to:  
`/workspace/test.txt`

If normalization escapes the capability root → **reject**.

This prevents the exact Harness bug where:

- `/sandbox/helloworld.pas` → `G:\sandbox\helloworld.pas`
- `/workspace/test.txt` → `G:\workspace\test.txt`

GRISP simply **does not allow OS path interpretation**.

---

## 🧪 4. **Virtualized Storage Backend**
GRISP stores file content in:

- memory  
- embedded graph nodes  
- encrypted blobs  
- or a real backend (optional)

But the model **never knows** where the data actually lives.

This prevents:

- real disk writes  
- real path exposure  
- real permission escalation  
- real OS interaction  

The model only sees **graph nodes**, not files.

---

## 🧠 5. **Deterministic Tool Invocation**
DeepSeek Harness fails because the model:

- hallucinates tool calls  
- misinterprets greetings  
- escalates privileges  
- writes files without instruction  

GRISP solves this by:

- requiring explicit **intent blocks**  
- requiring explicit **capability blocks**  
- rejecting unsolicited tool calls  
- rejecting hallucinated tool names  
- rejecting hallucinated parameters  

Every tool call is:

- deterministic  
- validated  
- capability‑checked  
- graph‑verified  

---

## 🧨 6. **Rewrite Rules for File Operations**
GRISP uses rewrite rules to define file operations:

Example:

```
(rule
  (match (write file x))
  (rewrite (update-block x)))
```

This means:

- The model cannot invent new operations  
- The model cannot bypass rules  
- The model cannot escalate privileges  
- The model cannot reinterpret paths  

Rewrite rules are **mathematically enforced**, not heuristically interpreted.

---

## 🧭 7. **Workspace Isolation**
GRISP defines workspaces as **sealed graph regions**:

- `/workspace`  
- `/sandbox`  
- `/tmp`  

Each region has:

- its own capability envelope  
- its own rewrite rules  
- its own storage backend  
- its own size limits  

The model cannot:

- escape a region  
- write outside a region  
- read outside a region  
- create new regions  
- escalate region privileges  

This directly fixes the Harness issue where the model writes to:

- `G:\sandbox\`  
- `G:\workspace\`  
- instead of the configured workspace

GRISP simply **does not expose the OS**.
