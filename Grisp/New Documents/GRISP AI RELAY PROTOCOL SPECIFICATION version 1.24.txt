# GARP/1.24

## Gateway AI Runtime Protocol

### Protocol Specification

### Freeze Candidate

**Status:** Normative
**Version:** 1.24
**Protocol Identifier:** `GARP/1.24`
**Wire Version:** `0x00`
**Document Language:** English
**Encoding:** UTF-8
**Transport:** Reliable byte stream, normally TCP
**Security Model:** Mutual challenge-response using a deployment-provisioned shared secret
**Primary Purpose:** Deterministic transport and browser-session boundary between an AI runtime and a browser-based AI gateway

---

# 1. Scope

## 1.1 Purpose

GARP defines the transport, authentication, browser-session, provider-adapter, generation-event, cancellation, recovery, and optional replay interfaces between an external AI runtime and a browser gateway.

GARP is a transport and browser-session protocol.

GARP does not define:

* AI quality scoring.
* Artifact acceptance.
* GRISP compilation semantics.
* GRISP runtime semantics.
* Policy approval semantics.
* Human approval semantics.
* Provider-specific credential acquisition.
* Provider-specific internal implementation details.

## 1.2 Architectural role

The intended architecture is:

```text
GRISP / AI Runtime
        |
        v
      GARP
        |
        v
Browser Gateway (e.g. Firefox)
        |
        v
Provider Adapter
        |
        v
AI Provider
```

The provider adapter is the sole component responsible for translating provider-specific browser behavior into the provider-independent GARP model.

## 1.3 Design principles

Implementations MUST be:

* deterministic where the protocol defines deterministic behavior;
* fail-closed on malformed or ambiguous input;
* explicit about state;
* explicit about evidence;
* explicit about request and session identity;
* resistant to stale browser actors and stale provider observations;
* resistant to duplicate execution;
* resistant to replay of authentication messages;
* safe against partial browser failures;
* independent of provider-specific selectors at the protocol layer.

# 3. Protocol identity

## 3.1 Canonical protocol name

The only canonical protocol name is:

```text
Gateway AI Runtime Protocol
```

The canonical acronym is:

```text
GARP
```

The canonical semantic protocol identifier is:

```text
GARP/1.24
```

## 3.2 Wire version

The wire version is:

```text
0x00
```

`0x00` is the only wire version defined by GARP/1.24.

The semantic protocol version is independent of the wire version.

## 3.3 Identity scope and artifact naming

The protocol distinguishes between:

1. **Protocol Identity:** The protocol defined herein is strictly identified as `GARP` with semantic version `GARP/1.24`.
2. **Artifact Identity:** Authoritative normative specification artifacts MUST use `GARP` and `GARP/1.24`.
3. **Implementation Identity:** Software projects, daemon executables, client libraries, or host applications implementing GARP MAY use independent product or project names without affecting protocol conformance.

# 4. Transport

## 4.1 Transport properties

The transport MUST provide:

* ordered bytes;
* reliable delivery semantics;
* connection-oriented behavior;
* explicit connection closure.

TCP is the reference transport.

## 4.2 TLS

For non-loopback operation, implementations MUST use TLS 1.2 or later.

For loopback operation, TLS MAY be omitted when the host operating-system security boundary protects the listener adequately.

## 4.3 Local binding

A gateway MAY bind only to loopback:

```text
127.0.0.1
::1
```

A gateway MUST NOT expose an unauthenticated GARP listener on a non-loopback interface.

# 5. Byte order

All multibyte integer fields in the binary header are encoded big-endian.

For example:

```text
0x000000A7
```

is encoded:

```text
00 00 00 A7
```

# 6. Frame format

Every GARP frame consists of a fixed 48-byte header followed by the frame payload.

```text
+----------------------+----------------+
| Offset               | Size           |
+----------------------+----------------+
| magic                | 4              |
| wire_version         | 1              |
| flags                | 1              |
| header_len           | 2              |
| payload_len          | 4              |
| message_type         | 2              |
| reserved             | 2              |
| request_uuid         | 16             |
| session_uuid         | 16             |
| payload              | payload_len    |
+----------------------+----------------+
```

The header is exactly:

```text
48 bytes
```

### Terminology: Frame Payload vs Envelope Payload

To avoid ambiguity, GARP distinguishes between:

1. **Frame Payload:** The raw byte sequence of length `payload_len` immediately following the fixed 48-byte binary header. In base GARP, the frame payload is the serialized UTF-8 JSON Common Envelope.
2. **Envelope Payload:** The inner JSON object stored in the `"payload"` member of the Common Envelope, whose schema is specific to the message type.

## 6.1 Magic

Offset: `0`, Length: `4`, Value: `GARP`, ASCII bytes: `47 41 52 50`.

Any other value MUST cause immediate frame rejection.

## 6.2 Wire version

Offset: `4`, Length: `1`, Required value: `00`.

Any unsupported wire version MUST produce `UNSUPPORTED_WIRE_VERSION` and MUST NOT be interpreted using a different framing rule.

## 6.3 Flags

Offset: `5`, Length: `1`.

Base GARP/1.24 requires `flags = 0` unless a negotiated extension explicitly defines a flag.

Unknown or unnegotiated flag bits MUST cause `UNSUPPORTED_FEATURE`.

## 6.4 Header length

Offset: `6`, Length: `2`, Required value: `48` (encoded `00 30`).

The field is attacker-controlled input and MUST be validated before the implementation proceeds. A value other than 48 MUST cause frame rejection.

## 6.5 Payload length

Offset: `8`, Length: `4`.

Unsigned 32-bit integer specifying the exact byte length of the frame payload.

Wire constraints: `0 <= payload_len <= 4294967295`.

The receiver MUST validate the payload length against the currently applicable limit before allocating storage for the payload.

Two distinct limits exist and MUST NOT be conflated:

1. **Handshake limit** (`handshake_limit`): applies to every frame exchanged while the receiving peer has not yet successfully received and validated the peer's `CAPABILITIES` message. Fixed:

```text
handshake_limit = 1048576  (1 MiB)
```

2. **Application limit** (`application_limit`): applies to a frame only after the receiving peer has itself successfully received and validated the peer's `CAPABILITIES` message:

```text
application_limit = min(advertised_max_payload_bytes, 4294967295)
```

For any received frame, the effective limit is determined locally and deterministically by the receiver:

```text
effective_limit =
    handshake_limit      if the receiver has not yet successfully received and validated the peer's CAPABILITIES
    application_limit    otherwise
```

The receiver MUST apply this rule symmetrically for both directions. The receiver does NOT require any acknowledgement that the peer has processed the receiver's own CAPABILITIES; each direction is governed independently by the receiver of the frames in that direction.

No implementation may allocate unbounded memory based solely on an attacker-controlled payload length. The receiver MUST reject a frame whose `payload_len` exceeds `effective_limit` before allocating storage for the payload.

## 6.6 Message type

Offset: `12`, Length: `2`. Unsigned big-endian message code.

## 6.7 Reserved

Offset: `14`, Length: `2`, Required value: `0` (encoded `00 00`).

Any nonzero value MUST cause `INVALID_ARGUMENT`.

## 6.8 Request UUID

Offset: `16`, Length: `16`. Raw UUID bytes.

Nil UUID:

```text
00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00
```

## 6.9 Session UUID

Offset: `32`, Length: `16`. Raw session UUID.

---

# 7. UUID encoding

## 7.1 Binary encoding

UUIDs are encoded as 16 raw bytes in RFC-style network byte order.

## 7.2 JSON encoding

UUID-bearing envelope fields are always present.

```json
"request_id": "uuid"
"session_id": "uuid"
```

or:

```json
"request_id": null
"session_id": null
```

A JSON `null` in an envelope identity field means the corresponding binary UUID field is all zero (nil UUID).

## 7.3 Application objects

Application-level objects MAY use the string representation of the nil UUID:

```text
00000000-0000-0000-0000-000000000000
```

This is distinct from the envelope identity representation. The distinction is intentional.

## 7.4 UUID generation

Client-created request identifiers SHOULD be generated using a cryptographically secure random source and SHOULD use UUID version 4 semantics.

# 8. Validation order

A receiver MUST validate a frame in this order:

1. fixed header availability;
2. magic;
3. wire version;
4. header length;
5. payload length against applicable limit;
6. flags;
7. reserved field;
8. message type;
9. payload byte acquisition;
10. payload encoding;
11. JSON syntax;
12. duplicate JSON member detection;
13. common envelope member presence and types;
14. header-to-envelope identity and message-type binding;
15. message schema;
16. connection and authentication state;
17. request identity and deduplication;
18. session identity;
19. target identity;
20. state transition and provider semantics.

An implementation MAY perform additional checks earlier when the result is equivalent and deterministic.

---

# 9. JSON representation

## 9.1 Encoding

All JSON payloads MUST be UTF-8.

## 9.2 Duplicate object keys

Duplicate object member names MUST be rejected. An implementation MUST NOT silently select first-key or last-key semantics.

## 9.3 Closed objects

All base GARP message and payload objects are closed unless explicitly declared open. Unknown members in a closed object MUST cause `INVALID_ARGUMENT`. Unknown extension members are permitted only through an explicitly declared `_extensions` object.

## 9.4 Open extension object

In base GARP, the `_extensions` object is permitted only within `PROMPT.options`.

Where a schema explicitly permits:

```json
"_extensions": {}
```

the `_extensions` object is open to negotiated extensions.

Its serialized size remains strictly bounded by the enclosing frame payload and the applicable `max_payload_bytes` limit.

For the avoidance of ambiguity, when an implementation needs to compute a canonical byte size for an `_extensions` object (for example, to enforce a bound deterministically), it MUST use RFC 8785 JSON Canonicalization Scheme (JCS) semantics. This requirement is limited to size bounding and does not make JCS the general wire format for arbitrary frames.

# 10. JSON integer types and bounds

JavaScript number precision MUST NOT be relied upon for protocol `uint64` values.

## 10.1 uint64-string

Every protocol field defined as `uint64` in JSON MUST be encoded as a decimal string matching:

```text
^(0|[1-9][0-9]{0,19})$
```

and representing a value no greater than `18446744073709551615`.

## 10.2 uint32

Fields defined as `uint32` MAY be encoded as JSON numbers. Range: `0 .. 4294967295`.

## 10.3 Booleans

Booleans MUST use JSON `true` or `false`. Strings MUST NOT be used as boolean substitutes in base schemas.

## 10.4 Protocol string bounds

All string fields in base schemas have defined byte-length bounds:

* `provider`: 1 .. 64 bytes
* `tab_id`: 1 .. 64 bytes
* `actor_instance`: 1 .. 64 bytes
* `code`: 1 .. 64 bytes
* `strategy`: 1 .. 64 bytes
* `title`: 0 .. 512 bytes
* `message`: 0 .. 1024 bytes
* `url`: 1 .. 4096 bytes

The following diagnostic-specific string fields inherit the same bounds as their generic counterparts:

* `DIAGNOSTIC.code`: 1 .. 64 bytes
* `DIAGNOSTIC.message`: 0 .. 1024 bytes
* `DIAGNOSTIC.actor_instance`: 1 .. 64 bytes

A string exceeding its defined bound MUST be rejected with `INVALID_ARGUMENT`.

## 10.5 Protocol duration bounds

All duration and timeout fields (represented as uint64-strings in milliseconds) are bounded:

* `timeout_ms`: `0 <= timeout_ms <= 86400000` (max 24 hours).
* `continuation_wait_ms`, `recovery_deadline_ms`, `retry_after_ms`, `idle_timeout_ms`, `interval_ms`, `response_retention_ms`: `0 <= value <= 864000000` (max 10 days).

A duration exceeding its bound MUST be rejected with `INVALID_ARGUMENT`.

# 11. Common envelope

Every JSON message uses the following structure:

```json
{
  "garp": "1.24",
  "type": "MESSAGE_TYPE",
  "request_id": null,
  "session_id": null,
  "timestamp": "2026-01-01T00:00:00.000Z",
  "sequence": null,
  "payload": {}
}
```

## 11.1 Required members

Always present: `garp`, `type`, `request_id`, `session_id`, `timestamp`, `payload`.

`sequence` is always present as either a uint64-string or null.

## 11.2 garp

Required value: `1.24`.

## 11.3 type

ASCII uppercase registry name.

## 11.4 request_id

For a command issued by a client, this is the unique command identifier.

For a response (`RESPONSE` or command-correlated `ERROR`), it identifies the originating command request ID.

For handshake correlation messages (`HELLO_CHALLENGE`, `HELLO_AUTH`, `HELLO_ACK`), it MAY equal the initiating `HELLO` request ID.

For all session-scoped events, envelope `request_id` MUST be `null` (and header `request_uuid` MUST be all-zero nil UUID). Command correlation for prompts is carried inside `payload.prompt_request_id`.

For unsolicited connection-scoped events (`CAPABILITIES`, `PONG`, `BROWSER_STATUS`), envelope `request_id` MUST be `null`.

### Global asynchronous event correlation rule

This rule is stated authoritatively once here and referenced normatively by §85 and by every message schema. It applies to every asynchronous event, i.e. every event that is not a direct, synchronous command response.

For every asynchronous event:

* `envelope.request_id` MUST be `null`.
* `header.request_uuid` MUST be the all-zero nil UUID.
* Any correlation to an originating operation MUST be carried inside operation-specific payload fields, such as `payload.prompt_request_id`.

This rule is normative for both session-scoped and connection-scoped asynchronous events. It applies to all present and future asynchronous events unless an explicit negotiated extension overrides it for its own message types, and any such override MUST be stated in the extension's own normative text.

## 11.5 session_id

Session-scoped messages and session-scoped commands contain the session UUID.

Connection-scoped messages contain `null`.

## 11.6 timestamp

Strict RFC 3339 / ISO 8601 UTC timestamp string with millisecond precision: `YYYY-MM-DDTHH:MM:SS.sssZ`.

Timestamp is informational. Timeouts and deadline decisions MUST use monotonic clocks.

## 11.7 sequence

Session-scoped events use monotonically increasing sequence values.

Connection-scoped messages, commands, and direct command responses use `null`.

## 11.8 payload

JSON object whose exact schema is defined by the message type.

# 12. Header-to-envelope identity binding

The binary header and JSON envelope MUST agree.

```text
header.message_type  = registry(type)
header.request_uuid  = envelope.request_id
header.session_uuid  = envelope.session_id
```

A mismatch MUST cause `HEADER_JSON_MISMATCH`.

An unknown binary message code MUST instead cause `UNKNOWN_MESSAGE_TYPE`.

An otherwise valid binary message code carrying an unknown JSON `type` MUST cause `UNKNOWN_MESSAGE_TYPE`.

# 15. Feature names and modifiers

Feature names MUST match:

```text
^[a-z0-9][a-z0-9._-]{0,127}$
```

The canonical extension name does NOT include any leading punctuation (e.g. `ext-pong`).

During handshake feature negotiation, a client or server MAY prefix a feature name with `!` to declare it a **required feature**.

The `!` prefix is a handshake negotiation token modifier indicating that the connection MUST fail if the peer does not support it.

The `!` modifier is cryptographically bound into the negotiation transcript and MUST NOT be silently stripped.

Validation MUST occur before canonicalization.

Duplicate canonical feature names MUST be rejected.

Feature names MUST be sorted by raw UTF-8 byte order after validation and without applying locale-sensitive collation.

# 16. Authentication

## 16.1 Purpose

Authentication proves: possession of the shared secret; knowledge of the current challenge; agreement on semantic version; agreement on wire version; agreement on offered features; agreement on final negotiated features; peer identity metadata.

## 16.2 Shared secret

The shared secret MUST contain at least 32 raw bytes. The deployment MUST define how the configured secret is represented.

No implementation may silently reinterpret a configured textual value as hexadecimal when the deployment expects raw bytes, or vice versa.

## 16.3 Normative test secret

The authentication test vector uses exactly these raw ASCII bytes:

```text
0123456789abcdef0123456789abcdef
```

This is 32 bytes. It is NOT a hexadecimal encoding of 16 bytes.

## 16.4 Client nonce

The client nonce MUST be exactly 16 raw bytes. It is represented in JSON as unpadded Base64URL. Padding characters MUST be rejected. Decode failures MUST cause authentication failure.

## 16.5 Server nonce

The server nonce MUST be exactly 16 raw bytes. It is represented using the same rules as the client nonce.

## 16.6 Authentication transcript

The proof transcript contains these fields in exactly this order:

```text
domain
client_nonce
server_nonce
selected_semantic_version
selected_wire_version
offered_feature_set
final_feature_set
client_name
client_version
server_name
server_version
```

Every field in the transcript (domain, client_nonce, server_nonce, selected_semantic_version, selected_wire_version, client_name, client_version, server_name, server_version) is encoded with a 4-byte big-endian length prefix followed by raw bytes:

```text
u32be(byte_length)
raw bytes
```

The feature-list encoding is:

```text
u32be(feature_count)
repeat feature_count times:
    u32be(feature_byte_length)
    feature UTF-8 bytes
```

Domains are ASCII. Version strings are UTF-8. Feature names are UTF-8. Identity strings are UTF-8.

The negotiated wire version is encoded as the UTF-8 string `0x00`.

The selected semantic version is `1.24`.

## 16.7 Proof

The proof is:

```text
HMAC-SHA256(shared_secret, transcript)
```

The resulting proof is exactly 32 raw bytes. Its JSON representation is unpadded Base64URL. Comparison MUST be constant-time.

## 16.8 Domains

The client-to-server proof domain is `GARP/1.24/client-proof`.

The server-to-client proof domain is `GARP/1.24/server-proof`.

## 16.9 Negotiation binding

Both the original offered feature set and final negotiated feature set are included in the transcript.

Therefore `!ext-pong` cannot be changed to `ext-pong` without invalidating the proof.

The required-feature marker is cryptographically bound.

## 16.10 Timestamp

Authentication proofs do not include the timestamp. Freshness is provided by the nonces. The timestamp remains informational.

# 17. Authentication messages

## 17.1 HELLO

Header:

```text
request_uuid = client-generated UUID
session_uuid = nil
```

Payload:

```json
{
  "client_name": "GARPClient",
  "client_version": "1.24.0",
  "versions": ["1.24"],
  "wire_versions": ["0x00"],
  "features": ["!ext-pong"],
  "client_nonce": "BASE64URL"
}
```

## 17.2 HELLO_CHALLENGE

Payload:

```json
{
  "server_name": "GarpGateway",
  "server_version": "1.24.0",
  "selected_version": "1.24",
  "selected_wire_version": "0x00",
  "features": ["!ext-pong"],

```

The response correlation identifier equals the initiating HELLO transaction identifier.

## 17.3 HELLO_AUTH

Payload:

```json
{
  "client_proof": "BASE64URL"
}
```

Its request UUID equals the correlated HELLO transaction identifier.

## 17.4 HELLO_ACK

Payload:

```json
{
  "server_proof": "BASE64URL",
  "selected_version": "1.24",
  "selected_wire_version": "0x00",
  "features": ["!ext-pong"]
}
```

HELLO_ACK completes authentication only after the client verifies the server proof.

# 18. Request-ID uniqueness and correlation exception

## 18.1 New command IDs

A client-generated command request ID MUST be unique within the connection.

## 18.2 Handshake transaction entry

The entire HELLO handshake sequence:

```text
HELLO             request_id = X
HELLO_CHALLENGE   request_id = X
HELLO_AUTH        request_id = X
HELLO_ACK         request_id = X
```

occupies exactly **one** entry in the connection request-ID namespace.

Reusing that transaction ID for handshake correlation does not constitute issuance of additional client command request IDs.

## 18.3 Application responses

A `RESPONSE` or protocol `ERROR` associated with a command uses that command's request ID.

The receiving implementation MUST NOT interpret a normal response as a new request.

---

# 19. Replay protection

Authentication replay protection MUST survive gateway process restarts for at least 24 hours.

The replay-protection store MAY be: durable local storage; encrypted persistent storage; shared durable key-value storage; another mechanism providing equivalent guarantees.

## 19.1 Lost replay state

If authentication replay state is lost or cannot be re-established:

```text
the gateway MUST NOT continue accepting the affected secret.
```

The affected shared secret MUST be disabled and rotated. A gateway MUST NOT resume authentication with the same secret merely because the process restarted.

This rule applies to authentication replay state only. Application session state and event history MAY still be lost on restart unless separately persisted.

## 19.2 Replay key

The implementation MUST detect reuse of an authenticated handshake transcript for the same credential context.

A practical deterministic key is `SHA-256(transcript_core)` where `transcript_core` contains both nonces and all negotiation-binding fields.

---

# 20. Handshake timeout

The default handshake timeout is `10000 ms`, measured using a monotonic clock.

If authentication does not complete within the deadline, the connection MUST close.

The error condition is `HANDSHAKE_TIMEOUT`.

---

# 21. CAPABILITIES

CAPABILITIES is a connection-scoped message.

Header identity:

```text
request_uuid = nil
session_uuid = nil
```

Sequence: `null`.

It is emitted immediately after `HELLO_ACK` and before application commands are processed.

A gateway MUST also emit a new CAPABILITIES event when effective negotiated capabilities materially change.

---

# 22. Capability structure

The CAPABILITIES payload is:

```json
{
  "protocol": "1.24",
  "wire_version": "0x00",
  "limits": {
    "handshake_timeout_ms": "10000",
    "max_payload_bytes": 16777216,
    "max_prompt_size": 1048576,
    "max_response_size": 16777216,
    "max_outstanding_requests": 128,
    "max_queued_events": 8192,
    "max_event_history_memory_mb": 64,
    "max_generation_buffer_mb": 32,
    "response_retention_ms": "86400000",
    "continuation_wait_ms": "300000",
    "recovery_deadline_ms": "300000",
    "max_error_details_bytes": 65536,
    "max_diagnostic_details_bytes": 65536
  },
  "keepalive": {
    "enabled": true,
    "idle_timeout_ms": "30000",
    "interval_ms": "10000"
  },
  "providers": [],
  "extensions": []
}
```

The values above are illustrative. The implementation MUST advertise its actual enforced values.

### Explicit type and range declarations

The following members of `limits` are of JSON type `uint32` (encoded as JSON numbers) with range `0 .. 4294967295`:

* `max_payload_bytes`, `max_prompt_size`, `max_response_size`, `max_outstanding_requests`, `max_queued_events`, `max_event_history_memory_mb`, `max_generation_buffer_mb`, `max_error_details_bytes`, `max_diagnostic_details_bytes`.

The following members of `limits` are `uint64-string` per §10.1 and bounded per §10.5:

* `handshake_timeout_ms`, `response_retention_ms`, `continuation_wait_ms`, `recovery_deadline_ms`.

The following members of `keepalive` are `uint64-string` per §10.1 and bounded per §10.5:

* `idle_timeout_ms`, `interval_ms`.

`keepalive.enabled` is JSON `boolean`.

A receiver MUST reject a CAPABILITIES payload whose limit fields violate these type or range declarations with `INVALID_ARGUMENT`.

## 22.1 Provider entries

Each provider entry contains:

```json
{
  "id": "deepseek",
  "version": "1.0.0",
  "state": "AVAILABLE",
  "input_strategies": [
    "provider_native_send",
    "keyboard_enter"
  ],
  "capabilities": {
    "streaming": true,
    "cancellation": true,
    "continuation": true,
    "diagnostics": true
  }
}
```

### Required fields

Every provider entry MUST contain all of the following members:

* `id` — string, 1 .. 64 bytes.
* `version` — string, 1 .. 64 bytes.
* `state` — string, one of `AVAILABLE`, `UNAVAILABLE`, `AUTH_REQUIRED`, `RATE_LIMITED`, `DEGRADED`.
* `input_strategies` — array of strings, each 1 .. 64 bytes, at least one element, no duplicates.
* `capabilities` — object (see below).

Any provider entry missing a required member MUST cause the entire CAPABILITIES frame to be rejected with `INVALID_ARGUMENT`.

### The `capabilities` object

The base `capabilities` object is **closed**. It MUST contain exactly the following members, each of JSON type `boolean`:

```text
streaming
cancellation
continuation
diagnostics
```

Additional members MUST NOT be present in base GARP. Additional boolean capability names are permitted only through an explicitly negotiated extension.

### Ordering

`providers` MAY be empty only when no provider adapter is currently installed or usable.

Providers MUST be sorted by `id` using raw UTF-8 byte order. Input strategy arrays MUST use the same ordering rule.

### Input strategies

An **input strategy** is a provider-adapter-defined, provider-independent identifier for the mechanism used to submit input to the provider. The canonical name of an input strategy MUST match:

```text
^[a-z][a-z0-9_]{0,63}$
```

The base protocol does not mandate any particular input strategy. Strategies advertised in `input_strategies` MUST be a subset of the strategies the adapter is currently able to use for the current page and provider context.

### Canonical definition of "provider unavailable"

A provider is **unavailable** for a given session when any of the following holds, as established by authoritative adapter evidence:

* the provider adapter for the configured provider is not installed;
* the provider adapter is installed but disabled;
* the provider adapter has crashed;
* the provider's browser context associated with the session is no longer present;
* the provider adapter has reported that it cannot serve the current page.

A provider that is merely rate-limited or that requires interactive authentication is not "unavailable"; those conditions are represented by dedicated events and session states.

## 22.2 Extensions

```json
[
  {
    "name": "ext-pong",
    "version": "1.0"
  }
]
```

Extensions MUST be listed by their canonical name (without `!`) and sorted by name.

## 22.3 Limit breach behaviors

* Prompt length exceeding `max_prompt_size`: command rejected with `INVALID_ARGUMENT`.
* Outstanding requests exceeding `max_outstanding_requests`: command rejected with `OUTSTANDING_REQUEST_LIMIT`.
* Response content exceeding `max_response_size`: prompt submits a `RESPONSE_TOO_LARGE` terminal failure candidate (`partial = true`) to the arbiter of §74.
* Internal generation buffer exceeding `max_generation_buffer_mb`: prompt submits a `GENERATION_BUFFER_LIMIT` terminal failure candidate (`partial = true`) to the arbiter of §74.

### Definition of an outstanding request

An **outstanding request** is a client-issued command whose corresponding `RESPONSE` or command-correlated `ERROR` has not yet been committed by the gateway for transmission to that client.

For the purpose of `max_outstanding_requests`:

* Only client-issued commands count.
* A command is counted from the moment it is successfully received and parsed.
* A command stops being counted at the moment its correlated `RESPONSE` or `ERROR` is committed for transmission, regardless of when that frame is physically written to the transport.
* Unsolicited events never count.
* The HELLO handshake sequence counts as a single outstanding request.
* Rejected commands that produce a command-correlated `ERROR` still count until that `ERROR` is committed.

## 22.4 Capability changes and active prompts

When effective application limits change, the gateway MUST emit CAPABILITIES.

Clients MUST use the newest advertised values for future operations.

Previously accepted prompt input is not invalidated solely because a subsequently advertised `max_prompt_size` becomes smaller. Clients are NOT required to revalidate active prompts merely because a capability limit decreased. Safety limits for global memory, queue capacity, process safety, and connection safety MAY apply immediately and MAY affect active prompts, in which case the affected prompt MUST submit the corresponding terminal failure candidate (`RESPONSE_TOO_LARGE`, `GENERATION_BUFFER_LIMIT`, `EVENT_QUEUE_OVERFLOW`, or `RECOVERY_FAILED`) to the terminal arbiter of §74.

This section is the authoritative statement of capability-change semantics. §24 exists only as a non-normative cross-reference and MUST NOT be treated as an independent normative statement.

---

# 23. Bootstrap limits

The handshake limit is independent from application limits.

The bootstrap handshake payload maximum is 1 MiB.

Handshake messages remain subject to the bootstrap limit until the receiving peer has itself successfully received and validated the peer's CAPABILITIES message.

CAPABILITIES does not increase the handshake limit.

Application messages use the advertised effective application limit:

```text
application_limit = min(advertised_max_payload_bytes, 4294967295)
```

Therefore:

```text
handshake limit = 1 MiB, effective until the receiver has itself received and validated the peer's CAPABILITIES
application limit = advertised CAPABILITIES value, effective after that point
```

The effective limit as a function of the receiver's own local state is defined normatively in §6.5. No peer acknowledgement is required or defined for CAPABILITIES processing.

### Normative Mappings:

* `INVALID_ARGUMENT`: Malformed fields, out-of-range integers, string length limit breaches, unknown members in closed payload objects, nonzero reserved header bytes.
* `INVALID_ENVELOPE`: Missing required envelope members, extra keys in the top-level Common Envelope object, invalid envelope types or structure.
* `UNKNOWN_MESSAGE_TYPE`: Unrecognized header message code or unrecognized envelope type name.
* `UNKNOWN_MESSAGE_ID`: An operation references a `message_id` that does not exist within the active or targeted prompt.
* `HEADER_JSON_MISMATCH`: Discrepancy between header and envelope identity fields.
* `UNSUPPORTED_VERSION`: Negotiated semantic version is not supported.
* `UNSUPPORTED_WIRE_VERSION`: Wire version is not `0x00`.
* `UNSUPPORTED_FEATURE`: Unnegotiated extension flag or unsupported required feature (`!`).
* `AUTH_REQUIRED`: Command attempted before completing mutual handshake authentication.
* `AUTH_FAILED`: Verification of peer HMAC proof failed.
* `AUTH_REPLAY`: Replay of prior authentication nonces/transcript detected.
* `HANDSHAKE_TIMEOUT`: Handshake did not complete within `handshake_timeout_ms`.
* `DUPLICATE_REQUEST`: Duplicate non-idempotent command request ID received.
* `REVISION_GAP`: Generation revision gap detected.
* `EVENT_SEQUENCE_GAP`: Receiver detects gap in session event sequence.
* `EVENT_SEQUENCE_OVERFLOW`: Session event counter exceeds uint64 limit.
* `PAGE_GENERATION_OVERFLOW`: Page generation counter exceeds uint64 limit.
* `INVALID_MESSAGE_STATE`: Command executed in incompatible state, or losing race for an arbiter reservation. See §27.1.
* `SESSION_NOT_FOUND`: Target `session_id` does not exist.
* `SESSION_CLOSED`: Target session is terminally closed.
* `SESSION_BUSY`: Target session already has an active nonterminal prompt; the session-level prompt exclusivity reservation has been lost.
* `OUTSTANDING_REQUEST_LIMIT`: Connection has reached `max_outstanding_requests`.
* `TAB_NOT_FOUND`: Target `tab_id` does not exist.
* `TAB_UNAVAILABLE`: Target tab is crashed, restricted, or unavailable.
* `PROMPT_NOT_FOUND`: Referenced `prompt_request_id` does not exist within the targeted session.
* `PROMPT_NOT_ACTIVE`: Command requires an active prompt, but the referenced prompt exists and is not active.
* `PROMPT_ALREADY_TERMINAL`: Command targeted at a prompt whose terminal state has already been committed.
* `PROMPT_TIMEOUT`: Prompt exceeded configured `timeout_ms`.
* `PROMPT_CANCELLED`: Command targeted at a prompt whose terminal state is `CANCELLED`, and the command's semantics distinguish that specific terminal outcome.
* `RESPONSE_NOT_READY`: `GET_RESPONSE` called while prompt is still actively generating.
* `INPUT_VERIFICATION_FAILED`: Prompt injection verification failed.
* `SUBMISSION_FAILED`: Submission of input to provider failed.
* `STALE_ACTOR`: Result received from replaced browser actor.
* `NAVIGATION_DRIFT`: Unexpected URL or document replacement occurred during an active page-dependent prompt operation.
* `PROVIDER_UNAVAILABLE`: Selected provider is uninstalled, disabled, crashed, or its context has been invalidated for the active prompt.
* `PROVIDER_AUTH_REQUIRED`: Provider requires interactive user authentication.
* `PROVIDER_RATE_LIMITED`: Provider rejected submission due to rate limits.
* `PROVIDER_ERROR`: Provider internal error or generation failure.
* `RESPONSE_TOO_LARGE`: Accumulated response content exceeds `max_response_size`.
* `GENERATION_BUFFER_LIMIT`: Accumulated transient generation data exceeds `max_generation_buffer_mb`. Gateway resource limit, not semantic provider-response limit.
* `CONTINUATION_NOT_ALLOWED`: Continuation attempted when disabled from the start (`max_continuations = 0`).
* `CONTINUATION_LIMIT_REACHED`: Continuation requested after reaching configured `max_continuations` where `max_continuations > 0`.
* `CONTINUATION_TIMEOUT`: Continuation did not arrive within `continuation_wait_ms`.
* `CONTINUATION_NOT_AVAILABLE`: Provider adapter does not support continuation at all for the current prompt.
* `RECOVERY_FAILED`: Session recovery deadline expired without restoring authoritative state.
* `EVENT_QUEUE_OVERFLOW`: Session event storage exceeds `max_queued_events`.
* `EVENT_HISTORY_EXPIRED`: Requested sequence in `GET_EVENTS` has already been evicted from history.

## 27.1 Decision table for prompt-state error boundaries

| Condition at command arrival | Applicable code |
| --- | --- |
| Referenced `prompt_request_id` does not exist within the session | `PROMPT_NOT_FOUND` |
| Prompt state is `COMPLETED`, `FAILED`, or `CANCELLED` | `PROMPT_ALREADY_TERMINAL` |
| Prompt state is `CANCELLED` and the command's semantics distinguish the cancelled outcome | `PROMPT_CANCELLED` |
| Command requires the prompt to be active, prompt exists, prompt is in a nonterminal state incompatible with the command | `PROMPT_NOT_ACTIVE` |
| Command is incompatible with the current state for reasons other than active/terminal distinction, or an arbiter reservation race is lost | `INVALID_MESSAGE_STATE` |
| Prompt is in `CANCELLING` and a second `CANCEL_PROMPT` is received | `INVALID_MESSAGE_STATE` |

Normative consequences:

* `CANCEL_PROMPT` against a prompt in `PENDING`, `SUBMITTING`, `GENERATING`, or `WAITING_CONTINUATION` is accepted.
* `CANCEL_PROMPT` against a prompt in `CANCELLING` fails with `INVALID_MESSAGE_STATE`.
* `CANCEL_PROMPT` against a prompt in `COMPLETED`, `FAILED`, or `CANCELLED` fails with `PROMPT_ALREADY_TERMINAL`.
* `CONTINUE_PROMPT` against a prompt not in `WAITING_CONTINUATION` fails with `PROMPT_NOT_ACTIVE` if the prompt exists and is nonterminal, and with `PROMPT_ALREADY_TERMINAL` if the prompt is terminal.
* `GET_PROMPT_STATUS` and `GET_RESPONSE` accept prompts in all states including terminal states.
* A losing race in the auto-continue vs explicit `CONTINUE_PROMPT` arbitration fails with `INVALID_MESSAGE_STATE`.

# 30. Session arbiter

Each session MUST have a serialized arbiter.

The arbiter is responsible for:

* prompt reservation;
* prompt terminal commits;
* cancellation commits;
* timeout commits;
* retry transitions;
* recovery transitions;
* page-generation changes;
* provider-context invalidation transitions;
* event sequence allocation;
* session state transitions.

Operations affecting the same session MUST be serialized.

Read-only queries MAY execute concurrently, but MUST observe a consistent committed session snapshot.

# 32. RESET_SESSION

`RESET_SESSION` is a session-scoped command.

Header:

```text
request_uuid = new client command UUID
session_uuid = target session UUID
sequence = null
```

Request payload:

```json
{
  "options": {}
}
```

Response payload:

```json
{
  "success": true,
  "session_id": "uuid",
  "state": "PREPARING"
}
```

RESET_SESSION MUST:

1. stop provider activity where possible;
2. invalidate stale page actors;
3. invalidate stale asynchronous operations;
4. increment `page_generation`;
5. preserve the session ID;
6. preserve the session event sequence;
7. transition through `PREPARING`.

# 33. Page generation

`page_generation` is a uint64-string.

It identifies the current browser/page actor generation for the session.

It MUST increment on significant navigation, document replacement, or actor replacement as defined by the gateway.

It MUST NOT decrement.

It MUST NOT reset to zero during `RESET_SESSION`.

If increment would exceed `18446744073709551615`, the session MUST fail with `PAGE_GENERATION_OVERFLOW`.

# 34. Session readiness

A session is READY only when all required evidence has been established:

* target tab exists;
* correct provider context exists;
* provider adapter is usable;
* page generation is current;
* provider input is discoverable;
* provider authentication state is acceptable;
* no conflicting active prompt exists.

Readiness MUST NOT be inferred solely from tab existence.

# 42. Provider events

## 42.1 PROVIDER_CHANGED

Payload:

```json
{
  "previous_provider": "deepseek",
  "provider": "gemini",
  "page_generation": "8"
}
```

### Field semantics

* `provider` MUST be the session's newly authoritative provider identity after this observation.
* `previous_provider` MUST be the session's authoritative provider identity immediately prior to this observation, or `null` if the session had no prior authoritative provider (e.g. initial provider binding).
* If the observation changes the provider binding without changing the provider identity, `previous_provider` and `provider` MUST be equal.

### Effect on active prompt

If a `PROVIDER_CHANGED` event invalidates the provider context of an active prompt, the gateway MUST immediately submit a `PROVIDER_UNAVAILABLE` terminal failure candidate to the arbiter of §74 on behalf of the affected prompt. The prompt becomes terminally `FAILED` only if that candidate wins arbitration; if another terminal candidate has already been committed, the invalidation is discarded as stale evidence.

The provider context of an active prompt is invalidated when the provider identity, provider binding, or provider adapter instance that was used to submit or is currently driving the active prompt is no longer the authoritative provider context for the session. Changes that do not invalidate the active prompt's provider context (e.g. purely cosmetic metadata updates or unrelated provider registry updates) MUST NOT by themselves submit a terminal candidate.

### Session transition is atomic with the invalidation

The session transition triggered by a provider-context invalidation MUST be committed by the arbiter as part of the same serialized operation that submits the `PROVIDER_UNAVAILABLE` terminal candidate. The session transition does not depend on which terminal candidate wins prompt arbitration; it is a distinct session-level effect that reflects the fact that the provider context has been invalidated.

The session transition MUST be deterministically selected using the following evidence rule:

* If the invalidation is established and no in-flight provider operation attributable to the active prompt remains (verified by the provider adapter via authoritative evidence):
  ```text
  BUSY -> PREPARING
  ```
  reached via an internal reset-equivalent transition performed by the gateway (no client-issued `RESET_SESSION` is involved; the transition is equivalent to `RESET_SESSION` in its effect on `page_generation`, stale actors, and event sequence continuity). This transition is present in §31.

* If an in-flight provider operation attributable to the active prompt may still exist, or if authoritative evidence of provider cessation is unavailable (i.e. state is ambiguous):
  ```text
  BUSY -> RECOVERING
  ```

The arbiter MUST serialize this transition and MUST apply exactly one of the two outcomes above based on adapter-supplied fencing evidence. No other transition is permitted for this event.

### Provider-change evidence is adapter-defined

Whether "no in-flight provider operation attributable to the active prompt remains" is true is an adapter-specific determination. The protocol requires the adapter to make this determination using authoritative evidence and to supply the resulting fencing context; the protocol does not prescribe the adapter's internal evidence-gathering mechanism.

### Provider change during WAITING_CONTINUATION

If `PROVIDER_CHANGED` invalidates the provider context while the active prompt is in `WAITING_CONTINUATION`, the same rules apply: a `PROVIDER_UNAVAILABLE` terminal candidate is submitted, the `partial` flag is determined by §76, and the session transitions deterministically to `PREPARING` or `RECOVERING` atomically with the invalidation.

### Provider change with no active prompt

If `PROVIDER_CHANGED` occurs with no active prompt, the session follows its normal state transition rules; no terminal candidate is submitted.

## 42.2 PROVIDER_AUTH_REQUIRED

Payload:

```json
{
  "provider": "deepseek",
  "reason": "LOGIN_REQUIRED",
  "page_generation": "8"
}
```

An active prompt affected by provider authentication loss MUST submit a `PROVIDER_AUTH_REQUIRED` terminal failure candidate to the arbiter of §74. The prompt becomes terminally `FAILED` only if that candidate wins arbitration. The `partial` flag is determined by §76.

Once the terminal commit has been made, the session transitions to `AUTH_REQUIRED`.

### Provider authentication evidence

A provider adapter MUST define positive and negative evidence for provider authentication state:

* **Positive evidence of authentication:** authoritative adapter observation that the provider session is authenticated and usable.
* **Negative evidence of authentication loss:** authoritative adapter observation that the provider requires interactive authentication (e.g. a login prompt, an authentication error page, or loss of session cookies attributable to the provider).

Absence of positive evidence is NOT by itself negative evidence. The adapter MUST NOT submit a `PROVIDER_AUTH_REQUIRED` terminal candidate based solely on the absence of a positive observation.

When multiple browser actors are involved, authentication evidence MUST be attributed to a specific `actor_instance`, `page_generation`, and `provider` identity. Evidence from a subordinate actor whose `page_generation` does not match the session's current `page_generation`, whose `actor_instance` is no longer valid, or whose `provider` identity does not match the session's authoritative provider MUST be discarded.

If authentication evidence cannot be authoritatively established (neither positive nor negative) and the active prompt cannot continue safely, the prompt MUST submit a `RECOVERY_FAILED` terminal candidate and the session MUST enter `RECOVERING`, not `AUTH_REQUIRED`.

## 42.3 PROVIDER_RATE_LIMITED

Payload:

```json
{
  "provider": "deepseek",
  "retry_after_ms": "30000",
  "page_generation": "8"
}
```

`retry_after_ms = "0"` means retry timing is unknown.

An active prompt affected by rate limiting MUST submit a `PROVIDER_RATE_LIMITED` terminal failure candidate to the arbiter of §74. The prompt becomes terminally `FAILED` only if that candidate wins arbitration. The `partial` flag is determined by §76.

Once the terminal commit has been made, the session enters `RATE_LIMITED`.

# 61. GENERATION_DELTA

Payload:


# 64. Continuation

## 64.1 Continuation lifecycle

`GENERATING -> WAITING_CONTINUATION`.

A continuation does not create a new prompt.

## 64.2 Continuation contract

1. Each prompt has an associated `continuation_count`, initialized to `0` at prompt acceptance.
2. The prompt option `max_continuations` is a JSON `uint32` in the range `0 .. 1024` (§50.3). It is fixed at prompt acceptance and MUST NOT change for the lifetime of the prompt.
3. `continuation_count` is incremented by exactly `1` upon verified provider submission of a continuation (`CONTINUATION_SUBMITTED`, §67).
4. `continuation_count` MUST NOT exceed `max_continuations`.
5. When `max_continuations = 0`, continuation is disallowed from the start. If the provider requests a continuation, the gateway MUST NOT emit `CONTINUATION_REQUIRED`; it MUST fail the prompt with `CONTINUATION_NOT_ALLOWED` (`partial = true` iff committed content exists, otherwise `partial = false`).
6. When `max_continuations > 0` and `continuation_count` has reached `max_continuations`, the gateway MUST NOT emit `CONTINUATION_REQUIRED`; it MUST fail the prompt with `CONTINUATION_LIMIT_REACHED` (`partial = true` iff committed content exists, otherwise `partial = false`).
7. Otherwise, when the provider requests a continuation, the gateway MUST emit `CONTINUATION_REQUIRED` with the current `continuation_count` and the prompt enters `WAITING_CONTINUATION`.

## 64.3 Continuation availability

A provider adapter that does not support continuation at all for the current prompt MUST advertise `capabilities.continuation = false` for its provider entry. If a continuation is nonetheless requested by the provider and the adapter has advertised that continuation is not available, the gateway MUST fail the prompt with `CONTINUATION_NOT_AVAILABLE` (`partial = true` iff committed content exists, otherwise `partial = false`).

`CONTINUATION_NOT_AVAILABLE` means the adapter cannot perform continuation at all for this prompt; it is distinct from `CONTINUATION_NOT_ALLOWED` (disabled by prompt options) and `CONTINUATION_LIMIT_REACHED` (configured bound reached).

## 64.4 Continuation vs retry

Continuation and retry are distinct mechanisms and MUST NOT be conflated:

* A continuation is a prompt-scoped, provider-requested operation that extends the current generation.
* A retry is a session-scoped or prompt-scoped re-attempt of a previously failed or ambiguous provider operation, governed by §77 and §78.

A continuation MUST NOT be implemented as a retry, and a retry MUST NOT be implemented as a continuation.

If a continuation cannot be performed because the provider operation is ambiguous, the prompt MUST fail with `RECOVERY_FAILED` and the session MUST enter `RECOVERING` rather than retrying.

## 64.5 Continuation vs cancellation

If a `CANCEL_PROMPT` is accepted while the prompt is in `WAITING_CONTINUATION`, the prompt transitions to `CANCELLING` and the continuation is abandoned. The prompt's terminal state is then determined exclusively by the terminal arbitration defined in §74, using evidence from cancellation, provider completion, and recovery as they arrive.

An in-flight continuation that was started before `CANCEL_PROMPT` was accepted MUST be fenced by the cancellation. If a result from that in-flight continuation arrives after the cancellation was accepted:

* the result MUST be discarded as a stale operation;
* the gateway MUST NOT emit `CONTINUATION_SUBMITTED` for it;
* the gateway MUST NOT alter the prompt state, session state, or event sequence as a result of it;
* a `DIAGNOSTIC` event MAY be emitted to record the discarded continuation, but this is optional and MUST NOT be treated as an authoritative protocol state change.

### Revision Equality Invariant:

In single-message completion, `revision` MUST strictly equal the last committed revision for that message.

In multi-message completion, each `message.revision` MUST strictly equal that message's last committed revision.

An adapter MUST NOT emit a completion snapshot that skips uncommitted delta revisions.

`partial` MUST NOT appear in GENERATION_COMPLETED.

### Completion content invariant

GENERATION_COMPLETED MUST represent exactly the message content corresponding to the final accepted revision for each message in the snapshot:

* For a message whose final accepted revision was produced by `APPEND` mode, the completion `response` MUST equal the content produced by applying the full sequence of accepted revisions up to and including that final revision, using §61's mode rules.
* For a message whose final accepted revision was produced by `REPLACE` mode, the completion `response` MUST equal the replacement text carried by that final revision, regardless of any earlier revisions.
* For a message that mixes `APPEND` and `REPLACE` revisions across its lifetime, the completion `response` MUST equal the content produced by applying each accepted revision in order, using its declared mode.

An adapter MUST NOT emit a completion snapshot whose `response` field does not equal the content defined by the revision sequence above.

# 72. Cancellation

CANCEL_PROMPT is a session-scoped command valid for any nonterminal prompt state except `CANCELLING`:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
```

A second CANCEL_PROMPT against a prompt already in `CANCELLING` fails with `INVALID_MESSAGE_STATE`. `CANCELLING` is a nonterminal state; a second cancellation is not a "prompt already terminal" condition. See §27.1.

Header:

```text
request_uuid = new client command UUID
session_uuid = target session UUID
sequence = null
```

Request payload:

```json
{
  "prompt_request_id": "uuid"
}
```

Accepted cancellation moves the prompt to `CANCELLING`.

Command response:

```json
{
  "success": true,
  "command_state": "ACCEPTED"
}
```

If the prompt is already in a terminal state (`COMPLETED`, `FAILED`, `CANCELLED`), CANCEL_PROMPT fails with `PROMPT_ALREADY_TERMINAL`.

## 72.1 Cancellation race semantics

### Cancellation during SUBMITTING

If `CANCEL_PROMPT` is accepted while the prompt is in `SUBMITTING`, the prompt moves to `CANCELLING` and the in-flight submission is fenced by the cancellation.

If the submission subsequently succeeds at the provider, that result is **submission evidence only**. It MUST NOT by itself be treated as cancellation evidence or as cessation evidence. Submission success proves that the provider received input; it does not prove that provider execution stopped.

The gateway MUST then obtain authoritative provider evidence establishing exactly one of:

1. provider execution did not begin;
2. provider execution began and subsequently ceased;
3. provider execution completed.

The corresponding terminal candidate is submitted to the terminal arbiter under §74:

* case 1 (provider execution did not begin): the cancellation evidence is authoritative and the candidate is `CANCELLED`;
* case 2 (provider execution began and ceased): the cancellation evidence is authoritative and the candidate is `CANCELLED`;
* case 3 (provider execution completed): the candidate is `COMPLETED`.

If provider state remains ambiguous and cannot be authoritatively established before the recovery deadline, the prompt's terminal candidate is `FAILED` with `RECOVERY_FAILED`.

### Cancellation during RECOVERING

If `CANCEL_PROMPT` is accepted while the session is in `RECOVERING` and the prompt is in `CANCELLING`, the command fails with `INVALID_MESSAGE_STATE`. The prompt is already in `CANCELLING`; no second cancellation is accepted. The existing cancellation continues to be resolved by §75.

### Cancellation during RETRYING

If `CANCEL_PROMPT` is accepted while the session is in `RETRYING` with an active prompt, the prompt moves to `CANCELLING`. The in-flight retry is fenced by the cancellation. Terminal resolution follows the same rules as cancellation during `SUBMITTING`.

### Cancellation vs page-generation drift

If a page-generation change occurs while the prompt is in `CANCELLING`, the resulting `NAVIGATION_DRIFT` event is treated as evidence only. It does not by itself determine the prompt's terminal state. The prompt's terminal state is determined exclusively by the terminal arbitration defined in §74.

---

# 73. Cancellation evidence

Terminal CANCELLED requires positive provider cessation evidence.

"No new output appeared" alone is insufficient unless backed by an authoritative deadline invariant.

Submission success is NOT cessation evidence.

---

# 74. Terminal arbitration

Each prompt has exactly one terminal commit:

```text
COMPLETED
FAILED
CANCELLED
```

The arbiter serializes all terminal candidates. The first valid candidate that commits wins. Once committed, the prompt can never reopen.

### Terminal arbitration ownership

Once any terminal candidate has been submitted to the session arbiter, the prompt is resolved exclusively by this section. Navigation drift, cancellation uncertainty, timeout, provider failure, recovery failure, revision gap, response size limits, generation buffer limits, and provider unavailability are **evidence sources**; none of them bypasses terminal arbitration. In particular:

* A `CANCEL_PROMPT` acceptance submits a cancellation candidate.
* A provider completion observation submits a completion candidate.
* A provider failure observation submits a failure candidate.
* A timeout expiry submits a failure candidate with `PROMPT_TIMEOUT`.
* A navigation-drift observation submits a failure candidate with `NAVIGATION_DRIFT`.
* A recovery failure observation submits a failure candidate with `RECOVERY_FAILED`.
* A `PROVIDER_CHANGED` provider-context invalidation submits a failure candidate with `PROVIDER_UNAVAILABLE`.

The arbiter commits exactly one of these candidates, using the first valid candidate that commits as the winner. All other candidates are discarded. No candidate receives priority over any other candidate by virtue of its source.

### Session transitions are separate

Session state transitions (e.g. `BUSY -> PREPARING` on provider invalidation, `RECOVERING -> FAILED` on recovery failure) are distinct from prompt terminal arbitration. A session transition MAY be committed atomically with a terminal candidate submission, as §42.1 requires for provider-context invalidation; the session transition does not depend on whether the candidate subsequently wins prompt arbitration.

### Interaction of §75 and §76

If a prompt is in `CANCELLING` and a navigation drift occurs, the navigation drift does not independently fail the prompt. It is recorded as evidence. The prompt's terminal state is then determined by the arbiter per §74.

---

# 75. Cancellation failure and recovery terminal resolution

If cancellation is accepted by the gateway but provider cessation cannot be immediately verified:

The session transitions to `RECOVERING` while the prompt remains in the nonterminal state `CANCELLING`.

### Recovery Resolution Rules:

Recovery-established terminal evidence enters the exact same first-commit-wins terminal arbitration mechanism defined in §74. Recovery does not receive any priority over ordinary completion or cancellation evidence.

1. If recovery establishes that provider cessation succeeded and its terminal candidate wins arbitration:
   ```text
   prompt:  CANCELLING -> CANCELLED
   session: RECOVERING -> READY
   ```
2. If recovery establishes that the provider completed generation before cancellation took effect and its terminal candidate wins arbitration:
   ```text
   prompt:  CANCELLING -> COMPLETED
   session: RECOVERING -> READY
   ```
3. If recovery cannot establish authoritative state or the recovery deadline expires:
   ```text
   prompt:  CANCELLING -> FAILED (error: RECOVERY_FAILED)
   session: RECOVERING -> FAILED
   ```

The session transition on recovery failure is `RECOVERING -> FAILED` unconditionally. A subsequent `RESET_SESSION` (or an internal reset-equivalent transition) is required to leave `FAILED`.

If a navigation drift occurs during recovery, it is recorded as evidence but does not independently fail the prompt. The prompt's terminal state is determined by §74.

---

# 76. Navigation drift during active prompt

Navigation drift during any active page-dependent prompt operation invalidates page-dependent operations. The active page-dependent prompt states are:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
CANCELLING
```

When navigation drift occurs in any of these states, the prompt's terminal outcome is determined by the terminal arbitration defined in §74, using the navigation-drift observation as a failure candidate (`NAVIGATION_DRIFT`) unless a terminal candidate has already been committed. The session enters `RECOVERING` (or remains in `RECOVERING` if already recovering).

The `partial` flag on the resulting `GENERATION_FAILED` event MUST be set according to the following normative rule:

```text
partial = true   if authoritative response content has already been committed at least once for the prompt
partial = false  otherwise
```

This rule is historical: once any authoritative response content has been committed for the prompt, `partial` remains `true` for the remainder of the prompt's lifetime. A later `REPLACE` operation that produces an empty string MUST NOT cause `partial` to revert to `false`.

This rule applies uniformly to navigation drift failures, provider failures, recovery failures, generation buffer limit failures, response size limit failures, continuation failures, and provider unavailability failures. It is invalid to report `partial = true` when no authoritative response content has ever been committed.

---

# 77. RETRYING

RETRYING exists only for operations whose adapter proves retry safety without duplicating external actions.

Speculative replay of ambiguous submissions is forbidden.

### RETRYING is a session state, not a prompt state

`RETRYING` is a session execution state. It is not a member of the prompt lifecycle state set (§48). During `RETRYING` with an active prompt, the prompt remains in its current nonterminal lifecycle state unless a specific retry operation explicitly commits a prompt-state transition. An implementation MUST NOT invent a prompt state named `RETRYING`.

---

# 78. RETRYING transitions

With active prompt:

```text
BUSY -> RETRYING
RETRYING -> BUSY
```

Without active prompt:

```text
PREPARING -> RETRYING
RETRYING -> PREPARING
```

If retry fails: `RETRYING -> FAILED`.

---

# 79. Prompt resumability

A prompt is resumable only when:

1. provider submission state is known;
2. provider-side operation is attributable to the prompt;
3. page generation is validated;
4. continuation will not duplicate external execution.

---

# 80. Response and generation buffer size limits

Two distinct limits exist:

* `max_response_size`: the protocol-level bound on accumulated response content retained for delivery to the client. This limits the semantic provider response as observed by the client.
* `max_generation_buffer_mb`: the internal gateway buffering bound on transient generation data used by the adapter before or during commit. This is a **gateway resource limit**, not a semantic provider-response limit. Clients MUST NOT interpret `max_generation_buffer_mb` as a maximum possible provider answer size.

These limits MUST NOT be conflated.

If accumulated response content exceeds `max_response_size`, the prompt submits a `RESPONSE_TOO_LARGE` terminal failure candidate (`partial = true`) to the arbiter of §74.

If accumulated transient generation data exceeds `max_generation_buffer_mb`, the prompt submits a `GENERATION_BUFFER_LIMIT` terminal failure candidate (`partial = true`) to the arbiter of §74.

In both cases, if the candidate wins arbitration and the prompt terminally fails, existing committed content is preserved and the session enters `RECOVERING`.

An implementation MUST NOT treat the limit violation as bypassing terminal arbitration. The prompt becomes terminally `FAILED` only if the corresponding candidate wins arbitration under §74.

# 84. Event queue overflow

Event queue overflow is fail-closed.

If session event storage exceeds `max_queued_events`, the gateway MUST produce `EVENT_QUEUE_OVERFLOW` and transition to `FAILED`.

The transition to `FAILED` is deterministic; an implementation MUST NOT choose `RECOVERING` for this condition. Because the gateway has violated the client's event-observation contract, silent repair via recovery is not permitted; the session must be explicitly reset to resume.

---

# 85. Session event sequence

All session-scoped events have:

```text
session_id != null
request_id = null
sequence = uint64-string
```

Sequence numbers are monotonic, arbiter-allocated, never repeat, never reset, and survive `RESET_SESSION`.

### Global event correlation rule

The authoritative statement is in §11.4. It is reproduced here only as a cross-reference and MUST NOT be treated as an independent normative statement: for every session-scoped asynchronous event, `envelope.request_id` MUST be `null` and the binary `header.request_uuid` MUST be the all-zero nil UUID. Correlation with an originating command or operation MUST be carried inside operation-specific payload fields.

---

# 86. Sequence allocation

First event: `sequence = "1"`. Subsequent events increment by 1.

Overflow beyond uint64 produces `EVENT_SEQUENCE_OVERFLOW` and fails closed.

---

# 87. Event ordering

The sequence value defines authoritative event order.

Two events MUST NOT share a sequence number. Sequence numbers MUST NOT decrease.

---

# 88. Sequence gaps at receiver

Receiving N+1 before N MUST report `EVENT_SEQUENCE_GAP` unless replayed via `ext-replay-store`.

---

# 89. Generation event sequencing

The following events consume session sequence numbers:

```text
SESSION_READY
SESSION_CHANGED
NAVIGATION
NAVIGATION_DRIFT
```

# 91. Actor fencing

Every asynchronous provider/browser operation whose result may outlive the initiating actor MUST be associated with the following fencing context:

```text
provider            (nullable; see below)
session_id
page_generation
actor_instance
prompt_request_id   (nullable; see below)
```

`prompt_request_id` is nullable:

```text
prompt_request_id = prompt UUID when the operation is prompt-associated;
                  null otherwise.
```

Operations that may exist without an active prompt include session preparation, tab discovery, provider readiness inspection, recovery, and browser navigation handling. For such operations, `prompt_request_id` MUST be `null`.

### Provider identity binding

The fencing context is partitioned into two classes of operations:

* **Provider-context operations.** Operations that produce, observe, or affect provider state. These MUST carry a non-null `provider` identity matching the session's authoritative provider. Provider-context operations include, without limitation: `PROVIDER_ERROR`, `PROVIDER_AUTH_REQUIRED`, `PROVIDER_RATE_LIMITED`, `PROVIDER_CHANGED`, submission evidence, generation evidence, cessation evidence, completion evidence, and provider readiness inspection.

* **Non-provider browser operations.** Operations that do not produce, observe, or affect provider state. These MAY carry a null `provider` identity. Non-provider browser operations include, without limitation: session preparation before provider binding is established, tab discovery not specifically attributable to a provider, and browser navigation handling not specifically attributable to a provider. If a non-provider browser operation includes a `provider` field, it MUST be `null`.

Every provider-context operation's evidence MUST be discarded as stale if its `provider` identity does not match the session's authoritative provider at the time the evidence is evaluated. This rule applies to all provider-context operations, including but not limited to those enumerated above.

This closes the stale-provider race in which a superseded provider context produces evidence that would otherwise be attributed to the current session.

### Fencing discard

Results with stale fencing identifiers MUST be discarded. An operation whose `prompt_request_id` is non-null MUST additionally be discarded if the referenced prompt is no longer the active prompt of the session, or if the prompt has reached a terminal state.

### Multi-actor page-generation fencing

A session MAY have one or more subordinate browser actors beneath the top-level session actor. Every subordinate actor MUST carry:

* the `page_generation` value that was current when the subordinate actor was created;
* its own `actor_instance` identifier, unique for its lifetime.

A result produced by a subordinate actor is acceptable only if:

1. the subordinate actor's `page_generation` matches the session's current `page_generation`;
2. the subordinate actor's `actor_instance` matches the actor's currently valid identifier for that session;
3. if the operation is prompt-associated, the `prompt_request_id` matches the session's active prompt;
4. if the operation is a provider-context operation, the `provider` identity matches the session's authoritative provider.

A top-level `page_generation` change invalidates all nested subordinate actors. Any subsequent result from a subordinate actor bound to the prior `page_generation` MUST be discarded and reported as `STALE_ACTOR`.

Subordinate actors MAY be independently invalidated. Independent invalidation of a subordinate actor MUST change that subordinate actor's `actor_instance`. Subsequent results from the prior subordinate `actor_instance` MUST be discarded as `STALE_ACTOR`, even if the top-level `page_generation` is unchanged.

Subordinate actors MUST NOT have independent read/write `page_generation` values.

### Forward reference

For the requirement that completion evidence specifically carries a non-null `prompt_request_id`, see §131.

---

# 92. Actor instance

`actor_instance` is unique for an actor's lifetime. Replacement of a top-level actor increments `page_generation`. Replacement of a subordinate actor changes that subordinate actor's `actor_instance` and MAY or MAY NOT increment the top-level `page_generation`.

# 101. Keepalive timing and liveness

The keepalive mechanism is defined only when `ext-pong` is present in the final negotiated feature set. If `ext-pong` is not negotiated, the gateway MUST NOT emit unsolicited `PONG` frames.

When `ext-pong` is negotiated and `keepalive.enabled` is true:

1. `interval_ms` MUST be greater than `0`.
2. `idle_timeout_ms` MUST be greater than `0`.
3. `interval_ms` MUST be strictly less than `idle_timeout_ms`.
4. The gateway maintains two monotonic timestamps per connection:
   * `last_outbound_protocol_time`: the time of the most recent protocol frame transmitted by the gateway on this connection.
   * `last_inbound_authenticated_time`: the time of the most recent valid authenticated inbound frame received from the peer.
5. When `now - last_outbound_protocol_time >= interval_ms`, the gateway emits an unsolicited `PONG`. Emitting this `PONG` updates `last_outbound_protocol_time`.
6. Valid authenticated inbound frames update `last_inbound_authenticated_time`.
7. An `ERROR` frame generated by invalid traffic does not constitute positive liveness and MUST NOT update `last_inbound_authenticated_time`.
8. If `now - last_inbound_authenticated_time >= idle_timeout_ms`, the connection MUST close.

All timing decisions MUST use a monotonic clock. Implementations MUST NOT use raw TCP byte activity as a substitute for `last_outbound_protocol_time` or `last_inbound_authenticated_time`.

## 109.1 Replay enumeration atomicity

`GET_EVENTS` enumeration is atomic with respect to the retained event history. The following rules are normative:

1. The gateway captures a single atomic snapshot of the retained event history at the moment the request is processed.
2. Concurrent additions to the history do not appear in the response; they are observable only through subsequent `GET_EVENTS` calls or through live event delivery.
3. Concurrent evictions do not modify the captured snapshot; the snapshot is taken against the state of the history at capture time.
4. Gaps within the captured snapshot are not permitted. The response MUST contain a contiguous run of sequence numbers beginning at `from_sequence`, ending no later than `current_last_sequence`, and containing at most `max_events` entries.
5. `next_sequence` MUST be retained by the client for subsequent `GET_EVENTS` calls.

### `next_sequence` is normative

When the returned `events` array is non-empty, `next_sequence` MUST equal the sequence number of the last returned event plus exactly `1`:

```text
next_sequence = last_returned_sequence + 1
```

When the returned `events` array is empty, `next_sequence` MUST equal `from_sequence`.

An implementation MUST NOT return any other value for `next_sequence`.

6. Retention expiration during enumeration MUST NOT produce a partial or gapped result. If the earliest retained sequence is greater than `from_sequence`, the gateway MUST reject with `EVENT_HISTORY_EXPIRED` (§110). If the earliest retained sequence is less than or equal to `from_sequence`, the snapshot MUST be taken from the retained history at capture time.
7. `complete` is `true` if and only if the returned `events` array reaches the current last sequence at capture time. Otherwise `complete` is `false`.

---

# 110. Expired replay history

If `from_sequence` is older than the earliest retained sequence, the gateway MUST return `EVENT_HISTORY_EXPIRED`.

Skipping missing history is forbidden.

---

# 111. Replay snapshot semantics

`GET_EVENTS` captures an atomic snapshot of retained history. Concurrent additions or evictions do not modify the captured snapshot. See §109.1 for the complete normative enumeration rules.

---

# 112. Replay retention

Oldest sequence values are evicted first. Lower sequence wins eviction order.

Retention is bounded by `max_event_history_memory_mb`. `response_retention_ms` applies to prompt terminal records as defined in §106 and does not by itself bound event history retention.

---

# 113. Replay persistence

Application event history MAY be lost on restart; authentication replay state MUST survive.

# 115. BROWSER_STATUS

```text
request_uuid = nil

sequence = null
```

### Lifecycle emission points

BROWSER_STATUS is an unsolicited connection-scoped event and MUST be emitted in the following order and at the following times:

# 122. Event queue behavior

# 125. Session state and prompt state invariant

The following invariants are normative:

* A session has at most one active nonterminal prompt.
* `BUSY` is the exclusive-prompt-execution state. The session is `BUSY` exactly when it has one active nonterminal prompt and is not in `RECOVERING` or `RETRYING`.
* `RECOVERING` and `RETRYING` may coexist with an active nonterminal prompt.
* The session MUST NOT be `BUSY` when no active nonterminal prompt exists.

These invariants replace any prior statement of the form "`session.state = BUSY` iff the session has exactly one active nonterminal prompt", which was inconsistent with §75 and §78.

---

# 126. CLOSED invariant

CLOSED sessions have no active prompt, pending recovery, or pending retry, and cannot be mutated.

---

# 127. FAILED invariant

FAILED sessions cannot return to READY without an explicit reset/recovery transition.

# 129. Timeout fencing

# 130. Cancellation fencing

Cancellation arriving after terminal commit is stale and has no effect.

The nullability of `prompt_request_id` stated in §91 applies only to non-prompt-associated operations; it does not relax this requirement.

Completion evidence is also a provider-context operation, and therefore `provider` MUST be present and MUST match the session's authoritative provider at evaluation time.

# 140. Semantic-version downgrade test

Given:

```text
offered = ["!ext-pong"]
final = ["ext-pong"]
```

the final feature set differs from the offered feature set: the `!` required-feature marker is dropped. The transcript length is:

```text
164 bytes
```

The resulting client proof MUST differ from the proof produced by the vector in §139. Implementations MUST recompute both proofs from the transcript construction defined in §16.6.

The change from `!ext-pong` (9 bytes) to `ext-pong` (8 bytes) reduces the transcript length by exactly one byte per feature-set field, for a total reduction of one byte in the final-feature-set encoding. The client-proof and server-proof transcripts for the downgrade case are therefore both 164 bytes.

# 141. Header conformance tests

The implementation MUST reject invalid magic, wire versions other than 0x00, header length != 48, nonzero reserved bits, payload length exceeding limit, unknown message types, and header/envelope identity mismatches.

---

# 142. Unknown message tests

Unknown binary type: `0x7FFF` results in `UNKNOWN_MESSAGE_TYPE`.

Known binary type with mismatching envelope type results in `HEADER_JSON_MISMATCH`.

---

# 143. Session concurrency test

Two concurrent PROMPT commands against READY produce exactly one `ACCEPTED` and one `SESSION_BUSY`.

---

# 144. Generation ordering test

Revisions 1, 2, 3 accepted. 1, 3 causes `REVISION_GAP`. 1, 2, 2 discards duplicate 2.

---

# 145. Continuation test

Given `max_continuations = 0`, provider continuation request immediately produces `GENERATION_FAILED` with `CONTINUATION_NOT_ALLOWED`. The `partial` flag is determined by §76 (`partial = true` iff authoritative response content has been committed at least once for the prompt, otherwise `false`).

Given `max_continuations > 0` and the bound reached, provider continuation request immediately produces `GENERATION_FAILED` with `CONTINUATION_LIMIT_REACHED`. The `partial` flag is determined by §76.

Given an adapter that does not support continuation for the current prompt, a provider continuation request produces `GENERATION_FAILED` with `CONTINUATION_NOT_AVAILABLE`. The `partial` flag is determined by §76.

---

# 146. Cancellation test

CANCEL_PROMPT during GENERATING transitions to `CANCELLING`, then to `GENERATION_CANCELLED` only upon verified cessation.

CANCEL_PROMPT against a prompt already in `CANCELLING` fails with `INVALID_MESSAGE_STATE`.

CANCEL_PROMPT against a terminal prompt fails with `PROMPT_ALREADY_TERMINAL`.

---

# 147. Completion/cancellation race test

The first terminal commit between completion and cancellation evidence wins. Recovery-established evidence enters the same arbitration and receives no priority. Provider-context invalidation commits its session transition atomically with its terminal candidate submission (§42.1), regardless of which terminal candidate wins prompt arbitration.

---

# 148. Prompt timeout test

Timeout committing before terminal completion permanently fails the prompt with `PROMPT_TIMEOUT`.

---

# 149. Recovery deadline test

Unresolved recovery deadline expiry fails prompt with `RECOVERY_FAILED`. Session transitions unconditionally to `FAILED` (§96).

---

# 150. Navigation drift test

Page generation change during any active page-dependent prompt state causes `NAVIGATION_DRIFT` and session recovery. The `partial` flag on the resulting failure MUST follow the normative rule in §76, including its historical semantics.

---

# 151. Rate-limit test

Rate limit submits a `PROVIDER_RATE_LIMITED` terminal candidate; upon commit, session enters `RATE_LIMITED`, clears to `PREPARING` -> `READY`.

---

# 152. Authentication-required test

Auth loss submits a `PROVIDER_AUTH_REQUIRED` terminal candidate; upon commit, session enters `AUTH_REQUIRED`, clears to `PREPARING` -> `READY`.

---

# 153. Event sequence test

Event sequence continues monotonically across `RESET_SESSION`.

---

# 154. Replay expiration test

Requesting sequence older than earliest retained returns `EVENT_HISTORY_EXPIRED`.

---

# 155. Replay snapshot test

`GET_EVENTS` returns atomic history snapshot unaffected by concurrent additions/evictions. See §109.1.

---

# 156. Event queue overflow test

Queue storage exceeding `max_queued_events` produces `EVENT_QUEUE_OVERFLOW` and deterministically fails the session (`FAILED`), per §84.

---

# 157. Extension flag test

Unnegotiated extension flag bits produce `UNSUPPORTED_FEATURE`.

---

# 158. JSON duplicate-key test

Duplicate object member names MUST be rejected.

---

# 159. Prompt opacity test

Input bytes `20 20 41 0D 0A 42 0A 43 0D 0A 43 61 66 65 CC 81 20 20` preserved exactly.

---

# 160. Capability limit test

Handshake payloads exceeding 1 MiB rejected even if application `max_payload_bytes` is larger.

# 165. Determinism invariants

Arbiter defines commit ordering. Timestamps are informational. Timeouts use monotonic clocks. Replay snapshots are atomic. Eviction is sequence-based. Feature ordering is raw UTF-8 byte ordering.

---

# 166. Failure philosophy

Fail-closed: when authoritative state cannot be proven, implementation MUST transition to explicit error or recovery.

---

# 167. Provider adapter contract

Adapter must expose authoritative evidence for all states and cessation; no guessing permitted.

---

# 168. Browser actor replacement

Actor replacement increments `page_generation`. Stale callbacks cannot mutate new generations. Subordinate actors are additionally fenced by their own `actor_instance` and by the `page_generation` under which they were created; a top-level generation change invalidates all subordinate actors with `STALE_ACTOR`. Subordinate actors do not have independent read/write generations.

---

# 169. Process restart

Session/event history MAY be lost; authentication replay protection MUST NOT be lost while secret remains active.

# 177. Final normative statement

GARP/1.24 defines a deterministic, authenticated, fenced browser AI gateway protocol.

Its fundamental contract is:

```text
authenticate
    ↓
negotiate
    ↓
identify session
    ↓
establish browser/provider state
    ↓
reserve exactly one prompt
    ↓
verify input
    ↓
verify submission
    ↓
observe generation
    ↓
enforce message and revision order
    ↓
handle continuation explicitly
    ↓
handle cancellation explicitly
    ↓
commit exactly one terminal outcome
    ↓
retain/replay committed state where supported
```

At every stage, uncertainty is represented explicitly.

No implementation may convert uncertainty into an assumed successful provider action.
