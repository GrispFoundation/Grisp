# GARP/1.03

## Gateway AI Runtime Protocol

### Normative Specification

**Status:** Draft / Implementation Specification
**Protocol:** GARP/1.03
**Wire Version Byte:** `0x13`
**Previous Version:** GARP/1.02 (`0x12`)
**Transport:** TCP
**Encoding:** Binary GARP frame with UTF-8 JSON payloads
**Default TCP Endpoint:** `127.0.0.1:9999`

---

# Part I — Architecture and Protocol Model

## 1. Purpose

GARP defines a deterministic transport and browser-automation boundary between an external controller and browser-hosted AI providers.

GARP provides:

* browser tab management;
* provider session management;
* provider readiness detection;
* prompt injection;
* verified provider submission;
* generation observation;
* cancellation;
* continuation;
* provider and browser diagnostics;
* authenticated transport;
* deterministic request/event correlation.

GARP does **not** define:

* semantic correctness of AI responses;
* GRISP artifact validity;
* compilation correctness;
* program execution correctness;
* policy acceptance of generated artifacts;
* model quality;
* semantic scoring.

The browser/provider side is an untrusted semantic boundary. GARP transports observations; the downstream GRISP system determines whether those observations are acceptable.

---

# 2. Fundamental Architectural Rule

GARP/1.03 adopts one mandatory command-response architecture:

> **Every client command is answered synchronously by exactly one `RESPONSE` message.**

No command may use a command-specific message type as its synchronous response.

Therefore:

```text
COMMAND
    |
    v
RESPONSE
```

is the universal synchronous request/response pattern.

Asynchronous notifications use distinct semantic event message types:

```text
SESSION_READY
SESSION_CHANGED
INPUT_SUBMITTED
GENERATION_STARTED
GENERATION_DELTA
GENERATION_PROGRESS
CONTINUATION_REQUIRED
CONTINUATION_SUBMITTED
GENERATION_COMPLETED
GENERATION_FAILED
NAVIGATION
PROVIDER_ERROR
AUTH_REQUIRED
RATE_LIMITED
DIAGNOSTIC
```

These event messages are never command replies.

## 2.1 Example

The command:

```text
LIST_TABS
```

always receives:

```text
RESPONSE
```

with:

```json
{
  "command": "list_tabs",
  "success": true,
  "result": {
    "tabs": []
  }
}
```

It MUST NOT receive `LIST_TABS` as a response.

Likewise:

```text
CAPABILITIES
    -> RESPONSE

BROWSER_STATUS
    -> RESPONSE

CREATE_SESSION
    -> RESPONSE

OPEN_TAB
    -> RESPONSE

SELECT_TAB
    -> RESPONSE

PROMPT
    -> RESPONSE
```

The events emitted as a result of those operations are separate.

---

# 3. Why This Convention Is Normative

The single-response convention eliminates four classes of ambiguity:

1. A client does not need to maintain a table of which commands return themselves and which return `RESPONSE`.
2. Every request has one authoritative synchronous completion message.
3. Event messages cannot accidentally be interpreted as command completion.
4. Forward compatibility is improved because new commands automatically inherit the same response mechanism.

The command's semantic result is carried inside:

```text
RESPONSE.payload.result
```

The asynchronous lifecycle remains event-driven.

---

# 4. Command/Event Separation

GARP distinguishes:

### 4.1 Commands

Commands are requests initiated by the client.

Registered commands:

```text
HELLO
HELLO_AUTH
CAPABILITIES
BROWSER_STATUS
LIST_TABS
OPEN_TAB
CLOSE_TAB
SELECT_TAB
CREATE_SESSION
ATTACH_SESSION
DETACH_SESSION
CLOSE_SESSION
RESET_SESSION
PROMPT
CANCEL_PROMPT
GET_PROMPT_STATUS
GET_RESPONSE
SUBSCRIBE_RESPONSE
PING
```

### 4.2 Events

Events are generated by the gateway.

Registered events:

```text
HELLO_CHALLENGE
SESSION_READY
SESSION_CHANGED
INPUT_SUBMITTED
GENERATION_STARTED
GENERATION_DELTA
GENERATION_PROGRESS
CONTINUATION_REQUIRED
CONTINUATION_SUBMITTED
GENERATION_COMPLETED
GENERATION_FAILED
NAVIGATION
PROVIDER_ERROR
AUTH_REQUIRED
RATE_LIMITED
DIAGNOSTIC
PONG
```

`RESPONSE` is neither a command nor a lifecycle event. It is the universal synchronous command-result envelope.

`ERROR` is the transport/protocol failure mechanism and is not a normal command result.

# 6. Deprecated 1.02 Response Messages

GARP/1.02 permitted command-specific acknowledgment types such as:

```text
PROMPT_ACK
CANCEL_ACK
```

GARP/1.03 removes this architectural ambiguity.

`PROMPT_ACK` and `CANCEL_ACK` are retained in the numeric registry only for decoding old frames where required by compatibility implementations, but are **deprecated** and MUST NOT be emitted by a conforming GARP/1.03 implementation.

Their functions are replaced by:

```text
PROMPT -> RESPONSE
CANCEL_PROMPT -> RESPONSE
```

The actual asynchronous prompt lifecycle is reported by events.

# 7. Universal Command Response Model

Every command except `HELLO_AUTH` during the handshake exception described below follows:

```text
COMMAND
    ->
RESPONSE
```

The response contains:

```json
{
  "command": "command_name",
  "success": true,
  "result": {}
}
```

or:

```json
{
  "command": "command_name",
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable description",
    "retryable": false,
    "state": "ERROR"
  }
}
```

The outer GARP frame carries the authoritative correlation:

```text
request_id
```

The `command` field identifies the originating command.

---

# 8. Command Response Invariant

For each accepted request:

```text
request_id = X
```

there MUST be exactly one synchronous:

```text
RESPONSE(request_id = X)
```

A conforming implementation MUST NOT emit two successful or failed synchronous responses for one request.

Lifecycle events may subsequently use the same `request_id`.

---

# 9. Event Correlation

Events generated because of a command SHOULD include:

```text
request_id
session_id
message_id
sequence
page_generation
timestamp
```

when applicable.

For generation requests:

```text
PROMPT
  |
  +--> RESPONSE
  |
  +--> INPUT_SUBMITTED
  +--> GENERATION_STARTED
  +--> GENERATION_DELTA*
  +--> GENERATION_PROGRESS*
  +--> CONTINUATION_REQUIRED?
  +--> CONTINUATION_SUBMITTED?
  +--> GENERATION_COMPLETED
```

or:

```text
PROMPT
  |
  +--> RESPONSE
  |
  +--> GENERATION_FAILED
```

# 11. Prompt Lifecycle

The authoritative prompt path is:

```text
READY
  |
  v
INJECTING
  |
  v
INJECTION_VERIFIED
  |
  v
SUBMITTING
  |
  v
SUBMISSION_VERIFIED
  |
  v
GENERATION_STARTED
  |
  v
STREAMING
  |
  +--> CONTINUATION_REQUIRED
  |       |
  |       v
  |   CONTINUATION_SUBMITTED
  |       |
  |       +----> STREAMING
  |
  v
GENERATION_COMPLETED
```

No event named `GENERATION_STARTED` may be emitted before verified provider submission.

No `INPUT_SUBMITTED` event may be emitted unless:

1. the prompt was injected;
2. the resulting input was verified;
3. a provider submission mechanism was successfully executed and verified.

---

# 12. Readiness

A session entering `PREPARING` does not imply readiness.

A client MUST NOT infer readiness from:

* elapsed time;
* tab creation;
* browser navigation initiation;
* `about:blank` replacement;
* actor creation.

Readiness is established only from provider inspection.

`SESSION_READY` means:

```text
session.state = READY
inputState = READY
provider input exists and is usable
```

A session that remains preparing MUST use:

```text
SESSION_CHANGED
```

or:

```text
DIAGNOSTIC
```

rather than falsely emitting `SESSION_READY`.

---

# 13. Page Generation

Every session has:

```text
page_generation
```

The value:

* starts at a positive integer;
* monotonically increases;
* identifies the logical browser document/actor generation.

It MUST increase when the active provider document is replaced in a way that can invalidate DOM references, including relevant:

* navigation;
* document replacement;
* actor replacement;
* conversation replacement;
* browser-side recreation of the provider page.

Cached DOM elements MUST NOT be treated as authoritative after generation change.

---

# 14. Actor Rebinding

`session_id` survives actor replacement.

The gateway MUST reacquire the current window-global/actor for every child operation.

A stale actor MUST NOT write state into a newer page generation.

Where necessary, the gateway MUST reject a stale child result with an appropriate diagnostic or protocol error.

---

# 15. Input Injection Requirements

Provider adapters are responsible for provider-specific input discovery.

A conforming adapter MUST distinguish:

```text
input discovered
input mutated
input mutation verified
submission mechanism discovered
submission executed
submission verified
```

These are distinct states.

The gateway MUST NOT assume that:

```text
element.value = prompt
```

means the provider received the prompt.

For controlled framework inputs, native setter/event techniques or equivalent provider-compatible mechanisms MUST be used.

After injection, the adapter MUST verify the current live input element.

DOM replacement after mutation MUST be detected.

---

# 16. Submission Requirements

A provider submission is successful only when the adapter can establish that a valid submission operation occurred.

Possible mechanisms include:

```text
button_click
keyboard_enter
form_submit
provider_specific
```

The adapter MUST NOT report:

```text
submit_method = successful
```

when no actual submission method was found.

---

# 17. Diagnostics

Diagnostics are centrally controlled by:

```text
--debug-ai-automation
```

Recommended levels:

```text
OFF
ERROR
BASIC
VERBOSE
TRACE
```

Diagnostics MAY include:

```text
timestamp
session_id
request_id
provider
tab_id
page_generation
actor_instance
operation
stage
severity
selector
candidate_count
element metadata
visibility
enabled state
input method
verification result
submission method
```

Diagnostics MUST NOT expose:

* authentication secrets;
* cookies;
* bearer tokens;
* HMAC secrets;
* passwords.

Prompt content MUST NOT be logged by default.

# Part II — Wire and Common Schema

# 18. Fixed Header

The fixed GARP header length is:

```text
48 bytes
```

The wire version for GARP/1.03 is:

```text
0x13
```

Payload encoding is UTF-8 JSON.

The exact binary header layout MUST remain stable within the specified version.

---

# 19. Common Message Envelope Fields

The following fields may appear in the JSON payload or be supplied as frame metadata according to the implementation's binary/JSON mapping.

### `request_id`

String.

Identifies a client request.

### `session_id`

String.

Identifies a logical browser/provider session.

### `message_id`

String.

Identifies an observed/generated response message.

### `sequence`

Unsigned integer.

Monotonically increasing within the relevant request event stream.

### `page_generation`

Unsigned integer.

Authoritative logical page generation.

### `timestamp`

RFC 3339 / ISO-8601 UTC timestamp.

# 96. HELLO_AUTH

## Type

```text
0x0007
```

## Direction

Client -> Gateway.

## Payload

```json
{
  "protocol": "GARP/1.03",
  "client_id": "string",
  "client_nonce": "string",
  "server_nonce": "string",
  "proof": "hex-or-base64"
}
```

## Proof

The proof is:

```text
HMAC-SHA256(
    shared_secret,
    "GARP/1.03" |
    client_id |
    client_nonce |
    server_nonce
)
```

The `HELLO_AUTH` numeric/semantic mapping is normative:

```text
0x0007 <-> "hello_auth"
```

Implementations MUST support both encoding and decoding of this type.

# Part V — Command/Response Rules

# 135. Mandatory Response Rule

For all commands:

```text
command -> exactly one RESPONSE
```

A conforming implementation MUST NOT choose between:

```text
command-specific response
```

and:

```text
RESPONSE
```

The choice has already been made by GARP/1.03:

```text
RESPONSE
```

is mandatory.

---

# 136. Event Rule

Events are independent of synchronous command completion.

For example:

```text
CREATE_SESSION
    ->
RESPONSE
    ->
SESSION_CHANGED*
    ->
SESSION_READY
```

and:

```text
PROMPT
    ->
RESPONSE
    ->
INPUT_SUBMITTED
    ->
GENERATION_STARTED
    ->
GENERATION_DELTA*
    ->
GENERATION_COMPLETED
```

The event sequence MAY continue after the corresponding `RESPONSE`.

---

# 137. No Semantic Overloading

A message MUST NOT serve simultaneously as:

* command result;
* event;
* transport error.

In particular:

```text
SESSION_READY
```

is never a response to:

```text
CREATE_SESSION
```

It is an asynchronous event indicating later readiness.

---

# 138. Request Identity

Every command that initiates an asynchronous operation MUST have a unique:

```text
request_id
```

`request_id` reuse is forbidden unless it is an exact replay of the same logical request and the implementation explicitly supports idempotent replay.

Otherwise the gateway MUST return:

```text
REQUEST_ID_REUSE
```

---

# 139. Prompt Identity

A prompt request has:

```text
request_id
message_id
session_id
```

`request_id` identifies the operation.

`message_id` identifies the resulting provider response.

These identifiers MUST NOT be conflated.

---

# 140. Sequence

Within one request event stream:

```text
sequence
```

MUST be monotonically increasing.

Consumers MUST be able to detect:

* duplicate events;
* reordered events;
* missing events.

---

# Part VI — Validation

# 141. Validation Order

A receiver MUST validate in this order:

1. frame structure;
2. protocol version;
3. message type;
4. payload encoding;
5. JSON syntax;
6. message schema;
7. authentication state;
8. request identity;
9. session identity;
10. state transition;
11. provider-specific semantics.

Invalid messages MUST fail closed.

---

# 142. Unknown Fields

Unknown fields MAY be ignored unless explicitly marked normative.

Unknown message types MUST NOT be silently reinterpreted as known message types.

---

# 143. Required Field Enforcement

Required fields MUST be present.

Wrong JSON types MUST cause validation failure.

Example:

```json
{
  "page_generation": "two"
}
```

is invalid.

It MUST NOT be coerced to:

```text
2
```

# Part VIII — Security

# 150. Authentication

GARP authentication uses HMAC-SHA256.

The shared secret MUST never be transmitted directly.

The challenge/response material incorporates:

```text
protocol
client_id
client_nonce
server_nonce
```

This prevents replay of an earlier handshake transcript.

---

# 151. Secret Handling

Implementations MUST NOT log:

```text
shared_secret
HMAC proof input
cookies
session tokens
provider passwords
authorization headers
```

---

# 152. Prompt Confidentiality

Prompts and provider responses may contain sensitive information.

Therefore diagnostics MUST default to metadata-only reporting.

Raw prompt logging is disabled by default.

# Part IX — Conformance Invariants

# 153. Core Invariants

### I1

GARP/1.03 wire version is `0x13`.

### I2

The fixed header is 48 bytes.

### I3

`0x0007` maps to `HELLO_AUTH`.

### I4

`HELLO_AUTH` is normative and bidirectionally encoded/decoded.

### I5

Every command has exactly one synchronous `RESPONSE`.

### I6

Command-specific synchronous response message types are forbidden in GARP/1.03.

### I7

`PROMPT_ACK` MUST NOT be emitted.

### I8

`CANCEL_ACK` MUST NOT be emitted.

### I9

`SESSION_READY` means actual readiness.

### I10

Fixed sleeps are not readiness proof.

### I11

`INPUT_SUBMITTED` requires verified input injection.

### I12

`INPUT_SUBMITTED` requires verified provider submission.

### I13

`GENERATION_STARTED` occurs only after `INPUT_SUBMITTED`.

### I14

`page_generation` is monotonically increasing.

### I15

Stale actor state MUST NOT overwrite current page state.

### I16

`tab_id` is stable identity.

### I17

Tab index is not identity.

### I18

`request_id` identifies an operation.

### I19

`message_id` identifies the provider response.

### I20

Semantic correctness is outside GARP.

### I21

Provider-specific automation is isolated inside provider adapters.

### I22

Diagnostics are centralized.

### I23

Secrets are never emitted in diagnostics.

### I24

Raw prompts are not logged by default.

# 155. Required Event Sequence for Prompt

Minimum successful sequence:

```text
PROMPT
RESPONSE(success=true)
INPUT_SUBMITTED
GENERATION_STARTED
GENERATION_COMPLETED
```

Streaming generation adds zero or more:

```text
GENERATION_PROGRESS
GENERATION_DELTA
```

Continuation may add:

```text
CONTINUATION_REQUIRED
CONTINUATION_SUBMITTED
```

before subsequent generation events.

---

# 156. Required Failure Sequence

A failed prompt MAY produce:

```text
PROMPT
RESPONSE(success=true)
GENERATION_FAILED
```

when the request was accepted but execution later failed.

A command that cannot even be accepted produces:

```text
COMMAND
RESPONSE(success=false)
```

and does not start the asynchronous operation.

# Part X — Architectural Consequence for the Firefox Implementation

The Firefox implementation MUST therefore be reorganized around the following split:

```text
GarpConnection
    |
    v
AIAutomation
    |
    +--> command handler
    |       |
    |       +--> RESPONSE
    |
    +--> lifecycle/event broadcaster
            |
            +--> SESSION_READY
            +--> SESSION_CHANGED
            +--> INPUT_SUBMITTED
            +--> GENERATION_STARTED
            +--> GENERATION_DELTA
            +--> GENERATION_COMPLETED
            +--> ...
```

`GarpRequestManager` MUST NOT fabricate command-specific acknowledgment message types.

For example:

```js
connection.send("response", {
  command: "prompt",
  success: true,
  result: {
    request_id: request.requestId,
    session_id: request.sessionId,
    state: "ACCEPTED"
  }
});
```

rather than:

```js
connection.send("prompt_ack", ...);
```

Likewise:

```js
connection.send("response", {
  command: "list_tabs",
  success: true,
  result: { tabs }
});
```

rather than:

```js
connection.send("list_tabs", ...);
```

# Part XI — Compatibility

# 157. GARP/1.02 Compatibility

A GARP/1.03 implementation MAY accept incoming GARP/1.02 connections when explicitly configured for compatibility.

When operating in 1.03 mode:

* wire version MUST be `0x13`;
* normal command responses MUST use `RESPONSE`;
* deprecated 1.02 acknowledgment messages MUST NOT be emitted.

---

# 158. Migration Rule

The migration is therefore:

```text
GARP/1.02

LIST_TABS      -> LIST_TABS or RESPONSE
CAPABILITIES   -> CAPABILITIES or RESPONSE
PROMPT         -> PROMPT_ACK
CANCEL_PROMPT  -> CANCEL_ACK
```

to:

```text
GARP/1.03

LIST_TABS      -> RESPONSE
CAPABILITIES   -> RESPONSE
BROWSER_STATUS -> RESPONSE
CREATE_SESSION -> RESPONSE
PROMPT         -> RESPONSE
CANCEL_PROMPT  -> RESPONSE
PING           -> RESPONSE
```

with asynchronous lifecycle events remaining separate.

# Part XII — Final Architectural Principle

GARP/1.03 has exactly three fundamentally different message roles:

```text
1. COMMAND
2. RESPONSE
3. EVENT
```

plus:

```text
4. PROTOCOL ERROR
```

The governing model is:

```text
                 +------------------+
                 |      COMMAND     |
                 +---------+--------+
                           |
                           v
                 +------------------+
                 |     RESPONSE     |
                 +------------------+
                           |
                           |
              asynchronous execution
                           |
                           v
                 +------------------+
                 |      EVENTS      |
                 +------------------+
```

This is the canonical GARP/1.03 architecture.

There is no longer an implementation choice between command-specific response messages and generic `RESPONSE`.

**`RESPONSE` is the one and only synchronous command-result mechanism in GARP/1.03.**

The semantic event stream remains independently typed and is responsible for lifecycle progression, provider interaction, generation observation, diagnostics, navigation, and failures.
