**GARP/1.06**

## Gateway AI Runtime Protocol

### Consolidated Normative Specification

**Status:** Implementation-Ready  
**Protocol Identifier:** `GARP/1.06`  
**Wire Version:** `0x16`  
**Previous Wire Version:** `0x15` (`GARP/1.05`)  
**Transport:** TCP  
**Payload:** UTF-8 JSON  
**Default Endpoint:** `127.0.0.1:9999`

---

# Part I — Scope, Goals, and Architecture

## 1. Purpose

GARP (Gateway AI Runtime Protocol) defines an authenticated, stateful protocol between an external controller and a browser-resident AI automation gateway.

GARP provides a deterministic interface for:

* browser and tab management;
* provider discovery and capability advertisement;
* logical AI sessions;
* browser navigation tracking;
* provider readiness;
* prompt injection and verification;
* prompt submission and verification;
* generation observation and streaming;
* continuation;
* cancellation;
* provider error reporting;
* structured diagnostics;
* request correlation;
* response retention and retrieval;
* authenticated transport.

GARP does **not** define:

* AI semantic correctness;
* generated-code correctness;
* GRISP artifact acceptance;
* compilation or runtime correctness;
* policy acceptance;
* model quality;
* semantic scoring.

The intended architecture is:

```text
External Controller
       |
       | GARP/1.06
       v
Firefox AI Gateway
       |
       v
Provider Adapter
       |
       v
Browser / Provider
       |
       v
Untrusted AI Output
       |
       v
GRISP / Verification Layer
```

---

## 2. Trust Boundary

The browser and AI provider are outside the trusted semantic core.

GARP MUST treat:

* browser DOM state;
* provider UI state;
* provider-generated text;
* provider-generated metadata;
* model-generated source code

as observations originating from an untrusted environment.

GARP transports and verifies transport-level facts.  
It does not decide whether AI output is correct.

---

## 3. Architectural Model

GARP/1.06 has four message roles:

```text
COMMAND
RESPONSE
EVENT
PROTOCOL ERROR
```

### 3.1 Command
A client-originated operation request.

### 3.2 Response
The universal synchronous result of an ordinary command.

### 3.3 Event
An asynchronous notification of state, progress, generation, navigation, diagnostics, or provider conditions.

### 3.4 Protocol Error
A protocol-level failure that prevents normal command processing.

---

## 4. Universal Command Response Rule

Every ordinary command MUST have exactly one synchronous `RESPONSE`.

```text
COMMAND
   |
   v
RESPONSE
```

Command-specific synchronous response message types are forbidden.

Typed messages are used for asynchronous events only.

---

## 5. Handshake Exception

The initial authentication protocol has its own state machine:

```text
HELLO
  |
  v
HELLO_CHALLENGE
  |
  v
HELLO_AUTH
  |
  v
HELLO_ACK
```

Handshake messages are not normal command responses.  
Ordinary command processing MUST NOT begin before authentication succeeds.

---

## 6. Design Principle

GARP MUST distinguish:

```text
request accepted
```

from:

```text
operation executed
```

and:

```text
operation observed as successful
```

Example:

```text
PROMPT
  |
  +--> RESPONSE(ACCEPTED)
  |
  +--> INPUT_SUBMITTED
  |
  +--> GENERATION_STARTED
  |
  +--> GENERATION_COMPLETED
```

The initial `RESPONSE` establishes only gateway acceptance.

## 8. Version Isolation

The numeric registry, payload schemas, state semantics, and wire framing of GARP/1.06 form one coherent version.  
A receiver MUST NOT mix mappings or schemas from different versions.

## 9. Supported Versions

`HELLO` MAY contain:

```json
{
  "supported_versions": ["GARP/1.06", "GARP/1.05"]
}
```

Version downgrade MUST be explicit.

## 10. Version Mismatch

Unsupported wire version MUST terminate protocol processing.  
Preferred error: `UNSUPPORTED_VERSION`.

# Part III — Canonical Wire Format

## 11. Frame Structure

```text
48-byte fixed header
+
UTF-8 JSON payload
```

Frame length = `48 + payload_length`.

## 12. Byte Order

All integer fields in the binary header use network byte order (big-endian).  
No platform-native struct packing is permitted.

## 13. Maximum Payload

```text
16 MiB = 16,777,216 bytes
```

Maximum frame length: `16,777,264` bytes.  
Larger payloads MUST be rejected.

## 14. Fixed Header Layout

| Offset | Size | Field          | Encoding          |
|-------:|-----:|----------------|-------------------|
| 0      | 4    | Magic          | ASCII `GARP`      |
| 4      | 1    | Wire version   | `uint8` (`0x16`)  |
| 5      | 1    | Flags          | `uint8`           |
| 6      | 2    | Header length  | `uint16` BE       |
| 8      | 4    | Payload length | `uint32` BE       |
| 12     | 2    | Message type   | `uint16` BE       |
| 14     | 2    | Reserved       | MUST be zero      |
| 16     | 16   | Request ID     | UUID bytes        |
| 32     | 16   | Session ID     | UUID bytes        |

Total: 48 bytes.

## 15–23. Header Field Rules

- Magic MUST be `47 41 52 50` (`GARP`).
- Wire version MUST be `0x16`.
- Flags: all bits reserved; MUST be zero unless an explicit extension is negotiated.
- Header length MUST be 48.
- Payload length is the exact number of bytes following the header.
- Message type MUST match the semantic name in the registry.
- Request ID and Session ID in the header MUST match any corresponding JSON fields (or be the zero UUID when absent).
- UUID binary representation MUST correspond exactly to the canonical textual form used in JSON.

A mismatch between header and JSON identity fields is a protocol error (`HEADER_JSON_MISMATCH`).

# Part VI — Handshake and Authentication

## 29–40. Authentication

GARP/1.06 retains the mutual HMAC-SHA256 design of 1.05 with the following clarifications and hardenings:

- Nonces: 32 cryptographically random bytes, encoded as 64 lowercase hex characters.
- Transcripts remain length-prefixed and domain-separated:
  - Client: `GARP/1.06/CLIENT-AUTH`
  - Server: `GARP/1.06/SERVER-AUTH`
- Constant-time comparison is mandatory.
- Default handshake timeout: 10 seconds (configurable).
- Failed authentication terminates the handshake; a fresh handshake with fresh nonces is required.
- `HELLO_ACK` MUST contain a valid server proof before `authenticated` may be reported as true.

Additional requirement:  
Implementations MUST support secure storage and rotation of the shared secret.  
Compromise of the shared secret requires immediate invalidation of all existing sessions.

# Part XII — Readiness

## 64–67. Readiness Rules

Unchanged: readiness is observed state, never elapsed time.

# Part XIII — Page Generations and Actor Safety

## 68–72. Fencing

Unchanged.  
`page_generation` is a monotonic fencing token.  
Stale actor / stale generation results MUST be discarded or rejected with `STALE_ACTOR` / `STALE_PAGE_GENERATION`.

# Part XIV — Prompt Commands

## 73–79. PROMPT, CANCEL_PROMPT, GET_PROMPT_STATUS, GET_RESPONSE, SUBSCRIBE_RESPONSE

- Prompt text MUST NOT be trimmed, rewritten, or semantically mutated by the transport.
- `SUBSCRIBE_RESPONSE` supports optional `from_sequence` for replay.
- Subscriptions are connection-scoped.
- Response retention default remains 24 hours (advertised in `CAPABILITIES`).

---

# Part XV — Input Injection

## 80–86. Injection Rules

Unchanged core requirements:  
live discovery → injection → verification.  
Controlled-framework inputs require native value setters + appropriate events.  
Node replacement must be detected and re-queried.  
Prompt content is never logged by default (length and optional hash only).

---

# Part XVI — Provider Submission

## 87–91. Submission Rules

Verified submission is required before `INPUT_SUBMITTED`.  
`INPUT_SUBMITTED` MUST precede `GENERATION_STARTED`.

---

# Part XVII — Generation

## 92–102. Generation Observation

- `GENERATION_DELTA` carries explicit `mode: "DELTA" | "REPLACE"`.
- `revision` (provider text version) is independent of `sequence` (GARP event order).
- Revision gaps are detectable; clients SHOULD fall back to `GET_RESPONSE`.
- Completion is based on the strategy advertised in `CAPABILITIES`.
- `GENERATION_COMPLETED` is a transport-level terminal success only.

---

# Part XVIII — Continuation

## 103–106. Continuation

Bounded by `max_continuations` (default 8).  
Exceeding the limit terminates with `CONTINUATION_FAILED`.

---

# Part XIX — Cancellation

## 107–109. Cancellation Arbitration

The three concrete cases from 1.05 remain normative:

- Completion observed before cancellation acceptance → `COMPLETE` wins.
- Cancellation accepted and provider stop verified → `CANCELLED` wins.
- Cancellation accepted but provider completion observed first → `COMPLETE` wins.

Exactly one authoritative terminal state per request.

# Part XXII — Keepalive

## 123–125. PING / PONG

Recommended defaults: 30 s interval, 120 s idle timeout (configurable).  
Idle timeout is not mandatory unless explicitly configured.

# Part XXIII — Concurrency and Flow Control

## 126–134. Rules

- Multiple outstanding requests per connection are permitted.
- At most one active prompt per session.
- Events for a single request have strictly increasing `sequence` (starting at 1).
- Silent event loss is forbidden; back-pressure or explicit failure is required.
- Buffer limits MUST be defined and SHOULD be advertised in `CAPABILITIES`.

# Part XXXIII — Reconnection and Connection Loss

## 160–163. Policy

- Connection loss does not automatically destroy logical session or request state.
- Recommended policy: in-flight requests continue; responses remain retrievable for the retention period.
- Subscriptions are connection-scoped and are lost on disconnect.
- Reconnecting clients MUST perform a fresh handshake.
- Clients discover surviving state via `GET_PROMPT_STATUS`, `GET_RESPONSE`, and `SUBSCRIBE_RESPONSE`.

# Part XLIII — Security Considerations

## 211. Threat Model (Normative Summary)

GARP/1.06 assumes:

- The TCP connection may be local or network-exposed.
- The shared secret is the sole long-term authenticator.
- The browser and provider are untrusted.
- An attacker may attempt replay, identity confusion, or diagnostic leakage.

## 212. Required Protections

- Mutual authentication with domain-separated transcripts.
- Fresh nonces on every handshake.
- Constant-time proof verification.
- No secret material in diagnostics or logs.
- Header/JSON identity consistency checks.
- Fail-closed behaviour on any ambiguity.

## 213. Shared Secret Management

Implementations MUST provide a mechanism to rotate the shared secret.  
After rotation, all existing authenticated connections MUST be terminated and re-authenticated.

## 214. Recommendations

- Prefer localhost or mutually authenticated TLS for non-local deployments.
- Treat prompt and response content as sensitive; disable raw logging by default.
- Monitor for excessive authentication failures.

# Part XLIV — Final Normative Principles

## 215–228. Core Principles

All principles from GARP/1.05 remain in force.  
Additional explicit principles for 1.06:

- **Complete identity consistency** — binary and JSON identities never disagree.
- **Minimum adapter contract** — every provider adapter implements the defined operation set.
- **Observable diagnostics** — classic automation failure classes are distinguishable under debug.
- **Explicit retention and eviction** — clients can rely on advertised retention or receive a clear eviction signal.
- **Security as a first-class concern** — authentication, secret handling, and diagnostic hygiene are normative.

## 230. Status

GARP/1.06 is the consolidated normative successor to GARP/1.05.

It preserves the clean COMMAND / RESPONSE / EVENT architecture, the verified injection/submission model, page-generation fencing, and transport-only semantics, while adding:

- fully specified 48-byte framing (inherited and locked);
- mutual authentication with domain separation;
- rigorous identity consistency rules;
- explicit generation reassembly (`DELTA` / `REPLACE` + revision);
- concrete cancellation arbitration;
- normative minimum provider adapter contract;
- flow-control and retention guarantees;
- a dedicated Security Considerations section;
- expanded conformance requirements.

**GARP/1.06 is the recommended implementation target.**
