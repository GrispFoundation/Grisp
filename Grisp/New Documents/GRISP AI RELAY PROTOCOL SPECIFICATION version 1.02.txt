# GRISP AI RELAY PROTOCOL SPECIFICATION

## GARP/1.02

**Status:** NORMATIVE
**Version:** GARP/1.02
**Parent specifications:** GRISP Agent Specification v1.0; GRISP v1.0 Implementation Contract, Revision 2
**Semantic AI contract:** GAI/1.0
**Transport:** TCP localhost, UTF-8, length-framed binary envelope
**Default mode:** FAIL-CLOSED

---

# PART I — PROTOCOL SPECIFICATION

# 1. PURPOSE

GARP is the GRISP ↔ Firefox AI Gateway transport and browser-session protocol.

GARP makes Firefox a reliable, stateful, provider-independent AI transport and interaction endpoint rather than a loose JSON command socket or collection of ad-hoc DOM scripts.

GARP defines:

* connection handshake and feature negotiation;
* request identity;
* session identity;
* tab identity;
* response/message identity;
* sequence identity;
* browser AI session lifecycle;
* provider-input readiness;
* prompt injection;
* prompt injection verification;
* provider submission;
* provider submission verification;
* cancellation;
* continuation;
* streaming response events;
* provider adapter boundaries;
* structured errors;
* heartbeat;
* reconnection;
* page-generation tracking;
* Firefox actor replacement;
* stale-actor protection;
* local gateway security;
* deterministic transport state transitions;
* centralized AI automation diagnostics;
* operator-controlled AI automation debugging.

GARP does **not** define:

* artifact acceptance;
* compile semantics;
* runtime verification;
* GRISP policy;
* AI quality scoring;
* final acceptance;
* artifact identity or hashing;
* GAI semantic artifact structure.

Those belong to GRISP core, GAI/1.0, or the GRISP implementation contract.

The architectural boundary is:

```text
Firefox = provider interaction, observation, and transport
GRISP   = interpretation and verification
AI      = reasoning
tools   = measurement
policy  = authorization
```

The AI response transported by GARP is untrusted.

Diagnostic information is transport and implementation metadata. It SHALL NEVER alter semantic AI prompts or semantic AI responses.

---

# 2. DESIGN GOALS

GARP/1.02 SHALL provide:

1. stable request identity;
2. stable session identity;
3. stable tab identity;
4. provider-independent request correlation;
5. event-driven streaming;
6. explicit cancellation;
7. duplicate request suppression;
8. connection resilience;
9. page-generation tracking;
10. structured provider errors;
11. isolated provider adapters;
12. no semantic mutation by transport;
13. fail-closed behavior when state is unknown;
14. explicit session concurrency rules;
15. deterministic event ordering;
16. deterministic stale-state rejection;
17. explicit provider-input readiness;
18. verified prompt injection;
19. verified provider submission;
20. browser actor replacement resilience;
21. centralized structured AI automation diagnostics;
22. operator-controlled AI automation trace mode;
23. normative bidirectional message-type registry;
24. explicit separation between request acceptance and provider submission;
25. explicit separation between provider submission and generation start.

GARP SHALL NOT rely on newline-delimited JSON for message framing.

# 3. TERMINOLOGY

## 3.1 Client

The GRISP Agent or another trusted GRISP-side GARP client.

## 3.2 Gateway

The Firefox-side component implementing GARP.

## 3.3 Provider

An external AI service such as:

* ChatGPT;
* Gemini;
* Claude;
* DeepSeek;
* Grok;
* Copilot;
* Perplexity;
* Inception.

## 3.4 Adapter

A provider-specific Firefox module that knows how to:

* discover input;
* determine readiness;
* inject prompt text;
* verify injected prompt text;
* discover a submission mechanism;
* submit prompts;
* verify provider submission;
* observe generation;
* identify responses;
* detect continuation;
* perform continuation;
* cancel where supported;
* detect authentication;
* detect rate limits;
* detect provider errors;
* reset provider state.

## 3.5 Session

A logical AI conversation controlled through GARP.

A session is identified by `session_id`.

A session is associated with:

* provider;
* tab;
* conversation identity where available;
* session state;
* current page generation;
* current actor binding.

## 3.6 Tab

A Firefox browser tab with a stable `tab_id`.

`tab_index` is informational only.

## 3.7 Request

One AI operation identified by `request_id`.

## 3.8 Message

One AI response generation identified by `message_id`.

## 3.9 Event

An asynchronous GARP message describing state or generation progress.

## 3.10 Page Generation

A monotonically increasing integer associated with a session's current provider-page context.

It changes when the provider application context is significantly replaced, including navigation and JSWindowActor replacement.

## 3.11 Actor Instance

One concrete Firefox `JSWindowActorChild` instance associated with one page generation.

An actor instance SHALL NOT be assumed to survive navigation.

## 3.12 Sequence

A monotonically increasing integer associated with one event stream.

A stream is identified by:

```text
(request_id, message_id)
```

## 3.13 Provider Input

The concrete DOM element used by the provider to accept user prompt text.

## 3.14 Input Verification

Evidence that the requested prompt was actually accepted by the current provider input element and remained observable after the provider framework had an opportunity to process the input event.

## 3.15 Submission

The provider-side action that causes the entered prompt to be sent to the AI service.

Submission is distinct from input injection.

## 3.16 Submission Verification

Evidence that a provider submission method was actually invoked successfully according to the adapter contract.

## 3.17 Diagnostic Event

Structured internal or GARP-visible information describing AI automation execution.

Diagnostic information is non-semantic metadata.

# 4. IDENTITY MODEL

GARP SHALL distinguish:

```text
provider
model
session
browser_tab
conversation
worker_instance
actor_instance
request
message
page_generation
sequence
```

The following identities have independent meanings.

## 4.1 Provider Identity

Identifies the external AI provider.

Example:

```text
deepseek
```

## 4.2 Model Identity

Identifies the model used by the provider where the provider exposes one.

Model identity SHALL NOT be assumed equivalent to provider identity.

## 4.3 Session Identity

`session_id` identifies the logical browser AI conversation controlled by GARP.

It SHALL remain stable across:

* actor replacement;
* SPA navigation;
* ordinary reconnects.

## 4.4 Tab Identity

`tab_id` identifies a Firefox tab.

`tab_id` MUST NOT be derived from tab index.

`tab_index` MAY change without changing `tab_id`.

## 4.5 Request Identity

Every prompt operation SHALL have exactly one `request_id`.

## 4.6 Message Identity

Every response generation SHOULD have exactly one `message_id`.

Once established, `message_id` MUST NOT change during that generation.

## 4.7 Page Generation

Every session has an associated:

```text
page_generation : uint64
```

The initial value SHALL be nonzero.

Page generation SHALL strictly increase.

A stale event from an older page generation SHALL NOT overwrite state belonging to a newer page generation.

## 4.8 Actor Instance Identity

The gateway SHALL track the current actor instance associated with the session.

When the current actor instance changes:

```text
old actor
    ↓
new actor
    ↓
page_generation increases
```

A stale actor response SHALL NOT mutate authoritative session state.

## 4.9 Sequence

For one `(request_id, message_id)` stream:

```text
1, 2, 3, 4, ...
```

Sequence SHALL begin at `1`.

Sequence SHALL never silently reset within a stream.

# 5. TRANSPORT

## 5.1 Base Transport

GARP/1.02 SHALL use:

```text
TCP
localhost only
binary framing
UTF-8 JSON payload
```

The TCP connection SHALL NOT use newline termination as protocol framing.

---

# 6. GARP BINARY FRAME

Every frame SHALL begin with the following fixed header:

```text
magic[4]
version[1]
reserved[1]
header_length[2]
payload_length[4]
message_type[2]
reserved2[2]
request_id[16]
session_id[16]
payload[...]
```

The fixed header portion SHALL therefore be **48 bytes**.

All integer fields SHALL use unsigned big-endian encoding.

## 6.1 Magic

The first four bytes SHALL be:

```text
47 41 52 50
```

ASCII:

```text
GARP
```

## 6.2 Version

For GARP/1.02:

```text
version = 0x12
```

The wire version byte is authoritative.

## 6.3 Reserved Byte

The byte immediately following the version SHALL be zero unless a future explicitly negotiated extension assigns meaning to it.

## 6.4 Header Length

`header_length` SHALL be at least 48.

An implementation MAY support extended headers only when explicitly negotiated.

An implementation that does not support extended headers SHALL reject:

```text
header_length != 48
```

with:

```text
PROTOCOL_ERROR
```

## 6.5 Payload Length

`payload_length` is the exact number of payload bytes following the header.

It SHALL never include the header.

## 6.6 Message Type

`message_type` is a numeric registry identifier.

The JSON payload SHALL contain the corresponding human-readable `type`.

## 6.7 UUID Wire Encoding

`request_id` and `session_id` SHALL use raw 128-bit RFC 4122 UUID bytes.

The JSON representation SHALL use:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

## 6.8 Zero UUID

Messages without an applicable request or session identity SHALL encode all-zero bytes:

```text
00000000-0000-0000-0000-000000000000
```

in the binary header.

The JSON representation MAY omit the corresponding field where permitted by the message registry.

---

# 7. FRAME VALIDATION

The receiver SHALL reject a frame if:

* magic is invalid;
* protocol version is unsupported;
* header length is invalid;
* reserved fields are nonzero without negotiated meaning;
* payload length exceeds configured limits;
* message type is unknown;
* the frame is truncated;
* UTF-8 payload is invalid;
* JSON payload is invalid;
* JSON `protocol` is incompatible;
* JSON `type` does not match the numeric message type;
* required identity fields are missing.

Failure MUST be fail-closed.

A malformed frame SHALL NOT be partially processed.

---

# 8. FRAME SIZE LIMITS

GARP SHALL maintain configurable limits.

Recommended defaults:

```text
ordinary control payload     1 MiB
prompt payload              4 MiB
artifact/document payload  16 MiB
stream chunk               256 KiB
```

The implementation SHALL define one absolute maximum frame size that is at least 16 MiB.

A payload exceeding the applicable limit SHALL yield:

```text
FRAME_TOO_LARGE
```

and SHALL NOT be partially processed.

```text

0006 RESPONSE
0007 HELLO_AUTH

0010 LIST_TABS
0011 OPEN_TAB
0012 CLOSE_TAB
0013 SELECT_TAB

0020 CREATE_SESSION
0021 ATTACH_SESSION
0022 DETACH_SESSION
0023 CLOSE_SESSION
0024 RESET_SESSION

0030 PROMPT
0031 PROMPT_ACK
0032 CANCEL_PROMPT
0033 CANCEL_ACK
0034 GET_PROMPT_STATUS
0035 GET_RESPONSE
0036 SUBSCRIBE_RESPONSE

0040 SESSION_READY
0041 SESSION_CHANGED
0042 INPUT_SUBMITTED
0043 GENERATION_STARTED
0044 GENERATION_DELTA
0045 GENERATION_PROGRESS
0046 CONTINUATION_REQUIRED
0047 CONTINUATION_SUBMITTED
0048 GENERATION_COMPLETED
0049 GENERATION_FAILED

0050 NAVIGATION
0051 PROVIDER_ERROR
0052 AUTH_REQUIRED
0053 RATE_LIMITED
0054 DIAGNOSTIC

0060 PING
0061 PONG

00F0 ERROR
```

`HELLO_AUTH` is a first-class GARP/1.02 wire message.

It SHALL use:

```text
message_type = 0x0007
```

on the binary wire.

The corresponding JSON semantic type SHALL be:

```text
"hello_auth"
```

The mapping:

```text
0x0007 ↔ "hello_auth"
```

MUST exist in both directions in every conforming implementation:

```text
numeric message type → semantic message name
semantic message name → numeric message type
```

A conforming implementation SHALL support:

```text
encode("hello_auth") → 0x0007
decode(0x0007) → "hello_auth"
```

A missing mapping is a GARP/1.02 protocol implementation defect.

The implementation SHALL NOT require a compatibility patch, post-build modification, or provider-specific workaround to obtain a normative message mapping.

Unknown numeric message types SHALL result in:

```text
PROTOCOL_ERROR
```

unless a future negotiated extension explicitly permits them.

# 10. MESSAGE CLASSES

GARP defines:

```text
HELLO
COMMAND
RESPONSE
EVENT
ERROR
CONTROL
```

The numeric registry is authoritative for wire encoding.

The JSON `"type"` is authoritative for semantic interpretation.

Both MUST agree.

# 11. HANDSHAKE

The client SHALL initiate a connection with:

```json
{
  "protocol": "GARP/1.02",
  "type": "hello",
  "payload": {
    "client_id": "GRISP-Agent-...",
    "client_version": "1.0.0",
    "nonce": "..."
  }
}
```

The gateway SHALL respond with:

```text
HELLO_CHALLENGE
```

when authentication is enabled, followed by:

```text
HELLO_AUTH
HELLO_ACK
```

A gateway operating without authentication MAY respond directly with `HELLO_ACK`.

---

# 12. AUTHENTICATION

When authentication is enabled, the gateway SHALL perform challenge-response authentication.

The authenticated handshake consists of:

```text
HELLO
HELLO_CHALLENGE
HELLO_AUTH
HELLO_ACK
```

The mandatory numeric assignments are:

```text
HELLO           = 0x0001
HELLO_CHALLENGE = 0x0005
HELLO_AUTH      = 0x0007
HELLO_ACK       = 0x0002
```

`HELLO_AUTH` is a distinct wire message.

## 12.1 Challenge

Gateway:

```json
{
  "protocol": "GARP/1.02",
  "type": "hello_challenge",
  "payload": {
    "server_id": "...",
    "server_version": "...",
    "server_nonce": "...",
    "auth": {
      "algorithm": "HMAC-SHA256"
    }
  }
}
```

The binary frame SHALL contain:

```text
message_type = 0x0005
```

## 12.2 Authentication

Client:

```json
{
  "protocol": "GARP/1.02",
  "type": "hello_auth",
  "payload": {
    "client_id": "...",
    "client_nonce": "...",
    "server_nonce": "...",
    "proof": "hex..."
  }
}
```

The binary frame SHALL contain:

```text
message_type = 0x0007
```

The proof SHALL be:

```text
HMAC-SHA256(
    shared_secret,
    "GARP/1.02" |
    client_id |
    client_nonce |
    server_nonce
)
```

No page script SHALL have access to the shared secret.

## 12.3 Successful Handshake

The gateway returns:

```json
{
  "protocol": "GARP/1.02",
  "type": "hello_ack",
  "payload": {
    "server_id": "...",
    "server_version": "...",
    "browser": {
      "name": "Firefox",
      "version": "..."
    },
    "features": [
      "streaming",
      "cancel",
      "sessions",
      "stable_tabs",
      "response_events",
      "page_generation",
      "diagnostics"
    ]
  }
}
```

The binary frame SHALL contain:

```text
message_type = 0x0002
```

The connection enters:

```text
AUTHENTICATED
```

only after successful verification.

Failed authentication SHALL terminate the connection.

# 13. CONNECTION STATE MACHINE

```text
CONNECTED
    |
    v
HELLO_RECEIVED
    |
    v
AUTHENTICATING
    |
    v
AUTHENTICATED
    |
    v
READY
    |
    +----> CLOSING
```

Terminal connection states:

```text
CLOSING
CLOSED
```

A connection that has not successfully reached `READY` SHALL NOT accept normal commands.

---

# 14. HEARTBEAT

Both endpoints SHALL support:

```text
PING
PONG
```

Recommended heartbeat interval:

```text
10–30 seconds
```

Heartbeat timeout SHALL be configurable.

A heartbeat failure SHALL invalidate the TCP connection but SHALL NOT automatically destroy session identity.

---

# 15. RECONNECTION

A disconnected client MAY reconnect.

After reconnect:

```text
CONNECT
  ↓
HELLO
  ↓
AUTHENTICATE
  ↓
CAPABILITIES
  ↓
GET_PROMPT_STATUS
```

A request MAY remain associated with its session across reconnect.

Possible recovered request states:

```text
SUBMITTING
GENERATION_STARTED
STREAMING
CONTINUATION_REQUIRED
COMPLETE
FAILED
CANCELLED
UNKNOWN
```

`UNKNOWN` MUST remain distinct from `COMPLETE`.

A broken connection SHALL NEVER be interpreted as successful completion.

# 18. SESSION LIFECYCLE

Required commands:

```text
CREATE_SESSION
ATTACH_SESSION
DETACH_SESSION
CLOSE_SESSION
RESET_SESSION
```

Creating a session SHALL return:

```text
session_id
tab_id
provider
page_generation
state
```

A newly created session SHALL normally begin in:

```text
PREPARING
```

and SHALL NOT be considered ready merely because its tab exists.

A session SHALL survive JSWindowActor replacement.

---

# 19. SESSION READINESS

Session readiness SHALL be based on current provider state, not elapsed time.

The following are mandatory readiness conditions:

```text
current tab exists
current actor exists
current page generation is known
provider page is sufficiently loaded
provider authentication state is known
rate-limit state is known
provider input is discoverable
provider input is visible
provider input is enabled
```

A session SHALL enter:

```text
READY
```

only when the provider adapter reports:

```text
input_ready = true
```

and no blocking authentication or rate-limit condition exists.

A fixed client-side sleep SHALL NOT constitute readiness proof.

Waiting for readiness SHOULD be performed by the gateway.

A client MAY also receive `SESSION_READY` events and then submit a prompt.

A prompt received while the session is `PREPARING` SHALL either:

1. remain pending until readiness is established; or
2. be rejected with `SESSION_NOT_READY` / `INPUT_NOT_READY`.

It SHALL NOT be treated as successfully submitted merely because the request was syntactically valid.

---

# 20. SESSION CONCURRENCY

A session SHALL permit at most one active generation by default.

Submitting a second prompt while a generation is active SHALL yield:

```text
SESSION_BUSY
```

unless explicit concurrent-session support has been negotiated.

The gateway SHALL never silently double-submit a prompt.

---

# 21. PROMPT LIFECYCLE

The canonical state machine is:

```text
IDLE
  ↓
PREPARING
  ↓
INPUT_READY
  ↓
INJECTING
  ↓
INJECTION_VERIFIED
  ↓
SUBMITTING
  ↓
SUBMISSION_VERIFIED
  ↓
GENERATION_STARTED
  ↓
STREAMING
  ↓
CONTINUATION_REQUIRED
  ↓
STREAMING
  ↓
COMPLETE
```

Failure states include:

```text
AUTH_REQUIRED
RATE_LIMIT
PROVIDER_ERROR
DOM_ERROR
NAVIGATION_ERROR
TIMEOUT
CANCELLED
INPUT_NOT_READY
INPUT_INJECTION_FAILED
SUBMIT_FAILED
SUBMISSION_NOT_VERIFIED
RESPONSE_IDENTITY_UNKNOWN
STALE_ACTOR
STALE_PAGE_GENERATION
```

No state may silently transition to another state.

A timeout while looking for input SHALL NOT become `READY`.

A failed injection SHALL NOT become `SUBMISSION_VERIFIED`.

A failed submission SHALL NOT become `GENERATION_STARTED`.

---

# 22. PROMPT REQUEST

Canonical form:

```json
{
  "protocol": "GARP/1.02",
  "type": "prompt",
  "request_id": "...",
  "session_id": "...",
  "payload": {
    "prompt": {
      "format": "text",
      "text": "..."
    },
    "options": {
      "stream": true,
      "timeout_ms": 180000,
      "auto_continue": true
    }
  }
}
```

A prompt SHALL preserve the supplied semantic text exactly.

GARP transport SHALL NOT:

* trim semantic prompt text;
* alter whitespace;
* normalize line endings inside the semantic payload;
* inject debugging comments;
* remove Markdown;
* modify filenames;
* rewrite code;
* append instructions.

Logging SHALL be independent of semantic prompt transport.

---

# 23. PROMPT ACKNOWLEDGEMENT

The gateway SHALL acknowledge an accepted request:

```json
{
  "protocol": "GARP/1.02",
  "type": "prompt_ack",
  "request_id": "...",
  "session_id": "...",
  "payload": {
    "state": "accepted"
  }
}
```

`PROMPT_ACK` means only:

```text
request accepted by the GARP gateway
```

It does NOT mean:

```text
prompt injected
prompt injection verified
prompt submitted
submission verified
AI generation started
AI generation succeeded
```

The gateway SHALL NOT use `PROMPT_ACK` as evidence that provider submission succeeded.

---

# 24. INPUT DISCOVERY

A provider adapter SHALL discover the current provider input from the current document.

Discovery SHALL report:

```text
FOUND
NOT_FOUND
AMBIGUOUS
ERROR
```

An input candidate SHOULD expose diagnostic metadata including:

```text
selector
tag_name
id
class_name
role
placeholder
contenteditable
visible
enabled
owner_document
```

Broad generic selectors SHALL NOT silently override a more specific provider selector without diagnostic evidence.

The implementation SHALL NOT silently claim that a provider input exists when all provider-specific and permitted fallback discovery methods failed.

---

# 25. INPUT INJECTION

The adapter SHALL distinguish:

```text
input discovery
input injection
input verification
```

Supported strategies MAY include:

```text
native_value_setter
framework-aware_value_update
contenteditable_selection
input_event
keyboard_fallback
```

For ordinary HTML `<textarea>` or `<input>` elements, the implementation SHOULD prefer a native value setter over deprecated or unreliable `execCommand()` insertion.

After injection, the adapter SHALL dispatch the required input/change events for the provider framework.

The adapter SHALL verify the result.

For a textarea-like control, minimum verification SHALL establish:

```text
current value equals requested prompt
```

and SHOULD additionally verify after at least one event-loop turn or equivalent provider-framework processing opportunity.

For contenteditable controls, verification SHALL establish that the rendered/editor text corresponds to the requested prompt.

If verification fails:

```text
INPUT_INJECTION_FAILED
```

SHALL be raised.

A provider adapter SHALL NOT report successful input injection merely because a DOM mutation was attempted.

---

# 26. DOM RERENDER DETECTION

Provider frameworks MAY replace the input element immediately after an input event.

Therefore the adapter SHOULD re-query the provider input after injection.

The adapter SHOULD report:

```text
same_node
replacement_detected
verified_value_length
```

A prompt that was present only in an obsolete DOM node SHALL NOT be treated as successfully injected into the current provider editor.

If the current input has become a different node and the prompt is no longer present, the adapter SHALL re-inject or fail closed.

---

# 27. PROMPT SUBMISSION

Submission SHALL be a distinct operation after successful injection verification.

The adapter SHOULD support, in priority order:

```text
provider-specific send control
stable semantic send control
form submission where valid
keyboard fallback where safe
```

The adapter SHALL NOT silently return success when no valid submission mechanism was found.

If no supported submission method exists:

```text
SUBMIT_FAILED
```

SHALL be raised.

The result SHALL identify the method used:

```text
submit_method
```

Examples:

```text
button_click
form_submit
keyboard_enter
provider_specific
```

---

# 28. SUBMISSION VERIFICATION

After submission, the gateway SHALL establish evidence that submission actually occurred.

Acceptable provider-specific evidence MAY include:

```text
input cleared by provider
user message count increased
user message node appeared
conversation state changed
provider generation state changed
provider-specific submission acknowledgment
```

A click invocation alone is insufficient proof where the provider UI allows a disabled or inert control.

The adapter SHOULD report:

```text
submit_method
submission_verified
```

The gateway SHALL emit:

```text
INPUT_SUBMITTED
```

only after the adapter reports successful submission.

---

# 29. REQUEST EXECUTION ORDER

For a normal prompt, the gateway SHALL follow this logical order:

```text
PROMPT received
    ↓
request created
    ↓
session readiness verified
    ↓
current actor verified
    ↓
current page generation captured
    ↓
pre-submission snapshot captured
    ↓
prompt injected
    ↓
injection verified
    ↓
provider submission performed
    ↓
submission verified
    ↓
INPUT_SUBMITTED
    ↓
GENERATION_STARTED
    ↓
generation observation
```

`GENERATION_STARTED` SHALL NOT be emitted merely because `PROMPT` was received.

`GENERATION_STARTED` SHALL NOT be emitted before successful provider submission.

---

# 30. DUPLICATE REQUEST SUPPRESSION

`request_id` is an idempotency key.

A duplicate `PROMPT` with an already known `request_id` SHALL NOT cause another provider submission.

The gateway SHALL return the existing request state.

A duplicate request with different semantic prompt content SHALL be rejected as:

```text
REQUEST_ID_REUSE
```

---

# 31. RESPONSE IDENTITY

The gateway SHALL determine response ownership using:

```text
request_id
message_id
submission_generation
```

It SHALL NOT simply assume that:

```text
latest markdown element = current response
```

Before submission, the gateway SHALL capture a session snapshot.

After submission, a new response SHALL be associated with the request only when the provider-specific adapter establishes that the response belongs to that submission.

---

# 32. SESSION SNAPSHOT

Before submitting a prompt, Firefox SHALL establish:

```text
provider
tab_id
url
page_generation
actor_instance
input_ready
conversation_identity
last_message_id
last_message_count
last_message_text
```

The snapshot is the deterministic baseline for response association.

# 38. EVENT ORDERING

For one `(request_id, message_id)` stream:

```text
sequence 1
sequence 2
sequence 3
...
```

The receiver SHALL detect:

```text
duplicate sequence
out-of-order event
sequence gap
unexpected sequence reset
```

## 38.1 Duplicate Event

Same sequence and identical event content:

```text
replay
```

Same sequence with different event content:

```text
SEQUENCE_CONFLICT
```

## 38.2 Sequence Gap

A sequence gap SHALL NOT be silently treated as complete data.

The request becomes:

```text
DEGRADED
```

or:

```text
SEQUENCE_GAP
```

according to implementation policy.

---

# 39. PAGE GENERATION

`page_generation` SHALL increment when:

* top-level navigation occurs;
* provider application state is replaced;
* relevant same-document navigation replaces conversation state;
* browser reload occurs;
* JSWindowActorChild is replaced;
* conversation identity changes.

Ordinary DOM mutation SHALL NOT increment page generation.

A stale event from generation N SHALL NOT overwrite state from generation N+1.

Every operation requiring DOM access SHALL resolve against the current actor/page generation.

A previously acquired actor SHALL NOT be reused across an actor replacement unless the implementation has positively established that the actor remains current.

# 40. ACTOR REPLACEMENT

The Firefox actor architecture consists conceptually of:

```text
AIAutomationParent
AIAutomationChild
```

The parent process SHALL treat actor replacement as normal browser lifecycle behavior.

When actor replacement is detected:

```text
old actor invalid
    ↓
page_generation++
    ↓
current actor acquired
    ↓
session remains alive
    ↓
provider state re-inspected
```

The following identities SHALL survive actor replacement:

```text
session_id
tab_id
request_id
```

An actor response associated with an obsolete actor instance SHALL NOT mutate authoritative session state.

A new actor SHALL NOT inherit readiness merely because an old actor reported readiness.

The new actor SHALL re-establish current provider state.

# 49. DOM SEARCH RULES

Provider adapters SHOULD prefer:

```text

    ↓

    ↓
provider-specific structural selector
    ↓
```

Broad generic selectors SHOULD be avoided.

* selectors attempted;
* number of candidates;
* visibility;
* enabled state;
* selected candidate;
* reason for rejection of other candidates.

The implementation SHALL NOT silently claim that a provider control exists when every candidate selector failed.

# 50. DEEP DOM SEARCH

Shadow DOM support MAY be implemented by recursively searching shadow roots.

A provider adapter SHOULD cache discovered roots and invalidate its cache after relevant DOM mutation or navigation.

The adapter SHOULD NOT recursively traverse the entire page on every polling tick.

# PART II — GARP/1.02 IMPLEMENTATION CONTRACT

# 62. IMPLEMENTATION CONTRACT PURPOSE

The Implementation Contract makes the normative requirements executable by defining:

* exact internal modules;
* exact state ownership;
* exact binary encoding;
* exact message registry;
* exact sequence behavior;
* exact authentication;
* exact failure semantics;
* exact Firefox integration boundaries;
* exact actor lifecycle;
* exact provider readiness lifecycle;
* exact prompt submission lifecycle;
* exact diagnostic responsibilities;
* conformance test obligations.

An implementation SHALL NOT claim GARP/1.02 conformance merely because it exchanges compatible JSON.

It SHALL implement the normative wire, identity, state, interaction, and failure rules.

# 63. REQUIRED MODULES

# 64. CONNECTION OWNERSHIP

One TCP connection SHALL have exactly one:

```text

```

Connection state SHALL belong to the GARP connection object.

Session state SHALL NOT be stored only inside a TCP connection object.

This is required for reconnect.

# 65. SESSION OWNERSHIP

Session state SHALL belong to the session manager.

A session SHALL remain addressable independently of:

```text

JSWindowActor instance
tab index
DOM instance
```

---

# 66. REQUEST OWNERSHIP

Request state SHALL belong to the request manager.

A request SHALL remain addressable by `request_id` until the configured retention period expires.

Completed requests SHALL remain available long enough to support idempotent replay and reconnect.

---

# 67. TAB OWNERSHIP

The tab manager SHALL associate:

```text

```

and SHALL update:

```text

url
title
selected
```

without changing `tab_id`.

A closed tab SHALL invalidate its session state unless the session is explicitly detached.

# 68. PAGE-GENERATION IMPLEMENTATION

Every actor bind SHALL record:

```text

actor_instance
```

A newly bound actor MUST be associated with the current page generation.

A stale actor response SHALL be rejected.

A change in actor instance SHALL be treated as a generation boundary.

The externally observable invariant is:

```text
old actor ≠ current actor
    =>
stale actor
    =>
new current actor
```

```text
SUBMISSION_NOT_VERIFIED

STALE_PAGE_GENERATION

PROVIDER_RATE_LIMITED
```

A generic:

```text

```

# 81. FAILURE SEMANTICS

The following transformations are forbidden:

```text
PREPARING → READY without readiness evidence

input injection attempted
    →
INPUT_SUBMITTED without verification

submission attempted
    →
GENERATION_STARTED without submission evidence

broken TCP
    →
COMPLETE

unknown provider state
    →
READY

stale actor
    →
current actor

stale page generation
    →
current page generation

unknown response identity
    →
valid response

diagnostic output
    →
semantic prompt modification
```

The implementation MUST fail closed instead.

# 82. GARP INVARIANTS

The following invariants are mandatory.

```text
I1
Every GARP connection has explicit connection state.

I2
Every AI request has a unique request_id.

I3
Every AI session has a stable session_id.

I4
tab_index is never tab identity.

I5
Transport never modifies semantic content.

I6
Duplicate PROMPT with the same request_id never submits twice.

I7
Readiness timeout never becomes READY.

I8
A fixed client sleep is never readiness proof.

I9
A session is READY only when the current provider input is verified usable.

I10
Input injection failure never becomes successful submission.

I11
A stale DOM node never constitutes successful current-input injection.

I12
A prompt is not considered submitted merely because PROMPT_ACK was emitted.

I13
INPUT_SUBMITTED requires provider submission evidence.

I14
GENERATION_STARTED requires successful provider submission.

I15
Stale page_generation state never overwrites current state.

I16
A stale actor cannot mutate authoritative session state.

I17
A session survives actor replacement.

I18
A tab index change never changes tab identity.

I19
Continuation is never performed silently.

I20
Sequence gaps never become successful completion.

I21
Broken TCP connection never implies successful generation.

I22
Unknown provider state never becomes READY.

I23
Unknown response identity never becomes a valid response association.

I24
A failed authentication handshake never enters READY.

I25
Debugging never modifies the semantic prompt.

I26
Diagnostic logs never expose authentication secrets.

I27
PROMPT_ACK never implies provider generation success.

I28
Generation events use the current page generation.

I29
A page-generation transition invalidates stale DOM assumptions.

I30
Provider-specific selectors remain isolated inside provider adapters.

I31
A provider adapter never reports successful submission when no supported submission mechanism exists.

I32
A diagnostic system SHOULD identify the earliest known failing automation stage.

I33
HELLO_AUTH has the mandatory numeric wire type 0x0007.

I34
Every normative GARP message has a bidirectional numeric/semantic registry mapping.

I35
A conforming implementation does not require a compatibility patch to obtain a normative GARP message mapping.

I36
A binary message type and its JSON semantic type MUST agree according to the normative registry.

I37
A session SHALL NOT become READY merely because a browser tab or actor exists.

I38
A generation SHALL NOT be reported as started before successful provider submission.

I39
A provider submission SHALL NOT be reported successful merely because a DOM click was attempted.

I40
A provider input SHALL NOT be considered injected unless injection is verified.

I41
A current actor SHALL be reacquired after actor replacement.

I42
A stale actor SHALL NOT mutate authoritative state.

I43
Page generation SHALL increase on actor replacement.

I44
Diagnostic mode SHALL be observational only.

I45
Raw semantic prompt contents SHALL not be logged by default.

I46
Provider-specific DOM failures SHALL be diagnostically distinguishable from transport failures.

I47
PROMPT_ACK, INPUT_SUBMITTED, GENERATION_STARTED, and GENERATION_COMPLETED represent distinct semantic milestones.

I48
Unknown state SHALL remain unknown until sufficient evidence exists to establish a stronger state.
```

# 84. IMPLEMENTATION LESSONS INCORPORATED INTO GARP/1.02

The following failures were identified during live implementation testing and are now explicit normative requirements.

## 84.1 Asynchronous Session Preparation

`CREATE_SESSION` may return before the provider page is ready.

Therefore:

```text
CREATE_SESSION
```

does not imply:

```text
READY
```

## 84.2 Client Sleep Is Not Readiness

A fixed delay such as:

```text
1500 ms
```

does not constitute evidence that provider input is ready.

Readiness SHALL be determined by actual provider inspection.

## 84.3 Actor Replacement During Navigation

Provider navigation may replace the `JSWindowActorChild`.

Therefore:

```text
session identity != actor identity
```

and the gateway SHALL reacquire the current actor.

## 84.4 Stale Page Generation

A generation event SHALL NOT report an obsolete page generation after an actor replacement.

Current page generation SHALL be attached to provider operations and generation events.

## 84.5 Early Generation Event

A generation event emitted before provider submission is not valid evidence that generation started.

Therefore:

```text
INPUT_SUBMITTED
    ↓
GENERATION_STARTED
```

is mandatory ordering.

## 84.6 DOM Injection Is Not Automatically Provider State

Changing the DOM value of a textarea is not necessarily sufficient to update the provider framework.

Therefore prompt injection SHALL include:

```text
DOM/framework-compatible change
+
input event
+
verification
```

## 84.7 DOM Node Replacement

The provider may rerender its editor after an input event.

Therefore the current provider input MUST be rechecked after injection.

## 84.8 Submit Control Discovery

A provider-specific send control may change without GARP semantics changing.

Therefore provider adapters SHALL isolate selectors and report discovery failures explicitly.

## 84.9 Submission Is a Separate State

A successful DOM click attempt is not sufficient evidence that the provider accepted the prompt.

Therefore submission SHALL have an explicit verification stage.

## 84.10 Centralized Diagnostics

Without centralized diagnostics, DOM automation failures require indirect inference.

Therefore AI Automation SHALL expose structured diagnostics that permit an operator to determine:

```text
what was attempted
which actor was active
which page generation was active
which selector matched
which input was selected
whether input injection was verified
whether the DOM node was replaced
which submit mechanism was found
whether submission was verified
where execution failed
```

An implementation conforms to GARP/1.02 only when it demonstrates:

```text
HELLO negotiation
authentication
normative HELLO_AUTH mapping
stable session IDs
stable tab IDs
request correlation
message correlation
page-generation tracking
actor replacement handling
provider readiness
verified prompt injection
verified provider submission
ordered streaming
duplicate suppression
explicit cancellation
heartbeat

structured errors
provider state
fail-closed unknown state
centralized diagnostics
debug-mode isolation
semantic prompt preservation
```

Compatibility with earlier GARP versions SHALL NOT by itself constitute GARP/1.02 conformance.

An implementation SHALL use:

```text

```

for GARP/1.02 operation.

# 87. VERSION MIGRATION

GARP/1.02 supersedes GARP/1.01.

An implementation MAY support both versions during migration.

When both versions are supported:

```text

```

and:

```text
GARP/1.02
```

SHALL be treated as distinct protocol versions.

The implementation SHALL NOT silently reinterpret a GARP/1.01 frame as GARP/1.02.

The following GARP/1.02 additions are especially significant:

```text
verified provider readiness
verified input injection
verified provider submission
explicit actor-generation synchronization
centralized AI Automation diagnostics
--debug-ai-automation
normative bidirectional message registry
explicit HELLO_AUTH registry requirement
```

A GARP/1.02 implementation SHALL contain the complete normative registry, including:

# 89. STATUS

This document supersedes the earlier GARP/1.01 specification and associated informal compatibility patch notes once adopted.

The protocol specification and implementation contract SHALL be treated as one normative specification.

Any ambiguity between an implementation and the protocol SHALL be resolved by the normative rules in this document, not by observed behavior of an existing implementation.

# PART III — GARP/1.02 MESSAGE SCHEMAS

# 90. MESSAGE SCHEMA CONVENTIONS

This section is **NORMATIVE**.

Every GARP/1.02 message SHALL conform to exactly one schema defined in this section.

A message consists of:

```text
binary frame
    +
JSON semantic message
```

The binary frame and JSON message SHALL describe the same message type.

The following JSON-level conventions apply to all messages.

## 90.1 Common Envelope

A GARP message SHALL contain:

```json
{
  "protocol": "GARP/1.02",
  "type": "..."
}
```

Depending on the message type, it MAY or SHALL additionally contain:

```text
request_id
session_id
message_id
sequence
page_generation
timestamp
payload
```

Fields not explicitly permitted by a message schema SHOULD NOT be emitted.

Unknown fields MAY be ignored only when the message schema explicitly permits forward-compatible extension.

Unknown required fields SHALL cause:

```text
PROTOCOL_ERROR
```

```text
type: UUID string
required: message-specific
```

```text
required: message-specific
```

```text

required: message-specific
```


## 91.7 page_generation

```text

required: message-specific
minimum: 1
```

## 91.8 timestamp


```text
type: object | array
required: message-specific
```

# 134. EVENT SEQUENCING RULES

Only messages that belong to a generation stream SHALL use:

```text
message_id
sequence
page_generation
```

For each generation stream:

```text
(request_id, message_id)
```

sequence SHALL begin at:

```text
1
```

and increase by exactly one for each emitted event.

The canonical stream SHALL be:

```text
INPUT_SUBMITTED
    ↓
GENERATION_STARTED
    ↓
GENERATION_PROGRESS
    ↓
GENERATION_DELTA
    ↓
GENERATION_PROGRESS
    ↓
CONTINUATION_REQUIRED
    ↓
CONTINUATION_SUBMITTED
    ↓
GENERATION_DELTA
    ↓
GENERATION_COMPLETED
```

Some intermediate events MAY be omitted.

The following ordering is mandatory:

```text
INPUT_SUBMITTED < GENERATION_STARTED < GENERATION_COMPLETED
```

A generation SHALL NOT emit:

```text
GENERATION_STARTED
```

before:

```text
INPUT_SUBMITTED
```

---

# 135. PAGE GENERATION RULES FOR EVENTS

All generation events in one active generation SHALL use the page generation associated with the successful submission.

If navigation or actor replacement occurs while generation is active:

1. the old actor SHALL be considered stale;
2. the session SHALL acquire the new actor;
3. page generation SHALL increase;
4. old actor events SHALL be rejected;
5. the gateway SHALL establish the new provider state before continuing.

A generation event from a stale page generation SHALL NOT overwrite current authoritative state.

# 139. MESSAGE VALIDATION ORDER

A conforming receiver SHOULD validate messages in this order:

```text
1. binary frame integrity
2. protocol version
3. numeric message type
4. JSON parsing
5. protocol field
6. semantic type
7. identity fields
8. payload schema
9. state constraints
10. page-generation constraints
11. sequence constraints
```

Failure at an earlier level SHALL prevent later semantic processing.

# 140. BINARY/JSON CONSISTENCY

For every message:

```text
binary.message_type
```

MUST equal:

```text
GARPMessageNameToType(json.type)
```

and:

```text
GARPMessageTypeToName(binary.message_type)
```

MUST equal:

```text
json.type
```

Examples:

```text
0x0001 ↔ hello
0x0002 ↔ hello_ack
0x0005 ↔ hello_challenge
0x0006 ↔ response
0x0007 ↔ hello_auth
0x0030 ↔ prompt
0x0042 ↔ input_submitted
0x0043 ↔ generation_started
0x0044 ↔ generation_delta
0x0048 ↔ generation_completed
0x00F0 ↔ error
```

Any disagreement SHALL yield:

```text
PROTOCOL_ERROR
```

---

# 141. MESSAGE EXTENSION RULE

A future GARP version MAY add fields or message types.

A GARP/1.02 implementation SHALL NOT silently reinterpret a new message type as an existing type.

New fields MAY be tolerated only when:

1. they do not change the meaning of an existing required field;
2. they do not violate security or state invariants;
3. the implementation is explicitly documented as extension-tolerant.

Unknown required semantics SHALL result in:

```text
PROTOCOL_ERROR
```

# 144. COMPLETE GARP/1.02 MESSAGE CONTRACT

A conforming implementation SHALL therefore have an explicit schema for every registered message.

No registered message may rely solely on:

```text
"implementation-defined"
"provider-specific"
"same as previous message"
```

for its required wire or JSON structure.

Provider-specific payload extensions MAY exist only inside explicitly extensible fields such as:

```text
details
```

and SHALL NOT redefine core GARP semantics.

The following are therefore normative protocol milestones:

```text
HELLO
    ↓
HELLO_CHALLENGE
    ↓
HELLO_AUTH
    ↓
HELLO_ACK

CREATE_SESSION
    ↓
PREPARING
    ↓
SESSION_READY

PROMPT
    ↓
PROMPT_ACK
    ↓
INPUT_SUBMITTED
    ↓
GENERATION_STARTED
    ↓
GENERATION_DELTA / GENERATION_PROGRESS
    ↓
CONTINUATION_REQUIRED / CONTINUATION_SUBMITTED
    ↓
GENERATION_COMPLETED
```

Failure at any stage SHALL produce the appropriate structured failure state rather than being represented as success.

---

# 145. SCHEMA AUTHORITY

In GARP/1.02, the normative precedence order is:

```text
1. Binary message registry
2. Message schema in Part III
3. State-machine rules
4. Identity rules
5. Implementation contract
6. Examples
```

Examples SHALL NOT override the normative schema.

Observed behavior of existing Firefox or Delphi implementations SHALL NOT override the normative schema.

An implementation that deviates from a normative message schema is non-conforming even when another implementation accepts its message.

---

# 146. SCHEMA VERSIONING

The message schemas in this section are specific to:

```text
GARP/1.02
wire version = 0x12
JSON protocol = "GARP/1.02"
```

A future version SHALL define its own schema set or explicitly specify backward compatibility.

A GARP/1.02 endpoint SHALL reject a message whose JSON protocol or wire version identifies an unsupported protocol version.

# 147. FINAL MESSAGE-SCHEMA INVARIANTS

The following additional invariants are mandatory:

```text
I49
Every registered GARP/1.02 message has one normative JSON schema.

I50
Every registered GARP/1.02 message has one normative numeric message type.

I51
Every normative message has a bidirectional numeric/semantic registry mapping.

I52
HELLO_AUTH is permanently assigned to 0x0007 for GARP/1.02.

I53
Binary message type and JSON semantic type MUST agree.

I54
Message identity requirements SHALL be enforced according to the message schema.

I55
Generation events SHALL contain the identity needed to reconstruct their stream.

I56
A generation event SHALL NOT silently omit required sequence information.

I57
INPUT_SUBMITTED SHALL represent verified provider submission, not merely an attempted DOM operation.

I58
GENERATION_STARTED SHALL follow INPUT_SUBMITTED.

I59
PROMPT_ACK SHALL never be interpreted as provider submission success.

I60
A session readiness event SHALL represent actual provider readiness.

I61
A stale actor SHALL NOT produce authoritative generation events.

I62
A stale page generation SHALL NOT overwrite current session state.

I63
Diagnostics SHALL NOT modify protocol semantics.

I64
Diagnostics SHALL NOT expose authentication secrets.

I65
Prompt contents SHALL not be modified by the diagnostic system.

I66
Provider-specific extensions SHALL NOT redefine core GARP fields.

I67
Schema validation SHALL occur before state mutation.

I68
Malformed messages SHALL fail closed.

I69
A conformance implementation SHALL test every registered message schema.

I70
No separate compatibility patch is required for a normative GARP/1.02 registry entry.
```
