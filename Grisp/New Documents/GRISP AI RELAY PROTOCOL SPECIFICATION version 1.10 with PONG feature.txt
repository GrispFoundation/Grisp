# GARP/1.10

## Gateway AI Runtime Protocol

**Status:** Normative / Implementation Target
**Protocol Version:** `1.10`
**Wire Version:** `0x19`

---

# 1. Scope

GARP, the Gateway AI Runtime Protocol, defines an authenticated, deterministic interface between an external controller and an AI gateway operating browser-based AI providers.

GARP defines:

* transport framing;
* authentication;
* browser and tab management;
* logical AI sessions;
* prompt lifecycle;
* prompt identity;
* generation observation;
* response retrieval;
* cancellation;
* provider state;
* browser recovery;
* navigation tracking;
* event sequencing;
* bounded retention;
* optional event replay;
* connection keepalive;
* server-initiated liveness notification;
* diagnostics;
* capability negotiation;
* protocol evolution.

GARP does not define:

* model reasoning;
* AI planning;
* semantic correctness;
* provider internal implementation;
* prompt policy;
* downstream verification.

Provider-specific browser automation remains an implementation concern of the gateway.

---

# 2. Design Principles

GARP/1.10 deliberately maintains a small base protocol while preserving correctness.

The base protocol provides:

1. one active prompt per session;
2. explicit prompt identity;
3. bounded retained prompt history;
4. explicit target addressing;
5. persistent session event sequencing;
6. authoritative state snapshots;
7. explicit provider-blocked states;
8. page-generation fencing;
9. deterministic cancellation arbitration;
10. verified browser actions;
11. connection-level keepalive;
12. optional server-initiated `PONG`.

The base protocol does not provide:

* concurrent prompt execution within one session;
* prompt queues;
* subchannel multiplexing;
* unlimited event history.

Advanced functionality MAY be supplied through negotiated extensions.

---

# 3. Versioning

GARP/1.10 uses the existing GARP binary frame layout.

The wire version is:

```text id="9s0ow1"
0x19
```

The protocol version is:

```text id="8a4g4m"
1.10
```

GARP/1.10 does not alter the binary header layout.

The addition of the `PONG` message at `0x0071` is a protocol-level change while retaining the same frame format.

---

# 4. Protocol Compatibility

The selected protocol version is authoritative for the connection.

A GARP/1.10 implementation:

* MUST advertise `1.10` when supported;
* MAY advertise `1.09.1` for compatibility;
* MUST implement the semantics of the selected version;
* MUST NOT silently claim 1.10 behavior when `1.09.1` is selected.

A client advertising only `1.09.1` MAY communicate with a GARP/1.10 gateway using 1.09.1 semantics.

A client advertising only `1.09` MAY communicate only if the gateway explicitly supports 1.09.

A client and gateway MUST NOT use GARP/1.10-only message semantics when the negotiated version is `1.09.1`.

---

# 5. Core Object Model

The hierarchy is:

```text id="m8f8jf"
Connection
    |
    +-- Session
          |
          +-- active Prompt
          |
          +-- retained terminal Prompts
```

A connection MAY contain multiple sessions.

A session has:

```text id="k9tr4y"
0 or 1 active prompt
0 or more retained terminal prompts
```

Only one prompt may be active at any instant.

Terminal prompts remain independently identifiable until retention expiry or session closure.

---

# 6. Prompt Identity

The request UUID of a `PROMPT` command becomes its prompt request ID.

Example:

```text id="p5s4bk"
PROMPT
request_id = A

prompt_request_id = A
```

Every command operating on an existing prompt MUST explicitly provide:

```json id="0ou2xc"
{
  "target_request_id": "A"
}
```

This applies to:

* `CANCEL_PROMPT`;
* `GET_PROMPT_STATUS`;
* `GET_RESPONSE`;
* `SUBSCRIBE_RESPONSE`.

There is no implicit "current prompt" targeting.

---

# 7. Request Identity

Every command MUST have a unique non-zero request UUID.

The request UUID identifies the command itself.

For example:

```text id="c9y6l5"
PROMPT
request_id = A

GET_RESPONSE
request_id = B
target_request_id = A

RESPONSE
request_id = B
result.prompt_request_id = A
```

The binary request UUID identifies the command.

`target_request_id` identifies the prompt operation being addressed.

---

# 8. UUID Scope

Command request IDs MUST be unique within the lifetime of a connection.

Prompt request IDs MUST remain unique within the lifetime of a session.

A gateway MUST reject duplicate active command request IDs.

A target request ID MUST refer to a prompt belonging to the same session.

---

# 9. Target Resolution Precedence

When a target operation is received:

1. An unknown session produces `UNKNOWN_SESSION`.
2. A missing required `target_request_id` produces `INVALID_REQUEST`.
3. A malformed UUID produces `INVALID_ARGUMENT`.
4. A syntactically valid but unknown prompt produces `UNKNOWN_PROMPT`.
5. An expired prompt produces `PROMPT_EXPIRED`.
6. A known prompt in an invalid state produces the operation-specific error, such as `PROMPT_NOT_ACTIVE`.

This ordering is normative.

---

# 10. Transport

GARP operates over a reliable byte stream.

Supported transports:

* TCP;
* Unix-domain sockets where available.

The default deployment MUST use loopback or a Unix-domain socket.

Plaintext GARP MUST NOT be exposed to a non-loopback network.

TLS is REQUIRED for non-loopback TCP.

GARP authentication remains mandatory even when TLS is used.

---

# 11. Frame Format

Every GARP frame contains a fixed 48-byte header.

All multi-byte values are big-endian.

| Offset | Size | Field          |
| -----: | ---: | -------------- |
|      0 |    4 | Magic          |
|      4 |    1 | Wire Version   |
|      5 |    1 | Flags          |
|      6 |    2 | Header Length  |
|      8 |    4 | Payload Length |
|     12 |    2 | Message Type   |
|     14 |    2 | Reserved       |
|     16 |   16 | Request UUID   |
|     32 |   16 | Session UUID   |

---


```text id="itbckk"

```

```text id="va5b0m"
0x19
```

```text id="r7z8mm"
48
```


# 13. Flags

GARP/1.10 defines:

```text id="1bmyqf"
0x00  no flags
0x01  EXTENSION_PRESENT
```

Unknown flag bits MUST be rejected unless the relevant extension has been negotiated.

---

# 14. Payload

The payload MUST be valid UTF-8 JSON unless a negotiated extension defines an alternative encoding.

The JSON root MUST be an object.

Default maximum payload:

```text id="yt5cs3"
16777216 bytes
```

The effective limit MUST be exposed through `CAPABILITIES`.

---

# 15. JSON Envelope

Every GARP JSON message MUST contain:

```json id="8n5i2f"
{
  "garp": "1.10",
  "type": "message_name",
  "timestamp": "2026-09-16T20:15:31.427Z",
  "payload": {}
}
```

Required fields:

```text id="qhzawo"
garp
type
timestamp
payload
```

`garp` MUST equal the negotiated protocol version.

---

# 16. Timestamp

Timestamps MUST use:

```text id="6fw7vj"
YYYY-MM-DDTHH:MM:SS.sssZ
```

Milliseconds are exactly three decimal digits.

All timestamps are UTC.

A receiver MUST NOT reject a valid message solely because of ordinary clock skew.

Implementations SHOULD maintain reasonably synchronized clocks.

---

# 17. Header/JSON Consistency

The binary header and JSON envelope MUST agree.

The binary `message_type` MUST correspond exactly to JSON `type`.

Where JSON `request_id` is present, it MUST equal the binary request UUID.

Where JSON `session_id` is present, it MUST equal the binary session UUID unless the message is explicitly creating a new session.

A mismatch MUST produce a protocol error.

For prompt-related events, `prompt_request_id` identifies the prompt and MAY differ from the binary event request UUID according to the event schema.

---

# 18. RESPONSE Session Header

A `RESPONSE` to a session-scoped command MUST carry the same session UUID as the command.

A response to a connection-level command MUST use the nil session UUID.

Therefore:

```text id="8pbuaw"
session command → session RESPONSE
connection command → connection RESPONSE
```

# 20. Registry Consistency Rule

Every registered message type MUST have exactly one authoritative definition.

A message type MUST NOT:

* have multiple numeric assignments;
* have multiple meanings;
* have incompatible schemas;
* appear twice in the registry.

Every normative message example MUST use fields valid for that message.

# 21. Handshake

The handshake is:

```text id="s0x3o9"
HELLO
    ↓
HELLO_CHALLENGE
    ↓
HELLO_AUTH
    ↓
HELLO_ACK
```

No application command is valid before authentication.

---

# 22. Handshake Request UUID

The handshake uses one fresh request UUID:

```text id="khpbm2"
HELLO              = H
HELLO_CHALLENGE    = H
HELLO_AUTH         = H
HELLO_ACK          = H
```

The handshake UUID MUST be non-zero.

Handshake messages are not `RESPONSE` messages.

---

# 25. Feature Representation

The `features` field in handshake messages is always an array of strings.

Example:

```json id="aj3nkm"
{
  "features": [
    "ext-replay-store",
    "ext-pong"
  ]
}
```

A required feature is prefixed with `!`.

Example:

```text id="izc5ak"
!ext-replay-store
```

The `!` is not part of the canonical feature name.

---

# 26. PONG Negotiation

PONG support is negotiated through the handshake feature set.

The canonical feature name is:

```text id="o5exu1"
ext-pong
```

A gateway MUST NOT emit `PONG` unless:

```text id="xbp9te"
ext-pong
```

has been successfully negotiated.

A client MUST NOT infer PONG support from:

* receiving `RESPONSE` to `PING`;
* receiving any other message.

PONG support is established solely by successful protocol negotiation and MUST be reported by `HELLO_ACK`.

`CAPABILITIES` reports the effective PONG configuration but does not independently enable it.

---

# 27. HELLO_AUTH

The authentication proof uses HMAC-SHA-256.

The shared secret MUST contain at least 32 bytes of secret material.

The proof is calculated over the exact transcript defined in Section 28.

---

# 28. Authentication Transcript

The transcript consists of these fields in exactly this order:

```text id="1y89ts"
u32be(domain_length)
domain_utf8

u32be(client_nonce_length)
client_nonce_raw

u32be(server_nonce_length)
server_nonce_raw

u32be(selected_version_length)
selected_version_utf8

u32be(client_name_length)
client_name_utf8

u32be(client_version_length)
client_version_utf8

u32be(server_name_length)
server_name_utf8

u32be(server_version_length)
server_version_utf8
```

All length fields are unsigned 32-bit big-endian byte counts.

The domain is exactly:

```text id="cjpoar"
GARP
```

The nonce fields contain the raw bytes represented by the Base64URL nonce values.

The name and version fields contain their UTF-8 byte representations.

The transcript is the exact concatenation of these fields.

The HMAC is:

```text id="3eiybl"
HMAC-SHA256(secret, transcript)
```

---

# 29. Base64URL Encoding

Nonce and proof values use unpadded Base64URL.

Allowed alphabet:

```text id="h5h7in"
A-Z
a-z
0-9
-
_
```

The `=` character MUST NOT appear.

Nonce fields represent raw random bytes.

Proof fields represent raw HMAC bytes.

---

# 30. HMAC Verification

The verifier MUST compare the received and expected HMAC using a constant-time comparison.

Failed verification MUST terminate authentication.

# 32. Unsupported Version

If the client advertises no protocol version supported by the gateway, the gateway MUST reject the handshake with:

```text id="ddgxjf"
UNSUPPORTED_VERSION
```

No session may be created.

---

# 33. Authentication Replay Protection

The gateway MUST:

* use unpredictable nonces;
* reject reuse of accepted authentication transcripts;
* expire incomplete handshakes;
* maintain a bounded replay cache.

Recommended incomplete-handshake lifetime:

```text id="5na7hk"
5 minutes
```

---

# 34. Authentication Rate Limiting

Authentication failures MUST be rate-limited.

The gateway SHOULD use:

* endpoint throttling;
* bounded delay;
* bounded handshake state;
* handshake timeouts.

# 35. RESPONSE

`RESPONSE` is the universal result of a valid command.

Success:

```json id="m5z6ul"
{
  "garp": "1.10",
  "type": "response",
  "timestamp": "2026-09-16T20:15:31.500Z",
  "payload": {
    "success": true,
    "result": {}
  }
}
```

Failure:

```json id="l4j2ze"
{
  "garp": "1.10",
  "type": "response",
  "timestamp": "2026-09-16T20:15:31.500Z",
  "payload": {
    "success": false,
    "error": {
      "code": "SESSION_BUSY",
      "retryable": true,
      "message": "Session already has an active prompt."
    }
  }
}
```

When `success=true`, `error` MUST be absent.

When `success=false`, `error` MUST be present.

# 40. Session State Definitions

### CREATED

Logical session exists but is not prepared.

### PREPARING

Browser/provider context is being prepared.

### READY

Verified browser/provider context is available for a new prompt.

### BUSY

One prompt is active.

### AUTH_REQUIRED

User/provider authentication is required.

### RATE_LIMITED

Provider rate limiting prevents ordinary operation.

### RECOVERING

Gateway is actively repairing browser/provider context.

### RETRYING

Gateway is waiting for or executing another recovery attempt.

### FAILED

Automatic recovery cannot currently restore the session.

### CLOSED

Session is permanently closed.

---

# 41. Provider Authentication Loss

When provider authentication is lost:

```text id="0d5f7m"
session → AUTH_REQUIRED
```

If a prompt is active, that prompt MUST terminate as:

```text id="6y5q8h"
GENERATION_FAILED
```

with:

```json id="5m7cxw"
{
  "code": "PROVIDER_AUTH_REQUIRED",
  "retryable": false,
  "message": "Provider authentication is required."
}
```

The failed prompt remains retained.

The session remains `AUTH_REQUIRED` until authentication has been positively verified.

---

# 42. Rate Limiting

When provider rate limiting prevents continuation:

```text id="t8wr6b"
session → RATE_LIMITED
```

If provider behavior terminates the operation, the prompt MUST become:

```text id="z0zvcz"
FAILED
```

with:

```text id="11j8i7"
PROVIDER_RATE_LIMITED
```

If provider behavior explicitly permits continuation, the prompt MAY remain active while the session is `RATE_LIMITED`.

The gateway MUST NOT report `READY` while the provider remains blocked.

---

# 43. RECOVERING

`RECOVERING` means active repair work is being performed.

Examples:

* actor reacquisition;
* DOM rediscovery;
* context rebuild;
* adapter revalidation.

---

# 44. RETRYING

`RETRYING` means another recovery attempt has been selected and is waiting for or executing its retry operation.

It MUST NOT conceal:

```text id="mye1qh"
AUTH_REQUIRED
RATE_LIMITED
```

---

# 51. ATTACH_SESSION

Attachment MUST revalidate:

* tab;
* provider;
* actor;
* page generation;
* input capability.

---

# 52. DETACH_SESSION

After successful detach:

```text id="1lj1c7"
session → CREATED
```

The session MUST NOT accept prompts while detached.

---

# 53. RESET_SESSION

Reset MUST:

1. terminate or cancel active generation where possible;
2. clear active prompt state;
3. invalidate stale actors;
4. reacquire browser/provider state;
5. establish valid context;
6. enter `PREPARING`;
7. emit `SESSION_READY` after verification.

Completed terminal prompt history MAY remain.

---

# 54. CLOSE_SESSION

Closing a session:

1. terminates any active prompt;
2. prevents new operations;
3. invalidates all retained prompt records;
4. releases session resources;
5. transitions to `CLOSED`.

Subsequent operations using the former session MUST return:

```text id="9w8o20"
UNKNOWN_SESSION
```

Default prompt/response retention:


# 58. PROMPT Acceptance

A successful `PROMPT` response MUST use:

```text id="9h4j8m"
state = ACCEPTED
```

Example:

```json id="l7h0x1"
{
  "success": true,
  "result": {
    "prompt_request_id": "uuid",
    "state": "ACCEPTED"
  }
}
```

`ACCEPTED` is a command-result state.

It is not a prompt lifecycle state.

The prompt subsequently enters:

```text id="dlh7sb"
SUBMITTING
```

when browser submission actually begins.

This prevents command acceptance from being confused with execution.

# 59. Prompt Submission Ordering

The gateway MUST perform:

```text id="j5w7tq"

    ↓

    ↓
prompt verification
    ↓
submit action
    ↓
submission verification
    ↓
INPUT_SUBMITTED
    ↓
generation detection
    ↓
GENERATION_STARTED
```

No later externally visible state may be emitted without evidence for its prerequisite.



---

# 76. Cancellation Verification

`cancel_verified=true` means the gateway has evidence that provider generation has stopped.

`cancel_verified=false` means the gateway accepted cancellation but could not verify provider cessation.

A gateway MUST NOT report `true` based solely on attempting a browser cancellation action.

When false, the session MUST NOT return to `READY` while generation may still occur.

The gateway SHOULD enter `RECOVERING` when needed to establish safe provider cessation.

---

# 77. Cancellation Arbitration

Exactly one terminal state wins.

## Case A — Completion committed before cancellation

`COMPLETED` wins.

## Case B — Cancellation accepted and provider stop verified first

`CANCELLED` wins.

## Case C — Provider completion commits before cancellation

`COMPLETED` wins.

## Case D — Cancellation accepted but stop unverified

`CANCELLED` MAY be committed only with:

```text id="tot2c3"
cancel_verified=false
```

The gateway MUST prevent overlapping generation.

# 80. Subscription Expiry

When the subscribed prompt expires:

1. the subscription MUST terminate;
2. the gateway SHOULD emit a diagnostic;
3. the diagnostic code MUST be `SUBSCRIPTION_EXPIRED`;
4. no further generation events may be delivered through that subscription.

# 99. PING

`PING` is an ordinary command:

```text id="7lzyin"
0x0070
```

Example:

```json id="cl9jrk"
{
  "garp": "1.10",
  "type": "ping",
  "timestamp": "2026-09-16T20:40:00.000Z",
  "payload": {}
}
```

`PING` MUST receive exactly one:

```text id="g7i8sk"
RESPONSE(success=true)
```

A `PING` MUST NOT be required for PONG generation.

A `PING` MUST NOT cause a PONG.

---

# 100. PONG

`PONG` is:

```text id="wst4j4"
0x0071
```

`PONG` is a server-initiated, connection-scoped liveness event.

Example:

```json id="i0o7mz"
{
  "garp": "1.10",
  "type": "pong",
  "timestamp": "2026-09-16T20:40:30.000Z",
  "payload": {}
}
```

PONG has the following mandatory header semantics:

```text id="u0t0g7"
request UUID = nil UUID
session UUID = nil UUID
```

PONG MUST NOT contain:

```text id="k4i4s8"
request_id
target_request_id
session_id
sequence
prompt_request_id
revision
```

PONG has no session association.

PONG is not a command result.

PONG MUST NOT be interpreted as a response to `PING`.

The client MUST NOT respond to PONG.

---

# 101. PONG Emission

PONG is emitted independently of PING.

The gateway MUST NOT emit PONG merely because it received PING.

When `ext-pong` has been negotiated and:

```text id="nsyy6h"
pong.enabled = true
```

the gateway SHOULD emit PONG periodically according to:

```text id="3anqss"
pong.interval_ms
```

The gateway SHOULD emit PONG only when no other frame has been sent on the connection within the effective interval.

Therefore normal connection activity MAY suppress an otherwise due PONG.

A PONG is not required immediately after a PING.

---

# 102. PONG Negotiation Timing

The gateway MUST NOT emit PONG before the successful handshake has established:

```text id="0d2n83"
ext-pong
```

and `HELLO_ACK` has been delivered.

`CAPABILITIES` reports the effective interval and timeout.

PONG MUST NOT be used before the feature negotiation is complete.

---

# 103. PONG Client Semantics

A client that negotiated PONG support MUST recognize PONG as a valid connection-scoped event.

The client MUST NOT infer PONG support from receiving a `RESPONSE` to `PING`.

A client that did not negotiate PONG support will not receive PONG.

A conforming gateway MUST NOT emit PONG to a client that did not negotiate it.

---

# 104. PONG Liveness Timeout

For a client with PONG enabled:

```text id="35lax2"
pong.timeout_ms
```

is the maximum permitted interval without receiving PONG.

The default is:

```text id="c88x9r"
90000 ms
```

or 90 seconds.

If no PONG is received within the effective timeout, the client SHOULD consider the connection stale.

The client MAY:

* initiate reconnect;
* report connection loss;
* do both.

The gateway MAY similarly determine that the peer is unresponsive according to its configured connection policy.

---

# 105. PONG and Backpressure

PONG is connection-scoped and contains no application state.

PONG MUST NOT consume a session event sequence number.

PONG MUST NOT consume retained session event history.

PONG SHOULD use a dedicated lightweight delivery path where practical.

If normal connection backpressure delays PONG, that is not by itself a protocol violation.

A client that receives no PONG within the effective timeout SHOULD consider the connection stale regardless of other queued application traffic.

---

# 106. Keepalive Defaults

Unless overridden by the effective negotiated capability:

```text id="pvm8ly"
pong.interval_ms = 30000
pong.timeout_ms  = 90000
```

The timeout MUST be greater than the interval.

A configured timeout less than or equal to the interval MUST be rejected as invalid configuration.

---

# 107. Flow Control

Implementations MUST bound:

* outstanding commands;
* outbound application-event queues;
* diagnostic buffering;
* payload sizes.

Application events MUST NOT be silently discarded.

PONG is exempt from application-event retention and session event sequencing.

Implementations SHOULD prioritize PONG sufficiently to satisfy the configured liveness deadline.

---

# 132. Conformance Levels

## Level 1 — Transport

Requires:

* framing;
* version negotiation;
* HMAC;
* RESPONSE;
* ERROR;
* PING;
* capabilities.

## Level 2 — Browser

Adds:

* browser status;
* tabs;
* sessions;
* navigation;
* page generation.

## Level 3 — Generation

Adds:

* prompt creation;
* verified input;
* verified submission;
* generation observation;
* message identity;
* append/replace semantics;
* response retrieval;
* cancellation;
* completion;
* failure.

## Level 4 — Recovery

Adds:

* stale actor handling;
* navigation drift;
* provider changes;
* authentication-required state;
* rate-limit state;
* recovery states;
* diagnostics.

## Level 5 — Replay

Adds:

```text id="5h6w83"
ext-replay-store
```

## Level 6 — PONG

Adds:

```text id="6v8y1b"
ext-pong
```

and deterministic server-initiated liveness signaling.

# 133. Extension Model

Future functionality SHOULD use:

```text id="q3t47q"
optional field
optional event
negotiated extension
reserved message type
```

Changes to:

* frame layout;
* authentication transcript;
* required state semantics;
* field types;

require a new wire version.

---

# 134. Reserved Extensions

Potential future extensions include:

```text id="d3jhn9"
ext-replay-store
ext-pong
ext-compression
ext-binary-payload
ext-subchannels
ext-multi-prompt
```

Only negotiated extensions have semantics.

---

# 135. Future Multi-Prompt Extension

`ext-multi-prompt` MAY introduce:

* multiple concurrent prompts;
* queues;
* independent prompt streams;
* targeted cancellation among concurrent prompts.

The existing request/target identity model remains applicable.

---

# 136. Future Subchannel Extension

`ext-subchannels` MAY introduce logical connection multiplexing.

It is not required for ordinary GARP/1.10.

---

# 137. Future Compression Extension

`ext-compression` MAY introduce compressed payloads.

Compression MUST NOT be inferred merely from `EXTENSION_PRESENT`.

The extension MUST define exact encoding semantics.

---

# 138. Multi-Session Architecture

A connection MAY contain multiple sessions.

A recommended mapping is:

```text id="5qgk03"
one logical browser/provider context → one session
```

A gateway MAY choose another deterministic mapping.

---

# 139. Provider Adapter Strategy

Provider adapters SHOULD use deterministic strategy ordering:

```text id="2znttm"
semantic accessibility
    ↓
stable provider attributes
    ↓
known structural selectors
    ↓
fallback discovery
```

The successful strategy SHOULD be diagnosable.

---

# 140. Security Requirements

A conforming gateway MUST:

* authenticate peers;
* use cryptographically strong nonces;
* reject authentication replay;
* validate all frame lengths;
* validate JSON;
* validate UTF-8;
* validate UUIDs;
* validate protocol state;
* rate-limit authentication failures;
* use constant-time HMAC comparison;
* prevent diagnostic secret leakage.

Secrets, cookies, access tokens, and authentication proofs MUST NOT be emitted through ordinary diagnostics.

---

# 141. Browser Security Boundary

Provider page content is untrusted.

Page content MUST NOT redefine:

* GARP framing;
* authentication;
* session identity;
* UUID ownership;
* authorization;
* state transitions;
* feature negotiation.

Provider output is data.

---

# 142. Final Canonical Rules

```text id="7tq8lj"
1. GARP/1.10 uses wire version 0x19.

2. Every command has a unique request_id.

3. PROMPT request_id becomes prompt_request_id.

4. Existing-prompt operations use target_request_id.

5. A target must belong to the command session.

6. A session has at most one active prompt.

7. Terminal prompts may remain independently retrievable.

8. PROMPT acceptance returns ACCEPTED, not SUBMITTING.

9. SUBMITTING begins only when browser submission actually begins.

10. INPUT_SUBMITTED requires verified submission.

11. GENERATION_STARTED requires generation evidence.

12. A prompt may contain multiple logical response messages.

13. Each logical response message has message_id.

14. Message revisions are independent.

15. GENERATION_DELTA uses APPEND or REPLACE.

16. Exactly one terminal prompt state may be committed.

17. Cancellation always uses explicit target_request_id.

18. cancel_verified reports actual provider-stop verification.

19. Cancellation follows the four normative race cases.

20. AUTH_REQUIRED is a first-class session state.

21. RATE_LIMITED is a first-class session state.

22. RECOVERING means repair is being performed.

23. RETRYING means a recovery retry is waiting or executing.

24. AUTH_REQUIRED and RATE_LIMITED cannot be hidden inside recovery.

25. GET_SESSION is 0x0025.

26. PROVIDER_CHANGED exists only at 0x0045.

27. Session event sequence starts at 1.

28. Session event sequence increments exactly by one.

29. Session event sequence continues across reconnect.

30. Response revisions are distinct from event sequence.

31. GET_RESPONSE(target=A) returns A or an explicit error.

32. GET_PROMPT_STATUS(target=A) returns A or an explicit error.

33. PONG is 0x0071.

34. PONG is negotiated through ext-pong.

35. PONG is connection-scoped.

36. PONG uses nil request UUID.

37. PONG uses nil session UUID.

38. PONG has no sequence.

39. PONG is never a response to PING.

40. PING always receives exactly one RESPONSE.

41. Receiving PING never triggers PONG.

42. PONG may be emitted independently.

43. PONG is emitted only after negotiation.

44. PONG uses the effective keepalive interval.

45. PONG timeout is explicit and actionable.

46. PONG does not participate in session event retention.

47. PONG does not participate in session event sequencing.

48. Replay is optional through ext-replay-store.

49. Replay never silently skips missing history.

50. Negotiated retention is authoritative.

51. Reduced retention is surfaced through capability refresh.

52. Subscription expiry is explicit.

53. Diagnostic levels are closed.

54. Diagnostic codes are namespaced.

55. Header and JSON identity must agree.

56. The authentication transcript is fully deterministic.

57. Nonces and proofs use unpadded Base64URL.

58. HMAC comparison is constant-time.

59. Closing a session invalidates its retained prompt records.

60. Process restart persistence is optional but must be consistent if claimed.

61. Multi-prompt remains an extension.

62. Subchannels remain an extension.

63. Compression remains an extension.

64. Every message type has exactly one authoritative definition.

65. Protocol success requires verified browser/provider state.
```

# 151. Implementation Target

GARP/1.10 is the implementation target.

The Firefox gateway and Delphi client are under the control of this project and MAY be modified as necessary to conform.

The protocol is therefore not constrained by today's implementation.

The implementation SHOULD be structured so that:

```text id="0k7v5h"
GARP transport
    ↓
GARP request manager
    ↓
session manager
    ↓
automation session
    ↓
provider adapter
    ↓
Firefox automation
```

can evolve independently without changing protocol semantics.
