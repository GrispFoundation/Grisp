# GARP/1.04

## Gateway AI Runtime Protocol

**Status:** Beta Implementation Specification
**Protocol Identifier:** `GARP/1.04`
**Wire Version Byte:** `0x14`
**Previous Version:** GARP/1.03 (`0x13`)
**Transport:** TCP
**Payload Encoding:** UTF-8 JSON
**Default Endpoint:** `127.0.0.1:9999`

---

# Part I — Purpose and Scope

## 1. Purpose

GARP (Gateway AI Runtime Protocol) defines the authenticated transport, browser-control, provider-automation, and generation-observation boundary between an external controller and AI providers operating inside a browser.

GARP provides a deterministic protocol for:

* browser status;
* browser tab management;
* provider capabilities;
* logical AI sessions;
* provider readiness;
* prompt injection;
* prompt submission;
* generation observation;
* streaming response delivery;
* continuation;
* cancellation;
* navigation tracking;
* provider errors;
* diagnostics;
* authenticated TCP communication.

GARP does not define:

* semantic correctness of AI output;
* correctness of generated source code;
* GRISP artifact acceptance;
* compilation or execution correctness;
* policy approval;
* model quality;
* semantic scoring;
* agent intelligence.

The provider and model remain outside the trusted semantic core.

---

# Part II — Architectural Model

## 2. Universal Message Architecture

GARP/1.04 defines four message roles:

```text
COMMAND
RESPONSE
EVENT
PROTOCOL ERROR
```

### COMMAND

A client-initiated request.

### RESPONSE

The single synchronous result mechanism for ordinary commands.

### EVENT

An asynchronous notification concerning state, progress, generation, navigation, diagnostics, or provider conditions.

### PROTOCOL ERROR

A connection/protocol failure that prevents normal command processing.

---

# 3. Mandatory Command/Response Rule

For every ordinary command:

```text
COMMAND
    |
    v
RESPONSE
```

There is exactly one synchronous command response.

A command-specific message type MUST NOT be used as the synchronous response.

For example:

```text
LIST_TABS -> RESPONSE
CAPABILITIES -> RESPONSE
BROWSER_STATUS -> RESPONSE
CREATE_SESSION -> RESPONSE
PROMPT -> RESPONSE
CANCEL_PROMPT -> RESPONSE
PING -> RESPONSE
```

This rule is normative.

---

# 4. Asynchronous Event Rule

Events are separate from command responses.

Example:

```text
CREATE_SESSION
    |
    +--> RESPONSE
    |
    +--> SESSION_CHANGED
    +--> SESSION_READY
```

Prompt execution:

```text
PROMPT
    |
    +--> RESPONSE
    |
    +--> INPUT_SUBMITTED
    +--> GENERATION_STARTED
    +--> GENERATION_DELTA*
    +--> GENERATION_PROGRESS*
    +--> CONTINUATION_REQUIRED?
    +--> CONTINUATION_SUBMITTED?
    +--> GENERATION_COMPLETED
```

A lifecycle event MUST NOT be interpreted as the synchronous response to the initiating command.

---

# 5. Handshake Exception

The initial protocol handshake is a dedicated state machine:

```text
HELLO
   |
   v
HELLO_CHALLENGE
   |
   v
HELLO_AUTH
   |
   v
HELLO_ACK
```

The handshake is completed before ordinary command processing begins.

---

# 6. Trust Boundary

GARP is a transport and observation boundary.

The trusted architecture is:

```text
External Controller
        |
        | GARP
        v
Firefox Gateway
        |
        v
Provider Adapter
        |
        v
Browser / Provider
        |
        v
Untrusted AI Output
        |
        v
GRISP / Verification Layer
```

The browser provider MUST NOT be treated as a trusted execution environment.

---

# Part III — Versioning and Wire Format

# 7. Protocol Version

GARP/1.04 identifies itself as:

```text
GARP/1.04
```

The wire protocol version byte is:

```text
0x14
```

GARP/1.03 used:

```text
0x13
```

and GARP/1.02 used:

```text
0x12
```

---

# 8. Fixed Header

The GARP fixed header is:

```text
48 bytes
```

The exact field layout MUST be implemented identically by encoder and decoder.

The receiver MUST reject:

* truncated headers;
* invalid header lengths;
* invalid payload lengths;
* oversized frames;
* malformed flags;
* unsupported protocol versions.

---

# 9. Payload

The payload is UTF-8 encoded JSON.

The JSON object associated with each message MUST conform to the schema specified for that message.

Implementations MUST NOT silently reinterpret invalid JSON types.

For example:

```json
{
  "page_generation": "2"
}
```

is not equivalent to:

```json
{
  "page_generation": 2
}
```

# 11. Registry Allocation Policy

Numeric message identifiers are intentionally grouped.

```text
0x0000–0x000F  protocol / handshake
0x0010–0x001F  browser / tabs
0x0020–0x002F  sessions
0x0030–0x003F  prompt commands
0x0040–0x004F  session/navigation events
0x0050–0x005F  generation events
0x0060–0x006F  provider/diagnostic events
0x0070–0x007F  keepalive
```

Unused identifiers remain reserved.

Future messages SHOULD be allocated within the corresponding functional range.

---

# 12. Removed Message Types

The following messages are not part of the active GARP/1.04 protocol:

```text
PROMPT_ACK
CANCEL_ACK
```

They MUST NOT be emitted by a GARP/1.04 implementation.

Their functions are replaced by:

```text
PROMPT        -> RESPONSE
CANCEL_PROMPT -> RESPONSE
```

# Part V — Common Fields

# 13. request_id

`request_id` is a string identifying one logical client command/request.

It MUST be unique within the connection's active request namespace unless idempotent replay semantics explicitly apply.

---

# 14. session_id

`session_id` is a stable logical identifier for a provider session.

It MUST survive:

* actor replacement;
* document replacement;
* provider navigation;
* reconnect handling where session persistence is supported.

---

# 15. message_id

`message_id` identifies one observed provider response message.

It is distinct from `request_id`.

One request MAY generate one or more observations, but the provider's resulting logical response MUST have one authoritative `message_id` once identified.

---

# 16. sequence

`sequence` is a monotonically increasing unsigned integer for a request-associated event stream.

The receiver MUST be able to detect:

* duplicate events;
* reordered events;
* missing events.

---

# 17. page_generation

`page_generation` identifies the logical browser document/actor generation associated with a session operation.

It MUST:

* be a positive integer;
* monotonically increase;
* never decrease.

---

# 18. timestamp

Timestamps MUST use UTC RFC 3339 / ISO-8601 representation.

Example:

```text
2026-09-15T21:00:00.000Z
```

# Part VI — Handshake Schemas

# 19. HELLO

**Numeric:** `0x0001`

**Direction:** Client -> Gateway

```json
{
  "protocol": "GARP/1.04",
  "client_id": "string",
  "client_nonce": "string",
  "features": ["string"],
  "metadata": {}
}
```

Required:

```text
protocol
client_id
client_nonce
```

---

# 20. HELLO_CHALLENGE

**Numeric:** `0x0002`

**Direction:** Gateway -> Client

```json
{
  "protocol": "GARP/1.04",
  "server_nonce": "string",
  "algorithm": "HMAC-SHA256"
}
```

---

# 21. HELLO_AUTH

**Numeric:** `0x0003`

**Direction:** Client -> Gateway

```json
{
  "protocol": "GARP/1.04",
  "client_id": "string",
  "client_nonce": "string",
  "server_nonce": "string",
  "proof": "string"
}
```

The proof is:

```text
HMAC-SHA256(
    shared_secret,
    "GARP/1.04" |
    client_id |
    client_nonce |
    server_nonce
)
```

The mapping:

```text
0x0003 <-> hello_auth
```

is normative and MUST work in both encoding and decoding directions.

---

# 22. HELLO_ACK

**Numeric:** `0x0004`

**Direction:** Gateway -> Client

```json
{
  "protocol": "GARP/1.04",
  "server_id": "string",
  "authenticated": true,
  "features": ["string"]
}
```

`authenticated=true` MUST NOT be reported until the gateway has successfully validated `HELLO_AUTH`.

---

# Part VII — Universal Response

# 23. RESPONSE

**Numeric:** `0x0005`

`RESPONSE` is the universal synchronous command-result envelope.

Success:

```json
{
  "command": "list_tabs",
  "success": true,
  "result": {}
}
```

Failure:

```json
{
  "command": "list_tabs",
  "success": false,
  "error": {
    "code": "TAB_NOT_FOUND",
    "message": "Tab not found",
    "retryable": false,
    "state": "ERROR"
  }
}
```

The outer GARP frame MUST contain the request correlation.

---

# 24. RESPONSE Rules

A conforming gateway MUST:

1. emit at most one synchronous response for one command;
2. emit exactly one response for an accepted ordinary command;
3. preserve the originating request correlation;
4. identify the originating command in `command`;
5. place command-specific data inside `result`.

No command may invent its own synchronous response message type.

---

# Part VIII — Protocol Error

# 25. ERROR

**Numeric:** `0x0006`

```json
{
  "code": "PROTOCOL_ERROR",
  "message": "Invalid frame",
  "retryable": false,
  "state": "ERROR",
  "details": {}
}
```

`ERROR` is reserved for conditions where normal protocol processing cannot continue.

An application-level command failure SHOULD normally use:

```text
RESPONSE(success=false)
```

instead.

The canonical successful execution path is:

```text
READY

  v
```

# Part XVII — Readiness

# 63. Readiness Is State, Not Time

Readiness MUST be determined from current browser/provider state.

The following are not sufficient evidence:

```text
tab created
navigation started
navigation ended
actor created
one second elapsed
1.5 seconds elapsed
3 seconds elapsed
```

Fixed client sleeps MUST NOT be treated as readiness proof.

---

# 64. Provider Inspection

The gateway MUST be able to query current provider state.

An inspection SHOULD establish:

```text
authenticated
rate_limited
input_ready
input_state
message_count
last_message_text
streaming
provider_state
url
```

---

# 65. SESSION_READY Requirement

`SESSION_READY` MUST imply:

```text
session.state = READY
inputState = READY
provider input exists
provider input is visible/usable
provider authentication requirements are satisfied
provider is not known to be rate limited
```

---

# Part XVIII — Actor and Page Generation Safety

# 66. Actor Replacement

Firefox JSWindow actors are not permanent identities.

A provider page may cause actor replacement due to navigation or document recreation.

The logical session MUST survive actor replacement.

---

# 67. Current Actor Acquisition

A gateway MUST reacquire the active actor for each browser-side operation.

The gateway MUST NOT depend indefinitely on a cached actor reference.

---

# 68. Stale Actor Rule

A result associated with an older `page_generation` MUST NOT overwrite authoritative state belonging to a newer page generation.

Stale results MUST either:

* be discarded;
* be explicitly diagnosed;
* cause an appropriate protocol failure.

---

# 69. Page Generation Changes

The gateway MUST advance `page_generation` when relevant identity changes occur, including:

* provider navigation;
* document replacement;
* actor replacement;
* conversation replacement;
* reset;
* attach to a new document.

The exact reason SHOULD be included in `NAVIGATION` or `DIAGNOSTIC`.

# Part XIX — Input Injection

# 70. Provider Adapter Responsibility

Each provider adapter owns provider-specific:

* input selectors;
* send-button selectors;
* response selectors;
* continuation selectors;
* authentication detection;
* rate-limit detection;
* provider-specific interaction methods.

---

# 71. Input Discovery

Input discovery MUST operate on the live document.

Adapters SHOULD support:

* normal DOM;
* shadow DOM where appropriate;
* provider-specific selectors;
* fallback selectors.

The adapter SHOULD report candidate information to the diagnostics subsystem.

---

# 72. Injection Verification

Successful assignment to the DOM is not sufficient.

After injection the provider adapter MUST verify that the current live input reflects the intended prompt.

Verification MUST account for controlled UI frameworks that may:

* replace the DOM node;
* reject programmatic values;
* overwrite the value;
* require input events;
* require change events;
* update a framework state object separately from DOM state.

---

# 73. Native Input Handling

For ordinary text inputs and textareas, implementations SHOULD use a browser-compatible native value-setting approach rather than relying exclusively on deprecated or unreliable `execCommand` insertion.

Input and change events SHOULD be dispatched where required by provider framework behavior.

---

# 74. DOM Replacement

If the provider replaces the input node after mutation:

```text
old input node
     |
     v
new input node
```

the adapter MUST re-query the current input and verify the new node.

The original element reference MUST NOT be trusted indefinitely.

# Part XX — Submission

# 75. Submission Methods

Providers MAY use:

```text

keyboard_enter
form_submit
provider_specific
```

The adapter MUST explicitly report which method succeeded.

---

# 76. Submission Failure

When no valid submission method is discovered:

```text
SUBMIT_FAILED
```

MUST be reported.

The gateway MUST NOT pretend that a prompt was submitted merely because it was injected into the DOM.

---

# 77. Submission Verification

Where provider behavior allows it, submission SHOULD be verified through observable state such as:

* prompt leaving editable input;
* generation indicator appearing;
* new user message appearing;
* provider DOM state changing;
* response observation beginning.

Submission verification SHOULD be provider-specific.

# Part XXI — Generation Observation

# 78. Observation Is Transport-Level

The gateway observes provider output.

It does not judge whether that output is:

* correct;
* safe;
* valid;
* compilable;
* useful;
* complete.

---

# 79. Message Detection

Adapters MAY identify response messages by:

* DOM node count;
* provider-specific message IDs;
* content changes;
* role metadata;
* DOM structure.

When possible, a stable provider-specific identity SHOULD be used.

---

# 80. Delta Rules

`GENERATION_DELTA` conveys the newly observed text portion.

If the current provider text does not extend the previous text, the adapter MUST NOT assume a simple append-only model.

The gateway MAY emit a full replacement observation when necessary.

---

# 81. Completion

A generation may be considered complete when:

* provider streaming state is inactive;
* no continuation condition remains;
* a response has been identified;
* the result has stabilized according to the configured provider-specific rules.

Completion timing MUST be based on state observation rather than a single arbitrary delay.

# Part XXII — Continuation

# 82. Continuation Detection

A continuation condition is provider-specific.

Examples may include:

* explicit Continue button;
* provider length-limit indication;
* provider-specific continuation control.

---

# 83. Continuation Limit

Automatic continuation MUST honor:

```text
max_continuations
```

The gateway MUST fail closed if the configured maximum is exceeded.

# Part XXIII — Cancellation

# 84. Cancellation

Cancellation requests a stop of active provider generation.

The request result:

```text
CANCEL_REQUESTED
```

does not guarantee that the provider has already stopped.

A subsequent provider/session event establishes the observed terminal state.

---

# 85. Cancellation Race

Cancellation and completion may race.

The gateway MUST use authoritative request state to ensure that a request is not emitted as both successfully completed and cancelled as its final state.

# Part XXV — Connection Processing

# 94. Frame Processing

The receiver MUST:

2. parse header;
3. validate header size;
4. validate payload size;
5. verify complete frame availability;
6. decode frame;
7. validate message type;

9. validate schema;
10. validate authentication state;

# 95. Serialized Command Processing

A connection implementation SHOULD serialize command dispatch so that concurrent callbacks cannot mutate the same session unpredictably.

# 129. Final Architectural Rules

GARP/1.04 establishes the following as foundational rules:

1. **One universal synchronous response:** every ordinary command returns `RESPONSE`.
2. **Typed asynchronous events:** lifecycle and generation state use dedicated event messages.
3. **Dedicated handshake:** `HELLO → HELLO_CHALLENGE → HELLO_AUTH → HELLO_ACK`.
4. **Grouped numeric registry:** protocol, browser, sessions, prompts, lifecycle, generation, diagnostics, and keepalive occupy separate numeric ranges.
5. **No fake readiness:** time delays do not establish provider readiness.
6. **Verified input:** DOM mutation is not sufficient without verification.
7. **Verified submission:** successful injection is not equivalent to successful submission.
8. **Strict generation ordering:** `INPUT_SUBMITTED` precedes `GENERATION_STARTED`.
9. **Actor safety:** stale actors and stale page generations cannot overwrite newer state.
10. **Central diagnostics:** automation debugging is structured and correlated.
11. **No secret leakage:** authentication material is excluded from diagnostics.
12. **No semantic trust:** GARP transports provider observations but does not decide whether AI output is correct.
