# GARP/1.12

## Gateway AI Runtime Protocol

**Status:** Normative / Implementation Target
**Protocol Version:** `1.12`
**Wire Version:** `0x19`

---

# 1. Purpose

GARP, the Gateway AI Runtime Protocol, defines a deterministic authenticated protocol between an external controller and an AI gateway operating browser-based AI providers.

GARP provides:

* authenticated transport;
* browser and tab management;
* logical sessions;
* one active prompt per session;
* explicit prompt identity;
* bounded prompt history;
* multi-message generation;
* streaming `APPEND` / `REPLACE` semantics;
* explicit continuation;
* deterministic cancellation;
* provider state;
* browser recovery;
* page-generation fencing;
* session event sequencing;
* authoritative snapshots;
* optional event replay;
* optional server-initiated PONG;
* structured diagnostics;
* structured capability discovery;
* deterministic protocol evolution.

GARP does not define AI reasoning, planning, semantic correctness, model policy, or downstream verification.

---

# 2. Design Principles

The base protocol intentionally remains small.

The fundamental model is:

```text
Connection
    |
    +-- Session
          |
          +-- one active Prompt
          |
          +-- retained terminal Prompts
```

A session MUST NOT execute two active prompts concurrently.

A session MAY retain multiple completed, failed, or cancelled prompt records.

A retained prompt remains explicitly addressable until retention expiry or session closure.

---

# 3. Explicit Non-Goals

The following are not base GARP/1.12 features:

```text
concurrent prompts within one session
prompt queues
subchannel multiplexing
mandatory compression
mandatory binary-media transport
unlimited event history
```

Future extensions MAY add these capabilities.

---

# 4. Versioning

GARP/1.12 uses:

```text
protocol_version = 1.12
wire_version     = 0x19
```

The 48-byte binary frame remains unchanged.

The change from 1.11 to 1.12 is therefore a protocol-semantic revision, not a binary frame redesign.

---

# 5. Version Negotiation

The client advertises supported protocol versions in `HELLO`.

The gateway selects one advertised version.

The selected protocol version governs all semantics for the connection.

A gateway MUST NOT use 1.12-only semantics when an older version has been selected.

A client MUST NOT assume 1.12 semantics merely because the peer uses wire version `0x19`.

---

# 6. Transport

GARP operates over a reliable byte stream.

Supported transports:

* TCP;
* Unix-domain sockets where available.

Plaintext GARP MUST NOT be exposed to non-loopback networks.

TLS is REQUIRED for non-loopback TCP.

Authentication remains mandatory when TLS is used.

---

# 7. Local Security

Loopback is not itself a cryptographic security boundary.

On multi-user hosts, shared environments, containers, or other deployments where another process may access loopback traffic, deployments handling sensitive information SHOULD use:

* Unix-domain socket permissions;
* TLS;
* host-level access control;
* or an equivalent isolation mechanism.

---

# 8. Frame Format

Every frame contains a fixed 48-byte header.

All multi-byte integers are big-endian.

| Offset | Size | Field          |
| -----: | ---: | -------------- |
|      0 |    4 | Magic          |
|      4 |    1 | Wire Version   |
|      5 |    1 | Flags          |
|      6 |    2 | Header Length  |
|      8 |    4 | Payload Length |
|     12 |    2 | Message Type   |
|     14 |    2 | Reserved       |
|     16 |   16 | Request UUID   |
|     32 |   16 | Session UUID   |

# 10. UUID Encoding

UUIDs in the binary header MUST use their canonical 16-byte network-order representation.

Implementations MUST NOT serialize platform-specific in-memory UUID structures directly.

The nil UUID is:

```text id="2mpom7"
00000000-0000-0000-0000-000000000000
```

---

# 11. Flags

GARP/1.12 defines:

```text id="s81kb2"
0x00  no flags
0x01  EXTENSION_PRESENT
```

Unknown flags MUST be rejected unless the corresponding extension has been successfully negotiated.

---

# 12. Payload Encoding

Base payloads are UTF-8 JSON.

The JSON root MUST be an object.

Default maximum payload:

```text id="umr0hm"
16777216 bytes
```

The effective maximum MUST be advertised through `CAPABILITIES`.

---

# 13. JSON Envelope

Every JSON message MUST contain:

```json id="n5z2me"
{
  "garp": "1.12",
  "type": "message_name",
  "timestamp": "2026-09-16T20:15:31.427Z",
  "payload": {}
}
```

Required fields:

```text id="bqnvby"
garp
type
timestamp
payload
```

`garp` MUST equal the negotiated protocol version.

---

# 14. Timestamp

Timestamp format is exactly:

```text id="c4kz84"
YYYY-MM-DDTHH:MM:SS.sssZ
```

All timestamps are UTC.

A receiver MUST NOT reject a message solely because of normal clock skew.

---

# 15. Header/JSON Consistency

The binary header is authoritative for binary framing.

The JSON envelope is authoritative for JSON semantics.

The following MUST agree:

```text id="o2rhhy"
header.message_type ↔ JSON type
header.request_uuid ↔ JSON request_id, when present
header.session_uuid ↔ JSON session_id, when present
```

A mismatch MUST fail closed with:

```text id="90v7ok"
HEADER_JSON_MISMATCH
```

For prompt events:

```text id="o54j5q"
prompt_request_id
```

identifies the prompt and is independent of the current command request UUID.

---

# 16. Schema Authority

When any ambiguity exists, authority is:

```text id="d9lq6w"
1. normative requirements
2. common envelope / identity rules
3. message schema
4. normative field tables
5. state and invariant rules
6. examples
7. explanatory prose
```

An example MUST NOT override a normative rule.

---

# 17. Unknown JSON Fields

Unknown JSON fields MUST be ignored unless the relevant schema explicitly declares that field space closed.

Unknown fields MUST NOT break forward compatibility by default.

Extension-specific fields SHOULD be placed under `_extensions`.

---

# 18. Extension Object

When `EXTENSION_PRESENT` is set, the JSON object MAY contain:

```json id="4bix0e"
{
  "_extensions": {
    "ext-example": {
      "value": {}
    }
  }
}
```

`_extensions` is an object keyed by extension name.

Unknown optional extensions MAY be ignored.

Unknown required extensions MUST cause negotiation failure.

---

# 19. Message Validation Order

Inbound messages MUST be validated in this order:

```text id="0tzy0l"
1. frame structure
2. wire version
3. header fields
4. message type
5. payload encoding
6. JSON syntax
7. common envelope
8. message schema
9. connection/authentication state
10. request identity
11. session identity
12. target identity
13. state transition
14. provider-specific semantics
```

The first applicable failure determines the validation result.

# 21. Registry Consistency

Every registered message MUST have exactly one authoritative definition.

No message may have:

* multiple numeric assignments;
* multiple meanings;
* incompatible schemas;
* duplicate registry entries.

---

# 22. Handshake

The handshake is:

```text id="73ixfl"
HELLO
    ↓
HELLO_CHALLENGE
    ↓
HELLO_AUTH
    ↓
HELLO_ACK
```

No application command is valid before successful authentication.

---

# 23. Handshake Request UUID

The handshake uses one fresh UUID:

```text id="ufj3l2"
HELLO            = H
HELLO_CHALLENGE  = H
HELLO_AUTH       = H
HELLO_ACK        = H
```

This UUID is non-zero.

---

# 24. HELLO

Example:

```json id="nl0yxp"
{
  "garp": "1.12",
  "type": "hello",
  "timestamp": "2026-09-16T20:15:31.427Z",
  "payload": {
    "client_name": "GARP101.Client",
    "client_version": "1.12.0",
    "supported_versions": ["1.12", "1.11"],
    "features": [
      "ext-pong",
      "ext-replay-store"
    ],
    "nonce": "base64url"
  }
}
```

The client nonce MUST contain at least 128 bits of cryptographically secure random data.

---

# 25. HELLO_CHALLENGE

Example:

```json id="7i9uwc"
{
  "garp": "1.12",
  "type": "hello_challenge",
  "timestamp": "2026-09-16T20:15:31.428Z",
  "payload": {
    "server_name": "GARP Firefox Gateway",
    "server_version": "1.12.0",
    "selected_version": "1.12",
    "nonce": "base64url",
    "features": [
      "ext-pong"
    ]
  }
}
```

The server nonce MUST contain at least 128 bits of cryptographically secure random data.

---

# 26. Feature Negotiation

`HELLO.features` represents features offered by the client.

`HELLO_CHALLENGE.features` represents features accepted by the gateway.

`HELLO_ACK.features` represents the final negotiated set.

A feature offered by the client but absent from the challenge is declined.

A feature marked with `!` is required.

If a required feature is declined, the handshake MUST fail.

The final negotiated feature set is exactly the set advertised by `HELLO_ACK`.

---

# 27. Feature Representation

Handshake features are always strings:

```text id="74xl1u"
["ext-pong", "ext-replay-store"]
```

Negotiated parameters are not encoded in this array.

They are reported through `CAPABILITIES`.

---

# 28. Base64URL

Nonce and proof values use unpadded Base64URL.

Allowed alphabet:

```text id="62th4d"
A-Z
a-z
0-9
-
_
```

The `=` padding character MUST NOT appear.

Nonce values represent raw bytes.

Proof values represent raw HMAC bytes.

---

# 29. Authentication Transcript

The authentication transcript consists of exactly:

```text id="vhu3kf"
u32be(domain_length)
domain_utf8

u32be(client_nonce_length)
client_nonce_raw

u32be(server_nonce_length)
server_nonce_raw

u32be(selected_version_length)
selected_version_utf8

u32be(client_name_length)
client_name_utf8

u32be(client_version_length)
client_version_utf8

u32be(server_name_length)
server_name_utf8

u32be(server_version_length)
server_version_utf8
```

All lengths are unsigned 32-bit big-endian byte counts.

The transcript contains raw nonce bytes, not Base64URL text.

The domain for client authentication is:

```text id="kb7nye"
GARP-CLIENT-AUTH
```

The domain for server authentication is:

```text id="s1zkvl"
GARP-SERVER-AUTH
```

The selected protocol version is included explicitly in the transcript and therefore binds authentication to the negotiated version.

---

# 30. Shared Secret

The shared secret is an out-of-band byte string.

It MUST contain at least:

```text id="hg1xx1"
32 bytes
```

of secret material.

The protocol does not mandate a particular provisioning representation.

A deployment MAY provision the secret as:

* raw bytes;
* hexadecimal;
* Base64;
* another secure configuration representation.

The provisioning format MUST be converted to the exact shared-secret bytes before HMAC calculation.

---

# 31. Client Authentication

Client proof:

```text id="8yr7x9"
HMAC-SHA256(secret, client_transcript)
```

The gateway MUST verify the proof using constant-time comparison.

---

# 32. Server Authentication

`HELLO_ACK` MUST contain:

```json id="ojm0f8"
{
  "server_proof": "base64url"
}
```

Server proof:

```text id="bq6eas"
HMAC-SHA256(secret, server_transcript)
```

The client MUST verify `server_proof`.

The client MUST complete server-proof verification before transmitting sensitive application content.

A client MUST NOT rely solely on:

```text id="s8xzo3"
"authenticated": true
```

to establish gateway identity.

---

# 33. HELLO_ACK

Example:

```json id="h3hj9e"
{
  "garp": "1.12",
  "type": "hello_ack",
  "timestamp": "2026-09-16T20:15:31.430Z",
  "payload": {
    "authenticated": true,
    "selected_version": "1.12",
    "features": [
      "ext-pong"
    ],
    "server_proof": "base64url"
  }
}
```

The connection enters `AUTHENTICATED` only after successful server-proof verification by the client.

---

# 34. Authentication Replay Protection

The gateway MUST:

* use unpredictable nonces;
* reject reuse of an accepted authentication transcript;
* maintain a bounded replay cache;
* expire incomplete handshakes.

Accepted authentication transcript identities SHOULD remain protected against replay for at least 24 hours.

---

# 35. Authentication Timeout

Incomplete handshakes SHOULD expire after:

```text id="nukqzi"
5 seconds
```

---

# 36. Authentication Backoff

Repeated authentication failures SHOULD use bounded exponential backoff:

```text id="9tvieq"
1 s
2 s
4 s
8 s
16 s
30 s maximum
```

Bounded random jitter SHOULD be added.

Successful authentication resets the failure counter.

---

# 37. RESPONSE

A valid command receives exactly one terminal `RESPONSE`.

Success:

```json id="g3b7f1"
{
  "garp": "1.12",
  "type": "response",
  "timestamp": "2026-09-16T20:15:31.500Z",
  "payload": {
    "success": true,
    "result": {}
  }
}
```

Failure:

```json id="wxbn9g"
{
  "garp": "1.12",
  "type": "response",
  "timestamp": "2026-09-16T20:15:31.500Z",
  "payload": {
    "success": false,
    "error": {
      "code": "SESSION_BUSY",
      "retryable": true,
      "message": "Session already has an active prompt."
    }
  }
}
```

# 40. AUTH_REQUIRED

When provider authentication is required:

```text id="zrl7yk"
session → AUTH_REQUIRED
```

If an active prompt exists, it MUST terminate with:

```text id="0swx6n"
GENERATION_FAILED
```

and:

```text id="5v29ow"
PROVIDER_AUTH_REQUIRED
```

The prompt remains retained as failed.

---

# 41. RATE_LIMITED

When provider rate limiting prevents operation:

```text id="tgnv40"
session → RATE_LIMITED
```

If the provider terminates the operation, the active prompt MUST fail with:

```text id="fmi2e5"
PROVIDER_RATE_LIMITED
```

If provider semantics explicitly permit continuation, the prompt MAY remain active.

The session MUST NOT become `READY` while provider blocking remains active.

---

# 42. RECOVERING

`RECOVERING` means active repair is being performed.

Examples:

* actor reacquisition;
* DOM rediscovery;
* context reconstruction;
* adapter revalidation.

---

# 43. RETRYING

`RETRYING` means another recovery attempt has been selected and is being waited for or executed.

It MUST NOT conceal:

```text id="7392q1"
AUTH_REQUIRED
RATE_LIMITED
```

# 49. ATTACH_SESSION

Attachment MUST revalidate:

* tab;
* provider;
* actor;
* page generation;
* input capability.

The session returns through `PREPARING` before reaching `READY`.

---

# 50. DETACH_SESSION

A detached session MUST NOT accept new prompts.

The session SHOULD return to:

```text id="r7tgrz"
CREATED
```

---

# 51. RESET_SESSION

Reset MUST:

1. terminate or cancel the active prompt where possible;
2. invalidate stale actors;
3. reacquire browser/provider state;
4. establish a valid page context;
5. enter `PREPARING`;
6. emit `SESSION_READY` after verification.

Completed terminal history MAY remain.

---

# 52. CLOSE_SESSION

Closing a session:

1. terminates an active prompt;
2. prevents new operations;
3. invalidates all retained prompt records;
4. releases session resources;
5. transitions to `CLOSED`.

Subsequent use of the session MUST return:

```text id="lq8hlw"
UNKNOWN_SESSION
```

# 54. Prompt Options

`PROMPT.options` MAY contain:

```json id="as02qb"
{
  "timeout_ms": 120000,
  "auto_continue": false,
  "max_continuations": 3,
  "force_focus": true,
  "simulate_enter": false
}
```

### timeout_ms

Maximum desired prompt-operation duration.

`0` means no client-requested timeout.

### auto_continue

If `true`, the gateway MAY automatically continue when provider continuation is required.

### max_continuations

Maximum permitted continuation operations.

`0` means no continuation is allowed.

### force_focus

Requests provider input focus before submission.

### simulate_enter

Requests Enter-equivalent submission when supported.

---

# 55. Option Schema

The `options` object is a closed base-protocol field set.

Unknown base option names MUST produce:

```text id="70e99d"
INVALID_ARGUMENT
```

Extension-specific options MUST be placed under `_extensions`.

This explicitly overrides the general unknown-field rule for the base `PROMPT.options` object.

---

# 56. Prompt Acceptance

A successful `PROMPT` command returns:

```text id="oe8et7"
state = ACCEPTED
```

Example:

```json id="ref3om"
{
  "success": true,
  "result": {
    "prompt_request_id": "uuid",
    "state": "ACCEPTED"
  }
}
```

`ACCEPTED` is a command-result state, not a prompt lifecycle state.

Immediately after acceptance, the prompt record is in a gateway-owned pre-execution state.

The first externally observable prompt lifecycle state is `SUBMITTING`.

A prompt MUST NOT be reported as `GENERATING` before generation evidence exists.

---

# 57. Prompt Submission Ordering

The logical order is:

```text id="kp5e2h"
session verification
    ↓
input discovery
    ↓
input injection
    ↓
input verification
    ↓
submit action
    ↓
submission verification
    ↓
INPUT_SUBMITTED
    ↓
generation detection
    ↓
GENERATION_STARTED
```

---

# 58. Prompt Mutation Prohibition

The transport MUST NOT silently:

* trim whitespace;
* alter line endings;
* normalize Unicode;
* collapse whitespace;
* change capitalization;
* reinterpret prompt text;
* otherwise alter the bytes or characters intentionally supplied by the caller.

Prompt content is opaque data at the GARP boundary.

---

# 59. Prompt Page-Generation Binding

When provider interaction begins, the prompt is bound to the page generation of the validated browser context.

Provider operations MUST verify that the page generation remains current.

---

# 60. Page-Generation Fencing

Navigation or browser-context replacement increments:

```text id="1z12a8"
page_generation
```

Every relevant browser/generation event MUST carry page generation.

Every asynchronous state write MUST be fenced.

Conceptually:

```text id="ou9d6i"
write_generation < current_generation
    => reject write
```

An older actor MUST NOT overwrite newer authoritative state.

# 62. Response Format

Closed enumeration:

```text id="6t6p47"
text
markdown
html
unknown
```

# 63. Logical Response Messages

One prompt MAY contain multiple logical provider response messages.

Each logical message has:

```text id="5c3frk"
message_id
```

unique within that prompt.

A new `message_id` is created when the provider begins a new logical assistant response within the same prompt.

A provider message boundary MAY arise from:

* a new assistant response;
* a provider tool/result boundary;
* a new response block;
* continuation that begins a new logical provider response.

The provider adapter MUST use a deterministic rule for identifying message boundaries.

---

# 64. Continuation and Message Identity

Continuation does not automatically imply a new message.

The adapter MUST determine whether continuation:

```text id="2qy0kh"
continues the existing logical message
```

or:

```text id="xur0m6"
creates a new logical message
```

based on provider-observable semantics.

The decision MUST be deterministic for a given adapter and provider behavior.

---

# 65. Message Revision

Message revision is scoped to:

```text id="3n0a8f"
(prompt_request_id, message_id)
```

Initial revision:

```text id="hqs4fq"
0
```

First authoritative content:

```text id="e57q0y"
1
```

Every authoritative content change increments revision.

# 75. Continuation Limits

When:

```text id="b3b4i1"

```

the gateway MUST NOT automatically submit another continuation.

The prompt MUST fail with:

```text id="2b39qm"
CONTINUATION_LIMIT_REACHED
```

when another continuation is required.

The failure MUST contain:

```text id="xppq8f"

```

according to whether authoritative response content exists.

---

# 76. Auto-Continue

When:

```text id="j65j6b"

```

the gateway MAY automatically submit continuations.

It MUST NOT exceed `max_continuations`.

When:

```text id="n3rvpq"
auto_continue = false
```

the gateway MUST wait in `WAITING_CONTINUATION` until `CONTINUE_PROMPT` is received.

This makes `auto_continue=false` fully usable.

# 77. Prompt Timeout

When `timeout_ms > 0`, the gateway SHOULD terminate the prompt when the configured duration has elapsed.

If the operation has not reached a terminal state, it MUST terminate as:

```text id="s7q5q3"
FAILED
```

with:

```text id="5u0j42"
PROMPT_TIMEOUT
```

and:

```text id="e3m646"
partial = true|false
```

according to authoritative response content.

A timeout MUST NOT permit the session to return to `READY` while provider generation may still be active.

# 82. Cancellation Verification

`cancel_verified=true` means provider generation cessation has been verified.

`cancel_verified=false` means cancellation was accepted but cessation could not be verified.

The gateway MUST NOT claim verified cancellation merely because a cancellation action returned without exception.

---

# 83. Cancellation Arbitration

The terminal race is resolved as follows.

### Case A

Completion is committed before cancellation is accepted:

```text id="x6c9uw"
COMPLETED
```

wins.

### Case B

Cancellation is accepted and provider stop is verified before completion commits:

```text id="1zg0bx"
CANCELLED
```

wins.

### Case C

Provider completion commits before cancellation can commit:

```text id="m7wjyk"
COMPLETED
```

wins.

### Case D

Cancellation is accepted but provider stop cannot be verified:

```text id="rqw6qy"
CANCELLED
```

MAY be committed with:

```text id="6vvi6c"
cancel_verified=false
```

but the session MUST enter or remain:

```text id="ms3czp"
RECOVERING
```

until provider cessation has been positively verified.

The session MUST NOT return to `READY` while overlapping generation remains possible.

# 89. Subscription Expiry

1. the subscription MUST terminate;

# 108. PING

`PING` is:

```text id="q0i2m9"
0x0070
```

It is an ordinary command.

It MUST receive exactly one `RESPONSE(success=true)`.

Receiving PING MUST NOT cause PONG emission.

---

# 109. PONG

`PONG` is:

```text id="7u7mgk"
0x0071
```

It is an unsolicited connection-scoped liveness event.

PONG:

* is not a command result;
* is not a response to PING;
* has nil request UUID;
* has nil session UUID;
* has no sequence;
* has no prompt identity;
* has no revision;
* has empty payload.

Example:

```json id="2c9xwe"
{
  "garp": "1.12",
  "type": "pong",
  "timestamp": "2026-09-16T20:40:30.000Z",
  "payload": {}
}
```

---

# 110. PONG Emission

The gateway MUST NOT emit PONG merely because it received PING.

After `ext-pong` is negotiated and `pong.enabled=true`, the gateway SHOULD emit PONG when no other frame has been sent on the connection during:

```text id="hlb2vq"
pong.interval_ms
```

Ordinary connection traffic MAY suppress a scheduled PONG.

PONG MUST NOT be emitted before `HELLO_ACK`.

---

# 111. PONG Negotiation

A gateway MUST NOT emit PONG unless `ext-pong` is present in the final negotiated feature set.

The client MUST NOT infer PONG support from:

```text id="bk9r7v"
PING → RESPONSE
```

PONG support is established only by negotiation.

---

# 112. PONG Liveness

Default:

```text id="w5h2r0"
interval_ms = 30000
timeout_ms  = 90000
```

For PONG-enabled clients, an inbound GARP frame demonstrates application-layer activity.

The client's liveness timer MUST therefore be reset on receipt of **any valid inbound frame**.

A client that receives no valid frame within:

```text id="j0wc0l"
pong.timeout_ms
```

SHOULD consider the connection stale.

The client MAY reconnect or report connection loss.

---

# 113. PONG and Backpressure

PONG does not consume:

* session sequence;
* session history;
* prompt history.

PONG is not retained.

PONG SHOULD use a lightweight connection path.

A delayed PONG is not itself a protocol violation.

The liveness timeout considers all valid inbound traffic, not PONG alone.

---

# 114. Flow Control

Implementations MUST bound:

* outstanding requests;
* queued application events;
* diagnostics;
* generation buffers;
* prompt sizes;
* response sizes.

Application events MUST NOT be silently discarded.

PONG is exempt from session event retention and sequence accounting.

# 116. Adapter Strategy

Provider DOM structures are expected to change.

The gateway MUST favor explicit failure over false success.

Provider adapter versions and selector strategy versions SHOULD be exposed through `CAPABILITIES`.

---

# 117. Untrusted Page Content

Provider page content is untrusted.

Page-derived strings MUST be treated as opaque data.

The gateway MUST NOT:

* evaluate provider text as executable code;
* execute provider text as JavaScript;
* trust DOM text as protocol JSON;
* interpret provider text as GARP commands;
* allow page content to modify session identity;
* allow page content to alter authentication state.

---

# 118. Browser Security Boundary

Page content MUST NOT redefine:

* GARP framing;
* authentication;
* session identity;
* UUID ownership;
* authorization;
* state transitions;
* extension negotiation.

---

# 119. State Write Fencing

Every asynchronous browser/provider state write MUST carry or derive its effective page generation.

A write for an older page generation MUST be rejected.

Example:

```text id="w03oy7"
current = 15
write = 14
→ reject
```

A newer valid state MUST NOT be overwritten by a stale actor.

---

# 120. Operational Responsibility

GARP does not authorize circumvention of provider security controls.

Implementations MUST NOT use protocol semantics to:

* bypass CAPTCHAs;
* defeat access controls;
* evade provider rate limits.

Implementations SHOULD respect provider authentication, rate limits, terms, and applicable policies.

# 125. Conformance Invariants

### C1

Every command has a unique request ID.

### C2

Every command response correlates to that request ID.

### C3

Existing-prompt operations require `target_request_id`.

### C4

Target belongs to the same session.

### C5

One session has at most one active prompt.

### C6

Terminal prompts remain addressable until expiry.

### C7

`GET_RESPONSE(target=A)` never returns B.

### C8

`CANCEL_PROMPT(target=A)` never cancels B.

### C9

Prompt identity remains unchanged across continuation.

### C10

Message IDs are stable within a prompt.

### C11

Message revision is scoped to `(prompt_request_id,message_id)`.

### C12

APPEND and REPLACE semantics are distinct.

### C13

PROMPT acceptance returns `ACCEPTED`.

### C14

INPUT_SUBMITTED requires verified submission.

### C15

GENERATION_STARTED requires generation evidence.

### C16

Continuation is explicitly targetable with `CONTINUE_PROMPT`.

### C17

Continuation count cannot exceed `max_continuations`.

### C18

Exactly one terminal prompt state may be committed.

### C19

Cancellation reports `cancel_verified`.

### C20

Cancellation follows all four arbitration cases.

### C21

AUTH_REQUIRED is authoritative.

### C22

# 149. Future Extensions

Reserved future extensions include:

```text id="5l1vxm"
ext-multi-prompt
ext-subchannels
ext-compression
ext-binary-media
```

These do not alter the 1.12 base protocol unless explicitly negotiated.

---

# 150. Multi-Prompt Extension

A future `ext-multi-prompt` MAY introduce:

* simultaneous prompts;
* per-prompt scheduling;
* prompt queues;
* independent concurrent generation.

The existing:

```text id="x7nb2i"
request_id
target_request_id
prompt_request_id
message_id
```

identity model is intended to remain compatible.

---

# 151. Binary Media Extension

A future binary-media extension MUST NOT alter the 48-byte base header.

It MUST define:

* payload encoding;
* media type;
* fragmentation;
* size limits;
* integrity;
* memory limits.

---

# 152. Compression Extension

A future compression extension MUST define:

* algorithm;
* compressed representation;
* decompression limits;
* expansion-ratio protection;
* negotiation;
* failure semantics.

Compression MUST NOT be inferred merely from `EXTENSION_PRESENT`.

---

# 153. Subchannel Extension

A future subchannel extension MAY add logical multiplexing.

It remains outside the base protocol.

---

# 154. Determinism

Where multiple implementation strategies exist, externally visible behavior MUST be deterministic.

This applies to:

* provider selector strategies;
* recovery strategies;
* capability ordering;
* diagnostics;
* message boundary detection.

---

# 155. Adapter Fragility

Provider DOM structures are expected to change.

A gateway that loses its provider assumptions MUST fail explicitly rather than falsely reporting success.

Provider DOM changes do not automatically require a GARP protocol revision.

---

GARP/1.12 supersedes GARP/1.11 as the implementation target.

GARP/1.07 remains historical material useful for future extension design.

GARP/1.12 is intended to provide the stable base:

```text id="2xk7no"
small base
+
explicit identity
+
mutual authentication
+
verified browser execution
+
multi-message streaming
+
explicit continuation
+
deterministic cancellation
+
strict page fencing
+
persistent sequencing
+
bounded history
+
optional replay
+
optional PONG
+
structured capabilities
+
test vectors
+
controlled extensibility
```

No base-protocol feature should be added merely to anticipate hypothetical future requirements. New functionality SHOULD first be considered as a negotiated extension unless it is required to preserve correctness, interoperability, security, or deterministic operation.
