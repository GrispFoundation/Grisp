# GARP/1.06

## Gateway AI Runtime Protocol

**Status:** Beta / Release-Candidate Implementation Specification
**Protocol Identifier:** `GARP/1.06`
**Wire Version:** `0x16`
**Previous Version:** GARP/1.05 (`0x15`)
**Transport:** TCP
**Payload Encoding:** UTF-8 JSON
**Default Endpoint:** `127.0.0.1:9999`

---

# Part I — Scope and Design Goals

## 1. Purpose

GARP (Gateway AI Runtime Protocol) defines a deterministic transport and browser-automation protocol between an external controller and an AI-capable browser gateway.

GARP provides:

* authenticated TCP communication;
* browser and tab management;
* provider capability discovery;
* logical provider sessions;
* browser navigation tracking;
* readiness detection;
* prompt injection;
* prompt verification;
* provider submission;
* submission verification;
* generation observation;
* streaming;
* continuation;
* cancellation;
* response retrieval;
* event subscription;
* diagnostics;
* deterministic request correlation;
* deterministic state transitions.

GARP does not define:

* semantic correctness of AI output;
* correctness of generated source code;
* compilation correctness;
* execution correctness;
* GRISP artifact acceptance;
* policy acceptance;
* model quality;
* semantic scoring.

---

# 2. Trust Boundary

The browser and remote AI provider are outside the trusted semantic core.

The following are untrusted observations:

* provider DOM;
* provider UI state;
* provider-generated text;
* provider-generated metadata;
* provider response identity;
* provider completion indications.

GARP verifies transport and automation facts.

GRISP or another downstream system MUST perform semantic validation.

---

# 3. Architectural Model

GARP/1.06 defines four message roles:

```text
COMMAND
RESPONSE
EVENT
PROTOCOL ERROR
```

## 3.1 COMMAND

A client-originated operation.

## 3.2 RESPONSE

The single synchronous result of an ordinary command.

## 3.3 EVENT

An asynchronous state or lifecycle notification.

## 3.4 PROTOCOL ERROR

A protocol-level failure that prevents normal command processing.

---

# 4. Universal Command/Response Rule

Every ordinary command MUST contain its own unique:

```text
request_id
```

Every ordinary command MUST receive exactly one synchronous:

```text
RESPONSE
```

Therefore:

```text
COMMAND(request_id=X)
       |
       v
RESPONSE(request_id=X)
```

is the universal command model.

No ordinary command may use a command-specific message type as its synchronous result.

---

# 5. Command Correlation and Target Correlation

GARP/1.06 permanently separates:

```text
request_id
```

from:

```text
target_request_id
```

## `request_id`

Identifies the command currently being executed.

## `target_request_id`

Identifies a previously created request that the current command operates on.

This distinction is mandatory.

For example:

```json
{
  "request_id": "A",
  "target_request_id": "B"
}
```

means:

> Command A is operating on request B.

The header `request_id` is always:

```text
A
```

The JSON `target_request_id` is:

```text
B
```

This applies to:

* `CANCEL_PROMPT`;
* `GET_PROMPT_STATUS`;
* `GET_RESPONSE`;
* `SUBSCRIBE_RESPONSE`.

A target request identifier MUST NEVER be placed in the current command's `request_id` field.

---

# 6. Command Pipelining

GARP/1.06 permits multiple outstanding commands on one authenticated connection.

Example:

```text
LIST_TABS       request_id=A
OPEN_TAB        request_id=B
CREATE_SESSION  request_id=C
```

may all be outstanding simultaneously.

Responses correlate through:

```text
request_id
```

The command name alone MUST NOT be used as correlation.

---

# 7. Session Serialization

Connection concurrency does not imply session execution concurrency.

Different sessions MAY execute concurrently.

Within one logical session:

> At most one active `PROMPT` request may execute at a time.

A second prompt MUST receive:

```text
SESSION_BUSY
```

inside its own:

```text
RESPONSE(success=false)
```

---

# Part II — Versioning

# 8. Protocol Version

The canonical protocol identifier is:

```text
GARP/1.06
```

The native wire version is:

```text
0x16
```

---

# 9. Version Negotiation

`HELLO` contains:

```json
{
  "protocol": "GARP/1.06",
  "supported_versions": [
    "GARP/1.06",
    "GARP/1.05"
  ]
}
```

The wire-version byte on the initial `HELLO` identifies the client's proposed framing version.

The gateway MUST select one mutually supported protocol version.

The selected version is returned in `HELLO_ACK`:

```json
{
  "protocol": "GARP/1.06",
  "selected_version": "GARP/1.06"
}
```

A gateway MAY accept a prior wire version for compatibility when its framing is known and safely decodable.

If a frame is structurally decodable but its wire version is unsupported, the gateway SHOULD return:

```text
UNSUPPORTED_VERSION
```

with the supported-version list in `details`.

If the frame cannot be decoded safely, the gateway MAY close the connection without a normal response.

---

# 10. Registry Isolation

Once the negotiated protocol version is established:

* its numeric registry is authoritative;
* its schemas are authoritative;
* its state model is authoritative;
* its error definitions are authoritative.

A registry from another version MUST NOT be mixed into the active session.

---

# Part III — Wire Format

# 11. Frame Structure

Every GARP/1.06 frame is:

```text
48-byte fixed header
+
UTF-8 JSON payload
```

---

# 12. Byte Order

All integer fields are encoded:

```text
big-endian / network byte order
```

Native compiler struct packing MUST NOT be used.

---

# 13. Header Layout

| Offset | Size | Field          | Encoding     |
| -----: | ---: | -------------- | ------------ |
|    `0` |    4 | Magic          | ASCII `GARP` |
|    `4` |    1 | Wire version   | `uint8`      |
|    `5` |    1 | Flags          | `uint8`      |
|    `6` |    2 | Header length  | BE `uint16`  |
|    `8` |    4 | Payload length | BE `uint32`  |
|   `12` |    2 | Message type   | BE `uint16`  |
|   `14` |    2 | Reserved       | BE `uint16`  |
|   `16` |   16 | Request ID     | UUID bytes   |
|   `32` |   16 | Session ID     | UUID bytes   |

Total:

```text
48 bytes
```

---

# 14. Magic

Bytes `0..3` MUST equal:

```text
47 41 52 50
```

which represents:

```text
GARP
```

---

# 15. Wire Version

Byte `4` is:

```text
0x16
```

for GARP/1.06.

---

# 16. Flags

All GARP/1.06 flags are currently reserved.

Therefore:

```text
flags == 0
```

is mandatory unless a separately negotiated extension explicitly defines a flag.

Unknown non-zero flags MUST cause:

```text
UNSUPPORTED_FLAGS
```

or `PROTOCOL_ERROR`.

---

# 17. Header Length

Header length MUST equal:

```text
48
```

Any other value is invalid in GARP/1.06.

---

# 18. Payload Length

Payload length is the number of bytes following the header.

It is measured in bytes, not Unicode characters.

---

# 19. Maximum Payload

Maximum payload:

```text
16,777,216 bytes
```

Maximum complete frame:

```text
16,777,264 bytes
```

A larger frame MUST be rejected with:

```text
FRAME_TOO_LARGE
```

---

# 20. UUID Encoding

All UUIDs in the header are exactly 16 bytes.

JSON representation uses canonical textual UUID form:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

The binary and textual representations MUST identify the same UUID.

---

# 21. Required Header Identity Rule

For a message whose identity matrix requires `request_id`:

```text
header.request_id != zero
```

and:

```text
json.request_id == header.request_id
```

must both be true.

For a message whose identity matrix forbids `request_id`:

```text
header.request_id == zero
```

must be true.

The same rule applies to `session_id`.

There is no longer a `MAY` condition for required identity fields.

---

# 22. Reserved Header Field

Bytes `14..15` MUST be zero in GARP/1.06.

Non-zero values MUST be rejected.

---

# Part V — Common Envelope

# 32. JSON Common Envelope

Messages containing common protocol metadata use:

```json
{
  "request_id": "uuid",
  "session_id": "uuid",
  "message_id": "uuid",
  "sequence": 1,
  "page_generation": 2,
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

Only fields required by the message schema are included.

The field definitions below are normative.

---

# 33. request_id

Identifies the current command/request.

A command's own `request_id` is never the ID of another request.

---

# 34. target_request_id

Identifies a previously created request operated on by the current command.

Used by:

```text
CANCEL_PROMPT
GET_PROMPT_STATUS
GET_RESPONSE
SUBSCRIBE_RESPONSE
```

---

# 35. session_id

Identifies a logical provider/browser session.

It remains stable across:

* actor replacement;
* page replacement;
* connection reconnection where persistence is supported.

---

# 36. message_id

Identifies the logical provider response.

---

# 37. sequence

Identifies ordering of GARP events within an event stream.

Sequence is independent of text revision.

---

# 38. page_generation

Identifies the logical browser document/actor generation.

It acts as a fencing token.

---

# 39. timestamp

Every message MUST use:

```text
RFC 3339 UTC
```

Example:

```text
2026-09-15T21:00:00.000Z
```

Milliseconds SHOULD be present.

Timestamps are informational and MUST NOT be used as ordering keys.

---

# 40. Canonical Event Envelope

All request-associated asynchronous events MUST contain:

```json
{
  "request_id": "uuid",
  "session_id": "uuid",
  "message_id": "uuid",
  "sequence": 1,
  "page_generation": 2,
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

followed by event-specific fields.

Session events without a request use:

```text
request_id = omitted
message_id = omitted
```

but still carry:

```text
session_id
sequence
page_generation
timestamp
```

---

# 41. Sequence Namespace

Sequence numbering has an explicit scope.

## Request Event Stream

Events associated with a request use:

```text
sequence_scope = request
```

The first event is:

```text
sequence = 1
```

## Session Event Stream

Session-level events without a request use:

```text
sequence_scope = session
```

A separate monotonically increasing session sequence is maintained.

Therefore sequence numbers from different streams MUST NOT be compared.

---

# 42. Sequence and Revision

The protocol distinguishes:

```text
sequence
```

from:

```text
revision
```

`sequence` orders GARP messages.

`revision` versions provider text.

They are independent.

---

# Part VII — Handshake and Authentication

# 44. Authentication Model

GARP/1.06 uses mutual HMAC-SHA256 authentication.

Authentication proves peer possession of a shared secret.

It does not encrypt application payloads.

---

# 45. Security Boundary

The default GARP deployment is:

```text
127.0.0.1:9999
```

For local-only operation:

* the gateway SHOULD bind only to loopback;
* remote clients MUST NOT be accepted by default.

If the gateway accepts non-loopback traffic, one of the following MUST be used:

```text
TLS
```

or an explicitly specified authenticated/encrypted transport extension.

HMAC alone does not provide confidentiality.

---

# 46. Shared Secret Provisioning

The shared secret is provisioned out-of-band.

It MUST NOT be transmitted through GARP.

The shared secret SHOULD contain at least:

```text
32 bytes of cryptographically random material
```

Implementations SHOULD support secret rotation.

Secret storage SHOULD use an operating-system protected credential store or equivalent secure storage.

---

# 47. Nonces

Both sides generate:

```text
32 random bytes
```

represented in JSON as:

```text
64 lowercase hexadecimal characters
```

Nonces MUST be fresh for every handshake.

Nonce reuse MUST be rejected.

**Type:** `0x0001`

```json
{
  "protocol": "GARP/1.06",
  "supported_versions": [
    "GARP/1.06",

  "client_id": "uuid",
  "client_nonce": "64-hex-chars",
  "features": [],
  "metadata": {},

```

Required:

```text
protocol
supported_versions
client_id
client_nonce
timestamp
```

# 49. HELLO_CHALLENGE

**Type:** `0x0002`

```json
{
  "protocol": "GARP/1.06",
  "server_id": "uuid",
  "server_nonce": "64-hex-chars",
  "algorithm": "HMAC-SHA256",
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

---

# 50. Authentication Transcript

The transcript consists of length-prefixed UTF-8/binary fields:

```text
u32be(domain_length)
domain

u32be(protocol_length)
protocol

u32be(client_id_length)
client_id

u32be(client_nonce_length)
client_nonce

u32be(server_id_length)
server_id

u32be(server_nonce_length)
server_nonce
```

No ambiguous variable-length concatenation is permitted.

---

# 51. Client Authentication Domain

```text
GARP/1.06/CLIENT-AUTH
```

The client proof is:

```text
HMAC-SHA256(
    shared_secret,
    client-auth-transcript
)
```

---

```json
{
  "protocol": "GARP/1.06",
```

```text
GARP/1.06/SERVER-AUTH
```

The server proof MUST use an independently domain-separated transcript.

**Type:** `0x0004`

```json
{
  "protocol": "GARP/1.06",
```

---

# 55. Constant-Time Comparison

Authentication proofs MUST be compared using constant-time comparison.

---

# 56. Authentication Timeout

Default:

```text
10 seconds
```

A handshake exceeding this interval MUST be terminated.

---

# 57. Authentication Failure

Authentication failure MUST terminate the handshake.

The preferred code is:

```text
AUTH_FAILED
```

A fresh handshake with fresh nonces is required for retry.

---

# 58. Authentication Attempt Limiting

Implementations SHOULD impose a failed-attempt limit per source.

A recommended default is:

```text
5 failed attempts per 60 seconds
```

A temporary backoff SHOULD apply after repeated failures.

---

# Part VIII — Universal RESPONSE

# 59. RESPONSE

**Type:** `0x0005`

Every ordinary command receives exactly one response.

Success:

```json
{
  "request_id": "uuid",
  "command": "list_tabs",
  "success": true,
  "result": {},
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

Failure:

```json
{
  "request_id": "uuid",
  "command": "list_tabs",
  "success": false,
  "error": {
    "code": "TAB_NOT_FOUND",
    "message": "Tab not found",
    "retryable": false,
    "state": "ERROR"
  },
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

---

# 60. RESPONSE Session ID

If the command is session-associated:

```text
session_id
```

MUST be included in the response.

---

# 61. RESPONSE Command Field

`command` MUST exactly identify the originating command.

The value is lower-case semantic form:

```text
list_tabs
create_session
prompt
cancel_prompt
get_response
```

---

# 62. Response Uniqueness

Exactly one synchronous response MUST exist per command.

---

# Part IX — Protocol ERROR

# 63. ERROR

**Type:** `0x0006`

```json
{
  "code": "PROTOCOL_ERROR",
  "message": "Invalid frame",
  "retryable": false,
  "state": "ERROR",
  "details": {},
  "timestamp": "2026-09-15T21:00:00.000Z"
}
```

---

# 64. RESPONSE Failure vs ERROR

Use:

```text
RESPONSE(success=false)
```

for an application-level command failure.

Use:

```text
ERROR
```

when the protocol cannot safely process the message.

Examples:

```text
SESSION_NOT_FOUND -> RESPONSE failure
SESSION_BUSY      -> RESPONSE failure
```

# 114. Session Transition Table

| Current        | Event                   | Next                   |
| -------------- | ----------------------- | ---------------------- |
| NEW            | create                  | PREPARING              |
| NEW            | attach                  | PREPARING              |
| PREPARING      | not ready               | PREPARING              |
| PREPARING      | ready                   | READY                  |
| PREPARING      | auth required           | AUTH_REQUIRED          |
| PREPARING      | rate limited            | RATE_LIMITED           |
| READY          | prompt accepted         | BUSY                   |
| READY          | auth required           | AUTH_REQUIRED          |
| READY          | rate limited            | RATE_LIMITED           |
| BUSY           | generation completed    | READY                  |
| BUSY           | generation cancelled    | READY                  |
| BUSY           | recoverable failure     | READY                  |
| BUSY           | unrecoverable failure   | ERROR                  |
| AUTH_REQUIRED  | authentication restored | PREPARING              |
| RATE_LIMITED   | rate limit cleared      | PREPARING              |
| ERROR          | recovery initiated      | PREPARING              |
| any non-CLOSED | close                   | CLOSED                 |
| CLOSED         | —                       | no outgoing transition |

---

# 115. Navigation Transition

A relevant navigation MUST cause:

```text
READY -> PREPARING
```

or:

```text
BUSY -> PREPARING
```

unless the implementation cannot safely preserve the active generation, in which case the active request MUST terminate according to the failure/recovery policy.

---

# 116. Input Transition Table

```text
UNKNOWN
    -> NOT_READY
    -> READY

NOT_READY
    -> READY
    -> NOT_READY

READY
    -> INJECTING
    -> NOT_READY

INJECTING
    -> INJECTION_VERIFIED
    -> READY
    -> NOT_READY

INJECTION_VERIFIED
    -> SUBMITTING
    -> READY

SUBMITTING
    -> SUBMISSION_VERIFIED
    -> READY
    -> NOT_READY
```

---

# 117. Generation Transition Table

```text
IDLE
    -> STARTING

STARTING
    -> STREAMING
    -> FAILED
    -> CANCELLED

STREAMING
    -> STREAMING
    -> CONTINUATION_REQUIRED
    -> COMPLETING
    -> FAILED
    -> CANCELLED

CONTINUATION_REQUIRED
    -> STREAMING
    -> FAILED
    -> CANCELLED

COMPLETING
    -> COMPLETE
    -> FAILED

COMPLETE
    -> IDLE

FAILED
    -> IDLE

CANCELLED
    -> IDLE
```

# 118. Illegal Transition Rule

The implementation MUST reject or fail closed on impossible transitions.

Examples:

```text
IDLE -> COMPLETE
READY -> GENERATION_COMPLETED
PREPARING -> INPUT_SUBMITTED
INJECTING -> GENERATION_STARTED
```

are invalid.

# Part XIX — Page Generation and Actor Fencing

# 122. Page Generation

`page_generation` is monotonically increasing.

It MUST increase on:

* relevant navigation;
* document replacement;
* actor replacement;
* provider conversation replacement;
* reset;
* attachment to a new document.

---

# 123. Actor Replacement

Actors are ephemeral.

Logical sessions survive actor replacement.

The current actor MUST be reacquired for browser-side operations.

---

# 124. Stale Actor Rule

A stale actor result MUST NOT overwrite newer authoritative state.

The gateway MUST fence results using:

```text page_generation
```

# 125. Commit Rule

# Part XXIV — Cancellation

# 142. Cancellation

Cancellation has separate states:

```text
CANCEL_REQUESTED
CANCELLED
```

---

# 143. Cancellation Arbitration

### Case A

Provider completion observed before cancellation acceptance:

```text
COMPLETE
```

wins.

### Case B

Cancellation accepted and provider termination verified before completion:

```text
CANCELLED
```

wins.

### Case C

Cancellation accepted but provider completion is observed before provider stop is verified:

```text
COMPLETE
```

wins.

Exactly one terminal state is authoritative.

---

# 144. GENERATION_CANCELLED

When cancellation wins, the gateway MUST emit:

```text
GENERATION_CANCELLED
```

and MUST NOT emit:

```text
GENERATION_COMPLETED
```

as the authoritative terminal event.

Response eviction is represented as a failed `RESPONSE` to `GET_RESPONSE`.


There is no separate `RESPONSE_EVICTED` message type.

# Part XXVI — Connection Loss and Recovery

# 148. Connection Loss

Connection loss does not inherently destroy:

* session state;
* active request state;
* retained responses.

Provided the implementation supports persistence.

---

# 149. Active Request Continuation

The default implementation policy is:

```text
connection lost
      ->
request continues where possible
      ->
retained result remains queryable
```

---

# 150. Reconnection

A reconnecting client MUST authenticate again.

It MUST then use:

```text
GET_PROMPT_STATUS
GET_RESPONSE
SUBSCRIBE_RESPONSE
```

using the current command's `request_id` and the target request's `target_request_id`.

---

# 151. Subscription Recovery

Subscriptions themselves do not survive connection loss.

A client must create a new subscription after reconnect.


# 154. Backpressure

When the event queue reaches capacity, the gateway MUST:

* apply transport/application backpressure;
* or explicitly fail the affected stream/request;
* or terminate the affected connection.

Silent event loss is forbidden.

# Part XXXIII — Versioned JSON Schema Model

# 174. Schema Authority

For GARP/1.06 the normative authority order is:

```text
1. Binary framing rules
2. Message identity rules
3. Common envelope rules
4. Per-message schema
5. Normative prose
6. Examples
```

Examples never override the schema.

# 175. Canonical Schema Composition

A message schema consists conceptually of:

```text
CommonEnvelope
+
MessageSpecificFields
```

For example:

```text
GENERATION_DELTA
=

+
{
    revision,
    mode,
    text_delta | text
}
```

This prevents identity fields from being accidentally omitted from individual examples.

```text
integer
number
string
boolean
object
array
null
```

No implicit type conversion is permitted.

# Part XXXVI — Security Considerations

# 183. Confidentiality

HMAC authentication does not encrypt payloads.

A remote deployment MUST use TLS or another authenticated encrypted transport.

---

# 184. Integrity

Within the local default configuration, the trust assumption is loopback.

Remote transport MUST provide integrity protection beyond handshake authentication.

---

# 185. Replay

Replay is mitigated through fresh client and server nonces.

A reused nonce MUST be rejected.

---

# 186. Key Rotation

Implementations SHOULD permit shared-secret rotation without changing protocol semantics.

The new key MUST take effect through an out-of-band provisioning procedure.

---

# 187. Brute Force Protection

Implementations SHOULD rate-limit failed authentication attempts.

---

# 188. Secret Logging

Authentication material MUST never appear in diagnostics.

---

# Part XXXVII — Recovery

# 189. Tab Closure

Unexpected tab closure MUST invalidate the affected browser binding.

Active requests MUST terminate or recover according to the session recovery policy.

---

# 190. Browser Restart

Browser restart invalidates actor references.

Sessions MUST transition into a non-ready state before recovery.

---

# 191. Actor Restart

Actor replacement MUST advance `page_generation`.

---

# 192. Provider Authentication Loss

If the provider becomes unauthenticated:

```text
READY/BUSY
    ->
AUTH_REQUIRED
```

The active request MUST either fail or pause according to provider-specific capabilities.

An implementation MUST document which behavior it provides.

---

# 193. Rate Limiting During Generation

If a provider becomes rate limited during generation:

```text
BUSY
    ->
RATE_LIMITED
```

may occur.

The active request MUST not falsely complete.

---

A request MUST NOT become both:


and:


Completed:




# Part XXXIX — Conformance Invariants

# 197. Wire Invariants

### I1

Protocol is `GARP/1.06`.

### I2

Wire version is `0x16`.

### I3

Header length is 48 bytes.

### I4

Magic is `GARP`.

### I5

All integers are big-endian.

### I6

Maximum payload is 16 MiB.

### I7

Reserved header bytes are zero.

### I8

Binary and JSON identities agree.

# 198. Correlation Invariants

### I9

Every ordinary command has a unique `request_id`.

### I10

Every ordinary command receives exactly one `RESPONSE`.

### I11

The response `request_id` equals the command `request_id`.

### I12

Targeted commands use `target_request_id`.

### I13

`target_request_id` is never used as the current command's `request_id`.

### I14

Concurrent commands are correlated by request ID, not command name.

### I15

A request ID cannot be reused while the request remains retained.

### I16

`0x0001 = HELLO`.

### I17

`0x0002 = HELLO_CHALLENGE`.

### I18

`0x0003 = HELLO_AUTH`.

`0x0004 = HELLO_ACK`.

### I20

`0x0005 = RESPONSE`.

### I21

`0x0006 = ERROR`.

### I22

`0x0058 = GENERATION_CANCELLED`.

### I23

Numeric and semantic mappings are bidirectional.

# 200. Authentication Invariants

### I24

Client and server nonces contain 32 random bytes.

### I25

Nonces are fresh for each handshake.

### I26

Authentication transcripts are unambiguous.

### I27

Client and server proofs use domain separation.

### I30

HMAC alone is not treated as payload confidentiality.

# 203. Input/Submission Invariants

### I43

### I45

### I63

### I64

```text
PROMPT(request=A)
  ->
RESPONSE(request=A, success=true)
  ->
GENERATION_FAILED(request=A)
```

# 228. Submission Failure

```text
PROMPT
  ->
RESPONSE(success=true)
  ->
DIAGNOSTIC(submit_discovery)
  ->
GENERATION_FAILED(code=SUBMISSION_METHOD_NOT_FOUND)
```

No:

```text
INPUT_SUBMITTED
```

and no:

```text
GENERATION_STARTED
```

may be emitted.

# Part XLIII — Extension Mechanism

# 230. Reserved Extensions

Future protocol extensions MUST define:

* extension identifier;
* message/field ownership;
* negotiation mechanism;
* compatibility rules;
* security impact.

---

# 231. Flags

No flag may become active merely because a peer sends a non-zero value.

An extension MUST be explicitly negotiated before its flags are used.

Until then:

```text
flags == 0
```

is mandatory.

---

# 232. Enumerations

Closed enumerations defined by GARP/1.06 MUST NOT gain silent provider-specific values.

Provider-specific values require:

* mapping to the standard vocabulary;
* or an explicitly negotiated extension.

# Part XLIV — Final Architectural Rules

# 233. One Command Identity

Every ordinary command has exactly one:

```text
request_id
```

---

# 234. Targeting Is Separate

Commands operating on an existing request use:

```text
target_request_id
```

---

# 235. One Synchronous Response

Every ordinary command has exactly one:

```text
RESPONSE
```

---

# 236. Events Are Asynchronous

Typed lifecycle messages are events.

They are never synchronous command replies.

---

# 237. Readiness Is State

Time does not establish readiness.

---

# 238. Injection Is Not Submission

A DOM mutation is not provider submission.

---

# 239. Submission Is Not Generation

Verified provider submission is not proof that generation has begun.

---

# 240. Generation Is Not Semantic Correctness

GARP observes and transports provider output.

GRISP verifies meaning.

---

# 241. Page Generation Is a Fence

Older browser generations cannot overwrite newer authoritative state.

---

# 242. Sequence Is Ordering

`sequence` orders GARP events.

---

# 243. Revision Is Text Versioning

`revision` versions provider text observations.

---

# 244. Cancellation Is a Terminal Event

A verified cancellation produces:

```text
GENERATION_CANCELLED
```

---

# 245. No Silent Event Loss

Events MUST NOT disappear without an explicit failure or backpressure mechanism.

---

# 246. No Secret Leakage

Authentication credentials and secrets MUST never appear in diagnostics.

---

# 247. No Silent Prompt Mutation

The transport preserves prompt content exactly.

---

# 248. Fail Closed

Protocol ambiguity MUST NOT be resolved by guessing.

# Part XLVI — GARP/1.06 Status

GARP/1.06 is the consolidated successor to GARP/1.05.

It preserves the architectural improvements of GARP/1.04 and the normative completeness developed from GARP/1.02 while correcting the internal contradictions identified during review.

The principal 1.06 corrections are:

```text
1. request_id is mandatory for every ordinary command
2. target_request_id is separate from request_id
3. command correlation and target correlation are never conflated
4. all schemas use an explicit common envelope
5. identity requirements and examples are consistent
6. timestamp semantics are normative
7. session and request sequence namespaces are distinct
8. GENERATION_CANCELLED is an explicit terminal event
9. GET_RESPONSE returns revision
10. event retention is advertised
11. response eviction is a failed GET_RESPONSE
12. completion and finish-reason vocabularies are defined
13. CAPABILITIES MUST advertise operational limits
14. remote TCP security boundaries are explicit
15. shared-secret provisioning and rotation are defined
16. authentication failure limiting is defined
17. version handling is explicit
18. `CLOSE_TAB` and `SELECT_TAB` no longer duplicate RESPONSE.success
19. generation progress/delta ordering is explicitly interleavable
20. machine-readable JSON Schema publication is part of the conformance target
```

The canonical architecture is therefore:

```text
                      GARP/1.06
                          |
          +---------------+---------------+
          |               |               |
       COMMAND         RESPONSE         EVENT
          |               |               |
          |               |               |
          +---------------+---------------+
                          |
                  deterministic
                   correlation
                          |
                          v
                 Firefox Gateway
                          |
                          v
                  Provider Adapter
                          |
                          v
                    Browser / AI
                          |
                          v
                 Untrusted Output
                          |
                          v
                   GRISP Verification
```

**GARP/1.06 is the canonical specification for implementation going forward.**
