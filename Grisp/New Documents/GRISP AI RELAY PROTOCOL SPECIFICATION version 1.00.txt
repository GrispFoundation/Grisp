GRISP AI RELAY PROTOCOL SPECIFICATION

GARP/1.0

Status: NORMATIVE
Version: GARP/1.0
Parent specifications: GRISP Agent Specification v1.0; GRISP v1.0 Implementation Contract, Revision 2
Transport: TCP localhost, UTF-8, length-framed binary envelope
Payload serialization: UTF-8 JSON
Semantic AI exchange: GAI/1.0, separate contract
Default mode: fail-closed

1. PURPOSE

GARP is the GRISP <-> Firefox AI Gateway transport and browser-session protocol.

GARP exists to make Firefox a reliable, stateful AI-provider transport/adapter endpoint, rather than a loose JSON command socket or a collection of ad-hoc DOM scripts.

GARP defines:
- connection handshake and feature negotiation;
- request, session, tab, message, and sequence identity;
- browser AI session lifecycle;
- prompt submission and cancellation;
- streaming response events;
- provider adapter boundaries;
- structured errors;
- heartbeat and reconnection behavior;
- security constraints for the local browser gateway.

GARP does NOT define:
- artifact acceptance;
- compile semantics;
- runtime verification semantics;
- GRISP policy semantics;
- AI quality scoring;
- final acceptance decisions;
- artifact identity or hashing;
- GAI structured artifact semantics.

Those belong to GRISP core, GAI/1.0, or the GRISP implementation contract.

The architectural boundary is:

Firefox = observe and transport
GRISP   = interpret and verify
AI      = reason
tools   = measure
policy  = authorize

2. DESIGN GOALS

GARP/1.0 SHALL provide:
1. stable request identity;
2. stable session identity;
3. stable tab identity;
4. provider-independent request correlation;
5. event-driven streaming;
6. explicit cancellation;
7. duplicate request suppression;
8. connection resilience;
9. page-generation tracking;
10. structured provider errors;
11. isolated provider adapters;
12. no semantic mutation by transport;
13. fail-closed behavior when state is unknown.

The protocol SHALL NOT rely on newline-delimited JSON. Newline framing is vulnerable to embedded framing, oversized messages, lack of message identity, lack of cancellation, ambiguous async ordering, no streaming event model, and no version negotiation.

3. TERMINOLOGY

Client
  The GRISP Agent.

Gateway
  The Firefox AI Gateway implementing GARP.

Provider
  An external AI service such as ChatGPT, Gemini, Claude, DeepSeek, Grok, Copilot, Perplexity, or Inception.

Adapter
  A provider-specific Firefox module that knows how to discover, submit, observe, continue, cancel, and diagnose interaction with one provider.

Session
  A logical AI conversation controlled through the gateway. A session is identified by session_id and is bound to a provider, tab, and conversation identity where available.

Tab
  A browser tab with stable identity tab_id. tab_index is informational only.

Request
  One AI operation associated with a unique request_id.

Message
  One AI response identity within a session, identified by message_id.

Event
  An asynchronous GARP message describing browser/provider/session state or generation progress.

Page generation
  A monotonically incremented value that changes on significant navigation or SPA actor replacement.

Sequence
  A monotonically increasing integer for a stream identified by (request_id, message_id).

GARP SHALL distinguish:

provider
model
session
browser_tab
conversation
worker_instance

Two providers are not assumed independent merely because their names differ.

4.1 Parent/Child Split

The gateway SHALL preserve a parent/child actor separation.

Parent actor owns:
connection
sessions
requests
timeouts
cancellation
routing
event ordering
stream aggregation
browser-level state

Child actor owns:
DOM discovery
input interaction
submission
provider-specific observation
provider-specific state extraction

The parent/child boundary SHALL be structured and request-correlated.

Conceptual internal parent/child protocol:

Parent:
    PrepareSession
    InspectReady
    InjectPrompt
    SubmitPrompt
    ObserveGeneration
    ContinueGeneration
    CancelGeneration

Child:
    ReadyState
    InputState
    SubmissionState
    GenerationEvent
    ProviderError

This preserves the useful existing design where response polling is kept in the parent to survive SPA navigation, but formalizes it into explicit sessions, events, and identities.

5. TRANSPORT

5.1 Base Transport

GARP/1.0 SHALL use:
TCP localhost
UTF-8
length-framed binary envelope

JSON MAY be used as the payload serialization, but message framing SHALL NOT depend on newline termination.

5.2 Canonical Frame

Recommended canonical v1 frame:

magic[4]
version[1]
flags[1]
header_length[2]
payload_length[4]
message_type[2]
reserved[2]
request_id[16]
session_id[16]
payload[...]

All integers SHALL use big-endian encoding.

magic SHALL be:
"GARP"

The payload SHALL be UTF-8 JSON.

header_length allows future extension. reserved fields SHALL be zero unless defined by a later version or flag.

5.3 Frame Constraints

The gateway SHALL enforce:
maximum frame size
header validity
payload length validity
protocol version
message type
reserved-field rules

Recommended initial limits:
control frame = 1 MiB
prompt        = 4 MiB
artifact      = 16 MiB
stream chunk  = 256 KiB

These values SHALL be configurable.

5.4 Required Transport Properties

Required:
UTF-8
binary length framing
request IDs
session IDs
sequence IDs
version negotiation
structured errors
timeouts
cancellation
heartbeat

Recommended:
compression for large streams
message acknowledgements
connection authentication
diagnostic subscriptions

5.5 No Semantic Mutation

The transport layer SHALL never:
alter prompts
insert debug comments
rewrite code
remove Markdown
fix filenames

Transport transports data. Normalization belongs to GRISP.

8. IDENTITY MODEL

8.1 Core Identifiers

Every request SHALL have:
request_id

tab_id

message_id

Every stream event SHALL have:
sequence

8.2 Message Identity Matrix

Fields are required according to message type:

Message              | request_id      | session_id      | tab_id          | message_id | sequence
HELLO                | no              | no              | no              | no         | no
HELLO_ACK            | no              | no              | no              | no         | no
PING                 | no              | no              | no              | no         | no
PONG                 | no              | no              | no              | no         | no
CREATE_SESSION       | yes             | returned        | optional        | no         | no
PROMPT               | yes             | yes             | yes             | no         | no
PROMPT_ACK           | yes             | yes             | yes             | no         | no
GENERATION_STARTED   | yes             | yes             | yes             | yes        | yes
GENERATION_DELTA     | yes             | yes             | yes             | yes        | yes
GENERATION_COMPLETED | yes             | yes             | yes             | yes        | final
CANCEL_PROMPT        | yes             | yes             | yes             | no         | no
CANCEL_ACK           | yes             | yes             | yes             | optional   | no
ERROR                | when applicable | when applicable | when applicable | optional   | optional

This avoids incorrectly making every identifier mandatory on every protocol message.

8.3 Tab Identity

The current implementation identifies tabs primarily by numeric index. That is unsuitable as persistent identity because tab indexes can change.

New rule:
tab_id = GUID
tab_index = informational metadata only

A changing index SHALL NOT change identity.

8.4 Page Generation

Every significant navigation or SPA actor replacement SHALL increment:
page_generation

Example:
tab_id = A
page_generation = 17

A response event from page generation 16 SHALL NOT silently overwrite generation 17 state.

This directly addresses actor reacquisition after navigation.

9.1 Session Commands

Required:

9.2 Session Concurrency

A Firefox AI session SHALL have a single active prompt by default.

Attempting:
PROMPT request A
PROMPT request B
against the same session while A is generating SHALL yield:
SESSION_BUSY

unless concurrent conversations are explicitly supported.

This eliminates accidental double-submit problems.

9.3 Session Recovery

If Firefox reloads or SPA navigation recreates an actor:
session_id remains stable
tab_id remains stable
page_generation increments

Firefox rebinds the child actor automatically. GRISP need not know about the actor lifecycle.

14.2 Event Ordering

Each event SHALL contain:
request_id
sequence
timestamp

For one (request_id, message_id) stream, sequence must monotonically increase.

The receiver shall detect:
duplicate
out-of-order
gap
unexpected reset

A gap SHALL NOT be silently treated as complete response data.

If events arrive out of order, the receiver can reorder deterministically using sequence numbers.

15. RESPONSE IDENTITY

Firefox SHALL associate a prompt with a response using:
request_id
message_id
submission_generation

Never infer the new response merely by asking:
what is the newest markdown node?

The new protocol must establish:
before submission:
  last assistant message = X

after submission:
  new assistant message = Y

therefore:
  Y belongs to this request

Before submitting, Firefox SHALL send:
SESSION_SNAPSHOT
containing:
provider
tab_id
url
page_generation
input_ready
conversation_identity
last_message_id
ui_state

This gives GRISP a deterministic starting point.

16. CONTINUATION HANDLING

The existing implementation automatically looks for "Continue" buttons and clicks them.

The redesign SHALL preserve this capability but make it stateful.

Firefox SHALL emit:

{
  "type": "continuation_required",
  "request_id": "...",
  "session_id": "...",
  "message_id": "...",
  "payload": {
    "reason": "provider_length_limit"
  }
}

GRISP can then decide:
continue automatically
or
do not continue

The browser SHALL not silently add content without recording the event.

17. CANCELLATION

GRISP:

{
  "type": "cancel_prompt",
  "request_id": "...",
  "reason": "task_timeout"
}

Firefox:

{
  "type": "prompt_cancelled",
  "request_id": "...",
  "state": "cancelled"
}

Cancellation SHALL propagate to:
task
worker request
GARP request
Firefox session
provider interaction

Provider-specific cancellation mechanisms SHALL be used where possible.

Otherwise the adapter SHALL terminate observation and mark the request cancelled.

Terminal state:
CANCELLED
means cancellation has been acknowledged. It does not mean:
SUCCESS

18. IDEMPOTENCY AND DUPLICATE SUPPRESSION

Requests SHALL support an idempotency key.

For example:
request_id = UUID

A duplicate PROMPT with the same request ID SHALL NOT submit the same prompt twice.

Possible result:
existing request state
or:
IDEMPOTENT_REPLAY
but never another prompt submission.

This is particularly important for Firefox automation, where retries may otherwise cause duplicate messages.

19. BACKPRESSURE

Streaming responses can be large.

GARP SHALL support:
sequence numbers
chunk sizes
maximum in-flight bytes
acknowledgements where necessary

The server SHALL not require GRISP to poll rapidly to avoid losing response information.

20. CONNECTION RESILIENCE AND HEARTBEAT

A broken TCP connection SHALL NOT automatically mean that the AI task is lost.

Firefox SHALL maintain session state independently.

On reconnect:
CONNECT
 v
HELLO
 v
CAPABILITIES
 v
GET_PROMPT_STATUS

GRISP may reconnect and issue GET_PROMPT_STATUS using:
request_id
session_id

Firefox responds:
SUBMITTING
STREAMING
COMPLETE
FAILED
UNKNOWN

Both sides SHALL support:
PING
PONG

Suggested interval:
10-30 seconds

A connection that disappears should be detected independently of an active prompt.

A heartbeat failure does not automatically destroy persistent session identity.

Provider adapters SHALL detect rate limits where possible.

23.2 Authentication

Firefox SHALL explicitly detect:
AUTH_REQUIRED

GRISP shall treat that as a deterministic state.

Adapters should detect provider-specific authenticated and unauthenticated UI states, not merely login-like URLs.

24. DOM ADAPTER RULES

Provider adapters SHALL avoid broad selectors wherever possible.

Preferred selector order:
preferred stable selector
 v
semantic attribute
 v
provider-specific structural selector
 v
strict diagnostic fallback

A fallback SHALL identify why it believes an element is the correct element.

The current code contains wide fallback selectors and broad message selection. New rules SHALL reduce accidental UI matches.

24.1 Deep DOM Search

The existing child actor recursively walks shadow roots and DOM nodes. The redesign SHOULD cache discovered roots where possible.

Do not recursively traverse the entire DOM on every poll.

Instead:
page mutation
 v
invalidate provider cache
 v
rediscover only when necessary

This reduces CPU cost and accidental UI matches.

24.2 Injection Strategy

Provider adapters SHALL provide explicit input methods:
set_value
dispatch_input
submit_button
keyboard_fallback

The adapter SHALL report exactly which mechanism succeeded.

Example:
{
  "input_method": "contenteditable",
  "submit_method": "button_click"
}

Keyboard simulation SHALL remain a last resort.

The current implementation already deliberately avoids unsafe keyboard events because they caused Firefox IPC instability. That principle should remain.

25. BROWSER DIAGNOSTICS

GARP SHALL expose diagnostics without requiring GRISP to scrape raw logs.

Example:

{
  "type": "diagnostic",
  "request_id": "...",
  "provider": "copilot",
  "stage": "submit",
  "state": "button_not_ready",
  "details": {
    "input_found": true,
    "button_found": true,
    "button_enabled": false
  }
}

This is more useful than generic:
Send button unavailable

25.1 Automatic Adapter Health Test

At startup, Firefox SHALL test each configured provider adapter.

Example checks:
input discovery
button discovery
response discovery
continuation discovery
authentication detection

The system should report:
DeepSeek adapter: PASS
Gemini adapter: PASS
ChatGPT adapter: PASS
...

This is preferable to finding adapter breakage in the middle of an AI task.

26. POLLING VS EVENT OBSERVATION

The present design repeatedly polls every 500 ms and considers text "done" after stable observations.

Polling can remain as a fallback, but the preferred order should be:

provider DOM mutation/events
 v
adapter state transition
 v
parent event
 v
GARP event

Fallback:
polling

This substantially reduces latency and stale-state problems.

26.1 Stable Response Detection

If polling must be used, the state machine should track:
response_message_id
text_revision
dom_revision
streaming_state
provider_busy_state

not merely:
same text 2/6 times

Stability is a heuristic. Message identity plus provider state should be authoritative.

29.1 Debug Mode

Debug mode SHALL never modify prompts.

The current system uses injected HTML comments such as:
<!-- DEBUG: ... -->
inside prompts. This is undesirable because the debugging mechanism modifies the actual input seen by the external AI.

New rule:
Debug metadata SHALL travel in the transport envelope, never inside the semantic prompt.

Example:

{
  "type": "prompt",
  "request_id": "...",
  "debug": {
    "phase": "candidate_generation"
  },
  "prompt": {
    "text": "actual user task"
  }
}

This makes debugging non-invasive.

30. RELATIONSHIP TO GAI/1.0 AND GRISP CORE

GARP is exclusively the transport and browser-session protocol.

GAI/1.0 is the semantic contract between GRISP and an AI worker. It defines structured AI requests and responses, including artifact outputs.

GRISP core defines task, artifact, evidence, policy, state machine, acceptance, and commit semantics.

GARP does not define:
artifact acceptance
compile semantics
policy semantics
AI quality scoring

The AI response carried over GARP is untrusted. GRISP performs:
decode
 v
schema validation
 v
artifact extraction
 v
artifact validation
 v
hash verification

GARP does not grant authority to an AI model.

34. GARP-SPECIFIC INVARIANTS

These are derived from the GRISP invariants and specialized for GARP:

I7  EVERY AI REQUEST MUST HAVE A UNIQUE REQUEST ID.
I8  EVERY AI SESSION MUST HAVE A STABLE SESSION ID.
I9  TAB INDEX IS NOT TAB IDENTITY.
I10 TRANSPORT MUST NOT MODIFY SEMANTIC CONTENT.

Additional GARP invariants:
A duplicate PROMPT with the same request_id SHALL NOT submit twice.
A readiness timeout SHALL NOT become READY.
A stale page_generation event SHALL NOT overwrite current session state.
A continuation SHALL NOT be performed silently without a recorded event.
A sequence gap SHALL NOT be treated as complete response data.
A broken TCP connection SHALL NOT automatically destroy persistent session identity.

35. SUMMARY

GARP/1.0 makes Firefox a reliable, stateful, provider-independent AI transport endpoint.

It provides:
- length-framed binary transport over localhost TCP;
- explicit handshake and feature negotiation;
- stable request, session, tab, message, and sequence identity;
- session and tab lifecycle;
- event-driven streaming responses;
- cancellation, continuation, heartbeat, and reconnection;
