# GARP/1.05

## Gateway AI Runtime Protocol

### Consolidated Normative Specification

**Status:** Beta / Implementation-Ready Draft
**Protocol Identifier:** `GARP/1.05`
**Wire Version:** `0x15`
**Previous Wire Version:** `0x14` (`GARP/1.04`)
**Transport:** TCP
**Payload:** UTF-8 JSON
**Default Endpoint:** `127.0.0.1:9999`

---

# Part I — Scope, Goals, and Architecture

## 1. Purpose

GARP (Gateway AI Runtime Protocol) defines an authenticated, stateful protocol between an external controller and a browser-resident AI automation gateway.

GARP provides a deterministic interface for:

* browser and tab management;
* provider discovery;
* logical AI sessions;
* browser navigation tracking;
* provider readiness;
* prompt injection;
* prompt submission;
* generation observation;
* streaming;
* continuation;
* cancellation;
* provider error reporting;
* diagnostics;
* request correlation;
* authenticated transport.

GARP does **not** define:

* AI semantic correctness;
* generated-code correctness;
* GRISP artifact acceptance;
* compilation correctness;
* runtime correctness;
* policy acceptance;
* model quality;
* semantic scoring.

The intended architecture is:

```text
External Controller
       |
       | GARP/1.05
       v
Firefox AI Gateway
       |
       v
Provider Adapter
       |
       v
Browser / Provider
       |
       v
Untrusted AI Output
       |
       v
GRISP / Verification Layer
```

---

# 2. Trust Boundary

The browser and AI provider are outside the trusted semantic core.

GARP MUST treat:

* browser DOM state;
* provider UI state;
* provider-generated text;
* provider-generated metadata;
* model-generated source code

as observations originating from an untrusted environment.

GARP transports and verifies transport-level facts.

It does not decide whether AI output is correct.

---

# 3. Architectural Model

GARP/1.05 has four message roles:

```text
COMMAND
RESPONSE
EVENT
PROTOCOL ERROR
```

## 3.1 Command

A client-originated operation request.

## 3.2 Response

The universal synchronous result of an ordinary command.

## 3.3 Event

An asynchronous notification.

Events communicate:

* state changes;
* navigation;
* input/submission progress;
* generation progress;
* generation completion/failure;
* provider conditions;
* diagnostics.

## 3.4 Protocol Error

A protocol-level failure that prevents normal command processing.

---

# 4. Universal Command Response Rule

Every ordinary command MUST have exactly one synchronous `RESPONSE`.

The canonical model is:

```text
COMMAND
   |
   v
RESPONSE
```

Command-specific synchronous response message types are forbidden.

Therefore:

```text
CAPABILITIES      -> RESPONSE
BROWSER_STATUS    -> RESPONSE
LIST_TABS         -> RESPONSE
OPEN_TAB          -> RESPONSE
CREATE_SESSION    -> RESPONSE
PROMPT            -> RESPONSE
CANCEL_PROMPT     -> RESPONSE
GET_RESPONSE      -> RESPONSE
PING              -> RESPONSE
```

Typed messages are used for asynchronous events only.

---

# 5. Handshake Exception

The initial authentication protocol has its own state machine:

```text
HELLO
  |
  v
HELLO_CHALLENGE
  |
  v
HELLO_AUTH
  |
  v
HELLO_ACK
```

Handshake messages are not normal command responses.

Ordinary command processing MUST NOT begin before authentication succeeds.

---

# 6. Design Principle

GARP MUST distinguish:

```text
request accepted
```

from:

```text
operation executed
```

and:

```text
operation observed as successful
```

For example:

```text
PROMPT
  |
  +--> RESPONSE(ACCEPTED)
  |
  +--> INPUT_SUBMITTED
  |
  +--> GENERATION_STARTED
  |
  +--> GENERATION_COMPLETED
```

The initial `RESPONSE` does not establish any provider-side success.

---

# Part II — Versioning and Compatibility

# 7. Protocol Identity

The canonical protocol identifier is:

```text
GARP/1.05
```

The wire version byte is:

```text
0x15
```

---

# 8. Version Isolation

The numeric registry, payload schemas, state semantics, and wire framing belonging to GARP/1.05 MUST be interpreted as one coherent version.

A receiver MUST NOT combine:

```text
GARP/1.04 numeric mappings
```

with:

```text
GARP/1.05 payload semantics
```

or vice versa.

---

# 9. Supported Versions

`HELLO` MAY contain:

```json
{
  "supported_versions": [
    "GARP/1.05",
    "GARP/1.04"
  ]
}
```

The currently active native GARP/1.05 wire encoding remains:

```text
0x15
```

Version downgrade MUST NOT occur implicitly.

If a peer intends to use another version, it MUST establish that version explicitly according to the compatibility mechanism supported by the implementation.

---

# 10. Version Mismatch

An implementation receiving an unsupported wire version MUST terminate protocol processing.

Where a valid response is still possible, the implementation SHOULD report:

```text
UNSUPPORTED_VERSION
```

otherwise the connection MAY be closed without a normal response.

---

# Part III — Canonical Wire Format

# 11. Frame Structure

Every GARP frame consists of:

```text
48-byte fixed header
+
UTF-8 JSON payload
```

The frame length is:

```text
48 + payload_length
```

---

# 12. Byte Order

All integer fields in the binary header MUST use:

```text
network byte order / big-endian
```

No compiler- or platform-native struct packing is permitted.

---

# 13. Maximum Payload

The maximum JSON payload length is:

```text
16 MiB = 16,777,216 bytes
```

The maximum complete frame length is therefore:

```text
16,777,264 bytes
```

A receiver MUST reject larger payloads.

---

# 14. Fixed Header Layout

The canonical 48-byte header is:

| Offset | Size | Field          | Encoding     |
| -----: | ---: | -------------- | ------------ |
|    `0` |    4 | Magic          | ASCII `GARP` |
|    `4` |    1 | Wire version   | `uint8`      |
|    `5` |    1 | Flags          | `uint8`      |
|    `6` |    2 | Header length  | `uint16`, BE |
|    `8` |    4 | Payload length | `uint32`, BE |
|   `12` |    2 | Message type   | `uint16`, BE |
|   `14` |    2 | Reserved       | MUST be zero |
|   `16` |   16 | Request ID     | UUID bytes   |
|   `32` |   16 | Session ID     | UUID bytes   |

Total:

```text
48 bytes
```

---

# 15. Magic

The first four bytes MUST be:

```text
47 41 52 50
```

representing:

```text
GARP
```

A frame with another magic value MUST be rejected.

---

# 16. Wire Version

Byte offset `4` contains:

```text
0x15
```

for GARP/1.05.

---

# 17. Flags

Flags are currently reserved.

For GARP/1.05:

```text
bits 0..7 = 0
```

An implementation MUST reject an unsupported non-zero flag unless the flag is explicitly defined by an applicable extension.

---

# 18. Header Length

The header length MUST equal:

```text
48
```

A different value is invalid for GARP/1.05.

---

# 19. Payload Length

The payload length is the number of bytes following the fixed header.

It is not the number of Unicode characters.

---

# 20. Message Type

Message type is the canonical numerical registry identifier.

The numeric identifier and JSON semantic message name MUST agree.

A mismatch MUST fail closed.

---

# 21. Request ID in the Header

For ordinary commands and their associated events, the binary header MAY contain the request UUID.

For messages without request identity:

```text
00000000000000000000000000000000
```

MUST be used.

When a JSON `request_id` is present, it MUST equal the header request ID.

---

# 22. Session ID in the Header

For session-associated messages, the header MAY contain the session UUID.

For messages without a session:

```text
00000000000000000000000000000000
```

MUST be used.

When a JSON `session_id` is present, it MUST equal the header session ID.

---

# 23. UUID Representation

Protocol identifiers transmitted in the binary header MUST be 128-bit UUID values.

JSON representation MUST use canonical textual form:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

The binary representation MUST correspond exactly to the UUID represented by the JSON field.

---


# 26. Removed Acknowledgment Messages

The following identifiers are no longer active in GARP/1.05:

```text

CANCEL_ACK
```

They MUST NOT be emitted.

The replacement is:

```text
PROMPT        -> RESPONSE
CANCEL_PROMPT -> RESPONSE
```

# 28. Correlation Rule

JSON identity and binary-header identity MUST be consistent.

A message MUST NOT contain:

```text
header request_id = A
JSON request_id = B
```

Such a message MUST fail closed.

# Part VI — Handshake and Authentication

# 29. Authentication Goals

Authentication MUST provide:

* peer authentication;
* replay resistance;
* transcript binding;
* protocol-version binding;
* constant-time proof verification.

---

# 30. Nonces

`client_nonce` and `server_nonce` MUST each contain 32 cryptographically random bytes.

JSON representation:

```text
64 lowercase hexadecimal characters
```

A nonce MUST NOT be reused across handshakes.

---

# 31. HELLO Schema

**Type:** `0x0001`

```json
{
  "protocol": "GARP/1.05",
  "supported_versions": [
    "GARP/1.05"
  ],
  "client_id": "uuid",
  "client_nonce": "64-hex-chars",
  "features": [],
  "metadata": {}
}
```

Required:

```text
protocol
supported_versions
client_id
client_nonce
```

`client_id` MUST be a UUID.

---

# 32. HELLO_CHALLENGE Schema

**Type:** `0x0002`

```json
{
  "protocol": "GARP/1.05",
  "server_id": "uuid",
  "server_nonce": "64-hex-chars",
  "algorithm": "HMAC-SHA256"
}
```

`server_id` MUST be a UUID.

---

# 33. Authentication Transcript

HMAC inputs MUST be unambiguous.

No direct variable-length concatenation is permitted.

The canonical transcript is:

```text
domain
protocol
client_id
client_nonce
server_id
server_nonce
```

encoded as:

```text
length-prefixed UTF-8/binary fields
```

Specifically:

```text
u32be(domain_length)
domain_utf8

u32be(protocol_length)
protocol_utf8

u32be(client_id_length)
client_id_utf8

u32be(client_nonce_length)
client_nonce_ascii

u32be(server_id_length)
server_id_utf8

u32be(server_nonce_length)
server_nonce_ascii
```

The domain for client authentication is:

```text
GARP/1.05/CLIENT-AUTH
```

---

# 34. HELLO_AUTH Schema

**Type:** `0x0003`

```json
{
  "protocol": "GARP/1.05",
  "client_id": "uuid",
  "server_id": "uuid",
  "client_nonce": "64-hex-chars",
  "server_nonce": "64-hex-chars",
  "proof": "64-lowercase-hex-chars"
}
```

The proof is:

```text
HMAC-SHA256(
    shared_secret,
    CLIENT-AUTH transcript
)
```

---

# 35. Server Authentication

`HELLO_ACK` MUST contain a server proof.

The server proof uses the same canonical field encoding with domain:

```text
GARP/1.05/SERVER-AUTH
```

This provides mutual authentication.

---

# 36. HELLO_ACK Schema

**Type:** `0x0004`

```json
{
  "protocol": "GARP/1.05",
  "server_id": "uuid",
  "client_id": "uuid",
  "authenticated": true,
  "server_proof": "64-lowercase-hex-chars",
  "features": []
}
```

`authenticated` MUST be true only after authentication has succeeded.

---

# 37. Authentication Failure

The following conditions MUST fail authentication:

* unknown client;
* invalid proof;
* incorrect nonce;
* nonce reuse;
* invalid protocol;
* invalid server identity;
* malformed proof encoding;
* timeout.

The preferred error code is:

```text
AUTH_FAILED
```

---

# 38. Constant-Time Verification

HMAC proofs MUST be compared using a constant-time comparison mechanism.

---

# 39. Authentication Timeout

The implementation MUST enforce a finite handshake timeout.

The default is:

```text
10 seconds
```

The value SHOULD be configurable.

---

# 40. Authentication Retry

Failed authentication MUST terminate the handshake.

A client MUST establish a fresh handshake and fresh nonces before retrying.

---

# Part VII — Universal RESPONSE

# 41. RESPONSE Schema

**Type:** `0x0005`

Success:

```json
{
  "command": "string",
  "success": true,
  "result": {}
}
```

Failure:

```json
{
  "command": "string",
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "string",
    "retryable": false,
    "state": "ERROR",
    "provider": "string",
    "details": {}
  }
}
```

---

# 42. RESPONSE Command Field

`command` MUST contain the exact lower-case semantic command name.

Examples:

```text
list_tabs
create_session
prompt
get_response
cancel_prompt
```

---

# 43. RESPONSE Uniqueness

Exactly one synchronous `RESPONSE` MUST be emitted for each ordinary command.

The gateway MUST NOT emit:

```text
RESPONSE success
RESPONSE failure
```

for the same request.

---

# 44. Asynchronous Events After RESPONSE

A successful `RESPONSE` does not terminate an asynchronous operation.

Events may follow.

---

# Part VIII — Error Protocol

# 45. ERROR

**Type:** `0x0006`

```json
{
  "code": "PROTOCOL_ERROR",
  "message": "string",
  "retryable": false,
  "state": "ERROR",
  "details": {}
}
```

---

# 46. ERROR vs RESPONSE Failure

Use `RESPONSE(success=false)` for an application-level command failure.

Use `ERROR` when the protocol itself cannot safely process the command.

Examples:

```text
unknown session
    -> RESPONSE(success=false)
```

```text
malformed frame
    -> ERROR
```

```text
invalid JSON
    -> ERROR
```

---

# 51. CLOSE_TAB

**Type:** `0x0014`

Request:

```json
{
  "tab_id": "uuid"
}
```

Result:

```json
{
  "success": true,
  "tab_id": "uuid"
}
```

If closing the tab would destroy an active session request, the gateway MUST first apply the session/request lifecycle rules.

The default behavior is to reject closing the tab while a session has an active request:

```text
SESSION_BUSY
```

An explicitly supported force mechanism MAY override this behavior.

# Part X — Session Commands

```json

  "provider": "deepseek",
  "tab_id": "uuid",
  "options": {}
}
```

```json
{
  "session_id": "uuid",
```

# Part XI — Session State Model

# 58. Session State

Session state and generation state are independent.

Session state:

```text
NEW
PREPARING
READY
BUSY
AUTH_REQUIRED
RATE_LIMITED
ERROR
CLOSED
```

---

# 59. Input State

```text
UNKNOWN
NOT_READY
READY
INJECTING
INJECTION_VERIFIED
SUBMITTING
SUBMISSION_VERIFIED
```

---

# 60. Generation State

```text
IDLE
STARTING
STREAMING
CONTINUATION_REQUIRED
COMPLETING
COMPLETE
FAILED
CANCELLED
```

---

# 61. Formal Session Transitions

| Current                | Event                            | Next                                            |
| ---------------------- | -------------------------------- | ----------------------------------------------- |
| `NEW`                  | create/attach                    | `PREPARING`                                     |
| `PREPARING`            | input unavailable                | `PREPARING`                                     |
| `PREPARING`            | provider ready                   | `READY`                                         |
| `READY`                | prompt accepted                  | `BUSY`                                          |
| `BUSY`                 | generation complete              | `READY`                                         |
| `BUSY`                 | generation failed                | `ERROR` or `READY` according to recovery policy |
| `READY`                | provider authentication required | `AUTH_REQUIRED`                                 |
| `PREPARING`            | authentication required          | `AUTH_REQUIRED`                                 |
| `READY`                | rate limited                     | `RATE_LIMITED`                                  |
| `PREPARING`            | rate limited                     | `RATE_LIMITED`                                  |
| `AUTH_REQUIRED`        | provider becomes authenticated   | `PREPARING`                                     |
| `RATE_LIMITED`         | limit clears                     | `PREPARING`                                     |
| any non-`CLOSED` state | close session                    | `CLOSED`                                        |

---

# 62. Navigation State Transition

Relevant navigation MUST cause:

```text
READY -> PREPARING
BUSY  -> PREPARING
```

or another explicitly applicable recovery state.

It MUST increment:

```text
page_generation
```

---

# 63. One Active Prompt Per Session

A session MUST NOT execute more than one active `PROMPT` simultaneously.

A second active prompt MUST fail with:

```text
SESSION_BUSY
```

This rule is independent of TCP connection concurrency.

# Part XIII — Page Generations and Actor Safety

# 68. Page Generation

`page_generation` is a logical fencing token.

It MUST:

* start at a positive integer;
* monotonically increase;
* never decrease;
* change when browser-side identity changes in a relevant way.

---

# 69. Causes of Generation Changes

At minimum:

* relevant navigation;
* document replacement;
* JSWindowActor replacement;
* attachment to a different document;
* session reset;
* provider conversation replacement where DOM identity becomes invalid.

---

# 70. Actor Replacement

Firefox JSWindowActors are transient.

A logical GARP session MUST survive actor replacement.

The gateway MUST reacquire the current actor for every child operation.

---

# 71. Stale Actor Rule

A child result associated with an older generation MUST NOT overwrite newer authoritative state.

A stale result MUST be:

```text
discarded
```

or:

```text
reported diagnostically
```

or:

```text
rejected with STALE_PAGE_GENERATION / STALE_ACTOR
```

according to the operation.

---

# 72. Fencing

Before committing a child operation result, the gateway MUST verify that:

```text
observed page_generation == current page_generation
```

or that the operation explicitly supports cross-generation semantics.

# Part XV — Input Injection

# 80. Provider Adapter Responsibility

Provider-specific automation belongs inside provider adapters.

Adapters own:

* input selectors;
* send selectors;
* response selectors;
* continuation selectors;
* authentication detection;
* rate-limit detection;
* injection strategies;
* submission strategies.

---

# 81. Input Discovery

Input discovery MUST operate on the current live document.

The implementation MAY search:

* normal DOM;
* shadow DOM;
* provider-specific DOM structures.

A discovered input MUST be:

* visible;
* enabled;
* writable;
* compatible with the selected injection strategy.

---

# 82. Injection State

The required logical sequence is:

```text
READY
  |
  v
INJECTING
  |
  v
INJECTION_VERIFIED
```

Failure at any stage produces:

```text
INPUT_INJECTION_FAILED
```

or a more specific error.

---

# 83. Controlled Inputs

For reactive browser frameworks, direct assignment to `.value` alone MUST NOT be considered sufficient.

The provider adapter SHOULD use a compatible mechanism such as:

* native prototype value setter;
* appropriate input events;
* appropriate change events;
* provider-specific framework-compatible interaction.

---

# 84. Injection Verification

After injection the adapter MUST verify the live input.

Verification SHOULD establish:

```text
current live element exists
current value reflects prompt
framework did not overwrite value
input remains writable
```

---

# 85. Node Replacement

The adapter MUST account for:

```text
old input element
      |
      v
DOM re-render
      |
      v
new input element
```

If the original node disappears, the adapter MUST re-query the live input.

---

# 86. Prompt Logging

Prompt content MUST NOT appear in normal diagnostics.

Diagnostics SHOULD use:

```text
prompt_length
hash, if specifically enabled
```

instead of plaintext content.

---


# Part XVII — Generation

# 92. GENERATION_STARTED

**Type:** `0x0051`

```json
{
  "state": "STARTING",
  "message_id": "uuid",
  "page_generation": 2
}
```

It MUST occur after `INPUT_SUBMITTED`.

---

# 93. Message Identity

`message_id` is the logical identity of the provider response being observed.

The gateway SHOULD establish a provider-native identity where available.

Otherwise it MAY use an internally generated UUID, provided the identity remains stable for the logical response.

---

# 94. Text Revision

Each observed logical provider message has:

```text
revision
```

Revision rules:

* starts at `1`;
* is monotonically increasing;
* increments whenever the logical observed text changes;
* is scoped to one `message_id`;
* is independent of transport `sequence`.

---

# 95. Transport Sequence vs Text Revision

These are different:

```text
sequence = ordering of GARP events
revision = version of observed provider text
```

Neither may be substituted for the other.

---

# 96. GENERATION_DELTA

**Type:** `0x0052`

Append observation:

```json
{
  "message_id": "uuid",
  "revision": 17,
  "mode": "DELTA",
  "text_delta": "new text"
}
```

Replacement observation:

```json
{
  "message_id": "uuid",
  "revision": 18,
  "mode": "REPLACE",
  "text": "complete current observed text"
}
```

---

# 97. Delta Reconstruction

For:

```text
mode = DELTA
```

the client MUST append `text_delta` to the text represented by the previous revision.

For:

```text
mode = REPLACE
```

the client MUST replace its complete accumulated text with `text`.

A client MUST NOT guess the mode from the text itself.

---

# 98. Revision Gaps

If a client receives:

```text
revision = 18
```

while expecting:

```text
17
```

it MUST detect a revision gap.

The client SHOULD request the current complete response using:

```text
GET_RESPONSE
```

or use a retained full observation where available.

---

# 99. GENERATION_PROGRESS

**Type:** `0x0053`


Example:


# Part XIX — Cancellation

# 107. Cancellation Model

Cancellation has two distinct stages:

```text
CANCEL_REQUESTED
```

and:

```text
CANCELLED
```

The former means cancellation was accepted by the gateway.

The latter means provider termination was observed.

---

# 108. Cancellation Arbitration

The authoritative terminal outcome is determined by observable order.

### Case A

Provider completion is observed before cancellation is accepted:

```text
COMPLETE
```

wins.

### Case B

Cancellation is accepted while generation remains active and provider stop is subsequently verified:

```text
CANCELLED
```

wins.

### Case C

Cancellation is accepted, but provider completion is observed before provider stop can be verified:

```text
COMPLETE
```

wins.

This rule eliminates an otherwise ambiguous completion/cancel race.

---

# 109. Cancellation Failure

If cancellation cannot be executed:

```text
CANCEL_FAILED
```

MUST be reported.

The request remains subject to the normal generation lifecycle.

# Part XXIII — Concurrency and Flow Control

# 126. Connection Concurrency

GARP permits multiple outstanding requests on one authenticated connection.

Each request is identified by:

```text
request_id
```

---

# 127. Session Concurrency

A session permits at most one active prompt request.

Thus:

```text
connection concurrency
```

does not imply:

```text
session execution concurrency
```

---

# 128. Different Sessions

Operations on different sessions MAY proceed concurrently.

---

# 129. Same Session

Operations that mutate the same session state MUST be serialized.

This includes:

* prompt start;
* prompt cancellation;
* reset;
* attach/detach;
* close;
* generation continuation.

---

# 130. Event Ordering

Events for one request MUST have strictly increasing:

```text
sequence
```

values.

Two different requests MAY have unrelated sequence streams.

---

# 131. Sequence Starting Value

The first request-associated event SHOULD use:

```text
sequence = 1
```

Sequence zero is reserved.

---

# 132. Sequence Gaps

A receiver detecting an impossible sequence transition SHOULD report:

```text
SEQUENCE_GAP
```

or:

```text
SEQUENCE_CONFLICT
```

depending on the condition.

---

# 133. Event Backpressure

A conforming gateway MUST NOT silently discard request-associated events.

If the connection cannot accept events within configured buffering limits, the gateway MUST either:

* apply backpressure;
* terminate the subscription;
* fail the connection explicitly.

Silent event loss is forbidden.

---

# 134. Buffer Limits

Implementations MUST define configurable limits for:

```text
maximum outstanding requests
maximum queued events
maximum event-history memory
maximum generation buffer
maximum prompt size
maximum response size
```

These values SHOULD be advertised in `CAPABILITIES`.

---

# Part XXIV — Response Retention

# 135. Completed Response Retention

A completed response MUST remain retrievable for at least the configured:

```text
response_retention_ms
```

period.

The default is:

```text
86,400,000 ms
```

or 24 hours.

A server MAY use a lower configured value only if advertised in `CAPABILITIES`.

---

# 136. Response Eviction

If an implementation evicts an otherwise valid response before its advertised retention period, it MUST emit or make available:

```text
RESPONSE_EVICTED
```

as an explicit error condition.

---

# 137. Reset Behavior

`RESET_SESSION` may invalidate retained response state associated with the reset session.

This is an explicit lifecycle boundary.

# Part XXVII — Validation and Schema Authority

# 142. Schema Authority

When defining a message, the normative sources are ordered:

```text
1. GARP/1.05 normative prose
2. normative message schema
3. normative field tables
4. examples
```

Examples MUST NOT override normative schema requirements.

---

# 143. Schema Version

The protocol version determines the normative message schema version unless a future extension explicitly defines an independent schema version.

Implementations MUST NOT silently accept a different schema version.

# 144. Required Fields

A required field MUST:

* exist;
* have the correct JSON type;
* satisfy its specified constraints.

Missing or incorrectly typed required fields MUST fail closed.

---

# 145. Unknown Fields

Unknown extension fields MAY be ignored when:

* their names are not reserved;
* they do not redefine normative fields;
* the receiving implementation can safely ignore them.

Unknown message types MUST NOT be interpreted as known message types.


A mismatch is a protocol error.

# Part XXXIII — Reconnection and Connection Loss

# 160. Connection Loss

Connection loss MUST NOT automatically destroy logical session state.

The session may survive if the implementation supports persistent session management.

---

# 161. Active Request on Disconnect

A gateway MUST have one explicit configured policy.

The recommended policy is:

```text
connection lost
      |
      v
request continues
      |
      v
response remains retrievable
```

This permits a reconnecting client to use:

```text
GET_PROMPT_STATUS
GET_RESPONSE
SUBSCRIBE_RESPONSE
```

where session/request retention remains available.

---

# 162. Subscription Loss

Subscriptions are connection-scoped.

A disconnected connection loses its subscriptions.

The logical request does not necessarily terminate.

---

# 163. Reconnection Identity

A reconnecting controller MUST authenticate again.

It MUST NOT reuse an old authenticated TCP connection state.

```text
  -> NOT_READY
  -> READY
```

```text

  -> STREAMING
  -> FAILED
```

```text

2. Validate session
3. Validate session state
4. Wait for actual provider readiness

7. Discover current input
8. Inject prompt
9. Verify live input
10. Resolve submission mechanism
11. Execute submission
12. Verify submission
13. Emit INPUT_SUBMITTED
14. Emit GENERATION_STARTED

16. Emit generation events
17. Handle continuation
18. Resolve completion/cancellation race
19. Emit terminal event
```

# Part XLIII — Final Normative Principles

# 211. One Response

Every ordinary command has one universal synchronous `RESPONSE`.

---

# 212. Events Are Events

Typed lifecycle messages are asynchronous events, never command replies.

---

# 213. Readiness Is Observable State

Time is not readiness.

---

# 214. Injection Is Not Submission

DOM mutation is not proof of provider submission.

---

# 215. Submission Is Not Generation

Successful provider submission is not proof of generation start.

---

# 216. Generation Is Not Semantic Correctness

GARP reports transport observations only.

---

# 217. Actors Are Ephemeral

Logical sessions survive browser actor replacement.

---

# 218. Page Generation Is a Fence

Older page generations cannot overwrite newer authoritative state.

---

# 219. Revision and Sequence Are Different

```text
sequence = GARP event ordering
revision = provider text version
```

---

# 220. Diagnostics Are Evidence

Diagnostics must report observable facts, not inferred success.

---

# 221. Fail Closed

Ambiguous protocol state MUST NOT be silently guessed.

---

# 222. No Silent Prompt Mutation

The transport MUST NOT:

* trim;
* rewrite;
* normalize;
* reinterpret

prompt content.

---

# 223. No Secret Leakage

Authentication credentials, cookies, tokens, and secrets MUST NOT be exposed through diagnostics.

---

# 224. Deterministic Terminal State

Every request MUST eventually have one authoritative terminal outcome:

```text
COMPLETE
FAILED
CANCELLED
```

subject to explicitly configured retention/recovery behavior.
