# GARP/1.19

## Gateway AI Runtime Protocol

### Protocol Specification

### Freeze Candidate

**Status:** Normative
**Version:** 1.19
**Protocol Identifier:** `GARP/1.19`
**Wire Version:** `0x00`
**Document Language:** English
**Encoding:** UTF-8
**Transport:** Reliable byte stream, normally TCP
**Security Model:** Mutual challenge-response using a deployment-provisioned shared secret
**Primary Purpose:** Deterministic transport and browser-session boundary between an AI runtime and a browser-based AI gateway

---

# 1. Scope

## 1.1 Purpose

GARP defines the transport, authentication, browser-session, provider-adapter, generation-event, cancellation, recovery, and optional replay interfaces between an external AI runtime and a browser gateway.

GARP is a transport and browser-session protocol.

GARP does not define:

* AI quality scoring.
* Artifact acceptance.
* GRISP compilation semantics.
* GRISP runtime semantics.
* Policy approval semantics.
* Human approval semantics.
* Provider-specific credential acquisition.
* Provider-specific internal implementation details.

## 1.2 Architectural role

The intended architecture is:

```text
GRISP / AI Runtime
        |
        v
      GARP
        |
        v
Browser Gateway (e.g. Firefox)
        |
        v
Provider Adapter
        |
        v
AI Provider
```

The provider adapter is the sole component responsible for translating provider-specific browser behavior into the provider-independent GARP model.

## 1.3 Design principles

Implementations MUST be:

* deterministic where the protocol defines deterministic behavior;
* fail-closed on malformed or ambiguous input;
* explicit about state;
* explicit about evidence;
* explicit about request and session identity;
* resistant to stale browser actors and stale provider observations;
* resistant to duplicate execution;
* resistant to replay of authentication messages;
* safe against partial browser failures;
* independent of provider-specific selectors at the protocol layer.

# 2. Normative language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **MAY**, and **OPTIONAL** are normative.

An implementation claiming GARP/1.19 conformance MUST implement all requirements marked MUST, MUST NOT, REQUIRED, SHALL, or SHALL NOT.

# 3. Protocol identity

## 3.1 Canonical protocol name

The only canonical protocol name is:

```text
Gateway AI Runtime Protocol
```

The canonical acronym is:

```text
GARP
```

The canonical semantic protocol identifier is:

```text
GARP/1.19
```

## 3.2 Wire version

The wire version is:

```text
0x00
```

`0x00` is the only wire version defined by GARP/1.19.

The semantic protocol version is independent of the wire version.

## 3.3 Identity scope and artifact naming

The protocol distinguishes between:

1. **Protocol Identity:** The protocol defined herein is strictly identified as `GARP` with semantic version `GARP/1.19`.
2. **Artifact Identity:** Authoritative normative specification artifacts MUST use `GARP` and `GARP/1.19`.
3. **Implementation Identity:** Software projects, daemon executables, client libraries, or host applications implementing GARP MAY use independent product or project names without affecting protocol conformance.

# 4. Transport

## 4.1 Transport properties

The transport MUST provide:

* ordered bytes;
* reliable delivery semantics;
* connection-oriented behavior;
* explicit connection closure.

TCP is the reference transport.

## 4.2 TLS

For non-loopback operation, implementations MUST use TLS 1.2 or later.

For loopback operation, TLS MAY be omitted when the host operating-system security boundary protects the listener adequately.

## 4.3 Local binding

A gateway MAY bind only to loopback:

```text
127.0.0.1
::1
```

A gateway MUST NOT expose an unauthenticated GARP listener on a non-loopback interface.

# 5. Byte order

All multibyte integer fields in the binary header are encoded big-endian.

For example:

```text
0x000000A7
```

is encoded:

```text
00 00 00 A7
```

# 6. Frame format

Every GARP frame consists of a fixed 48-byte header followed by the frame payload.

```text
+----------------------+----------------+
| Offset               | Size           |
+----------------------+----------------+
| magic                | 4              |
| wire_version         | 1              |
| flags                | 1              |
| header_len           | 2              |
| payload_len          | 4              |
| message_type         | 2              |
| reserved             | 2              |
| request_uuid         | 16             |
| session_uuid         | 16             |
| payload              | payload_len    |
+----------------------+----------------+
```

The header is exactly:

```text
48 bytes
```

### Terminology: Frame Payload vs Envelope Payload

To avoid ambiguity, GARP distinguishes between:

1. **Frame Payload:** The raw byte sequence of length `payload_len` immediately following the fixed 48-byte binary header. In base GARP, the frame payload is the serialized UTF-8 JSON Common Envelope.
2. **Envelope Payload:** The inner JSON object stored in the `"payload"` member of the Common Envelope, whose schema is specific to the message type.

## 6.1 Magic

Offset:

```text
0
```

Length:

```text
4
```

Value:

```text
GARP
```

ASCII bytes:

```text
47 41 52 50
```

Any other value MUST cause immediate frame rejection.

## 6.2 Wire version

Offset:

```text
4
```

Length:

```text
1
```

Required value:

```text
00
```

Any unsupported wire version MUST produce:

```text
UNSUPPORTED_WIRE_VERSION
```

and MUST NOT be interpreted using a different framing rule.

## 6.3 Flags

Offset:

```text
5
```

Length:

```text
1
```

Base GARP/1.19 requires:

```text
flags = 0
```

unless a negotiated extension explicitly defines a flag.

Unknown or unnegotiated flag bits MUST cause:

```text
UNSUPPORTED_FEATURE
```

## 6.4 Header length

Offset:

```text
6
```

Length:

```text
2
```

Required value:

```text
48
```

encoded:

```text
00 30
```

The field is attacker-controlled input and MUST be validated before the implementation proceeds.

A value other than 48 MUST cause frame rejection.

## 6.5 Payload length

Offset:

```text
8
```

Length:

```text
4
```

The value is an unsigned 32-bit integer specifying the exact byte length of the frame payload.

Wire constraints:

```text
0 <= payload_len <= 4294967295
```

The receiver MUST validate the payload length against the currently applicable limit before allocating storage for the payload:

```text
effective_limit = min(advertised_max_payload_bytes, 4294967295)
```

No implementation may allocate unbounded memory based solely on an attacker-controlled payload length.

## 6.6 Message type

Offset:

```text
12
```

Length:

```text
2
```

Unsigned big-endian message code.

## 6.7 Reserved

Offset:

```text
14
```

Length:

```text
2
```

Required value:

```text
0
```

encoded:

```text
00 00
```

Any nonzero value MUST cause:

```text
INVALID_ARGUMENT
```

## 6.8 Request UUID

Offset:

```text
16
```

Length:

```text
16
```

The raw UUID bytes associated with the frame.

Nil UUID:

```text
00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00
```

## 6.9 Session UUID

Offset:

```text
32
```

Length:

```text
16
```

The raw session UUID.

# 7. UUID encoding

## 7.1 Binary encoding

UUIDs are encoded as 16 raw bytes in RFC-style network byte order.

## 7.2 JSON encoding

UUID-bearing envelope fields are always present.

For envelope identity fields:

```json
"request_id": "uuid"
"session_id": "uuid"
```

or:

```json
"request_id": null
"session_id": null
```

A JSON `null` in an envelope identity field means the corresponding binary UUID field is all zero (nil UUID).

## 7.3 Application objects

Application-level objects MAY use the string representation of the nil UUID:

```text
00000000-0000-0000-0000-000000000000
```

This is distinct from the envelope identity representation.

The distinction is intentional.

## 7.4 UUID generation

Client-created request identifiers SHOULD be generated using a cryptographically secure random source and SHOULD use UUID version 4 semantics.

# 8. Validation order

A receiver MUST validate a frame in this order:

1. fixed header availability;
2. magic;
3. wire version;
4. header length;
5. payload length against applicable limit;
6. flags;
7. reserved field;
8. message type;
9. payload byte acquisition;
10. payload encoding;
11. JSON syntax;
12. duplicate JSON member detection;
13. common envelope member presence and types;
14. header-to-envelope identity and message-type binding;
15. message schema;
16. connection and authentication state;
17. request identity and deduplication;
18. session identity;
19. target identity;
20. state transition and provider semantics.

An implementation MAY perform additional checks earlier when the result is equivalent and deterministic.

---

# 9. JSON representation

## 9.1 Encoding

All JSON payloads MUST be UTF-8.

## 9.2 Duplicate object keys

Duplicate object member names MUST be rejected.

An implementation MUST NOT silently select first-key or last-key semantics for duplicate names.

## 9.3 Closed objects

All base GARP message and payload objects are closed unless explicitly declared open.

Unknown members in a closed object MUST cause:

```text
INVALID_ARGUMENT
```

Unknown extension members are permitted only through an explicitly declared `_extensions` object.

## 9.4 Open extension object

In base GARP, the `_extensions` object is permitted only within `PROMPT.options`.

Where a schema explicitly permits:

```json
"_extensions": {}
```

the `_extensions` object is open to negotiated extensions.

Its serialized size remains strictly bounded by the enclosing frame payload and the applicable `max_payload_bytes` limit.

---

# 10. JSON integer types and bounds

JavaScript number precision MUST NOT be relied upon for protocol `uint64` values.

## 10.1 uint64-string

Every protocol field defined as `uint64` in JSON MUST be encoded as a decimal string matching:

```text
^(0|[1-9][0-9]{0,19})$
```

and representing a value no greater than:

```text
18446744073709551615
```

Examples:

```json
"sequence": "1"
"revision": "2"
"page_generation": "7"
```

## 10.2 uint32

Fields defined as `uint32` MAY be encoded as JSON numbers.

Their range is:

```text
0 .. 4294967295
```

## 10.3 Booleans

Booleans MUST use JSON `true` or `false`.

Strings MUST NOT be used as boolean substitutes in base schemas.

## 10.4 Protocol string bounds

All string fields in base schemas have defined byte-length bounds to guarantee fail-closed processing:

* `provider`: 1 .. 64 bytes
* `tab_id`: 1 .. 64 bytes
* `actor_instance`: 1 .. 64 bytes
* `code`: 1 .. 64 bytes
* `strategy`: 1 .. 64 bytes
* `title`: 0 .. 512 bytes
* `message`: 0 .. 1024 bytes
* `url`: 1 .. 4096 bytes

A string exceeding its defined bound MUST be rejected with:

```text
INVALID_ARGUMENT
```

## 10.5 Protocol duration bounds

To prevent arithmetic overflow in 64-bit monotonic clock implementations, all duration and timeout fields (represented as uint64-strings in milliseconds) are bounded:

* Individual prompt timeout (`timeout_ms`): `0 <= timeout_ms <= 86400000` (max 24 hours).
* Session and connection durations (`continuation_wait_ms`, `recovery_deadline_ms`, `retry_after_ms`, `idle_timeout_ms`, `interval_ms`, `response_retention_ms`): `0 <= value <= 864000000` (max 10 days).

A duration exceeding its bound MUST be rejected with:

```text
INVALID_ARGUMENT
```

# 11. Common envelope

Every JSON message uses the following structure:

```json
{
  "garp": "1.19",
  "type": "MESSAGE_TYPE",
  "request_id": null,
  "session_id": null,
  "timestamp": "2026-01-01T00:00:00.000Z",
  "sequence": null,
  "payload": {}
}
```

## 11.1 Required members

The following are always present:

```text
garp
type
request_id
session_id
timestamp
payload
```

`sequence` is always present as either a uint64-string or null.

## 11.2 garp

Required value:

```text
1.19
```

## 11.3 type

ASCII uppercase registry name.

## 11.4 request_id

For a command issued by a client, this is the unique command identifier.

For a response (`RESPONSE` or command-correlated `ERROR`), it identifies the originating command request ID.

For handshake correlation messages (`HELLO_CHALLENGE`, `HELLO_AUTH`, `HELLO_ACK`), it MAY equal the initiating `HELLO` request ID.

For all session-scoped events (e.g. `GENERATION_DELTA`, `SESSION_READY`), envelope `request_id` MUST be:

```json
null
```

(and header `request_uuid` MUST be all-zero nil UUID). Command correlation for prompts is carried inside `payload.prompt_request_id`.

For unsolicited connection-scoped events (`CAPABILITIES`, `PONG`, `BROWSER_STATUS`), envelope `request_id` MUST be:

```json
null
```

## 11.5 session_id

Session-scoped messages and session-scoped commands contain the session UUID.

Connection-scoped messages contain:

```json
null
```

## 11.6 timestamp

Strict RFC 3339 / ISO 8601 UTC timestamp string with millisecond precision:

```text
YYYY-MM-DDTHH:MM:SS.sssZ
```

For example:

```json
"timestamp": "2026-01-01T00:00:00.000Z"
```

Timestamp is informational.

Timeouts and deadline decisions MUST use monotonic clocks.

## 11.7 sequence

Session-scoped events use monotonically increasing sequence values.

Connection-scoped messages, commands, and direct command responses use:

```json
null
```

## 11.8 payload

JSON object whose exact schema is defined by the message type.

# 12. Header-to-envelope identity binding

The binary header and JSON envelope MUST agree.

The following mappings are mandatory:

```text
header.message_type  = registry(type)
header.request_uuid  = envelope.request_id
header.session_uuid  = envelope.session_id
```

A mismatch MUST cause:

```text
HEADER_JSON_MISMATCH
```

An unknown binary message code MUST instead cause:

```text
UNKNOWN_MESSAGE_TYPE
```

An otherwise valid binary message code carrying an unknown JSON `type` MUST cause:

```text
UNKNOWN_MESSAGE_TYPE
```

Extension message codes MUST be allocated outside the base registry.


Extension flags are allocated independently from message codes.

* flag bit;
* negotiated feature name;
* semantic meaning;
* valid message classes.

Two extensions MUST NOT allocate the same flag bit for incompatible meanings.

An unknown or unnegotiated flag is invalid.

# 15. Feature names and modifiers

Feature names MUST match:

```text
^[a-z0-9][a-z0-9._-]{0,127}$
```

The canonical extension name does NOT include any leading punctuation (e.g. `ext-pong`).

During handshake feature negotiation, a client or server MAY prefix a feature name with:

```text
!
```

to declare it a **required feature** (e.g. `!ext-pong`).

The `!` prefix is a handshake negotiation token modifier indicating that the connection MUST fail if the peer does not support it.

The `!` modifier is cryptographically bound into the negotiation transcript and MUST NOT be silently stripped.

Validation MUST occur before canonicalization.

Duplicate canonical feature names MUST be rejected.

Feature names MUST be sorted by raw UTF-8 byte order after validation and without applying locale-sensitive collation.

# 16. Authentication

## 16.1 Purpose

Authentication proves:

1. possession of the shared secret;
2. knowledge of the current challenge;
3. agreement on semantic version;
4. agreement on wire version;
5. agreement on offered features;
6. agreement on final negotiated features;
7. peer identity metadata.

## 16.2 Shared secret

The shared secret MUST contain at least 32 raw bytes.

The deployment MUST define how the configured secret is represented.

No implementation may silently reinterpret a configured textual value as hexadecimal when the deployment expects raw bytes, or vice versa.

## 16.3 Normative test secret

The authentication test vector uses exactly these raw ASCII bytes:

```text
0123456789abcdef0123456789abcdef
```

This is 32 bytes.

It is NOT a hexadecimal encoding of 16 bytes.

## 16.4 Client nonce

The client nonce MUST be exactly 16 raw bytes.

It is represented in JSON as unpadded Base64URL.

Padding characters MUST be rejected.

Decode failures MUST cause authentication failure.

## 16.5 Server nonce

The server nonce MUST be exactly 16 raw bytes.

It is represented using the same rules as the client nonce.

## 16.6 Authentication transcript

The proof transcript contains these fields in exactly this order:

```text
domain
client_nonce
server_nonce
selected_semantic_version
selected_wire_version
offered_feature_set
final_feature_set
client_name
client_version
server_name
server_version
```

Every field in the transcript (domain, client_nonce, server_nonce, selected_semantic_version, selected_wire_version, client_name, client_version, server_name, server_version) is encoded with a 4-byte big-endian length prefix followed by raw bytes:

```text
u32be(byte_length)
raw bytes
```

The feature-list encoding is:

```text
u32be(feature_count)
repeat feature_count times:
    u32be(feature_byte_length)
    feature UTF-8 bytes
```

Domains are ASCII.

Version strings are UTF-8.

Feature names are UTF-8.

Identity strings are UTF-8.

The negotiated wire version is encoded as:

```text
0x00
```

represented in the transcript as the UTF-8 string:

```text
0x00
```

The selected semantic version is:

```text
1.19
```

## 16.7 Proof

The proof is:

```text
HMAC-SHA256(shared_secret, transcript)
```

The resulting proof is exactly 32 raw bytes.

Its JSON representation is unpadded Base64URL.

Comparison MUST be constant-time.

## 16.8 Domains

The client-to-server proof domain is:

```text
GARP/1.19/client-proof
```

The server-to-client proof domain is:

```text
GARP/1.19/server-proof
```

## 16.9 Negotiation binding

Both the original offered feature set and final negotiated feature set are included in the transcript.

Therefore:

```text
!ext-pong
```

cannot be changed to:

```text
ext-pong
```

without invalidating the proof.

The required-feature marker is cryptographically bound.

## 16.10 Timestamp

Authentication proofs do not include the timestamp.

Freshness is provided by the nonces.

The timestamp remains informational.

# 17. Authentication messages

## 17.1 HELLO

Header:

```text
request_uuid = client-generated UUID
session_uuid = nil
```

Payload:

```json
{
  "client_name": "GARPClient",
  "client_version": "1.19.0",
  "versions": ["1.19"],
  "wire_versions": ["0x00"],
  "features": ["!ext-pong"],
  "client_nonce": "BASE64URL"
}
```

## 17.2 HELLO_CHALLENGE

The server selects one semantic version and one wire version.

Payload:

```json
{
  "server_name": "GarpGateway",
  "server_version": "1.19.0",
  "selected_version": "1.19",
  "selected_wire_version": "0x00",
  "features": ["!ext-pong"],
  "server_nonce": "BASE64URL"
}
```

The response correlation identifier equals the initiating HELLO transaction identifier.

## 17.3 HELLO_AUTH

Payload:

```json
{
  "client_proof": "BASE64URL"
}
```

Its request UUID equals the correlated HELLO transaction identifier.

## 17.4 HELLO_ACK

Payload:

```json
{
  "server_proof": "BASE64URL",
  "selected_version": "1.19",
  "selected_wire_version": "0x00",
  "features": ["!ext-pong"]
}
```

HELLO_ACK completes authentication only after the client verifies the server proof.

# 18. Request-ID uniqueness and correlation exception

## 18.1 New command IDs

A client-generated command request ID MUST be unique within the connection.

## 18.2 Handshake transaction entry

The entire HELLO handshake sequence:

```text
HELLO             request_id = X
HELLO_CHALLENGE   request_id = X
HELLO_AUTH        request_id = X
HELLO_ACK         request_id = X
```

occupies exactly **one** entry in the connection request-ID namespace.

Reusing that transaction ID for handshake correlation does not constitute issuance of additional client command request IDs.

## 18.3 Application responses

A `RESPONSE` or protocol `ERROR` associated with a command uses that command's request ID.

The receiving implementation MUST NOT interpret a normal response as a new request.

---

# 19. Replay protection

Authentication replay protection MUST survive gateway process restarts for at least 24 hours.

The replay-protection store MAY be:

* durable local storage;
* encrypted persistent storage;
* shared durable key-value storage;
* another mechanism providing equivalent guarantees.

## 19.1 Lost replay state

If authentication replay state is lost or cannot be re-established:

```text
the gateway MUST NOT continue accepting the affected secret.
```

The affected shared secret MUST be disabled and rotated.

A gateway MUST NOT resume authentication with the same secret merely because the process restarted.

This rule applies to authentication replay state only.

Application session state and event history MAY still be lost on restart unless separately persisted.

## 19.2 Replay key

The implementation MUST detect reuse of an authenticated handshake transcript for the same credential context.

A practical deterministic key is:

```text
SHA-256(transcript_core)
```

where `transcript_core` contains both nonces and all negotiation-binding fields.

---

# 20. Handshake timeout

The default handshake timeout is:

```text
10000 ms
```

measured using a monotonic clock.

If authentication does not complete within the deadline, the connection MUST close.

The error condition is:

```text
HANDSHAKE_TIMEOUT
```

# 21. CAPABILITIES

CAPABILITIES is a connection-scoped message.

Header identity:

```text
request_uuid = nil
session_uuid = nil
```

Sequence:

```text
null
```

It is emitted immediately after `HELLO_ACK` and before application commands are processed.

A gateway MUST also emit a new CAPABILITIES event when effective negotiated capabilities materially change.

## 22.1 Provider entries

Each provider entry contains:

```json
{
  "id": "deepseek",
  "version": "1.0.0",

  "input_strategies": [
```

## 22.2 Extensions

Extensions use:

```json
[
  {
    "name": "ext-pong",
    "version": "1.0"
  }

```

Extensions MUST be listed by their canonical name (without `!`) and sorted by name.

## 22.3 Limit breach behaviors

When advertised limits are breached:

* Prompt length exceeding `max_prompt_size`: command rejected with `INVALID_ARGUMENT`.
* Outstanding requests exceeding `max_outstanding_requests`: command rejected with `SESSION_BUSY`.
* Generation buffer exceeding `max_generation_buffer_mb`: prompt fails with `RESPONSE_TOO_LARGE` (`partial = true`).

# 23. Bootstrap limits

The handshake limit is independent from application limits.

The bootstrap handshake payload maximum is:

```text
1 MiB
```

Handshake messages remain subject to the bootstrap limit for the entire connection.

CAPABILITIES does not increase the handshake limit.

Application messages use the advertised effective application limit:

```text
effective_limit = min(advertised_max_payload_bytes, 4294967295)
```

Therefore:

```text
handshake limit = 1 MiB for handshake lifetime
application limit = advertised CAPABILITIES value
```

---

# 24. Capability changes

When effective application limits change, the gateway MUST emit CAPABILITIES.

Clients MUST use the newest advertised values for future operations.

Previously accepted prompt input is not invalidated solely because a subsequently advertised `max_prompt_size` becomes smaller.

Safety limits for:

* global memory;
* queue capacity;
* process safety;
* connection safety;

MAY apply immediately.

---

# 25. Generic RESPONSE

The generic application response payload is:

```json
{
  "success": true
}
```

or:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable description"
  }
}
```

The `RESPONSE` payload MAY contain command-specific result fields.

`success` is REQUIRED in all application RESPONSE payloads.

---

# 26. Generic ERROR

`ERROR` is a protocol-level error and is not a successful application response.

Payload:

```json
{
  "code": "ERROR_CODE",
  "message": "Human-readable description"
}
```

Optional:

```json
{
  "details": {}
}
```

`details`, when present, is bounded by `max_error_details_bytes`.

### Scoping Rules for ERROR Frames:

1. **Command-correlated ERROR:** When emitted in direct response to an invalid or rejected command, the frame adopts the originating command's `request_id` and `session_id`.
2. **Session-originated asynchronous ERROR:** When emitted due to an asynchronous failure of an active session, `request_id` MUST be `null` and `session_id` MUST be the affected session's UUID.
3. **Connection-level ERROR:** When emitted due to framing or connection errors outside a session, `request_id` and `session_id` MUST both be `null`.

```text
CONTINUATION_TIMEOUT

RECOVERY_FAILED
EVENT_QUEUE_OVERFLOW

EVENT_HISTORY_EXPIRED
```

### Normative Mappings:

* `INVALID_ARGUMENT`: Malformed fields, out-of-range integers, string length limit breaches, or nonzero reserved header bytes.
* `INVALID_ENVELOPE`: Missing required envelope members, extra keys in closed objects, or invalid envelope types.
* `UNKNOWN_MESSAGE_TYPE`: Unrecognized header message code or unrecognized envelope type name.
* `UNKNOWN_MESSAGE_ID`: Referenced message identity is unknown for the targeted prompt.
* `HEADER_JSON_MISMATCH`: Discrepancy between header and envelope identity fields (`message_type`, `request_uuid`, `session_uuid`).
* `UNSUPPORTED_VERSION`: Negotiated semantic version is not supported.
* `UNSUPPORTED_WIRE_VERSION`: Wire version is not `0x00`.
* `UNSUPPORTED_FEATURE`: Unnegotiated extension flag or unsupported required feature (`!`).
* `AUTH_REQUIRED`: Command attempted before completing mutual handshake authentication.
* `AUTH_FAILED`: Verification of peer HMAC proof failed.
* `AUTH_REPLAY`: Replay of prior authentication nonces/transcript detected.
* `HANDSHAKE_TIMEOUT`: Handshake did not complete within `handshake_timeout_ms`.
* `DUPLICATE_REQUEST`: Duplicate non-idempotent command request ID received.
* `REVISION_GAP`: Generation revision gap detected (`revision > expected`).
* `EVENT_SEQUENCE_GAP`: Receiver detects gap in session event sequence.
* `EVENT_SEQUENCE_OVERFLOW`: Session event counter exceeds uint64 limit.
* `PAGE_GENERATION_OVERFLOW`: Page generation counter exceeds uint64 limit.
* `INVALID_MESSAGE_STATE`: Command executed in incompatible state (e.g. losing race in `CONTINUE_PROMPT`).
* `SESSION_NOT_FOUND`: Target `session_id` does not exist.
* `SESSION_CLOSED`: Target session is terminally closed.
* `SESSION_BUSY`: Target session has an active prompt or has reached `max_outstanding_requests`.
* `TAB_NOT_FOUND`: Target `tab_id` does not exist.
* `TAB_UNAVAILABLE`: Target tab is crashed, restricted, or unavailable.
* `PROMPT_NOT_FOUND`: Referenced `prompt_request_id` does not exist.
* `PROMPT_NOT_ACTIVE`: Operation targets prompt that is not currently active.
* `PROMPT_ALREADY_TERMINAL`: Operation attempted against already terminal prompt.
* `PROMPT_TIMEOUT`: Prompt exceeded configured `timeout_ms`.
* `PROMPT_CANCELLED`: Operation attempted against an already cancelled prompt.
* `RESPONSE_NOT_READY`: `GET_RESPONSE` called while prompt is still actively generating.
* `INPUT_VERIFICATION_FAILED`: Prompt injection verification failed.
* `SUBMISSION_FAILED`: Submission of input to provider failed.
* `STALE_ACTOR`: Result received from replaced browser actor.
* `NAVIGATION_DRIFT`: Unexpected URL or document replacement occurred during active generation.
* `PROVIDER_UNAVAILABLE`: Selected provider is uninstalled, disabled, or crashed.
* `PROVIDER_AUTH_REQUIRED`: Provider requires interactive user authentication.
* `PROVIDER_RATE_LIMITED`: Provider rejected submission due to rate limits.
* `PROVIDER_ERROR`: Provider internal error or generation failure.
* `RESPONSE_TOO_LARGE`: Accumulated response exceeds `max_response_size` or generation buffer.
* `CONTINUATION_NOT_ALLOWED`: Continuation attempted when disallowed by prompt options (`max_continuations = 0`).
* `CONTINUATION_LIMIT_REACHED`: Continuation requested after reaching configured `max_continuations`.
* `CONTINUATION_TIMEOUT`: Continuation did not arrive within `continuation_wait_ms`.
* `CONTINUATION_NOT_AVAILABLE`: Provider adapter does not support continuation.
* `RECOVERY_FAILED`: Session recovery deadline expired without restoring authoritative state.
* `EVENT_QUEUE_OVERFLOW`: Session event storage exceeds `max_queued_events`.
* `EVENT_HISTORY_EXPIRED`: Requested sequence in `GET_EVENTS` has already been evicted from history.

# 28. Session identity

A session has a stable immutable:

```text
session_id
```

The following properties are mutable:

```text
provider
tab_id
url
page_generation
state
```

A provider change does not change `session_id`.

A tab change does not change `session_id`.

A browser actor replacement (e.g. JSWindowActor) does not change `session_id`.

---

# 29. Session states

The complete session state set is:

```text
CREATED
PREPARING
READY
BUSY
AUTH_REQUIRED
RATE_LIMITED
RECOVERING
RETRYING
FAILED
CLOSED
```

---

# 30. Session arbiter

Each session MUST have a serialized arbiter.

The arbiter is responsible for:

* prompt reservation;
* prompt terminal commits;
* cancellation commits;
* timeout commits;
* retry transitions;
* recovery transitions;
* page-generation changes;
* event sequence allocation;
* session state transitions.

Operations affecting the same session MUST be serialized.

Read-only queries MAY execute concurrently, but MUST observe a consistent committed session snapshot.

---

# 31. Session transition rules

The following transitions are normative:

```text
CREATED -> PREPARING
CREATED -> FAILED
CREATED -> CLOSED

PREPARING -> READY
PREPARING -> AUTH_REQUIRED
PREPARING -> RATE_LIMITED
PREPARING -> RETRYING
PREPARING -> RECOVERING
PREPARING -> FAILED
PREPARING -> CLOSED

READY -> BUSY
READY -> PREPARING
READY -> AUTH_REQUIRED
READY -> RATE_LIMITED
READY -> RECOVERING
READY -> FAILED
READY -> CLOSED

BUSY -> READY
BUSY -> RETRYING
BUSY -> AUTH_REQUIRED
BUSY -> RATE_LIMITED
BUSY -> RECOVERING
BUSY -> FAILED
BUSY -> CLOSED

AUTH_REQUIRED -> PREPARING
AUTH_REQUIRED -> FAILED
AUTH_REQUIRED -> CLOSED

RATE_LIMITED -> PREPARING
RATE_LIMITED -> FAILED
RATE_LIMITED -> CLOSED

RECOVERING -> READY
RECOVERING -> BUSY
RECOVERING -> RETRYING
RECOVERING -> FAILED
RECOVERING -> CLOSED

RETRYING -> BUSY
RETRYING -> PREPARING
RETRYING -> FAILED
RETRYING -> CLOSED

FAILED -> PREPARING
FAILED -> CLOSED

CLOSED -> [no normal transition]
```

`RESET_SESSION` from any non-CLOSED state moves the session into `PREPARING`.

`RESET_SESSION` from `CLOSED` MUST reject with:

```text
SESSION_CLOSED
```

# 32. RESET_SESSION

`RESET_SESSION` is a session-scoped command.

Header:

```text
request_uuid = new client command UUID
session_uuid = target session UUID
sequence = null
```

Request payload:

```json
{
  "options": {}
}
```

Response payload:

```json
{
  "success": true,
  "session_id": "uuid",
  "state": "PREPARING"
}
```

RESET_SESSION MUST:

1. stop provider activity where possible;
2. invalidate stale page actors;
3. invalidate stale asynchronous operations;
4. increment `page_generation`;
5. preserve the session ID;
6. preserve the session event sequence;
7. transition through `PREPARING`.

The operation MUST NOT reset:

```text
sequence
session_id
```

---

# 33. Page generation

`page_generation` is a uint64-string.

It identifies the current browser/page actor generation for the session.

It MUST increment on significant navigation, document replacement, or actor replacement as defined by the gateway.

It MUST NOT decrement.

It MUST NOT reset to zero during `RESET_SESSION`.

If increment would exceed:

```text
18446744073709551615
```

the session MUST fail with:

```text
PAGE_GENERATION_OVERFLOW
```

---

# 34. Session readiness

A session is READY only when all required evidence has been established:

* target tab exists;
* correct provider context exists;
* provider adapter is usable;
* page generation is current;
* provider input is discoverable;
* provider authentication state is acceptable;
* no conflicting active prompt exists.

Readiness MUST NOT be inferred solely from tab existence.

# 48. Prompt model

A session permits at most one active prompt.

Prompt states are:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
CANCELLING
COMPLETED
FAILED
CANCELLED
```

`ACCEPTED` is a command-response result state only.

# 49. PROMPT

PROMPT is a session-scoped command.

Header:

```text
request_uuid = new client command UUID (prompt_request_id)
session_uuid = target session UUID
sequence = null
```

Request payload:

```json
{
  "prompt": "exact prompt text",
  "options": {
    "timeout_ms": "0",
    "auto_continue": false,
    "max_continuations": 8,
    "force_focus": false,
    "simulate_enter": false,
    "_extensions": {}
  }

```

## 49.1 Prompt text

The prompt string is opaque.

After JSON decoding, the exact Unicode string MUST be preserved without trimming, normalization, or modification.

---

# 50. Prompt options

## 50.1 timeout_ms

`uint64-string`. `0 <= timeout_ms <= 86400000` (max 24 hours).

```text
"0" = no prompt timeout
```

A nonzero timeout begins when the prompt acceptance commit occurs.

## 50.2 auto_continue

Default: `false`.

## 50.3 max_continuations

uint32. Range: `0 .. 1024`.

## 50.4 force_focus

Default: `false`. When true, failure to verify focus causes `INPUT_VERIFICATION_FAILED`.

## 50.5 simulate_enter

Default: `false`. When true, adapter uses keyboard Enter after exact input verification.

# 51. Prompt admission

The prompt admission process is atomic:

```text
READY
  |
  +-- reserve prompt
  |
  v
BUSY
  |
  v
PENDING
```

Two concurrent PROMPT commands against a READY session produce exactly one reservation; the other receives `SESSION_BUSY`.

---

# 52. PROMPT response

A successful PROMPT command returns:

```json
{
  "success": true,
  "command_state": "ACCEPTED",
  "prompt_state": "PENDING"
}
```

---

# 53. Prompt acceptance and timeout

A prompt timeout clock begins at acceptance commit.

A timeout that commits before terminal completion transitions the prompt to `FAILED` with error `PROMPT_TIMEOUT`.

Once terminally failed, the prompt cannot reopen.

---

# 54. Submission

The prompt transitions:

```text
PENDING -> SUBMITTING
```

Submission is complete only after positive evidence establishes provider acceptance.

---

# 55. Provider evidence

A provider adapter MUST define evidence for input readiness, submission, generation, cessation, and errors.

Absence of new DOM activity is not sufficient proof of cessation without an authoritative invariant.

# 62. Revision handling

For a given `message_id`:

* `revision < expected`: stale or duplicate; discard.
* `revision = expected`: accept.
* `revision > expected`: revision gap; prompt fails with `REVISION_GAP` (`partial = true`).

# 64. Continuation

Continuation lifecycle:

```text
GENERATING -> WAITING_CONTINUATION
```

A continuation does not create a new prompt.

# 65. CONTINUATION_REQUIRED

Payload:

```json
{
  "prompt_request_id": "uuid",
  "continuation_count": 3,
  "max_continuations": 8,
  "page_generation": "7"
}
```

### Continuation Count Rules:

1. `continuation_count` begins at `0` for each new prompt.
2. In `CONTINUATION_REQUIRED`, `continuation_count` indicates the number of continuation operations already performed and submitted for this prompt.
3. If `continuation_count >= max_continuations` (or if `max_continuations = 0`), the gateway MUST NOT emit `CONTINUATION_REQUIRED`. It MUST immediately fail: `CONTINUATION_LIMIT_REACHED` (`partial = true`).

# 69. GENERATION_COMPLETED

Single-message form:

```json
{
  "prompt_request_id": "uuid",
  "message_id": "uuid",
  "revision": "12",
  "response": "complete response",
  "page_generation": "7"
}
```

Multi-message form:

```json
{
  "prompt_request_id": "uuid",
  "messages": [
    {
      "message_id": "uuid",
      "revision": "3",
      "response": "first message"
    },
    {
      "message_id": "uuid",
      "revision": "8",
      "response": "second message"
    }
  ],
  "page_generation": "7"
}
```

### Revision Equality Invariant:

In single-message completion, `revision` MUST strictly equal the last committed revision for that message.

In multi-message completion, each `message.revision` MUST strictly equal that message's last committed revision.

An adapter MUST NOT emit a completion snapshot that skips uncommitted delta revisions.

`partial` MUST NOT appear in GENERATION_COMPLETED.

# 72. Cancellation

CANCEL_PROMPT is a session-scoped command valid for any nonterminal prompt state:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
RECOVERING
RETRYING
```

Header:

```text
request_uuid = new client command UUID
session_uuid = target session UUID
sequence = null
```

Request payload:

```json
{
  "prompt_request_id": "uuid"
}
```

Accepted cancellation moves the prompt to `CANCELLING`.

Command response:

```json
{
  "success": true,
  "command_state": "ACCEPTED"
}
```

If the prompt is already terminal, CANCEL_PROMPT fails with:

```text
PROMPT_ALREADY_TERMINAL
```

---

# 73. Cancellation evidence

Terminal CANCELLED requires positive provider cessation evidence.

"No new output appeared" alone is insufficient unless backed by an authoritative deadline invariant.

---

# 74. Terminal arbitration

Each prompt has exactly one terminal commit:

```text
COMPLETED
FAILED
CANCELLED
```

The arbiter serializes all terminal candidates. The first valid candidate that commits wins. Once committed, the prompt can never reopen.

---

# 75. Cancellation failure and recovery terminal resolution

If cancellation is accepted by the gateway but provider cessation cannot be immediately verified:

The session transitions to:

```text
RECOVERING
```

while the prompt remains in the nonterminal state:

```text
CANCELLING
```

### Recovery Resolution Rules:

1. If recovery establishes that provider cessation succeeded:
   ```text
   prompt:  CANCELLING -> CANCELLED
   session: RECOVERING -> READY
   ```
2. If recovery establishes that the provider completed generation before cancellation took effect:
   ```text
   prompt:  CANCELLING -> COMPLETED
   session: RECOVERING -> READY
   ```
3. If recovery cannot establish authoritative state or the recovery deadline expires:
   ```text
   prompt:  CANCELLING -> FAILED (error: RECOVERY_FAILED)
   session: RECOVERING -> FAILED (or PREPARING)
   ```

---

# 76. Navigation drift during active prompt

Navigation drift during active generation invalidates page-dependent operations.

The prompt MUST fail with `NAVIGATION_DRIFT` (`partial = true`), and the session enters `RECOVERING`.

---

# 77. RETRYING

RETRYING exists only for operations whose adapter proves retry safety without duplicating external actions.

Speculative replay of ambiguous submissions is forbidden.

---

# 78. RETRYING transitions

With active prompt:

```text
BUSY -> RETRYING
RETRYING -> BUSY
```

Without active prompt:

```text
PREPARING -> RETRYING
RETRYING -> PREPARING
```

If retry fails: `RETRYING -> FAILED`.

---

# 79. Prompt resumability

A prompt is resumable only when:

1. provider submission state is known;
2. provider-side operation is attributable to the prompt;
3. page generation is validated;
4. continuation will not duplicate external execution.

---

# 80. Response size limit

If accumulated response exceeds `max_response_size`, the prompt fails with `RESPONSE_TOO_LARGE` (`partial = true`).

Existing committed content is preserved. The session enters `RECOVERING`.

# 101. Keepalive timing and liveness

When `keepalive.enabled` is true:

1. `interval_ms` MUST be strictly less than `idle_timeout_ms`.
2. When the connection has been outbound-idle for `interval_ms`, the gateway sends `PONG`.
3. Valid authenticated inbound frames reset the peer liveness timer.
4. An `ERROR` frame generated by invalid traffic does not constitute positive liveness and MUST NOT reset an expired liveness timer.
5. If no frame arrives from the peer within `idle_timeout_ms`, the connection MUST close.


# 164. Security invariants

Guarantees:

```text
S01 malformed frames do not reach provider logic
S02 unauthenticated commands do not reach session logic

S04 stale browser results are fenced
S05 stale provider results are fenced
S06 duplicated non-idempotent actions are not replayed
S07 authentication proofs are compared in constant time
S08 authentication nonces are cryptographically random

S10 authentication secrets are never emitted in diagnostics
S11 provider credentials are never transported as GARP prompt content
S12 unknown extension flags are rejected
```

# 165. Determinism invariants

Arbiter defines commit ordering. Timestamps are informational. Timeouts use monotonic clocks. Replay snapshots are atomic. Eviction is sequence-based. Feature ordering is raw UTF-8 byte ordering.

---

# 166. Failure philosophy

Fail-closed: when authoritative state cannot be proven, implementation MUST transition to explicit error or recovery.

---

# 167. Provider adapter contract

Adapter must expose authoritative evidence for all states and cessation; no guessing permitted.

---

# 168. Browser actor replacement

Actor replacement increments `page_generation`. Stale callbacks cannot mutate new generations.

---

# 169. Process restart

Session/event history MAY be lost; authentication replay protection MUST NOT be lost while secret remains active.

# 177. Final normative statement

GARP/1.19 defines a deterministic, authenticated, fenced browser AI gateway protocol.

Its fundamental contract is:

```text
authenticate
    ↓
negotiate
    ↓
identify session
    ↓
establish browser/provider state
    ↓
reserve exactly one prompt
    ↓
verify input
    ↓
verify submission
    ↓
observe generation
    ↓
enforce message and revision order
    ↓
handle continuation explicitly
    ↓
handle cancellation explicitly
    ↓
commit exactly one terminal outcome
    ↓
retain/replay committed state where supported
```

At every stage, uncertainty is represented explicitly.

No implementation may convert uncertainty into an assumed successful provider action.
