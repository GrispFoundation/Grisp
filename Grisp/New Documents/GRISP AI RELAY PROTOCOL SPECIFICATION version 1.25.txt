# GARP/1.25

## Gateway AI Runtime Protocol

### Protocol Specification

### Freeze Candidate

**Status:** Normative
**Version:** 1.25
**Protocol Identifier:** `GARP/1.25`
**Wire Version:** `0x00`
**Document Language:** English
**Encoding:** UTF-8
**Transport:** Reliable byte stream, normally TCP
**Security Model:** Mutual challenge-response using a deployment-provisioned shared secret
**Primary Purpose:** Deterministic transport and browser-session boundary between an AI runtime and a browser-based AI gateway

---

# 1. Scope

## 1.1 Purpose

GARP defines the transport, authentication, browser-session, provider-adapter, generation-event, cancellation, recovery, and optional replay interfaces between an external AI runtime and a browser gateway.

GARP is a transport and browser-session protocol.

GARP does not define:

* AI quality scoring.
* Artifact acceptance.
* GRISP compilation semantics.
* GRISP runtime semantics.
* Policy approval semantics.
* Human approval semantics.
* Provider-specific credential acquisition.
* Provider-specific internal implementation details.

## 1.2 Architectural role

The intended architecture is:

```text
GRISP / AI Runtime
        |
        v
      GARP
        |
        v
Browser Gateway (e.g. Firefox)
        |
        v
Provider Adapter
        |
        v
AI Provider
```

The provider adapter is the sole component responsible for translating provider-specific browser behavior into the provider-independent GARP model.

## 1.3 Design principles

Implementations MUST be:

* deterministic where the protocol defines deterministic behavior;
* fail-closed on malformed or ambiguous input;
* explicit about state;
* explicit about evidence;
* explicit about request and session identity;
* resistant to stale browser actors and stale provider observations;
* resistant to duplicate execution;
* resistant to replay of authentication messages;
* safe against partial browser failures;
* independent of provider-specific selectors at the protocol layer.

In addition:

* provider observations MUST be treated as evidence, not as authority merely because a provider reports a state flag;
* response ownership MUST be established relative to a pre-submission session baseline;
* a terminal observation MUST NOT automatically constitute terminal completion;
* terminal completion MUST be committed only after the applicable terminal stability requirements have been satisfied;
* stale observations MUST NOT be permitted to create new protocol state.

# 3. Protocol identity

## 3.1 Canonical protocol name

The only canonical protocol name is:

```text
Gateway AI Runtime Protocol
```

The canonical acronym is:

```text
GARP
```

The canonical semantic protocol identifier is:

```text
GARP/1.25
```

## 3.2 Wire version

The wire version is:

```text
0x00
```

`0x00` is the only wire version defined by GARP/1.25.

The semantic protocol version is independent of the wire version.

## 3.3 Identity scope and artifact naming

The protocol distinguishes between:

1. **Protocol Identity:** The protocol defined herein is strictly identified as `GARP` with semantic version `GARP/1.25`.
2. **Artifact Identity:** Authoritative normative specification artifacts MUST use `GARP` and `GARP/1.25`.
3. **Implementation Identity:** Software projects, daemon executables, client libraries, or host applications implementing GARP MAY use independent product or project names without affecting protocol conformance.

# 4. Transport

## 4.1 Transport properties

The transport MUST provide:

* ordered bytes;
* reliable delivery semantics;
* connection-oriented behavior;
* explicit connection closure.

TCP is the reference transport.

## 4.2 TLS

For non-loopback operation, implementations MUST use TLS 1.2 or later.

For loopback operation, TLS MAY be omitted when the host-operating-system security boundary protects the listener adequately.

## 4.3 Local binding

A gateway MAY bind only to loopback:

```text
127.0.0.1
::1
```

A gateway MUST NOT expose an unauthenticated GARP listener on a non-loopback interface.

# 5. Byte order

All multibyte integer fields in the binary header are encoded big-endian.

For example:

```text
0x000000A7
```

is encoded:

```text
00 00 00 A7
```

# 6. Frame format

Every GARP frame consists of a fixed 48-byte header followed by the frame payload.

```text
+----------------------+----------------+
| Offset               | Size           |
+----------------------+----------------+
| magic                | 4              |
| wire_version         | 1              |
| flags                | 1              |
| header_len           | 2              |
| payload_len          | 4              |
| message_type         | 2              |
| reserved             | 2              |
| request_uuid         | 16             |
| session_uuid         | 16             |
| payload              | payload_len    |
+----------------------+----------------+
```

The header is exactly:

```text
48 bytes
```

### Terminology: Frame Payload vs Envelope Payload

To avoid ambiguity, GARP distinguishes between:

1. **Frame Payload:** The raw byte sequence of length `payload_len` immediately following the fixed 48-byte binary header. In base GARP, the frame payload is the serialized UTF-8 JSON Common Envelope.
2. **Envelope Payload:** The inner JSON object stored in the `"payload"` member of the Common Envelope, whose schema is specific to the message type.

## 6.1 Magic

Offset: `0`, Length: `4`, Value: `GARP`, ASCII bytes:

```text
47 41 52 50
```

Any other value MUST cause immediate frame rejection.

## 6.2 Wire version

Offset: `4`, Length: `1`, Required value:

```text
00
```

Any unsupported wire version MUST produce `UNSUPPORTED_WIRE_VERSION` and MUST NOT be interpreted using a different framing rule.

## 6.3 Flags

Offset: `5`, Length: `1`.

Base GARP/1.25 requires:

```text
flags = 0
```

unless a negotiated extension explicitly defines a flag.

Unknown or unnegotiated flag bits MUST cause `UNSUPPORTED_FEATURE`.

## 6.4 Header length

Offset: `6`, Length: `2`, Required value:

```text
48
```

encoded:

```text
00 30
```

The field is attacker-controlled input and MUST be validated before the implementation proceeds. A value other than 48 MUST cause frame rejection.

## 6.5 Payload length

Offset: `8`, Length: `4`.

Unsigned 32-bit integer specifying the exact byte length of the frame payload.

Wire constraints:

```text
0 <= payload_len <= 4294967295
```

The receiver MUST validate the payload length against the currently applicable limit before allocating storage for the payload.

Two distinct limits exist and MUST NOT be conflated:

1. **Handshake limit** (`handshake_limit`) applies to every frame exchanged while the receiving peer has not yet successfully received and validated the peer's `CAPABILITIES` message.

```text
handshake_limit = 1048576
```

2. **Application limit** (`application_limit`) applies to a frame only after the receiving peer has itself successfully received and validated the peer's `CAPABILITIES` message:

```text
application_limit =
    min(advertised_max_payload_bytes, 4294967295)
```

For any received frame:

```text
effective_limit =
    handshake_limit
        if the receiver has not yet successfully received
        and validated the peer's CAPABILITIES

    application_limit
        otherwise
```

The receiver MUST apply this rule independently to each transport direction.

No implementation may allocate unbounded memory based solely on an attacker-controlled payload length.

## 6.6 Message type

Offset: `12`, Length: `2`.

Unsigned big-endian message code.

## 6.7 Reserved

Offset: `14`, Length: `2`.

Required value:

```text
0
```

encoded:

```text
00 00
```

Any nonzero value MUST cause `INVALID_ARGUMENT`.

## 6.8 Request UUID

Offset: `16`, Length: `16`.

Raw UUID bytes.

Nil UUID:

```text
00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00
```

## 6.9 Session UUID

Offset: `32`, Length: `16`.

Raw session UUID.

---

# 7. UUID encoding

## 7.1 Binary encoding

UUIDs are encoded as 16 raw bytes in RFC-style network byte order.

## 7.2 JSON encoding

UUID-bearing envelope fields are always present.

```json
"request_id": "uuid"
"session_id": "uuid"
```

or:

```json
"request_id": null
"session_id": null
```

A JSON `null` in an envelope identity field means the corresponding binary UUID field is all zero.

## 7.3 Application objects

Application-level objects MAY use the string representation of the nil UUID:

```text
00000000-0000-0000-0000-000000000000
```

This is distinct from the envelope identity representation.

## 7.4 UUID generation

Client-created request identifiers SHOULD be generated using a cryptographically secure random source and SHOULD use UUID version 4 semantics.

---

# 8. Validation order

A receiver MUST validate a frame in this order:

1. fixed header availability;
2. magic;
3. wire version;
4. header length;
5. payload length against applicable limit;
6. flags;
7. reserved field;
8. message type;
9. payload byte acquisition;
10. payload encoding;
11. JSON syntax;
12. duplicate JSON member detection;
13. common envelope member presence and types;
14. header-to-envelope identity and message-type binding;
15. message schema;
16. connection and authentication state;
17. request identity and deduplication;
18. session identity;
19. target identity;
20. state transition and provider semantics.

An implementation MAY perform additional checks earlier when the result is equivalent and deterministic.

---

# 9. JSON representation

## 9.1 Encoding

All JSON payloads MUST be UTF-8.

## 9.2 Duplicate object keys

Duplicate object member names MUST be rejected.

An implementation MUST NOT silently select first-key or last-key semantics.

## 9.3 Closed objects

All base GARP message and payload objects are closed unless explicitly declared open.

Unknown members in a closed object MUST cause `INVALID_ARGUMENT`.

Unknown extension members are permitted only through an explicitly declared `_extensions` object.

## 9.4 Open extension object

In base GARP, the `_extensions` object is permitted only within `PROMPT.options`.

Its serialized size remains bounded by the enclosing frame and the applicable `max_payload_bytes`.

When a canonical byte size is required for deterministic size checking, RFC 8785 JCS semantics MUST be used for that size calculation only.

---

# 10. JSON integer types and bounds

JavaScript number precision MUST NOT be relied upon for protocol `uint64` values.

## 10.1 uint64-string

Every protocol field defined as `uint64` in JSON MUST be encoded as a decimal string matching:

```text
^(0|[1-9][0-9]{0,19})$
```

and representing no greater than:

```text
18446744073709551615
```

## 10.2 uint32

Fields defined as `uint32` MAY be encoded as JSON numbers.

Range:

```text
0 .. 4294967295
```

## 10.3 Booleans

Booleans MUST use JSON `true` or `false`.

Strings MUST NOT be used as boolean substitutes in base schemas.

## 10.4 Protocol string bounds

All string fields in base schemas have defined byte-length bounds:

* `provider`: 1 .. 64 bytes
* `tab_id`: 1 .. 64 bytes
* `actor_instance`: 1 .. 64 bytes
* `code`: 1 .. 64 bytes
* `strategy`: 1 .. 64 bytes
* `title`: 0 .. 512 bytes
* `message`: 0 .. 1024 bytes
* `url`: 1 .. 4096 bytes

A string exceeding its defined bound MUST be rejected with `INVALID_ARGUMENT`.

## 10.5 Protocol duration bounds

All duration and timeout fields represented as uint64-strings in milliseconds are bounded:

* `timeout_ms`: `0 .. 86400000`
* `continuation_wait_ms`: `0 .. 864000000`
* `recovery_deadline_ms`: `0 .. 864000000`
* `retry_after_ms`: `0 .. 864000000`
* `idle_timeout_ms`: `0 .. 864000000`
* `interval_ms`: `0 .. 864000000`
* `response_retention_ms`: `0 .. 864000000`

A duration exceeding its bound MUST be rejected with `INVALID_ARGUMENT`.

# 11. Common envelope

Every JSON message uses the following structure:

```json
{
  "garp": "1.25",
  "type": "MESSAGE_TYPE",
  "request_id": null,
  "session_id": null,
  "timestamp": "2026-01-01T00:00:00.000Z",
  "sequence": null,
  "payload": {}
}
```

## 11.1 Required members

Always present:

```text
garp
type
request_id
session_id
timestamp
sequence
payload
```

`sequence` is always present as either a uint64-string or null.

## 11.2 garp

Required value:

```text
1.25
```

## 11.3 type

ASCII uppercase registry name.

## 11.4 request_id

For a command issued by a client, this is the unique command identifier.

For a `RESPONSE` or command-correlated `ERROR`, it identifies the originating command request ID.

For handshake correlation messages (`HELLO_CHALLENGE`, `HELLO_AUTH`, `HELLO_ACK`), it MAY equal the initiating `HELLO` request ID.

For every asynchronous event:

```text
request_id = null
```

and the binary `request_uuid` MUST be nil.

Operation correlation MUST be carried inside the event payload.

For prompt-related asynchronous events, correlation is carried by:

```text
payload.prompt_request_id
```

## 11.5 session_id

Session-scoped messages contain the session UUID.

Connection-scoped messages contain null.

## 11.6 timestamp

Strict RFC 3339 / ISO 8601 UTC timestamp string with millisecond precision:

```text
YYYY-MM-DDTHH:MM:SS.sssZ
```

Timestamp is informational.

Timeouts and deadlines MUST use monotonic clocks.

## 11.7 sequence

Session-scoped events use monotonically increasing sequence values.

Connection-scoped messages, commands, and direct command responses use null.

## 11.8 payload

JSON object whose exact schema is defined by the message type.

# 12. Header-to-envelope identity binding

The binary header and JSON envelope MUST agree.

```text
header.message_type  = registry(type)
header.request_uuid  = envelope.request_id
header.session_uuid  = envelope.session_id
```

A mismatch MUST cause:

```text
HEADER_JSON_MISMATCH
```

An unknown binary message code MUST instead cause:

```text
UNKNOWN_MESSAGE_TYPE
```

# 15. Feature names and modifiers

Feature names MUST match:

```text
^[a-z0-9][a-z0-9._-]{0,127}$
```

The canonical extension name does NOT include any leading punctuation.

A feature MAY be prefixed with `!` during handshake negotiation to declare it required.

The `!` modifier is cryptographically bound into the negotiation transcript and MUST NOT be silently stripped.

Validation MUST occur before canonicalization.

Duplicate canonical feature names MUST be rejected.

Feature names MUST be sorted by raw UTF-8 byte order after validation and without locale-sensitive collation.

---

# 16. Authentication

## 16.1 Purpose

Authentication proves:

* possession of the shared secret;
* knowledge of the current challenge;
* agreement on semantic version;
* agreement on wire version;
* agreement on offered features;
* agreement on final negotiated features;
* peer identity metadata.

## 16.2 Shared secret

The shared secret MUST contain at least 32 raw bytes.

The deployment MUST define how the configured secret is represented.

No implementation may silently reinterpret a configured textual value as hexadecimal when the deployment expects raw bytes, or vice versa.

## 16.3 Normative test secret

The authentication test vector uses exactly these raw ASCII bytes:

```text
0123456789abcdef0123456789abcdef
```

This is 32 bytes.

It is NOT a hexadecimal encoding of 16 bytes.

## 16.4 Client nonce

The client nonce MUST be exactly 16 raw bytes.

It is represented in JSON as unpadded Base64URL.

Padding characters MUST be rejected.

Decode failures MUST cause authentication failure.

## 16.5 Server nonce

The server nonce MUST be exactly 16 raw bytes and use the same JSON representation rules.

## 16.6 Authentication transcript

The proof transcript contains these fields in exactly this order:

```text
domain
client_nonce
server_nonce
selected_semantic_version
selected_wire_version
offered_feature_set
final_feature_set
client_name
client_version
server_name
server_version
```

Every scalar transcript field is encoded:

```text
u32be(byte_length)
raw bytes
```

Feature-list encoding is:

```text
u32be(feature_count)

repeat feature_count times:
    u32be(feature_byte_length)
    feature UTF-8 bytes
```

The negotiated wire version is encoded as:

```text
0x00
```

The selected semantic version is:

```text
1.25
```

## 16.7 Proof

The proof is:

```text
HMAC-SHA256(shared_secret, transcript)
```

The result is exactly 32 raw bytes.

The JSON representation is unpadded Base64URL.

Comparison MUST be constant-time.

## 16.8 Domains

Client-to-server:

```text
GARP/1.25/client-proof
```

Server-to-client:

```text
GARP/1.25/server-proof
```

## 16.9 Negotiation binding

Both the original offered feature set and final negotiated feature set are included in the transcript.

Therefore:

```text
!ext-pong
```

cannot be changed to:

```text
ext-pong
```

without invalidating the proof.

## 16.10 Timestamp

Authentication proofs do not include the timestamp.

Freshness is provided by the nonces.

Header:

```text
request_uuid = client-generated UUID
```

```json
{
  "client_name": "GARPClient",
```

Payload:

```json
{
  "server_name": "GarpGateway",
  "server_version": "1.25.0",
  "selected_version": "1.25",
  "selected_wire_version": "0x00",
```

## 17.3 HELLO_AUTH

Payload:

```json
{
  "client_proof": "BASE64URL"
```

Payload:

```json
  "features": ["!ext-pong"]
}
```

# 18. Request-ID uniqueness and correlation exception

## 18.1 New command IDs

A client-generated command request ID MUST be unique within the connection.

## 18.2 Handshake transaction entry

The entire HELLO handshake sequence:

```text
HELLO
HELLO_CHALLENGE
HELLO_AUTH
HELLO_ACK
```

uses exactly one connection request-ID namespace entry.

That transaction identifier remains the correlation identifier for the complete handshake exchange.

## 18.3 Application responses

A `RESPONSE` or protocol `ERROR` associated with a command uses that command's request ID.

A response MUST NOT be interpreted as a new request.

---

# 19. Replay protection

Authentication replay protection MUST survive gateway process restarts for at least 24 hours.

If replay state is lost:

```text
the gateway MUST NOT continue accepting the affected secret.
```

The affected shared secret MUST be disabled and rotated.

Application session state MAY still be lost on restart unless separately persisted.

## 19.1 Replay key

A practical deterministic replay key is:

```text
SHA-256(transcript_core)
```

where `transcript_core` includes both nonces and all negotiation-binding fields.

---

# 20. Handshake timeout

The default handshake timeout is:

```text
10000 ms
```

measured using a monotonic clock.

If authentication does not complete within the deadline, the connection MUST close.

Error condition:

```text
HANDSHAKE_TIMEOUT
```

# 21. CAPABILITIES

CAPABILITIES is a connection-scoped message.

Header identity:

```text
request_uuid = nil
session_uuid = nil
```

Sequence:

```text
null
```

It is emitted immediately after HELLO_ACK and before application commands are processed.

A gateway MUST emit a new CAPABILITIES event when effective negotiated capabilities materially change.

```json
  "protocol": "1.25",

    "max_response_size": 16777216,

    "max_queued_events": 8192,

    "recovery_deadline_ms": "300000",

    "enabled": true,
```

```text
max_response_size
max_outstanding_requests
max_queued_events
max_event_history_memory_mb
```


Keepalive:


## 22.1 Provider entries

Every provider entry MUST contain:

```json
{
  "id": "deepseek",
  "version": "1.0.0",
  "state": "AVAILABLE",
  "input_strategies": [
    "provider_native_send",
    "keyboard_enter"
  ],
  "capabilities": {
    "streaming": true,
    "cancellation": true,
    "continuation": true,
    "diagnostics": true
  }
}
```

The `capabilities` object is closed and MUST contain exactly:

```text
streaming
cancellation
continuation
diagnostics
```

All are booleans.

Providers MUST be sorted by raw UTF-8 byte order of `id`.

Input strategy arrays MUST use the same ordering.

## 22.2 Extensions

Example:

```json
[
  {
    "name": "ext-pong",
    "version": "1.0"
  }
]
```

Extensions MUST be listed by canonical name without `!`.

## 22.3 Limit breach behaviors

Prompt input exceeding `max_prompt_size`:

```text
INVALID_ARGUMENT
```

Outstanding requests exceeding `max_outstanding_requests`:

```text
OUTSTANDING_REQUEST_LIMIT
```

Response content exceeding `max_response_size`:

```text
RESPONSE_TOO_LARGE
```

Transient generation data exceeding `max_generation_buffer_mb`:

```text
GENERATION_BUFFER_LIMIT
```

Both latter conditions enter terminal arbitration as described in §74.

## 22.4 Capability changes and active prompts

When effective application limits change, the gateway MUST emit CAPABILITIES.

Previously accepted prompts are not invalidated merely because an advertised future limit becomes smaller.

Global safety limits MAY affect active prompts immediately.

When they do, the corresponding terminal failure candidate MUST enter the terminal arbiter.

# 25. Generic RESPONSE

Generic successful response:

```json
{
  "success": true
}
```

Generic failed application response:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable description"
  }
}
```

`success` is REQUIRED in all application RESPONSE payloads.

# 26. Generic ERROR

`ERROR` is a protocol-level error and is not a successful application response.

Payload:

```json
{
  "code": "ERROR_CODE",
  "message": "Human-readable description"
}
```

Optional:

```json
{
  "details": {}
}
```

`details` are bounded by `max_error_details_bytes`.

### ERROR scoping

1. Command-correlated ERROR adopts the originating command IDs.
2. Session-originated asynchronous ERROR has `request_id = null`.
3. Connection-level ERROR has null request and session IDs.

# 28. Session identity

A session has a stable immutable `session_id`.

The following are mutable:

```text
provider
tab_id
url
page_generation
state
```

A provider change does not change the session ID.

A tab change does not change the session ID.

An actor replacement does not change the session ID.

# 29. Session states

```text
CREATED
PREPARING
READY
BUSY
AUTH_REQUIRED
RATE_LIMITED
RECOVERING
RETRYING
FAILED
CLOSED
```

# 30. Session arbiter

Each session MUST have a serialized arbiter.

The arbiter is responsible for:

* prompt reservation;
* prompt terminal commits;
* cancellation commits;
* timeout commits;
* retry transitions;
* recovery transitions;
* page-generation changes;
* provider-context invalidation transitions;
* event sequence allocation;
* session state transitions.

Operations affecting the same session MUST be serialized.

Read-only queries MAY execute concurrently, but MUST observe a consistent committed session snapshot.

The following transitions are normative:

```text

PREPARING -> FAILED

READY -> RECOVERING
READY -> FAILED
READY -> CLOSED

BUSY -> READY
BUSY -> PREPARING
BUSY -> RETRYING
BUSY -> AUTH_REQUIRED
BUSY -> RATE_LIMITED
BUSY -> RECOVERING
```

---

# 32. RESET_SESSION

RESET_SESSION is session-scoped.

It MUST:

1. stop provider activity where possible;
2. invalidate stale actors;
3. invalidate stale asynchronous operations;
4. increment `page_generation`;
5. preserve `session_id`;
6. preserve event sequence;
7. transition through `PREPARING`.

---

# 33. Page generation

`page_generation` is a uint64-string.

It identifies the current browser/page actor generation.

It MUST increment on significant navigation, document replacement, or top-level actor replacement.

It MUST NOT decrement.

It MUST NOT reset to zero during RESET_SESSION.

Overflow produces:

```text
PAGE_GENERATION_OVERFLOW
```

---

# 34. Session readiness

A session is READY only when all required evidence has been established:

* target tab exists;
* provider context exists;
* provider adapter is usable;
* page generation is current;
* provider input is discoverable;
* provider authentication state is acceptable;
* no conflicting active prompt exists.

Readiness MUST NOT be inferred solely from tab existence.

# 48. Prompt model

A session permits at most one active nonterminal prompt.

Prompt states are:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
CANCELLING
COMPLETED
FAILED
CANCELLED
```

`ACCEPTED` is a command-response result state only.

# 49. PROMPT and pre-submission snapshot

PROMPT uses:

```text
request_uuid = new client command UUID
session_uuid = target session UUID
```

The prompt request ID is:

```text
prompt_request_id = PROMPT.request_id
```

Before provider submission, the gateway MUST capture an immutable **pre-submission snapshot**.

The snapshot MUST establish, at minimum:

```text
session_id
provider
tab_id
page_generation
conversation identity when available
last authoritative assistant message identity when available
last authoritative assistant message count when available
last authoritative assistant message content when available
```

The snapshot defines the response-identity boundary for this prompt.

The snapshot MUST NOT be modified as a consequence of later polling or observation.

### 49.1 Snapshot versus observation state

The gateway MUST distinguish immutable baseline state from mutable observation state.

Conceptually:

```text
baseline_message_count
baseline_message_text
baseline_message_identity
```

are immutable for the lifetime of the prompt, while:

```text
last_observed_message_count
last_observed_message_text
last_observed_message_identity
```

are updated as new provider observations arrive.

The existence of mutable observations MUST NOT redefine the original prompt boundary.

The prompt transitions:


# 55. Provider evidence

A provider adapter MUST define authoritative evidence for:

* input readiness;
* submission;
* response identity;
* generation;
* cessation;
* continuation;
* errors.

The following are explicitly insufficient by themselves:

* lack of new DOM activity;
* a provider-specific boolean flag without corroborating identity;
* `done = true` by itself;
* `streaming = false` by itself;
* a repeated observation of an old message;
* observation of the newest visible message without establishing its post-submission ownership.

# 58. Message boundary and response identity

## 58.1 Logical message boundary

Priority:

1. provider-explicit logical message boundary;
2. otherwise one logical assistant message per prompt.

A continuation MUST NOT itself create a new logical message.

## 58.2 Post-submission response rule

A provider observation MUST NOT be attributed to the current prompt merely because it was observed after `PROMPT` submission.

The gateway MUST determine whether the observed response existed within the pre-submission snapshot.

A response is attributable to the current prompt only when it is established as a **post-baseline response candidate**.

## 58.3 Preferred identity mechanism

Where the provider supplies stable message IDs, the gateway MUST use them to distinguish pre-existing messages from post-submission messages.

A message ID belonging to the pre-submission baseline MUST NOT be treated as a newly generated message for the current prompt merely because that message is returned again by a later full-conversation observation.

## 58.4 Baseline-count fallback

When stable message identity is unavailable but the provider exposes a deterministic ordered message collection, the gateway MUST establish the pre-submission message boundary using the captured baseline count.

A later observation is eligible as a new response only from the post-baseline portion of that collection.

Conceptually:

```text
observed_messages =
    all_observed_messages[baseline_message_count .. end]
```

The baseline count is immutable.

## 58.5 Baseline-content fallback

When neither stable identity nor a reliable ordered count exists, content comparison MAY be used only as an additional evidence source.

Content equality alone MUST NOT be treated as proof that a response belongs to a new prompt.

## 58.6 Existing messages are not new responses

If an observation contains only messages already contained in the immutable pre-submission baseline:

```text
no response has been identified for the current prompt
```

The gateway MUST NOT emit:

```text
GENERATION_STARTED
GENERATION_DELTA
GENERATION_COMPLETED
```

for that prompt solely on the basis of those stale observations.

## 58.7 Response identity precedes generation start

The gateway MUST NOT emit `GENERATION_STARTED` for a prompt until it has identified at least one response message attributable to that prompt according to this section.

Provider-specific generation-start indicators MAY be recorded as diagnostics or adapter state, but they MUST NOT independently establish response ownership.

---

# 59. message_id

The gateway generates `message_id`, unique within the prompt and stable for the message lifetime.

When a provider exposes a usable stable message identity, the gateway MAY preserve that identity subject to the protocol's gateway-generated uniqueness requirements.

```json
  "prompt_request_id": "uuid",

  "revision": "0",
  "page_generation": "7"
}
```

# 62. Revision handling

For a given message:

```text
revision < expected
```

is stale or duplicate and MUST be discarded.

```text
revision = expected
```

is accepted.

```text
revision > expected
```

is a revision gap.

The prompt MUST then submit:

```text
REVISION_GAP
```

to terminal arbitration.

Multiple consecutive progress events MAY have identical payload state.

A progress event MUST NOT be interpreted as proof that generation is still changing.

# 69. GENERATION_COMPLETED and terminal stability

## 69.1 Terminal candidate

A provider observation MAY produce a **terminal candidate**.

A terminal candidate is not yet a terminal commit.

The minimum terminal candidate conditions are:

```text
prompt has an identified response
AND
done = true
AND
streaming = false
AND
continuation_required != true
AND
message_count > 0
AND
response content is non-empty
```

Equivalent provider-specific evidence MAY be used when the adapter exposes a semantically stronger representation.

## 69.2 Provider terminal flags are evidence

The following provider observations are not, by themselves, authoritative completion:

```text
done = true
streaming = false
authoritative_completion = true
provider_idle = true
```

They are terminal-candidate evidence.

The gateway remains responsible for response identity, fencing, stability, and terminal arbitration.

## 69.3 Terminal stability requirement

A terminal candidate MUST be confirmed by at least two consecutive observations in which:

1. the prompt remains the active prompt;
2. fencing remains valid;
3. terminal conditions remain true;
4. the observed response message count is unchanged;
5. the observed response content is unchanged.

Conceptually:

```text
Observation N:
    terminal candidate
    count = C
    text = T

Observation N+1:
    terminal candidate
    count = C
    text = T

=> stable terminal candidate
```

Only then MAY the gateway submit the candidate as:

```text
COMPLETED
```

to the terminal arbiter.

An implementation MAY use a stronger stability policy, but MUST NOT use fewer than two qualifying consecutive observations as its base terminal confirmation policy.

## 69.4 Stability reset

Terminal stability MUST reset to zero whenever any of the following occurs:

* `done` becomes false;
* `streaming` becomes true;
* `continuation_required` becomes true;
* message count changes;
* observed response content changes;
* response identity changes;
* fencing changes or becomes invalid.

Conceptually:

```text
terminal
terminal
        => stable = 2

terminal
nonterminal
        => stable = 0
```

## 69.5 Stable completion does not bypass fencing

Even when terminal stability has been satisfied, completion evidence MUST still pass:

* session fencing;
* provider identity fencing;
* page-generation fencing;
* actor-instance fencing;
* prompt-request fencing;
* message identity validation.

## 69.6 Completion content

Single-message form:

```json
{
  "prompt_request_id": "uuid",
  "message_id": "uuid",
  "revision": "12",
  "response": "complete response",
  "page_generation": "7"
}
```

Multi-message form:

```json
{
  "prompt_request_id": "uuid",
  "messages": [
    {
      "message_id": "uuid",
      "revision": "3",
      "response": "first message"
    },
    {
      "message_id": "uuid",
      "revision": "8",
      "response": "second message"
    }
  ],
  "page_generation": "7"
}
```

When exactly one tracked response message exists, the gateway SHOULD use the single-message form.

When more than one tracked response message exists, the gateway uses `messages`.

## 69.7 Completion snapshot invariant

The completion response MUST equal the content defined by the accepted revision sequence.

A completion snapshot MUST NOT contain stale pre-prompt messages.

A completion snapshot MUST NOT include historical assistant messages solely because the provider returned the full conversation view.

`partial` MUST NOT appear in GENERATION_COMPLETED.

```text

```

or:

```text

```

according to the same single-message/multi-message rules as completion.

The `partial` semantics are defined by §76.

Failures MUST enter the terminal arbiter.

# 71. GENERATION_CANCELLED

Cancellation requires verified cessation.

The terminal payload MUST represent the latest committed response snapshot available for the winning cancellation candidate.

`cancel_verified` MUST be true.

# 72. Cancellation

CANCEL_PROMPT remains valid for:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
```

and transitions the prompt to:

```text
CANCELLING
```

A second cancellation while already CANCELLING fails with:

```text
INVALID_MESSAGE_STATE
```

A cancellation against a terminal prompt fails with:

```text
PROMPT_ALREADY_TERMINAL
```

---

# 73. Cancellation evidence

Terminal CANCELLED requires positive provider cessation evidence.

The absence of new output alone is insufficient unless a provider-specific authoritative deadline invariant proves cessation.

Submission success is not cessation evidence.

---

# 74. Terminal arbitration

Each prompt has exactly one terminal commit:

```text
COMPLETED
FAILED
CANCELLED
```

The session arbiter serializes all terminal candidates.

The first valid candidate that commits wins.

Once committed, the prompt can never reopen.

### Terminal candidate sources

The following are candidate sources:

```text
completion
cancellation
timeout
provider failure
navigation drift
provider invalidation
authentication loss
rate limit
revision gap
response-size limit
generation-buffer limit
continuation failure
recovery failure
```

No candidate source automatically bypasses the arbiter.

### Terminal candidates versus terminal commits

A provider observation MUST first produce evidence.

The gateway converts that evidence into a terminal candidate only after validating:

```text
request identity
session identity
provider identity
page generation
actor instance
prompt state
message identity
applicable content rules
```

Only the session arbiter may convert a valid candidate into the actual terminal state.

---

# 75. Cancellation failure and recovery terminal resolution

If cancellation is accepted but provider cessation cannot immediately be proven:

```text
session -> RECOVERING
prompt  -> CANCELLING
```

Recovery evidence enters the same terminal arbitration as ordinary completion and cancellation evidence.

If recovery establishes cessation and cancellation wins:

```text
CANCELLING -> CANCELLED
RECOVERING -> READY
```

If recovery establishes provider completion and completion wins:

```text
CANCELLING -> COMPLETED
RECOVERING -> READY
```

If recovery cannot establish authoritative state before the recovery deadline:

```text
CANCELLING -> FAILED
RECOVERING -> FAILED
```

with:

```text
RECOVERY_FAILED
```

---

# 76. Navigation drift during active prompt

Navigation drift during:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
CANCELLING
```

invalidates page-dependent operations.

The resulting terminal outcome is determined by §74.

The `partial` flag is historical:

```text
partial = true
```

if authoritative response content has ever been committed for the prompt.

Otherwise:

```text
partial = false
```

Once true, `partial` MUST NOT revert to false during that prompt's lifetime.

This remains true even after a `REPLACE` operation produces an empty string.

---

# 77. RETRYING

RETRYING is a session execution state.

It is not a prompt lifecycle state.

Speculative replay of ambiguous submissions is forbidden.

---

# 78. RETRYING transitions

With active prompt:

```text
BUSY -> RETRYING
RETRYING -> BUSY
```

Without active prompt:

```text
PREPARING -> RETRYING
RETRYING -> PREPARING
```

If retry fails:

```text
RETRYING -> FAILED
```

---

# 79. Prompt resumability

A prompt is resumable only when:

1. provider submission state is known;
2. provider-side operation is attributable to the prompt;
3. page generation is validated;
4. continuation or retry cannot duplicate external execution.

---

# 80. Response and generation buffer limits

`max_response_size` and `max_generation_buffer_mb` are distinct.

`max_response_size` limits the semantic response retained for client delivery.

`max_generation_buffer_mb` limits transient internal gateway buffering.

The two limits MUST NOT be conflated.

Both violations enter terminal arbitration.

# 84. Event queue overflow

Event queue overflow is fail-closed.

If session event storage exceeds `max_queued_events`:

```text
EVENT_QUEUE_OVERFLOW
```

is produced and the session transitions to:

```text
FAILED
```

Explicit reset is required before normal operation resumes.

# 85. Session event sequence

All session-scoped asynchronous events have:

```text
session_id != null
request_id = null
sequence = uint64-string
```

Sequence numbers are:

* monotonic;
* unique;
* never reset;
* never reused.

---

# 86. Sequence allocation

First session event:

```text
sequence = "1"
```

Every subsequent session event increments by exactly one.

Overflow causes:

```text
EVENT_SEQUENCE_OVERFLOW
```

---

# 87. Event ordering

The sequence value defines authoritative event order.

Two events MUST NOT share a sequence number.

Sequence numbers MUST NOT decrease.

---

# 88. Sequence gaps at receiver

Receiving N+1 before N MUST report:

```text
EVENT_SEQUENCE_GAP
```

unless replay is being used through `ext-replay-store`.

# 89. Generation event sequencing

The following consume session sequence values:

```text
SESSION_READY
SESSION_CHANGED
NAVIGATION
NAVIGATION_DRIFT
RECOVERY_STATE
```

# 90. DIAGNOSTIC

Diagnostics are observational.

They MUST NOT alter normative protocol state transitions.

`DIAGNOSTIC` may be used to document:

* stale observations;
* discarded provider messages;
* rejected response identity;
* actor replacement;
* stability reset;
* discarded late continuation;
* terminal arbitration candidates;
* provider ambiguity.

Diagnostic content MUST NOT contain credentials or authentication secrets.

# 91. Actor fencing

Every asynchronous operation whose result may outlive the initiating actor MUST be associated with:

```text
provider
session_id
page_generation
actor_instance
prompt_request_id
```

where `provider` and `prompt_request_id` are nullable only where explicitly permitted by the operation type.

## 91.1 Provider-context operations

Provider-context operations MUST carry a non-null provider identity matching the session's authoritative provider.

Examples include:

* provider readiness;
* provider submission;
* generation;
* cessation;
* completion;
* provider errors;
* authentication state;
* rate limiting.

Evidence with a provider identity different from the session's authoritative provider MUST be discarded as stale evidence.

## 91.2 Non-provider operations

Operations that do not affect provider state MAY use:

```text
provider = null
```

## 91.3 Prompt fencing

Prompt-associated operations MUST carry:

```text
prompt_request_id = active prompt UUID
```

An operation MUST be discarded if its prompt is no longer active or has become terminal.

## 91.4 Page-generation fencing

Every subordinate actor MUST carry the page generation under which it was created.

Results from an old page generation MUST be discarded.

## 91.5 Actor-instance fencing

Every actor has a unique `actor_instance`.

A replacement changes the actor instance.

Late results from the old instance MUST be discarded.

## 91.6 Stale results

A stale result MUST NOT:

* mutate current session state;
* mutate current prompt state;
* create a new response;
* create generation events;
* reset terminal stability;
* commit a terminal outcome.

A diagnostic MAY record the discard.

---

# 92. Actor instance

`actor_instance` is unique for an actor lifetime.

Top-level actor replacement increments `page_generation`.

Subordinate actor replacement changes `actor_instance`.

```text
actor_instance
```

Stale callbacks cannot mutate the current generation.

# 169. Process restart

Session and event history MAY be lost on restart.

Authentication replay protection MUST NOT be lost while the same secret remains active.

# 177. Final normative statement

GARP/1.25 defines a deterministic, authenticated, fenced browser AI gateway protocol.

Its fundamental contract is:

```text
authenticate
    ↓
negotiate
    ↓
identify session
    ↓
establish browser/provider state
    ↓
capture immutable pre-submission baseline
    ↓
reserve exactly one prompt
    ↓
verify input
    ↓
verify submission
    ↓
identify post-baseline response
    ↓
observe generation
    ↓
enforce message and revision order
    ↓
handle continuation explicitly
    ↓
handle cancellation explicitly
    ↓
evaluate terminal candidates
    ↓
confirm terminal stability
    ↓
verify final fencing
    ↓
commit exactly one terminal outcome
    ↓
retain/replay committed state where supported
```

At every stage, uncertainty is represented explicitly.

A provider observation is not automatically authoritative merely because it reports a terminal-looking state.

A previously existing browser message is not a new response merely because it is observed again after a new prompt.

A `done=true` observation is not, by itself, a completed GARP generation.

A `GENERATION_STARTED` event means that the gateway has established current-prompt response identity.

A `GENERATION_COMPLETED` event means that the gateway has established a stable, fenced, post-baseline response and committed the completion through the session arbiter.

No implementation may convert uncertainty into an assumed successful provider action.
