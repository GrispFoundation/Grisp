# GARP/1.16

## Gateway AI Runtime Protocol

### Beta Implementation Freeze Specification

**Protocol name:** Gateway AI Runtime Protocol
**Abbreviation:** GARP
**Semantic protocol version:** `1.16`
**Wire version:** `0x00`
**Status:** Beta Implementation Freeze
**Supersedes:** GARP/1.15

---

# 1. Scope

GARP defines a deterministic protocol boundary between an AI client and a browser-based AI gateway.

GARP provides:

* authenticated transport;
* browser and tab management;
* logical sessions;
* one active prompt per session;
* verified browser input and submission;
* streaming generation observation;
* multi-message responses;
* explicit continuation;
* deterministic cancellation;
* provider and navigation state;
* page-generation fencing;
* bounded recovery;
* persistent event sequencing;
* optional replay;
* optional PONG keepalive;
* explicit protocol diagnostics.

GARP is intended for AI providers whose user interfaces are exposed through browser pages rather than a directly controlled provider API.

Provider pages, DOM state, generated content, browser actors, and adapter observations are untrusted inputs.

The base protocol remains intentionally small. Features that are not required for base correctness MUST be negotiated explicitly as extensions.

# 2. Normative Language

The terms:

* **MUST**
* **MUST NOT**
* **REQUIRED**
* **SHOULD**
* **SHOULD NOT**
* **MAY**

are normative.

# 3. Core Evidence Model

GARP distinguishes four evidence levels:

```text
ATTEMPTED
OBSERVED
VERIFIED
COMMITTED
```

The meanings are:

### ATTEMPTED

Software attempted an operation.

Examples:

```text
click performed
key press issued
DOM setter invoked
submission function called
```

### OBSERVED

A resulting provider/browser condition was observed.

Examples:

```text
input text appears
provider response bubble appears
generation indicator appears
provider error appears
```

### VERIFIED

The observed result satisfies the applicable adapter verification rule.

Examples:

```text
input contains exact requested prompt
provider submission has demonstrable effect
provider generation has definitely started
provider cessation has been established
```

### COMMITTED

The authoritative GARP state machine accepted the verified fact and committed the corresponding protocol state.

Only committed state may determine externally visible terminal protocol outcomes.

---

# 4. No False Success

GARP MUST NOT manufacture success from:

* intention;
* attempted activity;
* ambiguous observation;
* stale state;
* unsupported provider assumptions.

The following progression is mandatory:

```text
ATTEMPTED
    ↓
OBSERVED
    ↓
VERIFIED
    ↓
COMMITTED
```

Not every operation necessarily exposes every intermediate state externally.

---

# 5. Determinism

Externally visible GARP behavior MUST be deterministic for identical:

1. negotiated protocol state;
2. authenticated peer identities;
3. command inputs;
4. session state;
5. provider observations;
6. adapter behavior;
7. retained history.

Implementations MUST NOT depend on unspecified:

* object iteration order;
* locale;
* Unicode normalization;
* concurrent commit timing;
* random selection;
* undocumented provider behavior.

When multiple concurrent operations are possible, the authoritative session arbiter MUST determine the commit order.

---

# 6. Semantic and Wire Versions

GARP semantic version:

```text
1.16
```

Wire version:

```text
0x00
```

These are distinct.

The semantic version identifies protocol meaning, schemas, and state-machine rules.

The wire version identifies the fixed binary framing format.

Wire-compatible does not mean semantically compatible.

---

# 7. Fixed Wire Header

Every GARP base frame contains exactly 48 header bytes.

```text
+---------------------------------------------------------------+
|                         48-byte header                        |
+---------------------------------------------------------------+
|                         payload bytes                         |
+---------------------------------------------------------------+
```

The header layout is:

| Offset | Size | Field        | Encoding      |
| -----: | ---: | ------------ | ------------- |
|      0 |    4 | magic        | ASCII `GARP`  |
|      4 |    1 | wire_version | `0x00`        |
|      5 |    1 | flags        | defined in §9 |
|      6 |    2 | header_len   | BE uint16     |
|      8 |    4 | payload_len  | BE uint32     |
|     12 |    2 | message_type | BE uint16     |
|     14 |    2 | reserved     | MUST be zero  |
|     16 |   16 | request_uuid | raw UUID      |
|     32 |   16 | session_uuid | raw UUID      |

---

# 8. Header Length

Base GARP requires:

```text
header_len = 48
```

A receiver MUST reject any base GARP frame whose `header_len` is not exactly `48`.

Future incompatible header layouts require a future wire version.

The current beta protocol does not define header extension bytes.

---

# 9. Flags

Base GARP defines no flags.

Therefore:

```text
flags = 0x00
```

MUST be used unless a negotiated extension explicitly defines one or more bits.

A non-zero flag is valid only when every corresponding bit is defined by an extension present in the final negotiated feature set.

Unknown or unnegotiated flag bits MUST fail closed.

---

# 10. Reserved Header Field

The `reserved` field MUST equal:

```text
0x0000
```

A non-zero value MUST fail closed.

---

# 11. Payload Length

`payload_len` is the number of payload bytes following the 48-byte header.

The receiver MUST validate the length against the applicable bootstrap or negotiated payload maximum before allocating the payload buffer.

The receiver MUST NOT allocate memory based solely on an attacker-controlled 32-bit length.

---

# 12. Bootstrap Limits

Before `CAPABILITIES` is received, the connection MUST use these bootstrap limits:

```text
max_payload_bytes_default = 1048576
max_extensions_bytes_default = 65536
```

These limits apply at minimum to:

* HELLO;
* HELLO_CHALLENGE;
* HELLO_AUTH;
* HELLO_ACK;
* all other pre-capability protocol traffic.

After authenticated capability negotiation, the effective advertised limits MAY replace the bootstrap limits only when the new limits are equal to or stricter than the bootstrap limits for connection-level handshake traffic.

---

# 13. UUID Representation

UUIDs are exactly 16 bytes.

The binary representation is the 128-bit UUID value encoded most-significant-byte first.

The same byte sequence is used by:

* header UUID fields;
* JSON textual UUID representation after parsing;
* authentication correlation where applicable.

The nil UUID is:

```text
00000000-0000-0000-0000-000000000000
```

---

# 14. JSON UUID Representation

When an envelope UUID field is non-nil, it contains the canonical textual UUID.

When the corresponding binary header UUID is nil, the envelope field MUST be:

```json
null
```

The following are therefore equivalent representations of identity state:

```text
binary nil UUID
```

and:

```json
null
```

A nil UUID MUST NOT be represented by omission.

A nil UUID MUST NOT be represented by the string:

```text
"00000000-0000-0000-0000-000000000000"
```

in base GARP envelope identity fields.

The nil UUID string remains permitted wherever an application-level object explicitly defines a UUID string rather than an envelope identity.

---

# 15. Common JSON Envelope

Every base JSON message has:

```json
{
  "garp": "1.16",
  "type": "PING",
  "request_id": "00000000-0000-0000-0000-000000000001",
  "session_id": null,
  "timestamp": "2026-01-01T00:00:00.000Z",
  "payload": {}
}
```

The envelope fields are:

| Field        | Type         | Requirement                                       |
| ------------ | ------------ | ------------------------------------------------- |
| `garp`       | string       | REQUIRED, exactly `1.16`                          |
| `type`       | string       | REQUIRED, exact uppercase registry name           |
| `request_id` | UUID or null | REQUIRED                                          |
| `session_id` | UUID or null | REQUIRED                                          |
| `timestamp`  | string       | REQUIRED                                          |
| `sequence`   | uint64       | REQUIRED only for session-scoped sequenced events |
| `payload`    | object       | REQUIRED                                          |

`sequence` MUST be omitted from messages that do not define a sequence.

The envelope itself is closed.

---

# 16. Header / Envelope Identity Mapping

The following mappings are mandatory:

```text
header.message_type == registry code of envelope.type

header.request_uuid == envelope.request_id
    after converting both to raw UUID values

header.session_uuid == envelope.session_id
    after converting both to raw UUID values
```

A mismatch MUST fail closed with:

```text
HEADER_JSON_MISMATCH
```

For nil binary UUID:

```text
header UUID = all zero bytes
JSON field = null
```

is the only base envelope representation.

---

# 17. Event Sequence

Session-scoped events contain:

```json
"sequence": 123
```

at the root of the envelope.

Sequence:

* starts at `1`;
* increments by exactly `1`;
* is unique within the session;
* continues across reconnect;
* continues across `RESET_SESSION`;
* does not reset when prompt state changes.

Sequence `0` is reserved.

Connection-scoped messages do not have a sequence.

---

# 18. Timestamp

Senders MUST emit:

```text
YYYY-MM-DDTHH:MM:SS.sssZ
```

with exactly three fractional digits.

Receivers MAY accept zero through three fractional digits.

Receivers MUST reject years outside:

```text
1970..2100
```

Timestamp is informational metadata only.

It does not determine ordering or deadlines.

Timeouts and arbitration use monotonic clocks.

---

# 19. JSON Encoding

Base payloads are UTF-8 JSON.

JSON decoding MAY interpret JSON escape sequences.

After decoding, the resulting application string MUST NOT be silently normalized.

JSON serialization whitespace and key order have no semantic meaning except where this specification explicitly defines a canonical representation for a cryptographic or size calculation.

---

# 20. Unknown Fields

All base objects are explicitly classified.

A **closed** object permits exactly its defined base fields plus `_extensions` when explicitly stated.

An **open** object permits unknown fields subject to the rules of its message definition.

Unknown fields in a closed object MUST fail with:

```text
INVALID_ARGUMENT
```

Unknown fields in an open object MAY be ignored.

---

# 21. `_extensions`

`_extensions` is the reserved extension namespace.

When permitted, `_extensions` MUST be an object.

Base protocol fields MUST NOT be redefined through `_extensions`.

Extension content is bounded by:

```text
max_extensions_bytes
```

The size is measured from the exact UTF-8 byte slice occupied by the `_extensions` JSON member in the received payload, including the member name, colon, value, and syntactic whitespace belonging to that member.

Implementations MUST NOT reserialize `_extensions` to determine its received size.

---

# 22. Validation Order

The authoritative validation order is:

1. frame structure;
2. wire version;
3. header length;
4. payload length against bootstrap/effective limit;
5. flags and reserved header fields;
6. binary message type;
7. payload encoding;
8. JSON syntax;
9. common envelope;
10. message schema;
11. connection/authentication state;
12. request identity;
13. session identity;
14. target identity;
15. state transition;
16. provider semantics.

Unknown binary message types fail at step 6.

Known binary and JSON type disagreement fails at step 9 with:

```text
HEADER_JSON_MISMATCH
```

For unauthenticated protected operations, the implementation MAY terminate the connection immediately after identifying a protocol violation rather than exposing detailed application-schema information.

1. normative requirements;

5. state machine;
6. conformance tests;
7. examples;
8. explanatory prose.

# 26. HELLO

Header:

```text
request_uuid = new non-nil UUID
session_uuid = nil
```

Payload is closed:

```json
{
  "client_name": "GARPClient",
  "client_version": "1.16.0",
  "supported_versions": ["1.16"],
  "supported_wire_versions": ["0x00"],
  "features": [],
  "client_nonce": "..."
}
```

Limits:

| Field                     | Type      | Constraint               |
| ------------------------- | --------- | ------------------------ |
| `client_name`             | string    | 1–128 UTF-8 bytes        |
| `client_version`          | string    | 1–64 UTF-8 bytes         |
| `supported_versions`      | string[]  | 1–32 entries             |
| `supported_wire_versions` | string[]  | 1–32 entries             |
| `features`                | string[]  | 0–64 entries             |
| `client_nonce`            | Base64URL | exactly 16 decoded bytes |

# 28. Feature Validation

Features MUST be validated before canonicalization.

Each feature:

* MUST contain ASCII bytes;
* MUST contain 1–128 bytes after removing an optional leading `!`;
* MUST NOT contain `!` after the optional leading marker;
* MUST NOT be empty;
* MUST NOT contain control characters.

Required form:

```text
!ext-pong
```

Canonical name:

```text
ext-pong
```

Duplicate feature names are forbidden.

Therefore:

```text
["ext-pong", "ext-pong"]
```

is invalid.

And:

```text
["ext-pong", "!ext-pong"]
```

is also invalid because it refers to the same canonical feature twice.

---

# 29. Feature Negotiation

The client offer contains canonical feature names optionally prefixed with `!`.

The gateway MUST:

1. validate the offer;
2. identify required features;
3. determine supported optional features;
4. fail if any required feature is unsupported;
5. construct the accepted feature set;
6. sort canonical feature names by raw UTF-8 byte order;
7. publish the canonical accepted set.

The gateway MUST NOT add a feature that was not offered.

`HELLO_CHALLENGE.features` contains the accepted canonical feature names without `!`.

`HELLO_ACK.features` MUST equal the final accepted canonical set exactly.

---

# 30. Feature Negotiation Failure

If no overlapping protocol version exists:

```text
UNSUPPORTED_VERSION
```

If no overlapping wire version exists:

```text
UNSUPPORTED_WIRE_VERSION
```

If a required feature is unsupported:

```text
UNSUPPORTED_FEATURE
```

These are connection-level protocol failures.

---

# 31. HELLO_AUTH

`HELLO_AUTH` is sent only after `HELLO_CHALLENGE`.

Header:

```text
request_uuid = new non-nil UUID
session_uuid = nil
```

Payload:

```json
{
  "client_proof": "..."
}
```

`client_proof` MUST be exactly 32 decoded bytes represented using unpadded Base64URL.

The proof is:

```text
HMAC-SHA256(
    shared_secret,
    transcript("GARP-CLIENT-AUTH")
)
```

---

# 32. HELLO_ACK

`HELLO_ACK` is sent only after successful `HELLO_AUTH`.

Header:

```text
request_uuid = HELLO_AUTH.request_uuid
session_uuid = nil
```

Payload:

```json
{
  "server_proof": "...",
  "selected_version": "1.16",
  "selected_wire_version": "0x00",
  "features": []
}
```

`server_proof` is exactly 32 decoded bytes represented using unpadded Base64URL.

The client MUST verify `server_proof` before sending sensitive provider-directed content.

---

# 33. Authentication Secret

The shared secret MUST contain at least 32 raw bytes.

Secret provisioning format is deployment-specific.

The authentication algorithm operates on raw secret bytes.

The protocol MUST NOT silently hex-decode or Base64-decode a provisioning value unless deployment configuration explicitly defines that encoding.

---

# 34. Authentication Domains

Client:

```text
GARP-CLIENT-AUTH
```

Server:

```text
GARP-SERVER-AUTH
```

These exact ASCII strings are used as the transcript domain field.

---

# 35. Authentication Transcript

The exact transcript is:

```text
u32be(length(domain ASCII bytes))
domain

u32be(length(client_nonce raw bytes))
client_nonce

u32be(length(server_nonce raw bytes))
server_nonce

u32be(length(selected_version UTF-8 bytes))
selected_version

u32be(length(selected_wire_version UTF-8 bytes))
selected_wire_version

u32be(feature_count)

for each feature in canonical byte-sorted order:
    u32be(length(feature UTF-8 bytes))
    feature

u32be(length(client_name UTF-8 bytes))
client_name

u32be(length(client_version UTF-8 bytes))
client_version

u32be(length(server_name UTF-8 bytes))
server_name

u32be(length(server_version UTF-8 bytes))
server_version
```

No separators or NUL bytes are inserted.

All lengths are byte counts.

Feature required markers are not included in canonical transcript features.

---

# 36. Nonce Encoding

`client_nonce` and `server_nonce`:

* MUST be generated by a cryptographically secure random source;
* MUST be exactly 16 bytes;
* MUST be represented using unpadded Base64URL;
* MUST decode successfully before transcript construction.

Padding characters `=` MUST be rejected.

Malformed Base64URL MUST fail authentication.

---

# 37. Authentication Comparison

Authentication proofs MUST:

1. be Base64URL decoded;
2. have exactly 32 bytes;
3. be compared using constant-time comparison.

---

# 38. Authentication Replay

The gateway MUST prevent reuse of accepted authentication transcript material.

The minimum replay-protection interval is:

```text
24 hours
```

The mechanism MUST provide actual 24-hour protection under configured load.

A cache that silently evicts still-valid replay entries is insufficient by itself.

An implementation MAY use:

* durable TTL storage;
* distributed key/value storage;
* persistent database state;
* another mechanism with equivalent guarantee.

A gateway restart MUST NOT silently invalidate the required replay guarantee while reusing the same authentication secret.

If durable replay protection is unavailable after restart, the gateway MUST reject new authentication using the affected secret until replay state is safely re-established, or the deployment MUST rotate the secret.

---

# 39. Handshake Timeout

An incomplete handshake MUST expire after:

```text
5000 ms
```

Authentication backoff does not require an already-expiring handshake connection to remain open.

Backoff applies to subsequent attempts.

---

# 40. Authentication Backoff

Recommended schedule:

```text
1000 ms
2000 ms
4000 ms
8000 ms
16000 ms
30000 ms maximum
```

Jitter SHOULD be added.

---

# 41. Connection State Machine

```text
NEW
 |
 | HELLO
 v
HELLO_RECEIVED
 |
 | HELLO_CHALLENGE
 v
CHALLENGE_SENT
 |
 | HELLO_AUTH
 v
AUTH_VERIFYING
 |
 | valid proof
 v
AUTHENTICATED_PENDING_ACK
 |
 | HELLO_ACK
 v
AUTHENTICATED
 |
 v
APPLICATION
```

The client-side interpretation is:

```text
CONNECTING
  ↓
HELLO_SENT
  ↓
CHALLENGE_RECEIVED
  ↓
AUTH_SENT
  ↓
HELLO_ACK_RECEIVED
  ↓
AUTHENTICATED
```

Application content MUST NOT be sent until the client has verified the server proof.

---

# 42. RESPONSE

Successful command response:

```json
{
  "success": true,
  "result": {}
}
```

Failed command response:

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "..."
  }
}
```

`result` is an object.

`error` is an object.

The envelope carries the originating request and session identities.

---

# 43. Application Failure vs Protocol Failure

Use:

```text
RESPONSE(success=false)
```

for a command that was successfully parsed and authorized but cannot complete its requested application operation.

Examples:

```text
SESSION_BUSY
UNKNOWN_SESSION
UNKNOWN_PROMPT
INVALID_STATE
PROMPT_TIMEOUT
CONTINUATION_TIMEOUT
CONTINUATION_LIMIT_REACHED
PROVIDER_RATE_LIMITED
```

Use:

```text
ERROR
```

for protocol-processing failures.

Examples:

```text
INVALID_ARGUMENT
UNKNOWN_MESSAGE_TYPE
INVALID_ENVELOPE
HEADER_JSON_MISMATCH
UNSUPPORTED_VERSION
UNSUPPORTED_WIRE_VERSION
AUTH_FAILED
AUTH_REPLAY
```

---

# 44. ERROR Payload

`ERROR` payload is closed:

```json
{
  "code": "HEADER_JSON_MISMATCH",
  "message": "Header and JSON identity disagree."
}
```

Fields:

| Field     | Type   | Required |
| --------- | ------ | -------- |
| `code`    | string | yes      |
| `message` | string | yes      |
| `details` | object | optional |

`message` MUST be 1–4096 UTF-8 bytes.

`details` is bounded by the extension/detail limit defined in §129.

---

# 45. Session Identity

`session_id` alone is the immutable identity of a session.

The following are mutable session attributes:

```text
provider
tab_id
page_generation
state
url
```

A provider or tab change does not change `session_id`.

---

# 46. Session States

A session is exactly one of:

```text
CREATED
PREPARING
READY
BUSY
AUTH_REQUIRED
RATE_LIMITED
RECOVERING
RETRYING
FAILED
CLOSED
```

---

# 47. Session State Semantics

### CREATED

Session record exists.

### PREPARING

Browser/provider context is being established or reconstructed.

### READY

No active prompt exists and no unsafe provider state remains.

### BUSY

An active prompt exists.

### AUTH_REQUIRED

Provider authentication is required.

### RATE_LIMITED

Provider interaction is blocked by provider throttling.

### RECOVERING

The gateway is actively resolving an unsafe or stale condition.

### RETRYING

A retryable transient condition is being retried.

### FAILED

The session cannot safely continue.

### CLOSED

The session is terminated.

---

# 48. Session Transition Matrix

| Current        | Trigger                          | Next              |
| -------------- | -------------------------------- | ----------------- |
| CREATED        | begin preparation                | PREPARING         |
| PREPARING      | preparation succeeds             | READY             |
| PREPARING      | provider auth required           | AUTH_REQUIRED     |
| PREPARING      | rate limit detected              | RATE_LIMITED      |
| PREPARING      | unrecoverable error              | FAILED            |
| READY          | prompt accepted                  | BUSY              |
| READY          | auth lost                        | AUTH_REQUIRED     |
| READY          | rate limited                     | RATE_LIMITED      |
| READY          | recovery required                | RECOVERING        |
| BUSY           | prompt remains active            | BUSY              |
| BUSY           | safe terminal prompt             | READY             |
| BUSY           | auth lost                        | AUTH_REQUIRED     |
| BUSY           | rate limited                     | RATE_LIMITED      |
| BUSY           | recovery required                | RECOVERING        |
| AUTH_REQUIRED  | provider auth restored           | PREPARING         |
| RATE_LIMITED   | block resolved                   | PREPARING         |
| RECOVERING     | recovery succeeds, no prompt     | READY             |
| RECOVERING     | recovery succeeds, prompt active | BUSY              |
| RECOVERING     | recovery deadline                | FAILED            |
| RETRYING       | retry succeeds                   | BUSY or PREPARING |
| RETRYING       | retry exhausted                  | FAILED            |
| FAILED         | RESET_SESSION                    | PREPARING         |
| any non-CLOSED | CLOSE_SESSION                    | CLOSED            |

---

# 49. Session Arbiter

Every session MUST have one authoritative command/state arbiter.

The arbiter MUST serialize:

* prompt reservation;
* terminal prompt commits;
* cancellation commits;
* recovery commits;
* state transitions;
* event sequence allocation.

A per-session single-threaded commit queue is a conforming implementation.

A global single-threaded gateway is not required.

---

# 50. Atomic Prompt Reservation

The transition:

```text
READY
```

to:

```text
BUSY
```

and reservation of the prompt identity MUST be atomic.

Two simultaneous `PROMPT` commands MUST NOT both succeed.

Exactly one reservation wins.

All other concurrent prompt creations fail with:

```text
SESSION_BUSY
```

---

# 51. Page Generation

`page_generation` is:

```text
uint64
```

Initial value:

```text
0
```

It increments by exactly `1`.

It changes when page-dependent state becomes invalid through:

* navigation;
* document recreation;
* actor replacement;
* browser restart affecting the session;
* reload requiring invalidation;
* provider-page replacement.

Overflow MUST fail the session safely.

---

# 52. Page-Generation Read/Write Fencing

Every asynchronous page-dependent operation MUST capture:

```text
read_generation
write_generation
```

A provider observation MUST be discarded if the generation has changed since the observation began.

A state write MUST commit only when:

```text
write_generation == current_page_generation
```

Stale actors MUST NOT commit current state.

---

# 53. Prompt Request

`PROMPT` payload is closed:

```json
{
  "text": "prompt content",
  "options": {}
}
```

`text` is required.

`options` is optional.

The successful response is:

```json
{
  "success": true,
  "result": {
    "state": "ACCEPTED",
    "prompt_request_id": "..."
  }
}
```

`ACCEPTED` is a command result only.

It is not a lifecycle state.

The authoritative prompt lifecycle immediately after acceptance is:

```text
PENDING
```

---

# 54. Prompt Lifecycle States

Prompt lifecycle states are:

```text
PENDING
SUBMITTING
GENERATING
WAITING_CONTINUATION
CANCELLING
COMPLETED
FAILED
CANCELLED
```

`NONE` is not a prompt lifecycle state.

`NONE` is valid only in session-level `GET_SESSION.prompt_state` when there is no active prompt.

A targeted `GET_PROMPT_STATUS` never returns `NONE`.

---

# 55. Prompt Options

The `options` object is closed except for its permitted `_extensions` member.

Fields:

| Field               | Type    | Default | Range           |
| ------------------- | ------- | ------- | --------------- |
| `timeout_ms`        | uint64  | `0`     | `0..UINT64_MAX` |
| `auto_continue`     | boolean | `false` | —               |
| `max_continuations` | uint32  | `8`     | `0..1024`       |
| `force_focus`       | boolean | `false` | —               |
| `simulate_enter`    | boolean | `false` | —               |
| `_extensions`       | object  | omitted | bounded         |

`timeout_ms=0` explicitly means no client prompt timeout.

`max_continuations=0` explicitly means continuation is not permitted.

All other resource limits do not acquire unlimited semantics from the numeric value `0`.

---

# 56. Prompt Acceptance and Timeout

Prompt timeout begins at the monotonic commit time of:

```text
RESPONSE(success=true,state=ACCEPTED)
```

The timeout does not begin at:

* DOM discovery;
* input injection;
* submission;
* generation start.

The deadline is:

```text
acceptance_time + timeout_ms
```

when `timeout_ms > 0`.

---

# 57. Prompt Content Opacity

The exact decoded `text` string MUST be preserved.

The gateway MUST NOT silently:

* trim;
* collapse whitespace;
* change capitalization;
* normalize Unicode;
* normalize line endings;
* insert characters;
* remove characters.

JSON escape decoding is allowed.

Post-decoding normalization is prohibited.

---

# 58. Verified Input Injection

Input processing:

```text
DISCOVERING
→ INJECTING
→ VERIFIED
```

The adapter MUST positively establish that the provider input control contains the exact requested prompt.

---

# 59. Submission Verification

Submission processing:

```text
ATTEMPTED
→ OBSERVED
→ VERIFIED
→ COMMITTED
```

`INPUT_SUBMITTED` is emitted only after verified submission.

A click/key event alone is insufficient.

---

`GET_SESSION.input_state` is one of:

```text
IDLE
DISCOVERING
INJECTING
VERIFIED
SUBMITTING
SUBMITTED
FAILED
```

# 61. Generation State

`GET_SESSION.generation_state` is one of:

```text
IDLE
STARTING
GENERATING
WAITING_CONTINUATION
STOPPING
COMPLETED
FAILED
CANCELLED
```

These fields are observational session fields.

The prompt lifecycle remains authoritative for prompt state.

---

# 62. Message Identity

`message_id` is an opaque UTF-8 string.

Constraints:

```text
1..128 UTF-8 bytes
```

It MUST be unique within one prompt.

It remains stable after announcement.

---

# 63. Message Record

Canonical message object:

```json
{
  "message_id": "M1",
  "revision": 1,
  "content": "Hello"
}
```

Fields:

| Field        | Type   |
| ------------ | ------ |
| `message_id` | string |
| `revision`   | uint64 |
| `content`    | string |

Revision `0` represents no authoritative content.

First authoritative content uses revision `1`.

---

# 64. Message Boundary Rule

The adapter MUST use this deterministic rule:

1. If the provider exposes explicit logical assistant-message boundaries, use them.
2. Otherwise, the prompt has exactly one logical message.
3. Continuation alone does not create a new message.
4. A new provider-observed logical assistant response creates a new message.

A message MUST NOT be split merely because:

* content exceeds a size;
* a delta is large;
* a timer expires;
* a network packet ends;
* a buffer flush occurs.

---

# 65. GENERATION_STARTED

Payload:

```json
{
  "prompt_request_id": "...",
  "message_id": "M1",
  "page_generation": 7
}
```

Every new message identity MUST be announced by `GENERATION_STARTED`.

A `GENERATION_DELTA` referencing an unknown message ID is a protocol error.

---

# 66. GENERATION_DELTA

Payload:

```json
{
  "prompt_request_id": "...",
  "message_id": "M1",
  "revision": 2,
  "mode": "APPEND",
  "delta": " world",
  "page_generation": 7
}
```

`mode` is:

```text
APPEND
REPLACE
```

---

# 67. Revision Ordering

For one `(prompt_request_id,message_id)`:

```text
next_revision = previous_revision + 1
```

A delta with:

```text
revision < expected
```

is a duplicate/stale event and MUST be discarded.

A delta with:

```text
revision > expected
```

is a sequence gap and MUST fail the affected generation stream.

The client MUST NOT infer missing content.

---

# 68. APPEND

For `APPEND`:

```text
new_content = previous_content + delta
```

No other mutation is permitted.

---

# 69. REPLACE

For `REPLACE`:

```text
new_content = delta
```

The supplied delta is the complete new message content.

---

# 70. GENERATION_PROGRESS

Payload:

```json
{
  "prompt_request_id": "...",
  "message_count": 2,
  "page_generation": 7
}
```

`message_count` is the number of message identities whose `GENERATION_STARTED` event has been committed.

---

# 71. CONTINUATION_REQUIRED

Payload:

```json
{
  "prompt_request_id": "...",
  "page_generation": 7,
  "continuation_count": 0
}
```

The prompt transitions to:

```text
WAITING_CONTINUATION
```

If:

```text
max_continuations = 0
```

the gateway MUST NOT emit `CONTINUATION_REQUIRED`.

Instead it MUST fail the prompt with:

```text
CONTINUATION_LIMIT_REACHED
```

and preserve applicable partial response data.

---

# 72. Automatic Continuation

When:

```text
auto_continue = true
```

the gateway MAY submit continuation automatically.

When:

```text
auto_continue = false
```

the gateway MUST wait for `CONTINUE_PROMPT`.

Automatic continuation MUST obey:

```text
continuation_count < max_continuations
```

---

# 73. Continuation Race

If `auto_continue=true` and a client simultaneously issues `CONTINUE_PROMPT`, the per-session arbiter serializes the requests.

The first valid continuation reservation wins.

The losing operation returns:

```text
INVALID_STATE
```

unless the prompt has already become terminal, in which case the appropriate terminal-target error applies.

A continuation reservation MUST NOT be committed twice.

---

# 74. CONTINUE_PROMPT

Payload:

```json
{
  "target_request_id": "..."
}
```

Successful response:

```json
{
  "success": true,
  "result": {
    "state": "ACCEPTED"
  }
}
```

The flow is:

```text
WAITING_CONTINUATION
→ RESPONSE(ACCEPTED)
→ SUBMITTING
→ CONTINUATION_SUBMITTED
→ GENERATING
```

A resumed existing message does not require a new `GENERATION_STARTED`.

If a new provider logical message is established, a new `GENERATION_STARTED` is required.

---

# 75. Continuation Count

`continuation_count` starts at `0`.

It increments only after:

```text
CONTINUATION_SUBMITTED
```

has been verified and committed.

When:

```text
continuation_count >= max_continuations
```

another continuation MUST fail with:

```text
CONTINUATION_LIMIT_REACHED
```

---

# 76. Continuation Wait Timeout

`continuation_wait_ms` is an effective capability.

When a prompt enters `WAITING_CONTINUATION`, the gateway starts the continuation wait deadline.

When the deadline expires:

```text
CONTINUATION_TIMEOUT
```

is committed.

If no provider activity remains, the session MAY return to `READY`.

---

# 77. Generation Completion

`GENERATION_COMPLETED` is authoritative terminal completion.

For one message:

```json
{
  "prompt_request_id": "...",
  "message_id": "M1",
  "revision": 3,
  "response": "Hello GARP",
  "page_generation": 7
}
```

For multiple messages:

```json
{
  "prompt_request_id": "...",
  "messages": [
    {
      "message_id": "M1",
      "revision": 3,
      "content": "Hello"
    },
    {
      "message_id": "M2",
      "revision": 2,
      "content": "World"
    }
  ],
  "page_generation": 7
}
```

When `messages` is present:

```text
response MUST be omitted.
```

When `response` is present:

```text
messages MUST be omitted.
```

`partial` MUST NOT appear.

```json

}
```

```text

```

not necessarily:

```text
prompt already cancelled
```

```json

  "success": true,
  "result": {
    "state": "ACCEPTED"
  }
}
```

```text

```

---

# 84. Cancellation Arbitration

Completion, cancellation, and timeout are serialized through the session arbiter.

The authoritative order is the commit order.

### Completion wins

If completion commits before cancellation or timeout:

```text
COMPLETED
```

### Cancellation wins

If cancellation commits before completion and provider cessation is verified:

```text
CANCELLED
```

### Timeout wins

If timeout commits before completion or cancellation:

```text
FAILED
PROMPT_TIMEOUT
```

Once a terminal state has been committed:

```text
COMPLETED
FAILED
CANCELLED
```

it MUST NOT be reopened.

There is no later “correction” from one terminal state to another.

This resolves the timeout/completion contradiction.

---

# 85. Cancellation Verification

A terminal:

```text
CANCELLED
```

requires verified provider cessation.

If cancellation has been accepted but cessation is not yet verified:

```text
prompt = CANCELLING
session = RECOVERING
```

A non-terminal recovery event MAY report:

```text
cancel_verified = false
```

The terminal `GENERATION_CANCELLED` event MUST only report:

```text
cancel_verified = true
```

---

# 86. Cancellation Recovery

When cancellation remains unverified:

```text
CANCELLING
```

continues until either:

1. provider cessation is verified;
2. provider completion commits;
3. recovery deadline expires.

Case 1:

```text
CANCELLED
```

Case 2:

```text
COMPLETED
```

Case 3:

```text
FAILED
RECOVERY_FAILED
```

This is deterministic.

---

# 87. Prompt Timeout Recovery

When prompt timeout commits:

```text
prompt = FAILED
error = PROMPT_TIMEOUT
```

If provider cessation is unknown:

```text
session = RECOVERING
```

A later provider observation MUST NOT reopen the failed prompt.

The only completion that matters is completion committed before timeout.

---

# 88. Recovery Deadline

Every recovery has a finite deadline:

```text
recovery_deadline_ms
```

If the condition remains unresolved at the deadline:

```text
session = FAILED
```

and any affected non-terminal prompt becomes:

```text
FAILED
error = RECOVERY_FAILED
```

No unresolved recovery may remain indefinitely.

# 91. AUTH_REQUIRED

The base provider event is:

```text
AUTH_REQUIRED
```

Its payload:

```json
{
  "provider": "deepseek",
  "reason": "LOGIN_REQUIRED",
  "page_generation": 7
}
```

When this event is committed:

```text
session = AUTH_REQUIRED
```

An active prompt is failed with:

```text
PROVIDER_AUTH_REQUIRED
```

The session exits `AUTH_REQUIRED` only after provider authentication has been positively verified.

The recovery path is:

```text
AUTH_REQUIRED
→ PREPARING
→ READY
```

or:

```text
AUTH_REQUIRED
→ PREPARING
→ BUSY
```

when a prompt is explicitly resumable.

A prompt is resumable only when the gateway has preserved sufficient state to continue it without duplicating provider submission.


---

# 93. Provider Evidence

Provider evidence is any provider-specific observation satisfying the adapter's declared rule for the fact being established.

Examples:

### Input verification

* exact input value observed in intended control.

### Submission verification

* provider UI state demonstrably transitions out of input state;
* a new provider response boundary appears;
* provider-native submission state is observed.

### Generation start

* provider generation indicator;
* first authoritative generated content;
* explicit provider generation event;
* equivalent provider-specific evidence.

### Provider cessation

At least one positive stop condition:

* provider generation indicator absent after a verified stop operation;
* provider has entered a terminal response state;
* provider exposes explicit completion/cancellation state;
* browser actor definitively observes that the active generation has ended.

Merely failing to observe new deltas is not sufficient evidence of cessation.

Each adapter MUST define:

```text

adapter_version
selector_strategy_version
input discovery
input verification
submission
submission verification
generation-start evidence
generation-content observation
message-boundary rule
continuation detection
provider-cessation detection
provider-authentication detection
rate-limit detection
```

An adapter that cannot establish required evidence MUST fail explicitly.

# 95. Selector Strategy

`selector_strategy_version` is an opaque adapter version identifier.

It identifies the deterministic selector/discovery algorithm used by the adapter.

Changing selectors or discovery logic SHOULD increment it.

A selector mismatch MUST NOT silently fall back to arbitrary DOM elements.

Selector drift is reported through:

```text
DIAGNOSTIC
code = INPUT_SELECTOR_DRIFT
```

# 96. Provider Content Trust

Provider content is untrusted.

The gateway MUST NOT:

* execute generated provider text as code;
* interpret arbitrary DOM text as GARP commands;
* treat DOM JSON-looking text as protocol JSON;
* trust provider-supplied identifiers as GARP identities.

# 113. Diagnostic Codes

Base diagnostic codes include:

```text
INPUT_SELECTOR_DRIFT
REPLAY_RETENTION_REDUCED
RECOVERY_FAILED
GENERATION_STALL
STALE_EVENT_DISCARDED
```

Diagnostic codes are not message types.

---

# 114. Diagnostic Throttling

Repeated diagnostics MAY be throttled by:

```text
code + stage + actor_instance
```

A throttling implementation MUST NOT suppress:

* security failures;
* state-transition diagnostics;
* terminal failure diagnostics;
* recovery deadline diagnostics.

A throttling window MUST be finite and MUST NOT silently suppress a diagnostic forever.

---

# 115. Event Sequence and Diagnostics

Session-scoped diagnostics consume the normal session sequence.

Connection-scoped diagnostics do not.

Example:

```text
SESSION_READY sequence=10
DIAGNOSTIC sequence=11
GENERATION_STARTED sequence=12
```

---

# 116. PING

`PING` is a connection-scoped command.

Envelope:

```text
request_id = non-nil
session_id = null
sequence = absent
```

Payload:

```json
{}
```

PING MUST receive exactly one:

```json
{
  "success": true,
  "result": {}
}
```

PING MUST NOT cause PONG.

---

# 117. PONG

PONG is an unsolicited connection-scoped event.

It is available only when:

```text
ext-pong
```

is negotiated.

Envelope:

```text
request_id = null
session_id = null
sequence = absent
```

Payload:

```json
{}
```

PONG:

* is not a response to PING;
* does not consume event sequence;
* does not enter event history;
* does not enter replay;
* does not require client response.

---

# 118. PONG Timing

Defaults:

```text
interval_ms = 30000
timeout_ms = 90000
```

Required relationship:

```text
interval_ms * 3 <= timeout_ms
```

The gateway SHOULD send PONG when no other valid outbound frame has been sent during `interval_ms`.

Normal traffic MAY suppress PONG.

---

# 119. PONG Liveness

The client liveness timer MUST reset on receipt of any valid inbound GARP frame.

Examples:

```text
RESPONSE
GENERATION_STARTED
GENERATION_DELTA
GENERATION_PROGRESS
DIAGNOSTIC
PONG
```

A connection MUST NOT be declared stale merely because no PONG arrived while valid traffic continues within `timeout_ms`.

---

# 120. Replay Extension

Optional feature:

```text
ext-replay-store
```

The extension provides:

```text
GET_EVENTS = 0x0100
```

The extension code range:

```text
0x0100..0x01FF
```

is reserved for replay-related messages.

Future extension code ranges MUST be allocated without collision.

---

# 121. GET_EVENTS

`GET_EVENTS` is an extension command.

Header:

```text
request_uuid = non-nil
session_uuid = requested session
```

Payload:

```json
{
  "from_sequence": 5,
  "max_events": 100
}
```

Rules:

```text
from_sequence MUST be >= 1
max_events MUST be 1..4096
```

A successful command returns:

```json
{
  "success": true,
  "result": {
    "events": [],
    "next_sequence": 105,
    "complete": true
  }
}
```

`complete=true` means:

> all retained events from `from_sequence` through the last currently retained event at the time of query have been returned.

`complete=false` means:

> more retained events exist and may be requested using `next_sequence`.

`next_sequence` is the sequence immediately after the last returned event.

---

# 122. Replay Expiration

If:

```text
from_sequence
```

is no longer retained:

```text
EVENT_HISTORY_EXPIRED
```

MUST be returned.

The gateway MUST NOT silently begin at a later retained sequence.

`from_sequence=0` is invalid and returns:

```text
INVALID_ARGUMENT
```

---

# 123. Replay Ordering

Replayed events:

* retain original sequence;
* retain original event type;
* retain original event payload;
* retain original request/session identities;
* do not receive new sequence values.

Replay does not alter current state.

---

# 124. Replay Retention

Replay storage MUST use deterministic eviction.

The gateway MUST define:

```text
retention by age
retention by memory
retention by event count
```

as applicable.

When multiple limits apply, an event expires as soon as any configured retention limit excludes it.

---

# 125. Replay Retention Reduction

When effective replay retention is reduced:

1. `CAPABILITIES` MUST be updated;
2. a session/connection diagnostic MUST be emitted:

   ```text
   REPLAY_RETENTION_REDUCED
   ```
3. the new bound is effective for subsequent retention.

Payload:

```json
{}
```

```json

}
```

```json

}
```

---

# 127. CLOSE_SESSION Semantics

Closing a session:

1. enters `CLOSED`;
2. invalidates page actors;
3. stops active provider work where possible;
4. terminates any non-terminal prompt as:

   ```text
   FAILED
   SESSION_CLOSED
   ```
5. releases resources;
6. invalidates retained session history according to closure policy.

Subsequent access returns:

```text
UNKNOWN_SESSION
```

---

# 128. RESET_SESSION Semantics

Reset:

1. advances page generation;
2. invalidates all page actors;
3. invalidates stale asynchronous work;
4. stops active provider work where possible;
5. reconstructs browser/provider state;
6. transitions through `PREPARING`.

Event sequence continues monotonically.

Sequence does not reset.

---

# 129. Size Limits

In addition to payload limits, implementations MUST enforce:

```text
max_prompt_size
max_response_size
max_generation_buffer_mb
max_queued_events
max_extensions_bytes
diagnostic_details_bytes
```

All are hard bounds.

A limit-exceeded condition MUST fail before partial external side effects become visible.

---

# 130. Prompt Size

`PROMPT.text` UTF-8 byte length MUST NOT exceed:

```text
max_prompt_size
```

The gateway MUST reject oversized prompts before attempting provider input injection.

---

# 131. Generation Buffer Overflow

If the generation buffer reaches:

```text
max_generation_buffer_mb
```

the gateway MUST:

1. stop accepting additional buffered content;
2. emit a generation failure:

   ```text
   BUFFER_OVERFLOW
   ```
3. transition the prompt to:

   ```text
   FAILED
   ```
4. enter recovery if provider activity may still exist.

Silent truncation is prohibited.

---

# 132. Provider Error

`PROVIDER_ERROR` payload:

```json
{
  "provider": "deepseek",
  "code": "PROVIDER_ERROR_CODE",
  "message": "Provider operation failed.",
  "retryable": false,
  "page_generation": 7
}
```

`retryable` indicates whether the adapter believes a retry is safe.

A retryable provider error enters:

```text
RETRYING
```

only after the prompt/session arbiter commits the retry transition.

---

# 133. Retry Rules

A retry MUST preserve:

```text
session_id
prompt_request_id
```

An unsafe provider action MUST NOT be duplicated unless the gateway can establish that the previous external action was not committed.

A retry MUST respect page-generation fencing.

---

# 134. Retry State Machine

```text
BUSY
  ↓ transient failure
RETRYING
  ↓ retry committed
BUSY
```

Failure:

```text
RETRYING
  ↓ exhaustion
FAILED
```

A retry MUST NOT silently create a second prompt.

---

# 135. Provider Authentication

Provider authentication is adapter-observed state.

The adapter MUST define positive evidence for authentication.

Examples include:

* provider authenticated-page state;
* authenticated session indicators;
* successful authenticated provider operation.

Absence of a login page is not alone sufficient unless explicitly defined as provider evidence.

---

# 136. Provider Rate Limit

Rate-limit detection is adapter-defined.

The adapter MUST have a deterministic rule for recognized provider rate-limit evidence.

An arbitrary provider phrase MUST NOT automatically be interpreted as rate limiting without a defined adapter rule.

---

# 137. Prompt Retention

Terminal prompt records may remain retained according to:

```text
response_retention_ms
```

A terminal prompt record is immutable with respect to:

* identity;
* terminal state;
* content;
* revisions.

Retention expiration MAY delete the record.

Therefore:

```text
immutable != permanently retained
```

```text

GET_PROMPT_STATUS
SUBSCRIBE_RESPONSE
CONTINUE_PROMPT
CANCEL_PROMPT
```

must return the appropriate expiration error rather than reconstructing the prompt from unrelated later state.


# 141. Page-Generation Scope

Page generation is scoped to the session's provider page context.

If the provider uses:

* frames;
* shadow DOM;
* nested document actors;

they are all subordinate to the session page generation.

A navigation or document replacement anywhere that invalidates provider actors MUST advance the session page generation.

---

# 142. Browser Restart

A browser restart that invalidates provider page state MUST:

1. advance page generation;
2. invalidate actors;
3. enter `RECOVERING` or `PREPARING` as appropriate.

Base GARP does not require process-restart persistence for live sessions.

---

# 143. Process Restart

Without an explicit persistence extension, gateway process restart MAY destroy:

* sessions;
* active prompts;
* subscriptions;
* replay history.

Clients MUST NOT assume survival.

Authentication replay protection is an exception and MUST retain the security guarantee required by §38.




No sequence values are reused.

# 177. Mandatory Invariants

**C1.** Fixed header size is 48 bytes.

**C2.** Wire version is `0x00`.

**C3.** Base flags are zero unless negotiated extension semantics define them.

# 178. Security Properties

GARP/1.16 provides:

```text
mutual authentication
+
nonce freshness
+
feature/version transcript binding
+
replay protection
+
constant-time proof comparison
+
bounded input allocation
+
provider-content distrust
+
page-generation fencing
+
atomic session arbitration
```

HMAC with a static shared secret does not provide forward secrecy.

Secret rotation is a deployment responsibility.

Non-loopback deployments MUST use TLS or equivalent secure transport.

---

# 179. Loopback Security

Loopback TCP is not a cryptographic trust boundary.

Multi-user deployments SHOULD prefer:

* Unix-domain sockets with restrictive permissions on POSIX;
* named pipes with ACLs on Windows;
* equivalent operating-system access controls.

# 180. Extension Rules

An extension MUST:

1. have a unique feature name;
2. define negotiation;
3. define all message codes;
4. define payload schemas;
5. define error behavior;
6. define sequence behavior;
7. define identity behavior;
8. define resource bounds;
9. define conformance tests.

No extension may silently modify an existing base message meaning.

# 188. Final Normative Principle

GARP exists to create a trustworthy boundary around an inherently unreliable browser automation environment.

The protocol therefore distinguishes:

```text
ATTEMPTED
```

from:

```text
OBSERVED
```

from:

```text
VERIFIED
```

from:

```text
COMMITTED
```

An implementation MUST never skip from:

```text
attempt
```

to:

```text
success
```

without the evidence required for the operation.

The provider page is untrusted.

DOM actors are replaceable.

Navigations make old observations stale.

Provider UIs drift.

Network timing is nondeterministic.

GARP therefore makes only the authoritative committed state externally normative.
