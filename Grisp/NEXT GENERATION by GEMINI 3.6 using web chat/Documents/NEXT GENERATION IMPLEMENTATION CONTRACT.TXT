# GRISP v1.0 Implementation Contract

## Revision 2

**Status:** Implementation baseline
**Normative parent:** GRISP Agent Specification v1.0
**Primary implementation:** Delphi / Windows
**Browser gateway:** Firefox
**Transport:** GARP/1.0
**AI semantic exchange:** GAI/1.0
**Default mode:** fail-closed

---

# 1. Scope

This document is the **implementation contract** for GRISP v1.0.

It does not redefine the architecture.

The architecture specification establishes the system's authority model, candidate/evidence model, hard acceptance gates, Firefox gateway concept, state-machine requirements, and non-negotiable invariants.

This document defines the concrete contracts required to implement those requirements:

```text
data types
serialization
canonicalization
hashing
state transitions
acceptance predicates
parser behavior
evidence semantics
tool contracts
commit semantics
GAI messages
GARP messages
GARP framing
Firefox interfaces
conformance tests
```

The implementation SHALL conform to this document unless the normative architecture specification explicitly requires otherwise.

```text

│ GRISP Semantic Contract             │

└──────────────────┬──────────────────┘

        ┌──────────┴──────────┐

│ AI semantics    │   │ Browser transport│
└─────────────────┘   └─────────────────┘
        │                     │
        └──────────┬──────────┘
                   ▼
        ┌─────────────────────┐
        │ Implementation      │
        │ Delphi / Firefox /  │
        │ storage / tools     │
        └─────────────────────┘
```

The implementation SHALL NOT allow:

```text

```

to leak into:

```text

```

nor allow:

```text

```

to become:

```text

```

# 3. Canonical terminology

The following terms have precise meanings.

### Task

Normalized user request.

### AI Response

Raw response received from an AI worker.

An AI response is **not automatically an artifact**.

### Candidate

A task-specific attempt represented by an artifact plus its lifecycle state and evidence.

### ArtifactBundle

Canonical collection of one or more files.

### ArtifactFile

One file within an ArtifactBundle.

### Artifact Identity

Cryptographic identity of the canonical artifact representation.

### Evidence

Immutable record of an observation or deterministic operation.

### ToolResult

Immediate structured result returned by a tool invocation.

### Decision

Final deterministic acceptance/rejection record.

### Session

Logical AI conversation controlled through a worker transport.

### Tab

Stable browser-tab identity.

### Request

One AI operation associated with a unique request ID.

### Message

One AI response identity within a session.

# 9. Artifact identity

Two separate hashes shall be maintained conceptually.

## 9.1 File content hash

```text
content_sha256 =
SHA256(exact content bytes)
```

The hash input is the exact byte representation associated with the artifact.

No implicit:

```text
CRLF → LF
Unicode normalization
whitespace trimming
encoding conversion
```

is permitted before hashing.

## 9.2 Artifact identity

```text
artifact_id =
"sha256:" + SHA256(canonical_artifact_manifest_bytes)
```

The artifact manifest contains file hashes.

Therefore:

```text
ArtifactBundle
    ↓
canonical manifest
    ↓
SHA-256
    ↓
artifact_id
```

`artifact_id` SHALL NOT be included in the manifest being hashed.

---

# 10. Why exact bytes matter

The implementation must preserve the distinction between:

```text
logical source
```

and:

```text
physical artifact bytes
```

When an operation changes bytes, it creates a new artifact.

For example:

```text
Artifact A
   ↓
newline normalization
   ↓
Artifact B
```

B must receive a different identity if its canonical manifest changes.

This guarantees that verification is against the same artifact that is eventually committed.

---

# 11. Canonical file ordering

Files SHALL be sorted before inclusion in the canonical manifest.

Primary key:

```text
filename UTF-8 byte sequence
```

Comparison is lexicographical and case-sensitive.

Secondary key:

```text
content_sha256 UTF-8 byte sequence
```

If both are identical, the records are semantically duplicates and SHALL normally be rejected as duplicate files rather than relying on an arbitrary tertiary ordering.

The implementation SHALL NOT use locale-dependent comparison.

The implementation SHALL NOT use case-insensitive comparison.

The implementation SHALL NOT use Windows filesystem sort order.

# 14. Metadata canonicalization

`metadata` is allowed to contain:


# 15. Canonical JSON serialization

The canonical serializer SHALL produce:

```text
UTF-8
no insignificant whitespace
no line breaks outside strings
fixed property ordering
stable string escaping
stable integer formatting
```

The implementation SHALL NOT depend on incidental property ordering of a JSON library.

`TJSONObject.ToJSON`, `JSON.stringify`, or equivalent library behavior may be used only after conformance with the canonical serializer has been demonstrated.

For cross-language interoperability, a dedicated canonical serializer is preferred.

---

# 16. Number representation

v1.0 canonical metadata numbers SHALL use:

```text
integer
```

where practical.

Floating-point numbers are NOT part of core artifact identity semantics unless explicitly introduced by a later schema revision.

This avoids implementation-dependent representations such as:

```text
1
1.0
1e0
```

representing the same mathematical value differently.

# 17. Canonicalization algorithm

The reference algorithm is:

```text
1. Obtain exact file bytes.
2. Compute SHA-256 for every file.
3. Validate filename uniqueness.
4. Sort file records by filename UTF-8 bytes.
5. Construct canonical manifest.
6. Serialize using canonical JSON rules.
7. Encode serialized manifest as UTF-8.
8. SHA-256 the resulting bytes.
9. Prefix with "sha256:".
```

Pseudo-operation:

```text
ComputeArtifactId(bundle):

    for file in bundle.files:
        file.content_sha256 = SHA256(file.exact_bytes)
        file.size_bytes = Length(file.exact_bytes)

    ValidateFileNames(bundle.files)

    files := SortCanonical(bundle.files)

    manifest := BuildCanonicalManifest(bundle, files)

    bytes := CanonicalJsonUtf8(manifest)

    return "sha256:" + SHA256(bytes)
```

# 22. Markdown compatibility path

Markdown is compatibility-only.

The parser SHALL:

```text
1. scan the entire response
2. identify all fenced blocks
3. identify language tags
4. identify explicit filenames
5. associate blocks with filenames
6. detect conflicts
7. validate filenames
8. determine whether exactly one valid interpretation exists
```

It SHALL NOT:

```text
take first code block
ignore remaining blocks
invent a filename
delete suspicious tokens
guess the user's intended source
```

---

# 23. Markdown ambiguity

Examples:

```text
zero valid artifact interpretations
    → PARSE_ERROR

one valid interpretation
    → PARSED

two valid interpretations
    → PARSE_AMBIGUOUS
```

A parser must prefer rejection over invention.

---

# 24. No heuristic cleanup

The implementation shall not contain artifact extraction rules equivalent to:

```text
remove "CopyDownload"
remove "Delphiprogram"
remove "Pascalprogram"
strip unexpected provider prefixes
delete arbitrary leading tokens
```

Unexpected contamination becomes a diagnostic.

Example:

```text
code
↓
unexpected token
↓
PARSE_ERROR
```

not:

```text
code
↓
string replacement
↓
maybe-valid code
```

This is consistent with the architecture's requirement that malformed output become a parse failure rather than guessed content.

---

# 25. Filename inference

Filename inference is prohibited in strict artifact parsing.

If the task explicitly supplies a filename requirement, the parser may validate against that expected filename.

Otherwise:

```text

    →
PARSE_ERROR
```

The parser shall not invent:

```text
HelloWorld.dpr
main.pas
program.py
```

# 37. Test validity

A generated test is invalid when it:

```text
tests a nonexistent API
recreates the implementation
tests generated helper code instead of the target
asserts an unstated contract
cannot execute against the actual artifact
```

Such a test produces:

```text
TEST_INVALID
```

and cannot produce acceptance evidence.

This directly implements the architecture's prohibition on self-testing tests that invent functions not present in the actual artifact.

# 38. Acceptance predicate

The implementation shall express acceptance as a deterministic predicate.

Conceptually:

```text
Acceptable(Task, Candidate) =
    ArtifactValid
    AND StaticValid
    AND PolicyValid
    AND RequiredBuildValid
    AND RequiredRuntimeValid
    AND RequiredTestsValid
    AND ProvenanceComplete
    AND FinalVerificationValid
```

The relevant predicates are determined by the task's artifact contract.

Missing evidence for a required check means:

```text
false
```

not:

```text
unknown → assumed true
```

# 41. Candidate state versus evidence

State is derived from facts.

Evidence is the record of those facts.

Example:

```text
CompileResult(status=ok)
        ↓
CompileEvidence
        ↓
Candidate state = COMPILED
```

The implementation should not permit:

```text
state := COMPILED
```

without satisfying the corresponding transition guard.

---

# 42. State transition contract

Every transition is defined by:

```text
CurrentState
Event
Guard
NextState
Reason
```

Example:

```text
COMPILE_PENDING
+
CompileCompleted(status=ok)
+
no compiler error diagnostics
    →
COMPILED
```

Failure:

```text
COMPILE_PENDING
+
CompileCompleted(status=failed)
    →
COMPILE_FAILED
```

Unknown result:

```text
COMPILE_PENDING
+
missing/invalid result
    →
VERIFICATION_FAILED
```

It must never become:

```text

```

by default.

# 43. Runtime applicability

Runtime verification SHALL be explicitly derived from artifact kind.

Example:

```text
EXECUTABLE:
    compile = required
    runtime = required
    tests = task-dependent

UNIT:
    compile = required
    runtime = usually via harness
    tests = required where contract specifies

DOCUMENTATION:
    compile = not applicable
    runtime = not applicable
    schema/content checks = applicable
```

"Not applicable" is an explicit contract value.

It is not inferred merely because an operation was skipped.

# 46. Repair semantics

A repair always creates a new artifact.

```text
parent_artifact_id = previous artifact
```

The parent remains immutable.

A repair must preserve evidence describing why it was requested.

Example:

```text
Artifact A
   ↓
Compile evidence
   ↓
Repair request
   ↓
Artifact B
```

---

# 47. Parser repair

When the failure is structural:

```text
artifact extraction failure
```

the first recovery operation SHOULD target parsing/framing.

Only when the artifact itself is invalid should an implementation repair request rewrite source code.

This preserves useful source content and avoids unnecessary LLM regeneration.

---

# 48. Final verification contract

Final verification shall operate on the exact candidate selected for commit.

Required:

```text
verify artifact identity
verify exact files
parse final artifact
static validate
compile exact bytes
runtime verify exact output
run mandatory tests
policy check
record evidence
```

Any mutation between those steps invalidates the final verification.

---

# 49. Commit contract

Commit shall be treated as a cryptographically checked materialization.

```text
FINAL_VERIFIED
    ↓
COMMIT_PENDING
    ↓
prepare
    ↓
stage exact bytes
    ↓
atomic write
    ↓
re-read committed bytes
    ↓
hash committed bytes
    ↓
compare against verified identity
    ↓
record COMMIT evidence
    ↓
COMMITTED
```

If the re-read hash differs:

```text
COMMIT_FAILED
```

The result SHALL NOT be reported as committed.

---

# 50. No force acceptance

There shall be no mechanism equivalent to:

```text
--force-commit
```

that changes:

```text
REJECTED
```

into:

```text
ACCEPTED
```

A developer may export an unverified draft, but it must remain outside the accepted artifact namespace.

For example:

```text
/workspace/draft/
```

versus:

```text
/workspace/final/
```

Only the latter contains accepted artifacts.

# 66. Sequence semantics

For one `(request_id, message_id)` stream:

```text
sequence
```

must monotonically increase.

The receiver shall detect:

```text
duplicate
out-of-order
gap
unexpected reset
```

A gap SHALL NOT be silently treated as complete response data.

---

# 67. Duplicate request semantics

`request_id` is the idempotency key.

Receiving the same command again with the same `request_id` SHALL NOT cause a second provider submission.

Possible result:

```text
existing request state
```

or:

```text
IDEMPOTENT_REPLAY
```

but never another prompt submission.

# 68. Session semantics

A GARP session is identified by:

```text
session_id
```

A session is bound to:

```text
provider
tab_id
conversation identity
```

The session survives actor replacement.

# 69. Tab semantics

A browser tab has:

```text

url
title
selected
provider
session_id
state
```

`tab_id` is authoritative.

`tab_index` is informational.

The index may change without changing tab identity. The architecture explicitly requires this distinction.

# 70. Page generation

# 78. GARP connection resilience

```text

 ↓

 ↓
```

# 79. Cancellation semantics

Cancellation propagates:

```text
task
 ↓
worker request
 ↓
GARP request
 ↓
Firefox session
 ↓

```

Each layer reports its own result.

Terminal state:

```text
CANCELLED
```

means cancellation has been acknowledged.

It does not mean:

```text
SUCCESS
```

# 80. Heartbeat

Both sides support:

```text

```

Suggested period:

```text

```

A heartbeat failure does not automatically destroy persistent session identity.

# 110. Canonical implementation rule

The most important implementation rule is:

```text
DO NOT MAKE THE IMPLEMENTATION MORE PERMISSIVE
THAN THE SPECIFICATION.
```

When implementation encounters ambiguity:

```text
reject
```

When evidence is missing:

```text
fail the gate
```

When identity is uncertain:

```text
fail verification
```

When the browser state is unknown:

```text
report unknown/error
```

When the AI response is malformed:

```text
PARSE_ERROR
```

When committed bytes differ from verified bytes:

```text
COMMIT_FAILED
```

The system's job is not to make questionable inputs look successful.

Its job is to make the boundary between:

```text
UNVERIFIED
```

and:

```text
VERIFIED
```

unmistakable.

# 111. Final implementation principle

The implementation shall preserve this transformation:

```text
UNTRUSTED INPUT
      ↓
STRICT INTERPRETATION
      ↓
IMMUTABLE ARTIFACT
      ↓
OBJECTIVE MEASUREMENT
      ↓
IMMUTABLE EVIDENCE
      ↓
DETERMINISTIC GATE
      ↓
FINAL RE-VERIFICATION
      ↓
BYTE-IDENTICAL COMMIT
```

and never:

```text
UNTRUSTED INPUT
      ↓
HEURISTIC CLEANUP
      ↓
ASSUMED CORRECT
      ↓
COMMIT
```

This implementation contract is therefore the layer from which the actual Delphi code, conformance tests, GAI definitions, and GARP implementation should now be derived.
