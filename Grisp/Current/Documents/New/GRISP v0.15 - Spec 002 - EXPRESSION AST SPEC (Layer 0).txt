=====================================================================
======  GRISP v0.15 - Spec 002 - EXPRESSION AST SPEC (Layer 0)  =====
=====================================================================

STATUS: Stable Draft
LAYER: Deterministic Engine Contract (Layer 0)
VERSION: grisp-expression-ast-v0.15
DEPENDENCIES:
  - Canonical IR v0.15
  - Transaction Model v0.15

---------------------------------------------------------------------
1. PURPOSE
---------------------------------------------------------------------
The GRISP Expression AST v0.15 defines the **only legal representation**
of all expressions inside the Canonical IR.

This AST:
  - Eliminates all string-based expressions
  - Ensures deterministic evaluation
  - Enables static analysis, read/write inference, and optimization
  - Is stable across GRISP versions
  - Is language-agnostic (Delphi, Rust, Python, etc.)

Every expression in:
  - rule patterns
  - rule actions
  - function calls
  - constraints
  - event payloads
  - object/array literals

MUST be represented using this AST.

---------------------------------------------------------------------
2. DESIGN PRINCIPLES
---------------------------------------------------------------------
- **No strings**: No embedded DSLs, no inline code, no ad-hoc syntax.
- **Fully normalized**: Every expression is a JSON object with a `kind`.
- **Deterministic**: No ambiguity, no implicit coercions.
- **Extensible**: `meta` fields allow tooling extensions.
- **Pure structure**: No trust, no runtime policy, no AI substrate logic.

---------------------------------------------------------------------
3. BASE EXPRESSION STRUCTURE
---------------------------------------------------------------------
Every expression node has:

{
  "kind": "string",
  "type_hint": "string | null",
  "meta": { ... }
}

- `kind` determines the node type.
- `type_hint` is optional static typing information.
- `meta` is ignored by engines but used by tools.

---------------------------------------------------------------------
4. EXPRESSION KINDS
---------------------------------------------------------------------
The allowed expression kinds are:

  - literal
  - var
  - field
  - call
  - binary
  - unary
  - conditional
  - collection
  - object
  - array

These are described below.

---------------------------------------------------------------------
5. LITERAL EXPRESSIONS
---------------------------------------------------------------------
{
  "kind": "literal",
  "literal_type": "integer | number | string | boolean | null",
  "value": <value>,
  "format_hint": "string | null",
  "meta": { ... }
}

Examples:
  - integer literal
  - string literal
  - boolean literal

Literal nodes MUST NOT contain trust metadata (trust lives outside IR).

---------------------------------------------------------------------
6. VARIABLE REFERENCES
---------------------------------------------------------------------
{
  "kind": "var",
  "name": "string",
  "namespace": "string | null",
  "meta": { ... }
}

- `name` refers to a pattern variable or let-binding.
- `namespace` is optional for nested scopes.

---------------------------------------------------------------------
7. FIELD ACCESS
---------------------------------------------------------------------
{
  "kind": "field",
  "var": "string | field-access | var-ref",
  "field": "string",
  "safe": false,
  "meta": { ... }
}

- `safe=true` means missing fields return null instead of error.

---------------------------------------------------------------------
8. FUNCTION CALLS
---------------------------------------------------------------------
{
  "kind": "call",
  "fn": "string",
  "args": [ <expression> ],
  "kwargs": { "name": <expression> },
  "meta": { ... }
}

- `fn` MUST reference a function defined in the Canonical IR.
- `args` and `kwargs` MUST be expression nodes.

---------------------------------------------------------------------
9. BINARY OPERATIONS
---------------------------------------------------------------------
{
  "kind": "binary",
  "op": "+ | - | * | / | % | == | != | < | > | <= | >= | and | or | in | not_in | contains",
  "left": <expression>,
  "right": <expression>,
  "meta": { ... }
}

Binary operations MUST be deterministic.

---------------------------------------------------------------------
10. UNARY OPERATIONS
---------------------------------------------------------------------
{
  "kind": "unary",
  "op": "- | not",
  "operand": <expression>,
  "meta": { ... }
}

---------------------------------------------------------------------
11. CONDITIONAL EXPRESSIONS
---------------------------------------------------------------------
{
  "kind": "conditional",
  "cond": <expression>,
  "then": <expression>,
  "else": <expression>,
  "meta": { ... }
}

All branches MUST be valid expressions.

---------------------------------------------------------------------
12. COLLECTION EXPRESSIONS
---------------------------------------------------------------------
{
  "kind": "collection",
  "source": {
    "type": "string",
    "query": { ... }
  },
  "order_by": [
    { "field": "string", "direction": "asc | desc" }
  ],
  "limit": 1,
  "meta": { ... }
}

Used for:
  - iterating over node sets
  - filtered collections
  - ordered selections

---------------------------------------------------------------------
13. OBJECT EXPRESSIONS
---------------------------------------------------------------------
{
  "kind": "object",
  "fields": {
    "fieldName": <expression>
  },
  "meta": { ... }
}

Used for:
  - event payloads
  - structured values
  - function arguments

---------------------------------------------------------------------
14. ARRAY EXPRESSIONS
---------------------------------------------------------------------
{
  "kind": "array",
  "items": [ <expression>, ... ],
  "meta": { ... }
}

Used for:
  - lists
  - multi-value payloads
  - composite structures

---------------------------------------------------------------------
15. META FIELD
---------------------------------------------------------------------
The `meta` field is an open extension point.

Engines MUST ignore unknown fields.

Tools MAY use:
  - source mapping
  - debugging info
  - static analysis hints
  - trust annotations (outside canonical IR)

---------------------------------------------------------------------
16. VALIDATION RULES
---------------------------------------------------------------------
The compiler MUST validate:
  - All expressions have a valid `kind`
  - All required fields are present
  - No unknown fields except inside `meta`
  - All nested expressions are valid AST nodes
  - No circular references
  - All function names exist in the Canonical IR

---------------------------------------------------------------------
17. WHAT IS NOT IN EXPRESSION AST v0.15
---------------------------------------------------------------------
The AST does NOT include:
  - trust metadata
  - clarify actions
  - runtime policy
  - AI substrate constructs
  - tool capability declarations

These belong to other specs.

---------------------------------------------------------------------
18. SUMMARY
---------------------------------------------------------------------
The Expression AST v0.15 is:
  - deterministic
  - normalized
  - minimal
  - stable
  - language-agnostic

It is the foundation for:
  - rule evaluation
  - static analysis
  - conflict detection
  - deterministic replay
