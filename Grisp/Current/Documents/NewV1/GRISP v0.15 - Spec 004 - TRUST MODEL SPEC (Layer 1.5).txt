=====================================================================
======  GRISP v0.15 - Spec 004 - TRUST MODEL SPEC (Layer 1.5)  ======
=====================================================================

STATUS: Stable Draft
LAYER: Trust & Provenance (Layer 1.5)
VERSION: grisp-trust-model-v0.15
DEPENDENCIES:
  - Canonical IR v0.15
  - Expression AST v0.15
  - Boundary Contract v0.15

---------------------------------------------------------------------
1. PURPOSE
---------------------------------------------------------------------
The GRISP Trust Model v0.15 defines how **every value** flowing through
the GRISP substrate acquires, propagates, and loses trust.

It ensures:
  - LLM-generated values cannot silently escalate privilege
  - Tool outputs cannot launder untrusted inputs
  - Human confirmations are explicit and auditable
  - Deterministic trust propagation across all operations
  - Full traceability of provenance

This model is the foundation for safe AI-driven automation.

---------------------------------------------------------------------
2. TRUST LEVELS
---------------------------------------------------------------------
Trust levels form a strict partial order:

  llm_asserted < tool_returned < system_derived < human_confirmed

Definitions:

- llm_asserted  
    Value originated from an LLM or unknown source.

- tool_returned  
    Value returned by a tool execution.

- system_derived  
    Value computed deterministically from trusted inputs.

- human_confirmed  
    Value explicitly approved by a human operator.

Special:
- unknown  
    Treated as llm_asserted.

---------------------------------------------------------------------
3. TRUST ANNOTATIONS
---------------------------------------------------------------------
Every value may carry:

_top-level trust_:
{
  "_trust": {
    "level": "tool_returned",
    "source": "task-service",
    "acquired_at": "...",
    "session_turn": 3
  }
}

_field-level trust_:
{
  "_field_trust": {
    "query_override": {
      "level": "llm_asserted",
      "source": "llm:session-42"
    }
  }
}

Field-level trust overrides top-level trust.

---------------------------------------------------------------------
4. TRUST IN EXPRESSION AST
---------------------------------------------------------------------
Expressions may include:

"meta": {
  "trust": {
    "level": "...",
    "source": "...",
    "session_turn": 3
  }
}

Engines MUST read trust from meta.trust when present.

---------------------------------------------------------------------
5. TRUST PROPAGATION RULES
---------------------------------------------------------------------
Fundamental rule:

  trust(result) = min(trust(inputs))

Examples:

- Arithmetic:
    tool_returned + llm_asserted → llm_asserted

- Field access:
    trust(field) = field-level trust OR top-level trust

- Conditionals:
    trust(if cond then a else b) = min(cond, a, b)

- Collections:
    trust(element) = min(collection, element)

---------------------------------------------------------------------
6. TRUST PROMOTION
---------------------------------------------------------------------
Trust can ONLY be promoted via a confirm action.

Implicit promotion is forbidden.

Promotion metadata:

{
  "promoted_by": "operator:alice",
  "promotion_reason": "Reviewed query"
}

---------------------------------------------------------------------
7. TOOL TRUST CLASSES
---------------------------------------------------------------------
Tools declare:

- verified
- external
- llm_facing
- privileged

llm_facing tools ALWAYS return llm_asserted.

privileged tools require human_confirmed inputs.

---------------------------------------------------------------------
8. TRUST GATES
---------------------------------------------------------------------
Default minimum trust required:

  update → tool_returned  
  create → tool_returned  
  delete → human_confirmed  
  call   → tool-defined  
  emit   → llm_asserted  
  clarify→ llm_asserted  

Runtime profiles may tighten gates.

---------------------------------------------------------------------
9. CONFIRM ACTION
---------------------------------------------------------------------
A confirm action suspends execution until a human approves.

{
  "confirm": "Task.query_override",
  "required_level": "human_confirmed",
  "reason": "Query targets privileged tool",
  "timeout_ms": 300000,
  "on_timeout": "fail"
}

---------------------------------------------------------------------
10. TAINT TRACKING
---------------------------------------------------------------------
Every value carries a taint tag (trust annotation).

Rules:
  - llm_asserted taints all downstream values
  - system_derived only applies if all inputs are trusted
  - taint persists across rule firings

---------------------------------------------------------------------
11. TAINT BOUNDARY RULES
---------------------------------------------------------------------
Rules may declare:

"metadata": {
  "taint_boundary": true
}

Such rules:
  - may accept llm_asserted inputs
  - MUST output system_derived or higher
  - are audited more strictly

---------------------------------------------------------------------
12. TRUST VIOLATIONS
---------------------------------------------------------------------
Types:

- INSUFFICIENT_TRUST
- TAINT_BOUNDARY_VIOLATION
- TRUST_PROMOTION_REJECTED

Example:

{
  "violation_type": "INSUFFICIENT_TRUST",
  "required_level": "tool_returned",
  "actual_level": "llm_asserted",
  "value_path": "Task.query_override"
}

---------------------------------------------------------------------
13. RESOLUTION TRACE INTEGRATION
---------------------------------------------------------------------
Every trust event is recorded:

- trust_assignment
- trust_propagation
- trust_gate_check
- trust_promotion

Trace entries MUST be immutable.

---------------------------------------------------------------------
14. TRUST DECAY (OPTIONAL)
---------------------------------------------------------------------
Deployments MAY define:

- human_confirmed → tool_returned after N days
- system_derived → tool_returned after M days

Decay is optional and implementation-specific.

---------------------------------------------------------------------
15. WHAT IS NOT IN TRUST MODEL v0.15
---------------------------------------------------------------------
Not included:
  - AI substrate semantics
  - Boundary contract structure
  - Canonical IR semantics
  - Runtime policy
  - Tool capability definitions

These are defined in other specs.

---------------------------------------------------------------------
16. SUMMARY
---------------------------------------------------------------------
The Trust Model v0.15 provides:

  - strict trust ordering
  - deterministic propagation
  - explicit promotion
  - taint tracking
  - trust gates
  - auditability
  - safe integration with LLMs

It is the backbone of secure AI-driven automation.
