GRISP SPEC 008 — ACTION MODEL (v0.17 DRAFT)

Status: Draft
Layer: 0 (Deterministic Core)
Depends on: Spec 001 Canonical IR, Spec 002 Expression AST, Spec 003 Node and Edge Model, Spec 004 Type System, Spec 005 Pattern Model, Spec 006 Match Discovery Model, Spec 007 Transaction and Conflict Model, Spec 014 Dependency Set Model

Purpose:
This specification defines the deterministic semantics of actions in GRISP. Actions describe how the state graph changes when a rule fires. The Action Model ensures that all engines evaluate actions identically, stage changes identically, and commit changes identically.

1. Overview
Actions are executed after a match is selected and validated. Actions must be deterministic, side-effect free during evaluation, and must produce a staged set of changes. Actions do not modify the state directly. Only the Transaction Model applies staged changes.

2. Action Types
The Action Model supports the following action types:
create_node
update_node
delete_node
create_edge
delete_edge
emit_event
Actions appear in the then clause of a rule. Actions must be evaluated in the order they appear.

3. Deterministic Evaluation
Action evaluation must be deterministic. All Expression ASTs used in actions must be evaluated using the deterministic rules defined in Spec 002. Actions must not depend on nondeterministic functions. Actions must not modify the state during evaluation.

4. Create Node
A create_node action has:
type: node type name
fields: mapping from field_name to Expression AST
Evaluation steps:
1. Evaluate all field expressions.
2. Validate field types.
3. Allocate a new node id.
4. Produce a staged node creation entry.
Node creation contributes an extent version increment for the node type at commit time.

5. Update Node
An update_node action has:
target: identifier referencing a bound node
fields: mapping from field_name to Expression AST
Evaluation steps:
1. Evaluate all field expressions.
2. Validate field types.
3. Produce a staged node update entry.
Node updates increment the node version at commit time. Node updates also increment predicate and ordering versions for fields used in filters or order_by expressions.

6. Delete Node
A delete_node action has:
target: identifier referencing a bound node
Evaluation steps:
1. Produce a staged node deletion entry.
Node deletion increments the node version and the extent version at commit time. Node deletion also removes all incident edges.

7. Create Edge
A create_edge action has:
type: edge type name
source: identifier referencing a bound node
target: identifier referencing a bound node
Evaluation steps:
1. Validate that source and target types match the edge type.
2. Allocate a new edge id.
3. Produce a staged edge creation entry.
Edge creation increments the edge version at commit time.

8. Delete Edge
A delete_edge action has:
target: identifier referencing a bound edge
Evaluation steps:
1. Produce a staged edge deletion entry.
Edge deletion increments the edge version at commit time.

9. Emit Event
An emit_event action has:
payload: Expression AST
Evaluation steps:
1. Evaluate the payload expression.
2. Produce an event entry.
Events do not affect deterministic state and do not participate in dependency tracking.

10. Action Ordering
Actions must be evaluated in the order they appear. Staged changes must preserve this order. Commit ordering is defined in Spec 007 and must not depend on action order.

11. Deterministic Node ID Allocation
Node ids must be unique but may be nondeterministic. Engines must not derive semantics from node id structure. Node id allocation must not affect deterministic behavior because node ids are treated as opaque identifiers.

12. Deterministic Edge ID Allocation
Edge ids must be unique but may be nondeterministic. Engines must not derive semantics from edge id structure. Edge id allocation must not affect deterministic behavior.

13. Interaction with Dependency Set Model
Actions do not add dependencies. Dependencies are computed during match discovery. However, actions may modify fields or structures that appear in dependency sets. Conflict detection ensures that such modifications do not violate determinism.

14. Interaction with Transaction Model
Actions produce staged changes. The Transaction Model:
- validates dependencies
- detects conflicts
- commits staged changes
Actions must not bypass the Transaction Model.

15. Interaction with Golden Files
Golden files must capture:
- evaluated action expressions
- staged node creations
- staged node updates
- staged node deletions
- staged edge creations
- staged edge deletions
- emitted events
Any deviation indicates nonconformance.

16. Invalid Actions
An action is invalid if:
- it references unknown node or edge types
- it references unknown bindings
- it produces type errors
- it violates structural constraints
- it uses nondeterministic functions
Invalid actions must cause transaction failure.

17. Extensibility
Future versions may extend actions with:
- deterministic aggregations
- deterministic batch operations
- deterministic structural rewrites
All extensions must preserve determinism.
