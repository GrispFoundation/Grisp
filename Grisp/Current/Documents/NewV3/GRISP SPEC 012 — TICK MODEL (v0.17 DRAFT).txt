GRISP SPEC 012 — TICK MODEL (v0.17 DRAFT)

Status: Draft
Layer: 0 (Deterministic Core)
Depends on: Spec 001 Canonical IR, Spec 006 Match Discovery Model, Spec 007 Transaction and Conflict Model, Spec 013 Selection Model, Spec 014 Dependency Set Model

Purpose:
This specification defines the Tick Model for GRISP. A tick is the fundamental unit of deterministic execution. Each tick consists of match discovery, selection, transaction execution, and state transition. The Tick Model ensures that all engines execute rules in the same order and produce identical results.

1. Overview
A tick is a deterministic execution cycle consisting of:
1. match discovery
2. match selection
3. transaction execution
4. commit or abort
5. event emission
6. tick finalization
Only one transaction may commit per tick. A tick must be fully deterministic.

2. Tick Lifecycle
The lifecycle of a tick is:
1. Begin tick
2. Discover matches
3. Select one match
4. Validate dependencies
5. Execute actions
6. Detect conflicts
7. Commit or abort
8. Emit events
9. End tick
If no matches are available, the tick performs no state changes.

3. Tick Start
At the start of a tick:
- the state is stable
- all version counters are current
- no staged changes exist
- match discovery begins from a clean snapshot

4. Match Discovery Phase
The engine must:
- enumerate all rules
- discover all matches for each rule
- compute dependency sets
- compute match keys
- compute match ages
Match discovery must be deterministic and must not modify the state.

5. Selection Phase
The engine must:
- compute a score for each match
- apply fairness adjustments
- break ties deterministically
- select exactly one match
If no matches exist, the tick ends with no state changes.

6. Transaction Phase
The engine must:
- validate dependencies
- evaluate actions
- stage changes
- detect conflicts
If validation or conflict detection fails, the match is discarded and the engine returns to match discovery.

7. Commit Phase
If no conflicts are detected:
- apply staged node creations
- apply staged node updates
- apply staged node deletions
- apply staged edge creations
- apply staged edge deletions
- update version counters
Commit must be atomic and deterministic.

8. Event Emission Phase
If the transaction commits:
- emit events in the order of emit_event actions
Events must not be emitted if the transaction aborts.

9. Tick End
At the end of the tick:
- the state is stable
- all version counters reflect committed changes
- match ages are updated
- the tick counter increments

10. Tick Counter
The engine maintains a tick counter starting at 1. The tick counter increments after each tick. The tick counter is used for:
- match age computation
- golden file recording
The tick counter must not affect deterministic semantics.

11. Deterministic Ordering Requirements
The following must be deterministic:
- match discovery order
- match selection order
- transaction execution order
- commit order
- event emission order
- tick ordering
Any nondeterministic ordering is forbidden.

12. No Parallel Execution
Ticks must not run in parallel. Transactions must not run in parallel. Match discovery must not run in parallel with state mutation. All execution must be strictly sequential.

13. Tick Termination Conditions
A tick terminates when:
- a transaction commits
- or no matches exist
- or all matches fail validation or conflict detection
If all matches fail, the tick ends with no state changes.

14. Interaction with Match Discovery Model
Match discovery occurs at the start of each tick. Match discovery must not see staged changes. Match discovery must be repeated after any transaction abort.

15. Interaction with Selection Model
The Selection Model chooses exactly one match per tick. The Tick Model executes that match. If the match fails, the Selection Model must choose a new match.

16. Interaction with Transaction Model
The Transaction Model executes the selected match. The Tick Model ensures that only one transaction may commit per tick.

17. Interaction with Dependency Set Model
Dependency sets are computed during match discovery. Dependency validation occurs during the transaction phase. The Tick Model ensures that dependency sets remain valid until validation.

18. Interaction with Golden File Model
Golden files must record:
- tick number
- discovered matches
- selected match
- dependency validation result
- conflict detection result
- staged changes
- committed changes
- events
Any deviation indicates nonconformance.

19. Extensibility
Future versions may extend the Tick Model with:
- deterministic multi-match execution
- deterministic batching
- deterministic tick grouping
All extensions must preserve determinism.

End of GRISP SPEC 012 — TICK MODEL (v0.17 DRAFT)
