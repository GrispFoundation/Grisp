GRISP SPEC 009 — EVENT MODEL (v0.17 DRAFT)

Status: Draft
Layer: 0 (Deterministic Core)
Depends on: Spec 001 Canonical IR, Spec 002 Expression AST, Spec 003 Node and Edge Model, Spec 004 Type System, Spec 005 Pattern Model, Spec 006 Match Discovery Model, Spec 007 Transaction and Conflict Model, Spec 008 Action Model

Purpose:
This specification defines the deterministic event model for GRISP. Events represent external notifications emitted by rules. Events do not affect deterministic state and do not participate in dependency tracking. The Event Model ensures that all engines emit identical events for the same Canonical IR and initial state.

1. Overview
Events are produced by emit_event actions. Events are immutable, deterministic outputs that may be consumed by external systems. Events do not modify the state graph. Events do not influence match discovery, selection, or conflict detection. Events are part of the observable behavior of a GRISP engine.

2. Event Structure
An event consists of:
event_id: a unique identifier
rule_id: the rule that emitted the event
payload: a value produced by evaluating an Expression AST
timestamp: optional engine-provided timestamp (non-deterministic, not part of golden files)
metadata: optional engine-defined metadata

Only event_id, rule_id, and payload are part of deterministic semantics.

3. Deterministic Event Payloads
The payload of an event must be produced by evaluating an Expression AST. Payload evaluation must be deterministic. Payloads may contain:
- primitive values
- lists
- maps
Payloads must not contain node or edge references. Payloads must not contain nondeterministic values.

4. Event Emission Semantics
Events are emitted during transaction commit. The sequence of emitted events must match the order of emit_event actions in the then clause. Events must not be emitted if the transaction aborts. Events must not be emitted during dependency validation or conflict detection.

5. Event Ordering
Events must be emitted in the order they appear in the then clause. If multiple events are emitted in a single transaction, their order must be preserved. If multiple transactions occur across ticks, events must be ordered by tick number and then by action order.

6. Event Identity
Each event must have a unique event_id. Event ids may be nondeterministic but must not affect deterministic semantics. Event ids must not be reused. Event ids must not encode semantic information.

7. Event Visibility
Events are visible to:
- external systems
- golden file capture
Events are not visible to:
- match discovery
- selection model
- dependency tracking
- conflict detection
Events must not influence deterministic execution.

8. Event Evaluation Rules
Event payload expressions must:
- be well-typed
- evaluate deterministically
- not reference nondeterministic functions
- not reference node or edge references directly
- not modify the state

9. Interaction with Transaction Model
Events are produced only if:
- dependency validation succeeds
- conflict detection succeeds
- commit succeeds
Events must be included in the transaction commit record. Events must not be emitted for aborted transactions.

10. Interaction with Dependency Set Model
Events do not contribute dependencies. Events do not depend on version counters. Events do not affect dependency validation. Events must not reference fields or structures that would require dependency tracking.

11. Interaction with Golden Files
Golden files must capture:
- event emission order
- event payloads
- rule_id associated with each event
Golden files must not capture:
- event_id
- timestamps
- engine metadata
Any deviation indicates nonconformance.

12. Invalid Events
An event is invalid if:
- its payload expression is ill-typed
- its payload expression references nondeterministic functions
- its payload expression references node or edge references
- its payload expression fails evaluation
Invalid events must cause transaction failure.

13. Event Consumers
Event consumers are external to the deterministic core. Engines may:
- deliver events to subscribers
- log events
- forward events to external systems
Event delivery must not affect deterministic execution.

14. Extensibility
Future versions may extend the Event Model with:
- structured event schemas
- deterministic event batching
- event routing rules
All extensions must preserve determinism.
