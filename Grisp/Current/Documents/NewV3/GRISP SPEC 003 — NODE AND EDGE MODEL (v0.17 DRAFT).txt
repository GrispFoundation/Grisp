GRISP SPEC 003 — NODE AND EDGE MODEL (v0.17 DRAFT)

Status: Draft
Layer: 0 (Deterministic Core)
Depends on: Spec 001 Canonical IR, Spec 011 State Model, Spec 014 Dependency Set Model

Purpose:
This specification defines the static and runtime structure of nodes and edges in GRISP. It describes how node types and edge types declared in the Canonical IR map to concrete instances in the state graph. It also defines the deterministic rules for identity, field storage, edge storage, and structural constraints. The Node and Edge Model is the foundation for all deterministic state transitions.

1. Overview
The state graph consists of node instances and edge instances. Node instances represent typed entities with fields. Edge instances represent typed directed relationships between nodes. All state transitions operate on these instances. The Node and Edge Model defines how instances are created, updated, deleted, and validated.

2. Node Instance Structure
A node instance has the following fields:
id: a globally unique identifier string
type: the node type name as declared in the Canonical IR
fields: a mapping from field_name to field_value
version: a monotonically increasing integer used for conflict detection
metadata: optional engine-defined metadata not used for deterministic semantics

Node ids must be unique across the entire state graph. Node ids must be stable for the lifetime of the node. Node ids must not be reused after deletion.

3. Node Field Semantics
Each node type defines a fixed set of fields. A node instance must contain exactly those fields. Field values must conform to the field type declared in the Canonical IR. Field updates must increment the node version counter. Field updates must be atomic and deterministic.

4. Node Creation
A create_node action produces a new node instance. The engine must:
- allocate a unique node id
- set the node type
- initialize all fields to the values provided in the action
- set version to 1
- insert the node into the state graph
- increment the extent version for the node type

Node creation must be deterministic with respect to field initialization. Node id generation may be nondeterministic but must not affect deterministic semantics because node ids are not compared numerically.

5. Node Update
An update_node action modifies one or more fields of an existing node. The engine must:
- evaluate all field expressions deterministically
- apply all field updates atomically
- increment the node version counter
- increment predicate and ordering versions for any updated fields

Node updates must not change the node id or node type.

6. Node Deletion
A delete_node action removes a node instance. The engine must:
- increment the node version counter before deletion
- remove all edges incident to the node
- remove the node from the state graph
- increment the extent version for the node type

Node deletion invalidates any match that depends on the node or its fields.

7. Edge Instance Structure
An edge instance has the following fields:
id: a globally unique identifier string
type: the edge type name as declared in the Canonical IR
source: the id of the source node
target: the id of the target node
version: a monotonically increasing integer used for conflict detection
metadata: optional engine-defined metadata not used for deterministic semantics

Edge ids must be unique across the entire state graph. Edge ids must not be reused after deletion.

8. Edge Semantics
Edge types define allowed source and target node types. All edge instances must conform to these constraints. Edge instances do not contain fields beyond source, target, and metadata. Edge instances participate in dependency tracking via Edge dependencies.

9. Edge Creation
A create_edge action produces a new edge instance. The engine must:
- allocate a unique edge id
- set the edge type
- set the source and target node ids
- set version to 1
- insert the edge into the state graph
- increment the edge version counter for the edge type

Edge creation must be deterministic with respect to source and target resolution.

10. Edge Deletion
A delete_edge action removes an edge instance. The engine must:
- increment the edge version counter for the edge type
- remove the edge from the state graph

Edge deletion invalidates any match that depends on the edge type.

11. Structural Constraints
Node and edge types may declare multiplicity constraints. Engines must enforce:
- one-to-one
- one-to-many
- many-to-one
- many-to-many

Violations must cause transaction failure before commit.

12. Identity and Determinism
Node and edge ids must be treated as opaque identifiers. Engines must not derive ordering or semantics from the lexical form of ids. All deterministic ordering must be explicitly defined in the Canonical IR or Expression AST.

13. Interaction with Dependency Set Model
Node and edge instances contribute version counters used in dependency validation. The following version counters must be maintained:
- node version
- field-level predicate versions
- field-level ordering versions
- type-level extent versions
- edge-type version counters

Dependency validation uses these counters to determine whether a match remains valid.

14. Interaction with Transaction Model
All node and edge operations occur within transactions. Transactions must:
- stage node and edge operations
- validate dependencies before commit
- apply operations atomically
- update version counters deterministically

15. Interaction with Golden Files
Golden files must capture:
- node creation and deletion events
- edge creation and deletion events
- version counter changes
- structural state transitions

Golden files must not depend on nondeterministic node or edge ids.

16. Extensibility
Future versions may extend node and edge metadata, field types, or structural constraints. All extensions must preserve determinism and must integrate with the Dependency Set Model.
