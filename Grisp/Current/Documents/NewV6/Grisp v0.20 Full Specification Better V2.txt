GRISP DETERMINISTIC KERNEL SPECIFICATION v0.20

SPEC 000 CORE PRINCIPLES

The GRISP Deterministic Kernel defines a fully deterministic execution model for rule-driven state transitions over a typed graph.

For identical Canonical IR and identical initial state, all conformant engines must produce identical observable behavior.

Observable behavior consists solely of:

* Committed state transitions
* Emitted events
* Golden file output

All other implementation details are non-normative.

The kernel is governed by the following principles:

1. Determinism

All observable behavior must be deterministic.

The following are forbidden within deterministic semantics:

* Floating point arithmetic
* Random number generation
* System time
* Memory addresses
* Pointer identity
* Thread scheduling
* Hash-based ordering
* Runtime metadata
* Engine-specific behavior

2. Explicitness

All reads, writes, dependencies, identifiers, ordering rules, and version counters must be explicitly represented.

No implicit reads are permitted.

3. Frozen Discovery

Match discovery occurs exactly once per tick.

The resulting discovery snapshot is immutable for the remainder of the tick.

4. Dependency Validation

Dependency validation is the sole correctness mechanism.

Conflict detection does not exist.

5. Single Commit

At most one transaction may commit per tick.

6. Canonical Ordering

Every ordered operation must have an explicitly defined deterministic ordering.

7. Canonical Serialization

All deterministic artifacts must serialize canonically.

8. Referential Transparency

Expressions are pure.

Actions are effectful only during commit.

9. No Identifier Reuse

Identifiers are unique for the lifetime of the graph.

Deleted identifiers must never be reused.

10. Cross-Engine Reproducibility

All conformant engines must produce identical golden files.

---

SPEC 001 NUMERIC MODEL

All numeric values are signed 64-bit integers.

Floating point values are forbidden.

Fixed-point values are represented as scaled integers.

Scale factors must be explicitly declared.

Division uses truncation toward zero.

Modulo uses standard signed integer remainder semantics.

Arithmetic overflow is a fatal conformance error.

The following counters must never overflow:

* tick_counter
* sequence counters
* match_age
* existence_version
* field_version
* predicate_version
* ordering_version
* extent_version
* edge_type_version
* adjacency_version

Overflow of any deterministic counter is a fatal conformance error.

---

SPEC 002 TYPE SYSTEM

The type system defines:

* Node Types
* Edge Types
* Field Types

All types must be explicitly declared.

Type inference is forbidden.

Allowed field types:

* Integer
* FixedPoint
* Boolean
* String
* List
* Map
* Identifier

Fields must be deterministic and serializable.

Runtime handles, pointers, references, and engine-specific objects are forbidden.

---

SPEC 003 IDENTIFIER MODEL

Identifiers are deterministic strings.

Node identifier format:

type_name:sequence

Edge identifier format:

type_name:sequence

Sequence counters are maintained independently for each type.

Sequence counters:

* start at 0
* increment monotonically
* never decrease
* never wrap
* are never reused

Identifier allocation occurs only during commit.

Identifier ordering is defined as:

1. type_name lexicographic ascending
2. sequence numeric ascending

This ordering defines global identifier ordering.

Whenever the specification refers to:

ascending node_id

or

ascending edge_id

it refers to identifier ordering defined herein.

---

SPEC 004 STATE MODEL

Deterministic state consists of:

* Nodes
* Edges
* Version Counters
* Sequence Counters
* Tick Counter

A node consists of:

* id
* type
* fields
* existence_version
* field_versions

field_versions contains one counter per field.

An edge consists of:

* id
* type
* source
* target
* fields
* field_versions

The state contains:

extent_version[node_type]

predicate_version[node_type][field_name]

ordering_version[node_type][field_name]

edge_type_version[edge_type]

adjacency_version[node_id][edge_type][direction]

Direction is:

* incoming
* outgoing

All version counters begin at 1.

The state must satisfy:

* node identifiers unique
* edge identifiers unique
* no dangling edges
* all fields type-valid
* all constraints satisfied

---

SPEC 005 CANONICAL IR

Canonical IR is the sole executable representation of a GRISP manifest.

All manifests must compile into Canonical IR before execution.

Canonical IR contains:

* Type Definitions
* Function Definitions
* Rule Definitions
* Initial State
* Constants

Canonical IR must contain:

* No syntactic sugar
* No implicit defaults
* No runtime metadata
* No engine-specific structures

Canonical IR must be stable under round-trip serialization.

Parsing and re-serializing Canonical IR must produce identical output.

---

SPEC 006 FUNCTION MODEL

Functions are either:

* pure
* effect_deterministic

Pure functions:

* are referentially transparent
* may only depend on arguments
* may not read state

effect_deterministic functions:

* are referentially transparent
* may read state
* may not modify state

Every effect_deterministic function must declare:

declared_reads

declared_reads specifies all dependency types potentially read by the function.

Dependency extraction must include declared_reads.

Recursion is forbidden.

Function execution must terminate.

Nondeterministic functions are forbidden.

---

SPEC 007 EXPRESSION MODEL

Expressions represent pure computation.

Expressions may contain:

* literals
* bindings
* arithmetic
* boolean logic
* collection expressions
* function calls

Expressions must not:

* mutate state
* allocate identifiers
* observe runtime metadata
* observe events
* perform nondeterministic operations

Short-circuit evaluation is permitted.

Dependency extraction must analyze all branches.

---

SPEC 008 PATTERN MODEL

Patterns bind graph elements.

Pattern evaluation is deterministic.

Node enumeration uses ascending node_id ordering.

Edge enumeration uses ascending edge_id ordering.

Pattern constraints may use expressions.

Patterns may contain let bindings.

Let bindings:

* are evaluated during discovery
* are immutable
* do not participate in match identity

Pattern evaluation must not mutate state.

---

SPEC 009 MATCH DISCOVERY MODEL

Discovery occurs exactly once per tick.

Discovery produces a frozen snapshot.

A match consists of:

* rule_id
* bindings
* let_values
* dependencies
* dependency_snapshot
* match_key

Match discovery must not:

* mutate state
* allocate identifiers
* observe runtime metadata
* observe events

Match identity is defined by match_key.

match_key consists of:

* rule_id
* bindings

Bindings are serialized as:

name=identifier

Binding names are sorted lexicographically.

Let values are excluded from match identity.

---

SPEC 010 DEPENDENCY MODEL

Dependency types are:

NodeExistence(node_id)

Field(element_id, field_name)

Predicate(node_type, field_name)

Ordering(node_type, field_name)

Extent(node_type)

EdgeType(edge_type)

Adjacency(node_id, edge_type, direction)

Dependency extraction is mandatory for:

* patterns
* where clauses
* let expressions
* priority expressions
* action argument expressions
* event payload expressions
* function declared_reads

Dependency extraction must analyze all branches.

Dependency extraction must be complete.

Required validation mapping:

NodeExistence(node_id)
→ existence_version

Field(element_id, field_name)
→ field_versions[field_name]

Predicate(node_type, field_name)
→ predicate_version[node_type][field_name]

Ordering(node_type, field_name)
→ ordering_version[node_type][field_name]

Extent(node_type)
→ extent_version[node_type]

EdgeType(edge_type)
→ edge_type_version[edge_type]

Adjacency(node_id, edge_type, direction)
→ adjacency_version[node_id][edge_type][direction]

A match validates iff every dependency version equals its snapshot version.

No additional correctness mechanism exists.

---

SPEC 011 MATCH LIFECYCLE MODEL

Matches persist across ticks through match_key identity.

match_age is defined as:

number of consecutive ticks in which the same match_key appears.

New matches begin with:

match_age = 0

If a match disappears:

its age is forgotten.

If rediscovered later:

it is treated as a new match.

match_age overflow is a fatal conformance error.

---

SPEC 012 SELECTION MODEL

Selection operates exclusively on the discovery snapshot.

For each match:

score =
(base_priority × priority_scale)
+
(match_age × fairness_scale)

All calculations use signed 64-bit arithmetic.

Overflow is a fatal conformance error.

Matches are ordered by:

1. score descending
2. match_key ascending

Selection must not:

* mutate state
* allocate identifiers
* perform validation

---

SPEC 013 ACTION MODEL

Action evaluation occurs after successful dependency validation.

Action evaluation is pure.

Actions may not:

* mutate state
* allocate identifiers
* introduce new reads

Permitted actions:

CreateNode

CreateEdge

UpdateField

DeleteEdge

DeleteNode

EmitEvent

All expressions contained within action arguments participate in dependency extraction.

---

SPEC 014 TRANSACTION MODEL

A transaction consists of:

1. dependency validation
2. action evaluation
3. write staging
4. commit
5. event publication

Only one transaction may commit per tick.

If validation fails:

the candidate match is discarded.

The next ranked match is considered.

---

SPEC 015 COMMIT MODEL

Commit applies staged writes atomically.

Partial commit is forbidden.

Commit order is:

1. CreateNode
2. CreateEdge
3. UpdateField
4. DeleteEdge
5. DeleteNode

Identifier allocation occurs during CreateNode and CreateEdge processing.

DeleteNode automatically stages deletion of all incident edges.

Deletion of an edge increments:

* edge_type_version
* adjacency_version of both endpoints
* existence_version of both endpoints

Node creation increments:

* extent_version
* predicate_version for all fields
* ordering_version for all fields

Node deletion increments:

* extent_version
* predicate_version for all fields
* ordering_version for all fields

Field update increments:

* field_versions[field]
* predicate_version
* ordering_version

Commit must preserve all state invariants.

---

SPEC 016 EVENT MODEL

Events are deterministic outputs.

Events consist of:

* rule_id
* payload

Events become visible only after successful commit.

Event payload expressions:

* are pure
* participate in dependency extraction
* may not introduce new reads

Events must not influence matching or execution.

---

SPEC 017 TICK MODEL

Tick execution proceeds:

1. Increment tick_counter
2. Discover matches
3. Compute scores
4. Rank matches
5. Select candidate
6. Validate dependencies
7. If invalid, continue ranking
8. If valid, evaluate actions
9. Commit transaction
10. Publish events
11. End tick

Discovery occurs exactly once.

Rediscovery within a tick is forbidden.

At most one transaction may commit.

---

SPEC 018 CANONICAL SERIALIZATION

Canonical serialization uses:

* UTF-8 encoding
* LF line endings
* lexicographically sorted object keys
* deterministic list ordering
* canonical integer encoding

Integers:

* no leading zeros
* base 10

All deterministic artifacts must use canonical serialization.

This includes:

* Canonical IR
* Golden Files
* Conformance Outputs

Round-trip serialization must be stable.

---

SPEC 019 GOLDEN FILE MODEL

Golden files capture observable behavior only.

Normative fields:

* initial_state
* ticks
* final_state

Each tick contains:

* tick_number
* selected_match_key
* committed_changes
* events

Diagnostic information is non-normative.

If present, diagnostics must be ignored for conformance.

---

SPEC 020 CONFORMANCE

A conformant engine must:

* implement every normative rule
* reject invalid Canonical IR
* prohibit nondeterminism
* prohibit floating point arithmetic
* prohibit identifier reuse
* prohibit counter overflow

For identical:

* Canonical IR
* Initial State

all conformant engines must produce identical:

* committed changes
* emitted events
* final state
* golden files

Conformance is determined exclusively through observable behavior defined by this specification.

END OF GRISP DETERMINISTIC KERNEL SPECIFICATION v0.20

My assessment: this is much closer to a freeze candidate than the earlier versions because the concepts have been reduced to a small core set, the dependency validation mappings are explicit, 
extent_version is restored, action expressions are formally included in dependency extraction,
node deletion semantics are defined, and the previously dangling function concept now has its own model. 
The remaining work I'd do before a v1.0 freeze would be mostly adding precise examples and conformance test vectors rather than changing architecture.
