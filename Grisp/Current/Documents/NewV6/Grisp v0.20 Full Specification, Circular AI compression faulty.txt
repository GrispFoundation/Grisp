SPEC 000 Core Principles

The GRISP deterministic kernel defines a fully deterministic, replay‑safe, cross‑engine‑consistent execution model for rule‑driven state transitions over a typed graph. All conformant engines must produce identical observable behavior for identical manifests and initial states. The following principles govern all deterministic semantics.

Determinism
All observable behavior must be deterministic. No floating point arithmetic, no nondeterministic functions, no hash‑based ordering, no runtime metadata in semantics, and no nondeterministic identifier allocation are permitted.

Explicitness
All reads, writes, dependencies, identifiers, ordering rules, and version counters must be explicit in the Canonical IR. No implicit behavior is permitted.

Single‑Commit Tick
Each tick may commit at most one transaction. Conflict detection is removed from the deterministic kernel. Dependency validation is the sole mechanism for determining match validity.

Frozen Discovery Snapshot
Match discovery occurs exactly once per tick and produces a frozen discovery snapshot. All selection, validation, and commit operations must use this snapshot. Rediscovery within the same tick is forbidden.

Dependency Validation
A match is valid if and only if all dependency snapshots match the current state. No other correctness mechanism exists. Dependency validation subsumes conflict detection.

Canonical Ordering
All lists, collections, match enumerations, and identifier comparisons must follow deterministic ordering rules. All tie‑breaking must use lexicographic ordering of canonical identifiers, defined as raw byte‑by‑byte comparison of UTF‑8 encoded strings.

Canonical Serialization
All deterministic outputs, including golden files, must use canonical serialization: UTF‑8, lexicographically sorted keys, deterministic integer encoding, deterministic list ordering, and no floating point values. Golden files must serialize as canonical JSON with no comments, no trailing commas, and integers without leading zeros.

Deterministic Identifiers
Node and edge identifiers must be allocated deterministically according to the Identifier Model. Identifiers must not depend on runtime metadata, memory layout, timestamps, random numbers, or hash functions. Identifiers must not be reused. Sequence counters must persist across ticks and must be part of deterministic state.

No Runtime Metadata in Semantics
Runtime metadata may exist in engines but must not participate in matching, dependency extraction, selection, validation, commit, or golden file output.

Minimal Observable Surface
Golden files must capture only observable deterministic behavior: initial state, selected match, committed changes, events, and final state. Diagnostic information is optional and non‑normative.

Referential Transparency
Expressions must be pure and referentially transparent. Actions must not introduce new reads. Event payload expressions must not introduce new dependencies beyond those already extracted from the expressions that computed their inputs.

No Implicit Reads
All reads must be captured by dependency extraction. Engines may include additional dependencies but must not omit required ones.

No Identifier Reuse
Identifiers must never be reused. Deleted identifiers must not reappear. Sequence counters must never decrease.

No Version Counter Wrap
Version counters and sequence counters must be 64‑bit signed integers. Overflow is a fatal conformance error. If overflow would occur, the tick must abort with no state changes and the engine must report a fatal conformance error.

Cross‑Engine Reproducibility
Any conformant engine must produce identical golden files for identical manifests and initial states. All deterministic semantics must be fully reproducible across implementations, platforms, and languages.

End of SPEC 000.

SPEC 001 Canonical IR

The Canonical IR is the fully explicit, fully deterministic representation of a GRISP manifest. All manifests must be compiled into Canonical IR before execution. Canonical IR must contain no implicit behavior. All field accesses, collection operations, function calls, action expressions, event payload expressions, and dependency declarations must be explicit.

Canonical IR must serialize deterministically. All objects must serialize with lexicographically sorted keys using raw UTF‑8 byte ordering. All lists must preserve declared order. All integers must serialize without leading zeros. All strings must serialize as UTF‑8. Floating point values are forbidden. All numeric values must be integers or fixed‑point integers represented as integers.

Canonical IR must not contain runtime metadata, pointers, references, nondeterministic values, or engine‑specific structures. Canonical IR must not contain implicit defaults. All defaults must be explicitly represented.

Canonical IR must be stable under round‑trip serialization. A manifest compiled to Canonical IR, serialized, and reloaded must produce identical Canonical IR.

Canonical IR must include explicit dependency declarations for all effect_deterministic functions. Each function must declare the fields, collections, and dependency types it reads. Engines must verify that declared dependencies match the function body. Circular function dependencies are forbidden and must be rejected before execution.

Canonical IR must include explicit rule identifiers. Rule identifiers must be unique, stable, and deterministic. Rule identifiers must not depend on runtime metadata or nondeterministic values. Rule identifiers must be preserved across serialization and must appear in match_key.

Canonical IR must include explicit type definitions for all node types, edge types, and field types. Fixed‑point field types must declare their scale factor explicitly. Engines must not infer scale factors.

Canonical IR must include explicit ordering for rule action lists. The textual order of actions in Canonical IR determines the deterministic ordering of staged writes during commit.

Canonical IR must include explicit initial values for all fields of all nodes in initial_state. No implicit initialization is permitted.

Canonical IR must include explicit definitions for all effect_deterministic functions, including their declared reads, argument types, return types, and bodies. Canonical IR must not include nondeterministic or side‑effecting functions.

Canonical IR must include explicit pattern definitions, including variable names, type bindings, and where clauses. Canonical IR must not infer pattern structure.

Canonical IR must include explicit event definitions, including payload expressions. Event payload expressions must not introduce new dependencies beyond those already extracted from their constituent expressions.

Canonical IR must include explicit collection definitions, including source type, filter expression, order_by list, and limit. Canonical IR must not infer collection semantics.

Canonical IR must include explicit dependency extraction results for each rule. Engines must verify that dependency extraction performed at compile time matches the dependency extraction algorithm defined in the specification.

Canonical IR must include explicit version counter initialization for initial_state, including existence_version, field_versions, predicate_version, ordering_version, extent_version, edge_type_version, and sequence counters for all node and edge types.

Canonical IR must include explicit error conditions for manifest validation. Any manifest that violates type rules, dependency rules, identifier rules, or function rules must be rejected before execution.

End of SPEC 001.

SPEC 002 Type System

The type system defines all node types, edge types, and field types used in the deterministic kernel. All types must be explicitly declared in the Canonical IR. No type inference is permitted. All field types must be deterministic, serializable, and free of nondeterministic behavior.

Node types define a set of named fields. Each field must have a declared type. Field types may be integer, fixed‑point integer, string, boolean, or other deterministic scalar types defined by the manifest. Floating point types are forbidden. Fixed‑point integer types must declare an explicit scale factor. Engines must not infer scale factors.

Edge types define a source node type, a target node type, and an optional set of fields. Edge fields follow the same type rules as node fields. Edge types must be explicitly declared. No implicit edge types are permitted.

Each node type must have the following version counters in state: predicate_version[node_type][field_name], ordering_version[node_type][field_name], and extent_version[node_type]. predicate_version increments when any node of that type updates the specified field or when any node of that type is created or deleted. ordering_version increments when any node of that type updates the specified field or when any node of that type is created or deleted. extent_version increments when any node of that type is created or deleted.

Each edge type must have edge_type_version[edge_type] in state. edge_type_version increments when any edge of that type is created or deleted.

Node identifiers must follow the Identifier Model. Edge identifiers must follow the Identifier Model. Identifiers must not be reused. Identifiers must not depend on runtime metadata or nondeterministic values.

Field types must not include references, pointers, handles, or runtime objects. Field types must not include nondeterministic values. Field types must not include floating point values. Field types must serialize deterministically.

All type definitions must appear in Canonical IR before any rule definitions. All rules must reference only declared types. Any reference to an undeclared type is a manifest error.

End of SPEC 002.


SPEC 003 Expression Model

The expression model defines all deterministic expressions that may appear in patterns, where clauses, filter expressions, order_by expressions, let expressions, action arguments, event payload expressions, and effect_deterministic function bodies. All expressions must be deterministic, total, and free of side effects. Expressions must not depend on runtime metadata, nondeterministic values, or external I/O.

Expressions operate over bound variables, literal values, deterministic functions, and deterministic collections. Expressions must not allocate identifiers. Expressions must not mutate state. Expressions must not observe staged writes. Expressions must not observe events. Expressions must not observe tick counters, match_age, or any runtime metadata.

Expressions may read fields of bound nodes or edges. Any field access in any expression must be included in dependency extraction. Field accesses must be explicit in Canonical IR. No implicit field accesses are permitted.

Expressions may call pure functions. Pure functions must be total, deterministic, and side‑effect free. Pure functions must not read or write state. Pure functions must not depend on nondeterministic values. Pure functions must not depend on runtime metadata.

Expressions may call effect_deterministic functions. Effect_deterministic functions must declare all state reads in Canonical IR. Engines must verify that the function body does not read any state outside its declared reads. Calls to effect_deterministic functions must contribute their declared dependencies to the rule’s dependency set. Circular function dependencies are forbidden.

Expressions may construct collections. A collection expression must specify a source type, a filter expression, an order_by list, and an optional limit. Collection expressions must not infer filter or ordering semantics. All filter and ordering expressions must be explicit. Collection expressions must not depend on nondeterministic ordering. Collection expressions must not depend on runtime metadata.

Expressions may reference let‑bound values. Let expressions must be evaluated deterministically and must not introduce new dependencies beyond those extracted from their constituent expressions. Let expressions must not mutate state. Let expressions must not allocate identifiers. Let expressions must not depend on nondeterministic values.

Expressions may appear in event payloads. Event payload expressions must not introduce new dependencies beyond those already extracted from the expressions that computed their inputs. Event payload expressions must not read fields or nodes that are not already part of the rule’s dependency set.

Expressions must not reference nodes or edges created in the same transaction. Expressions must operate only on the state visible at match discovery time. Expressions must not reference identifiers that do not exist in the discovery snapshot.

Expressions must be referentially transparent. Evaluating the same expression with the same inputs must produce the same output. Expressions must not depend on evaluation order. Expressions must not depend on short‑circuit behavior for dependency extraction; dependency extraction must consider all branches.

Expressions must serialize deterministically in Canonical IR. All expression structures must be explicit. All function calls must be explicit. All field accesses must be explicit. All collection definitions must be explicit. All literal values must be explicit.

End of SPEC 003.


SPEC 004 State Model

The state model defines the complete deterministic state visible to the rule engine. All conformant engines must maintain identical logical state for identical manifests and initial states. The state model must not contain runtime metadata, nondeterministic values, or engine‑specific structures. Only the structures defined in this specification may appear in deterministic state.

The state consists of the following components:

1. Nodes  
A node is an instance of a declared node type. Each node has a deterministic identifier of the form type_name:sequence. Each node contains a set of fields defined by its type. Each field stores a deterministic value. Each node maintains the following version counters: existence_version and field_versions[field_name].

existence_version increments when any edge incident to the node is created or deleted and increments immediately before the node is deleted. existence_version must be at least 1 for all nodes in initial_state. existence_version must never wrap. Overflow is a fatal conformance error.

field_versions[field_name] increments when the corresponding field is updated. field_versions[field_name] must be at least 1 for all fields in initial_state. field_versions must never wrap. Overflow is a fatal conformance error.

2. Edges  
An edge is an instance of a declared edge type. Each edge has a deterministic identifier of the form type_name:sequence. Each edge references a source node and a target node. Each edge may contain fields defined by its type. Edges do not maintain per‑edge version counters. Edge invalidation is handled through edge_type_version, adjacency dependencies, and node existence_version.

3. Node type version counters  
Each node type T maintains predicate_version[T][field_name], ordering_version[T][field_name], and extent_version[T].

predicate_version[T][field_name] increments when any node of type T updates the specified field or when any node of type T is created or deleted.

ordering_version[T][field_name] increments when any node of type T updates the specified field or when any node of type T is created or deleted.

extent_version[T] increments when any node of type T is created or deleted.

All node type version counters must be at least 1 in initial_state. All must be 64‑bit signed integers. Overflow is a fatal conformance error.

4. Edge type version counters  
Each edge type E maintains edge_type_version[E]. edge_type_version[E] increments when any edge of type E is created or deleted. edge_type_version[E] must be at least 1 in initial_state. Overflow is a fatal conformance error.

5. Sequence counters  
Each node type T maintains sequence_counter[T]. Each edge type E maintains sequence_counter[E]. These counters determine the next sequence number for identifier allocation. sequence_counter[T] must be at least the maximum sequence observed among all existing nodes of type T. sequence_counter[E] must be at least the maximum sequence observed among all existing edges of type E. Sequence counters must be part of deterministic state and must appear in initial_state and final_state. Sequence counters must never decrease. Sequence counters must never wrap. Overflow is a fatal conformance error.

6. Tick counter  
The tick counter is a deterministic integer that increments at the start of each tick. The tick counter must be part of deterministic state. The tick counter must never wrap. Overflow is a fatal conformance error.

7. Events  
Events produced by committed transactions are not part of state but are part of deterministic output. Events must not influence deterministic state. Events must not influence dependency extraction. Events must not influence match discovery.

8. No runtime metadata  
The state must not contain timestamps, memory addresses, nondeterministic identifiers, or any engine‑specific metadata. The state must not contain caches, indexes, or auxiliary structures unless they are fully derived from deterministic state and do not appear in golden files.

9. Deterministic initialization  
initial_state must contain all nodes, edges, field values, version counters, and sequence counters. No implicit initialization is permitted. All version counters and sequence counters must be explicitly present or deterministically derived from initial_state according to the rules of this specification.

10. Deterministic evolution  
All state changes must occur only through committed transactions. No other mechanism may mutate state. No state mutation may occur during match discovery, selection, or validation.

End of SPEC 004.


SPEC 005 Pattern Model

The pattern model defines how rules bind nodes and edges from the state graph. Patterns must be explicit in Canonical IR. No implicit pattern structure is permitted. Patterns must not depend on runtime metadata or nondeterministic values. Patterns must not allocate identifiers. Patterns must not mutate state.

A pattern consists of one or more bindings. Each binding associates a variable name with a declared node type or edge type. Each binding must be explicit. Each binding must appear exactly once. Patterns must not contain duplicate variable names. Patterns must not contain undeclared types.

Binding a node introduces a NodeExistence dependency on that node. NodeExistence(node_id) snapshots and validates against the node’s existence_version. Binding a node does not introduce any field dependencies unless fields are explicitly accessed in expressions. Binding a node does not introduce any adjacency dependencies unless adjacency is explicitly referenced in expressions.

Binding an edge introduces a NodeExistence dependency on the source node and the target node. Binding an edge introduces an EdgeType dependency on the edge’s type. Binding an edge does not introduce any field dependencies unless fields are explicitly accessed in expressions. Binding an edge does not introduce any adjacency dependencies unless adjacency is explicitly referenced in expressions.

Patterns may include where clauses. Where clauses must be deterministic expressions. Where clauses must not allocate identifiers. Where clauses must not mutate state. Where clauses must not depend on nondeterministic values. Where clauses must not depend on runtime metadata. Where clauses must not reference nodes or edges created in the same transaction.

Where clauses may read fields of bound nodes or edges. Any field access in a where clause must be included in dependency extraction. Field dependencies must snapshot field_versions[field_name] only. Field dependencies must not snapshot existence_version.

Where clauses may call pure functions. Where clauses may call effect_deterministic functions. Calls to effect_deterministic functions must contribute their declared dependencies to the rule’s dependency set.

Where clauses may reference collections. Collection expressions must be explicit. Collection expressions must not infer filter or ordering semantics. Collection expressions must not depend on nondeterministic ordering. Collection expressions must not depend on runtime metadata.

Patterns must not reference nodes or edges that do not exist in the discovery snapshot. Patterns must not reference identifiers created in the same transaction. Patterns must not reference deleted identifiers.

Patterns must serialize deterministically in Canonical IR. All bindings must be explicit. All where clauses must be explicit. All field accesses must be explicit. All function calls must be explicit. All collection definitions must be explicit.

End of SPEC 005.


SPEC 006 Match Discovery Model

Match discovery is the deterministic process that identifies all candidate matches for all rules at the start of each tick. Match discovery must occur exactly once per tick. Match discovery must operate over the state as it exists at the start of the tick. Match discovery must not observe staged writes, events, or any state changes that occur later in the tick. Match discovery must not depend on runtime metadata or nondeterministic values.

Match discovery must enumerate all rules in deterministic order. Rule ordering must be the lexicographic ordering of rule identifiers using raw UTF‑8 byte comparison. Rule ordering must not depend on rule position in the manifest or source file. Rule ordering must not depend on runtime metadata.

For each rule, match discovery must enumerate all possible bindings that satisfy the pattern and where clauses. Enumeration must follow deterministic ordering rules. Node enumeration must follow identifier ordering. Edge enumeration must follow identifier ordering. Collection enumeration must follow deterministic ordering defined by the collection’s order_by clause. If no order_by clause is present, collection enumeration must follow identifier ordering.

Match discovery must evaluate all where clauses deterministically. Where clause evaluation must not mutate state. Where clause evaluation must not allocate identifiers. Where clause evaluation must not depend on nondeterministic values. Where clause evaluation must not depend on runtime metadata. Where clause evaluation must not observe staged writes.

Match discovery must evaluate all let expressions deterministically. Let expressions must not introduce new dependencies beyond those extracted from their constituent expressions. Let expressions must not mutate state. Let expressions must not allocate identifiers. Let expressions must not depend on nondeterministic values.

Match discovery must evaluate all effect_deterministic function calls deterministically. All declared reads of effect_deterministic functions must be included in the rule’s dependency set. Engines must verify that effect_deterministic functions do not read state outside their declared reads.

Match discovery must produce a frozen discovery snapshot. The frozen discovery snapshot contains the following for each match:

1. rule_id  
2. sorted bindings of all pattern variables  
3. let‑bound values  
4. dependency set  
5. dependency snapshot  
6. match_key  
7. match_age

The dependency snapshot records the version counters for all dependencies at the moment of match discovery. Field dependencies snapshot field_versions[field_name]. NodeExistence dependencies snapshot existence_version. Predicate dependencies snapshot predicate_version[node_type][field_name]. Ordering dependencies snapshot ordering_version[node_type][field_name]. Extent dependencies snapshot extent_version[node_type]. EdgeType dependencies snapshot edge_type_version[edge_type]. Adjacency dependencies snapshot existence_version of the referenced node.

match_key is the canonical identity of the match. match_key consists of the rule identifier followed by the sorted list of bound identifiers. Let‑bound values must not participate in match_key. match_key must serialize deterministically as a UTF‑8 string.

match_age is the number of consecutive ticks in which the same match_key has appeared. A newly discovered match must have match_age = 0. If a match with the same match_key appeared in the previous tick, match_age increments by 1. If a match did not appear in the previous tick, match_age resets to 0. match_age must be a 64‑bit signed integer. Overflow is a fatal conformance error.

Match discovery must not perform dependency validation. Dependency validation occurs later in the tick. Match discovery must not discard matches based on dependency changes. Match discovery must not observe state changes that occur after discovery.

Match discovery must produce a complete list of matches for all rules. No match may be omitted. No match may be added after discovery. No match may be modified after discovery. The frozen discovery snapshot must remain immutable for the remainder of the tick.

End of SPEC 006.


SPEC 007 Dependency Set Model

The dependency set model defines all dependency types, how dependencies are extracted, how dependency snapshots are recorded, and how dependency validation determines match validity. Dependency validation is the sole mechanism for determining whether a match remains valid at commit time. No other correctness mechanism exists.

All dependencies must be explicit. Engines may include additional dependencies but must not omit required ones. Dependency extraction must be structural and must not depend on runtime values, short‑circuit behavior, or evaluation order. Dependency extraction must operate over the Canonical IR and must not depend on engine implementation details.

The dependency model defines the following dependency types:

1. NodeExistence(node_id)  
This dependency is created whenever a pattern binds a node. NodeExistence snapshots and validates against the node’s existence_version. If the node is deleted or any incident edge is created or deleted, existence_version changes and the dependency becomes invalid.

2. Field(node_id, field_name)  
This dependency is created whenever an expression reads a field of a bound node. Field snapshots and validates against field_versions[field_name] only. Field dependencies must not snapshot existence_version. Field dependencies must not be invalidated by changes to unrelated fields.

3. Predicate(node_type, field_name)  
This dependency is created whenever a collection filter references a field of a node type. Predicate snapshots and validates against predicate_version[node_type][field_name]. Predicate dependencies detect changes that may affect filter membership, including field updates and node creation or deletion.

4. Ordering(node_type, field_name)  
This dependency is created whenever a collection order_by references a field of a node type. Ordering snapshots and validates against ordering_version[node_type][field_name]. Ordering dependencies detect changes that may affect ordering, including field updates and node creation or deletion.

5. Extent(node_type)  
This dependency is created whenever a collection enumerates all nodes of a type. Extent snapshots and validates against extent_version[node_type]. Extent dependencies detect changes to the size of the collection, including node creation and deletion.

6. EdgeType(edge_type)  
This dependency is created whenever a collection enumerates all edges of a type. EdgeType snapshots and validates against edge_type_version[edge_type]. EdgeType dependencies detect changes to the set of edges of that type.

7. Adjacency(node_id, edge_type, direction)  
This dependency is created whenever a collection over an edge type filters on source or target and constrains it to a specific node. If the filter constrains E.source to node N, an Adjacency(N, E, outgoing) dependency is created. If the filter constrains E.target to node N, an Adjacency(N, E, incoming) dependency is created. Adjacency snapshots and validates against the existence_version of the referenced node. Adjacency dependencies detect changes to incident edges.

Dependency extraction rules:

Binding a node introduces NodeExistence(node_id).  
Binding an edge introduces NodeExistence(source_id), NodeExistence(target_id), and EdgeType(edge_type).

Field accesses introduce Field(node_id, field_name).

Collection over node type T introduces Extent(T).  
Collection filter referencing T.field introduces Predicate(T, field_name).  
Collection order_by referencing T.field introduces Ordering(T, field_name).

Collection over edge type E introduces EdgeType(E).  
Collection filter referencing E.field introduces Predicate(E, field_name).  
Collection order_by referencing E.field introduces Ordering(E, field_name).  
Filter constraining E.source to node N introduces Adjacency(N, E, outgoing).  
Filter constraining E.target to node N introduces Adjacency(N, E, incoming).

Let expressions introduce dependencies from all field accesses, collection operations, and effect_deterministic function calls they contain. Let expressions must not introduce new dependencies beyond those extracted from their constituent expressions.

Event payload expressions introduce dependencies from all field accesses, collection operations, and effect_deterministic function calls they contain. Event payload expressions must not introduce new dependencies beyond those already extracted from the expressions that computed their inputs.

Effect_deterministic function calls introduce all dependencies declared in their declared_reads list.

Dependency snapshots:

For each dependency D, match discovery records the current version counter associated with D. Field dependencies snapshot field_versions[field_name]. NodeExistence and Adjacency dependencies snapshot existence_version. Predicate dependencies snapshot predicate_version[node_type][field_name]. Ordering dependencies snapshot ordering_version[node_type][field_name]. Extent dependencies snapshot extent_version[node_type]. EdgeType dependencies snapshot edge_type_version[edge_type].

Dependency validation:

A match is valid if and only if every dependency snapshot matches the current version counter. If any dependency snapshot differs from the current version counter, the match is invalid. Dependency validation must not be skipped. Dependency validation must not be approximated. Dependency validation must not depend on runtime metadata.

End of SPEC 007.


SPEC 008 Selection Model

The selection model defines how the engine chooses exactly one match to attempt for commit during each tick. Selection must be deterministic. Selection must operate exclusively on the frozen discovery snapshot produced in match discovery. Selection must not observe any state changes that occur after discovery. Selection must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior.

Selection consists of computing a deterministic score for each match, sorting all matches by that score, and selecting the highest‑scoring match. If multiple matches have identical scores, deterministic tie‑breaking rules must be applied. If no matches exist, the tick commits no transaction and produces no events.

Each match has a base priority. Base priority is an integer value computed from the rule’s priority expression. The priority expression must be deterministic. The priority expression must not depend on runtime metadata. The priority expression must not depend on nondeterministic values. The priority expression must not allocate identifiers. The priority expression must not mutate state.

Each match has a fairness boost. The fairness boost is computed as match_age multiplied by fairness_scale. fairness_scale must be 1. match_age must be a 64‑bit signed integer. match_age must not overflow. Overflow is a fatal conformance error.

Each match has a scaled priority. The scaled priority is computed as base priority multiplied by priority_scale. priority_scale must be 1000000. priority_scale must not be changed by manifests or engines.

The final score for a match is computed as scaled priority plus fairness boost. All arithmetic must use 64‑bit signed integer operations. Overflow is a fatal conformance error.

The engine must compute the final score for every match in the frozen discovery snapshot. The engine must then sort all matches by final score in descending order. Sorting must be stable and deterministic. Sorting must not depend on runtime metadata. Sorting must not depend on nondeterministic values.

If two matches have identical final scores, the engine must break ties deterministically using lexicographic ordering of match_key. match_key must be compared using raw UTF‑8 byte ordering. match_key must not include let‑bound values. match_key must not include runtime metadata.

The match with the highest final score after tie‑breaking is the selected match. The selected match is the only match that proceeds to dependency validation. All other matches are discarded for this tick.

Selection must not perform dependency validation. Selection must not observe staged writes. Selection must not observe events. Selection must not observe state changes that occur after discovery.

Selection must not modify match_age. match_age is updated only at the start of the next tick during match discovery.

Selection must not modify state. Selection must not allocate identifiers. Selection must not mutate version counters. Selection must not produce events.

If the selected match fails dependency validation, the engine must discard it and proceed to the next match in the sorted list. The engine must not restart match discovery. The engine must not recompute scores. The engine must not modify the sorted list. The engine must continue until a valid match is found or the list is exhausted.

If all matches fail dependency validation, the tick commits no transaction and produces no events. The tick counter increments. match_age updates in the next tick.

End of SPEC 008.


SPEC 009 Tick Model

The tick model defines the deterministic sequence of operations that occur during each tick. All conformant engines must follow this sequence exactly. No step may be reordered, omitted, or interleaved with another. No state mutation may occur outside the commit step. No nondeterministic behavior is permitted at any stage.

A tick consists of the following deterministic phases:

1. Tick counter increment  
At the start of each tick, the tick counter increments by 1. The tick counter must be a 64‑bit signed integer. Overflow is a fatal conformance error. No other state changes may occur during this phase.

2. Match discovery  
The engine performs match discovery for all rules. Match discovery must enumerate all matches deterministically. Match discovery must evaluate all where clauses, let expressions, collection expressions, and effect_deterministic function calls deterministically. Match discovery must produce a frozen discovery snapshot. No state mutation may occur during match discovery.

3. Match scoring  
The engine computes the final score for each match in the frozen discovery snapshot. The final score is computed as scaled priority plus fairness boost. scaled priority is base priority multiplied by priority_scale. fairness boost is match_age multiplied by fairness_scale. All arithmetic must use 64‑bit signed integers. Overflow is a fatal conformance error. No state mutation may occur during match scoring.

4. Match ranking  
The engine sorts all matches by final score in descending order. Sorting must be deterministic. Sorting must be stable. Sorting must not depend on runtime metadata. If two matches have identical final scores, the engine must break ties using lexicographic ordering of match_key. No state mutation may occur during match ranking.

5. Match selection  
The engine selects the highest‑ranked match and attempts dependency validation. If the selected match fails validation, the engine must discard it and proceed to the next match in the ranked list. The engine must not restart match discovery. The engine must not recompute scores. The engine must not modify the ranked list. The engine must continue until a valid match is found or the list is exhausted. No state mutation may occur during match selection.

6. Dependency validation  
The engine validates the selected match by comparing each dependency snapshot to the current version counter. If any dependency snapshot differs from the current version counter, the match is invalid. If the match is invalid, the engine must discard it and proceed to the next match in the ranked list. If all matches are invalid, the tick commits no transaction. No state mutation may occur during dependency validation.

7. Commit  
If a valid match is found, the engine evaluates the actions of the rule and stages all writes. Action evaluation must be deterministic. Action evaluation must not read fields or nodes that are not part of the match’s dependency set. Action evaluation must not allocate identifiers except through CreateNode and CreateEdge. Action evaluation must not mutate state directly.

After all actions are evaluated, the engine applies staged writes in deterministic order. All CreateNode actions must be applied before all CreateEdge actions. Within each category, actions must be applied in the order they appear in the rule’s action list. Identifier allocation must follow the Identifier Model. All version counters must be updated according to the State Model. All state mutations must occur only during commit.

8. Event emission  
If the rule defines events, the engine must evaluate event payload expressions deterministically and emit events. Event payload expressions must not introduce new dependencies beyond those already extracted. Events must not mutate state. Events must not influence match discovery, selection, or validation. Events must appear in the golden file in deterministic order.

9. End of tick  
After commit and event emission, the tick ends. No further state changes may occur until the next tick. match_age updates occur at the start of the next tick during match discovery.

End of SPEC 009.


SPEC 010 Action Model

The action model defines all deterministic state mutations that may occur during commit. Actions must be explicit in Canonical IR. Actions must not introduce implicit reads. Actions must not introduce nondeterministic behavior. Actions must not depend on runtime metadata. Actions must not mutate state outside the commit phase. Actions must not allocate identifiers except through CreateNode and CreateEdge.

Actions are evaluated after a match has been selected and validated. Action evaluation must be deterministic. Action evaluation must not read any field or node that is not part of the match’s dependency set. Any field access in an action expression must be included in dependency extraction. If an action expression references a field not covered by dependency extraction, the manifest is invalid and must be rejected before execution.

Actions may contain expressions. Expressions in actions must follow the Expression Model. Expressions must not mutate state. Expressions must not allocate identifiers. Expressions must not depend on nondeterministic values. Expressions must not depend on runtime metadata. Expressions must not reference nodes or edges created in the same transaction.

The following actions are permitted:

1. UpdateField(node_id, field_name, expression)  
This action updates a field of a node. The expression must be deterministic. The expression must not read fields or nodes outside the dependency set. The update must increment field_versions[field_name] of the node. The update must not modify existence_version. The update must not modify any other field_versions. The update must not modify any other node or edge.

2. UpdateEdgeField(edge_id, field_name, expression)  
This action updates a field of an edge. The expression must be deterministic. The expression must not read fields or nodes outside the dependency set. The update must not modify existence_version of any node. The update must not modify edge_type_version. The update must increment no version counters except those associated with the updated field.

3. CreateNode(node_type, field_initializers)  
This action creates a new node. The node identifier must be allocated deterministically using the sequence_counter[node_type]. The sequence counter must increment by 1. The new node must have existence_version = 1 and field_versions[field_name] = 1 for all fields. Creating a node must increment predicate_version[node_type][field_name] for all fields of the node type. Creating a node must increment ordering_version[node_type][field_name] for all fields of the node type. Creating a node must increment extent_version[node_type].

4. CreateEdge(edge_type, source_id, target_id, field_initializers)  
This action creates a new edge. The edge identifier must be allocated deterministically using the sequence_counter[edge_type]. The sequence counter must increment by 1. Creating an edge must increment edge_type_version[edge_type]. Creating an edge must increment existence_version of the source node and the target node. Creating an edge must not modify any field_versions.

5. DeleteNode(node_id)  
This action deletes a node. Deleting a node must increment existence_version of the node immediately before deletion. Deleting a node must delete all incident edges. Deleting each incident edge must increment edge_type_version of the edge’s type and must increment existence_version of the other endpoint. Deleting a node must increment predicate_version[node_type][field_name] for all fields of the node type. Deleting a node must increment ordering_version[node_type][field_name] for all fields of the node type. Deleting a node must increment extent_version[node_type]. Deleted identifiers must not be reused.

6. DeleteEdge(edge_id)  
This action deletes an edge. Deleting an edge must increment edge_type_version[edge_type]. Deleting an edge must increment existence_version of the source node and the target node. Deleting an edge must not modify any field_versions. Deleted identifiers must not be reused.

Action ordering:

All actions must be evaluated in the order they appear in the rule’s action list. All CreateNode actions must be applied before all CreateEdge actions. All DeleteEdge actions must be applied before DeleteNode actions. All UpdateField and UpdateEdgeField actions must be applied after all creations and deletions. This ordering must be deterministic and must not depend on engine implementation details.

Staged writes:

Action evaluation must produce a list of staged writes. Staged writes must not mutate state until commit. Staged writes must be applied in deterministic order. Staged writes must not be reordered by the engine. Staged writes must not be merged or optimized in ways that change observable behavior.

Identifier allocation:

Identifier allocation must follow the Identifier Model. Identifiers must not depend on runtime metadata. Identifiers must not depend on nondeterministic values. Identifiers must not be reused. Identifiers must serialize deterministically.

End of SPEC 010.


SPEC 011 Event Model

The event model defines how events are produced during commit and how they appear in deterministic output. Events must not influence deterministic state. Events must not influence match discovery, selection, or dependency validation. Events must not introduce new dependencies. Events must not depend on runtime metadata or nondeterministic values. Events must serialize deterministically.

Events are produced only by rules that explicitly declare event emissions. Events must be emitted only during the commit phase of a valid match. Events must not be emitted during match discovery, match scoring, match ranking, or dependency validation. Events must not be emitted by invalid matches. Events must not be emitted by rules that do not commit.

An event consists of an event type and a payload. The event type must be a deterministic string declared in the manifest. The event type must serialize deterministically. The event type must not depend on runtime metadata.

The event payload is computed from deterministic expressions. Event payload expressions must follow the Expression Model. Event payload expressions must not introduce new dependencies beyond those already extracted from the expressions that computed their inputs. Event payload expressions must not read fields or nodes that are not part of the match’s dependency set. Event payload expressions must not allocate identifiers. Event payload expressions must not mutate state. Event payload expressions must not depend on nondeterministic values.

Event payloads may reference let‑bound values. Let‑bound values must not introduce new dependencies. Let‑bound values must not depend on nondeterministic values. Let‑bound values must not depend on runtime metadata.

Event payloads may contain identifiers. Identifiers in event payloads must be treated as literal values. Identifiers in event payloads must not be interpreted as live references. Identifiers in event payloads must not participate in dependency extraction. Identifiers in event payloads must not influence match validity.

Events must be emitted in deterministic order. The order of events must follow the order of event declarations in the rule’s action list. If multiple events are emitted by the same rule, they must appear in the order they are declared. If multiple events are emitted by different rules, only one rule may commit per tick, so event ordering is determined solely by the committing rule.

Events must serialize deterministically in golden files. Event serialization must follow canonical JSON rules. Event payloads must serialize deterministically. Event lists must preserve deterministic ordering. Event serialization must not include runtime metadata.

Events must not mutate state. Events must not modify version counters. Events must not modify sequence counters. Events must not modify nodes or edges. Events must not modify tick counters. Events must not modify match_age.

Events must not influence future ticks. Events must not influence match discovery. Events must not influence selection. Events must not influence dependency validation. Events must not influence commit. Events must not influence identifier allocation. Events must not influence version counters.

Events are purely observational outputs. Events must appear in golden files exactly as produced. Events must be reproducible across all conformant engines. Events must be identical for identical manifests and initial states.

End of SPEC 011.


SPEC 012 Collection Model

The collection model defines how deterministic collections of nodes or edges are constructed, filtered, ordered, and enumerated. Collections must be fully explicit in Canonical IR. Collections must not infer semantics. Collections must not depend on runtime metadata or nondeterministic values. Collections must not mutate state. Collections must not allocate identifiers.

A collection expression consists of the following components:

1. A source type  
The source type must be a declared node type or edge type. The source type must be explicit. The source type must not be inferred. The source type determines whether the collection enumerates nodes or edges.

2. A filter expression  
The filter expression must be a deterministic expression that evaluates to a boolean. The filter expression must not mutate state. The filter expression must not allocate identifiers. The filter expression must not depend on nondeterministic values. The filter expression must not depend on runtime metadata. The filter expression may reference fields of the source type. The filter expression may reference bound variables. The filter expression may call pure functions or effect_deterministic functions. All field accesses in the filter expression must be included in dependency extraction. All effect_deterministic function calls must contribute their declared dependencies.

3. An order_by list  
The order_by list must be explicit. The order_by list must contain zero or more ordering keys. Each ordering key must reference a field of the source type. Each ordering key must specify ascending or descending order. If the order_by list is empty, the collection must be ordered by identifier ordering. All ordering keys must be included in dependency extraction. Ordering dependencies must snapshot ordering_version[node_type][field_name] or ordering_version[edge_type][field_name] depending on the source type.

4. An optional limit  
The limit must be a deterministic integer expression. The limit must not depend on nondeterministic values. The limit must not depend on runtime metadata. The limit must not be negative. If the limit is omitted, the collection enumerates all matching elements.

Collection semantics:

A collection enumerates all nodes or edges of the source type. Enumeration must follow deterministic ordering rules. Enumeration must not depend on runtime metadata. Enumeration must not depend on nondeterministic values.

For node collections:

The engine must enumerate all nodes of the specified type. The engine must apply the filter expression to each node. The engine must order the filtered nodes according to the order_by list. If the order_by list is empty, the engine must order nodes by identifier ordering. The engine must apply the limit if present.

For edge collections:

The engine must enumerate all edges of the specified type. The engine must apply the filter expression to each edge. The engine must order the filtered edges according to the order_by list. If the order_by list is empty, the engine must order edges by identifier ordering. The engine must apply the limit if present.

Dependency extraction:

A collection over node type T introduces Extent(T).  
A collection filter referencing T.field introduces Predicate(T, field_name).  
A collection order_by referencing T.field introduces Ordering(T, field_name).

A collection over edge type E introduces EdgeType(E).  
A collection filter referencing E.field introduces Predicate(E, field_name).  
A collection order_by referencing E.field introduces Ordering(E, field_name).

If the filter constrains E.source to a bound node N, the collection introduces Adjacency(N, E, outgoing).  
If the filter constrains E.target to a bound node N, the collection introduces Adjacency(N, E, incoming).

Collection evaluation:

Collection evaluation must be deterministic. Collection evaluation must not mutate state. Collection evaluation must not allocate identifiers. Collection evaluation must not depend on nondeterministic values. Collection evaluation must not depend on runtime metadata. Collection evaluation must not observe staged writes. Collection evaluation must not observe events.

Collection evaluation must operate only on the state visible at match discovery time. Collection evaluation must not reference nodes or edges created in the same transaction. Collection evaluation must not reference deleted identifiers.

Collection serialization:

Collections must serialize deterministically in Canonical IR. The source type must be explicit. The filter expression must be explicit. The order_by list must be explicit. The limit must be explicit if present. No implicit defaults are permitted.

End of SPEC 012.


SPEC 013 Identifier Model

The identifier model defines how deterministic identifiers for nodes and edges are allocated, represented, compared, serialized, and preserved across ticks. Identifiers must be fully deterministic. Identifiers must not depend on runtime metadata, memory layout, timestamps, random numbers, hash functions, or any nondeterministic source. Identifiers must never be reused. Identifiers must never decrease. Identifiers must never wrap. Identifier allocation must be part of deterministic state.

Identifier structure:

A node identifier has the form NodeType:sequence.  
An edge identifier has the form EdgeType:sequence.

NodeType and EdgeType must be UTF‑8 strings declared in the manifest. sequence must be a 64‑bit signed integer. sequence must be allocated from sequence_counter[type]. sequence_counter[type] must be part of deterministic state. sequence_counter[type] must never decrease. sequence_counter[type] must never wrap. Overflow is a fatal conformance error.

Identifier allocation:

When a CreateNode action is committed, the engine must allocate a new identifier using sequence_counter[node_type]. The identifier must be node_type:sequence_counter[node_type]. The sequence counter must then increment by 1.

When a CreateEdge action is committed, the engine must allocate a new identifier using sequence_counter[edge_type]. The identifier must be edge_type:sequence_counter[edge_type]. The sequence counter must then increment by 1.

Identifier allocation must occur only during commit. Identifier allocation must not occur during match discovery, match scoring, match ranking, or dependency validation. Identifier allocation must not occur during event emission. Identifier allocation must not occur during expression evaluation.

Identifier reuse:

Identifiers must never be reused. Once a node or edge is deleted, its identifier must never appear again in any future state. Deleted identifiers must not be reallocated. Deleted identifiers must not be recycled. Deleted identifiers must not be repurposed.

Identifier comparison:

Identifier comparison must use lexicographic ordering of the UTF‑8 encoded identifier string. Comparison must be byte‑by‑byte. Comparison must not depend on locale. Comparison must not depend on case folding. Comparison must not depend on numeric interpretation of the sequence component. Comparison must not depend on runtime metadata.

Identifier ordering:

Identifier ordering must be used for deterministic enumeration of nodes and edges when no order_by clause is present. Identifier ordering must be used for deterministic tie‑breaking in match selection. Identifier ordering must be used for deterministic serialization of collections and golden files.

Identifier serialization:

Identifiers must serialize as UTF‑8 strings. Identifiers must not include quotes, prefixes, suffixes, or metadata. Identifiers must not include leading zeros in the sequence component. Identifiers must not include whitespace. Identifiers must not include nondeterministic components.

Identifier stability:

Identifiers must remain stable across ticks. Identifiers must remain stable across serialization and deserialization. Identifiers must remain stable across engine implementations. Identifiers must remain stable across platforms. Identifiers must remain stable across golden file generation.

Identifier validity:

An identifier is valid if and only if it refers to an existing node or edge in the current state. Expressions must not reference invalid identifiers. Patterns must not bind invalid identifiers. Actions must not reference invalid identifiers. Event payloads may contain invalid identifiers as literal values, but such identifiers must not be interpreted as references.

Identifier lifetime:

A node identifier becomes valid when the node is created and becomes invalid immediately after the node is deleted. An edge identifier becomes valid when the edge is created and becomes invalid immediately after the edge is deleted. Identifiers must not be referenced after deletion except as literal values in event payloads.

Identifier determinism:

All conformant engines must allocate identifiers in exactly the same order for identical manifests and initial states. All conformant engines must produce identical identifier sequences. All conformant engines must serialize identifiers identically. All conformant engines must compare identifiers identically.

End of SPEC 013.


SPEC 014 Version Counter Model

The version counter model defines how all version counters behave, how they are incremented, how they are validated, and how they participate in dependency validation. Version counters must be 64‑bit signed integers. Version counters must never decrease. Version counters must never wrap. Overflow is a fatal conformance error. All version counters must be part of deterministic state and must appear in initial_state and final_state.

The following version counters exist:

1. existence_version[node_id]  
This counter increments when any edge incident to the node is created or deleted. This counter increments immediately before the node is deleted. This counter must be at least 1 for all nodes in initial_state. This counter must never wrap. This counter participates in NodeExistence and Adjacency dependencies.

2. field_versions[node_id][field_name]  
This counter increments when the corresponding field is updated. This counter must be at least 1 for all fields in initial_state. This counter must never wrap. This counter participates in Field dependencies.

3. predicate_version[node_type][field_name]  
This counter increments when any node of the specified type updates the specified field. This counter increments when any node of the specified type is created or deleted. This counter must be at least 1 in initial_state. This counter must never wrap. This counter participates in Predicate dependencies.

4. ordering_version[node_type][field_name]  
This counter increments when any node of the specified type updates the specified field. This counter increments when any node of the specified type is created or deleted. This counter must be at least 1 in initial_state. This counter must never wrap. This counter participates in Ordering dependencies.

5. extent_version[node_type]  
This counter increments when any node of the specified type is created or deleted. This counter must be at least 1 in initial_state. This counter must never wrap. This counter participates in Extent dependencies.

6. edge_type_version[edge_type]  
This counter increments when any edge of the specified type is created or deleted. This counter must be at least 1 in initial_state. This counter must never wrap. This counter participates in EdgeType dependencies.

7. sequence_counter[type]  
This counter determines the next sequence number for identifier allocation. This counter must be at least the maximum sequence observed among all existing identifiers of that type. This counter must never decrease. This counter must never wrap. Overflow is a fatal conformance error. This counter participates in identifier allocation but does not participate in dependency validation.

8. tick_counter  
This counter increments at the start of each tick. This counter must never decrease. This counter must never wrap. Overflow is a fatal conformance error. This counter does not participate in dependency validation.

Increment rules:

Updating a node field increments field_versions[node_id][field_name].  
Updating a node field increments predicate_version[node_type][field_name].  
Updating a node field increments ordering_version[node_type][field_name].

Creating a node increments predicate_version[node_type][field_name] for all fields of the node type.  
Creating a node increments ordering_version[node_type][field_name] for all fields of the node type.  
Creating a node increments extent_version[node_type].

Deleting a node increments existence_version[node_id] immediately before deletion.  
Deleting a node increments predicate_version[node_type][field_name] for all fields of the node type.  
Deleting a node increments ordering_version[node_type][field_name] for all fields of the node type.  
Deleting a node increments extent_version[node_type].

Creating an edge increments edge_type_version[edge_type].  
Creating an edge increments existence_version[source_id].  
Creating an edge increments existence_version[target_id].

Deleting an edge increments edge_type_version[edge_type].  
Deleting an edge increments existence_version[source_id].  
Deleting an edge increments existence_version[target_id].

Validation rules:

A dependency is valid if and only if the current version counter equals the snapshot recorded during match discovery. If any version counter differs, the dependency is invalid. If any dependency is invalid, the match is invalid. No other correctness mechanism exists.

Version counters must not be compared using any method other than exact integer equality. Version counters must not be compared using greater‑than or less‑than. Version counters must not be interpreted as timestamps. Version counters must not be interpreted as logical clocks. Version counters must not be interpreted as ordering metadata.

Version counters must be serialized deterministically. Version counters must appear in golden files exactly as integers. Version counters must not include leading zeros. Version counters must not include metadata.

End of SPEC 014.


SPEC 015 Dependency Validation Model

The dependency validation model defines how the engine determines whether a selected match is still valid at commit time. Dependency validation is the sole correctness mechanism in the deterministic kernel. No other mechanism may be used. Conflict detection is forbidden. Rediscovery is forbidden. Re‑evaluation of expressions is forbidden. Only dependency validation determines match validity.

Dependency validation occurs after match selection and before commit. Dependency validation must operate on the current state. Dependency validation must not observe staged writes. Dependency validation must not observe events. Dependency validation must not depend on runtime metadata or nondeterministic values.

A match contains a dependency set and a dependency snapshot. The dependency set contains all dependencies extracted during match discovery. The dependency snapshot contains the version counter values recorded at discovery time. Dependency validation compares each dependency snapshot to the current version counter.

A dependency is valid if and only if the current version counter equals the snapshot. If any dependency is invalid, the match is invalid. If any dependency is invalid, the engine must discard the match and proceed to the next match in the ranked list. The engine must not restart match discovery. The engine must not recompute scores. The engine must not modify the ranked list.

Validation rules for each dependency type:

NodeExistence(node_id):  
Valid if existence_version[node_id] equals the snapshot.  
Invalid if the node was deleted or any incident edge was created or deleted.

Field(node_id, field_name):  
Valid if field_versions[node_id][field_name] equals the snapshot.  
Invalid if the field was updated.  
Field dependencies do not observe existence_version.

Predicate(node_type, field_name):  
Valid if predicate_version[node_type][field_name] equals the snapshot.  
Invalid if any node of that type updated the field or if any node of that type was created or deleted.

Ordering(node_type, field_name):  
Valid if ordering_version[node_type][field_name] equals the snapshot.  
Invalid if any node of that type updated the field or if any node of that type was created or deleted.

Extent(node_type):  
Valid if extent_version[node_type] equals the snapshot.  
Invalid if any node of that type was created or deleted.

EdgeType(edge_type):  
Valid if edge_type_version[edge_type] equals the snapshot.  
Invalid if any edge of that type was created or deleted.

Adjacency(node_id, edge_type, direction):  
Valid if existence_version[node_id] equals the snapshot.  
Invalid if any edge incident to the node was created or deleted.

Dependency validation must not use greater‑than or less‑than comparisons. Dependency validation must use exact integer equality. Dependency validation must not interpret version counters as timestamps or logical clocks.

If all dependencies are valid, the match is valid and commit proceeds. If any dependency is invalid, the match is invalid and must be discarded. If all matches are invalid, the tick commits no transaction and produces no events.

Dependency validation must not mutate state. Dependency validation must not allocate identifiers. Dependency validation must not modify version counters. Dependency validation must not modify match_age. Dependency validation must not modify the frozen discovery snapshot.

Dependency validation must be reproducible across all conformant engines. Dependency validation must produce identical results for identical manifests and initial states.

End of SPEC 015.


SPEC 016 Rule Model

The rule model defines the complete structure, semantics, and deterministic behavior of rules in the GRISP execution model. A rule is the fundamental unit of reactive logic. Each rule must be explicit in Canonical IR. No implicit rule behavior is permitted. Rules must not depend on runtime metadata or nondeterministic values. Rules must not mutate state outside the commit phase.

A rule consists of the following components:

1. rule_id  
A deterministic UTF‑8 string that uniquely identifies the rule. rule_id must be stable across serialization. rule_id must not depend on source file position. rule_id must not depend on runtime metadata. rule_id participates in match_key and tie‑breaking.

2. pattern  
A set of explicit bindings that match nodes and edges. The pattern must follow the Pattern Model. The pattern must not contain implicit bindings. The pattern must not reference undeclared types. The pattern must not reference invalid identifiers. The pattern must not allocate identifiers. The pattern must not mutate state.

3. where clause  
A deterministic boolean expression that filters matches. The where clause must follow the Expression Model. The where clause must not mutate state. The where clause must not allocate identifiers. The where clause must not depend on nondeterministic values. The where clause must not depend on runtime metadata.

4. let bindings  
A set of deterministic expressions that compute intermediate values. Let expressions must follow the Expression Model. Let expressions must not introduce new dependencies beyond those extracted from their constituent expressions. Let expressions must not mutate state. Let expressions must not allocate identifiers.

5. priority expression  
A deterministic integer expression that determines the base priority of the match. The priority expression must not depend on nondeterministic values. The priority expression must not depend on runtime metadata. The priority expression must not mutate state. The priority expression must not allocate identifiers.

6. actions  
A list of explicit actions that mutate state during commit. Actions must follow the Action Model. Actions must not introduce implicit reads. Actions must not depend on nondeterministic values. Actions must not depend on runtime metadata. Actions must not read fields or nodes outside the dependency set. Actions must not mutate state outside commit.

7. events  
A list of event declarations. Events must follow the Event Model. Event payload expressions must not introduce new dependencies. Event payload expressions must not mutate state. Event payload expressions must not allocate identifiers.

Rule evaluation lifecycle:

1. Match discovery  
The engine enumerates all possible bindings that satisfy the pattern and where clause. Let expressions are evaluated. Dependencies are extracted. A frozen discovery snapshot is produced.

2. Match scoring  
The engine evaluates the priority expression. The engine computes scaled priority and fairness boost. The engine computes the final score.

3. Match ranking  
The engine sorts matches by final score. Ties are broken using lexicographic ordering of match_key.

4. Match selection  
The highest‑ranked match is selected. If dependency validation fails, the engine proceeds to the next match.

5. Dependency validation  
The engine compares dependency snapshots to current version counters. If all dependencies match, the rule is valid.

6. Commit  
The engine evaluates actions. Staged writes are produced. Staged writes are applied in deterministic order. State is mutated.

7. Event emission  
Event payload expressions are evaluated. Events are emitted in deterministic order.

Rule determinism requirements:

Rules must not contain nondeterministic expressions.  
Rules must not depend on runtime metadata.  
Rules must not allocate identifiers except through CreateNode and CreateEdge.  
Rules must not mutate state outside commit.  
Rules must not reference nodes or edges created in the same transaction.  
Rules must not reference deleted identifiers.  
Rules must serialize deterministically in Canonical IR.

Rule ordering:

Rules must be ordered lexicographically by rule_id during match discovery.  
Rule ordering must not depend on manifest order.  
Rule ordering must not depend on runtime metadata.

Rule validity:

A rule is valid if and only if all of the following hold:

1. All types referenced in the rule are declared.  
2. All fields referenced in the rule exist.  
3. All expressions are deterministic.  
4. All dependencies are extractable.  
5. All actions are valid.  
6. The rule introduces no implicit behavior.  
7. The rule serializes deterministically.

Invalid rules must cause manifest rejection before execution.

End of SPEC 016.


SPEC 017 Deterministic Serialization Model

The deterministic serialization model defines how all GRISP structures must be serialized into canonical form for golden files, debugging output, and cross‑engine conformance testing. Serialization must be fully deterministic. Serialization must not depend on runtime metadata, memory layout, hash maps, iteration order of internal data structures, locale settings, or nondeterministic behavior of any kind.

Serialization scope:

The following structures must serialize deterministically:
1. State (nodes, edges, fields, version counters, sequence counters, tick counter)
2. Events
3. Matches (for debugging)
4. Canonical IR
5. Identifiers
6. Literal values
7. Collections
8. Rule structures (for debugging)

Serialization format:

All deterministic serialization must use canonical JSON. Canonical JSON is defined as follows:
1. UTF‑8 encoding only.
2. No whitespace except single spaces after colons and commas.
3. No pretty‑printing or indentation.
4. Object keys sorted lexicographically by raw UTF‑8 byte order.
5. Arrays preserve deterministic ordering.
6. Strings must not contain escape sequences except those required by JSON.
7. Numbers must not contain leading zeros.
8. Booleans must be lowercase true or false.
9. Null must be lowercase null.

Serialization of identifiers:

Identifiers must serialize as UTF‑8 strings in the form Type:sequence. Identifiers must not include metadata. Identifiers must not include whitespace. Identifiers must not include leading zeros in the sequence component.

Serialization of nodes:

Nodes must serialize as objects with the following keys:
id  
type  
fields  
existence_version  
field_versions  

fields must serialize as an object with keys sorted lexicographically.  
field_versions must serialize as an object with keys sorted lexicographically.

Serialization of edges:

Edges must serialize as objects with the following keys:
id  
type  
source  
target  
fields  

fields must serialize as an object with keys sorted lexicographically.

Serialization of version counters:

All version counters must serialize as integers. Version counters must not include leading zeros. Version counters must not include metadata. Version counters must not be omitted.

Serialization of events:

Events must serialize as objects with the following keys:
type  
payload  

Events must appear in an array in deterministic order.  
Event payloads must serialize deterministically using canonical JSON.

Serialization of matches (debug only):

Matches must serialize as objects with the following keys:
rule_id  
bindings  
let_values  
dependencies  
match_key  
match_age  

bindings must serialize as an object with variable names sorted lexicographically.  
dependencies must serialize as an array sorted lexicographically by dependency type and then by identifier.

Serialization of Canonical IR:

Canonical IR must serialize deterministically.  
All rule definitions must appear in lexicographic order of rule_id.  
All type definitions must appear in lexicographic order of type name.  
All fields must appear in lexicographic order.  
All expressions must serialize in fully expanded form.  
No implicit defaults are permitted.

Serialization determinism requirements:

Serialization must produce identical output across:
1. All conformant engines  
2. All platforms  
3. All CPU architectures  
4. All memory layouts  
5. All execution schedules  

Serialization must not depend on:
1. Hash map iteration order  
2. Memory addresses  
3. Thread scheduling  
4. Floating point behavior  
5. Locale or regional settings  
6. Time zones  
7. System clocks  
8. Random number generators  

Serialization must be stable across ticks.  
Serialization must be stable across engine restarts.  
Serialization must be stable across manifest reloads.

Golden file requirements:

Golden files must contain:
1. initial_state  
2. final_state  
3. events  

Golden files must serialize using canonical JSON.  
Golden files must not contain comments.  
Golden files must not contain metadata.  
Golden files must not contain nondeterministic content.

End of SPEC 017.


SPEC 018 Canonical IR Model

The Canonical IR model defines the fully expanded, deterministic intermediate representation used for conformance testing, manifest validation, dependency extraction, and cross‑engine reproducibility. Canonical IR must be produced by all conformant engines. Canonical IR must be stable, explicit, and free of syntactic sugar. Canonical IR must not depend on runtime metadata or nondeterministic values.

Canonical IR purpose:

1. Provide a single, unambiguous representation of all rules, types, fields, expressions, and actions.
2. Ensure that dependency extraction is structural and deterministic.
3. Ensure that all engines interpret manifests identically.
4. Eliminate all syntactic sugar, implicit defaults, and shorthand constructs.
5. Provide a stable basis for golden file generation and conformance testing.

Canonical IR properties:

1. Fully explicit  
All types, fields, rules, patterns, expressions, actions, and events must be expanded into explicit structures. No implicit behavior is permitted. No omitted fields are permitted. No inferred semantics are permitted.

2. Deterministic ordering  
All lists must be sorted lexicographically by UTF‑8 byte order unless the specification defines a different deterministic ordering. This includes:
type definitions  
field definitions  
rule definitions  
pattern bindings  
let bindings  
action lists  
event lists  
expression arguments  
object keys  

3. No syntactic sugar  
Canonical IR must not contain:
shorthand field access  
implicit pattern bindings  
implicit ordering rules  
implicit collection filters  
implicit default values  
implicit event payloads  
implicit priority expressions  

4. No comments  
Canonical IR must not contain comments, annotations, or metadata.

5. No whitespace variation  
Canonical IR must not depend on indentation, formatting, or whitespace. Only structural content matters.

Canonical IR structure:

A manifest in Canonical IR consists of the following top‑level sections:

1. types  
A list of all node and edge types. Each type definition must include:
type_name  
kind (node or edge)  
fields (explicit list)  
For edge types, source_type and target_type must be explicit.

2. rules  
A list of all rules. Each rule must include:
rule_id  
pattern (explicit list of bindings)  
where (explicit expression tree)  
let (explicit list of bindings)  
priority (explicit expression tree)  
actions (explicit list)  
events (explicit list)

3. functions  
A list of pure and effect_deterministic functions. Each function must include:
function_name  
parameters  
body (explicit expression tree)

SPEC 019 Expression Model

7. Arithmetic expressions

8. Boolean expressions  
Boolean expressions must be explicit. Boolean operators must not rely on short‑circuit behavior. All operands must be evaluated. Boolean expressions must not mutate state.

9. Comparison expressions  
Comparison expressions must be explicit. Comparisons must be deterministic. Comparisons must not depend on runtime metadata. Comparisons must not be applied to identifiers except lexicographic string comparison.

10. String expressions  
String concatenation must be deterministic. String expressions must not depend on locale. String expressions must not depend on runtime metadata.

SPEC 021 Pattern Model

The pattern model defines how rules bind nodes and edges, how pattern variables are introduced, how structural constraints are expressed, and how deterministic match enumeration is performed. Patterns must be explicit in Canonical IR. Patterns must not infer semantics. Patterns must not depend on runtime metadata or nondeterministic values. Patterns must not mutate state.

Pattern structure:

A pattern consists of a list of explicit bindings. Each binding introduces a variable and associates it with a node type or edge type. Bindings must be explicit. Bindings must not reference undeclared types. Bindings must not reference invalid identifiers. Bindings must not allocate identifiers.

Binding forms:

1. Node binding  
node_var: NodeType  
This binds node_var to a node of the specified type. This introduces a NodeExistence dependency for each match.

2. Edge binding  
edge_var: EdgeType  
This binds edge_var to an edge of the specified type. This introduces NodeExistence dependencies for the source and target nodes and an EdgeType dependency for the edge type.

3. Constrained edge binding  
edge_var: EdgeType(source = node_var, target = node_var2)  
This binds an edge and constrains its endpoints. This introduces Adjacency dependencies for the constrained endpoints.

4. Field constraints  
node_var.field == expression  
node_var.field != expression  
node_var.field < expression  
node_var.field > expression  
node_var.field <= expression  
node_var.field >= expression  
Field constraints must be explicit. Field constraints must not rely on short‑circuit behavior. Field constraints must not mutate state. Field constraints must introduce Field dependencies.

5. Equality constraints  
node_var1 == node_var2  
node_var1 != node_var2  
Equality constraints must be explicit. Equality constraints must not infer semantics. Equality constraints must not mutate state.

Pattern determinism:

Patterns must be deterministic. Patterns must not depend on:
system time  
random numbers  
memory layout  
thread scheduling  
locale  
runtime metadata  

Patterns must not contain nondeterministic constructs.  
Patterns must not contain implicit joins.  
Patterns must not contain implicit filters.  
Patterns must not contain implicit ordering.

Pattern enumeration:

Pattern enumeration must follow deterministic ordering rules:
1. Node enumeration must follow identifier ordering.  
2. Edge enumeration must follow identifier ordering.  
3. Constrained enumeration must follow identifier ordering of the constrained variable.  
4. All combinations must be enumerated in lexicographic order of variable names.

Pattern evaluation:

Pattern evaluation occurs during match discovery.  
Pattern evaluation must not mutate state.  
Pattern evaluation must not allocate identifiers.  
Pattern evaluation must not observe staged writes.  
Pattern evaluation must not observe events.

Pattern validity:

A pattern is valid if and only if:
1. All referenced types exist.  
2. All referenced fields exist.  
3. All constraints are deterministic.  
4. All dependencies are extractable.  
5. No nondeterministic constructs are used.  
6. No state mutation occurs.  
7. No identifier allocation occurs.  
8. The pattern serializes deterministically.  

Invalid patterns must cause manifest rejection before execution.

Pattern binding lifetime:

Pattern variables exist only during match discovery, scoring, ranking, and validation.  
Pattern variables must not be referenced during commit except through actions that reference the bound identifiers.  
Pattern variables must not be referenced after the tick ends.

Pattern and dependency interaction:

Binding a node introduces NodeExistence(node_id).  
Binding an edge introduces NodeExistence(source_id), NodeExistence(target_id), and EdgeType(edge_type).  
Field constraints introduce Field dependencies.  
Equality constraints introduce no additional dependencies.  
Constrained edge bindings introduce Adjacency dependencies.

SPEC 022 Match Key Model

The match key model defines the deterministic string used to break ties between matches that have identical final scores. match_key must be fully deterministic. match_key must not depend on runtime metadata, nondeterministic values, memory layout, or engine‑specific behavior. match_key must serialize deterministically and must be identical across all conformant engines.

Purpose of match_key:

1. Provide a deterministic tie‑breaker when two or more matches have identical final scores.  
2. Ensure stable ordering of matches across engines, platforms, and executions.  
3. Ensure that match selection is reproducible and independent of internal data structures.

match_key construction:

match_key is a UTF‑8 string constructed by concatenating the following components in order:

1. rule_id  
2. A separator character (colon)  
3. A deterministic serialization of all pattern bindings  
4. A separator character (colon)  
5. A deterministic serialization of all let‑bound values  

No additional components may be included.  
No metadata may be included.  
No whitespace may be included except as part of literal values.  
No escaping rules beyond canonical JSON string rules may be used.

Pattern binding serialization:

Pattern bindings must be serialized in lexicographic order of variable name.  
Each binding must serialize as variable_name=identifier.  
Identifiers must serialize exactly as defined in the Identifier Model.  
No additional formatting is permitted.

Example (illustrative only):  
a=NodeType:1,b=NodeType:7,c=EdgeType:3

Let‑bound value serialization:

Let‑bound values must be serialized in lexicographic order of variable name.  
Each let binding must serialize as variable_name=value.  
Values must serialize using canonical JSON rules.  
Let‑bound values must not include nondeterministic content.  
Let‑bound values must not include references to nodes or edges created in the same transaction.

Example (illustrative only):  
x=5,y="hello"

match_key concatenation:

The final match_key is constructed as:

rule_id + ":" + pattern_bindings_serialized + ":" + let_values_serialized

If a rule has no let bindings, the final colon must still appear, followed by an empty string.  
If a rule has no pattern bindings (rare but permitted), the middle section must be empty.

match_key determinism:

match_key must be identical across all conformant engines.  
match_key must be identical across platforms.  
match_key must be identical across executions.  
match_key must not depend on hash map ordering.  
match_key must not depend on memory layout.  
match_key must not depend on thread scheduling.  
match_key must not depend on locale or encoding settings.

match_key comparison:

match_key comparison must use raw UTF‑8 byte lexicographic ordering.  
Comparison must not use locale‑aware ordering.  
Comparison must not use case folding.  
Comparison must not interpret numeric substrings as numbers.  
Comparison must not normalize Unicode.

match_key and match selection:

match_key is used only when two or more matches have identical final scores.  
match_key must not influence scoring.  
match_key must not influence dependency extraction.  
match_key must not influence commit.  
match_key must not influence event emission.

match_key validity:

A match_key is valid if and only if:
1. It is constructed exactly according to this specification.  
2. All identifiers are valid at match discovery time.  
3. All let‑bound values serialize deterministically.  
4. No nondeterministic content is included.  
5. No implicit behavior is included.  

Invalid match_key construction must cause manifest rejection before execution.

End of SPEC 022.


SPEC 023 Deterministic Ordering Model

Ordering must not depend on runtime metadata, memory layout, hash map iteration order, thread scheduling, locale, or nondeterministic values. Ordering must be identical across all conformant engines.

Ordering categories:

1. Identifier ordering  
Identifiers must be ordered lexicographically by raw UTF‑8 byte order.  
Identifier ordering must not interpret numeric substrings as numbers.  
Identifier ordering must not use locale‑aware comparison.  
Identifier ordering must not normalize Unicode.  
Identifier ordering must not depend on case folding.

2. Rule ordering  
Rules must be ordered lexicographically by rule_id.  
Rule ordering must not depend on manifest order.  
Rule ordering must not depend on runtime metadata.  
Rule ordering determines the order in which rules participate in match discovery.

3. Pattern binding ordering  
Pattern bindings must be ordered lexicographically by variable name.  
Pattern binding ordering must be used when constructing match_key.  
Pattern binding ordering must be used when serializing matches.

4. Let binding ordering  
Let bindings must be ordered lexicographically by variable name.  
Let binding ordering must be used when constructing match_key.  
Let binding ordering must be used when serializing matches.

5. Action ordering  
Actions must be applied in the following deterministic order:  
a. All CreateNode actions, in the order they appear in the rule.  
b. All CreateEdge actions, in the order they appear in the rule.  
c. All DeleteEdge actions, in the order they appear in the rule.  
d. All DeleteNode actions, in the order they appear in the rule.  
e. All UpdateField and UpdateEdgeField actions, in the order they appear in the rule.  
Action ordering must not be changed by the engine.

6. Event ordering  
Events must be emitted in the order they appear in the rule’s event list.  
If multiple events are emitted, they must appear in deterministic order.  
Event ordering must not depend on runtime metadata.

7. Collection ordering  
Collections must be ordered according to the explicit order_by list.  
If order_by is empty, identifier ordering must be used.  
Collection ordering must not depend on internal data structures.

8. Dependency ordering  
Dependencies must be sorted lexicographically by dependency type and then by identifier.  
Dependency ordering must be used when serializing matches.  
Dependency ordering must not influence match selection.

9. Match ranking ordering  
Matches must be sorted by final score in descending order.  
If final scores are equal, match_key lexicographic ordering must be used.  
Sorting must be stable and deterministic.

10. Canonical IR ordering  
All lists in Canonical IR must be sorted lexicographically unless otherwise specified.  
This includes:  
type definitions  
field definitions  
rule definitions  
function definitions  
pattern bindings  
let bindings  
action lists  
event lists  
expression arguments  
object keys  

Ordering determinism:

All ordering must be reproducible across:  
all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Ordering must not depend on:  
hash map iteration order  
pointer addresses  
thread scheduling  
locale or encoding settings  
system time  
random numbers  

Ordering validity:

Ordering is valid if and only if:  
1. It is lexicographic by raw UTF‑8 byte order.  
2. It does not depend on nondeterministic behavior.  
3. It is stable across executions.  
4. It is stable across platforms.  
5. It is stable across serialization and deserialization.  
6. It is fully explicit in Canonical IR.

SPEC 024 Fairness Model

The fairness model defines how GRISP ensures that long‑lived matches do not starve and that rules with persistently valid matches eventually fire, even if their base priority is lower than competing rules. Fairness must be deterministic. Fairness must not depend on runtime metadata, nondeterministic values, or engine‑specific scheduling. Fairness must not introduce nondeterministic behavior into match selection.

Fairness purpose:

1. Prevent starvation of matches that remain valid across many ticks.  
2. Ensure that low‑priority rules eventually fire if their matches persist.  
3. Maintain deterministic behavior across all conformant engines.  
4. Provide a reproducible mechanism for aging matches.

Fairness mechanism:

Fairness is implemented through match_age and fairness_scale.

match_age:

match_age is an integer associated with each match candidate.  
match_age increments by 1 at the start of each tick for every match that:  
1. existed in the previous tick’s discovery snapshot, and  
2. still exists in the current tick’s discovery snapshot with identical bindings.

match_age resets to 0 when:  
1. the match is selected and committed, or  
2. the match becomes invalid due to dependency changes, or  
3. the match disappears because its pattern no longer matches.

match_age must never become negative.  
match_age must never wrap.  
Overflow is a fatal conformance error.

fairness_scale:

fairness_scale is a deterministic integer constant defined in the manifest.  
fairness_scale must be non‑negative.  
fairness_scale must not depend on runtime metadata.  
fairness_scale must not depend on nondeterministic values.

Fairness boost:

fairness_boost = match_age * fairness_scale

All arithmetic must use 64‑bit signed integers.  
Overflow is a fatal conformance error.

Final score:

final_score = scaled_priority + fairness_boost

scaled_priority = base_priority * priority_scale

priority_scale is a deterministic integer constant defined in the manifest.

Fairness determinism:

Fairness must be deterministic across:  
all conformant engines  
all platforms  
all CPU architectures  
all execution schedules  

Fairness must not depend on:  
system time  
random numbers  
thread scheduling  
memory layout  
locale  

Fairness must not introduce nondeterministic ordering.

Fairness and match selection:

Fairness influences match selection only through final_score.  
Fairness must not influence dependency extraction.  
Fairness must not influence match_key.  
Fairness must not influence commit.  
Fairness must not influence event emission.

Fairness and match lifetime:

A match that persists across ticks accumulates fairness_boost.  
A match that disappears loses all accumulated fairness.  
A match that becomes invalid loses all accumulated fairness.  
A match that fires resets its fairness to zero.

Fairness and starvation prevention:

If two matches have identical base priority and priority_scale, the match that persists longer will eventually have a higher final_score due to fairness_boost.  
This ensures that long‑lived matches eventually fire.  
This ensures that no match can be permanently starved by another match with equal or lower base priority.

Fairness validity:

Fairness is valid if and only if:  
1. match_age increments deterministically.  
2. fairness_scale is deterministic.  
3. fairness_boost is computed deterministically.  
4. final_score is computed deterministically.  
5. No nondeterministic constructs are used.  
6. No runtime metadata is used.  
7. No implicit behavior is introduced.  

Invalid fairness configuration must cause manifest rejection before execution.

End of SPEC 024.


SPEC 025 Tick Model

The tick model defines the deterministic execution cycle of the GRISP engine. Each tick represents one complete evaluation‑and‑commit cycle. Ticks must be deterministic. Ticks must not depend on runtime metadata, nondeterministic values, thread scheduling, or engine‑specific behavior. All conformant engines must produce identical results for identical manifests and initial states.

Tick phases:

A tick consists of the following phases, executed in strict order:

1. Tick start  
2. Match discovery  
3. Match scoring  
4. Match ranking  
5. Match selection  
6. Dependency validation  
7. Commit  
8. Event emission  
9. Tick end

No phase may be skipped. No phase may be reordered. No phase may be merged with another.

Phase 1: Tick start

tick_counter increments by 1.  
match_age for all previously discovered matches increments by 1 if and only if the match reappears with identical bindings.  
match_age resets to 0 for all new matches.  
match_age resets to 0 for all matches that disappeared or became invalid.

Phase 2: Match discovery

The engine enumerates all rules in lexicographic order of rule_id.  
For each rule, the engine enumerates all pattern bindings in deterministic order.  
The engine evaluates where clauses.  
The engine evaluates let bindings.  
The engine extracts dependencies.  
The engine records a frozen discovery snapshot for each match.  
The engine computes match_age updates.

Match discovery must not mutate state.  
Match discovery must not allocate identifiers.  
Match discovery must not observe staged writes.  
Match discovery must not observe events.

Phase 3: Match scoring

For each match, the engine computes:  
base_priority (from the rule’s priority expression)  
scaled_priority = base_priority * priority_scale  
fairness_boost = match_age * fairness_scale  
final_score = scaled_priority + fairness_boost

All arithmetic must use 64‑bit signed integers.  
Overflow is a fatal conformance error.

Phase 4: Match ranking

Matches are sorted by final_score in descending order.  
If final_score is equal, match_key lexicographic ordering is used.  
Sorting must be stable and deterministic.

Phase 5: Match selection

The engine selects the highest‑ranked match.  
If no matches exist, the tick commits no transaction and produces no events.

Phase 6: Dependency validation

The engine compares each dependency snapshot to current version counters.  
If all dependencies match, the match is valid.  
If any dependency is invalid, the match is discarded and the engine proceeds to the next match in ranked order.  
If all matches are invalid, the tick commits no transaction and produces no events.

Phase 7: Commit

The engine evaluates actions in deterministic order.  
The engine produces staged writes.  
Staged writes are applied in deterministic order.  
State is mutated.  
Identifier allocation occurs only during this phase.

Commit must not read fields or nodes outside the dependency set.  
Commit must not allocate identifiers except through CreateNode and CreateEdge.  
Commit must not observe events.

Phase 8: Event emission

The engine evaluates event payload expressions.  
Events are emitted in deterministic order.  
Events must not mutate state.  
Events must not influence future ticks.

Phase 9: Tick end

All staged writes have been applied.  
All events have been emitted.  
The tick is complete.  
The engine proceeds to the next tick.

Tick determinism:

Ticks must be deterministic across:  
all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Ticks must not depend on:  
system time  
random numbers  
thread scheduling  
locale  
runtime metadata  

Tick validity:

A tick is valid if and only if:  
1. All phases execute in order.  
2. All deterministic rules are followed.  
3. No nondeterministic constructs are used.  
4. No invalid dependencies are accepted.  
5. No invalid actions are executed.  
6. No invalid events are emitted.  
7. All version counters remain consistent.  
8. All identifier allocations are deterministic.

Invalid tick behavior must cause manifest rejection or engine failure.

End of SPEC 025.


SPEC 026 Staged Write Model

The staged write model defines how all state mutations produced by actions are collected, ordered, validated, and applied during the commit phase. Staged writes ensure deterministic state mutation and prevent actions from observing partially applied updates. Staged writes must be deterministic. Staged writes must not depend on runtime metadata or nondeterministic values.

Staged write purpose:

1. Ensure that all actions execute against the same pre‑commit state.  
2. Ensure deterministic ordering of state mutations.  
3. Prevent actions from observing intermediate updates.  
4. Guarantee that dependency validation protects all reads.  
5. Ensure reproducibility across all conformant engines.

Staged write categories:

1. Node creation writes  
2. Edge creation writes  
3. Node deletion writes  
4. Edge deletion writes  
5. Field update writes (node fields)  
6. Field update writes (edge fields)

All staged writes must be collected before any write is applied.  
No staged write may be applied during action evaluation.  
No staged write may be visible to expressions or event payloads.

Staged write ordering:

Staged writes must be applied in the following deterministic order:

1. CreateNode writes  
2. CreateEdge writes  
3. DeleteEdge writes  
4. DeleteNode writes  
5. UpdateField writes  
6. UpdateEdgeField writes

This ordering is mandatory.  
This ordering must not be changed by the engine.  
This ordering must not depend on manifest order.  
This ordering must not depend on runtime metadata.

Staged write structure:

Each staged write must contain:

1. write_type  
2. target identifier (if applicable)  
3. field_name (for updates)  
4. value (for updates)  
5. node_type or edge_type (for creations)  
6. source_id and target_id (for edge creations)  
7. field_initializers (for creations)

Staged write determinism:

Staged writes must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Staged writes must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers  

Staged write validation:

Before applying staged writes, the engine must validate:

1. All identifiers referenced by writes are valid.  
2. All fields referenced by writes exist.  
3. All created nodes and edges have valid types.  
4. All deleted nodes and edges exist.  
5. All updated fields exist.  
6. No write violates type constraints.  
7. No write violates edge endpoint constraints.  
8. No write attempts to update a deleted identifier.  
9. No write attempts to delete an already deleted identifier.

Invalid staged writes must cause the match to be rejected.  
Invalid staged writes must not be partially applied.  
Invalid staged writes must not mutate state.

Staged write application:

After validation, staged writes must be applied in deterministic order.  
Applying a staged write may increment version counters as defined in the Version Counter Model.  
Applying a staged write may allocate identifiers (for creations).  
Applying a staged write must not trigger additional reads.  
Applying a staged write must not trigger additional writes.  
Applying a staged write must not emit events.

Staged write visibility:

Staged writes must not be visible to:

match discovery  
let expressions  
priority expressions  
event payload expressions  
dependency extraction  
other actions within the same commit  

Staged writes become visible only after commit completes.

Staged write and dependency interaction:

Staged writes must not invalidate dependencies of the match being committed.  
Staged writes may invalidate dependencies of other matches.  
Invalidated matches must be discarded in future ticks.

Staged write validity:

A staged write is valid if and only if:

1. It is structurally correct.  
2. It references valid identifiers.  
3. It respects type constraints.  
4. It respects field constraints.  
5. It respects edge endpoint constraints.  
6. It does not violate version counter rules.  
7. It does not introduce nondeterministic behavior.  
8. It serializes deterministically.

Invalid staged writes must cause manifest rejection or match rejection.

End of SPEC 026.


SPEC 027 Action Model

The action model defines all permissible state‑mutating operations that may occur during the commit phase of a tick. Actions must be explicit. Actions must not depend on runtime metadata or nondeterministic values. Actions must not read state outside the dependency set. Actions must not observe staged writes. Actions must not allocate identifiers except through CreateNode and CreateEdge. Actions must serialize deterministically in Canonical IR.

Action categories:

1. CreateNode  
2. CreateEdge  
3. DeleteNode  
4. DeleteEdge  
5. UpdateField (node fields)  
6. UpdateEdgeField (edge fields)

No other action types are permitted.  
Actions must not be extended by engine implementations.  
Actions must not be overloaded or reinterpreted.

────────────────────────────────────────

1. CreateNode

CreateNode(node_type, field_initializers)

This action creates a new node of the specified type.  
Identifier allocation occurs during commit using sequence_counter[node_type].  
field_initializers must be explicit.  
field_initializers must include all fields of the node type.  
field_initializers must not omit fields.  
field_initializers must not include extra fields.  
field_initializers must not depend on nondeterministic values.

CreateNode must not read fields or nodes outside the dependency set.  
CreateNode must not reference nodes or edges created earlier in the same commit.  
CreateNode increments:  
sequence_counter[node_type]  
predicate_version[node_type][field_name] for all fields  
ordering_version[node_type][field_name] for all fields  
extent_version[node_type]

────────────────────────────────────────

2. CreateEdge

CreateEdge(edge_type, source_id, target_id, field_initializers)

This action creates a new edge of the specified type.  
Identifier allocation occurs during commit using sequence_counter[edge_type].  
source_id and target_id must reference valid nodes.  
field_initializers must be explicit and complete.

CreateEdge increments:  
sequence_counter[edge_type]  
edge_type_version[edge_type]  
existence_version[source_id]  
existence_version[target_id]

CreateEdge must not reference nodes created earlier in the same commit.  
CreateEdge must not reference deleted nodes.  
CreateEdge must not mutate state outside commit.

────────────────────────────────────────

3. DeleteNode

DeleteNode(node_id)

This action deletes a node.  
DeleteNode must delete all edges incident to the node.  
DeleteNode must not delete nodes created earlier in the same commit.  
DeleteNode must not delete nodes already deleted.

DeleteNode increments:  
existence_version[node_id] (immediately before deletion)  
predicate_version[node_type][field_name] for all fields  
ordering_version[node_type][field_name] for all fields  
extent_version[node_type]

All incident edges must be deleted using DeleteEdge semantics.

────────────────────────────────────────

4. DeleteEdge

DeleteEdge(edge_id)

This action deletes an edge.  
DeleteEdge must not delete edges created earlier in the same commit.  
DeleteEdge must not delete edges already deleted.

DeleteEdge increments:  
edge_type_version[edge_type]  
existence_version[source_id]  
existence_version[target_id]

────────────────────────────────────────

5. UpdateField

UpdateField(node_id, field_name, expression)

This action updates a node field.  
expression must be deterministic.  
expression must not read fields or nodes outside the dependency set.  
expression must not reference nodes or edges created in the same commit.  
expression must not allocate identifiers.

UpdateField increments:  
field_versions[node_id][field_name]  
predicate_version[node_type][field_name]  
ordering_version[node_type][field_name]

────────────────────────────────────────

6. UpdateEdgeField

UpdateEdgeField(edge_id, field_name, expression)

This action updates an edge field.  
expression must be deterministic.  
expression must not read fields or nodes outside the dependency set.  
expression must not reference nodes or edges created in the same commit.  
expression must not allocate identifiers.

UpdateEdgeField increments:  
field_versions[edge_id][field_name]  
predicate_version[edge_type][field_name]  
ordering_version[edge_type][field_name]

────────────────────────────────────────

Action determinism:

Actions must be deterministic across:  
all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Actions must not depend on:  
system time  
random numbers  
thread scheduling  
locale  
runtime metadata

────────────────────────────────────────

Action ordering:

Actions must be applied in the following deterministic order:

1. CreateNode  
2. CreateEdge  
3. DeleteEdge  
4. DeleteNode  
5. UpdateField  
6. UpdateEdgeField

This ordering is mandatory and must not be altered.

────────────────────────────────────────

Action validity:

An action is valid if and only if:

1. All referenced identifiers exist.  
2. All referenced fields exist.  
3. All referenced types exist.  
4. All expressions are deterministic.  
5. All dependencies are satisfied.  
6. No nondeterministic constructs are used.  
7. No state mutation occurs outside commit.  
8. No identifier allocation occurs except through CreateNode and CreateEdge.  
9. The action serializes deterministically.

Invalid actions must cause match rejection.

────────────────────────────────────────

End of SPEC 027.


SPEC 028 Event Model

The event model defines how events are declared, evaluated, emitted, ordered, and serialized within the GRISP deterministic execution model. Events must be deterministic. Events must not mutate state. Events must not depend on runtime metadata or nondeterministic values. Events must serialize deterministically and must be identical across all conformant engines.

Purpose of events:

1. Provide a deterministic mechanism for external observers to react to state changes.  
2. Allow rules to emit structured information without mutating state.  
3. Ensure reproducibility across all engines, platforms, and executions.  
4. Provide a stable interface for downstream systems.

Event declaration:

Each event declaration must include:

1. event_type (UTF‑8 string)  
2. payload_expression (explicit expression tree)

Event declarations must be explicit.  
Event declarations must not include implicit payloads.  
Event declarations must not include nondeterministic constructs.  
Event declarations must serialize deterministically in Canonical IR.

Event payload expressions:

Payload expressions must follow the Expression Model.  
Payload expressions must not mutate state.  
Payload expressions must not allocate identifiers.  
Payload expressions must not reference nodes or edges created in the same commit.  
Payload expressions must not depend on nondeterministic values.  
Payload expressions must not observe staged writes.

Payload expressions may reference:

pattern variables  
let‑bound values  
pure functions  
effect_deterministic functions (with declared_reads)  
literal values  
deterministic expressions  

Payload expressions must not reference:

version counters  
sequence counters  
tick counters  
runtime metadata  
system time  
random numbers  

Event emission:

Events are emitted during the event emission phase of the tick.  
Event emission occurs after commit.  
Event emission must not mutate state.  
Event emission must not influence dependency validation.  
Event emission must not influence match selection.  
Event emission must not influence future ticks.

Event ordering:

Events must be emitted in the order they appear in the rule’s event list.  
If multiple rules fire in the same tick (not possible in GRISP v0.20), ordering would be lexicographic by rule_id, but GRISP v0.20 fires at most one rule per tick.  
Event ordering must not depend on runtime metadata.  
Event ordering must not depend on nondeterministic values.

Event structure:

Each emitted event must serialize as an object with the following keys:

type  
payload  

type must be a UTF‑8 string.  
payload must serialize using canonical JSON.  
payload must not contain nondeterministic content.  
payload must not contain invalid identifiers.

Event determinism:

Events must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Events must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers  

Event validity:

An event is valid if and only if:

1. event_type is a valid UTF‑8 string.  
2. payload_expression is deterministic.  
3. payload_expression does not mutate state.  
4. payload_expression does not allocate identifiers.  
5. payload_expression does not reference invalid identifiers.  
6. payload_expression serializes deterministically.  
7. No nondeterministic constructs are used.  
8. No implicit behavior is introduced.

Invalid events must cause manifest rejection before execution.

Event lifecycle summary:

1. Declared in rule.  
2. Evaluated after commit.  
3. Emitted in deterministic order.  
4. Serialized using canonical JSON.  
5. Delivered to external observers.  
6. Never influence engine state.

End of SPEC 028.


SPEC 029 Collection Model

The collection model defines how GRISP evaluates, filters, orders, and materializes collections during match discovery, let evaluation, priority evaluation, and event payload evaluation. Collections must be deterministic. Collections must not depend on runtime metadata or nondeterministic values. Collections must not mutate state. Collections must not allocate identifiers.

Collection purpose:

1. Provide deterministic iteration over sets of nodes, edges, or values.  
2. Allow rules to express queries over graph structure.  
3. Ensure reproducibility across all conformant engines.  
4. Provide a stable basis for dependency extraction.

Collection categories:

1. Node collections  
2. Edge collections  
3. Field‑derived collections  
4. Expression‑derived collections  
5. Filtered collections  
6. Ordered collections  
7. Mapped collections  
8. Reduced collections

All collections must be explicit in Canonical IR.  
No implicit filtering, ordering, or mapping is permitted.

Node collections:

A node collection enumerates all nodes of a given type.  
Node collections introduce an Extent dependency on the node type.  
Node collections must enumerate nodes in identifier order.  
Node collections must not include deleted nodes.  
Node collections must not include nodes created in the same commit.

Edge collections:

An edge collection enumerates all edges of a given type.  
Edge collections introduce an EdgeType dependency.  
Edge collections must enumerate edges in identifier order.  
Edge collections must not include deleted edges.  
Edge collections must not include edges created in the same commit.

Field‑derived collections:

A field‑derived collection extracts a field value from each element of another collection.  
Field‑derived collections introduce Field dependencies.  
Field‑derived collections must preserve deterministic ordering.

Expression‑derived collections:

A collection may be constructed from literal arrays or deterministic expressions.  
Expression‑derived collections must not depend on nondeterministic values.  
Expression‑derived collections must not mutate state.

Filtered collections:

A filtered collection applies a deterministic boolean predicate to each element.  
The predicate must follow the Expression Model.  
The predicate must not mutate state.  
The predicate must not allocate identifiers.  
Filtering must preserve ordering of surviving elements.  
Filtering must not introduce nondeterministic behavior.

Ordered collections:

An ordered collection applies an explicit order_by list.  
Each order_by entry must be an explicit expression.  
Ordering must be deterministic.  
Ordering must not depend on runtime metadata.  
If order_by is empty, identifier ordering is used.  
Ordering must not use locale‑aware comparison.  
Ordering must not normalize Unicode.

Mapped collections:

A mapped collection applies a deterministic expression to each element.  
Mapping must not mutate state.  
Mapping must not allocate identifiers.  
Mapping must not introduce nondeterministic behavior.  
Mapping must preserve the ordering of the source collection.

Reduced collections:

A reduced collection applies a deterministic reduction operator such as sum, min, max, or count.  
Reduction must not mutate state.  
Reduction must not allocate identifiers.  
Reduction must not depend on nondeterministic values.  
Reduction must not depend on runtime metadata.

Collection determinism:

Collections must be deterministic across:  
all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Collections must not depend on:  
hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Collection dependency extraction:

Node collections introduce Extent(node_type).  
Edge collections introduce EdgeType(edge_type).  
Field‑derived collections introduce Field dependencies.  
Filtered collections inherit dependencies from the predicate.  
Ordered collections inherit dependencies from order_by expressions.  
Mapped collections inherit dependencies from mapping expressions.  
Reduced collections inherit dependencies from reduction expressions.

Collection validity:

A collection is valid if and only if:

1. All referenced types exist.  
2. All referenced fields exist.  
3. All expressions are deterministic.  
4. All dependencies are extractable.  
5. No nondeterministic constructs are used.  
6. No state mutation occurs.  
7. No identifier allocation occurs.  
8. The collection serializes deterministically.

Invalid collections must cause manifest rejection before execution.

End of SPEC 029.


SPEC 030 Identifier Model

The identifier model defines the structure, allocation, comparison, serialization, and determinism requirements for all identifiers used in GRISP. Identifiers must be deterministic. Identifiers must not depend on runtime metadata, memory layout, nondeterministic values, or engine‑specific behavior. Identifiers must serialize deterministically and must be identical across all conformant engines.

Identifier purpose:

1. Provide stable, deterministic references to nodes and edges.  
2. Ensure reproducible ordering across all engines and platforms.  
3. Support deterministic serialization in canonical JSON.  
4. Support deterministic match_key construction.  
5. Support deterministic dependency extraction.

Identifier structure:

Identifiers must be UTF‑8 strings of the form:

TypeName:sequence

TypeName is the declared node or edge type.  
sequence is a non‑negative integer with no leading zeros.  
sequence must be allocated deterministically using sequence counters.

Identifier allocation:

Identifiers are allocated only during commit.  
Identifiers must be allocated by incrementing sequence_counter[type_name].  
sequence_counter[type_name] must start at 0 for each type.  
sequence_counter[type_name] must increment by exactly 1 for each allocation.  
sequence_counter[type_name] must never decrement.  
sequence_counter[type_name] must never skip values.  
sequence_counter[type_name] must never wrap.  
Overflow is a fatal conformance error.

Identifier determinism:

Identifier allocation must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Identifier allocation must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Identifier comparison:

Identifiers must be compared using raw UTF‑8 byte lexicographic ordering.  
Identifier comparison must not interpret numeric substrings as numbers.  
Identifier comparison must not use locale‑aware ordering.  
Identifier comparison must not normalize Unicode.  
Identifier comparison must not apply case folding.

Identifier validity:

An identifier is valid if and only if:

1. It matches the TypeName:sequence format.  
2. TypeName is a declared type.  
3. sequence is a non‑negative integer with no leading zeros.  
4. The identifier refers to an existing node or edge.  
5. The identifier has not been deleted.  
6. The identifier does not refer to an object created later in the same commit.  
7. The identifier serializes deterministically.

Invalid identifiers must cause manifest rejection or match rejection.

Identifier lifetime:

Identifiers persist until deleted.  
Identifiers must not be reused after deletion.  
Identifiers must not be recycled across ticks.  
Identifiers must not be recycled across engine restarts.  
Identifiers must not be recycled across manifest reloads.

Identifier and dependency interaction:

NodeExistence dependencies reference node identifiers.  
EdgeType dependencies reference edge type names, not identifiers.  
Adjacency dependencies reference node identifiers.  
Field dependencies reference node or edge identifiers.  
Ordering and Predicate dependencies reference type names.

Identifier serialization:

Identifiers must serialize as UTF‑8 strings without escaping except as required by canonical JSON.  
Identifiers must not include whitespace.  
Identifiers must not include metadata.  
Identifiers must not include nondeterministic content.

Identifier and match_key:

Identifiers must appear in match_key exactly as allocated.  
Identifiers must not be transformed.  
Identifiers must not be normalized.  
Identifiers must not be abbreviated.

Identifier and canonical IR:

Identifiers must not appear in Canonical IR except in debugging output.  
Canonical IR must not contain allocated identifiers.  
Canonical IR must not depend on identifier values.

Identifier and commit:

Identifiers may only be allocated during commit.  
Identifiers must not be allocated during match discovery.  
Identifiers must not be allocated during let evaluation.  
Identifiers must not be allocated during priority evaluation.  
Identifiers must not be allocated during event payload evaluation.

Identifier and nondeterminism:

Identifiers must not encode nondeterministic information such as:

timestamps  
memory addresses  
thread ids  
random numbers  
hash values  

Any such encoding is a conformance violation.

End of SPEC 030.


SPEC 031 Version Counter Model

The version counter model defines how GRISP tracks state changes, detects invalidated matches, enforces dependency correctness, and guarantees deterministic behavior across all conformant engines. Version counters must be deterministic. Version counters must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Version counters must serialize deterministically.

Purpose of version counters:

1. Detect when a match becomes invalid due to state changes.  
2. Ensure that rules only fire when all dependencies remain stable.  
3. Provide deterministic invalidation semantics.  
4. Support reproducible match discovery and validation.  
5. Guarantee that no rule observes stale or partially updated state.

Version counter categories:

1. existence_version[node_id]  
2. field_versions[node_id][field_name]  
3. field_versions[edge_id][field_name]  
4. predicate_version[type_name][field_name]  
5. ordering_version[type_name][field_name]  
6. extent_version[type_name]  
7. edge_type_version[edge_type]  
8. sequence_counter[type_name] (identifier allocation)

All version counters must be 64‑bit signed integers.  
All version counters must start at 0.  
All increments must be exactly +1.  
Version counters must never decrement.  
Version counters must never skip values.  
Version counters must never wrap.  
Overflow is a fatal conformance error.

1. existence_version

existence_version[node_id] increments when:  
a. the node is created (implicitly, via sequence_counter allocation)  
b. the node is deleted  
c. an edge incident to the node is created  
d. an edge incident to the node is deleted

existence_version ensures that adjacency and existence dependencies are validated deterministically.

2. field_versions

field_versions[node_id][field_name] increments when:  
a. UpdateField modifies the field  
b. DeleteNode deletes the node (all fields increment once)

field_versions[edge_id][field_name] increments when:  
a. UpdateEdgeField modifies the field  
b. DeleteEdge deletes the edge (all fields increment once)

3. predicate_version

predicate_version[type_name][field_name] increments when:  
a. any node or edge of that type has the field updated  
b. any node or edge of that type is created  
c. any node or edge of that type is deleted

predicate_version ensures that collection filters remain valid.

4. ordering_version

ordering_version[type_name][field_name] increments when:  
a. any node or edge of that type has the field updated  
b. any node or edge of that type is created  
c. any node or edge of that type is deleted

ordering_version ensures that ordered collections remain valid.

5. extent_version

extent_version[type_name] increments when:  
a. a node of that type is created  
b. a node of that type is deleted

extent_version ensures that node collections remain valid.

6. edge_type_version

edge_type_version[edge_type] increments when:  
a. an edge of that type is created  
b. an edge of that type is deleted

edge_type_version ensures that edge collections remain valid.

7. sequence_counter

sequence_counter[type_name] increments when:  
a. CreateNode allocates a new node identifier  
b. CreateEdge allocates a new edge identifier

sequence_counter must never be read by rules.  
sequence_counter must not appear in expressions.  
sequence_counter must not influence match selection.

Dependency validation:

During dependency validation, the engine compares:  
recorded_version == current_version

If any version counter differs, the match is invalid.  
Invalid matches must be discarded.  
Invalid matches must not fire.  
Invalid matches must not produce staged writes.  
Invalid matches must not emit events.

Version counter determinism:

Version counters must be deterministic across:  
all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Version counters must not depend on:  
hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Version counter validity:

A version counter is valid if and only if:  
1. It increments exactly as defined.  
2. It never decrements.  
3. It never skips values.  
4. It never wraps.  
5. It serializes deterministically.  
6. It does not encode nondeterministic information.  
7. It is used only for dependency validation.

Invalid version counter behavior must cause engine failure or manifest rejection.

End of SPEC 031.


SPEC 032 Dependency Model

The dependency model defines how GRISP determines whether a match remains valid between discovery and commit. Dependencies must be deterministic. Dependencies must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Dependencies must serialize deterministically and must be identical across all conformant engines.

Purpose of dependencies:

1. Ensure that matches remain valid between discovery and commit.  
2. Prevent rules from firing based on stale or inconsistent state.  
3. Guarantee deterministic invalidation of matches.  
4. Support reproducible match selection across all engines.  
5. Provide a minimal, explicit set of version counters that must remain stable.

Dependency categories:

1. NodeExistence(node_id)  
2. Field(node_id or edge_id, field_name)  
3. Predicate(type_name, field_name)  
4. Ordering(type_name, field_name)  
5. Extent(type_name)  
6. EdgeType(edge_type)  
7. Adjacency(edge_type, source_id, target_id)

All dependencies must be explicit.  
No implicit dependencies are permitted.  
No inferred dependencies are permitted.  
No dependency may reference nodes or edges created in the same commit.

Dependency extraction:

Dependencies are extracted during match discovery.  
Dependencies must be extracted from:

pattern bindings  
field accesses  
collection operations  
effect_deterministic function declared_reads  
where expressions  
let expressions  
priority expressions  

Dependencies must not be extracted from:

event payload expressions  
actions  
staged writes  
commit phase behavior  

Dependency extraction must be deterministic.  
Dependency extraction must not depend on hash map iteration order.

Dependency structure:

Each dependency records:

dependency_type  
identifier or type_name  
field_name (if applicable)  
recorded_version (the version counter at discovery time)

recorded_version must be captured exactly once.  
recorded_version must not be updated after discovery.  
recorded_version must not depend on nondeterministic values.

Dependency validation:

During dependency validation, the engine checks:

recorded_version == current_version

If equal, the dependency is valid.  
If not equal, the dependency is invalid.  
If any dependency is invalid, the match is discarded.  
Invalid matches must not fire.  
Invalid matches must not produce staged writes.  
Invalid matches must not emit events.

Dependency types in detail:

1. NodeExistence(node_id)  
Tracks existence_version[node_id].  
Introduced by node bindings and adjacency constraints.

2. Field(id, field_name)  
Tracks field_versions[id][field_name].  
Introduced by field accesses and field‑derived collections.

3. Predicate(type_name, field_name)  
Tracks predicate_version[type_name][field_name].  
Introduced by filtered collections.

4. Ordering(type_name, field_name)  
Tracks ordering_version[type_name][field_name].  
Introduced by ordered collections.

5. Extent(type_name)  
Tracks extent_version[type_name].  
Introduced by node collections.

6. EdgeType(edge_type)  
Tracks edge_type_version[edge_type].  
Introduced by edge collections.

7. Adjacency(edge_type, source_id, target_id)  
Tracks existence_version[source_id] and existence_version[target_id].  
Introduced by constrained edge bindings.

Dependency determinism:

Dependencies must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Dependencies must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Dependency ordering:

Dependencies must be sorted lexicographically by:

1. dependency_type  
2. identifier or type_name  
3. field_name (if applicable)

Dependency ordering must be used when serializing matches.  
Dependency ordering must not influence match selection.

Dependency validity:

A dependency is valid if and only if:

1. It references a valid identifier or type.  
2. It references a valid field (if applicable).  
3. It records a valid version counter.  
4. It does not reference objects created in the same commit.  
5. It serializes deterministically.  
6. It does not include nondeterministic content.

Invalid dependencies must cause manifest rejection or match rejection.

End of SPEC 032.


SPEC 033 Rule Model

The rule model defines the complete structure, semantics, determinism requirements, and execution behavior of rules in GRISP. Rules are the fundamental unit of computation. Rules must be deterministic. Rules must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Rules must serialize deterministically in Canonical IR.

Rule purpose:

1. Define pattern‑based state transformations.  
2. Provide deterministic matching, scoring, and selection.  
3. Emit deterministic events.  
4. Mutate state only through explicit actions.  
5. Support reproducible execution across all conformant engines.

Rule structure:

Each rule consists of the following components:

1. rule_id  
2. pattern (explicit list of bindings)  
3. where clause (deterministic boolean expression)  
4. let bindings (explicit list of deterministic expressions)  
5. priority expression  
6. actions (explicit list)  
7. events (explicit list)

All components must be explicit.  
No implicit behavior is permitted.  
No omitted fields are permitted in Canonical IR.

1. rule_id

rule_id must be a UTF‑8 string.  
rule_id must be unique across the manifest.  
rule_id must serialize deterministically.  
rule_id determines rule ordering during match discovery.

2. pattern

The pattern must follow the Pattern Model.  
The pattern defines the structural bindings for match discovery.  
The pattern introduces NodeExistence, EdgeType, Adjacency, Field, Predicate, Ordering, and Extent dependencies.

3. where clause

The where clause must be a deterministic boolean expression.  
The where clause must not mutate state.  
The where clause must not allocate identifiers.  
The where clause must not reference nodes or edges created in the same commit.  
The where clause must not depend on nondeterministic values.

4. let bindings

Let bindings must be explicit.  
Let bindings must evaluate deterministic expressions.  
Let bindings must not mutate state.  
Let bindings must not allocate identifiers.  
Let bindings must not reference nodes or edges created in the same commit.  
Let bindings must not depend on nondeterministic values.  
Let bindings must serialize deterministically.

5. priority expression

The priority expression must be a deterministic integer expression.  
The priority expression must not mutate state.  
The priority expression must not allocate identifiers.  
The priority expression must not depend on nondeterministic values.  
The priority expression must serialize deterministically.

base_priority = priority_expression  
scaled_priority = base_priority * priority_scale  
final_score = scaled_priority + fairness_boost

6. actions

Actions must follow the Action Model.  
Actions must be explicit.  
Actions must not read state outside the dependency set.  
Actions must not observe staged writes.  
Actions must not allocate identifiers except through CreateNode and CreateEdge.  
Actions must serialize deterministically.

7. events

Events must follow the Event Model.  
Events must be explicit.  
Events must not mutate state.  
Events must serialize deterministically.

Rule determinism:

Rules must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Rules must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Rule evaluation phases:

Rules participate in the following phases:

1. match discovery  
2. where evaluation  
3. let evaluation  
4. priority evaluation  
5. dependency extraction  
6. match scoring  
7. match ranking  
8. match selection  
9. commit (actions)  
10. event emission

Rules must not perform any computation outside these phases.

Rule validity:

A rule is valid if and only if:

1. rule_id is unique.  
2. All pattern bindings are valid.  
3. All where expressions are deterministic.  
4. All let expressions are deterministic.  
5. All priority expressions are deterministic.  
6. All actions are valid.  
7. All events are valid.

SPEC 034 Canonical IR Model

The Canonical IR (Intermediate Representation) model defines the exact, deterministic, engine‑independent serialization format for GRISP manifests. Canonical IR ensures that all conformant engines interpret manifests identically. Canonical IR must be deterministic. Canonical IR must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior.

Purpose of Canonical IR:

1. Provide a single, unambiguous representation of all manifests.  
2. Ensure deterministic parsing and interpretation across all engines.  
3. Eliminate ambiguity caused by formatting, whitespace, or ordering.  
4. Support reproducible hashing, comparison, and validation.  
5. Guarantee that two manifests with identical semantics produce identical IR.

Canonical IR properties:

1. Fully explicit  
2. Fully ordered  
3. Fully deterministic  
4. Free of syntactic sugar  
5. Free of optional fields  
6. Free of comments  
7. Free of whitespace significance  
8. Free of nondeterministic constructs

Canonical IR structure:

The top‑level Canonical IR object contains:

types  
functions  
rules  
constants  
priority_scale  
fairness_scale  

All keys must appear exactly once.  
All keys must appear in lexicographic order.  
All values must be explicit.

1. types

types is a list of type definitions.  
Each type definition must include:

type_name  
kind (node or edge)  
fields (explicit list)  
source_type (for edges)  
target_type (for edges)

Fields must be sorted lexicographically by field_name.  
Types must be sorted lexicographically by type_name.

2. functions

functions is a list of function definitions.  
Each function definition must include:

function_name  
parameters  
return_type  
body  
declared_reads (for effect_deterministic functions)

Functions must be sorted lexicographically by function_name.  
Parameters must be sorted lexicographically by parameter name.  
declared_reads must be sorted lexicographically.

3. rules

rules is a list of rule definitions.  
Each rule definition must include:

rule_id  
pattern  
where  
let  
priority  
actions  
events

Rules must be sorted lexicographically by rule_id.  
Pattern bindings must be sorted lexicographically by variable name.  
Let bindings must be sorted lexicographically by variable name.  
Actions must appear in manifest order but serialize deterministically.  
Events must appear in manifest order.

4. constants

constants is a list of literal name/value pairs.  
constants must be sorted lexicographically by name.  
constants must serialize deterministically.

5. priority_scale

priority_scale must be an integer literal.  
priority_scale must serialize deterministically.

6. fairness_scale

fairness_scale must be an integer literal.  
fairness_scale must serialize deterministically.

Canonical IR expression rules:

Expressions must serialize as explicit trees.  
Expressions must not serialize as infix strings.  
Expressions must not omit parentheses.  
Expressions must not rely on operator precedence.  
Expressions must not include whitespace beyond JSON rules.  
Expressions must not include comments.

Canonical IR ordering rules:

All lists must be sorted lexicographically unless otherwise specified.  
All object keys must be sorted lexicographically.  
All identifiers must appear exactly as declared.  
All strings must be UTF‑8.  
All numbers must be decimal integers with no leading zeros.

Canonical IR determinism:

Canonical IR must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Canonical IR must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Canonical IR validity:

Canonical IR is valid if and only if:

1. All required keys are present.  
2. All lists are sorted correctly.  
3. All expressions are explicit.  
4. All fields are explicit.  
5. All types, functions, and rules serialize deterministically.  
6. No nondeterministic constructs are present.  
7. No implicit behavior is present.  
8. No identifiers appear in IR.  
9. The IR is fully canonical.

Invalid Canonical IR must cause manifest rejection.

End of SPEC 034.

SPEC 037 Pattern Model

The pattern model defines how structural graph patterns are declared, matched, constrained, and serialized within GRISP. Patterns are the foundation of match discovery. Patterns must be deterministic. Patterns must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Patterns must serialize deterministically in Canonical IR.

Purpose of patterns:

1. Define the structural shape that must exist in the graph for a rule to match.  
2. Bind nodes and edges to variables.  
3. Introduce deterministic dependencies.  
4. Provide the basis for where evaluation, let evaluation, and priority evaluation.  
5. Ensure reproducible match discovery across all conformant engines.

Pattern components:

1. Node bindings  
2. Edge bindings  
3. Adjacency constraints  
4. Field constraints  
5. Type constraints  
6. Optionality (not supported in GRISP v0.20)  
7. Negation (not supported in GRISP v0.20)

All pattern components must be explicit.  
No implicit constraints are permitted.  
No implicit joins are permitted.  
No implicit filtering is permitted.

1. Node bindings

A node binding introduces a variable bound to a node of a specific type:

var: NodeType

Node bindings introduce:

NodeExistence(var)  
Extent(NodeType)

Node bindings must not reference nodes created in the same commit.  
Node bindings must not reference deleted nodes.

2. Edge bindings

An edge binding introduces a variable bound to an edge of a specific type:

var: EdgeType

Edge bindings introduce:

EdgeType(EdgeType)  
Field(var, field_name) for all fields  
Adjacency constraints when endpoints are referenced

Edge bindings must not reference edges created in the same commit.  
Edge bindings must not reference deleted edges.

3. Adjacency constraints

Adjacency constraints connect node and edge bindings:

edge_var.source == node_var  
edge_var.target == node_var

Adjacency constraints introduce:

NodeExistence(node_var)  
Adjacency(EdgeType, source_id, target_id)

Adjacency constraints must be explicit.  
Adjacency constraints must not be inferred.

4. Field constraints

Field constraints restrict matches based on field values:

node_var.field == expression  
edge_var.field == expression

Field constraints introduce:

Field(node_var, field_name)  
Field(edge_var, field_name)

Field constraints must be deterministic.  
Field constraints must not mutate state.  
Field constraints must not allocate identifiers.

5. Type constraints

Type constraints are implicit in node and edge bindings.  
Type constraints must not be overridden.  
Type constraints must not be dynamic.

6. Unsupported constructs

The following constructs are not supported in GRISP v0.20:

optional pattern elements  
negative pattern elements  
disjunctions  
recursive patterns  
wildcard types  
pattern functions  
pattern macros  

Any attempt to use unsupported constructs must cause manifest rejection.

Pattern ordering:

Pattern bindings must be sorted lexicographically by variable name in Canonical IR.  
Pattern ordering must not influence match discovery semantics.  
Pattern ordering must not influence match selection.

Pattern determinism:

Patterns must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Patterns must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

1. All variables are uniquely named.

5. All field constraints are deterministic.  
6. All dependencies are extractable.  
7. No nondeterministic constructs are used.  
8. No implicit behavior is introduced.  
9. The pattern serializes deterministically.

Invalid patterns must cause manifest rejection.

Pattern lifecycle:

1. Declared in rule.  
2. Participates in match discovery every tick.  
3. Produces zero or more structural bindings.  
4. Feeds into where evaluation, let evaluation, and priority evaluation.  
5. Remains active until manifest is replaced.

SPEC 040 Priority Model

The priority model defines how GRISP computes deterministic rule priorities, fairness adjustments, and final match scores. Priority evaluation determines which match is selected when multiple valid matches exist. Priority computation must be deterministic. Priority computation must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Priority computation must serialize deterministically in Canonical IR.

Purpose of the priority model:

1. Provide deterministic rule selection when multiple matches exist.  
2. Allow rules to express relative importance.  
3. Ensure fairness across repeated ticks.  
4. Guarantee reproducible match selection across all conformant engines.

Priority components:

1. base_priority  
2. priority_scale  
3. match_age  
4. fairness_scale  
5. final_score  

All components must be deterministic.  
All arithmetic must use 64‑bit signed integers.  
Overflow is a fatal conformance error.

1. base_priority

base_priority is computed from the rule’s priority expression.  
The priority expression must be a deterministic integer expression.  
The priority expression may reference:

pattern variables  
let variables  
pure functions  
effect_deterministic functions  
deterministic expressions  

The priority expression must not reference:

nodes or edges created in the same commit  
version counters  
sequence counters  
tick counters  
runtime metadata  
system time  
random numbers  

2. priority_scale

priority_scale is a manifest‑level integer constant.  
priority_scale must be deterministic.  
priority_scale must serialize deterministically.  
priority_scale must be applied uniformly to all rules.

scaled_priority = base_priority * priority_scale

3. match_age

match_age is the number of consecutive ticks in which the same match (same match_key) has remained valid but not selected.  
match_age increments by 1 each tick if:

the match reappears with identical bindings  
the match was not selected  
the match was not invalidated  

match_age resets to 0 if:

the match disappears  
the match becomes invalid  
the match is selected  

match_age must be deterministic.  
match_age must not depend on runtime metadata.

4. fairness_scale

fairness_scale is a manifest‑level integer constant.  
fairness_scale must be deterministic.  
fairness_scale must serialize deterministically.

fairness_boost = match_age * fairness_scale

5. final_score

final_score = scaled_priority + fairness_boost

final_score must be a 64‑bit signed integer.  
final_score must not overflow.  
final_score must be deterministic.

Priority ordering:

Matches are ranked by:

1. final_score (descending)  
2. match_key (lexicographic)  

Sorting must be stable.  
Sorting must be deterministic.  
Sorting must not depend on hash map iteration order.

Priority determinism:

Priority computation must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Priority computation must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Priority validity:

Priority computation is valid if and only if:

1. The priority expression is deterministic.  
2. All referenced variables are declared.  
3. All referenced fields exist.  
4. All referenced functions are valid.  
5. All arithmetic fits in 64‑bit signed integers.  
6. No nondeterministic constructs are used.  
7. The computation serializes deterministically.

Invalid priority expressions must cause manifest rejection.

Priority lifecycle:

1. base_priority computed during match discovery  
2. scaled_priority computed using priority_scale  
3. match_age updated at tick start  
4. fairness_boost computed  
5. final_score computed  
6. matches ranked  
7. highest‑ranked valid match selected  

End of SPEC 040.


SPEC 041 Match Model

The match model defines how GRISP discovers, evaluates, validates, ranks, and selects matches for rule execution. A match represents a fully bound instance of a rule’s pattern, where clause, and let bindings. Match processing must be deterministic. Match processing must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Match processing must serialize deterministically.

Purpose of the match model:

1. Identify all valid instances of rule patterns.  
2. Apply semantic filtering via where clauses.  
3. Compute deterministic let bindings.  
4. Extract dependencies for validation.  
5. Compute deterministic priority scores.  
6. Rank matches deterministically.  
7. Select exactly one match per tick.

Match lifecycle:

1. Structural match discovery  
2. Where clause evaluation  
3. Let binding evaluation  
4. Dependency extraction  
5. Priority evaluation  
6. Match_key construction  
7. Match scoring  
8. Match ranking  
9. Match selection  
10. Commit and event emission

Each phase must be deterministic.

1. Structural match discovery

The engine enumerates all possible bindings that satisfy the pattern.  
Structural matches must be discovered in lexicographic order of variable names.  
Structural matches must not include nodes or edges created in the same commit.  
Structural matches must not include deleted nodes or edges.  
Structural matches introduce initial dependencies:

NodeExistence  
EdgeType  
Adjacency  
Field  
Extent  

2. Where clause evaluation

For each structural match, the where clause is evaluated.  
If the where clause evaluates to false, the match is discarded.  
Where evaluation may introduce additional dependencies.  
Where evaluation must be deterministic.

3. Let binding evaluation

Let bindings are evaluated in lexicographic order.  
Let bindings may reference earlier let bindings.  
Let bindings may introduce additional dependencies.  
Let bindings must be deterministic.

4. Dependency extraction

All dependencies from:

pattern  
where clause  
let bindings  
priority expression  
declared_reads  

must be collected.  
Dependencies must be sorted lexicographically.  
Dependencies must be recorded with their version counters.  
Dependencies must not reference objects created in the same commit.

5. Priority evaluation

base_priority is computed from the priority expression.  
scaled_priority = base_priority * priority_scale  
fairness_boost = match_age * fairness_scale  
final_score = scaled_priority + fairness_boost  

Priority evaluation must be deterministic.  
Priority evaluation must not overflow 64‑bit signed integers.

6. Match_key construction

match_key is a deterministic serialization of:

rule_id  
pattern variable bindings (identifiers only)  

match_key must be unique for each distinct binding.  
match_key must be stable across ticks.  
match_key must be lexicographically comparable.  
match_key must not include nondeterministic content.

7. Match scoring

Each match receives a final_score.  
Matches must be sorted by:

1. final_score (descending)  
2. match_key (lexicographic)  

Sorting must be deterministic.  
Sorting must not depend on hash map iteration order.

8. Match ranking

The sorted list of matches forms the ranked match set.  
Only the highest‑ranked match may be selected.  
Ties are broken by match_key.

9. Match selection

Exactly one match is selected per tick.  
If no matches exist, no rule fires.  
If matches exist, the highest‑ranked valid match fires.  
Match selection must be deterministic.

10. Commit and event emission

The selected match executes its actions during commit.  
Events are emitted after commit.  
All other matches are discarded.

Match validity:

A match is valid if and only if:

1. All dependencies remain stable.  
2. All expressions are deterministic.  
3. No referenced identifiers were deleted.  
4. No referenced identifiers were created in the same commit.  
5. No nondeterministic constructs were used.  
6. The match serializes deterministically.

Invalid matches must be discarded before commit.

Match determinism:

Match processing must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Match processing must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

End of SPEC 041.


SPEC 042 Match Key Model

The match key model defines how GRISP constructs deterministic, stable identifiers for matches. Match keys ensure that fairness, match aging, and tie‑breaking behave identically across all conformant engines. Match keys must be deterministic. Match keys must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Match keys must serialize deterministically.

Purpose of the match key:

1. Provide a stable identity for each match across ticks.  
2. Support deterministic fairness aging.  
3. Support deterministic tie‑breaking when final_score is equal.  
4. Ensure reproducible match selection across all engines.  
5. Prevent nondeterministic ordering of matches.

Match key structure:

A match key consists of:

rule_id  
pattern variable bindings (identifiers only)  

Match keys must not include:

field values  
let values  
priority values  
event payloads  
actions  
dependencies  
runtime metadata  

Match keys must be minimal and deterministic.

Match key serialization:

Match keys must serialize as a UTF‑8 string.  
Match keys must serialize deterministically.  
Match keys must not include whitespace except as required by canonical JSON.  
Match keys must not include nondeterministic content.  
Match keys must not include memory addresses, timestamps, or random values.

Match key ordering:

Match keys must be compared lexicographically using raw UTF‑8 byte ordering.  
Match key ordering must not use locale‑aware comparison.  
Match key ordering must not normalize Unicode.  
Match key ordering must not interpret numeric substrings as numbers.

Match key determinism:

Match key construction must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Match key construction must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Match key construction rules:

1. rule_id appears first.  
2. Pattern variables appear in lexicographic order by variable name.  
3. Each variable contributes its identifier.  
4. Identifiers must appear exactly as allocated.  
5. No additional fields or metadata may be included.  
6. No implicit ordering or filtering is permitted.

Example structure (conceptual, not syntax):

(rule_id, varA_id, varB_id, varC_id)

Match key stability:

A match key remains stable across ticks if:

1. The same rule_id applies.  
2. The same identifiers are bound to the same variables.  
3. No referenced identifiers were deleted.  
4. No referenced identifiers were created in the same commit.  
5. The match remains structurally identical.

Match key instability:

A match key becomes invalid if:

1. Any bound identifier is deleted.  
2. Any bound identifier changes type (impossible in GRISP).  
3. The pattern no longer matches.  
4. The where clause fails.  
5. Dependencies become invalid.  
6. The rule is removed or replaced.  
7. The manifest is replaced.

When a match key becomes invalid, match_age resets to 0.

Match key and fairness:

match_age increments only when:

1. The match reappears with the same match key.  
2. The match is not selected.  
3. The match remains valid.

match_age resets when:

1. The match disappears.  
2. The match becomes invalid.  
3. The match is selected.  
4. The match key changes.

Match key validity:

A match key is valid if and only if:

1. rule_id is valid.  
2. All referenced identifiers exist.  
3. All referenced identifiers are stable.  
4. No nondeterministic content is included.  
5. The key serializes deterministically.  
6. The key is lexicographically comparable.

Invalid match keys must cause match rejection.

Match key lifecycle:

1. Constructed during match discovery.  
2. Used for fairness aging.  
3. Used for tie‑breaking during ranking.  
4. Discarded after commit.  
5. Reconstructed every tick.

End of SPEC 042.


SPEC 043 Commit Model

The commit model defines how GRISP applies state‑mutating actions in a deterministic, atomic, and isolated manner. Commit is the only phase in which the graph state may change. Commit must be deterministic. Commit must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Commit must serialize deterministically.

Purpose of the commit model:

1. Apply the selected match’s actions atomically.  
2. Ensure deterministic state transitions.  
3. Update version counters consistently.  
4. Allocate identifiers deterministically.  
5. Guarantee reproducible behavior across all conformant engines.

Commit phases:

1. Action evaluation  
2. Identifier allocation  
3. State mutation  
4. Version counter updates  
5. Post‑commit invariants  
6. Event emission (outside commit)

Commit must be atomic.  
Commit must not interleave with match discovery.  
Commit must not interleave with event emission.

1. Action evaluation

Actions are evaluated in manifest order.  
Actions may reference:

pattern variables  
let variables  
pure functions  
effect_deterministic functions  
deterministic expressions  

Actions must not reference:

nodes or edges created earlier in the same commit  
version counters  
sequence counters  
tick counters  
runtime metadata  
system time  
random numbers  

Action evaluation must be deterministic.

2. Identifier allocation

Identifiers may only be allocated by:

CreateNode  
CreateEdge  

Identifier allocation rules:

sequence_counter[type_name] increments by exactly 1  
identifier = type_name:sequence  
identifier must be unique  
identifier must serialize deterministically  
identifier must not depend on nondeterministic values  

Identifiers must not be allocated by any other mechanism.

3. State mutation

State mutation includes:

node creation  
edge creation  
field updates  
node deletion  
edge deletion  

State mutation must be deterministic.  
State mutation must not depend on hash map iteration order.  
State mutation must not depend on pointer addresses.

State mutation rules:

CreateNode  
Creates a new node with default field values.  
Allocates a deterministic identifier.  
Increments existence_version for the new node.  
Increments extent_version for the node type.

CreateEdge  
Creates a new edge with default field values.  
Allocates a deterministic identifier.  
Increments edge_type_version for the edge type.  
Increments existence_version for source and target nodes.

UpdateField  
Updates a node or edge field.  
Increments field_versions[id][field_name].  
Increments predicate_version[type][field_name].  
Increments ordering_version[type][field_name].

DeleteNode  
Deletes a node.  
Increments existence_version[node_id].  
Increments extent_version[type].  
Deletes all incident edges.  
Each deleted edge increments edge_type_version and existence_version of its endpoints.

DeleteEdge  
Deletes an edge.  
Increments edge_type_version.  
Increments existence_version of source and target nodes.

4. Version counter updates

Version counters must be updated exactly as defined in the Version Counter Model.  
Version counters must not be updated implicitly.  
Version counters must not be skipped.  
Version counters must not overflow.

5. Post‑commit invariants

After commit:

All identifiers must be unique.  
All version counters must be consistent.  
All deleted objects must be fully removed.  
All created objects must be fully initialized.  
No staged writes may remain.  
No partial state may exist.

6. Event emission (outside commit)

Events are emitted after commit.  
Events must not mutate state.  
Events must serialize deterministically.

Commit determinism:

Commit must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Commit must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Commit validity:

Commit is valid if and only if:

1. All actions are valid.  
2. All identifiers are allocated deterministically.  
3. All version counters are updated correctly.  
4. No nondeterministic constructs are used.  
5. No invalid references occur.  
6. The resulting state is consistent.  
7. The commit serializes deterministically.

Invalid commits must cause engine failure.

Commit lifecycle:

1. Selected match triggers commit.  
2. Actions evaluated.  
3. Identifiers allocated.  
4. State mutated.  
5. Version counters updated.  
6. Post‑commit invariants enforced.  
7. Events emitted.  
8. Tick completes.

End of SPEC 043.

The event model defines how GRISP constructs, serializes, and emits deterministic events after commit. Events allow rules to communicate state changes or notifications to external systems or higher‑level logic. Events must be deterministic. Events must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Events must serialize deterministically.

Purpose of the event model:

1. Provide deterministic, structured outputs from rule execution.  
2. Allow external systems to observe state transitions.  
3. Ensure reproducible event streams across all conformant engines.  
4. Separate state mutation (commit) from notification (post‑commit).  
5. Guarantee deterministic event ordering.

Event lifecycle:

1. Declared in rule  
2. Evaluated after commit  
3. Serialized deterministically  
4. Emitted in manifest order  
5. Delivered to the event sink  
6. Discarded after emission  

Events must not mutate state.  
Events must not allocate identifiers.  
Events must not read staged writes.

Event structure:

Each event consists of:

event_name  
payload_expression  

event_name must be a UTF‑8 string.  
event_name must be unique within the rule.  
payload_expression must follow the Expression Model.  
payload_expression must be deterministic.

Event ordering:

Events must be emitted:

1. In the order they appear in the rule  
2. After commit completes  
3. Before the next tick begins  

Event ordering must be deterministic.  
Event ordering must not depend on hash map iteration order.

Event payload evaluation:

Event payloads may reference:

pattern variables  
let variables  
pure functions  
effect_deterministic functions  
deterministic expressions  

Event payloads must not reference:

nodes or edges created earlier in the same commit  
version counters  
sequence counters  
tick counters  
runtime metadata  
system time  
random numbers  

Event payloads must not mutate state.  
Event payloads must not allocate identifiers.

Event serialization:

Events must serialize deterministically as:

event_name  
payload (canonical JSON)  

Event payloads must follow canonical JSON rules:

sorted object keys  
deterministic arrays  
UTF‑8 strings  
no nondeterministic content  

Event determinism:

Event emission must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Events must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Event dependencies:

Event payload expressions may introduce dependencies, but these dependencies do not affect match validity.  
Dependencies introduced by event payloads must not influence match selection.  
Dependencies introduced by event payloads must not be used for invalidation.

Event validity:

An event is valid if and only if:

1. event_name is unique within the rule  
2. payload_expression is deterministic  
3. all referenced variables are declared  
4. all referenced fields exist  
5. all referenced functions are valid  
6. no nondeterministic constructs are used  
7. no state mutation occurs  
8. no identifier allocation occurs

Invalid events must cause manifest rejection.

Event sink requirements:

The event sink must:

accept events in deterministic order  
not mutate engine state  
not introduce nondeterminism  
not reorder events  
not drop events  
not modify event payloads  

Event sink behavior is outside the scope of GRISP but must preserve determinism.

Event lifecycle summary:

1. Rule selected  
2. Commit applies state changes  
3. Events evaluated  
4. Events serialized  
5. Events emitted  
6. Tick completes  

End of SPEC 044.


SPEC 045 Tick Model

The tick model defines the deterministic execution cycle of the GRISP engine. Each tick represents one complete evaluation‑and‑commit cycle. All GRISP behavior is organized around ticks. Ticks must be deterministic. Ticks must not depend on runtime metadata, nondeterministic values, or engine‑specific behavior. Ticks must serialize deterministically.

Purpose of the tick model:

1. Provide a deterministic execution boundary.  
2. Ensure that match discovery and commit never interleave.  
3. Guarantee that exactly one rule fires per tick (or none).  
4. Maintain fairness through match aging.  
5. Produce deterministic event streams.  
6. Ensure reproducible behavior across all conformant engines.

Tick phases:

1. Tick start  
2. Match discovery  
3. Match evaluation  
4. Dependency validation  
5. Priority computation  
6. Match ranking  
7. Match selection  
8. Commit  
9. Event emission  
10. Tick end

Each phase must be deterministic.

1. Tick start

At tick start:

match_age counters are updated  
deleted objects from previous tick are fully purged  
no staged writes exist  
all version counters are stable  
the graph is in a consistent state  

Tick start must not mutate state except for match_age updates.

2. Match discovery

The engine enumerates all possible matches for all rules.  
Rules are processed in lexicographic order of rule_id.  
Pattern matching must be deterministic.  
Where clauses must be evaluated deterministically.  
Let bindings must be evaluated deterministically.  
Dependencies must be extracted deterministically.  
Matches must not include objects created in the same tick.

3. Match evaluation

For each match:

pattern is bound  
where clause is evaluated  
let bindings are evaluated  
priority expression is evaluated  
dependencies are extracted  
match_key is constructed  

Matches that fail any step are discarded.

4. Dependency validation

For each match:

recorded_version == current_version must hold for all dependencies  

If any dependency is invalid, the match is discarded.  
Invalid matches must not be scored or ranked.

5. Priority computation

For each valid match:

base_priority is computed  
scaled_priority = base_priority * priority_scale  
fairness_boost = match_age * fairness_scale  
final_score = scaled_priority + fairness_boost  

Priority computation must be deterministic.

6. Match ranking

Matches are sorted by:

1. final_score (descending)  
2. match_key (lexicographic)  

Sorting must be deterministic.  
Sorting must not depend on hash map iteration order.

7. Match selection

Exactly one match is selected:

If no matches exist, no rule fires.  
If matches exist, the highest‑ranked match fires.  
Match selection must be deterministic.

8. Commit

The selected match’s actions are applied atomically.  
Identifier allocation occurs.  
State mutation occurs.  
Version counters are updated.  
Post‑commit invariants are enforced.

Commit must be deterministic.

9. Event emission

Events declared in the selected rule are evaluated.  
Events are serialized deterministically.  
Events are emitted in manifest order.  
Events must not mutate state.

10. Tick end

At tick end:

all staged writes are cleared  
all events have been emitted  
the graph is in a consistent state  
the engine is ready for the next tick  

Tick determinism:

Tick execution must be deterministic across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules

Tick execution must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
system time  
random numbers

Tick validity:

A tick is valid if and only if:

1. All phases execute deterministically.  
2. Exactly one match fires (or none).  
3. Commit is valid.  
4. Events are deterministic.  
5. No nondeterministic constructs are used.  
6. The resulting state is consistent.

Invalid ticks must cause engine failure.

Tick lifecycle summary:

1. Begin tick  
2. Discover matches  
3. Evaluate matches  
4. Validate dependencies  
5. Compute priorities  
6. Rank matches  
7. Select match  
8. Commit  
9. Emit events  
10. End tick  

End of SPEC 045.


SPEC 046 Determinism Model

The determinism model defines the global, cross‑cutting rules that ensure all GRISP engines produce identical behavior for identical manifests and identical initial states. Determinism is the foundational requirement of GRISP. Any deviation from determinism constitutes a conformance failure. Determinism must be strict, total, and unconditional.

Purpose of the determinism model:

1. Guarantee reproducible execution across all conformant engines.  
2. Ensure that manifests behave identically across platforms, architectures, and schedules.  
3. Eliminate nondeterministic sources such as concurrency, randomness, or runtime metadata.  
4. Provide a deterministic foundation for debugging, verification, and reasoning.  
5. Ensure that GRISP is suitable for safety‑critical and correctness‑critical systems.

Determinism domains:

1. Structural determinism  
2. Expression determinism  
3. Function determinism  
4. Pattern determinism  
5. Match determinism  
6. Priority determinism  
7. Commit determinism  
8. Event determinism  
9. Serialization determinism  
10. Execution determinism

All domains must be deterministic.  
No domain may introduce nondeterminism.

1. Structural determinism

The graph structure must be deterministic.  
Node and edge identifiers must be deterministic.  
Identifier allocation must be deterministic.  
Version counters must be deterministic.  
Graph traversal must be deterministic.  
No hash map iteration order may influence behavior.

2. Expression determinism

All expressions must be deterministic.  
Expressions must not depend on:

system time  
random numbers  
pointer addresses  
thread scheduling  
locale  
floating point nondeterminism  
runtime metadata  

Expressions must serialize deterministically.

3. Function determinism

Functions must be deterministic.  
Pure functions must not read engine state.  
Effect_deterministic functions must declare all reads.  
Function bodies must serialize deterministically.  
Function evaluation must not depend on runtime metadata.

4. Pattern determinism

Pattern matching must be deterministic.  
Pattern bindings must be enumerated in lexicographic order.  
Pattern constraints must be explicit.  
No implicit joins or filters are permitted.  
Pattern matching must not depend on hash map iteration order.

5. Match determinism

Match discovery must be deterministic.  
Where evaluation must be deterministic.  
Let evaluation must be deterministic.  
Dependency extraction must be deterministic.  
Match_key construction must be deterministic.  
Match validity must be deterministic.

6. Priority determinism

Priority expressions must be deterministic.  
Priority scaling must be deterministic.  
Fairness aging must be deterministic.  
Match ranking must be deterministic.  
Tie‑breaking must be deterministic.

7. Commit determinism

Commit must be deterministic.  
Identifier allocation must be deterministic.  
State mutation must be deterministic.  
Version counter updates must be deterministic.  
Commit must not depend on hash map iteration order.

8. Event determinism

Event payloads must be deterministic.  
Event ordering must be deterministic.  
Event serialization must be deterministic.  
Event emission must not depend on runtime metadata.

9. Serialization determinism

Canonical IR must be deterministic.  
All object keys must be sorted lexicographically.  
All lists must be sorted deterministically.  
All expressions must serialize as explicit trees.  
No whitespace or formatting may influence semantics.

10. Execution determinism

Tick execution must be deterministic.  
Match selection must be deterministic.  
Commit must be deterministic.  
Event emission must be deterministic.  
The engine must not use concurrency to influence semantics.  
The engine must not use nondeterministic scheduling.

Prohibited nondeterminism sources:

system time  
random numbers  
floating point nondeterminism  
thread scheduling  
parallel execution  
hash map iteration order  
pointer addresses  
locale‑dependent behavior  
file system ordering  
network ordering  
environment variables  
process identifiers  

Any use of these sources is a conformance violation.

Determinism invariants:

1. Same manifest + same initial state = same behavior.  
2. Same match_key = same match identity across ticks.  
3. Same dependencies = same validation outcome.  
4. Same priority inputs = same final_score.  
5. Same commit inputs = same resulting state.  
6. Same event inputs = same event outputs.

Determinism enforcement:

Engines must enforce determinism at all levels.  
Engines must reject manifests that violate determinism.  
Engines must fail if nondeterminism is detected at runtime.  
Engines must not attempt to recover from nondeterminism.

Determinism lifecycle:

1. Manifest parsed into Canonical IR.  
2. All nondeterministic constructs rejected.  
3. Execution proceeds deterministically each tick.  
4. All state transitions deterministic.  
5. All events deterministic.  
6. Determinism preserved until manifest replacement.

End of SPEC 046.


SPEC 047 Conformance Model

The conformance model defines the requirements a GRISP engine must satisfy to be considered conformant. Conformance ensures that all engines behave identically for identical manifests and identical initial states. Conformance is strict. Any deviation from the conformance model constitutes a conformance failure.

Purpose of the conformance model:

1. Guarantee deterministic behavior across all conformant engines.  
2. Ensure that manifests execute identically across platforms.  
3. Provide a basis for verification, certification, and reproducibility.  
4. Prevent nondeterministic or undefined behavior.  
5. Ensure that GRISP remains suitable for correctness‑critical systems.

Conformance domains:

1. Canonical IR conformance  
2. Determinism conformance  
3. Execution conformance  
4. Action conformance  
5. Function conformance  
6. Pattern conformance  
7. Dependency conformance  
8. Version counter conformance  
9. Identifier allocation conformance  
10. Event conformance  
11. Error conformance

All domains must be satisfied.

1. Canonical IR conformance

A conformant engine must:

parse manifests into Canonical IR  
reject manifests that do not serialize deterministically  
reject manifests with missing or extra fields  
reject manifests with unsorted lists or keys  
reject manifests with nondeterministic expressions  
reject manifests with unsupported constructs  

Canonical IR must be the only accepted manifest format.

2. Determinism conformance

A conformant engine must:

execute deterministically  
reject nondeterministic constructs  
reject nondeterministic functions  
reject nondeterministic expressions  
reject nondeterministic ordering  
reject nondeterministic identifier allocation  

The engine must not introduce nondeterminism internally.

3. Execution conformance

A conformant engine must:

execute exactly one tick at a time  
never interleave match discovery and commit  
never interleave commit and event emission  
never execute multiple commits per tick  
never reorder events  
never reorder matches  

Execution must follow the Tick Model exactly.

4. Action conformance

A conformant engine must:

implement all actions exactly as defined  
reject invalid actions  
reject actions that reference undeclared variables  
reject actions that reference objects created earlier in the same commit  
reject actions that mutate state outside commit  
reject actions that allocate identifiers outside CreateNode and CreateEdge  

Actions must be applied atomically.

5. Function conformance

A conformant engine must:

evaluate pure functions deterministically  
evaluate effect_deterministic functions deterministically  
enforce declared_reads  
reject functions that mutate state  
reject functions that allocate identifiers  
reject functions that reference runtime metadata  

Function evaluation must follow the Function Model exactly.

6. Pattern conformance

A conformant engine must:

enumerate pattern matches deterministically  
reject patterns with undeclared variables  
reject patterns with invalid types or fields  
reject patterns with unsupported constructs  
reject patterns that introduce nondeterminism  

Pattern matching must follow the Pattern Model exactly.

7. Dependency conformance

A conformant engine must:

extract dependencies deterministically  
record version counters exactly once  
validate dependencies exactly as defined  
reject matches with invalid dependencies  
reject manifests with incomplete declared_reads  

Dependency handling must follow the Dependency Model exactly.

8. Version counter conformance

A conformant engine must:

increment version counters exactly as defined  
never skip increments  
never increment counters implicitly  
never decrement counters  
never reset counters  
never overflow counters  

Version counters must follow the Version Counter Model exactly.

9. Identifier allocation conformance

A conformant engine must:

allocate identifiers deterministically  
increment sequence counters exactly by 1  
never reuse identifiers  
never allocate identifiers implicitly  
never allocate identifiers outside commit  

Identifier allocation must follow the Identifier Model exactly.

10. Event conformance

A conformant engine must:

evaluate event payloads deterministically  
emit events in manifest order  
serialize events deterministically  
reject events with nondeterministic payloads  
reject events that mutate state  

Event handling must follow the Event Model exactly.

11. Error conformance

A conformant engine must:

fail fast on conformance violations  
never attempt to recover from nondeterminism  
never continue execution after invalid commit  
never silently ignore errors  
never produce partial state  

Conformance failures must be fatal.

Conformance invariants:

1. Same manifest + same initial state = same behavior.  
2. All engines must produce identical event streams.  
3. All engines must produce identical state transitions.  
4. All engines must produce identical match selections.  
5. All engines must produce identical identifier allocations.  
6. All engines must produce identical version counter updates.

Conformance lifecycle:

1. Manifest loaded  
2. Canonical IR validated  
3. Engine enters deterministic execution  
4. All ticks executed deterministically  
5. Conformance maintained until manifest replacement  

End of SPEC 047.


SPEC 048 Error Model

The error model defines how GRISP engines detect, classify, and respond to invalid manifests, invalid matches, invalid commits, nondeterministic behavior, and internal inconsistencies. GRISP requires strict, immediate, and deterministic error handling. Errors must never be ignored. Errors must never be recovered from. Errors must never produce partial or undefined behavior.

Purpose of the error model:

1. Ensure that invalid manifests are rejected deterministically.  
2. Ensure that invalid matches are discarded deterministically.  
3. Ensure that invalid commits cause engine failure.  
4. Ensure that nondeterminism is detected and treated as fatal.  
5. Ensure that engines never produce undefined or partial state.  
6. Provide a deterministic foundation for correctness‑critical systems.

Error categories:

1. Manifest errors  
2. Structural errors  
3. Expression errors  
4. Function errors  
5. Pattern errors  
6. Dependency errors  
7. Priority errors  
8. Match errors  
9. Commit errors  
10. Determinism errors  
11. Engine internal errors

All error categories must be handled deterministically.

1. Manifest errors

Manifest errors occur before execution begins.  
Manifest errors include:

invalid Canonical IR  
unsorted lists or keys  
missing required fields  
extra fields  
invalid types  
invalid functions  
invalid rules  
nondeterministic expressions  
unsupported constructs

Structural errors include:

invalid identifiers  
dangling edges  
missing fields  
invalid type references  
corrupted version counters

3. Expression errors

Expression errors include:

undefined variables  
invalid field references  
invalid function calls  
division by zero  
integer overflow  
nondeterministic constructs  
invalid comparisons

undeclared reads in effect_deterministic functions

5. Pattern errors

Pattern errors include:

undeclared variables  
invalid types  
invalid fields  
unsupported constructs  
nondeterministic constraints

6. Dependency errors

Dependency errors occur when validating dependencies.  
Dependency errors include:

missing dependencies  
incomplete declared_reads  
invalid version counters  
dependencies referencing deleted objects  
dependencies referencing objects created in the same commit  

Dependency errors must cause match rejection.

7. Priority errors

Priority errors occur during priority evaluation.  
Priority errors include:

integer overflow  
invalid expressions  
nondeterministic expressions  
invalid match_age

Match errors include:

invalid pattern bindings  
invalid where clause  
invalid let bindings  
invalid dependencies  
invalid match_key  
nondeterministic evaluation

Commit errors include:

invalid identifier allocation  
invalid field updates  
invalid deletions  
invalid version counter updates  
state mutation outside commit  
nondeterministic behavior  

Commit errors must cause engine failure.

10. Determinism errors

Determinism errors occur when nondeterminism is detected.  
Determinism errors include:

hash map iteration order influencing behavior  
pointer addresses influencing behavior  
thread scheduling influencing behavior  
locale influencing behavior  
system time influencing behavior  
random numbers influencing behavior  

Determinism errors must cause engine failure.

11. Engine internal errors

Internal errors include:

memory corruption  
unexpected null references  
invalid internal state  
unexpected exceptions  

Internal errors must cause engine failure.

Error handling rules:

1. Errors must never be ignored.  
2. Errors must never be silently corrected.  
3. Errors must never produce partial state.  
4. Errors must never allow execution to continue.  
5. Errors must be deterministic.  
6. Errors must not depend on runtime metadata.

Manifest errors → manifest rejection  
Match errors → match discarded  
Commit errors → engine failure  
Determinism errors → engine failure  
Internal errors → engine failure  

Error lifecycle:

1. Manifest loaded  
2. Manifest validated  
3. Errors cause rejection  
4. Execution begins  
5. Errors during match evaluation cause match rejection  
6. Errors during commit cause engine failure  
7. Errors during event emission cause engine failure

SPEC 049 Engine Model

The engine model defines the complete operational behavior of a conformant GRISP engine. It specifies how the engine loads manifests, maintains state, executes ticks, applies commits, emits events, enforces determinism, and handles errors. The engine model is the authoritative description of how a GRISP engine must behave.

Purpose of the engine model:

1. Define the complete lifecycle of a GRISP engine.  
2. Ensure deterministic execution across all conformant implementations.  
3. Provide a reference for engine developers.  
4. Guarantee correctness, reproducibility, and safety.  
5. Integrate all other models into a unified execution framework.

Engine lifecycle:

1. Engine initialization  
2. Manifest loading  
3. Canonical IR validation  
4. State initialization  
5. Tick execution loop  
6. Manifest replacement  
7. Engine shutdown  

Each stage must be deterministic.

1. Engine initialization

At startup, the engine must:

initialize empty graph state  
initialize all version counters to zero  
initialize all sequence counters to zero  
initialize match_age table to empty  
initialize event sink  
initialize deterministic memory structures  

The engine must not load any manifest automatically.  
The engine must not create any nodes or edges automatically.

2. Manifest loading

When a manifest is provided:

the engine must parse it into Canonical IR  
the engine must validate Canonical IR  
the engine must reject invalid manifests  
the engine must replace the previous manifest atomically  

Manifest replacement resets:

all match_age counters  
all pending matches  
all pending events  

Manifest replacement does not modify graph state.

3. Canonical IR validation

The engine must validate:

types  
functions  
rules  
constants  
priority_scale  
fairness_scale  
expression trees  
declared_reads  
ordering of all lists  
deterministic serialization  

Validation must be deterministic.  
Validation must reject any nondeterministic construct.

4. State initialization

After manifest validation:

the engine enters deterministic execution mode  
the graph state remains unchanged  
all version counters remain unchanged  
all sequence counters remain unchanged  

State initialization must not mutate the graph.

5. Tick execution loop

The engine enters the tick loop:

loop forever or until shutdown  
execute one deterministic tick  
emit events  
wait for next tick trigger  

Tick triggers may be external or internal but must not influence semantics.

Tick execution must follow the Tick Model exactly.

6. Manifest replacement

A manifest may be replaced at any tick boundary.  
Manifest replacement must be atomic.  
Manifest replacement must not interleave with tick execution.  
Manifest replacement must not modify graph state.  
Manifest replacement resets match_age.

7. Engine shutdown

Shutdown must be deterministic.  
Shutdown must not emit additional events.  
Shutdown must not mutate graph state.  
Shutdown must not leave partial state.

Engine responsibilities:

A conformant engine must:

enforce determinism  
enforce conformance  
enforce atomicity of commit  
enforce ordering of events  
enforce ordering of matches  
enforce version counter rules  
enforce identifier allocation rules  
enforce dependency validation  
enforce error handling rules  

Engine prohibitions:

A conformant engine must not:

introduce nondeterminism  
use concurrency to influence semantics  
use hash map iteration order  
use pointer addresses  
use system time  
use random numbers  
use locale‑dependent behavior  
mutate state outside commit  
allocate identifiers outside commit  
evaluate expressions during commit except action values  
evaluate events before commit  
evaluate commit before match selection  

Engine internal structures:

The engine must maintain:

graph state  
version counters  
sequence counters  
match_age table  
manifest IR  
event sink  
deterministic memory structures  

Engine internal structures must not leak nondeterminism.

Engine invariants:

1. Graph state is always consistent.  
2. Version counters are always correct.  
3. Identifiers are always unique.  
4. No partial commits occur.  
5. No nondeterministic behavior occurs.  
6. No invalid matches are selected.  
7. No invalid events are emitted.  
8. No invalid manifests are accepted.

Engine failure:

The engine must fail immediately if:

a commit error occurs  
a determinism error occurs  
a structural error occurs  
an internal error occurs  

Engine failure must halt execution.  
Engine failure must not produce partial state.

Engine restart:

After failure, the engine may be restarted with:

the same manifest  
a new manifest  
a new initial state  

Restart behavior is outside the scope of GRISP.

Engine determinism:

The engine must produce identical behavior across:

all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  
all conformant implementations  

Engine determinism is absolute.

End of SPEC 049.


SPEC 050 Canonical IR Model

The Canonical IR (Intermediate Representation) model defines the exact, deterministic, fully normalized representation of a GRISP manifest. Canonical IR is the only accepted input format for a conformant engine. All manifests must be converted to Canonical IR before execution. Canonical IR must be deterministic. Canonical IR must not contain any nondeterministic content. Canonical IR must be stable across all conformant engines.

Purpose of the Canonical IR model:

1. Provide a single, unambiguous representation of manifests.  
2. Eliminate syntactic variability.  
3. Ensure deterministic parsing and validation.  
4. Guarantee identical interpretation across all engines.  
5. Serve as the foundation for conformance and determinism.

Canonical IR properties:

1. Fully explicit  
2. Fully normalized  
3. Fully sorted  
4. Fully deterministic  
5. Free of syntactic sugar  
6. Free of optional shorthand  
7. Free of nondeterministic constructs  
8. Free of engine‑specific extensions  

Canonical IR must be strict and minimal.

Canonical IR structure:

A Canonical IR manifest consists of:

types  
functions  
rules  
priority_scale  
fairness_scale  
constants (if any)  

All sections must be present.  
All sections must be sorted lexicographically.  
All lists must be sorted lexicographically.  
All object keys must be sorted lexicographically.

Canonical IR encoding:

Canonical IR must be encoded as canonical JSON:

UTF‑8 encoding  
no BOM  
no comments  
no trailing commas  
sorted object keys  
deterministic whitespace rules  
no extraneous whitespace  
no tabs  
no formatting that affects semantics  

Canonical IR must serialize identically across all engines.

1. Types in Canonical IR

Types must include:

type_name  
kind (node or edge)  
fields (sorted lexicographically)  
field types (explicit)  
default values (explicit)  

Types must not include:

implicit fields  
implicit defaults  
engine‑specific metadata  

2. Functions in Canonical IR

Functions must include:

function_name  
parameters (sorted lexicographically)  
return_type  
body (explicit expression tree)  
declared_reads (sorted lexicographically, if present)  

Functions must not include:

implicit parameters  
implicit return types  
implicit reads  
syntactic sugar  

3. Rules in Canonical IR

Rules must include:

rule_id

let (sorted lexicographically by variable name)  
priority (explicit integer expression)  
actions (in manifest order)  
events (in manifest order)  

Rules must not include:

implicit constraints  
implicit ordering  
syntactic sugar  
optional pattern elements  
negation  

4. Expressions in Canonical IR

Expressions must be explicit trees.  
Expressions must not use infix notation.  
Expressions must not use implicit coercions.  
Expressions must not use implicit truthiness.

Allowed expression forms:

field_access  
function_call  
object  
array

comparison  
arithmetic  
boolean

Actions must be explicit objects with:

target (if applicable)  
field_name (if applicable)  
value_expression (if applicable)  

Actions must not include:

implicit targets  
implicit field names  
implicit values  

6. Events in Canonical IR

Events must include:

event_name  
payload_expression  

Events must not include:

implicit payloads  
implicit names  

7. Sorting rules

Sorting must use raw UTF‑8 lexicographic ordering.  
Sorting must not use locale‑aware ordering.  
Sorting must not normalize Unicode.  
Sorting must not interpret numeric substrings as numbers.

Sorting applies to:

type names  
field names  
function names  
parameter names  
rule_ids  
pattern variable names  
let variable names  
declared_reads  
object keys  
lists of items  

8. Deterministic normalization

Canonical IR must normalize:

all whitespace  
all numeric formats  
all string encodings  
all boolean values  
all null values  
all arrays  
all objects  

Normalization must be deterministic.

9. Canonical IR validity

Canonical IR is valid if and only if:

1. All required sections are present.  
2. All sections are sorted.  
3. All object keys are sorted.  
4. All expressions are explicit.  
5. All functions are explicit.  
6. All rules are explicit.  
7. No nondeterministic constructs exist.  
8. All references are valid.  
9. All types, fields, and functions exist.  
10. The IR serializes deterministically.

Invalid Canonical IR must cause manifest rejection.

10. Canonical IR lifecycle

1. Manifest provided by user.  
2. Manifest converted to Canonical IR.  
3. Canonical IR validated.  
4. Engine enters deterministic execution.  
5. Canonical IR remains active until manifest replacement.  
6. Canonical IR is never mutated.  
7. Canonical IR is replaced atomically.

Canonical IR is the single source of truth for execution.

SPEC 055 Where Clause Model

The where clause model defines how GRISP filters structural matches using deterministic boolean expressions. The where clause is the second stage of match evaluation, after structural pattern binding and before let binding evaluation. Where clauses must be deterministic. Where clauses must serialize deterministically. Where clauses must not introduce nondeterministic behavior.

Purpose of the where clause model:

1. Filter structural matches using deterministic logic.  
2. Enforce semantic constraints beyond structural pattern matching.  
3. Ensure reproducible match filtering across all engines.  
4. Provide a deterministic foundation for let bindings, priority, and actions.  
5. Introduce additional dependencies for validation.

Where clause properties:

1. Must be a deterministic boolean expression.  
2. Must evaluate to true or false.  
3. Must not mutate state.  
4. Must not allocate identifiers.  
5. Must not reference objects created in the same commit.  
6. Must not reference runtime metadata.  
7. Must serialize as an explicit expression tree.

Where clause evaluation:

Where clauses may reference:

pattern variables  
field values  
pure functions  
effect_deterministic functions  
let variables declared earlier (not allowed; let comes after where)  
deterministic expressions  

Where clauses must not reference:

let variables  
actions  
events  
version counters  
sequence counters  
tick counters  
system time  
random numbers  

Where clause evaluation must be deterministic across all engines.

Where clause dependencies:

Where clauses introduce dependencies based on:

field reads  
function declared_reads  
adjacency reads  
existence reads  
extent reads  

Dependencies must be extracted deterministically.  
Dependencies must be sorted lexicographically.  
Dependencies must be validated during match validation.

Where clause determinism:

Where clauses must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
floating point nondeterminism  
runtime metadata  

Where clauses must produce identical results across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Where clause validity:

A where clause is valid if and only if:

1. It is a deterministic boolean expression.  
2. All referenced variables are declared.  
3. All referenced fields exist.  
4. All referenced functions exist.  
5. All declared_reads are valid.  
6. No nondeterministic constructs are used.  
7. No state mutation occurs.  
8. No identifier allocation occurs.  
9. The expression serializes deterministically.  
10. No references target objects created in the same commit.  
11. No references target deleted objects.

Invalid where clauses must cause manifest rejection.

Where clause failure:

If a where clause evaluates to false:

the match is discarded  
no let bindings are evaluated  
no priority is computed  
no dependencies beyond structural ones are used  

Where clause lifecycle:

1. Declared in rule.  
2. Serialized into Canonical IR.  
3. Evaluated after structural pattern binding.  
4. Introduces dependencies.  
5. Determines whether match proceeds to let evaluation.  
6. Recomputed every tick.  
7. Persists until manifest replacement.

End of SPEC 055.


SPEC 056 Let Binding Model

The let binding model defines how GRISP computes deterministic intermediate values during match evaluation. Let bindings allow rules to derive additional values from pattern variables, field values, and function calls. Let bindings must be deterministic. Let bindings must serialize deterministically. Let bindings must not introduce nondeterministic behavior.

Purpose of the let binding model:

1. Provide deterministic intermediate computation.  
2. Allow complex expressions to be factored out of actions and priority.  
3. Support deterministic reuse of computed values.  
4. Introduce additional dependencies for validation.  
5. Ensure reproducible match evaluation across all engines.

Let binding properties:

1. Must be deterministic.  
2. Must evaluate after the where clause.  
3. Must evaluate before priority.  
4. Must evaluate before actions.  
5. Must not mutate state.  
6. Must not allocate identifiers.  
7. Must serialize as explicit expression trees.  
8. Must be evaluated in lexicographic order by variable name.

Let binding structure:

Each let binding consists of:

variable_name  
expression  

Variable names must be unique within the rule.  
Variable names must be sorted lexicographically in Canonical IR.

Let binding evaluation:

Let bindings may reference:

pattern variables  
earlier let variables  
pure functions  
effect_deterministic functions  
deterministic expressions  

Let bindings must not reference:

later let variables  
actions  
events  
version counters  
sequence counters  
tick counters  
system time  
random numbers  

Let binding evaluation must be deterministic across all engines.

Let binding dependencies:

Let bindings introduce dependencies based on:

field reads  
function declared_reads  
adjacency reads  
existence reads  
extent reads  

Dependencies must be extracted deterministically.  
Dependencies must be sorted lexicographically.  
Dependencies must be validated during match validation.

Let binding determinism:

Let bindings must not depend on:

hash map iteration order  
pointer addresses  
thread scheduling  
locale  
floating point nondeterminism  
runtime metadata  

Let bindings must produce identical results across:

all conformant engines  
all platforms  
all CPU architectures  
all memory layouts  
all execution schedules  

Let binding validity:

A let binding is valid if and only if:

1. It is deterministic.  
2. All referenced variables are declared.  
3. All referenced fields exist.  
4. All referenced functions exist.  
5. All declared_reads are valid.  
6. declared_reads is complete.  
7. No nondeterministic constructs are used.  
8. No state mutation occurs.  
9. No identifier allocation occurs.  
10. The expression serializes deterministically.  
11. No references target objects created in the same commit.  
12. No references target deleted objects.

Invalid let bindings must cause manifest rejection.

Let binding ordering:

Let bindings must be evaluated in lexicographic order by variable name.  
Ordering must be deterministic.  
Ordering must not depend on manifest formatting.

Let binding failure:

If a let binding evaluation fails:

the match is discarded  
no priority is computed  
no actions are executed  
no events are emitted  

Let binding lifecycle:

1. Declared in rule.  
2. Serialized into Canonical IR.  
3. Evaluated after the where clause.  
4. Introduces dependencies.  
5. Provides intermediate values for priority, actions, and events.  
6. Recomputed every tick.  
7. Persists until manifest replacement.

End of SPEC 056.
