UNIFIED SYSTEM SPECIFICATION
VERSION 3.1 – NORMATIVE INVARIANTS & COMPLETE CLOSURE
(Marker-Based Tool Manifests)
================================================================================

This specification defines a complete, layered architecture for AI‑assisted
software engineering, autonomous agents, and deterministic execution systems.
It supersedes all previous drafts. Version 3.1 adds a formal chapter of
Normative Invariants, establishing the absolute laws that the system must
uphold at runtime, thereby closing the final gap between design and
implementation.

The architecture separates seven concerns:

  1. Intent (what to achieve) – SIR
  2. Planning (how to achieve it) – Planner (heuristic, produces multiple candidates)
  3. Evaluation (choosing the best plan) – Evaluator (cost/risk/confidence ranking)
  4. Validation (deterministic checks + normalization) – Validator
  5. Execution (deterministic steps) – EIR + GRISP
  6. Persistence (file system, state) – LSBP
  7. Tools (external capabilities) – Tool Manifest Specification (marker‑based)

All components are designed for LLM friendliness, deterministic translation
wherever possible, and explicit interfaces.

================================================================================
PART I – OVERVIEW AND CORE PRINCIPLES
================================================================================

1. PURPOSE

This unified system provides a complete stack for:
- Expressing high-level goals, assumptions, and constraints (SIR)
- Automatically generating candidate executable plans from intent (Planner)
- Evaluating and ranking plans (Evaluator)
- Validating plans deterministically (Validator)
- Executing plans deterministically on a typed property graph (GRISP)
- Managing file system state with integrity and atomicity (LSBP)
- Interacting with external tools via schematised manifests (Tool Manifest Spec)

The stack is designed for:
- AI agents that need to reason, plan, and act
- Human‑AI collaborative software development
- Autonomous system control and monitoring
- Reproducible, verifiable state transitions

2. CORE PRINCIPLES

2.1 Separation of Intent from Execution
Intent (what) is expressed in SIR. Execution (how) is expressed in EIR.
The Planner + Evaluator + Validator chain explicitly transforms one into the other.

2.2 Heuristic Planning, Deterministic Validation and Execution
The Planner is intentionally non‑deterministic – different planners may produce
different candidate sets. The Evaluator uses fixed metrics to select the best
candidate. The Validator performs purely deterministic checks. GRISP executes
with full determinism.

2.3 Marker‑Based Structure
All language constructs use explicit ⟦BEGIN ...⟧ / ⟦END ...⟧ markers.
No symbols, no operator precedence, no implicit rules. This applies to
SIR, EIR, Tool Manifests, and LSBP documents.

2.4 Domain Independence
No domain‑specific constructs exist in the language. All domains are
represented as data or tool invocations.

2.5 Atomicity
All state changes (graph mutations and file system updates) are applied
atomically. Partial updates are never observable.

2.6 LLM Friendliness
The syntax is minimal, explicit, and free of punctuation noise. LLMs can
generate, repair, and extend it reliably.

2.7 Versioned State
All persistent state (WorldState, LSBP bundles, GRISP counters) is versioned
to enable reproducibility, replay, and audit.

2.8 Explicit Tool Contracts
Every external tool must expose a deterministic marker‑based manifest that
describes its capabilities, arguments, side effects, costs, and
preconditions/postconditions.

2.9 Explicit Semantic Grounding
The Planner must not guess the meaning of natural language terms. SIR now
includes a SEMANTIC MAP block that explicitly binds natural language phrases
to WorldState identifiers, Tool Manifest actions, and graph node types.
This transforms the Planner from a heuristic interpreter into a deterministic
linker.

2.10 Adaptive Costing
Tool costs are no longer static integers. Manifests support dynamic cost
expressions over WorldState variables (e.g., base + (record_count * 0.1)).
The Evaluator computes these costs against the current state at planning time,
ensuring accurate primary ranking.

2.11 Planner Shorthand & Normalization
To reduce LLM token expenditure, the Planner may emit a Compact EIR (CEIR)
using short macro-like markers (e.g., ⟦SET x = 5⟧). The Validator includes
a Normalizer that expands CEIR into the full 32‑block canonical EIR before
GRISP translation, ensuring the execution engine remains untouched.

2.12 Graceful Degradation
EIR now includes ON FAILURE blocks, allowing plans to define fallback
actions if a tool precondition fails mid‑execution, rather than halting
the entire pipeline.

PART II – SIR (SEMANTIC INTENT REPRESENTATION) SPECIFICATION
================================================================================

4. PURPOSE

SIR captures high‑level intent. It does not describe how to achieve anything;
it only states what is desired, believed, assumed, or known. SIR is stable
and changes only when the ontology of intent changes.

5. SIR STRUCTURAL MARKERS

All SIR blocks use the format:
  ⟦BEGIN <block>⟧
    ... content ...
  ⟦END <block>⟧

Block names are case‑sensitive and must consist of ASCII letters, digits,
and spaces (spaces are allowed inside block names for readability, but are
normalised to underscores internally). The normative canonical form replaces
spaces with underscores, but both forms are accepted.

5.1 Program Structure (5 blocks)
⟦BEGIN PROGRAM⟧ / ⟦END PROGRAM⟧
⟦BEGIN MODULE⟧ / ⟦END MODULE⟧
⟦BEGIN IMPORT⟧ / ⟦END IMPORT⟧
⟦BEGIN METADATA⟧ / ⟦END METADATA⟧
⟦BEGIN COMMENT⟧ / ⟦END COMMENT⟧

5.2 Intent Markers (18 blocks – includes SEMANTIC MAP)
⟦BEGIN GOAL⟧ / ⟦END GOAL⟧
⟦BEGIN SUBGOAL⟧ / ⟦END SUBGOAL⟧
⟦BEGIN QUESTION⟧ / ⟦END QUESTION⟧
⟦BEGIN OBSERVATION⟧ / ⟦END OBSERVATION⟧
⟦BEGIN FACT⟧ / ⟦END FACT⟧
⟦BEGIN ASSUMPTION⟧ / ⟦END ASSUMPTION⟧
⟦BEGIN CONSTRAINT⟧ / ⟦END CONSTRAINT⟧
⟦BEGIN HYPOTHESIS⟧ / ⟦END HYPOTHESIS⟧
⟦BEGIN EVIDENCE⟧ / ⟦END EVIDENCE⟧
⟦BEGIN COUNTER EVIDENCE⟧ / ⟦END COUNTER EVIDENCE⟧
⟦BEGIN ALTERNATIVE⟧ / ⟦END ALTERNATIVE⟧
⟦BEGIN RISK⟧ / ⟦END RISK⟧
⟦BEGIN CONFIDENCE⟧ / ⟦END CONFIDENCE⟧
⟦BEGIN DEPENDENCY⟧ / ⟦END DEPENDENCY⟧
⟦BEGIN UNKNOWN⟧ / ⟦END UNKNOWN⟧
⟦BEGIN POLICY⟧ / ⟦END POLICY⟧
⟦BEGIN INTENTION⟧ / ⟦END INTENTION⟧
⟦BEGIN SEMANTIC MAP⟧ / ⟦END SEMANTIC MAP⟧

Total: 5 + 18 = 23 blocks.

5.3 Semantic Map Structure (Normative)
The content of the SEMANTIC MAP block is structured. It consists of
⟦BEGIN MAPPING⟧ / ⟦END MAPPING⟧ pairs. Each mapping defines:
  • entity : Binds a natural language noun phrase to a WorldState variable.
  • action : Binds a natural language verb phrase to a Tool TARGET.ACTION.
  • constraint : Binds a natural language limit to a numeric WorldState field.

Format: ⟦BEGIN MAPPING⟧<type> = "<phrase>" : <identifier>⟦END MAPPING⟧

5.4 Content Rules for SIR
- Content inside GOAL, ASSUMPTION, etc. is free‑form natural language.
- The SEMANTIC MAP content is structured as defined above.
- Content must not contain structural markers (unless escaped).
- The Planner is responsible for interpreting the content.

5.5 SIR Example (with Semantic Map)

⟦BEGIN PROGRAM⟧
  ⟦BEGIN METADATA⟧
    author = "AI Architect"
    version = "2.0"
  ⟦END METADATA⟧

  ⟦BEGIN SEMANTIC MAP⟧
    ⟦BEGIN MAPPING⟧entity = "server room" : WorldState.zone_1_temp⟦END MAPPING⟧
    ⟦BEGIN MAPPING⟧action = "cool down" : CoolingSystem.set_speed⟦END MAPPING⟧
    ⟦BEGIN MAPPING⟧constraint = "max power" : 2000⟦END MAPPING⟧
  ⟦END SEMANTIC MAP⟧

  ⟦BEGIN GOAL⟧
    cool down the server room to 38 degrees within 5 minutes
  ⟦END GOAL⟧

  ⟦BEGIN CONSTRAINT⟧
    max power must not be exceeded
  ⟦END CONSTRAINT⟧
⟦END PROGRAM⟧

5.6 SIR Semantics
SIR blocks have no direct execution semantics. They are inputs to the Planner.
The Planner MUST ground every noun/verb in GOAL, CONSTRAINT, and ASSUMPTION
against the SEMANTIC MAP. If a term lacks a mapping, the Planner MUST fail
with error P004 – Unmapped Semantic Term.

================================================================================
PART III – PLANNER, EVALUATOR, VALIDATOR
================================================================================

6. PLANNER (Heuristic Candidate Generator)

The Planner is the strategic component that transforms SIR (intent) into
a set of candidate EIR plans. It is intentionally heuristic and non‑deterministic.

6.1 Planner Inputs (Normative)
The Planner receives exactly four inputs:
  1. A valid SIR document (parsed and semantically well‑formed)
  2. The current WorldState
  3. A set of Tool Manifests
  4. The current system configuration (resource limits)

6.2 Planner Grounding Rules (Normative)
The Planner MUST perform explicit grounding:
  a. Extract all entities from the SEMANTIC MAP.
  b. Replace every recognized term in GOALs and CONSTRAINTS with grounded identifiers.
  c. If any term is not found, fail with P004.
  d. Use grounded terms to instantiate VARIABLE and TOOL CALL blocks.

6.3 Planner Outputs (Normative)
The Planner produces a set of candidate plans. Each candidate consists of:
  a. An EIR document (MAY be in Compact EIR / CEIR shorthand).
  b. A Plan Manifest.

Plan Manifest schema:
⟦BEGIN PLAN MANIFEST⟧
  ⟦BEGIN PLAN ID⟧plan-001⟦END PLAN ID⟧
  ⟦BEGIN ESTIMATED TOOL CALLS⟧12⟦END ESTIMATED TOOL CALLS⟧
  ⟦BEGIN ESTIMATED RISK⟧low⟦END ESTIMATED RISK⟧
  ⟦BEGIN CONFIDENCE⟧0.87⟦END CONFIDENCE⟧
  ⟦BEGIN DEPENDENCIES⟧power_available⟦END DEPENDENCIES⟧
  ⟦BEGIN SELECTED TOOLS⟧CoolingSystem, Clock⟦END SELECTED TOOLS⟧
  ⟦BEGIN TIMESTAMP⟧2026-07-28T10:00:00Z⟦END TIMESTAMP⟧
⟦END PLAN MANIFEST⟧

6.4 Non‑Determinism (Normative)
Different Planner implementations may produce different candidate sets.
This is intentional. Only the Evaluator and Validator are required to be
deterministic.

7. EVALUATOR (Deterministic Ranker)

The Evaluator selects the best candidate plan from the set produced by the Planner.

7.1 Ranking Criteria (Normative, in priority order)
  1. Lowest dynamic cost (primary)
  2. Highest confidence (secondary)
  3. Lowest risk (tertiary)
Tie-breaker: lexicographically smaller plan_id.

7.2 Dynamic Cost Computation (Normative)
For each candidate:
  a. Extract every TOOL CALL.
  b. Look up the Tool Manifest's COST EXPRESSION.
  c. Substitute WorldState variable values from the current snapshot.
  d. Evaluate the arithmetic expression to an integer (milliseconds).
  e. Sum the costs across all calls.
If any COST EXPRESSION references a missing variable, reject with V014.

7.3 Determinism (Normative)
The Evaluator is deterministic. For a given candidate set and fixed WorldState,
the same plan is always selected.

8. VALIDATOR (Deterministic Checker + Normalizer)

The Validator performs purely deterministic checks. It includes a Normalizer
that expands CEIR into canonical EIR before validation.

8.0 Normalizer Phase (NEW)
The Normalizer:
  a. Parses all CEIR macro lines (⟦SET⟧, ⟦WHILE⟧, ⟦IF⟧, ⟦CALL⟧, ⟦TRANSITION⟧).
  b. Expands them into the full 32‑block canonical structure.
  c. If a CEIR macro is malformed, returns V013 – Compact Expansion Failed.

8.1 Validation Checks (Normative)
The Validator must perform the following checks in order:
  1. Syntax check (canonical EIR) – V001.
  2. Undefined variables – V002.
  3. Type mismatches – V003.
  4. Missing tool arguments – V004.
  5. Invalid state transitions – V005.
  6. Missing capabilities – V006.
  7. Dependency cycles – V007.
  8. Policy violations – V008.
  9. Resource limits – V009.
  10. Precondition verification – V010.
  11. Side‑effect consistency – V011.
  12. Invalid transition condition – V012.
  13. Dynamic Cost Verification (resolve COST EXPRESSION) – V014.
  14. Bundle Strategy Consistency – V015.

8.2 Validation Output (Normative)
If validation passes: outputs the canonical EIR document.
If validation fails: outputs a structured error object with code, message,
location, and context. The pipeline halts.

================================================================================
PART IV – EIR (EXECUTION INTERMEDIATE REPRESENTATION) SPECIFICATION
================================================================================

9. PURPOSE

EIR captures executable plans. It is generated by the Planner, evaluated,
validated, and then passed to GRISP. EIR is deterministic in structure
and translates directly to GRISP Canonical IR with no semantic ambiguity.
The Planner may emit Compact EIR (CEIR) which is expanded by the Validator.

10. EIR STRUCTURAL MARKERS

All EIR blocks use the format:
  ⟦BEGIN <block>⟧ ... ⟦END <block>⟧

10.1 Program Structure (5 blocks)
PROGRAM, MODULE, IMPORT, METADATA, COMMENT

10.2 Data Markers (6 blocks)
TYPE, VARIABLE, ASSIGNMENT, CONSTANT, LIST, MAP

10.3 Control Flow Markers (7 blocks)
CONDITION, LEFT OPERAND, COMPARISON TYPE, RIGHT OPERAND,
DECISION, ELSE, LOOP, FUNCTION, FUNCTION NAME, PARAMETERS, BODY, CALL

10.4 Tool and Effect Markers (10 blocks – added ON FAILURE)
TOOL CALL, TOOL TARGET, ACTION, ARGUMENTS,
RESULT, ERROR, ERROR CONDITION, ERROR ACTION,
RETRY, TIMEOUT, TRANSACTION, PARALLEL, ASYNCHRONOUS,
ON FAILURE, FAILURE CONDITION, FALLBACK

10.5 State Markers (4 blocks)
TRANSITION, FROM STATE, TO STATE, TRANSITION CONDITION

Total: 5 + 6 + 7 + 10 + 4 = 32 blocks.

10.6 Compact EIR (CEIR) Shorthand (Normative)
The Planner MAY emit the following compact markers. The Validator MUST expand them:

| Compact Marker | Expands To (Canonical) |
| :--- | :--- |
| ⟦SET x = expr⟧ | Full ASSIGNMENT block |
| ⟦IF cond THEN ... [ELSE ...]⟧ | Full DECISION / CONDITION / ELSE structure |
| ⟦WHILE cond DO ...⟧ | Full LOOP / CONDITION / STATEMENT structure |
| ⟦CALL tool.action(args)⟧ | Full TOOL CALL with TARGET, ACTION, ARGUMENTS |
| ⟦CALL ... INTO var⟧ | TOOL CALL followed by ASSIGNMENT of RESULT |
| ⟦TRANSITION from -> to IF cond⟧ | Full TRANSITION with FROM, TO, CONDITION |
| ⟦ON ERROR cond DO fallback⟧ | Full ON FAILURE block |

Rules: CEIR markers must be on a single line. The Normalizer preserves non‑CEIR blocks.

10.7 EIR Expression Language
Operators: +, -, *, /, //, %, ==, !=, <, <=, >, >=, &&, ||, !, ., [].
Literals: integers, fixed‑point, strings, booleans, identifiers.
Short‑circuit evaluation required for && and ||.

10.8 EIR Example (Mixed Compact and Canonical)

⟦BEGIN PROGRAM⟧
  ⟦BEGIN METADATA⟧plan_id = "plan-A"⟦END METADATA⟧

  ⟦SET current_temp = 0⟧
  ⟦SET fan_speed = 0⟧

  ⟦WHILE current_temp > 38 DO⟧
    ⟦CALL Hardware.read_sensor(sensor_id = "sensor_01") INTO current_temp⟧

    ⟦IF current_temp > 42 THEN⟧
      ⟦SET fan_speed = 100⟧
    ⟦ELSE IF current_temp > 40 THEN⟧
      ⟦SET fan_speed = 70⟧
    ⟦ELSE⟧
      ⟦SET fan_speed = 40⟧
    ⟦END IF⟧

    ⟦CALL CoolingSystem.set_speed(speed = fan_speed)⟧
    ⟦CALL Clock.sleep(duration = 30)⟧

    ⟦BEGIN ON FAILURE⟧
      ⟦BEGIN FAILURE CONDITION⟧TIMEOUT⟧END FAILURE CONDITION⟧
      ⟦BEGIN FALLBACK⟧
        ⟦CALL CoolingSystem.emergency_stop(force = true)⟧
      ⟦END FALLBACK⟧
    ⟦END ON FAILURE⟧
  ⟦END WHILE⟧
⟦END PROGRAM⟧

PART V – TOOL MANIFEST SPECIFICATION (MARKER‑BASED)
================================================================================

11. PURPOSE

Every external tool must expose a deterministic marker‑based manifest.
The Planner uses this manifest to reason about capabilities, arguments, costs,
side effects, retry policies, and bundling strategies.

12. ABSTRACT MANIFEST ELEMENTS (UPDATED)

- name: string (unique identifier)
- version: semantic version string
- description: string
- capabilities: set of strings
- actions: a set of action definitions

Each action definition contains:
  - action_name: string
  - arguments: set of argument schemas (name, type, required, min, max, default, description)
  - returns: return schema
  - side_effects: set of effect strings ("state_change", "network", "filesystem", "external_api", "none")
  - idempotent: boolean
  - cost_expression: string (arithmetic expression over WorldState variables) – NEW
  - timeout_ms: integer
  - retry_policy: max_attempts, delay_ms
  - permissions: set of strings
  - preconditions: set of strings (expressions over WorldState)
  - postconditions: set of strings (expressions over WorldState)
  - bundle_strategy: "immediate" | "lazy" | "never" – NEW

13. CONCRETE MARKER‑BASED SYNTAX (NORMATIVE)

13.1 Top‑Level Structure
⟦BEGIN TOOL MANIFEST⟧
  ⟦BEGIN NAME⟧CoolingSystem⟦END NAME⟧
  ⟦BEGIN VERSION⟧1.2.0⟦END VERSION⟧
  ⟦BEGIN DESCRIPTION⟧Controls industrial cooling fans⟦END DESCRIPTION⟧
  ⟦BEGIN CAPABILITIES⟧ ... ⟦END CAPABILITIES⟧
  ⟦BEGIN ACTIONS⟧ ... ⟦END ACTIONS⟧
⟦END TOOL MANIFEST⟧

13.2 Action Block Structure (UPDATED)
⟦BEGIN ACTION⟧
  ⟦BEGIN ACTION NAME⟧set_speed⟦END ACTION NAME⟧
  ⟦BEGIN ARGUMENTS⟧ ... ⟦END ARGUMENTS⟧
  ⟦BEGIN RETURNS⟧ ... ⟦END RETURNS⟧
  ⟦BEGIN SIDE EFFECTS⟧ ... ⟦END SIDE EFFECTS⟧
  ⟦BEGIN IDEMPOTENT⟧false⟦END IDEMPOTENT⟧
  ⟦BEGIN COST EXPRESSION⟧50 + (speed / 10)⟦END COST EXPRESSION⟧ (NEW)
  ⟦BEGIN TIMEOUT MS⟧1000⟦END TIMEOUT MS⟧
  ⟦BEGIN RETRY POLICY⟧ ... ⟦END RETRY POLICY⟧
  ⟦BEGIN PERMISSIONS⟧ ... ⟦END PERMISSIONS⟧
  ⟦BEGIN PRECONDITIONS⟧ ... ⟦END PRECONDITIONS⟧
  ⟦BEGIN POSTCONDITIONS⟧ ... ⟦END POSTCONDITIONS⟧
  ⟦BEGIN BUNDLE STRATEGY⟧lazy⟦END BUNDLE STRATEGY⟧ (NEW)
⟦END ACTION⟧

14. TOOL REGISTRY
The Planner must have access to a set of Tool Manifests, provided as input.

15. MANIFEST PARSING AND VALIDATION (UPDATED)
The Validator enforces all required fields, type correctness, range consistency,
and validity of COST EXPRESSION and BUNDLE STRATEGY.

PART VII – GRISP INTEGRATION AND MAPPING
================================================================================

21. GRISP OVERVIEW
GRISP is the deterministic execution engine (GRISP Deterministic Kernel v0.58).

22. EIR → GRISP MAPPING TABLE (NORMATIVE)
| EIR Construct               | GRISP Canonical IR                                   |
|-----------------------------|------------------------------------------------------|
| VARIABLE                    | GRISP Identifier                                     |
| ASSIGNMENT                  | UpdateField or CreateNode                            |
| CONDITION                   | Constraint expression (φ)                            |
| DECISION                    | Conditional rule: IF φ THEN A1 ELSE A2               |
| LOOP                        | Recursive rule with self‑call                        |
| FUNCTION                    | GRISP Rule with rule_id                              |
| CALL                        | Rule invocation                                      |
| TOOL CALL                   | CreateNode(type="ToolCall") + CreateEdge             |
| ON FAILURE                  | GRISP TryCatch wrapper                               |
| TRANSACTION                 | Atomic commit boundary                               |
| PARALLEL                    | Parallel action group                                |
| ASYNCHRONOUS                | Detached semantic                                    |
| TRANSITION                  | UpdateField on state variable                        |
| RETRY                       | Retry wrapper                                        |
| TIMEOUT                     | Timeout wrapper                                      |

23. GRISP → LSBP MAPPING (with bundle_strategy)
- immediate: Emit bundle immediately at write.
- lazy: Accumulate writes; emit single bundle at COMMIT.
- never: Do not emit LSBP bundle (graph only).

24. LSBP COMPLIANCE
All bundles comply with LSBP Specification v0.38 (canonical content, atomicity).

PART XI – NORMATIVE INVARIANTS (NEW – COMPLETE CLOSURE)
================================================================================

These invariants are absolute. They must hold at all times during the execution
of a conformant system. Violation of any invariant constitutes a fatal system
error (unless explicitly handled by an ON FAILURE block for runtime errors,
but the invariant itself remains the fundamental law). They serve as the
foundational correctness properties for the entire architecture.

29. INVARIANT I – VERSION IMMUTABILITY
Once a GRISP commit completes and the tick_counter increments, the associated
WorldState snapshot is immutable. No operation may mutate a past WorldState
version. Any attempt to do so MUST be rejected by the GRISP engine.

30. INVARIANT II – VARIABLE DECLARATION (Scope)
Every identifier referenced in an ASSIGNMENT, CONDITION, LOOP, or TOOL CALL
ARGUMENT MUST be declared in a VARIABLE block within the same scope (or
inherited from an outer scope). Undeclared variables are a fatal parse error
(V002) and cannot be recovered via ON FAILURE.

31. INVARIANT III – TOOL RESOLUTION UNIQUENESS
A TOOL CALL specifies a TARGET and an ACTION. This pair MUST resolve to
exactly ONE action definition across the entire set of loaded Tool Manifests.
If zero or more than one match is found, the Validator MUST reject the plan
with error V006 (Missing capability) or a new dedicated resolution error.

32. INVARIANT IV – DEPENDENCY ACYCLICITY
The graph of CALLs, TOOL CALLs, and TRANSITIONs MUST be acyclic. The Validator
detects cycles via DFS (error V007). The execution engine is not required to
handle cycles; if one slips past the Validator due to a bug, GRISP MUST abort
the transaction with a fatal error.

33. INVARIANT V – CEIR-CANONICAL BIJECTION (Normalization)
The Normalizer's expansion of Compact EIR (CEIR) into canonical EIR MUST be a
total, bijective (one-to-one) function for all syntactically valid CEIR
constructs. Two different CEIR documents MUST NEVER expand to the same
canonical EIR, and one CEIR MUST NEVER expand to two different canonical EIRs.
This ensures that CEIR is merely a shorthand, not a separate semantic layer.

34. INVARIANT VI – TRANSACTION ATOMICITY (All or Nothing)
Within a TRANSACTION block, either ALL operations (graph writes, LSBP bundle
emissions, tool calls marked as transactional) complete successfully, or NONE
of them are applied. Partial application is forbidden. GRISP MUST implement
this via a write-ahead log or shadow state that is only committed on success.

35. INVARIANT VII – CANONICAL SERIALIZATION (Byte-for-Byte)
The serialization of WorldState, LSBP bundles, and GRISP golden files MUST
be fully deterministic. For any given state, the serialized output MUST be
byte-for-byte identical across different runs, different machines, and
different implementations. This requires:
- Map keys sorted lexicographically.
- Floating-point representation fixed (e.g., decimal strings, not binary).
- No timestamps or UUIDs inside deterministic hashes (except in metadata
  which is excluded from the canonical hash domain).

36. INVARIANT VIII – PRECONDITION TRUTH AT EXECUTION
Immediately before a TOOL CALL is executed, the GRISP runtime MUST re-evaluate
the tool's PRECONDITIONS against the current WorldState snapshot. If any
precondition is false, the CALL MUST trigger the ON FAILURE handler if defined;
if no handler exists, the transaction MUST abort. The Validator's earlier check
(V010) is a static guarantee, but the runtime must defend against race
conditions.

37. INVARIANT IX – COST EXPRESSION TOTALITY
The COST EXPRESSION defined in a Tool Manifest MUST be a total function over
ALL possible WorldState snapshots. If evaluation results in a division by zero,
overflow, or a missing variable reference, the Validator MUST reject the plan
with V014. This ensures the Evaluator can never encounter a runtime cost
computation error during ranking.

38. INVARIANT X – BUNDLE STRATEGY CONSISTENCY
A TOOL CALL with SIDE EFFECTS containing "filesystem" MUST have a BUNDLE
STRATEGY defined. If the strategy is "lazy", all writes in the transaction
are collected into a single bundle. If "immediate", each write emits a
separate bundle. The GRISP engine MUST NOT mix strategies for the same
target path within a single transaction (this would cause write ordering
ambiguity).

39. INVARIANT XI – PLANNER GROUNDING COMPLETENESS
For a SIR document to be valid, the Planner MUST ground 100% of the noun
phrases appearing in GOAL, CONSTRAINT, and ASSUMPTION blocks that are
identifiable as entities. If the SEMANTIC MAP lacks a mapping, the Planner
MUST fail with error P004 before generating any candidates. This forces all
planning to occur against a fully resolved context.

40. INVARIANT XII – LSBP HASH VERIFICATION
Upon loading an LSBP bundle, the runtime MUST recompute its BundleID from
the canonical payload and compare it to the stored BundleID. If they mismatch,
the bundle MUST be rejected. This invariant is non-negotiable for security
and determinism.

APPENDIX C – DETERMINISM PROOFS (UPDATED)
================================================================================

C.1 Evaluator Determinism
Uses fixed total order (dynamic cost, confidence, risk, plan_id).
Cost expressions are pure functions over deterministic WorldState. Hence deterministic.

C.2 Validator Determinism (including Normalizer)
Normalizer is a pure syntactic expansion rule set. All validation checks are
pure functions over canonical EIR and WorldState. No external state. Hence deterministic.

C.3 Tool Manifest Parsing Determinism
Marker‑based syntax is line‑oriented with explicit BEGIN/END markers. Order
does not affect semantics. Hence deterministic.

C.4 EIR → GRISP Determinism
Mapping table (§22) is a total function. For any valid canonical EIR, the
GRISP IR is uniquely determined.

C.5 GRISP Determinism
Proven by GRISP Kernel v0.58. ORDER_CANONICAL ensures transition relation is a function.

C.6 LSBP Determinism (with bundle_strategy)
For "lazy", accumulation order is execution order (fixed by GRISP). For "immediate",
each bundle is emitted at a fixed tick/index. Hash computation is deterministic.

C.7 Overall Pipeline Determinism
Given the same Planner implementation, SIR (with Semantic Map), WorldState, and
Tool Manifests, the entire pipeline produces a unique observable outcome.
The CEIR expansion is bijective (Invariant V), ensuring this holds.
