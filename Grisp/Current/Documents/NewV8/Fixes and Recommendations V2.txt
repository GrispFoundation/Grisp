Fixes/Recommendation by AI2:

The current specification for the GRISP Deterministic Kernel contains critical ambiguities that allow for divergent implementations. To transform this from a draft into a robust, cross-engine standard, you must move from "implementation-defined" logic to "normative constraints."

Below are the architectural overhauls required to seal the determinism leaks identified in the consensus report.

### 1. Eliminating Determinism Breakers

These changes are mandatory to ensure that identical input always produces identical output.

* **Mandatory M_prev Lifecycle:**
* **The Problem:** Allowing implementations to choose between keeping or clearing `M_prev` after `NO_MATCH` creates divergent scoring histories.
* **The Fix:** Redefine the `NO_MATCH` rule. `M_prev` must be cleared at the end of every tick where no commit occurs. This ensures that every tick begins with a pristine candidate history, preventing the "memory" of previous ticks from affecting future scheduling decisions.


* **Forced Constraint Validation:**
* **The Problem:** The specification currently marks constraint re-evaluation as "optional" during commit.
* **The Fix:** Remove the "optional" qualifier. Constraint re-evaluation must be a mandatory, atomic step in the `COMMIT` phase. If a constraint is violated, the transition must fail and trigger an `INVARIANT_VIOLATION` error. This guarantees that no engine commits an invalid state.


* **Bounded Retry Loops:**
* **The Problem:** There is no hard limit on `SELECT` retries when validation fails, creating a risk of infinite livelock.
* **The Fix:** Introduce `MAX_RETRIES` per tick, defined as `|M_initial|` (the count of candidate matches discovered at the start of the tick). Once `Rejected.size() == |M_initial|`, the tick must terminate with a `NO_MATCH` or a failure code. This guarantees termination.



### 2. Architectural Overhauls

To support scaling and cross-engine interoperability, the state model requires formalization.

* **Explicit Identifier Allocation:**
* **The Problem:** The specification lacks a canonical rule for how sequence counters (the numeric part of an ID) are generated.
* **The Fix:** Add an `id_generator_state` object to the core configuration `<G, C, M_prev, ID_State>`. The `ID_State` must contain a monotonic counter for every node and edge type. `CreateNode(type)` must increment the specific counter for that `type` and use the resulting integer for the ID.


* **Schema Definition Language (SDL):**
* **The Problem:** The "No Nulls" requirement forces mandatory fields, but there is no mechanism to handle schema evolution or default values.
* **The Fix:** Introduce a JSON-based schema object that is stored in the initial state. This schema must define mandatory fields, default values, and versioning for each node/edge type. When an engine encounters a node update, it validates against the schema version current at that `tick_counter`.



### 3. Numeric & Semantic Hardening

These fixes resolve the "math" inconsistencies.

* **Standardized Rounding & Saturation:**
* **The Problem:** Truncation toward zero and unconstrained saturation of scores can mask differences in priority.
* **The Fix:**
* **Rounding:** Mandate `Half-to-Even` (Banker's rounding) for all fixed-point operations to prevent cumulative bias in iterative calculations.
* **Saturation:** Score saturation must trigger a `SCORE_SATURATION_WARNING` in the trace if the `base_priority` is high enough to cause it. This allows for debugging while maintaining a fixed fallback order (lexicographic `match_key`).




* **Defining Resource Limits:**
* **The Problem:** `RESOURCE_LIMIT_EXCEEDED` is a listed error, but what constitutes a limit is implementation-defined, making it non-portable.
* **The Fix:** Define "Conformance Profiles" (e.g., Level 1: 100k nodes/tick, Level 2: 1M nodes/tick). Implementations must declare their profile in the golden file header. Any input triggering a limit above the declared profile triggers `RESOURCE_LIMIT_EXCEEDED`.

### 🔧 Design Improvements / Overhauls (Recommended)

#### A. Simplify versioning model
**Problem:** Too many overlapping counters (`predicate_version`, `field_version`, `extent_version`, `edge_predicate_version`). In a single‑threaded deterministic kernel, version validation is **never triggered** because the snapshot never changes within a tick.

**Improvement:** Either:
- **Remove version validation entirely** (declare it reserved for future concurrent extensions) – simplifies implementation drastically while preserving determinism.  
- Or **keep only `extent_version` and `adjacency_version`** as the minimal set to detect concurrent modifications in a hypothetical multi‑tick parallel system. Document that in the current spec, version checks always pass.

Given the consensus that versioning is over‑engineered, I recommend **removing all version counters and validation** from the kernel specification, and instead rely on the fact that the kernel is sequential. This would cut specification complexity by ~30% and eliminate a whole class of bugs. However, that is a major design change – if the goal is to keep the spec as a foundation for future concurrency, then keep it but fix the gaps.

#### B. `M_prev` fairness model – prevent unbounded growth and ghost dominance
**Problem:** `M_prev` stores ages for **all** discovered matches each tick, leading to unbounded memory and “ghost” matches that never disappear.

**Improvement – Change to last‑seen tick model:**
Instead of storing cumulative age, store `last_seen_tick` for each `match_key`. Then `age(m) = current_tick - last_seen_tick` (capped). The match set `M` from discovery gives the current matches; `M_prev` can be pruned to only those `match_key`s that have been seen in the last `N` ticks (e.g., N = 1000, configurable but deterministic). This bounds memory and avoids age saturation dominance.

**Improvement – Two options:**

2. **Keep conservative recording but document the livelock risk** and state that it is intentional to simplify the dependency model.

The table covers: <br>• `CreateNode` (extent_version, field_version for each created field, existence_version, sequence_counter) <br>• `CreateEdge` (edge_type_version, edge_predicate_version for each field, existence_version, adjacency_version for source.out and target.in, sequence_counter) <br>• `DeleteNode` (extent_version, field_version for each field, existence_version, adjacency_version for all incident edges) <br>• `DeleteEdge` (edge_type_version, adjacency_version for source.out and target.in, existence_version) <br>• `UpdateField` (field_version or predicate_version, existence_version unchanged) |
| **4‑B** | **Adjacency‑deduplication key** – the key used for deduplication is `(node_id, edge_type, direction)`. The spec’s text is updated everywhere to use this exact tuple. |
| **4‑C** | **Read‑trace completeness** – every action’s compilation rule now explicitly lists all reads that must be added to `R`. For example, `CreateEdge` adds `ExtentRead(edge_type)`, `NodeExistence(src)`, `NodeExistence(tgt)`, `AdjacencyRead(src, edge_type, out)`, `AdjacencyRead(tgt, edge_type, in)`, and `SequenceCounterRead(edge_type)`. |
| **4‑D** | **Validation rule extension** – COMMIT validation now checks **all** read‑trace entries, including `EdgeExistence`, `PredicateVersion`, and `AdjacencyVersion` for both directions. | With a single, unambiguous table and matching read‑trace, every engine will compute the same version snapshots and accept/reject the same matches. |

## 5️⃣ Schema language & golden‑file serialization  

| # | Change | Effect |
|---|--------|--------|
| **5‑A** | **Minimal JSON schema DSL** – introduce a `type_definitions` object in the IR that maps each `type_name` to a list of fields, each field having a name, a primitive type (`int`, `fixed`, `bool`, `string`, `identifier`), and a `mandatory` flag. Example: <br>`"type_definitions": {"Person": [{"name":"age","type":"int","mandatory":true}, {"name":"name","type":"string","mandatory":true}]}` |
| **5‑B** | **`type_definitions_hash`** – defined as the SHA‑256 hash of the canonical JSON representation of `type_definitions` (keys sorted, no whitespace). |
| **5‑C** | **Graph serialization** – `initial_state` and `final_state` are JSON objects with two top‑level arrays: `"nodes"` and `"edges"`. Each node/edge object contains: <br>• `"id"` (canonical identifier) <br>• `"type"` (type name) <br>• `"fields"` (object with keys sorted lexicographically) <br>All arrays are sorted by identifier using `ORDER_CANONICAL`. |
| **5‑D** | **Golden‑file format** – the top‑level JSON now includes `"ir_schema_version": "1.0"` and a `"state"` object that contains `"nodes"` and `"edges"` as described. The `"ticks"` array records each tick exactly as before, but `committed_changes` now stores actions in the same canonical JSON format. | Guarantees that two engines with identical internal state produce byte‑identical golden files. |

## 6️⃣ Numeric model & expression language fixes  

| # | Change | Detail |
|---|--------|--------|
| **6‑A** | **Scale‑overflow rule** – any operation that would produce a scale > 18 results in a fatal error `FIXED_POINT_SCALE_OVERFLOW`. |
| **6‑B** | **Fixed‑point serialization** – for `scale = 0` the string has **no decimal point** (e.g. `"42"`). For `scale > 0` the string contains exactly `scale` digits after the decimal point (e.g. `"12.5000"` for scale 4). |
| **6‑C** | **Complete operator set** – add `!=`, `<=`, `>=`, `||` to the constraint grammar, and a unary `!` for boolean negation. |
| **6‑D** | **List / map literals & indexing** – extend the expression grammar with `[e₁,…,eₙ]` and `{"k₁":e₁,…}` and with `e₁[e₂]` for list or map lookup (out‑of‑bounds ⇒ fatal). |
| **6‑E** | **Short‑circuit dependency rule** – keep the current “record both operands” policy (deterministic read‑trace) but add a note that it is intentional and that the extra reads are harmless because version validation will succeed only if the underlying data has not changed. |
| **6‑F** | **Integer division operator** – `/` on integers yields a `FixedPoint(0)` result (promotion rule) and truncates toward zero; `//` is defined as *floor division* for signed integers (result is integer). Both are fatal on division‑by‑zero. | Removes ambiguities and makes the arithmetic model fully specified. |

## 7️⃣ Resource limits, diagnostics & auxiliary formats  

| # | Change | Reason |
|---|--------|--------|
| **7‑A** | **Define `RESOURCE_LIMIT_EXCEEDED`** – a minimal set of limits that every engine must enforce: <br>• `MAX_NODES = 2³¹‑1` <br>• `MAX_EDGES = 2³¹‑1` <br>• `MAX_MATCHES_PER_TICK = 2⁶⁴‑1` <br>All limits are configurable, but the default values above are mandatory. |
| **7‑B** | **Canonical Action Trace (CAT) format** – JSON array of objects, each object containing `op`, `target`, and any additional fields (`type`, `src`, `tgt`, `field`, `value`). Example: `{"op":"CreateNode","target":"Person:7","type":"Person","fields":{"age":30,"name":"Alice"}}`. |
| **7‑C** | **Debug‑mode rejection log** – optional field `"rejected_matches"` in the tick record that lists `match_key` and a short reason (e.g., `"stale_read"`). This field is omitted in production golden files but may be emitted when a `debug` flag is set. |
| **7‑D** | **Garbage‑collection policy for `M_prev`** – after each tick, entries whose `match_key` has not appeared in the last `K = 2³²` ticks may be removed. The rule is deterministic because `K` is a constant. | Prevents unbounded memory growth while preserving fairness for recent matches. |

## 8️⃣ Summary of the patch order  

1. **Determinism‑breaker fixes** (1‑A, 1‑B, 1‑C).  
2. **Identifier & counter model** (2‑A–2‑D).  
3. **Pattern enumeration & match‑key** (3‑A–3‑D).  
4. **Version‑counter table & read‑trace** (4‑A–4‑D).  
5. **Schema & golden‑file serialization** (5‑A–5‑D).  
6. **Numeric & expression extensions** (6‑A–6‑F).  
7. **Resource limits, CAT format, diagnostics** (7‑A–7‑D).  

Implementing the changes in this order guarantees that the most fundamental determinism violations are eliminated before any higher‑level features are touched.
