## Preamble

This specification defines the GRISP Deterministic Kernel v0.60. It establishes a mathematically closed, unified standard that collapses the classic division between matching, dependency tracking, and action execution into a single, formally verifiable architecture: **Deterministic Structural Graph Rewrite Calculus with Trace-Indexed Read Semantics (DSGRC-TRS)**.

# ================================================================================
SPEC 000 — CORE SYSTEM ENTITIES & VALUE DOMAIN

1.1 Primitive Numeric Types
All numeric fields, parameters, calculations, and intermediate registers must use 64-bit signed fixed-point representations with a fixed scale of exactly 18 decimal places (referred to as `FixedPoint`).

* The minimal value is $-9,223,372,036,854,775,808 \times 10^{-18}$.
* The maximal value is $+9,223,372,036,854,775,807 \times 10^{-18}$.
* Floating-point arithmetic, rounding behaviors, or platform-specific BigInt variations are strictly prohibited. Intermediate math must utilize a checked 128-bit accumulator before saturating or throwing overflow errors.

1.2 The System Configuration Space ($\Sigma$)
The global engine state is defined as a 4-tuple:


$$\Sigma = \langle G, C, T, M_{\text{prev}} \rangle$$

* **The Typed Graph ($G$):** A finite map of canonical structural identifiers (`Id`) to primitive typed node states, fields, and lexicographically sorted adjacency listings.
* **The Counter Map ($C$):** A mapping containing all internal tracking sequences:
* `C.tick`: The global clock epoch index.
* `C.version[id]`: The structural mutation tracking counter for node/edge existence.
* `C.adjacency[id]`: The sequence tracking mutation changes to a node's topology.


* **The Epoch Index ($T$):** Current frame indicator ($T \in \mathbb{Z}_{\geq 0}$).
* **The Match Cache ($M_{\text{prev}}$):** A mapping tracking $(\text{match\_key} \to \text{age})$ to maintain temporal continuity across tick boundaries.

# ================================================================================
SPEC 001 — THE UNIFIED OPERATIONAL KERNEL (THE 5 CORE RULES)

The transition of the system state from one deterministic frame to the next occurs via five strictly unrolled structural operational rules.

```
+---------------------------------------------------------------+
|                      THE 5-RULE KERNEL LOOP                   |
+---------------------------------------------------------------+
|                                                               |
|  [Rule 1: TICK]     --> Advance global clock epoch            |
|          │                                                    |
|          ▼                                                    |
|  [Rule 2: DISCOVER] --> Compute current match sets functionally  |
|          │                                                    |
|          ▼                                                    |
|  [Rule 3: SELECT]   --> Choose single match via strict total order|
|          │                                                    |
|          ▼                                                    |
|  [Rule 4: PLAN]     --> Syntax-directed unrolling to Trace & Read |
|          │                                                    |
|          ▼                                                    |
|  [Rule 5: COMMIT]   --> Validate Read-shroud & apply mutations|
|                                                               |
+---------------------------------------------------------------+

```

## Rule 1: Chronological Advance (TICK)

Advances the clock epoch. If the tick counter increments beyond $\text{INT64\_MAX}$, the engine must halt immediately with a fatal `COUNTER_OVERFLOW` error.


$$\frac{
C.\text{tick} + 1 \leq \text{INT64\_MAX} \quad C' = C[\text{tick} \mapsto C.\text{tick} + 1]
}{
\langle G, C, T, M_{\text{prev}} \rangle \xrightarrow{\text{TICK}} \langle G, C', T+1, M_{\text{prev}} \rangle
}$$

## Rule 2: Non-Oracle Structural Pattern Matching (DISCOVER)

The extraction of structural matches is a pure functional mapping over the graph topology $G$, eliminating scheduling heuristics.


$$\frac{
\text{EvalPatterns}(G, \text{IR}) = \mathcal{M} \quad 
\mathcal{M}' = \{ (m, \text{age}) \mid m \in \mathcal{M}, \, \text{age} = \text{ComputeAge}(m, M_{\text{prev}}) \}
}{
\langle G, C, T, M_{\text{prev}} \rangle \xrightarrow{\text{DISCOVER}} \langle G, C, T, M_{\text{prev}}, \mathcal{M}' \rangle
}$$


Where:


$$\text{ComputeAge}(m, M_{\text{prev}}) = \begin{cases} 
M_{\text{prev}}[\text{match\_key}(m)] + 1 & \text{if } \text{match\_key}(m) \in \text{dom}(M_{\text{prev}}) \\ 
0 & \text{otherwise} \end{cases}$$

## Rule 3: Strategy-Normalized Canonical Selection (SELECT)

To resolve rule execution conflicts without introducing race conditions, candidate traces are projected onto a single scalar metric and filtered through an immutable lexicographical sort key.


$$\frac{
\mathcal{M}' \neq \emptyset \quad 
\forall (m, \text{age}) \in \mathcal{M}'. \, \text{score}(m) = \text{priority}_{\text{base}}(m) \cdot \text{scale}_{\text{prio}} + \text{age} \cdot \text{scale}_{\text{fair}} \\
m^* = \min_{\prec} \{ m \mid (m, \text{age}) \in \mathcal{M}' \}
}{
\langle G, C, T, M_{\text{prev}}, \mathcal{M}' \rangle \xrightarrow{\text{SELECT}} \langle G, C, T, M_{\text{prev}}, \mathcal{M}', m^* \rangle
}$$


Where the strict canonical order relation $m_1 \prec m_2$ holds if and only if:


$$(\text{score}(m_1) > \text{score}(m_2)) \lor (\text{score}(m_1) == \text{score}(m_2) \land \text{match\_key}(m_1) <_{\text{lex}} \text{match\_key}(m_2))$$

## Rule 4: Syntax-Directed Trace Compilation (PLAN)

Translates the structural IR, the selected match $m^*$, and the graph $G$ into a unified execution plan consisting of an operational trace ($\pi$) and an induced read obligation set ($\mathcal{R}$).


$$\frac{
\mathcal{E}_{m^*} \vdash \langle A_{\text{rule}}, G \rangle \Downarrow \langle \pi, \mathcal{R} \rangle
}{
\langle G, C, T, M_{\text{prev}}, \mathcal{M}', m^* \rangle \xrightarrow{\text{PLAN}} \langle G, C, T, M_{\text{prev}}, \mathcal{M}', m^*, \pi, \mathcal{R} \rangle
}$$

## Rule 5: Trace Verification and State Morphism (COMMIT)

Validates the read obligations, checks structural invariants post-mutation, updates global version states, and advances history.


$$\frac{
\forall r \in \mathcal{R}. \, \text{CheckVersion}(r, G, C) == \text{Valid} \quad 
G' = \text{ApplyTrace}(\pi, G) \quad 
C' = \text{UpdateCounters}(\pi, C) \\
\text{VerifyStructuralInvariants}(G') == \text{True} \quad 
M_{\text{prev}}' = \{ \text{match\_key}(m) \mapsto \text{age} \mid (m, \text{age}) \in \mathcal{M}' \}
}{
\langle G, C, T, M_{\text{prev}}, \mathcal{M}', m^*, \pi, \mathcal{R} \rangle \xrightarrow{\text{COMMIT}} \langle G', C', T, M_{\text{prev}}', \emptyset \rangle
}$$


If validation fails with a non-fatal error, $m^*$ is dropped, and the engine loops back to **Rule 3** with the remaining matches in $\mathcal{M}'$.

SPEC 002 — SYNTAX-DIRECTED LOWERING & READ PROJECTION

2.1 Environment Context-Freeness
The compiler derivation environment $\mathcal{E}$ is initialized exclusively from the immutable bindings of the selected match $m^*$. The syntax-directed translation is strictly context-free: $\mathcal{E}$ is structural-invariant and bounded solely by the pairing of $(m^*, G)$. Traversal history, execution side-effects, or engine-specific pointer addresses cannot influence the lowering tree.

2.2 Core Inductive Lowering Clauses

Clause 2.2a: Terminal Action Block Nullification
An empty action stream produces an empty execution trace and zero read dependencies.


$$\frac{}{ \mathcal{E} \vdash \langle \emptyset, G \rangle \Downarrow \langle [\,], \emptyset \rangle }$$

Clause 2.2b: Field Update Lowering
Translating a property change requires calculating expression evaluations via sub-term reduction ($\Downarrow_{\text{expr}}$), which appends read tokens directly to the dependency shroud.


$$\frac{
\mathcal{E} \vdash \langle e, G \rangle \Downarrow_{\text{expr}} \langle k, \mathcal{R}_e \rangle \quad 
x_{\iota} = \mathcal{E}(x) \quad 
\mathcal{E} \vdash \langle A_{\text{tail}}, G \rangle \Downarrow \langle \pi_{\text{tail}}, \mathcal{R}_{\text{tail}} \rangle
}{
\mathcal{E} \vdash \langle \text{UpdateField}(x, f, e) \cdot A_{\text{tail}}, G \rangle \Downarrow \langle [\text{UpdateField}(x_{\iota}, f, k)] \cdot \pi_{\text{tail}}, \, \mathcal{R}_e \cup \{\text{NodeExistence}(x_{\iota})\} \cup \mathcal{R}_{\text{tail}} \rangle
}$$

Clause 2.2c: Cascade Deletion Deconstruction
When a structural node is scheduled for removal, its structural incident connections must be systematically decoupled. To prevent non-deterministic pointer chasing during graph walking, the topological evaluation must collect incident edges and sort them using a total canonical lexicographical ordering key over their underlying identifiers (`ORDER_CANONICAL`).


$$\frac{
x_{\iota} = \mathcal{E}(x) \quad 
\vec{e}_{\text{incident}} = \text{GetIncidentEdgesSorted}(x_{\iota}, G) \quad 
\pi_{\text{edges}} = [ \text{DeleteEdge}(\epsilon) \mid \epsilon \in \vec{e}_{\text{incident}} ] \\
\mathcal{R}_{\text{edges}} = \{ \text{Adjacency}(x_{\iota}, \epsilon) \cup \text{EdgeExistence}(\epsilon) \mid \epsilon \in \vec{e}_{\text{incident}} \} \quad 
\mathcal{E} \vdash \langle A_{\text{tail}}, G \rangle \Downarrow \langle \pi_{\text{tail}}, \mathcal{R}_{\text{tail}} \rangle
}{
\mathcal{E} \vdash \langle \text{DeleteNode}(x) \cdot A_{\text{tail}}, G \rangle \Downarrow \langle \pi_{\text{edges}} \cdot [\text{DeleteNode}(x_{\iota})] \cdot \pi_{\text{tail}}, \, \mathcal{R}_{\text{edges}} \cup \{\text{NodeExistence}(x_{\iota})\} \cup \mathcal{R}_{\text{tail}} \rangle
}$$

SPEC 003 — TRANSACTIONS & SHROUD VALIDATION MECHANICS

3.1 CheckVersion Primitives
During the application of **Rule 5**, every element $r \in \mathcal{R}$ must be evaluated against the active graph snapshot and the global counter tracking architecture. A read obligation is marked `Valid` if and only if:

* For `NodeExistence(id)` / `EdgeExistence(id)`: The corresponding entity exists in $G$ and its tracking sequence in $C.\text{version}[id]$ matches the initial state observed at the start of the current tick.
* For `Adjacency(id, edge_id)`: The topological connection remains unaltered, and $C.\text{adjacency}[id]$ has sustained no mid-tick revisions.
* For `Field(id, f)`: The value of field $f$ on entity $id$ matches the state from which the trace was generated.

3.2 Unified Counter Advancements
Upon validation success, counter updates must occur in a single atomic phase:

* Any `UpdateField` call increments $C.\text{version}[id]$ by exactly 1.
* Any implicit or explicit `DeleteEdge` call increments $C.\text{adjacency}[src\_id]$ and $C.\text{adjacency}[tgt\_id]$ by exactly 1.

# ================================================================================
SPEC 004 — CANONICAL SERIALIZATION BOUNDARIES

To enforce strict, hardware-independent cross-engine communication and state validation, state snapshots must utilize a deterministic text-based format adhering to the following strict layout constraints:

1. **Map Key Ordering:** All dictionary, collection, field, and attribute mappings must be serialized strictly in UTF-8 lexicographical key order.
2. **Numeric String Isolation:** To prevent type blurring or float coercion by external consuming systems, all `FixedPoint` numbers must be serialized as JSON string types containing exactly 18 decimal places (e.g., `"125.500000000000000000"`). Integer keys or tracking counters must be written as raw JSON numbers to maintain explicit type separation.
3. **Whitespace Elimination:** To ensure byte-perfect hashing across discrete networks and architectures, all line endings, indentation spaces, trailing spaces, or carriage returns inside the canonical stream must be omitted.

# ================================================================================
SPEC 005 — UNIFIED GRADED ERROR TAXONOMY

The kernel segregates exceptional behaviors into two strict architectural categories. Hybrid execution paths or non-normative error handling strategies are prohibited.

1. **NON-FATAL (Transactional Failures):**
* `TRANSACTION_STALE`: A counter inside the read-shroud changed mid-tick.
* `CONSTRAINT_VIOLATION`: Staged mutations violate a rule guard or model safety parameter.
* `DUPLICATE_FIELD_UPDATE`: Multiple instructions inside the linear trace $\pi$ attempt to modify the identical `(id, field)` target.
* *System Action:* Discard the candidate trace $\pi$, completely roll back any staged field shifts, drop $m^*$, and return execution to **Rule 3**.


2. **FATAL (Engine Panic States):**
* `COUNTER_OVERFLOW`: A version or global tick index surpasses the signed 64-bit bounds.
* `DIVISION_BY_ZERO`: An arithmetic compilation block attempts a invalid division path.
* `RESOURCE_LIMIT_EXCEEDED`: Active mutations break physical processing thresholds or max graph node bounds allocated to the execution tick.
* *System Action:* Immediately halt all processing pipelines, wipe out transactional caches, discard the current state modifications, and serialize a standard panic snapshot containing the active error tracking record.

1. **Frozen Discovery** – Match discovery occurs exactly once per tick. The snapshot is immutable.

**SPEC 000 – EXECUTION PHASES (New Unified Model)**

Each tick consists of five phases:

- **Phase D: Discovery** – Produce frozen match snapshot + initial dependency snapshot (expression reads).
- **Phase S: Selection** – Rank matches by score (base_priority * priority_scale + age * fairness_scale), descending score then ascending match_key.
- **Phase P: Planning** – For the selected match, compile to Canonical Action Trace (CAT) + augment dependencies.
- **Phase V: Validation** – Re-validate dependencies + transaction validity.
- **Phase C: Commit** – Atomic application or rollback + counter advancement + events + match history update.

If any phase fails non-fatally, discard the candidate and try the next (Phase S). Fatal errors halt with rollback to pre-tick state.

**Normative properties of Planning:**
- All implicit DeleteEdge expansions for DeleteNode occur here, using the precise algorithm from v0.49 SPEC 013 (incident edges from pre-commit state + staged creations, earliest index, sorted by (k, edge_id) via ORDER_CANONICAL, deduplication).

# GRISP DETERMINISTIC KERNEL SPECIFICATION v1.0

*Based on the structural operational semantics (SOS) kernel that resolves the v0.49/v0.50 debate.*

## 0. Core Principles

The GRISP kernel defines a **deterministic graph‑rewrite calculus** with syntax‑directed compilation, trace‑indexed read semantics, and atomic state transitions.

**Observable behavior** – committed state changes, emitted events, and golden file output – is identical for identical IR and initial state across all conformant engines.

The kernel is governed by these invariants:

1. **Single semantic object** – state is a tuple `⟨G, C, T, M_prev⟩` with no hidden runtime artifacts.
2. **Deterministic by construction** – all choice points eliminated via total orders and structural recursion.
3. **Read effects as derivation** – dependencies are induced by syntax‑directed translation, not tracked by separate system.
4. **CAG as trace** – the execution trace (Canonical Action Graph) is a projection of the compilation derivation.
5. **Atomic commit** – validation + application + counter update form a single, rollback‑able step.

## 1. Syntax of Canonical IR

The IR is inductively defined. Let `X` be variable names, `F` field names, `K` constants (integers, fixed‑point literals, booleans, strings, identifiers).

### 1.1 Expressions

```
e ::= k | x | x.f | e1 ⊕ e2 | len(e) | to_fixed(e, scale) | to_integer(e)
⊕ ::= + | - | * | / | // | % | < | <= | > | >= | == | != | && | ||
```

- `k` – literal (Integer, FixedPoint(s), Boolean, String, Identifier)
- `x` – variable reference (pattern binding or let)
- `x.f` – field access of a node/edge variable
- `len(e)` – list length
- `to_fixed(e, scale)` – conversion to fixed‑point with given scale (0–18)
- `to_integer(e)` – truncation to integer

### 1.2 Patterns

A pattern is a set of element bindings with deterministic enumeration order.

```
P ::= ∅ | MatchNode(x, type_name) · P | MatchEdge(x, type_name, src, tgt) · P
```

- `MatchNode(x, T)` binds variable `x` to each node of type `T`, enumerated in ascending identifier order (SPEC 3).
- `MatchEdge(x, T, s, t)` binds `x` to each edge of type `T` with source `s` and target `t`, enumerated by ascending edge identifier.

### 1.3 Constraints (where clause)

```
φ ::= True | e1 == e2 | e1 < e2 | φ1 && φ2 | (φ)
```

Constraints are evaluated in the order they appear, with short‑circuit semantics.

### 1.4 Let Bindings

```
B ::= ∅ | Let(x, e) · B
```

Each `Let` evaluates `e` during discovery, stores the value in variable `x`, and does **not** affect match identity or match key.

### 1.5 Actions

```
a ::= CreateNode(x, type_name, {f1: e1, ...})
    | CreateEdge(x, type_name, src, tgt, {f1: e1, ...})
    | UpdateField(target, field, e)
    | DeleteEdge(e)
    | DeleteNode(x)
    | EmitEvent(event_type, [e1, ...])
```

Actions are executed in the order given, **after** canonical expansion (implicit `DeleteEdge` insertion).

### 1.6 Rule Definition

```
Rule ::= Rule(rule_id, base_priority, priority_scale, fairness_scale, P, φ, B, A)
```

- `rule_id` – string matching `[A-Za-z_][A-Za-z0-9_-]*`
- `base_priority`, `priority_scale`, `fairness_scale` – non‑negative integers
- `P` – pattern (ordered list of bindings)
- `φ` – constraint (where clause)
- `B` – let bindings
- `A` – action block (sequence)

## 2. State Model

State `Σ = ⟨G, C, T, M_prev⟩` consists of:

- **G** – graph of nodes and edges, each with fields (no nulls, all fields mandatory).
- **C** – counters:
  - `tick_counter` (starts 0)
  - Sequence counters per node/edge type (starting from 0 or max+1 from initial state)
  - Version counters: `extent_version[type]`, `predicate_version[type][field]`, `ordering_dependency_version[type][field]`, `edge_type_version[type]`, `edge_predicate_version[type][field]`, `edge_ordering_dependency_version[type][field]`, `adjacency_version[node][type][dir]`, `existence_version[node/edge]`, `field_version[element][field]`
  - All version counters start at 1 for existing elements.
- **T** – current tick number (integer).
- **M_prev** – previous match set: a map from `match_key` to `age` (integer). Initialized empty.

**Invariants** (checked after each commit):
- No dangling edges (source/target exist)
- No dangling identifier references (recursively through lists/maps)
- All constraints satisfied
- No cycles in identifier references (checked via visited set)

## 3. Operational Semantics (SOS)

The kernel executes as a sequence of small‑step transitions:

```
⟨Σ, IR⟩ → ⟨Σ', IR⟩
```

### Rule 1: TICK

```
tick_counter < INT64_MAX
─────────────────────────────────────
⟨⟨G, C, T, M_prev⟩, IR⟩ → ⟨⟨G, C[tick_counter := C.tick_counter + 1], T+1, M_prev⟩, IR⟩
```

If overflow → fatal `COUNTER_OVERFLOW` (no transition).

### Rule 2: DISCOVER

Let `EvalPatterns(G, IR)` be the set of all matches obtained by:
- Enumerating pattern bindings in ascending identifier order (type_name lexicographic, then sequence number)
- Evaluating constraints (in order) and let bindings (in order) over the current graph `G`
- Each match `m` contains: `match_key`, `bindings` (identifier bindings only), `let_values` (for diagnostics), and a **read trace** `ℛ_m` of all graph elements accessed during pattern evaluation (node existence, field reads, adjacency traversals, extents, edge types).

**Age assignment:**
```
age(m) = if match_key(m) ∈ M_prev then M_prev[match_key(m)] + 1 else 0
```
Overflow (age > INT64_MAX) → fatal `COUNTER_OVERFLOW`.

The configuration becomes `⟨⟨G, C, T, M_prev, M⟩, IR⟩` where `M` is the set of discovered matches with ages.

### Rule 3: SELECT

For each match `m ∈ M`, compute:

```
score(m) = base_priority(m) × priority_scale(m) + age(m) × fairness_scale(m)
```

All arithmetic is checked (overflow → fatal `INTEGER_OVERFLOW`).

Total order:
1. Higher score first
2. If tie, lexicographically smaller `match_key` (canonical JSON serialization)

Let `m*` be the first match in this order (if `M` non‑empty).  
If `M` empty → tick ends with no commit (state unchanged).

Transition: `⟨Σ, IR, M⟩ → ⟨Σ, IR, M, m*⟩`

### Rule 4: PLAN (Syntax‑Directed Compilation)

The function `Compile(IR, G, m*)` is defined by **structural recursion** over the rule’s components. It produces a **Canonical Action Graph** as a sequence of primitive steps `α̂` and an associated **read set** `ℛ`.

#### Inductive definition (excerpt):

**Empty action block:**
```
Compile(∅, G, m*) = ( [], ∅ )
```

**UpdateField:**
```
Compile(UpdateField(x, f, e) · A, G, m*) =
  let (v, ℛ_e) = eval(e, G, m*)   // eval returns value + read set from sub‑expression
  let x_id = lookup(x, m*)
  let (α̂_tail, ℛ_tail) = Compile(A, G, m*)
  in ( [UpdateField(x_id, f, v)] · α̂_tail , ℛ_e ∪ {NodeExistence(x_id), FieldRead(x_id,f)} ∪ ℛ_tail )
```

**DeleteNode (with implicit edge deletion):**
```
Compile(DeleteNode(x) · A, G, m*) =
  let x_id = lookup(x, m*)
  let edges = GetIncidentEdgesSorted(x_id, G)   // sorted by edge identifier ascending
  let α̂_edges = map(DeleteEdge, edges)
  let ℛ_edges = ⋃_{e∈edges} { Adjacency(x_id, e), EdgeExistence(e) }
  let (α̂_tail, ℛ_tail) = Compile(A, G, m*)
  in ( α̂_edges · [DeleteNode(x_id)] · α̂_tail , ℛ_edges ∪ {NodeExistence(x_id)} ∪ ℛ_tail )
```

**CreateNode, CreateEdge, EmitEvent** – similar structural rules, each recording appropriate reads (e.g., source/target existence for edge creation).

**Note:** `GetIncidentEdgesSorted` returns a deterministic list using `ORDER_CANONICAL` on edge identifiers, and includes all edges present in `G` (pre‑commit state) plus any edges created earlier in the same action block (by tracking temporary handles). This ensures total order.

The result of `Compile` is `(α̂, ℛ)`.

Transition: `⟨Σ, IR, M, m*⟩ → ⟨Σ, IR, M, m*, α̂, ℛ⟩`

If compilation encounters a non‑fatal validation error (e.g., duplicate field update, missing target for edge), the candidate `m*` is discarded and SELECT is re‑invoked with the next candidate.

### Rule 5: COMMIT

**Premises:**
1. **Version validation:** For every read `r ∈ ℛ`:
   - If `r = NodeExistence(id)`, check that node exists and its `existence_version` equals the version recorded in `ℛ` (recorded during DISCOVER).
   - If `r = FieldRead(id,f)`, check `field_version[id][f]` unchanged.
   - Similarly for `EdgeExistence`, `Adjacency`, `Extent`, etc.
2. **Structural validation:** No duplicate `UpdateField` on same `(id,f)`, all targets exist (or are created earlier in `α̂`), no dangling identifiers after applying `α̂`, all constraints satisfied.
3. **Counter overflow pre‑check:** For every counter that would be incremented (sequence counters, version counters, `tick_counter` already advanced), ensure `post_value ≤ INT64_MAX`. If any overflow → fatal.

If any validation fails (non‑fatal), discard `m*` and return to SELECT with next candidate. Fatal errors halt engine and rollback.

**Application:**
- Apply each step in `α̂` in order to `G` to produce `G'`.
- Update counters `C → C'` according to the version increment rules (see table below).
- Emit events in the order they appear in `α̂` (each with its computed payload from pre‑commit state).

**Match history update:**
```
M_prev' = { match_key(m) → age(m) | m ∈ M }
```
(All matches from discovery snapshot, not just the committed one.)

Transition:
```
⟨⟨G, C, T, M_prev⟩, IR, M, m*, α̂, ℛ⟩ → ⟨⟨G', C', T+1, M_prev'⟩, IR⟩
```
(Note: `T` was already incremented in TICK; commit does not change tick number again.)

## 4. Version Increment Rules (Derived from Compile)

The following table summarizes counter increments **only when a change actually occurs** (No‑Op writes do not increment). These rules are consequences of the structural compilation semantics.

| Operation              | extent | pred(node) | order(node) | edge_pred | edge_order | edge_type | adjacency (source.out, target.in) | existence | field_vers |
|------------------------|--------|------------|-------------|-----------|------------|-----------|-----------------------------------|-----------|------------|
| CreateNode             | +1     | +1 (all)   | +1 (all)    | -         | -          | -         | -                                 | set to 1  | set to 1 each |
| DeleteNode             | +1     | +1 (all)   | +1 (all)    | -         | -          | -         | +1 per incident edge (after dedup)| removed   | removed    |
| CreateEdge             | -      | -          | -           | +1 (all)  | +1 (all)   | +1        | +1 source.out, target.in          | set to 1  | set to 1 each |
| DeleteEdge             | -      | -          | -           | -         | -          | +1        | +1 source.out, target.in          | removed   | removed    |
| UpdateField (node)     | -      | +1 (that)  | +1 (that)   | -         | -          | -         | -                                 | -         | +1 (that)  |
| UpdateField (edge)     | -      | -          | -           | +1 (that) | +1 (that)  | -         | -                                 | -         | +1 (that)  |

**Notes:**
- `+1 (all)` means increment the counter for every field of that type.
- `+1 (that)` means increment only the counter for the specific field.
- Adjacency increments happen exactly once per edge per endpoint, even if the edge is deleted by both explicit `DeleteEdge` and implicit `DeleteNode`; deduplication is applied using the earliest occurrence in `α̂`.
- For `DeleteNode`, incident edges are determined from pre‑commit state plus any staged creations earlier in the same transaction.

### Action blocks
\[
A ::= \emptyset \mid a \cdot A
\]

### Rules
\[
R ::= \text{Rule}(P, \phi, B, A, \text{priority params})
