### Detailed Synthesis of Key Problem Areas

#### 1. Determinism Breakers

There is a consensus that the specification currently allows for "leakage" of non-deterministic behavior.

* **The NO_MATCH Contradiction:** Specifying that `M_prev'` is "implementation-defined but deterministic" is a logical impossibility in a closed system. This must be standardized to a single rule (e.g., "always keep" or "always clear").


* **Optional Validation:** The option to skip constraint re-evaluation is a major design flaw. It creates a scenario where two conformant engines might commit different states based on whether they perform validation, violating the core theorem.



#### 2. Logical and Mathematical Hazards

The numeric and operational logic requires tighter binding to prevent implementation drift.

* **Arithmetic Precision:** Truncation toward zero and lack of explicit overflow handling for fixed-point division create "rounding drift". The specification should either mandate standard rounding or provide a concrete, universal error condition for precision loss.


* **Read-Trace Ambiguity:** There is a mismatch between short-circuit evaluation in execution and dependency extraction. While recording all dependencies is safer, it can lead to spurious retries or "stale read" failures that wouldn't occur in a runtime that only records executed reads.



#### 3. Schema and Identifier Omissions

A significant gap exists regarding the "physical" lifecycle of objects.

* **Schema Evolution:** The "No Nulls" requirement combined with mandatory fields creates an "all-or-nothing" update problem. Without a migration or default-value mechanism, the specification is effectively paralyzed for long-lived systems.


* **Object Identity:** The spec lacks a canonical rule for allocating node/edge IDs. Without a deterministic sequence counter increment strategy (e.g., `type:next_seq`), two engines will diverge the moment a `CreateNode` or `CreateEdge` is triggered.



#### 4. Semantic Ambiguities

* **Adjacency Versioning:** The deduplication logic for adjacency versioning is inconsistently defined, creating a risk that version counters will be mismanaged, causing incorrect staleness validation.

- **Score saturation** – can mask priority differences, relying solely on tie‑breaking (AI2, AI4).

- **Missing operators in constraints** – `!=`, `>`, `>=`, `<=`, `||` (AI6).

## Recommended Fix Order

1. **Remove all implementation‑defined / optional behaviour** – NO_MATCH, constraint re‑evaluation.
2. **Specify pattern enumeration as nested iteration over graph elements in a fixed total order** (e.g., nodes by identifier, then edges by identifier), with explicit definition of `sorted_binding_list` (by identifier name, then value using `ORDER_CANONICAL`).
3. **Add sequence counter semantics** – `CreateNode`/`CreateEdge` read the current counter for the type, increment it, and record that read in the trace.
4. **Define the type schema language** – even a minimal one (node/edge types, field names, types, mandatory/optional).
5. **Specify graph state JSON serialisation** – e.g., `{"nodes": [{"id": "...", "type": "...", "fields": {...}}], "edges": [...]}` with identifiers sorted by `ORDER_CANONICAL`.
6. **Clarify edge identity** – edges have globally unique identifiers (e.g., `"type:seq"` like nodes) independent of source/target.
7. **Add fixed‑point scale overflow rule** – e.g., fatal error if result scale > 18.
8. **Fix adjacency deduplication key** to `(node, edge_type, dir)`.
9. **Mandate a single initialisation rule** – sequence counters start at `max(existing)+1` or 0 if none exist.

Once these are addressed, the specification can truly claim “all conformant engines produce identical observable behaviour”. Without them, v0.51 is not ready for conformance.
