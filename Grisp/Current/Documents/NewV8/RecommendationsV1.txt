### 1. The Execution Loop: Livelocks and Time Drift

The fundamental transition system driving the kernel has logical holes that will either crash the engine or trap it in an endless cycle.

* 
**The Double Tick Increment:** The specification currently increments the tick counter twice: once in the TICK rule and again in the COMMIT rule. This causes the logical time (`T`) to drift out of sync with the underlying tick counter.


* **Recommendation:** Consolidate logical time. Drop `T` entirely and define `T ≡ C.tick_counter`. Ensure this counter is incremented exactly *once* per successful commit loop.




* 
**The Infinite Rejection Loop:** If a match fails a non-fatal validation (like a duplicate update or a missing target), the engine discards it and returns to the SELECT phase. However, because the candidate's score hasn't changed, SELECT will immediately pick the exact same failing match again.


* **Recommendation:** Introduce a temporary `Rejected` set for the duration of the tick. If `m*` fails validation, execute `Rejected := Rejected ∪ {m*}` or mathematically remove it via `M := M \ {m*}` before re-invoking SELECT.




* 
**The "Empty Match" Void:** The specification lacks a transition rule for what happens when `M` is empty.


* 
**Recommendation:** Define an explicit SOS rule for an empty match set that gracefully ends the tick, advances the tick counter, and preserves the un-aged `M_prev` state.





### 2. Version Validation and State Tracking

The optimistic concurrency model relies on checking versions, but the data structures defined don't hold the necessary information.

* 
**Ghost Read Traces:** The `DISCOVER` phase requires building a read trace (`ℛ_m`) of accessed elements, and `COMMIT` requires validating these against "the version recorded". However, the specification never defines *how* to store those version numbers in the trace.


* 
**Recommendation:** When building the native record structures for the trace, `ℛ_m` must explicitly store tuples of `(ElementID, Property, VersionValue)`. Without the captured integer value, the `COMMIT` phase has nothing to validate against.




* **Adjacency Double-Counting:** The version increment rules double-count edge deletions. If a node is deleted, the `PLAN` phase expands this into explicit `DeleteEdge(e)` commands for all incident edges, followed by `DeleteNode`. The table increments adjacency versions for *both* actions.


* **Recommendation:** Remove the adjacency increment from the `DeleteNode` table row. The expanded `DeleteEdge` actions will safely and naturally handle the adjacency increments.


* 
**Unbounded Memory Growth:** The system indefinitely tracks the age of every match in `M_prev`.


* 
**Recommendation:** Implement an eviction policy (e.g., purging matches that haven't been seen in $N$ ticks) or establish a maximum capacity for the dictionary.





### 3. Closing the Nondeterminism Gaps

For all engines to produce identical golden files, ambiguities in evaluation order and mathematics must be eliminated.

* 
**Short-Circuiting Must Be Mandatory:** The specification states that short-circuiting for boolean operators (`&&`, `||`) and constraints is "allowed". This completely destroys determinism, as one engine might evaluate a right-hand operand (triggering a read trace addition) while another skips it.


* 
**Recommendation:** Explicitly mandate that short-circuiting is *strictly required*. The dependency extraction must immediately halt reading variables once a logical condition is met.




* 
**Fairness Score Overflows:** The scoring formula ($base \times scale + age \times fairness$) uses unbounded age. In a 64-bit system, a long-running instance will eventually throw a fatal `INTEGER_OVERFLOW` simply because a rule survived too long.


* **Recommendation:** Use saturating arithmetic for the fairness score calculation. If the calculation hits `INT64_MAX`, it clamps to that value rather than killing the kernel.




* 
**Map and Tuple Ordering:** The sorting logic for internal maps and pattern cross-products is dangerously loose.


* 
**Recommendation:** For your proposed grammar's `map_literal`, enforce that all map keys must be strictly sorted by their UTF-8 byte values *before* evaluation or serialization.





### 4. Aligning with the v0.01 Grammar

Your proposed grammar introduces `let_block` and `where_block` sequentially.

* 
**The Let-Binding Trap:** The specification currently says that `let` bindings do *not* affect match identity. If your grammar's `let` block accesses graph state (e.g., `let x := node.field`), and two matches differ *only* by this evaluated value, they will collide in the `match_key`.


* 
**Recommendation:** If `let` blocks read graph state, those reads *must* be injected into the read trace `ℛ_m`. You must also clearly define if variables declared in a `let_block` are allowed to mutate or trigger side-effects within the `actions_block`.

## Consensus – what must be fixed, and how

### Tier 1 – correctness blockers (implementations will diverge)

**1. Tick is incremented twice**
- Problem: Rule 1 does `T+1` and `tick_counter+1`, Rule 5 COMMIT does `T+1` again. Your review shows T=0 → 1 → 2 in one tick.
- Fix: Drop `T` from Σ entirely. Keep only `C.tick_counter`. Increment it **once**, in COMMIT, after successful validation. Rule 1 becomes a no-op (or just a guard for overflow). This matches your grammar where there is no explicit tick – time advances only on commit.

**2. SOS states are not closed**
- Problem: Σ = ⟨G,C,T,M_prev⟩ but DISCOVER adds M, SELECT adds m*, PLAN adds α̂, ℛ.
- Fix: Define extended configuration explicitly:
  ```
  Σ0 = ⟨G,C,M_prev⟩
  Σ1 = ⟨G,C,M_prev,M⟩
  Σ2 = ⟨G,C,M_prev,M,m*⟩
  Σ3 = ⟨G,C,M_prev,M,m*,α̂,ℛ⟩
  ```
  The determinism theorem then quantifies over Σ0→Σ0, not over hidden intermediates.

**3. Infinite non-fatal rejection loop**
- You flagged it, I flagged it. Current text says "discard m* and go back to SELECT" but never removes it from M.
- Fix: After any non-fatal failure, set `M := M \ {m*}` before re-selecting. If M becomes empty, commit a no-op tick (still increment tick_counter, update M_prev to empty set). This guarantees termination.

**4. Read-set validation has no versions**
- DISCOVER records `ℛ_m` as bare reads, COMMIT compares to "version recorded during DISCOVER" – but no version is stored.
- Fix: Store versions in the read trace:
  ```
  FieldRead(id,f, v) where v = field_version[id][f] at discovery
  NodeExistence(id, v) where v = existence_version[id]
  ```
  PLAN must merge ℛ_m and ℛ (from action argument evaluation). Validation is then a simple equality check.

**5. Short-circuit "allowed" breaks determinism**
- Your point #6 is the biggest hidden issue. If `A || B` skips B on some engines, ℛ differs.
- Fix: Change spec language from "allowed" to "required, left-to-right, with conditional dependencies":
  - `e1 && e2`: evaluate e1, if false, ℛ = ℛ_e1, value = false
  - if true, evaluate e2, ℛ = ℛ_e1 ∪ ℛ_e2
  - Same for `||`. Document this in §2.1 and §4. This makes dependency extraction syntax-directed and deterministic.

**6. match_key JSON bottleneck**
- You asked: binary tuple or hash? Use binary tuple comparison, not hash.
- Fix: Define `match_key = (rule_id, [ (var, type, seq)... ])` sorted by var name, compared lexicographically using ORDER_CANONICAL. No JSON allocation. Store it as a struct for tie-breaking. This preserves total order and avoids heap fragmentation in Object Pascal.

### Tier 2 – semantic gaps that make the spec unimplementable

**7. Version increments are global and double-count**
- Current table does `+1 (all)` for every field on CreateNode, and double increments adjacency on DeleteNode.
- Fix per your §6 observation:
  - CreateNode: increment only `extent_version[type]`, `existence_version[new]`, and `field_version[new][f]` for each supplied field. Do **not** bump predicate_version for all fields.
  - DeleteNode expansion: perform explicit DeleteEdge actions, and **only** those DeleteEdge actions bump adjacency and edge_type. Remove the "+1 per incident edge" line from DeleteNode row.
  - UpdateField: bump only `field_version[id][f]` and `predicate_version[type][f]`. Drop ordering_dependency_version unless you actually use it for ordering queries (currently unused).

**8. No-op writes undefined**
- Spec says "No-Op writes do nothing" but doesn't define equality.
- Fix: Define no-op as bitwise value equality after canonical serialization. For FixedPoint, compare scaled integer, not string. No-op writes skip version bumps and are removed from α̂ during PLAN.

**9. Fairness overflow**
- `score = base*scale + age*fairness` overflows int64.
- Fix: Compute score in unsigned 128-bit, saturate at 2^63-1. Document that overflow is not fatal – it caps priority. This prevents a long-lived match from killing the kernel.

**10. Event payload evaluation**

### Detailed issues and concrete fixes

#### 1. Tick counter duplication and semantics
**Problem:** `TICK` increments both `tick_counter` and `T`; `COMMIT` also returns `T+1`.  
**Fix:** Choose one authoritative tick value. Recommended change:
- Remove `T` from the state model and use `C.tick_counter` as the single canonical tick number.
- Update all rules to increment `tick_counter` exactly once per successful commit. Make TICK only increment a pre‑commit counter if you need a pre‑discovery marker; otherwise remove the TICK rule or make it a no‑op that only increments `tick_counter` on commit.
**Specification edit:** Replace all occurrences of `T` with `C.tick_counter` and change COMMIT transition to `→ ⟨G', C', M_prev'⟩` with `C'.tick_counter = C.tick_counter + 1`.

#### 2. SOS closure and derivation artifacts
**Problem:** DISCOVER/SELECT/PLAN produce `M`, `m*`, `α̂`, `ℛ` but Σ omits them; the determinism theorem claims a single successor for Σ.  
**Fix:** Two options:
- **Preferred:** Treat DISCOVER/SELECT/PLAN as *derivation judgments* (not stateful transitions) and keep Σ minimal. Explicitly state that `M`, `m*`, `α̂`, `ℛ` are ephemeral derivation artifacts and not part of Σ. Update the determinism theorem to quantify over derivations: for a given Σ and IR the next committed Σ' is unique.
- **Alternative:** Extend Σ to include the intermediate artifacts and make transitions explicit.  
**Specification edit:** Add a paragraph in §5 defining derivation artifacts and revise the determinism theorem accordingly.

#### 3. Infinite reselection loop
**Problem:** If every candidate repeatedly fails validation, SELECT will pick the same top candidate forever.  
**Fix:** On non‑fatal rejection of `m*`, remove it from the current candidate set for the tick: `M := M \ {m*}` and record it in a per‑tick `Rejected` set. Re‑invoke SELECT on the reduced `M`. Ensure `M_prev` is not updated until COMMIT.  
**Specification edit:** Add a rule in SELECT/COMMIT describing `Rejected` and the reselection semantics.

#### 4. Read trace must record versions
**Problem:** DISCOVER records read kinds but not the version values needed for COMMIT validation.  
**Fix:** Define `ℛ_m` entries as tuples `(read_kind, element_id, recorded_version_value)` with a canonical serialization. For each read kind map to a specific counter/version field (e.g., `FieldRead(id,f)` → `field_version[id][f]`). Record the exact integer value observed during DISCOVER.  
**Specification edit:** Add a `ReadTraceSchema` subsection listing read kinds and the exact counter/version to capture.

#### 5. Short‑circuiting and dependency extraction
**Problem:** Allowing short‑circuiting without specifying dependency semantics yields different read sets.  
**Fix:** Make one of the following explicit:
- **Deterministic evaluation policy A:** *Always evaluate both operands* for `&&` and `||` when used in constraints and pattern lets; dependency set is union of both. This preserves determinism and makes read traces stable.
- **Policy B:** *Require short‑circuit evaluation* but mandate that dependency extraction must include reads from both operands regardless of runtime short‑circuit. This is less intuitive and more surprising.  
**Recommendation:** Adopt Policy A (evaluate both) for constraints and let expressions used in DISCOVER. Document performance implications.  
**Specification edit:** Replace “short‑circuit allowed” with “short‑circuit forbidden in DISCOVER; both operands evaluated for dependency extraction.”

#### 6. Score arithmetic overflow and age semantics
**Problem:** Age and score arithmetic can overflow and cause fatal errors.  
**Fix:** Use saturating arithmetic for age and score computations or widen to 128‑bit intermediate arithmetic for scoring only. Additionally, provide an age compaction policy: cap `age` at a configurable `AGE_MAX` and treat larger ages as `AGE_MAX`. Document that overflow in score computation yields `INTEGER_OVERFLOW` only if intermediate exceeds a safe bound after widening.  
**Specification edit:** Add numeric policy: scoring uses 128‑bit intermediates; ages saturate at `2^63-1` and do not cause fatal errors.

#### 7. Event payload evaluation timing
**Problem:** Ambiguity whether event payloads are evaluated during PLAN or at COMMIT against pre‑commit state.  
**Fix:** Choose and document one:
- **Option 1 (recommended):** Evaluate event payload expressions during PLAN and record their **values** in `α̂`. Emit those recorded values at COMMIT. This makes event emission deterministic and avoids surprising pre/post semantics.
- If you must evaluate at COMMIT, explicitly state that payload expressions are evaluated against the pre‑commit snapshot and record the read versions induced by that evaluation in `ℛ`.  
**Specification edit:** Make event payload evaluation policy explicit and add examples.

#### 8. `match_key` canonicalization
**Problem:** `match_key` canonical JSON rules are incomplete for nested maps/lists and identifier normalization.  
**Fix:** Add a canonicalization appendix:
- Unicode normalization form NFC for all strings.
- Map keys sorted by ORDER_CANONICAL.
- Identifiers serialized as `"type:seq"` with `seq` as decimal without leading zeros.
- Exclude `let_values` explicitly.
- Provide canonical examples and test vectors.  
**Specification edit:** Add `MatchKeyCanonicalization` subsection and include 10 test vectors.

#### 9. Adjacency deduplication and counter application order
**Problem:** “Earliest occurrence in `α̂`” is ambiguous; counter application order unspecified leading to double increments.  
**Fix:** Define a deterministic counter application algorithm:
- Apply primitive actions in `α̂` left‑to‑right.
- Maintain a deduplication map keyed by `(edge_id, endpoint)` to record the first index where adjacency increment should occur; only that first occurrence increments adjacency counters.
- After applying all actions, compute counter increments by scanning `α̂` and applying per‑action increments immediately in order.  
**Specification edit:** Add `CounterApplicationAlgorithm` with pseudocode and an example.

#### 10. `M_prev` retention and resource limits
**Problem:** `M_prev` can grow without bound.  
**Fix:** Define retention policy:
- Keep `M_prev` entries for at most `K` ticks (configurable), or
- Compact `M_prev` by storing only a bounded LRU or hashed age bucket.  
Add `RESOURCE_LIMIT_EXCEEDED` semantics when `M_prev` exceeds configured memory budget.  
**Specification edit:** Add `M_prevRetentionPolicy` and recommended default `K` (e.g., 10,000).
