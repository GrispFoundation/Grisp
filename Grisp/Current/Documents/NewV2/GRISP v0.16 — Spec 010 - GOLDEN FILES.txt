============  GRISP v0.16 — Spec 010 - GOLDEN FILES  ============

Status: Draft
Layer: 0 (Deterministic Verification Layer)
Depends on:
- Spec 001 Canonical IR
- Spec 002 Expression AST
- Spec 003 Runtime Profile
- Spec 007 Transaction Model
- Spec 011 State Model
- Spec 013 Selection Model

1. Purpose
Golden Files define the canonical, engine-independent reference outputs for GRISP. They ensure that any compliant engine produces identical results for the same inputs. Golden Files are used for conformance testing, regression testing, and deterministic verification.

2. Design Principles
- Golden Files must be deterministic.
- Golden Files must be canonical JSON.
- Golden Files must not depend on timing.
- Golden Files must not depend on external systems.
- Golden Files must not depend on nondeterministic ordering.
- Golden Files must fully specify expected engine behavior.

3. Golden File Categories
Golden Files are divided into the following categories:

3.1 Manifest Golden Files
Contain canonical IR manifests.

3.2 State Golden Files
Contain initial and final graph states.

3.3 Match Golden Files
Contain expected matches for each rule.

3.4 Transaction Golden Files
Contain expected transaction sequences.

3.5 Event Golden Files
Contain expected emitted events.

3.6 Error Golden Files
Contain expected structured errors.

4. Golden File Structure

{
  "golden_file_version": "grisp-golden-v0.16",
  "description": "string",
  "input": { ... },
  "expected_output": { ... },
  "metadata": {},
  "custom": {}
}

Fields:
golden_file_version: version identifier
description: human-readable description
input: structured input to the engine
expected_output: deterministic expected result

5. Manifest Golden Files
Manifest Golden Files contain:

{
  "manifest": { Canonical IR Manifest },
  "expected_validation": "ok|error",
  "expected_errors": [ ... ]
}

Rules:
- expected_validation must be deterministic.
- expected_errors must be structured.

6. State Golden Files
State Golden Files contain:

{
  "initial_state": { Graph State },
  "final_state": { Graph State }
}

Rules:
- Graph State is defined in Spec 011.
- All node and edge instances must be canonical.

7. Match Golden Files
Match Golden Files contain:

{
  "manifest": { Canonical IR Manifest },
  "state": { Graph State },
  "expected_matches": [
    {
      "rule_id": "string",
      "bindings": { ... },
      "let_values": { ... },
      "match_key": "string",
      "score": number
    }
  ]
}

Rules:
- match_key must follow Spec 013.
- score must follow Selection Model.

8. Transaction Golden Files
Transaction Golden Files contain:

{
  "manifest": { Canonical IR Manifest },
  "state": { Graph State },
  "runtime_profile": { Runtime Profile },
  "expected_transactions": [
    {
      "transaction_id": "string",
      "selected_match": { ... },
      "writes": { ... },
      "events": [ ... ]
    }
  ]
}

Rules:
- selected_match must match Match Golden Files.
- writes must match Transaction Model semantics.
- events must match Event Model.

9. Event Golden Files
Event Golden Files contain:

{
  "events": [
    {
      "event_type": "string",
      "payload": { ... },
      "timestamp": "logical_tick"
    }
  ]
}

Rules:
- timestamp must be logical, not wall-clock.

10. Error Golden Files
Error Golden Files contain:

{
  "input": { ... },
  "expected_error": {
    "code": "string",
    "message": "string",
    "details": { ... }
  }
}

Rules:
- errors must be deterministic.
- errors must not contain stack traces.

11. Canonical Serialization Rules
Golden Files must follow canonical JSON rules:
- sorted keys
- UTF-8 encoding
- no trailing commas
- deterministic number formatting
- no whitespace beyond single spaces

12. Deterministic Comparison
Golden Files must be compared using:
- byte-for-byte comparison
- no tolerance for formatting differences
- no tolerance for ordering differences

13. Test Execution Model
Golden Files are executed as follows:

Step 1: Load manifest.
Step 2: Load initial state.
Step 3: Apply deterministic engine steps.
Step 4: Capture output.
Step 5: Compare output to expected_output.
Step 6: Pass or fail.

14. Versioning
Golden Files must include:
- golden_file_version
- manifest_version
- runtime_profile_version

Golden Files must be regenerated when:
- IR changes
- Transaction Model changes
- Selection Model changes

15. Validation Rules
A Golden File is valid if:
- it follows canonical JSON
- expected_output is deterministic
- no unknown fields appear
- all dependencies are valid

16. Summary
Golden Files v0.16 define:
- deterministic reference outputs
- canonical test structures
- strict comparison rules
- complete coverage of engine behavior

Golden Files ensure that all GRISP engines behave identically.

============  END OF SPEC 010  ============
