============  GRISP v0.16 — Spec 007 - TRANSACTION MODEL  ============

Status: Draft
Layer: 0 (Deterministic Execution Core)
Depends on:
- Spec 001 Canonical IR
- Spec 002 Expression AST
- Spec 003 Runtime Profile
- Spec 004 Trust Model
- Spec 005 Boundary Contract
- Spec 011 State Model
- Spec 013 Selection Model

1. Purpose
The Transaction Model defines how GRISP evaluates rule matches, validates them, applies actions, detects invalidation, and commits deterministic state transitions. It is the core execution algorithm of the GRISP engine.

2. Design Principles
- Deterministic evaluation
- Deterministic match selection
- Deterministic commit
- No concurrency
- No nondeterministic ordering
- No time-based behavior
- No side effects outside commit

3. Transaction Lifecycle
A transaction consists of the following deterministic phases:

Step 1: Match discovery  
Step 2: Match scoring  
Step 3: Match selection  
Step 4: Read validation  
Step 5: Action evaluation  
Step 6: Write staging  
Step 7: Conflict and invalidation checks  
Step 8: Commit  
Step 9: Hook execution  
Step 10: Event emission

All steps must be executed in this order.

4. Match Discovery
For each rule:
- Evaluate all pattern bindings.
- Evaluate where clauses.
- Produce zero or more matches.

A match is:

{
  "rule_id": "string",
  "bindings": { "name": "node_id", ... },
  "let_values": { "name": <value>, ... },
  "inferred_reads": [...],
  "inferred_writes": [...],
  "match_key": "string"
}

match_key is defined in Spec 013.

5. Match Scoring
Match scoring uses the Selection Model (Spec 013). Runtime Profile provides parameters.

Score inputs:
- rule priority
- match age
- fairness window
- priority boost per tick

Score output must be deterministic.

6. Match Selection
The match with the highest score is selected.

Tie breaking uses:
- tie_breaker from Runtime Profile
- deterministic ordering rules from Spec 013

7. Read Validation
Before executing actions, the engine must validate that:
- all inferred_reads still match the current graph state
- no field read has changed since match discovery
- no fact has been deleted
- no edge has been modified if it was read

If validation fails:
- the match is invalidated
- the engine restarts from match discovery

8. Action Evaluation
Actions are evaluated in order.

Allowed actions:
- create
- update
- delete
- call
- emit

Action semantics are defined in Boundary Contract (Spec 005).

Action evaluation must:
- evaluate all expressions
- apply trust rules
- apply capability rules
- produce a write set

9. Write Staging
All writes are staged in a temporary buffer.

Staged writes include:
- new facts
- updated fields
- deleted facts
- created edges
- deleted edges
- emitted events

No writes may be applied to the graph state until commit.

10. Conflict and Invalidation Checks
v0.16 introduces a formal definition of conflict:

A conflict occurs if:
- a staged write modifies a field that has changed since match discovery
- a staged delete targets a fact that has changed since match discovery
- a staged edge modification targets an edge that has changed since match discovery
- trust requirements are not met
- capability requirements are not met

If a conflict occurs:
- the match is invalidated
- the engine restarts from match discovery

11. Commit
Commit applies staged writes atomically.

Commit steps:
- apply fact creations
- apply fact updates
- apply fact deletions
- apply edge modifications
- append events to event log

Commit must be atomic and deterministic.

12. Hook Execution
After commit, hooks may run.

Hooks:
- must run in commit order
- must not modify graph state
- may call external systems
- must be idempotent if retried
- must not affect determinism

Hook semantics are defined in Spec 008.

13. Event Emission
Events produced during commit are emitted after hooks.

Event structure is defined in Spec 012.

14. Match Aging
Each match has an age counter incremented per tick.

Age affects scoring:
- older matches receive priority boosts
- matches exceeding max_match_age are invalidated

15. Deterministic Tick Model
A tick is defined as:
- one full execution of the transaction lifecycle
- exactly one commit per tick (default)
- no wall-clock dependency

16. Error Handling
If an action fails:
- the transaction aborts
- no writes are committed
- an error is returned via Boundary Contract

17. Determinism Requirements
Transaction Model must be:
- fully deterministic
- independent of timing
- independent of external ordering
- independent of concurrency

18. Validation Rules
A transaction is valid if:
- all reads are validated
- no conflicts occur
- all trust rules pass
- all capability rules pass
- all actions are valid

19. Summary
Transaction Model v0.16 defines:
- deterministic match discovery
- deterministic scoring and selection
- deterministic read validation
- deterministic conflict detection
- deterministic commit
- deterministic hooks
- deterministic event emission

It is the core execution algorithm of GRISP.

============  END OF SPEC 007  ============
