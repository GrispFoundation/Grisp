============  GRISP v0.16 — Spec 013 - SELECTION MODEL  ============

Status: Draft
Layer: 0 (Deterministic Execution Core)
Depends on:
- Spec 001 Canonical IR
- Spec 003 Runtime Profile
- Spec 007 Transaction Model

1. Purpose
The Selection Model defines how GRISP scores, ranks, and selects rule matches for execution. It ensures deterministic behavior across all engines, independent of timing, concurrency, or implementation details.

2. Design Principles
- Selection must be deterministic.
- Selection must be reproducible.
- Selection must not depend on timing.
- Selection must not depend on external systems.
- Selection must not depend on nondeterministic ordering.
- Selection must be fully defined by manifest, runtime profile, and state.

3. Match Score Formula
Each match receives a score computed as:

score = base_priority
      + age_boost
      + fairness_boost
      + tie_break_component

All components must be deterministic.

4. Base Priority
Base priority is defined by rule metadata:

{
  "priority": <integer>
}

If omitted, default priority is 0.

5. Age Boost
Age boost increases score for older matches.

age_boost = match_age * priority_boost_per_tick

match_age:
- increments by 1 per tick
- resets to 0 when match is created

priority_boost_per_tick:
- defined in Runtime Profile
- default: 0.02

6. Fairness Boost
Fairness boost prevents starvation.

If match_age >= fairness_window:
  fairness_boost = 1.0
Else:
  fairness_boost = 0.0

fairness_window:
- defined in Runtime Profile
- default: 10

7. Tie Break Component
If two matches have identical scores, a deterministic tie breaker is applied.

tie_break_component is computed as:

tie_break_component = hash(match_key) * epsilon

epsilon:
- small constant
- default: 1e-9

hash:
- SHA-256 over UTF-8 bytes
- interpreted as unsigned integer
- normalized to [0, 1)

8. Match Key
match_key is a deterministic string representing the match.

match_key = rule_id + "|" + sorted(binding_pairs)

binding_pairs:
- each pair is "name=node_id"
- sorted lexicographically

Example:
"AssignTask|agent=agent_3|task=task_1"

9. Deterministic Ordering
Matches must be sorted by:
1. score (descending)
2. tie_break_component (descending)
3. match_key (lexicographic)

10. Selection Algorithm
Step 1: Compute score for each match.
Step 2: Sort matches deterministically.
Step 3: Select the first match.
Step 4: Execute transaction lifecycle.

11. Match Invalidation
A match is invalidated if:
- any read field changes
- any read node is deleted
- any read edge is modified
- match_age exceeds max_match_age

max_match_age:
- defined in Runtime Profile
- default: 100

12. Match Aging
match_age increments by 1 per tick.

Tick definition:
- one full transaction lifecycle
- independent of wall-clock time

13. Deterministic Hashing
Hashing rules:
- SHA-256
- UTF-8 encoding
- canonical JSON for structured values
- normalized to float in [0, 1)

14. Deterministic Floating Point Rules
Floating point operations must:
- use IEEE 754 double precision
- avoid rounding differences
- avoid platform-dependent behavior

15. Deterministic Sorting Rules
Sorting must:
- be stable
- be lexicographic for strings
- be numeric for scores
- be deterministic across all engines

16. Validation Rules
Selection Model is valid if:
- all matches have valid match_keys
- all scores are finite
- no NaN values appear
- sorting is deterministic

17. Summary
Selection Model v0.16 defines:
- deterministic scoring
- deterministic aging
- deterministic fairness
- deterministic tie breaking
- deterministic match selection

It ensures that all GRISP engines select the same match under the same conditions.

============  END OF SPEC 013  ============
