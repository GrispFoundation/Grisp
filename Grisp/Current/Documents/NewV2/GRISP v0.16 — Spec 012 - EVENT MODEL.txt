============  GRISP v0.16 — Spec 012 - EVENT MODEL  ============

Status: Draft
Layer: 1 (Post-Commit Notification Layer)
Depends on:
- Spec 001 Canonical IR
- Spec 007 Transaction Model
- Spec 008 Hook Semantics

1. Purpose
The Event Model defines how GRISP represents, stores, and emits events. Events are immutable records produced during transaction commit. They provide a deterministic audit trail and a mechanism for external systems to react to state changes.

2. Design Principles
- Events must be immutable.
- Events must be deterministic.
- Events must be canonical.
- Events must not modify graph state.
- Events must not depend on timing.
- Events must not depend on external systems.

3. Event Structure

{
  "event_id": "string",
  "event_type": "string",
  "payload": { ... },
  "tick": <integer>,
  "commit_id": "string"
}

Fields:
event_id: unique identifier
event_type: string describing the event
payload: structured data
tick: logical tick number
commit_id: identifier of the commit that produced the event

4. Event Types
Event types are defined by the manifest or by rule actions.

Examples:
- task_created
- task_updated
- task_deleted
- edge_created
- edge_deleted
- custom_event

Event types must be deterministic strings.

5. Event Emission
Events are emitted during commit.

Emission steps:
Step 1: Transaction Model stages events.
Step 2: Commit applies writes.
Step 3: Events are appended to event log.
Step 4: Hooks may read events.
Step 5: Boundary Contract returns events to external systems.

Events must not be emitted before commit.

6. Event Ordering
Events must be ordered deterministically:

Primary key: tick  
Secondary key: commit_id  
Tertiary key: event_id  

Within a single commit:
- events must appear in the order they were produced by actions

7. Event Log
The event log is an append-only structure:

{
  "events": [
    { event },
    { event },
    ...
  ]
}

Rules:
- events must never be modified
- events must never be deleted
- events must be stored in canonical order

8. Event ID Generation
event_id must be deterministic.

Default format:
event_<tick>_<sequence_number>

sequence_number increments per event within a commit.

9. Event Payload
Payload must be:
- structured
- canonical JSON
- deterministic
- free of trust
- free of AI metadata

Payload may contain:
- node identifiers
- field values
- edge identifiers
- rule identifiers
- commit metadata

10. Event Creation by Actions
Actions may explicitly create events using:

{
  "kind": "emit",
  "event_type": "string",
  "payload": { Expression AST }
}

Rules:
- payload expressions must be deterministic
- event_type must be a string literal
- emit must not modify graph state

11. System Events
The engine may emit system events:

commit_applied  
node_created  
node_updated  
node_deleted  
edge_created  
edge_deleted  

System events must follow the same structure as user-defined events.

12. Event Consumption
Events may be consumed by:
- hooks
- external systems
- logging systems
- monitoring systems

Events must not be consumed by:
- rule evaluation
- match scoring
- transaction logic

13. Event Retention
Retention policy is implementation-defined but must be deterministic.

Allowed policies:
- retain all events
- retain last N events
- retain events for last M ticks

Retention must not affect determinism of rule execution.

14. Event Serialization
Events must serialize to canonical JSON:
- sorted keys
- deterministic formatting
- UTF-8 encoding
- no trailing commas

15. Determinism Requirements
Events must not depend on:
- wall-clock time
- randomness
- external ordering
- concurrency

tick must be logical, not real time.

16. Validation Rules
An event is valid if:
- event_id is unique
- event_type is a string
- payload is structured
- tick is non-negative
- commit_id is valid
- canonical serialization is possible

17. Summary
Event Model v0.16 defines:
- deterministic event structure
- deterministic event ordering
- immutable event log
- structured event emission
- safe post-commit notifications

Events provide a deterministic audit trail and integration point for external systems.

============  END OF SPEC 012  ============
