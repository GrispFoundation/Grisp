============  GRISP v0.16 — Spec 011 - STATE MODEL  ============

Status: Draft
Layer: 0 (Deterministic Execution Core)
Depends on:
- Spec 001 Canonical IR
- Spec 002 Expression AST
- Spec 007 Transaction Model

1. Purpose
The State Model defines the in-memory representation of all facts, edges, and metadata that make up the GRISP graph state. It is the authoritative source of truth for rule evaluation, match discovery, and transaction commit.

2. Design Principles
- State must be deterministic.
- State must be canonical.
- State must be fully serializable.
- State must not contain trust.
- State must not contain AI metadata.
- State must not contain runtime policy.

3. Graph State Structure

{
  "nodes": {
    "<node_id>": {
      "type": "Task",
      "fields": {
        "name": "Example",
        "priority": 2,
        "lifecycle": "pending"
      }
    },
    ...
  },
  "edges": {
    "AssignedTo": [
      { "from": "task_1", "to": "agent_3" },
      ...
    ]
  },
  "metadata": {
    "next_node_id": 1234,
    "tick": 42
  }
}

4. Node Instances
A node instance is:

{
  "type": "NodeTypeName",
  "fields": {
    "<field_name>": <value>,
    ...
  }
}

Rules:
- All fields must conform to the node type schema.
- Missing fields must be filled with default values.
- Extra fields must be rejected.
- Node instances do not carry trust.

5. Node Identifiers
Node identifiers must be:
- unique
- stable
- canonical strings

Default format:
node_<integer>

Engines may use alternative formats if deterministic.

6. Edge Instances
Edges represent typed relationships.

Edge instance:

{
  "from": "node_id",
  "to": "node_id"
}

Rules:
- Edge type defines allowed from/to node types.
- Multiplicity constraints must be enforced.
- Duplicate edges must be rejected.
- Edge instances do not carry trust.

7. State Metadata
State metadata contains:
- next_node_id: deterministic node ID generator
- tick: logical tick counter

tick increments once per committed transaction.

8. Canonical Serialization
State must serialize to canonical JSON:
- sorted keys
- deterministic ordering of nodes
- deterministic ordering of edges
- deterministic number formatting

Node ordering:
- lexicographic by node_id

Edge ordering:
- lexicographic by from, then to

9. State Hashing
State hashing is used for:
- deterministic debugging
- golden file verification
- distributed consistency checks

Hash input:
- canonical JSON serialization of state

Hash algorithm:
- SHA-256 over UTF-8 bytes

10. State Transitions
State transitions occur only through commit.

Commit applies:
- node creations
- node updates
- node deletions
- edge creations
- edge deletions

No other mechanism may modify state.

11. Read Semantics
Reads occur during:
- pattern matching
- let evaluation
- action evaluation

Reads must:
- access only existing nodes
- access only existing edges
- access only valid fields
- be deterministic

12. Write Semantics
Writes occur only during commit.

Writes must:
- apply staged updates
- enforce schema
- enforce multiplicity
- enforce node type constraints
- enforce edge type constraints

13. Deletion Semantics
Deleting a node:
- removes the node
- removes all edges referencing the node
- invalidates any matches referencing the node

14. State Validation
State is valid if:
- all nodes conform to schema
- all edges conform to schema
- no dangling edges exist
- metadata fields are valid
- canonical serialization is possible

15. Determinism Requirements
State Model must not depend on:
- timing
- concurrency
- external systems
- nondeterministic ordering

16. Summary
State Model v0.16 defines:
- deterministic graph representation
- canonical node and edge structures
- deterministic serialization and hashing
- strict schema enforcement
- deterministic state transitions

It is the foundation for all GRISP execution.
