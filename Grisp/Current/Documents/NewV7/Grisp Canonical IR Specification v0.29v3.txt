## GRISP Canonical IR Specification v0.29v3

### Status

Normative Specification

This document defines the Canonical Intermediate Representation (IR) for GRISP systems.

The Canonical IR is the **sole executable representation** consumed by conformant GRISP engines. It maps directly onto the kernel concepts defined in the GRISP Deterministic Kernel Specification v0.29.

Source languages, DSLs, graphical editors, code generators, and manifest compilers SHALL compile to Canonical IR before execution.

The Canonical IR is a stable contract between:

* Parsers
* Compilers
* Validators
* Optimizers
* Execution Engines
* Test Harnesses

The Canonical IR is independent of source syntax.

---

## IR-001 Goals

The Canonical IR SHALL be:

* Deterministic
* Canonicalizable
* Serialization Stable
* Language Independent
* Fully Explicit
* Self Contained

The Canonical IR SHALL NOT depend upon:

* Source-language syntax
* Runtime reflection
* Host-language behavior
* External schema systems

---

## IR-002 Design Principles

All executable behavior SHALL be represented explicitly.

The IR SHALL contain:

* Type Definitions
* Function Definitions
* Rule Definitions
* Expressions
* Actions

The IR SHALL NOT contain:

* Comments
* Formatting directives
* Editor metadata
* Runtime implementation details
* Control‑flow constructs (`If`, `ForEach`) or local bindings (`Let`) as actions

---

## IR-003 Top-Level Structure

A Canonical IR document SHALL contain:

```json
{
  "ir_version": "grisp-ir-v0.29v3",
  "manifest_id": "...",
  "manifest_version": "...",
  "types": [],
  "functions": [],
  "rules": [],
  "constants": {},
  "metadata": {}
}
```

Required fields:

* `ir_version`
* `manifest_id`
* `manifest_version`
* `types`
* `functions`
* `rules`

Unknown top-level fields SHALL be rejected.

The following fields are descriptive metadata only:

* `manifest_id`
* `manifest_version`
* `metadata`

These fields SHALL NOT affect execution semantics. Engines SHALL ignore unrecognized metadata fields.

---

## IR-004 Type System

Supported primitive types:

```text
Boolean
Integer
String
Identifier
```

Supported compound types:

```text
List<T>
Map<String,T>
FixedPoint(scale)
```

Floating point types SHALL NOT exist.

Null SHALL NOT exist.

Undefined SHALL NOT exist.

---

## IR-005 Type Definitions

Node types SHALL be defined explicitly.

Example:

```json
{
  "kind": "node_type",
  "name": "Person",
  "fields": {
    "name": "String",
    "age": "Integer"
  }
}
```

All fields are mandatory.

Duplicate field names SHALL be rejected.

---

## IR-006 Edge Definitions

Example:

```json
{
  "kind": "edge_type",
  "name": "Friendship",
  "from": "Person",
  "to": "Person"
}
```

Edge endpoints SHALL reference valid node types.

---

## IR-007 Constants

Constants SHALL be immutable.

Example:

```json
{
  "MAX_LEVEL": {
    "type": "Integer",
    "value": 100
  }
}
```

Constants SHALL NOT depend on runtime state.

---

## IR-008 Functions

Functions SHALL be one of:

```text
pure
effect_deterministic
```

No other function categories exist.

Example:

```json
{
  "function_id": "CalculateTax",
  "kind": "pure",
  "parameters": [
    {
      "name": "income",
      "type": "Integer"
    }
  ],
  "return_type": "Integer"
}
```

---

## IR-009 Effect Functions

Effect-deterministic functions SHALL declare observable reads.

Example:

```json
{
  "function_id": "NearbyEnemies",
  "kind": "effect_deterministic",
  "declared_reads": [
    {
      "dependency": "Extent",
      "type": "Enemy"
    }
  ]
}
```

Missing required dependencies SHALL be rejected.

Under-declared dependencies SHALL be rejected.

---

## IR-010 Expressions

Expressions SHALL form immutable trees.

Supported expression kinds:

```text
Literal
Variable
FieldAccess
FunctionCall

Add
Subtract
Multiply
Divide
Modulo

Equal
NotEqual
Less
LessEqual
Greater
GreaterEqual

And
Or
Not

Conditional

MapLiteral
Array
```

Unknown expression kinds SHALL be rejected.

Expression evaluation SHALL be deterministic.

---

## IR-011 Literals

Allowed literal types:

```text
Boolean
Integer
String
Identifier
```

Example (Integer):

```json
{
  "kind": "Literal",
  "type": "Integer",
  "value": 42
}
```

Identifier example:

```json
{
  "kind": "Literal",
  "type": "Identifier",
  "value": "Person:42"
}
```

Identifier literals SHALL conform to the Kernel’s identifier grammar (`TypeName:nonNegativeInteger`), where `TypeName` allows letters, digits, underscore, and hyphen. Examples: `Person:0`, `Task-12:5`.

Malformed identifier literals SHALL be rejected.

Floating point literals SHALL be rejected.

Null literals SHALL be rejected.

---

## IR-012 Pattern Matching

Patterns define match generation.

Supported pattern kinds (as defined in Kernel SPEC 008):

```text
Binding
Edge
Existence
Let
Collection
Condition
```

Example (Binding):

```json
{
  "kind": "Binding",
  "variable": "p",
  "type": "Person"
}
```

Example (Edge):

```json
{
  "kind": "Edge",
  "edge_type": "Friendship",
  "from": "a",
  "to": "b"
}
```

Example (Condition):

```json
{
  "kind": "Condition",
  "expression": ...
}
```

Patterns SHALL be deterministic. `Let` bindings within patterns are permitted (Kernel SPEC 008) – they are evaluated during discovery, immutable, and excluded from match identity.

---

## IR-013 Constraints

Example:

```json
{
  "kind": "Constraint",
  "expression": {
    "kind": "Less",
    "left": {
      "kind": "FieldAccess",
      "variable": "p",
      "field": "age"
    },
    "right": {
      "kind": "Literal",
      "type": "Integer",
      "value": 100
    }
  }
}
```

---

## IR-014 Rule Definitions

Every rule SHALL possess:

```json
{
  "rule_id": "AgePerson",
  "priority": 100,
  "pattern": [],
  "actions": []
}
```

- `rule_id` SHALL be globally unique.
- `priority` corresponds to the rule’s `base_priority` as defined in Kernel SPEC 012. Global scaling factors (`priority_scale`, `fairness_scale`) are kernel configuration parameters and are not represented in Canonical IR.

---

## IR-015 Actions

Canonical IR supports exactly the six actions defined in Kernel SPEC 013:

```text
CreateNode
CreateEdge
UpdateField
DeleteNode
DeleteEdge
EmitEvent
```

No other action kinds exist.

Control‑flow constructs (`If`, `ForEach`) and local bindings (`Let`) SHALL NOT appear as actions. Any IR containing them is invalid.

Unknown action kinds SHALL be rejected.

---

## IR-016 Dependency Model

Dependencies SHALL be represented explicitly.

Supported dependency categories (matching Kernel SPEC 010):

```text
NodeExistence      # instance-level
EdgeExistence      # instance-level
Field
Predicate
Extent             # type-level
Ordering
EdgePredicate
EdgeOrdering
EdgeType
Adjacency          # instance-level with direction
```

---

## IR-017 Events

Events SHALL be deterministic.

Example:

```json
{
  "action": "EmitEvent",
  "event_type": "PersonAged",
  "payload": {
    "person": {
      "kind": "Variable",
      "name": "p"
    }
  }
}
```

Sampling SHALL NOT exist.
Probabilistic emission SHALL NOT exist.

**Dependency extraction:** Expressions inside `EmitEvent` payloads SHALL participate in dependency extraction. Dependencies SHALL be collected during discovery even if the transaction is later rejected. Therefore `EmitEvent` payload expressions contribute to observable reads.

---

## IR-018 Canonical Serialization

Canonical IR SHALL serialize as UTF-8 JSON.

Objects SHALL:

* Use lexicographically sorted keys
* Contain no duplicate keys

Arrays SHALL:

* Preserve declared ordering

Strings SHALL:

* Be encoded as UTF-8

Integers SHALL:

* Use canonical decimal representation
* Not contain leading zeros except for zero itself

Booleans SHALL be encoded as `true` or `false`.

Floating point values SHALL NOT appear.
Null values SHALL NOT appear.

**Round‑trip stability:** Parsing a valid Canonical IR document and immediately reserializing it SHALL produce an identical byte sequence.

Canonical serialization SHALL produce identical byte sequences across conformant implementations.

---

## IR-019 Validation Rules

A Canonical IR document SHALL be rejected if any of the following occur:

* Duplicate type names
* Duplicate rule identifiers
* Duplicate function identifiers
* Unknown type references
* Unknown field references
* Unknown expression kinds
* Unknown action kinds
* Unknown dependency kinds
* Invalid function signatures
* Invalid identifier syntax (including malformed identifier literals)
* Cyclic type definitions
* Floating point values
* Null values
* Non-deterministic function declarations
* **Under-declared effect function dependencies**
* **Ordering operations applied to non-orderable types** (per Kernel SPEC 002)
* **Temporary handles used in `UpdateField`** (Kernel SPEC 013)
* **Temporary handles used in `EmitEvent` payloads** (Kernel SPEC 013)
* **Recursive function definitions** (direct or mutual – Kernel SPEC 005)
* **`FixedPoint` addition or subtraction with mismatched scales** (Kernel SPEC 001)
* **Control‑flow actions (`If`, `ForEach`) or `Let` actions** – only the six primitive actions are allowed
* **EmitEvent payload expressions that are not pure or introduce undeclared reads**

Validation SHALL occur before execution.

---

## IR-020 Conformance

A conformant compiler SHALL:

* Produce valid Canonical IR
* Produce deterministic output
* Produce canonical serialization

A conformant engine SHALL:

* Accept valid Canonical IR
* Reject invalid Canonical IR
* Execute according to the GRISP Deterministic Kernel Specification v0.29

Observable behavior SHALL be identical across conformant engines.

---

## IR-021 Identifier Rules

Grammar for variable, function, and rule identifiers:

```text
Identifier ::= [A-Za-z_][A-Za-z0-9_]*
```

Identifiers SHALL be:

* Case-sensitive
* UTF-8 encoded
* Non-empty

The following identifiers SHALL be globally unique within a manifest:

* Type names
* Function identifiers
* Rule identifiers

Duplicate identifiers SHALL be rejected.

Identifiers beginning with `__grisp_` are reserved.

> Note: The `TypeName` portion of an identifier literal (e.g., `Task-12:5`) follows the Kernel’s type name grammar, which allows hyphens. That is a distinct syntactic context.

---

## IR-022 Type Grammar

Formal grammar:

```text
Type ::=
    Boolean
  | Integer
  | String
  | Identifier
  | FixedPoint(Integer)
  | List<Type>
  | Map<String,Type>
```

Restrictions:

* No `Set<T>`
* No floating point types
* No null type

`FixedPoint` scale SHALL be ≥ 0.

`FixedPoint` arithmetic rules (per Kernel SPEC 001):

* Addition/Subtraction: scales must match (otherwise invalid IR)
* Multiplication: result scale = left scale + right scale
* Division: result scale = dividend scale

Examples:
- `FixedPoint(2) + FixedPoint(2)` – valid
- `FixedPoint(2) + FixedPoint(3)` – invalid (rejected)

---

## IR-023 Function Signature Rules

Every function SHALL define:

* `function_id`
* `kind`
* `parameters`
* `return_type`

Function parameter names SHALL be unique.

Function kinds SHALL be `pure` or `effect_deterministic`.

Functions SHALL NOT:

* Access system time
* Generate random values
* Access implementation-specific state

Effect-deterministic functions SHALL declare required observable reads.

Recursive functions (direct or mutual) SHALL be rejected.

---

## IR-024 Complete Expression Catalog

Defined expression kinds:

| Category | Kinds |
|----------|-------|
| Literals | `Literal` |
| References | `Variable`, `FieldAccess` |
| Calls | `FunctionCall` |
| Arithmetic | `Add`, `Subtract`, `Multiply`, `Divide`, `Modulo` |
| Comparison | `Equal`, `NotEqual`, `Less`, `LessEqual`, `Greater`, `GreaterEqual` |
| Boolean | `And`, `Or`, `Not` |
| Conditional | `Conditional` |
| Collection | `MapLiteral`, `Array` |

`MapLiteral` constructs a `Map<String,V>`. The order of entries in a `MapLiteral` is not semantically meaningful; execution SHALL NOT depend on it. Canonical serialization orders keys lexicographically (IR-018).

Expression trees SHALL be immutable.

Expression evaluation SHALL be deterministic.

---

## IR-025 Pattern Semantics

Supported pattern kinds (normative mapping to Kernel SPEC 008):

* `Binding` – matches a node of a given type, binds variable
* `Edge` – matches an edge between two bound nodes
* `Existence` – tests existence without binding
* `Let` – local pure computation within pattern (excluded from match identity)
* `Collection` – iterates over a collection (e.g., adjacency)
* `Condition` – boolean constraint

Pattern evaluation SHALL NOT depend upon runtime ordering except where explicitly defined by the Kernel (e.g., ascending node/edge ID enumeration).

---

## IR-026 Action Semantics

Canonical actions (mapping to Kernel SPEC 013, SPEC 014, SPEC 015):

* `CreateNode(type, fields)` – stages node creation
* `CreateEdge(type, source, target, fields)` – stages edge creation
* `UpdateField(element, field, value)` – stages field update (no‑op if value unchanged)
* `DeleteNode(node)` – stages node deletion (automatically deletes incident edges)
* `DeleteEdge(edge)` – stages edge deletion
* `EmitEvent(event_type, payload)` – stages event emission

**Commit order** (Kernel SPEC 015) SHALL be:

1. `CreateNode`
2. `CreateEdge`
3. `UpdateField`
4. `DeleteEdge`
5. `DeleteNode`

The order of actions in the IR SHALL NOT alter commit semantics; the engine reorders according to the above.

**Temporary handles** (from `CreateNode`/`CreateEdge`) SHALL NOT appear in `UpdateField` targets or `EmitEvent` payloads. Any IR violating this is invalid.

**Event payload dependency extraction** occurs during discovery, before validation or commit.

---

## IR-027 Complete Dependency Catalog

Each dependency maps to a Kernel version counter (SPEC 010). The JSON representation uses the fields shown below.

### NodeExistence (instance-level)
```json
{ "dependency": "NodeExistence", "node": "p" }
```
`node` is a variable bound to a specific node identifier.

### EdgeExistence (instance-level)
```json
{ "dependency": "EdgeExistence", "edge": "e" }
```
`edge` is a variable bound to a specific edge identifier.

### Field
```json
{ "dependency": "Field", "element": "p", "field": "age" }
```
`element` is a variable referring to a node or edge.

### Predicate (node field predicate)
```json
{ "dependency": "Predicate", "type": "Person", "field": "age" }
```

### Extent (type‑wide presence)
```json
{ "dependency": "Extent", "type": "Person" }
```

### Ordering (node ordering dependency)
```json
{ "dependency": "Ordering", "type": "Person", "field": "age" }
```
Required for `min`, `max`, `sort` over nodes.

### EdgePredicate
```json
{ "dependency": "EdgePredicate", "edge_type": "Friendship", "field": "strength" }
```

### EdgeOrdering
```json
{ "dependency": "EdgeOrdering", "edge_type": "Friendship", "field": "strength" }
```

### EdgeType (edge set membership)
```json
{ "dependency": "EdgeType", "edge_type": "Friendship" }
```

### Adjacency (instance-level, with direction)
```json
{ "dependency": "Adjacency", "node": "p", "edge_type": "Friendship", "direction": "outgoing" }
```
Allowed directions: `"incoming"`, `"outgoing"`.

---

## IR-028 IR Invariants

The following invariants SHALL hold:

* **Determinism** – Identical IR and identical input state produce identical observable behavior.
* **Explicitness** – All executable behavior is represented explicitly.
* **Canonicality** – Equivalent IR documents serialize identically.
* **Type Safety** – All field references resolve to declared fields.
* **Dependency Completeness** – All observable reads are represented through the dependency model.
* **Stable Identity** – Type, function, and rule identifiers remain stable across serialization.

Violation of any invariant renders the IR invalid.
