## Part 2: BNF for Expressions (Simplified)

```bnf
<expression> ::= <literal>
               | <variable>
               | <field-access>
               | <function-call>
               | <arithmetic>
               | <comparison>
               | <boolean>
               | <conditional>
               | <map-literal>
               | <array-literal>

<literal> ::= { "kind": "Literal", "type": "Boolean", "value": <boolean> }
            | { "kind": "Literal", "type": "Integer", "value": <integer> }
            | { "kind": "Literal", "type": "String", "value": <string> }
            | { "kind": "Literal", "type": "Identifier", "value": <identifier-literal> }

<variable> ::= { "kind": "Variable", "name": <identifier> }

<field-access> ::= { "kind": "FieldAccess", "variable": <identifier>, "field": <identifier> }

<function-call> ::= { "kind": "FunctionCall", "function": <identifier>, "arguments": [ <expression>* ] }

<arithmetic> ::= { "kind": "Add" | "Subtract" | "Multiply" | "Divide" | "Modulo", "left": <expression>, "right": <expression> }

<comparison> ::= { "kind": "Equal" | "NotEqual" | "Less" | "LessEqual" | "Greater" | "GreaterEqual", "left": <expression>, "right": <expression> }

<boolean> ::= { "kind": "And" | "Or", "left": <expression>, "right": <expression> }
            | { "kind": "Not", "operand": <expression> }

<conditional> ::= { "kind": "Conditional", "condition": <expression>, "then": <expression>, "else": <expression> }

<map-literal> ::= { "kind": "MapLiteral", "entries": { <string>: <expression> (, <string>: <expression>)* } }

<array-literal> ::= { "kind": "Array", "elements": [ <expression> (, <expression>)* ] }

<identifier> ::= [A-Za-z_][A-Za-z0-9_]*
<identifier-literal> ::= <type-name> ":" [0-9]+
<type-name> ::= [A-Za-z_][A-Za-z0-9_-]*
<boolean> ::= true | false
<integer> ::= -?[0-9]+ (no leading zeros except single 0)
<string> ::= " ( [^"\\\x00-\x1F\x7F] | \\[\\"nrt] | \\u[0-9A-F]{4} )* "
```

### Patch to Appendix C (Counter Optimization Guidance) — normative edits applied

**Insert the following edits into Appendix C (replace the corresponding paragraphs):**

**C.1 Observable Invariants (amended)**  
All invariants in this appendix apply to the **post‑commit state** that becomes visible at the tick commit boundary. Engines MAY perform internal optimizations, batching, or epoching, but they MUST ensure that the final absolute counter values observable after commit are identical to those produced by a dense, eager implementation that applied operations in canonical commit order. Engines SHALL NOT rely on or expose intermediate counter values produced inside a tick; intermediate state within a tick is not observable to dependency validation or match discovery.

**C.2.5 On‑Demand Materialization (amended)**  
Materialization MUST be performed over the **discovery snapshot** captured at the start of the tick (the pre‑commit state) combined with the deterministic effects of the candidate transaction. Materialization MUST NOT consult or depend on any live state that is outside the discovery snapshot or on concurrent speculative changes. Materialization must occur **before** dependency validation completes and **before** the tick’s golden file record is written.

**C.2.2 Batched Increments (amended)**  
Batched increments are permitted provided they are applied atomically at commit time and are visible only at the tick commit boundary. Batches must be applied in a way that preserves the final post‑commit counter vector and must not change validation outcomes for the committing match. In particular, batched application must not make any increment visible prior to the tick commit boundary.

**C.3 Prohibited Optimizations (amended)**  
Replace the ambiguous reordering clause with the following normative rule:  
> Reordering of counter increments across different dependency categories is forbidden **unless** the final post‑commit counter vector is identical to the reference execution model defined by applying the canonical commit order (Kernel SPEC 015). Any reordering that would produce a different final counter vector or different validation outcome is prohibited.

**C.2.2 / C.3 cumulative increments clarification (amended)**  
All counter increments produced by operations within a transaction are **cumulative** and SHALL be reflected in the final post‑commit counters even if the created element does not persist in the final state (for example, an edge created and then auto‑deleted in the same transaction). Engines MUST account for both creation and deletion increments in the final counter values.

**Cross‑reference**  
Appendix C normative rules reference and defer to **IR‑017.5 Runtime Visibility Model** for snapshot and visibility semantics; IR‑017.5 is authoritative for materialization timing and snapshot lifetime.

# Helper: canonicalize with UTF-8 bytewise key ordering
def canonicalize(obj):
    def sort_key(k):
        return k.encode('utf-8')
    def _canonical(o):
        if isinstance(o, dict):
            items = sorted(o.items(), key=lambda kv: sort_key(kv[0]))
            return '{' + ','.join(f'{json.dumps(k, ensure_ascii=False)}:{_canonical(v)}' for k,v in items) + '}'
        if isinstance(o, list):
            return '[' + ','.join(_canonical(e) for e in o) + ']'
        return json.dumps(o, ensure_ascii=False)
    return _canonical(obj)

def load_json_file(path):
    with open(path, 'rb') as f:
        raw = f.read()
    try:
        parsed = json.loads(raw.decode('utf-8'))
    except Exception as e:
        print("ERROR: failed to parse engine output JSON:", e)
        sys.exit(2)
    return parsed

def strip_non_normative(obj):
    if isinstance(obj, dict):
        return {k: strip_non_normative(v) for k,v in obj.items() if k not in ("metadata","diagnostic","timestamp","engine_version")}
    if isinstance(obj, list):
        return [strip_non_normative(e) for e in obj]
    return obj

    engine_canon = canonicalize(strip_non_normative(engine_obj))
    if engine_canon == canonical_str:
        return True, None
    return False, (engine_canon, canonical_str)
