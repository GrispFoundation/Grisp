# GRISP DETERMINISTIC KERNEL SPECIFICATION v0.22

## SPEC 000 CORE PRINCIPLES

The GRISP Deterministic Kernel defines a fully deterministic execution model for rule-driven state transitions over a typed graph.

For identical Canonical IR and identical initial state, all conformant engines must produce identical observable behavior.

Observable behavior consists solely of:

* Committed state transitions
* Emitted events
* Golden file output

All other implementation details are non-normative.

The kernel is governed by the following principles:

1. **Determinism** – All observable behavior must be deterministic. Forbidden: floating point arithmetic, random number generation, system time, memory addresses, pointer identity, thread scheduling, hash‑based ordering, runtime metadata, engine‑specific behavior.

2. **Explicitness** – All reads, writes, dependencies, identifiers, ordering rules, and version counters must be explicitly represented. No implicit reads are permitted.

3. **Frozen Discovery** – Match discovery occurs exactly once per tick. The resulting discovery snapshot is immutable for the remainder of the tick.

4. **Dependency Validation** – Dependency validation is the sole correctness mechanism. Conflict detection does not exist.

5. **Single Commit** – At most one transaction may commit per tick.

6. **Canonical Ordering** – Every ordered operation must have an explicitly defined deterministic ordering.

7. **Canonical Serialization** – All deterministic artifacts must serialize canonically.

8. **Referential Transparency** – Expressions are pure. Actions are effectful only during commit.

9. **No Identifier Reuse** – Identifiers are unique for the lifetime of the graph. Deleted identifiers must never be reused.

10. **Cross-Engine Reproducibility** – All conformant engines must produce identical golden files.

---

## SPEC 001 NUMERIC MODEL

All numeric values are signed 64‑bit integers. Floating point values forbidden.

Fixed‑point values are represented as scaled integers. Scale factors must be explicitly declared.

Division uses truncation toward zero.

Modulo uses standard signed integer remainder semantics.

Arithmetic overflow is a fatal conformance error.

**No‑Op Arithmetic** – Arithmetic operations that produce a result equal to the existing value are valid. However, write operations that do not change observable state are treated as No‑Op Updates as defined in SPEC 015.

The following counters must never overflow (overflow is fatal):

* `tick_counter`
* sequence counters (per type)
* `match_age`
* `existence_version` (node and edge)
* `field_version`
* `predicate_version`
* `ordering_version`
* `extent_version`
* `edge_type_version`
* `adjacency_version`

---

## SPEC 002 TYPE SYSTEM

The type system defines: Node Types, Edge Types, Field Types. All types must be explicitly declared. Type inference is forbidden.

Allowed field types: `Integer`, `FixedPoint`, `Boolean`, `String`, `List`, `Map`, `Identifier`.

Fields must be deterministic and serializable.

Runtime handles, pointers, references, and engine‑specific objects are forbidden.

**String Semantics** – Strings are immutable Unicode text. Serialization uses UTF‑8. String comparison uses binary Unicode code point ordering. String equality is exact code point equality. Unicode normalization is not performed. Case folding is not performed. All engines must compare strings identically.

**Map Semantics** – Map keys must be strings. Map key uniqueness is determined using exact string equality. Map iteration order is undefined. Canonical serialization of maps is defined by SPEC 018.

---

## SPEC 003 IDENTIFIER MODEL

Identifiers are deterministic strings.

Node identifier format: `type_name:sequence`

Edge identifier format: `type_name:sequence`

Sequence counters are maintained independently for each type.

Sequence counters:

* start at 0
* increment monotonically (by exactly 1 each allocation)
* never decrease
* never wrap
* are never reused

Identifier allocation occurs only during commit.

Identifier ordering is defined as:

1. `type_name` lexicographic ascending (Unicode code point order)
2. `sequence` numeric ascending

This defines global identifier ordering.

Whenever the specification refers to “ascending node_id” or “ascending edge_id”, it refers to identifier ordering defined herein.

---

## SPEC 004 STATE MODEL

Deterministic state consists of: Nodes, Edges, Version Counters, Sequence Counters, Tick Counter.

**Node** consists of:

* `id`
* `type`
* `fields`
* `existence_version` (positive integer, defined only while node exists)
* `field_versions` (one counter per field, defined while node exists)

**Edge** consists of:

* `id`
* `type`
* `source`
* `target`
* `fields`
* `field_versions`
* `existence_version` (positive integer, defined only while edge exists)

The state contains the following global version counters:

* `extent_version[node_type]`
* `predicate_version[node_type][field_name]`
* `ordering_version[node_type][field_name]`
* `edge_type_version[edge_type]`
* `adjacency_version[node_id][edge_type][direction]` where direction is `incoming` or `outgoing`

All version counters **begin at 1**.

**Initial State Version Assignment** – For every node and edge present in the initial state (as defined in Canonical IR):
- `existence_version = 1`
- `field_versions[field] = 1` for each field
- Global counters are set to 1 (they start at 1, no extra increment). The initial state is treated as if it had been created before the first tick, with all version counters at base value.

State invariants (must hold after commit):

* Node identifiers unique
* Edge identifiers unique
* No dangling edges (every edge’s source and target refer to existing nodes)
* All fields type‑valid
* All constraints satisfied

---

## SPEC 005 CANONICAL IR

Canonical IR is the sole executable representation of a GRISP manifest.

All manifests must compile into Canonical IR before execution.

Canonical IR contains:

* Type Definitions
* Function Definitions
* Rule Definitions
* Initial State
* Constants

Canonical IR must contain:

* No syntactic sugar
* No implicit defaults
* No runtime metadata
* No engine‑specific structures

**Rule Identifier Stability** – Every rule definition must contain an explicit `rule_id`. `rule_id` values must be unique, stable, preserved by serialization. Compilers must not generate rule identifiers. Rule ordering within source manifests must not affect rule identity.

Canonical IR must be stable under round‑trip serialization. Parsing and re‑serializing Canonical IR must produce identical output.

**Function Termination** – Recursive function definitions (direct or mutual) are forbidden. There are no iterative constructs in the expression language (no `while`, `for`, or `loop`). Therefore all functions terminate by construction. Implementations must reject any function that contains recursion or any form of non‑structural iteration.

---

## SPEC 006 FUNCTION MODEL

Functions are either `pure` or `effect_deterministic`.

**Pure functions:**
- referentially transparent
- may only depend on arguments
- may not read state

**effect_deterministic functions:**
- referentially transparent
- may read state
- may not modify state

**Declared Reads** – Every `effect_deterministic` function must declare `declared_reads`. `declared_reads` specifies a **conservative superset** of all dependency types that may be read during function evaluation. Under‑declaration (missing a dependency that is actually read) is a conformance error. Over‑declaration (declaring a dependency that is never read) is permitted. Dependency extraction must include all `declared_reads`. Declared reads participate in dependency validation identically to directly extracted dependencies.

No recursion (SPEC 005). No nondeterministic functions.

---

## SPEC 007 EXPRESSION MODEL

Expressions represent pure computation.

Expressions may contain: literals, bindings, arithmetic, boolean logic, collection expressions, function calls.

Expressions must not: mutate state, allocate identifiers, observe runtime metadata, observe events, perform nondeterministic operations.

Short‑circuit evaluation is permitted.

Dependency extraction must analyze all branches.

---

## SPEC 008 PATTERN MODEL

Patterns bind graph elements. Pattern evaluation is deterministic.

Node enumeration uses ascending `node_id` ordering. Edge enumeration uses ascending `edge_id` ordering.

Pattern constraints may use expressions. Patterns may contain `let` bindings.

`let` bindings:
- are evaluated during discovery
- are immutable
- do **not** participate in match identity

Pattern evaluation must not mutate state.

---

## SPEC 009 MATCH DISCOVERY MODEL

Discovery occurs exactly once per tick. Produces a frozen snapshot.

A match consists of:
- `rule_id`
- `bindings`
- `let_values`
- `dependencies`
- `dependency_snapshot`
- `match_key`

Match discovery must not:
- mutate state
- allocate identifiers
- observe runtime metadata
- observe events

Match identity is defined by `match_key`. `match_key` consists of `rule_id` + `bindings`. Bindings are serialized as `name=identifier`. Binding names are sorted lexicographically. `let` values are excluded from match identity.

---

## SPEC 010 DEPENDENCY MODEL

**Dependency types** are:

* `NodeExistence(node_id)`
* `EdgeExistence(edge_id)`
* `Field(element_id, field_name)`
* `Predicate(node_type, field_name)`
* `Ordering(node_type, field_name)`
* `Extent(node_type)`
* `EdgeType(edge_type)`
* `Adjacency(node_id, edge_type, direction)`

**Dependency extraction** is mandatory for:
- patterns
- `where` clauses
- `let` expressions
- priority expressions
- action argument expressions
- event payload expressions
- function `declared_reads`

Dependency extraction must analyze all branches. Dependency extraction must be **complete** (no under‑approximation). Over‑approximation is permitted.

**Aggregate Dependency Rules** – For any aggregate operation (e.g., `count`, `sum`, `min`, `max`, `sort`), dependency extraction must include all dependencies capable of affecting the aggregate result, including dependencies required by:
- source enumeration (e.g., `Extent` for node sets, `Adjacency` for edges)
- filtering predicates
- projection expressions
- ordering expressions

Examples:

| Aggregate | Required dependencies |
|-----------|----------------------|
| `count(Person)` | `Extent(Person)` |
| `sum(Person.age)` | `Extent(Person)`, `Predicate(Person, age)` |
| `min(Person.age)`, `max(Person.age)` | `Extent(Person)`, `Ordering(Person, age)` |
| `sort(Person by age)` | `Extent(Person)`, `Ordering(Person, age)` |
| `sum(Person.age where Person.active = true)` | `Extent(Person)`, `Predicate(Person, age)`, `Predicate(Person, active)` |

**Validation mapping**:

| Dependency | Maps to version counter |
|------------|------------------------|
| `NodeExistence(node_id)` | `existence_version` of that node (if node exists) |
| `EdgeExistence(edge_id)` | `existence_version` of that edge (if edge exists) |
| `Field(element_id, field_name)` | `field_versions[field_name]` on that node/edge |
| `Predicate(node_type, field_name)` | `predicate_version[node_type][field_name]` |
| `Ordering(node_type, field_name)` | `ordering_version[node_type][field_name]` |
| `Extent(node_type)` | `extent_version[node_type]` |
| `EdgeType(edge_type)` | `edge_type_version[edge_type]` |
| `Adjacency(node_id, edge_type, direction)` | `adjacency_version[node_id][edge_type][direction]` |

A match validates **iff** every dependency version equals its snapshot version **and** every existence dependency (`NodeExistence`, `EdgeExistence`) still refers to an existing element.

No additional correctness mechanism exists.

---

## SPEC 011 MATCH LIFECYCLE MODEL

Matches persist across ticks through `match_key` identity.

Define `match_age` recursively:

- If the `match_key` was **not** present in the previous tick’s match set → new match: `age = 0`
- If the `match_key` **was** present in the previous tick → `age = previous_age + 1`

**Forgetting** – Only the immediate previous tick matters. If a match disappears for one or more ticks and later reappears, it is treated as a new match (`age = 0`). There is no long‑term memory.

`match_age` overflow is a fatal conformance error.

---

## SPEC 012 SELECTION MODEL

Selection operates exclusively on the discovery snapshot.

For each match: `score = (base_priority × priority_scale) + (match_age × fairness_scale)`

All calculations use signed 64‑bit arithmetic. Overflow is a fatal conformance error.

Matches are ordered by:
1. `score` descending
2. `match_key` ascending (using canonical serialized byte order as defined in SPEC 018)

Selection must not mutate state, allocate identifiers, or perform validation.

---

## SPEC 013 ACTION MODEL

Action evaluation occurs after successful dependency validation. Action evaluation is pure. Actions may not mutate state, allocate identifiers, or introduce new reads.

Permitted actions: `CreateNode`, `CreateEdge`, `UpdateField`, `DeleteEdge`, `DeleteNode`, `EmitEvent`.

All expressions contained within action arguments participate in dependency extraction.

**Action Consistency** – Action evaluation produces a **staged transaction**. The staged transaction must satisfy all transaction validity rules (SPEC 014) **before** commit begins. Invalid staged transactions are rejected. Rejection behaves identically to dependency validation failure: no state changes, no events published.

---

## SPEC 014 TRANSACTION MODEL

A transaction consists of:
1. dependency validation
2. action evaluation
3. write staging
4. staged transaction validation
5. commit
6. event publication

Only one transaction may commit per tick.

If validation fails (dependency validation **or** staged transaction validation), the candidate match is discarded and the next ranked match is considered.

**Staged Transaction Validation** – Before commit ordering is applied, the staged transaction is validated as a whole. The staged transaction must satisfy:

- **Existing target validity** – `UpdateField`, `DeleteNode`, `DeleteEdge` targets must exist.
- **Creation validity** – `CreateEdge` source and target nodes must exist **after** transaction application (i.e., they must be either pre‑existing or created by `CreateNode` earlier in the same transaction).
- **No dangling references** – The resulting committed state must contain no dangling edges.
- **State invariants** – All state invariants defined by SPEC 004 must hold after commit.

Failure of any staged transaction validation causes transaction rejection.

---

## SPEC 015 COMMIT MODEL

Commit applies staged writes atomically. Partial commit is forbidden.

Commit order is:
1. `CreateNode`
2. `CreateEdge`
3. `UpdateField`
4. `DeleteEdge`
5. `DeleteNode`

Identifier allocation occurs during `CreateNode` and `CreateEdge` processing.

`DeleteNode` automatically stages deletion of all incident edges. Incident edges are determined using the **pre‑commit state plus any staged edge creations** in the same transaction (i.e., the view of the graph after applying all staged creates, but before deletes). This ensures deterministic edge removal.

**No‑Op Updates** – `UpdateField` is a No‑Op Update when `new_value == existing_value` using exact type equality. No‑Op Updates: do not modify state, do not increment `field_versions`, `predicate_version`, or `ordering_version`. Ignored during commit.

**Predicate Version Semantics** – `predicate_version[node_type][field_name]` increments on node creation, node deletion, and field update producing a changed value (regardless of whether any rule references the field). No‑Op excluded.

**Ordering Version Semantics** – similarly increments on node creation, node deletion, and field update producing a changed value. No‑Op excluded.

**Transaction Write Validity** – A staged transaction must not contain operations whose targets cease to exist within the same transaction. The following are **invalid**:

- `UpdateField(X)` followed by `DeleteNode(X)`
- `UpdateField(E)` followed by `DeleteEdge(E)`
- `DeleteNode(X)` followed by another `DeleteNode(X)`
- `DeleteEdge(E)` followed by another `DeleteEdge(E)`
- `CreateNode(X)` followed by `DeleteNode(X)` (create‑then‑delete same node)
- `CreateEdge(E)` followed by `DeleteEdge(E)` (create‑then‑delete same edge)

Transaction validation must reject such staged transactions.

**Version increment summary** (changed values only, No‑Op excluded):

| Operation | `extent_version` | `predicate_version` | `ordering_version` | `edge_type_version` | `adjacency_version` | `existence_version` (node) | `existence_version` (edge) | `field_versions` |
|-----------|------------------|---------------------|--------------------|----------------------|---------------------|----------------------------|----------------------------|------------------|
| `CreateNode` | +1 (node_type) | +1 (all fields) | +1 (all fields) | – | – | set to 1 | – | set to 1 each |
| `DeleteNode` | +1 | +1 (all fields) | +1 (all fields) | – | +1 per incident edge (both dirs, per edge_type) | (removed) | – | – |
| `CreateEdge` | – | – | – | +1 | +1 source.out, target.in (per edge_type) | – | set to 1 | set to 1 each |
| `DeleteEdge` | – | – | – | +1 | +1 source.out, target.in (per edge_type) | – | (removed) | – |
| `UpdateField` (node field, changed) | – | +1 (that field) | +1 (that field) | – | – | – | – | +1 (that field) |
| `UpdateField` (edge field, changed) | – | – | – | – | – | – | – | +1 (that field) |

Commit must preserve all state invariants.

---

## SPEC 016 EVENT MODEL

Events are deterministic outputs. Events consist of `rule_id` and payload.

Events become visible only after successful commit.

Event payload expressions:
- are pure
- participate in dependency extraction
- may not introduce new reads

Events must not influence matching or execution.

---

## SPEC 017 TICK MODEL

Tick execution proceeds:

1. Increment `tick_counter`
2. Discover matches (frozen snapshot)
3. Compute scores
4. Rank matches
5. Select candidate
6. Validate dependencies
7. If invalid, continue ranking
8. If valid, evaluate actions
9. Validate staged transaction
10. If invalid, continue ranking
11. Commit transaction
12. Publish events
13. End tick

Discovery occurs exactly once. Rediscovery within a tick is forbidden. At most one transaction may commit.

---

## SPEC 018 CANONICAL SERIALIZATION

Canonical serialization uses:
- UTF‑8 encoding
- LF line endings
- lexicographically sorted object keys
- deterministic list ordering
- canonical integer encoding

Integers: base 10, no leading zeros, minus sign only for negative values.

Strings: serialized exactly, no normalization, UTF‑8 encoded.

**Recursive canonicalization** applies to all nested values (e.g., maps inside lists, lists inside maps). For maps, keys are sorted lexicographically by UTF‑8 byte order.

Round‑trip serialization must produce byte‑identical output.

All deterministic artifacts must use canonical serialization, including: Canonical IR, Golden Files, Conformance Outputs.

---

## SPEC 019 GOLDEN FILE MODEL

Golden files capture observable behavior only.

Normative fields:
- `initial_state`
- `ticks`
- `final_state`

Each tick contains:
- `tick_number`
- `selected_match_key`
- `committed_changes`
- `events`

Diagnostic information is non‑normative. If present, diagnostics must be ignored for conformance.

---

## SPEC 020 CONFORMANCE

A conformant engine must:
- implement every normative rule
- reject invalid Canonical IR
- prohibit nondeterminism
- prohibit floating point arithmetic
- prohibit identifier reuse
- prohibit counter overflow

For identical Canonical IR and initial state, all conformant engines must produce identical:
- committed changes
- emitted events
- final state
- golden files

Conformance is determined exclusively through observable behavior defined by this specification.
