# GRISP DETERMINISTIC KERNEL SPECIFICATION v0.24

## SPEC 000 CORE PRINCIPLES

The GRISP Deterministic Kernel defines a fully deterministic execution model for rule-driven state transitions over a typed graph.

For identical Canonical IR and identical initial state, all conformant engines must produce identical observable behavior.

Observable behavior consists solely of:

* Committed state transitions
* Emitted events
* Golden file output

All other implementation details are non-normative.

The kernel is governed by the following principles:

1. **Determinism** – All observable behavior must be deterministic. Forbidden: floating point arithmetic, random number generation, system time, memory addresses, pointer identity, thread scheduling, hash‑based ordering, runtime metadata, engine‑specific behavior.

2. **Explicitness** – All reads, writes, dependencies, identifiers, ordering rules, and version counters must be explicitly represented. No implicit reads are permitted.

3. **Frozen Discovery** – Match discovery occurs exactly once per tick. The resulting discovery snapshot is immutable for the remainder of the tick.

4. **Dependency Validation** – Dependency validation is the sole correctness mechanism. Conflict detection does not exist.

5. **Single Commit** – At most one transaction may commit per tick.

6. **Canonical Ordering** – Every ordered operation must have an explicitly defined deterministic ordering.

7. **Canonical Serialization** – All deterministic artifacts must serialize canonically.

8. **Referential Transparency** – Expressions are pure. Actions are effectful only during commit.

9. **No Identifier Reuse** – Identifiers are unique for the lifetime of the graph. Deleted identifiers must never be reused.

10. **Cross-Engine Reproducibility** – All conformant engines must produce identical golden files.

---

## SPEC 001 NUMERIC MODEL

All numeric values are signed 64‑bit integers. Floating point values forbidden. Fixed‑point as scaled integers, scale factors explicitly declared. Division truncates toward zero. Modulo standard remainder. Overflow fatal.

**No‑Op Arithmetic** – Arithmetic that yields existing value is valid; writes that don’t change state are No‑Op Updates (SPEC 015).

Counters that must never overflow (fatal): `tick_counter`, sequence counters, `match_age`, `existence_version` (node/edge), `field_version`, `predicate_version`, `ordering_version`, `extent_version`, `edge_type_version`, `adjacency_version`, `edge_predicate_version`, `edge_ordering_version`.

---

## SPEC 002 TYPE SYSTEM

**Type name grammar** – Type names follow the same character set as identifiers (SPEC 003) except that the colon (`:`) is **not** allowed. Thus type names are ASCII alphanumeric, underscore, hyphen; must start with letter or underscore. Case‑sensitive.

Allowed field types: `Integer`, `FixedPoint(scale)`, `Boolean`, `String`, `List`, `Map`, `Identifier`. `FixedPoint(scale)` must declare scale as non‑negative integer literal.

**Field mandatory semantics** – All declared fields are **mandatory**. Every node or edge must contain exactly the fields defined by its type, with no null values. The initial state and all updates must satisfy this.

**String Semantics** – Immutable Unicode. Serialization UTF‑8. Comparison binary Unicode code point order. Equality exact code point. No normalization, no case folding.

**List Semantics** – Homogeneous ordered list of same declared type. Equality element‑wise same order. Lexicographic ordering defined **iff** the element type is orderable (see below). Iteration order explicit.

**Map Semantics** – Keys must be strings. Uniqueness by exact string equality. Equality: two maps are equal iff they have the same set of keys and, for each key, the values are equal (recursively). Order of keys does not matter. Iteration order during execution undefined. Maps are **not orderable**. Canonical serialization orders keys lexicographically (UTF‑8 bytewise). Duplicate map keys in source IR or literals are **invalid**.

**Orderability** – A type `T` is orderable if it has a deterministic total order:
- `Integer`, `FixedPoint`, `Boolean`, `String`, `Identifier` are orderable.
- `List<T>` is orderable **iff** `T` is orderable.
- `Map` is not orderable.
Operations requiring ordering on non‑orderable types are **invalid IR**.

**Equality for compound types** – Equality for `List`, `Map`, and any nested combination (e.g., `Map<String, List<Integer>>`) is defined **recursively**: two values are equal if they have the same structure and all corresponding leaf values are equal per their type rules. This applies to No‑Op detection, golden file comparison, and match key construction.

**Empty field sets** – A node or edge type may declare zero fields. All version counters per field are vacuous; creation still increments `extent_version` etc. but no per‑field counters exist.

---

## SPEC 003 IDENTIFIER MODEL

Identifiers are deterministic strings conforming to the pattern: `[A-Za-z0-9_][A-Za-z0-9_:-]*` (ASCII alphanumeric, underscore, colon, hyphen; must not start with colon or hyphen). Colon is used only as separator between `type_name` and `sequence`.

Format: `type_name:sequence`

Sequence counters per type start at 0, increment monotonically by 1 each allocation, never decrease, never wrap, never reused. Allocation only during commit.

Identifier ordering:
1. `type_name` lexicographic ascending (ASCII bytewise – equivalent to Unicode code point for ASCII subset)
2. `sequence` numeric ascending

**Match key serialization** uses `name=identifier` – no escaping needed because identifiers contain no `=` or control characters.

---

## SPEC 004 STATE MODEL

Deterministic state consists of: Nodes, Edges, Version Counters, Sequence Counters, Tick Counter.

**Node**: `id`, `type`, `fields`, `existence_version` (positive integer, defined only while node exists), `field_versions` (one per field).

**Edge**: `id`, `type`, `source`, `target`, `fields`, `field_versions`, `existence_version` (positive integer, defined only while edge exists).

**Global version counters**:
- `extent_version[node_type]`
- `predicate_version[node_type][field_name]` (node fields)
- `ordering_version[node_type][field_name]` (node fields)
- `edge_predicate_version[edge_type][field_name]` (edge fields)
- `edge_ordering_version[edge_type][field_name]` (edge fields)
- `edge_type_version[edge_type]`
- `adjacency_version[node_id][edge_type][direction]` (direction = incoming/outgoing)

All version counters **begin at 1** in the initial state.

**Initial state version assignment** – For every node and edge in the initial state:
- `existence_version = 1`
- `field_versions[field] = 1` for each field
- Global counters set to 1. The initial state is treated as if created before the first tick, with all version counters at base value.

State invariants: unique IDs, no dangling edges, type‑valid fields, all constraints satisfied.

---

## SPEC 005 CANONICAL IR

Canonical IR is the sole executable representation. All manifests compile into it.

Canonical IR contains: Type Definitions, Function Definitions, Rule Definitions, Initial State, Constants.

Canonical IR must contain: No syntactic sugar, no implicit defaults, no runtime metadata, no engine‑specific structures.

**Rule Identifier Stability** – Every rule definition must contain an explicit `rule_id`. `rule_id` must be unique, stable, preserved by serialization. Compilers must not generate rule identifiers.

**Function Termination** – Recursive function definitions (direct or mutual) forbidden. The expression language has no iterative constructs (`while`, `for`). Therefore all functions terminate by construction. Implementations must reject any function containing recursion.

Round‑trip serialization must be byte‑identical.

---

## SPEC 006 FUNCTION MODEL

Functions are `pure` or `effect_deterministic`.

**Pure**: referentially transparent, only arguments, no state read.

**effect_deterministic**: referentially transparent, may read state, may not modify state.

**Declared Reads** – Every `effect_deterministic` function must declare `declared_reads`, a **conservative superset** of all dependency types that may be read. Under‑declaration error, over‑declaration permitted. Dependency extraction includes `declared_reads`.

No recursion, no nondeterministic functions.

---

## SPEC 007 EXPRESSION MODEL

Expressions represent pure computation. May contain: literals, bindings, arithmetic, boolean logic, collection expressions, function calls. Must not: mutate state, allocate IDs, observe metadata/events, nondeterministic ops. Short‑circuit allowed. Dependency extraction analyzes all branches.

---

## SPEC 008 PATTERN MODEL

Patterns bind graph elements deterministically. Node enumeration ascending `node_id`, edge enumeration ascending `edge_id`. Constraints may use expressions. May contain `let` bindings (evaluated during discovery, immutable, excluded from match identity). No mutation.

---

## SPEC 009 MATCH DISCOVERY MODEL

Discovery once per tick, frozen snapshot. Match contains: `rule_id`, `bindings`, `let_values`, `dependencies`, `dependency_snapshot`, `match_key`. Discovery must not mutate state, allocate IDs, observe metadata/events.

Match identity defined by `match_key` = `rule_id` + bindings. Bindings serialized as `name=identifier`, binding names sorted lexicographically. `let` values excluded.

**Match key ordering** – When match keys are compared, the ordering is the lexicographic order of their canonical serialized UTF‑8 byte sequences (SPEC 018).

---

## SPEC 010 DEPENDENCY MODEL

**Dependency types** (mapping as in v0.23, including `EdgePredicate`, `EdgeOrdering`).

**Dependency extraction** mandatory for patterns, where, let, priority, action arguments, event payloads, and function `declared_reads`. Must analyze all branches, must be **complete** (no under‑approximation). Over‑approximation permitted.

**Collection dependency rule** – For any iteration over a collection, include dependencies for membership, ordering (if used), and values.

**Normative extraction mapping** (examples – engines must extract at least these):

| Expression pattern | Dependencies |
|-------------------|--------------|
| `node.field` | `Field(node, field)`, `Predicate(node.type, field)`, `NodeExistence(node)` |
| `edge.field` | `Field(edge, field)`, `EdgePredicate(edge.type, field)`, `EdgeExistence(edge)` |
| `count(NodeType)` | `Extent(NodeType)` |
| `sum(NodeType.field)` | `Extent(NodeType)`, `Predicate(NodeType, field)` |
| `min(NodeType.field)`, `max(NodeType.field)` | `Extent(NodeType)`, `Ordering(NodeType, field)` |
| `sort(NodeType by field)` | `Extent(NodeType)`, `Ordering(NodeType, field)` |
| iteration over `node.outgoing(EdgeType)` | `Adjacency(node, EdgeType, outgoing)`, `EdgeType(EdgeType)` |
| iteration over `node.incoming(EdgeType)` | `Adjacency(node, EdgeType, incoming)`, `EdgeType(EdgeType)` |
| `exists(edge)` | `EdgeExistence(edge)` |

A match validates **iff** every dependency version equals its snapshot version **and** every existence dependency refers to an existing element.

No additional correctness mechanism.

## SPEC 011 MATCH LIFECYCLE MODEL

Define `match_age` recursively:
- Not present in previous tick → new: `age = 0`
- Present in previous tick → `age = previous_age + 1`

Only the immediate previous tick matters; if a match disappears and later reappears, it is new (`age = 0`). Overflow fatal.

---

## SPEC 012 SELECTION MODEL

Score = `(base_priority × priority_scale) + (match_age × fairness_scale)`. 64‑bit signed, overflow fatal. Order by score descending, then `match_key` ascending (canonical serialized byte order). No mutation, allocation, validation.

---

## SPEC 013 ACTION MODEL

Actions: `CreateNode`, `CreateEdge`, `UpdateField`, `DeleteEdge`, `DeleteNode`, `EmitEvent`. Action evaluation pure, produces staged transaction.

**Temporary creation handles** – When `CreateNode` or `CreateEdge` is staged, the action may refer to the newly created element using a temporary handle local to the transaction. Handles resolved to final IDs during commit. Handles do not escape the transaction; they cannot be stored in fields or emitted in events. **Identifier allocation order** – within each commit phase, identifiers allocated in the same order as the staged actions appear. This ensures deterministic mapping from handles to final IDs.

**Handle observability** – Handles may not appear in event payloads or `UpdateField`. Such IR is invalid.

Staged transaction must satisfy validity rules (SPEC 014) before commit. Invalid staged transactions rejected (no state change, no events).

---

## SPEC 014 TRANSACTION MODEL

Transaction steps:
1. Dependency validation
2. Action evaluation → staged writes (with handles)
3. Resolve temporary handles
4. Staged transaction validation
5. Commit
6. Event publication

Only one commit per tick. If validation fails, discard candidate and consider next.

**Staged Transaction Validation** – Must ensure:
- Existing target validity: `UpdateField`, `DeleteNode`, `DeleteEdge` targets exist (or created earlier).
- Creation validity: `CreateEdge` source and target exist after transaction (pre‑existing or created by `CreateNode`).
- No dangling references.
- State invariants hold.
- No self‑conflicting writes except where automatically merged.

**Automatic incident edge deletion exception** – `DeleteNode` implicitly stages deletion of all incident edges (determined from pre‑commit state plus staged creations). If an edge was explicitly created in the same transaction and then automatically deleted because its source/target node is deleted, that is **valid**. Explicit `DeleteEdge` of an edge that is also automatically deleted is merged (no conflict). Explicit `DeleteEdge` of an edge that was created and automatically deleted is also valid.

If validation fails, discard candidate.

---

## SPEC 015 COMMIT MODEL

Commit order:
1. `CreateNode`
2. `CreateEdge`
3. `UpdateField`
4. `DeleteEdge`
5. `DeleteNode`

`DeleteNode` automatically stages deletion of all incident edges (determined as per SPEC 014).

**No‑Op Updates** – `UpdateField` is No‑Op when `new_value == existing_value` (exact type equality, recursive for compound types). No‑Op updates ignored: no state change, no version increments.

**Predicate/Ordering version semantics** – Increment on node creation, node deletion, and field update **producing a changed value** (No‑Op excluded). Regardless of rule references.

**Transaction Write Validity** – Invalid unless automatically merged:
- `UpdateField(X)` then `DeleteNode(X)` (same for edges)
- duplicate explicit `DeleteNode(X)` or `DeleteEdge(E)`
- `CreateNode(X)` then explicit `DeleteNode(X)` (create‑then‑delete same node/edge)

Edge created then auto‑deleted due to node deletion is **allowed**.

**Version increment summary** (changed values only, No‑Op excluded) – same table as v0.23.

**Note:** `edge_type_version` increments only on edge creation or deletion (changes to the set of edges), not on field updates.

Commit must preserve all state invariants.

---

## SPEC 016 EVENT MODEL

Events: `rule_id` + payload. Visible only after successful commit. Payload expressions pure, participate in dependency extraction, no new reads. Events do not influence matching.

---

## SPEC 017 TICK MODEL

Tick steps:
1. Increment `tick_counter`
2. Discover matches (frozen snapshot)
3. Compute scores
4. Rank matches
5. Select candidate
6. Validate dependencies
7. If invalid, continue ranking
8. If valid, evaluate actions
9. Validate staged transaction
10. If invalid, continue ranking
11. Commit transaction
12. Publish events
13. End tick

Discovery exactly once, no rediscovery. At most one commit.

---

## SPEC 018 CANONICAL SERIALIZATION

Canonical serialization uses:
- UTF‑8 encoding
- LF line endings
- Lexicographically sorted object keys (UTF‑8 bytewise)
- Deterministic list ordering
- Canonical integer encoding (base 10, no leading zeros)

**String serialization** – Strings are enclosed in double quotes (`"`). The following characters are escaped:
- backslash → `\\`
- double quote → `\"`
- newline (U+000A) → `\n`
- carriage return (U+000D) → `\r`
- tab (U+0009) → `\t`
- Other control characters (U+0000–U+001F, U+007F) → `\uXXXX` (uppercase hexadecimal, zero‑padded to 4 digits).

All other Unicode characters are written literally as UTF‑8 bytes.

**Maps and records** – Serialized as `{` followed by comma‑separated `"key": value` pairs, keys sorted lexicographically (UTF‑8). No extra whitespace.

**Lists** – `[` comma‑separated values, no whitespace.

**Duplicate map keys** – Any map with duplicate keys is **invalid**.

**Recursive canonicalization** – Applied to all nested values.

Round‑trip serialization must produce byte‑identical output. Applies to Canonical IR, Golden Files, Conformance Outputs.

---

## SPEC 019 GOLDEN FILE MODEL

Golden files capture observable behavior only. Normative fields: `initial_state`, `ticks`, `final_state`. Each tick: `tick_number`, `selected_match_key`, `committed_changes`, `events`. Diagnostics non‑normative.

---

## SPEC 020 CONFORMANCE

A conformant engine must:
- implement every normative rule
- reject invalid Canonical IR
- prohibit nondeterminism, floats, identifier reuse, counter overflow

For identical Canonical IR and initial state, all conformant engines must produce identical observable behavior (committed changes, events, final state, golden files).

**Dependency extraction completeness** is normative; conformance tests will exercise all dependency types. Over‑approximation allowed, under‑approximation forbidden.

Conformance determined exclusively through observable behavior.
