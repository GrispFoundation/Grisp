Deze versie bouwt voort op v0.26 en dicht de laatste belangrijke gaten: `ordering_version` hernoemd naar `ordering_dependency_version` (om verwarring over semantiek te voorkomen), `match_age` vergetingsregel expliciet, deling door nul als runtime fatale fout (niet IR‑validatie), fixed‑point vergelijking zonder overflow, overal UTF‑8 bytewise ordening, formele grammatica voor `rule_id` en binding names, match key als canonieke serialisatie van een record (geen “JSON‑like”), event payload dependencies worden altijd geëxtraheerd, en het `DeleteNode`/`CreateEdge` hoekgeval is waterdicht gemaakt.

# GRISP DETERMINISTIC KERNEL SPECIFICATION v0.27

## SPEC 000 CORE PRINCIPLES

The GRISP Deterministic Kernel defines a fully deterministic execution model for rule-driven state transitions over a typed graph.

For identical Canonical IR and identical initial state, all conformant engines must produce identical observable behavior.

Observable behavior consists solely of:

* Committed state transitions
* Emitted events
* Golden file output

All other implementation details are non-normative.

The kernel is governed by the following principles:

1. **Determinism** – All observable behavior must be deterministic. Forbidden: floating point arithmetic, random number generation, system time, memory addresses, pointer identity, thread scheduling, hash‑based ordering, runtime metadata, engine‑specific behavior.

2. **Explicitness** – All reads, writes, dependencies, identifiers, ordering rules, and version counters must be explicitly represented. No implicit reads are permitted.

3. **Frozen Discovery** – Match discovery occurs exactly once per tick. The resulting discovery snapshot is immutable for the remainder of the tick.

4. **Dependency Validation** – Dependency validation is the sole correctness mechanism. Conflict detection does not exist.

5. **Single Commit** – At most one transaction may commit per tick.

6. **Canonical Ordering** – Every ordered operation must have an explicitly defined deterministic ordering.

7. **Canonical Serialization** – All deterministic artifacts must serialize canonically.

8. **Referential Transparency** – Expressions are pure. Actions are effectful only during commit.

9. **No Identifier Reuse** – Identifiers are unique for the lifetime of the graph. Deleted identifiers must never be reused.

10. **Cross-Engine Reproducibility** – All conformant engines must produce identical golden files.

**Fatal Conformance Error** – A fatal conformance error is an unrecoverable error that occurs during execution (e.g., arithmetic overflow, division by zero, counter overflow). Upon such an error, the engine must immediately halt execution. No further ticks are processed. The golden file must record the error and the state at the point of error in a deterministic manner (e.g., the current tick number and the error type). All conformant engines must produce identical golden file output for the same error condition.

## SPEC 001 NUMERIC MODEL

All numeric values are signed 64‑bit integers. Floating point values forbidden.

**Fixed‑point representation** – Fixed‑point values are represented as scaled integers. The scale factor is declared per field (SPEC 002) as a non‑negative integer denoting the number of fractional decimal digits. Example: scale `2` means the integer `123` represents `1.23`.

**Fixed‑point arithmetic** – Operations follow integer rules with scale handling:

- Addition, subtraction: scale factors must be equal; result has same scale.
- Multiplication: result scale = scale₁ + scale₂.
- **Division**: Let dividend have scale `s_d` and value `v_d`, divisor have scale `s_r` and value `v_r`. The quotient is computed as:  
  `quotient_value = (v_d * 10^(s_r)) // v_r`  
  where `//` denotes integer division truncating toward zero. The result scale is `s_d`. This yields a fixed‑point number with the same fractional precision as the dividend.

- **Comparison**: Two fixed‑point values must be compared without arithmetic overflow. Engines must use an algorithm equivalent to: compare `v_d * 10^(max(s_d, s_r))` and `v_r * 10^(max(s_d, s_r))` using arbitrary‑precision arithmetic (or a safe alternative) to avoid overflow. The result must match exact rational comparison.

If incompatible scales are used in addition or subtraction, the IR is invalid and must be rejected.

**Division by zero** – Any division operation (integer or fixed‑point) where the divisor evaluates to zero **during expression evaluation** is a fatal conformance error (execution halts). This is a runtime condition, not an IR validity check.

**Overflow** – Any arithmetic overflow (including intermediate results in fixed‑point comparisons) is a fatal conformance error.

**No‑Op Arithmetic** – A write operation that does not change the integer representation of a field is a No‑Op Update (SPEC 015).

The following counters must never overflow (fatal error if they would):
- `tick_counter`
- sequence counters (per type)
- `match_age`
- `existence_version` (node and edge)
- `field_version`
- `predicate_version`
- `ordering_dependency_version` (renamed from `ordering_version`)
- `extent_version`
- `edge_type_version`
- `adjacency_version`
- `edge_predicate_version`
- `edge_ordering_dependency_version`

## SPEC 002 TYPE SYSTEM

**Type name grammar** – A type name must match:
```
type_name = [A-Za-z_][A-Za-z0-9_-]*
```
(ASCII letters, underscore, digits, hyphen; must start with letter or underscore; colon `:` is **forbidden**). Case‑sensitive.

**Generic types** – The type system supports parametric types:
- `List<T>` – homogeneous list of elements of type `T`.
- `Map<K, V>` – map from keys of type `K` to values of type `V`. `K` must be `String` (keys are always strings). `V` can be any type (including nested lists/maps).

**Allowed base field types**:
- `Integer`
- `FixedPoint(scale)` where `scale` is a non‑negative integer literal
- `Boolean`
- `String`
- `Identifier`
- `List<T>` where `T` is any allowed type
- `Map<String, V>` where `V` is any allowed type

**Field mandatory semantics** – All declared fields are mandatory. Every node or edge must contain exactly the fields defined by its type, with no null values.

**String Semantics** – Strings are immutable Unicode text. Serialization: UTF‑8. Comparison: binary Unicode code point order. Equality: exact code point equality. No normalization, no case folding.

**List Semantics** – Homogeneous ordered list of `T`.
- Equality: element‑wise same order.
- Lexicographic ordering is defined **iff** `T` is orderable (see below). If `T` is not orderable, `List<T>` is not orderable.
- Iteration order is the explicit element order.

**Map Semantics** – Keys are strings.
- Key uniqueness: exact string equality.
- Equality: two maps are equal iff they have the same set of keys and for each key the values are equal (recursively). Order of keys does not matter.
- Iteration order during execution is undefined.
- Maps are **not orderable**.
- Duplicate map keys in source IR or literals are **invalid**.
- Canonical serialization orders keys lexicographically (UTF‑8 bytewise).

**Orderability** – A type `T` is orderable if it has a deterministic total order:
- `Integer`, `FixedPoint`, `Boolean`, `String`, `Identifier` are orderable.
- `List<T>` is orderable **iff** `T` is orderable (lexicographic order).
- `Map` is not orderable.
- Any type containing a non‑orderable component is not orderable.

Operations that require ordering (e.g., `min`, `max`, `sort`, `order by`) on a non‑orderable type are **invalid IR**.

**Equality for compound types** – Equality for `List`, `Map`, and any nested combination is defined **recursively**.

**Empty field sets** – A node or edge type may declare zero fields. All version counters per field are vacuous; creation still increments `extent_version` etc., but no per‑field counters exist.

## SPEC 003 IDENTIFIER MODEL

Identifiers are deterministic strings. The grammar is:
```
identifier = type_name ":" nonNegativeInteger
```
where `type_name` matches SPEC 002 (no colon), and `nonNegativeInteger` is a decimal integer without leading zeros (except the number `0` itself). Examples: `Person:0`, `Task_12:5`.

Sequence counters per type start at `0`, increment monotonically by `1` each allocation, never decrease, never wrap, never reused. Allocation only during commit.

Identifier ordering:
1. `type_name` lexicographic ascending using **UTF‑8 bytewise comparison** (since type names are ASCII, this is equivalent to ASCII order).
2. `sequence` numeric ascending.

This defines global identifier ordering. “ascending node_id” / “ascending edge_id” refers to this order.

**Match key serialization** – In match keys (SPEC 009), bindings are represented as `name=identifier`; the identifier string uses the exact format defined above. No escaping needed because identifiers contain no `=` or control characters.

---

## SPEC 004 STATE MODEL

Deterministic state consists of: Nodes, Edges, Version Counters, Sequence Counters, Tick Counter.

**Node**:
- `id`, `type`, `fields`
- `existence_version` (positive integer, defined only while node exists)
- `field_versions` (one per field, defined while node exists)

**Edge**:
- `id`, `type`, `source`, `target`, `fields`
- `existence_version` (positive integer, defined only while edge exists)
- `field_versions` (one per field, defined while edge exists)

**Global version counters**:
- `extent_version[node_type]`
- `predicate_version[node_type][field_name]` (node fields)
- `ordering_dependency_version[node_type][field_name]` (node fields) – *renamed*
- `edge_predicate_version[edge_type][field_name]` (edge fields)
- `edge_ordering_dependency_version[edge_type][field_name]` (edge fields) – *renamed*
- `edge_type_version[edge_type]` (tracks set membership changes)
- `adjacency_version[node_id][edge_type][direction]` where direction = `incoming` or `outgoing`

All version counters **begin at 1** in the initial state.

**Initial State Version Assignment** – For every node and edge present in the initial state:
- `existence_version = 1`
- `field_versions[field] = 1` for each field
- Global counters are set to 1. The initial state is treated as if created before the first tick, with all version counters at base value.

State invariants: unique IDs, no dangling edges, type‑valid fields, all constraints satisfied.

---

## SPEC 005 CANONICAL IR

Canonical IR is the sole executable representation. All manifests compile into it.

Canonical IR contains: Type Definitions, Function Definitions, Rule Definitions, Initial State, Constants.

Canonical IR must contain: No syntactic sugar, no implicit defaults, no runtime metadata, no engine‑specific structures.

**Rule Identifier Stability** – Every rule definition must contain an explicit `rule_id`. A `rule_id` is a string conforming to the same grammar as type names (SPEC 002): ASCII letters, digits, underscore, hyphen; start with letter or underscore. `rule_id` must be unique, stable across compilations, and preserved by serialization. Compilers must not generate rule identifiers.

**Function Termination** – Recursive function definitions (direct or mutual) are forbidden. The expression language has no iterative constructs. Therefore all functions terminate by construction. Implementations must reject any function containing recursion.

**IR Validity** – The IR must be validated before execution. If invalid, the engine must reject it.

Round‑trip serialization must be byte‑identical.

---

## SPEC 006 FUNCTION MODEL

Functions are `pure` or `effect_deterministic`.

**Pure**: referentially transparent, only arguments, no state read.

**effect_deterministic**: referentially transparent, may read state, may not modify state.

**Declared Reads** – Every `effect_deterministic` function must declare `declared_reads`, a **conservative superset** of all dependency types that may be read. Under‑declaration error, over‑declaration permitted. Dependency extraction includes `declared_reads`.

No recursion, no nondeterministic functions.

---

## SPEC 007 EXPRESSION MODEL

Expressions represent pure computation. May contain: literals, bindings, arithmetic, boolean logic, collection expressions, function calls. Must not: mutate state, allocate IDs, observe metadata/events, nondeterministic ops. Short‑circuit allowed. Dependency extraction analyzes all branches.

---

## SPEC 008 PATTERN MODEL

Patterns bind graph elements deterministically. Node enumeration ascending `node_id`, edge enumeration ascending `edge_id`. Constraints may use expressions. `let` bindings: evaluated during discovery, immutable, excluded from match identity. No mutation.

---

## SPEC 009 MATCH DISCOVERY MODEL

Discovery once per tick, frozen snapshot. Match contains: `rule_id`, `bindings`, `let_values`, `dependencies`, `dependency_snapshot`, `match_key`.

**Match key definition** – The match key is the **canonical serialization** (SPEC 018) of the following map (record):

```
{
  "rule_id": <rule_id>,
  "bindings": {
    <binding_name_1>: <identifier_1>,
    <binding_name_2>: <identifier_2>,
    ...
  }
}
```

- `rule_id` is a string.
- `bindings` is a map where keys are binding names and values are identifier strings.
- Binding names must conform to the same grammar as type names (ASCII letters, digits, underscore, hyphen; start with letter or underscore). They are sorted lexicographically by UTF‑8 byte order for canonical serialization.
- The map is serialized according to SPEC 018 (keys sorted, UTF‑8, no extra whitespace).
- `let_values` are excluded.

**Match key ordering** – When match keys are compared (e.g., tie‑breaking in SPEC 012), the ordering is the lexicographic order of their canonical serialized UTF‑8 byte sequences.

**Discovery constraints** – Must not mutate state, allocate identifiers, observe runtime metadata, or observe events.

---

## SPEC 010 DEPENDENCY MODEL

**Dependency types** and mapping (as in v0.26, but with `ordering` renamed to `ordering_dependency_version`). The mapping is:

| Dependency | Maps to |
|------------|---------|
| `NodeExistence(node_id)` | `node.existence_version` |
| `EdgeExistence(edge_id)` | `edge.existence_version` |
| `Field(element_id, field_name)` | `field_versions[field_name]` |
| `Predicate(node_type, field_name)` | `predicate_version[node_type][field_name]` |
| `Ordering(node_type, field_name)` | `ordering_dependency_version[node_type][field_name]` |
| `EdgePredicate(edge_type, field_name)` | `edge_predicate_version[edge_type][field_name]` |
| `EdgeOrdering(edge_type, field_name)` | `edge_ordering_dependency_version[edge_type][field_name]` |
| `Extent(node_type)` | `extent_version[node_type]` |
| `EdgeType(edge_type)` | `edge_type_version[edge_type]` |
| `Adjacency(node_id, edge_type, direction)` | `adjacency_version[node_id][edge_type][direction]` |

**Dependency extraction** mandatory for patterns, where, let, priority, action arguments, event payloads, function `declared_reads`. Must be complete (no under‑approximation). Over‑approximation allowed.

**Collection dependency rule** – For any iteration over a collection, include dependencies for membership, ordering (if used), and values.

**Normative extraction mapping** (examples – engines must extract at least these):

| Expression pattern | Dependencies |
|-------------------|--------------|
| `node.field` | `Field(node, field)`, `Predicate(node.type, field)`, `NodeExistence(node)` |
| `edge.field` | `Field(edge, field)`, `EdgePredicate(edge.type, field)`, `EdgeExistence(edge)` |
| `count(NodeType)` | `Extent(NodeType)` |
| `sum(NodeType.field)` | `Extent(NodeType)`, `Predicate(NodeType, field)` |
| `min(NodeType.field)`, `max(NodeType.field)` | `Extent(NodeType)`, `Ordering(NodeType, field)` |
| `sort(NodeType by field)` | `Extent(NodeType)`, `Ordering(NodeType, field)` |
| iteration over `node.outgoing(EdgeType)` | `Adjacency(node, EdgeType, outgoing)`, `EdgeType(EdgeType)` |
| iteration over `node.incoming(EdgeType)` | `Adjacency(node, EdgeType, incoming)`, `EdgeType(EdgeType)` |
| `exists(edge)` | `EdgeExistence(edge)` |

A match validates **iff** every dependency version equals its snapshot version **and** every existence dependency refers to an existing element.

No additional correctness mechanism.

## SPEC 011 MATCH LIFECYCLE MODEL

Define `match_age` recursively:
- If the `match_key` was **not** present in the previous tick’s match set → new match: `age = 0`.
- If the `match_key` **was** present in the previous tick → `age = previous_age + 1`.

**Forgetting** – Only the immediate previous tick matters. If a match disappears for one or more ticks and later reappears, it is treated as a new match (`age = 0`). There is no long‑term memory.

`match_age` overflow is a fatal conformance error.

---

## SPEC 012 SELECTION MODEL

Score = `(base_priority × priority_scale) + (match_age × fairness_scale)`. 64‑bit signed arithmetic, overflow fatal. Order by score descending, then `match_key` ascending (as defined in SPEC 009). No mutation, allocation, validation.

---

## SPEC 013 ACTION MODEL

Actions: `CreateNode`, `CreateEdge`, `UpdateField`, `DeleteEdge`, `DeleteNode`, `EmitEvent`. Action evaluation pure, produces staged transaction.

**Temporary creation handles** – Handles local to transaction, resolved to final IDs during commit. Identifier allocation order: same order as staged actions within each phase (CreateNode, then CreateEdge).

**Handle observability** – Handles may not appear in event payloads or `UpdateField`. Such IR is invalid.

**Event payload dependency extraction** – Expressions inside `EmitEvent` are analyzed for dependencies **during discovery** (before validation and commit) exactly like any other expression. This analysis occurs regardless of whether the event will eventually be published. Engines must not optimize away dependency extraction from event payloads.

Staged transaction must satisfy validity rules (SPEC 014) before commit. Invalid staged transactions rejected.

---

## SPEC 014 TRANSACTION MODEL

Transaction steps:
1. Dependency validation
2. Action evaluation → staged writes (with handles)
3. Resolve temporary handles
4. Staged transaction validation
5. Commit
6. Event publication

Only one commit per tick. If validation fails, discard candidate and consider next.

**Staged Transaction Validation** – Must ensure:
- Existing target validity: targets exist (or created earlier).
- Creation validity: `CreateEdge` source/target exist after transaction.
- No dangling references.
- State invariants hold.
- No self‑conflicting writes except automatically merged.

**Automatic incident edge deletion exception** – `DeleteNode` implicitly stages deletion of all incident edges (determined from pre‑commit state plus staged creations). If an edge was explicitly created in the same transaction and then auto‑deleted because its source/target node is deleted, that is **valid**. Explicit `DeleteEdge` of an edge that is also auto‑deleted is merged (no conflict). Explicit `DeleteEdge` of an edge that was created and auto‑deleted is also valid.

If validation fails, discard candidate.

---

## SPEC 015 COMMIT MODEL

Commit order:
1. `CreateNode`
2. `CreateEdge`
3. `UpdateField` (changed values only)
4. `DeleteEdge`
5. `DeleteNode`

`DeleteNode` automatically stages deletion of all incident edges (determined as per SPEC 014).

**No‑Op Updates** – `UpdateField` is No‑Op when `new_value == existing_value` (exact type equality, recursive). No‑Op updates ignored: no state change, no version increments.

**Version increment rules** – Only for changed values (No‑Op excluded). The increment table from v0.26 remains the same, with `ordering_version` renamed to `ordering_dependency_version` (and similarly for edges). The table is reproduced here for completeness:

| Operation | `extent_version` | `predicate_version` (node) | `ordering_dependency_version` (node) | `edge_predicate_version` (edge) | `edge_ordering_dependency_version` (edge) | `edge_type_version` | `adjacency_version` | node/edge `existence_version` | node/edge `field_versions` |
|-----------|------------------|---------------------------|--------------------------------------|--------------------------------|---------------------------------------------|---------------------|---------------------|------------------------------|---------------------------|
| `CreateNode` | +1 (node_type) | +1 (all fields) | +1 (all fields) | – | – | – | – | set to 1 | set to 1 each |
| `DeleteNode` | +1 | +1 (all fields) | +1 (all fields) | – | – | – | +1 per incident edge (both dirs, per edge_type) | removed | removed |
| `CreateEdge` | – | – | – | +1 (all fields) | +1 (all fields) | +1 | +1 source.out, target.in (per edge_type) | set to 1 | set to 1 each |
| `DeleteEdge` | – | – | – | – | – | +1 | +1 source.out, target.in (per edge_type) | removed | removed |
| `UpdateField` (node field, changed) | – | +1 (that field) | +1 (that field) | – | – | – | – | – | +1 (that field) |
| `UpdateField` (edge field, changed) | – | – | – | +1 (that field) | +1 (that field) | – | – | – | +1 (that field) |

**Note:** `edge_type_version` increments only on edge creation or deletion, not on field updates.

**Transaction Write Validity** – Invalid unless automatically merged:
- `UpdateField(X)` then `DeleteNode(X)` (same for edges)
- duplicate explicit `DeleteNode`/`DeleteEdge`
- `CreateNode(X)` then explicit `DeleteNode(X)` (create‑then‑delete same node/edge)

Edge created then auto‑deleted due to node deletion is **allowed**.

Commit preserves all state invariants.

---

## SPEC 016 EVENT MODEL

Events: `rule_id` + payload. Visible only after successful commit. Payload expressions pure, participate in dependency extraction, no new reads. Events do not influence matching.

---

## SPEC 017 TICK MODEL

Tick steps:
1. Increment `tick_counter`
2. Discover matches (frozen snapshot)
3. Compute scores
4. Rank matches
5. Select candidate
6. Validate dependencies
7. If invalid, continue ranking
8. If valid, evaluate actions
9. Validate staged transaction
10. If invalid, continue ranking
11. Commit transaction
12. Publish events
13. End tick

Discovery exactly once, no rediscovery. At most one commit.

---

## SPEC 018 CANONICAL SERIALIZATION

Canonical serialization uses:
- UTF‑8 encoding
- LF line endings
- Deterministic ordering of keys (UTF‑8 bytewise)
- Deterministic list ordering
- Canonical integer encoding

**General rules** – For any serialized object (map/record), keys are serialized in ascending lexicographic order using **UTF‑8 bytewise comparison**. Lists preserve explicit order.

**Integers** – Base 10, no leading zeros, minus sign only for negative values.

**String serialization** – Enclosed in double quotes (`"`). Escapes:
- backslash → `\\`
- double quote → `\"`
- newline → `\n`
- carriage return → `\r`
- tab → `\t`
- Other control characters (U+0000–U+001F, U+007F) → `\uXXXX` (uppercase hex, zero‑padded to 4 digits).

**Maps and records** – Serialized as `{` followed by comma‑separated `"key": value` pairs, keys sorted, no extra whitespace.

**Lists** – `[` comma‑separated values, no whitespace.

**Duplicate map keys** – Any map with duplicate keys is **invalid**.

**Recursive canonicalization** – Applied to all nested values.

Round‑trip serialization must be byte‑identical. Applies to Canonical IR, Golden Files, Conformance Outputs.

---

## SPEC 019 GOLDEN FILE MODEL

Golden files capture observable behavior only. Normative fields: `initial_state`, `ticks`, `final_state`. Each tick: `tick_number`, `selected_match_key` (canonical serialization of the match that committed, or `null`), `committed_changes`, `events`.

**Fatal conformance error** – If a fatal error occurs, the golden file must record the error and the state up to that point deterministically.

Diagnostics non‑normative.

---

## SPEC 020 CONFORMANCE

A conformant engine must:
- implement every normative rule
- reject invalid Canonical IR
- prohibit nondeterminism, floats, identifier reuse, counter overflow
- produce identical observable behavior for identical IR and initial state.

**Dependency extraction completeness** is normative; conformance tests will exercise all dependency types. Over‑approximation allowed, under‑approximation forbidden.

Conformance determined exclusively through observable behavior.
