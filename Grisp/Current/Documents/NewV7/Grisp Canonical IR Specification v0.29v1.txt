# GRISP Canonical IR Specification v0.29v1

## Status

Normative Specification

This document defines the Canonical Intermediate Representation (IR) for GRISP systems.

The Canonical IR is the sole executable representation consumed by conformant GRISP engines.

Source languages, DSLs, graphical editors, code generators, and manifest compilers SHALL compile to Canonical IR before execution.

The Canonical IR is a stable contract between:

* Parsers
* Compilers
* Validators
* Optimizers
* Execution Engines
* Test Harnesses

The Canonical IR is independent of source syntax.

---

# IR-001 Goals

The Canonical IR SHALL be:

* Deterministic
* Canonicalizable
* Serialization Stable
* Language Independent
* Fully Explicit
* Self Contained

The Canonical IR SHALL NOT depend upon:

* Source-language syntax
* Runtime reflection
* Host-language behavior
* External schema systems

---

# IR-002 Design Principles

All executable behavior SHALL be represented explicitly.

The IR SHALL contain:

* Type Definitions
* Function Definitions
* Rule Definitions
* Expressions
* Actions

The IR SHALL NOT contain:

* Comments
* Formatting directives
* Editor metadata
* Runtime implementation details

---

# IR-003 Top-Level Structure

A Canonical IR document SHALL contain:

```json
{
  "ir_version": "grisp-ir-0.29v1",
  "manifest_id": "...",
  "manifest_version": "...",

  "types": [],
  "functions": [],
  "rules": [],

  "constants": {},
  "metadata": {}
}
```

Required fields:

* ir_version
* manifest_id
* manifest_version
* types
* functions
* rules

Unknown top-level fields SHALL be rejected.

# IR-004 Type System

Supported primitive types:

```text
Boolean
Integer
String
Identifier
```

Supported compound types:

```text
List<T>
Set<T>
Map<K,V>
FixedPoint(scale)
```

Floating point types SHALL NOT exist.

Null SHALL NOT exist.

Undefined SHALL NOT exist.

---

# IR-005 Type Definitions

Node types SHALL be defined explicitly.

Example:

```json
{
  "kind": "node_type",
  "name": "Person",
  "fields": {
    "name": "String",
    "age": "Integer"
  }
}
```

All fields are mandatory.

Duplicate field names SHALL be rejected.

---

# IR-006 Edge Definitions

Example:

```json
{
  "kind": "edge_type",
  "name": "Friendship",
  "from": "Person",
  "to": "Person"
}
```

Edge endpoints SHALL reference valid node types.

---

# IR-007 Constants

Constants SHALL be immutable.

Example:

```json
{
  "MAX_LEVEL": {
    "type": "Integer",
    "value": 100
  }
}
```

Constants SHALL NOT depend on runtime state.

---

# IR-008 Functions

Functions SHALL be one of:

```text
pure
effect_deterministic
```

No other function categories exist.

Example:

```json
{
  "function_id": "CalculateTax",
  "kind": "pure",
  "parameters": [
    {
      "name": "income",
      "type": "Integer"
    }
  ],
  "return_type": "Integer"
}
```

---

# IR-009 Effect Functions

Effect functions SHALL declare observable reads.

Example:

```json
{
  "function_id": "NearbyEnemies",
  "kind": "effect_deterministic",

  "declared_reads": [
    {
      "dependency": "Extent",
      "type": "Enemy"
    }
  ]
}
```

Missing required dependencies SHALL be rejected.

---

# IR-017 Events

Events SHALL be deterministic.

Example:

```json
{
  "action": "EmitEvent",

  "event_type": "PersonAged",

  "payload": {
    "person": {
      "kind": "Variable",
      "name": "p"
    }
  }
}
```

Sampling SHALL NOT exist.

Probabilistic emission SHALL NOT exist.

---

# IR-018 Canonical Serialization

Canonical IR SHALL serialize as UTF-8 JSON.

Objects SHALL use lexicographically sorted keys.

Duplicate keys SHALL be rejected.

Trailing commas SHALL NOT exist.

Numbers SHALL be represented in canonical decimal form.

# IR-020 Conformance

A conformant compiler SHALL:

* Produce valid Canonical IR
* Produce deterministic output
* Produce canonical serialization

A conformant engine SHALL:

* Accept valid Canonical IR
* Reject invalid Canonical IR
* Execute according to the GRISP Deterministic Kernel Specification

Observable behavior SHALL be identical across conformant engines.


# IR-021 Identifier Rules

Identifiers SHALL follow the GRISP identifier model.

Grammar:

```text
Identifier ::= [A-Za-z_][A-Za-z0-9_]*
```

Identifiers SHALL be:

* Case-sensitive
* UTF-8 encoded
* Non-empty

The following identifiers SHALL be globally unique within a manifest:

* Type names
* Function identifiers
* Rule identifiers

Duplicate identifiers SHALL be rejected.

Reserved identifiers beginning with:

```text
__grisp_
```

are reserved for future GRISP specifications.

---

# IR-022 Type Grammar

The Canonical IR supports the following primitive types:

```text
Boolean
Integer
String
Identifier
```

The Canonical IR supports the following compound types:

```text
List<T>
Set<T>
Map<K,V>
FixedPoint(scale)
```

Formal grammar:

```text
Type ::=
    Boolean
  | Integer
  | String
  | Identifier
  | FixedPoint(Integer)
  | List<Type>
  | Set<Type>
  | Map<Type,Type>
```

Restrictions:

* Floating point types SHALL NOT exist.
* Null types SHALL NOT exist.
* Undefined types SHALL NOT exist.
* FixedPoint scale SHALL be greater than or equal to zero.

Examples:

```text
Integer

List<String>

Set<Identifier>

Map<String,Integer>

FixedPoint(2)
```

# IR-023 Function Signature Rules

Every function SHALL define:

* function_id
* kind
* parameters
* return_type

Example:

```json
{
  "function_id": "CalculateTax",
  "kind": "pure",
  "parameters": [
    {
      "name": "income",
      "type": "Integer"
    }
  ],
  "return_type": "Integer"
}
```

Function parameter names SHALL be unique.

Function kinds SHALL be one of:

```text
pure
effect_deterministic
```

No other function kinds exist.

Functions SHALL NOT:

* Access system time
* Generate random values
* Access implementation-specific state

Effect-deterministic functions SHALL declare required observable reads.

# IR-025 Pattern Semantics

Patterns define match generation.

Supported pattern kinds:

```text
Binding
Edge
Existence
Let
Collection
Condition
```

Binding Pattern:

```json
{
  "kind": "Binding",
  "variable": "p",
  "type": "Person"
}
```

A binding pattern matches graph elements of the specified type.

Edge Pattern:

```json
{
  "kind": "Edge",
  "edge_type": "Friendship",
  "from": "a",
  "to": "b"
}
```

An edge pattern matches graph relationships.

Condition Pattern:

```json
{
  "kind": "Condition",
  "expression": ...
}
```

A condition pattern evaluates a boolean expression.

Pattern evaluation SHALL be deterministic.

Pattern evaluation SHALL NOT depend upon runtime ordering except where explicitly defined by the kernel specification.

# IR-027 Complete Dependency Catalog

Dependencies represent observable reads.

The following dependency categories are defined:

```text
NodeExistence

EdgeExistence

Field

Predicate

Extent

Ordering

Adjacency
```

## NodeExistence

Represents observation of node presence.

Example:

```json
{
  "dependency": "NodeExistence",
  "type": "Person"
}
```

## EdgeExistence

Represents observation of edge presence.

Example:

```json
{
  "dependency": "EdgeExistence",
  "type": "Friendship"
}
```

## Field

Represents observation of a field value.

Example:

```json
{
  "dependency": "Field",
  "type": "Person",
  "field": "age"
}
```

## Predicate

Represents observation of a filtered subset.

## Extent

Represents observation of all instances of a type.

## Ordering

Represents observation of relative ordering.

## Adjacency

Represents observation of graph connectivity.

Dependency definitions SHALL conform to the GRISP Deterministic Kernel Specification.

# IR-028 Canonical Serialization Rules

Canonical IR SHALL serialize as UTF-8 JSON.

Objects SHALL:

* Use lexicographically sorted keys
* Contain no duplicate keys

Arrays SHALL:

* Preserve declared ordering

Strings SHALL:

* Be encoded as UTF-8

Integers SHALL:

* Use canonical decimal representation
* Not contain leading zeros except for zero itself

Booleans SHALL be encoded as:

```json
true
false
```

Floating point values SHALL NOT appear.

Null values SHALL NOT appear.

Canonical serialization SHALL produce identical byte sequences across conformant implementations.

---

# IR-029 Validation Rules

A Canonical IR document SHALL be rejected if any of the following occur:

* Duplicate type names
* Duplicate rule identifiers
* Duplicate function identifiers
* Unknown type references
* Unknown field references
* Unknown expression kinds
* Unknown action kinds
* Unknown dependency kinds
* Invalid function signatures
* Invalid identifier syntax
* Cyclic type definitions
* Floating point values
* Null values
* Non-deterministic function declarations

Validation SHALL occur before execution.

---

# IR-030 IR Invariants

The following invariants SHALL always hold.

## Determinism

Identical IR and identical input state SHALL produce identical observable behavior.

## Explicitness

All executable behavior SHALL be represented explicitly within the IR.

## Canonicality

Equivalent IR documents SHALL serialize identically.

## Type Safety

All field references SHALL resolve to valid declared fields.

## Dependency Completeness

All observable reads SHALL be represented through the dependency model.

## Stable Identity

Type identifiers, function identifiers, and rule identifiers SHALL remain stable across canonical serialization.

Violation of any invariant SHALL render the IR invalid.
