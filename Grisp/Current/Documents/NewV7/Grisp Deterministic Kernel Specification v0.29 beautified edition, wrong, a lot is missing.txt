GRISP DETERMINISTIC KERNEL SPECIFICATION v0.29

BEAUTIFIED EDITION 

SPEC 000 CORE PRINCIPLES

The GRISP Deterministic Kernel defines a fully deterministic
execution model for rule-driven state transitions over a typed
graph.

For identical Canonical IR and identical initial state, all
conformant engines must produce identical observable behavior.

Observable behavior consists solely of:

* Committed state transitions
* Emitted events
* Golden file output

All other implementation details are non-normative.

The kernel is governed by the following principles:

1. Determinism

All observable behavior must be deterministic.

The following are forbidden:

* Floating point arithmetic
* Random number generation
* System time
* Memory addresses
* Pointer identity
* Thread scheduling
* Hash-based ordering
* Runtime metadata
* Engine-specific behavior

2. Explicitness

All reads, writes, dependencies, identifiers, ordering rules,
and version counters must be explicitly represented.

No implicit reads are permitted.

3. Frozen Discovery

Match discovery occurs exactly once per tick.

The resulting discovery snapshot is immutable for the remainder
of the tick.

4. Dependency Validation

Dependency validation is the sole correctness mechanism.

Conflict detection does not exist.

5. Single Commit

At most one transaction may commit per tick.

6. Canonical Ordering

Every ordered operation must have an explicitly defined
deterministic ordering.

7. Canonical Serialization

All deterministic artifacts must serialize canonically.

8. Referential Transparency

Expressions are pure.

Actions are effectful only during commit.

9. No Identifier Reuse

Identifiers are unique for the lifetime of the graph.

Deleted identifiers must never be reused.

10. Cross-Engine Reproducibility

All conformant engines must produce identical golden files.

Fatal conformance errors, such as arithmetic overflow, division
by zero, or counter overflow, immediately halt execution.

The golden file must record the error deterministically.

---

SPEC 001 NUMERIC MODEL

All numeric values are signed 64-bit integers.

Floating point values are forbidden.

Fixed-point values are represented as scaled integers.

Scale factors must be explicitly declared.

Addition and subtraction require equal scales.

Multiplication adds scales.

Division preserves the dividend’s scale and truncates toward
zero.

Comparisons must avoid overflow using safe or arbitrary-
precision logic.

Any arithmetic overflow is a fatal conformance error.

The following counters must never overflow:

* tick_counter
* sequence counters
* match_age
* existence_version
* field_version
* predicate_version
* ordering_dependency_version
* extent_version
* edge_type_version
* adjacency_version
* edge_predicate_version
* edge_ordering_dependency_version

Overflow of any deterministic counter is a fatal error.

---

SPEC 002 TYPE SYSTEM

Allowed field types:

* Integer
* FixedPoint(scale)
* Boolean
* String
* Identifier
* List<T>
* Map<String, V>

All fields are mandatory.

Strings use UTF-8 and exact code-point equality.

Lists preserve order and are lexicographically comparable only
if their element type is orderable.

Maps are unordered, not orderable, and must have unique keys.

Orderability is strictly defined.

Operations requiring ordering on non-orderable types are
invalid.

---

SPEC 003 IDENTIFIER MODEL

Identifiers follow the format:

type_name:sequence_number

Sequence numbers:

* start at 0
* increment monotonically
* never decrease
* never wrap
* are never reused

Identifier ordering is defined as:

1. type_name lexicographic ascending
2. sequence numeric ascending

This ordering defines all ascending node_id and edge_id
semantics.

---

SPEC 004 STATE MODEL

Deterministic state consists of:

* Nodes
* Edges
* Version Counters
* Sequence Counters
* Tick Counter

A node contains:

* id
* type
* fields
* existence_version
* field_versions

An edge contains:

* id
* type
* source
* target
* fields
* field_versions

Global counters include:

extent_version[node_type]

predicate_version[node_type][field_name]

ordering_dependency_version[node_type][field_name]

edge_predicate_version[edge_type][field_name]

edge_ordering_dependency_version[edge_type][field_name]

edge_type_version[edge_type]

adjacency_version[node_id][edge_type][direction]

Direction is:

* incoming
* outgoing

All version counters begin at 1 in the initial state.

The state must satisfy:

* node identifiers unique
* edge identifiers unique
* no dangling edges
* all fields type-valid
* all constraints satisfied

---

SPEC 005 CANONICAL IR

Canonical IR is the sole executable representation of a GRISP
manifest.

Canonical IR contains:

* Type Definitions
* Function Definitions
* Rule Definitions
* Initial State
* Constants

Canonical IR must contain:

* No syntactic sugar
* No implicit defaults
* No runtime metadata
* No engine-specific structures

Rule identifiers must be explicit, stable, and unique.

Recursive functions are forbidden.

Round-trip serialization must produce byte-identical output.

---

SPEC 006 FUNCTION MODEL

Functions are either:

* pure
* effect_deterministic

Pure functions:

* are referentially transparent
* depend only on arguments
* may not read state

effect_deterministic functions:

* are referentially transparent
* may read state
* may not modify state

Every effect_deterministic function must declare:

declared_reads

declared_reads must conservatively include all dependency types
the function may read.

Under-declaration is a conformance error.

Over-declaration is permitted.

Recursion is forbidden.

All functions must terminate.

---

SPEC 007 EXPRESSION MODEL

Expressions represent pure computation.

Expressions may contain:

* literals
* bindings
* arithmetic
* boolean logic
* collection expressions
* function calls

Expressions must not:

* mutate state
* allocate identifiers
* observe runtime metadata
* observe events
* perform nondeterministic operations

Short-circuit evaluation is permitted.

Dependency extraction must analyze all branches.

---

SPEC 008 PATTERN MODEL

Patterns bind graph elements.

Pattern evaluation is deterministic.

Node enumeration uses ascending node_id ordering.

Edge enumeration uses ascending edge_id ordering.

Pattern constraints may use expressions.

Patterns may contain let bindings.

Let bindings:

* are evaluated during discovery
* are immutable
* do not participate in match identity

Pattern evaluation must not mutate state.

---

SPEC 009 MATCH DISCOVERY MODEL

Discovery occurs exactly once per tick.

Discovery produces a frozen snapshot.

A match consists of:

* rule_id
* bindings
* let_values
* dependencies
* dependency_snapshot
* match_key

Match discovery must not:

* mutate state
* allocate identifiers
* observe runtime metadata
* observe events

Match identity is defined by match_key.

match_key consists of:

* rule_id
* bindings

Bindings are serialized as:

name=identifier

Binding names are sorted lexicographically.

Let values are excluded from match identity.

SPEC 010 DEPENDENCY MODEL

Dependency types are:

NodeExistence(node_id)

EdgeExistence(edge_id)

Field(element_id, field_name)

Predicate(node_type, field_name)

Ordering(node_type, field_name)

EdgePredicate(edge_type, field_name)

EdgeOrdering(edge_type, field_name)

Extent(node_type)

EdgeType(edge_type)

Adjacency(node_id, edge_type, direction)

Dependency extraction is mandatory for:

* patterns
* where clauses
* let expressions
* priority expressions
* action argument expressions
* event payload expressions
* function declared_reads

Dependency extraction must analyze all branches.

Dependency extraction must be complete.

Over-declaration is permitted.

Required validation mapping:

NodeExistence(node_id)
→ node.existence_version

EdgeExistence(edge_id)
→ edge.existence_version

Field(element_id, field_name)
→ field_versions[field_name]

Predicate(node_type, field_name)
→ predicate_version[node_type][field_name]

Ordering(node_type, field_name)
→ ordering_dependency_version[node_type][field_name]

EdgePredicate(edge_type, field_name)
→ edge_predicate_version[edge_type][field_name]

EdgeOrdering(edge_type, field_name)
→ edge_ordering_dependency_version[edge_type][field_name]

Extent(node_type)
→ extent_version[node_type]

EdgeType(edge_type)
→ edge_type_version[edge_type]

Adjacency(node_id, edge_type, direction)
→ adjacency_version[node_id][edge_type][direction]

A match validates iff every dependency version equals its
snapshot version and all existence dependencies still refer to
existing elements.

No additional correctness mechanism exists.

---

SPEC 011 MATCH LIFECYCLE MODEL

Matches persist across ticks through match_key identity.

match_age is defined as:

If the match_key did not appear in the previous tick:

match_age = 0

If the match_key did appear:

match_age = previous_age + 1

If a match disappears:

its age is forgotten.

If rediscovered later:

it is treated as a new match.

match_age overflow is a fatal conformance error.

---

SPEC 012 SELECTION MODEL

Selection operates exclusively on the discovery snapshot.

For each match:

score =
(base_priority × priority_scale)
+
(match_age × fairness_scale)

All calculations use signed 64-bit arithmetic.

Overflow is a fatal conformance error.

Matches are ordered by:

1. score descending
2. match_key ascending

Selection must not:

* mutate state
* allocate identifiers
* perform validation

---

SPEC 013 ACTION MODEL

Actions are:

CreateNode

CreateEdge

UpdateField

DeleteEdge

DeleteNode

EmitEvent

Action evaluation is pure.

Actions may not:

* mutate state
* allocate identifiers
* introduce new reads

Temporary handles may refer to newly created nodes or edges
within the same transaction.

Handles may not appear in event payloads or be stored in fields.

All expressions inside actions participate in dependency
extraction, including event payload expressions, even if the
transaction is later rejected.

Action evaluation produces a staged transaction.

---

SPEC 014 TRANSACTION MODEL

A transaction consists of:

1. dependency validation
2. action evaluation
3. temporary handle resolution
4. staged transaction validation
5. commit
6. event publication

Only one transaction may commit per tick.

If validation fails:

the candidate match is discarded.

The next ranked match is considered.

Staged transaction validation must ensure:

* all UpdateField, DeleteNode, and DeleteEdge targets exist
* CreateEdge endpoints exist after applying staged creations
* no dangling references occur
* all state invariants hold
* no self-conflicting writes occur except those merged by
  automatic incident edge deletion

Automatic incident edge deletion:

Deleting a node implicitly deletes all incident edges.

If an edge is created and then auto-deleted in the same
transaction, this is valid.

Explicit DeleteEdge of an edge that is also auto-deleted is
merged without conflict.

---

SPEC 015 COMMIT MODEL

Commit applies staged writes atomically.

Partial commit is forbidden.

Commit order is:

1. CreateNode
2. CreateEdge
3. UpdateField
4. DeleteEdge
5. DeleteNode

No-op updates do not increment counters.

Version increments follow:

CreateNode:
* extent_version[node_type] += 1
* predicate_version for all fields += 1
* ordering_dependency_version for all fields += 1
* existence_version set to 1
* field_versions set to 1

DeleteNode:
* extent_version[node_type] += 1
* predicate_version for all fields += 1
* ordering_dependency_version for all fields += 1
* adjacency_version increments for all incident edges
* existence_version removed
* field_versions removed

CreateEdge:
* edge_predicate_version for all fields += 1
* edge_ordering_dependency_version for all fields += 1
* edge_type_version += 1
* adjacency_version increments for source and target
* existence_version set to 1
* field_versions set to 1

DeleteEdge:
* edge_type_version += 1
* adjacency_version increments for source and target
* existence_version removed
* field_versions removed

UpdateField (node field):
* predicate_version[node_type][field] += 1
* ordering_dependency_version[node_type][field] += 1
* field_versions[field] += 1

UpdateField (edge field):
* edge_predicate_version[edge_type][field] += 1
* edge_ordering_dependency_version[edge_type][field] += 1
* field_versions[field] += 1

Commit must preserve all state invariants.

---

SPEC 016 EVENT MODEL

Events are deterministic outputs.

An event consists of:

* rule_id
* payload

Events become visible only after successful commit.

Event payload expressions:

* are pure
* participate in dependency extraction
* may not introduce new reads

Events must not influence matching or execution.

---

SPEC 017 TICK MODEL

Tick execution proceeds:

1. Increment tick_counter
2. Discover matches
3. Compute scores
4. Rank matches
5. Select candidate
6. Validate dependencies
7. If invalid, continue ranking
8. If valid, evaluate actions
9. Validate staged transaction
10. If invalid, continue ranking
11. Commit transaction
12. Publish events
13. End tick

Discovery occurs exactly once.

Rediscovery within a tick is forbidden.

At most one transaction may commit.

---

SPEC 018 CANONICAL SERIALIZATION

Canonical serialization uses:

* UTF-8 encoding
* LF line endings
* lexicographically sorted object keys
* deterministic list ordering
* canonical integer encoding

Strings use strict escaping rules.

Duplicate map keys are invalid.

All deterministic artifacts must use canonical serialization.

Round-trip serialization must be stable.

---

SPEC 019 GOLDEN FILE MODEL

Golden files capture observable behavior only.

Normative fields:

* initial_state
* ticks
* final_state

Each tick contains:

* tick_number
* selected_match_key
* committed_changes
* events

Fatal conformance errors must be recorded deterministically.

Diagnostic information is non-normative and must be ignored for
conformance.

---

SPEC 020 CONFORMANCE

A conformant engine must:

* implement every normative rule
* reject invalid Canonical IR
* prohibit nondeterminism
* prohibit floating point arithmetic
* prohibit identifier reuse
* prohibit counter overflow

For identical Canonical IR and identical initial state, all
conformant engines must produce identical:

* committed changes
* emitted events
* final state
* golden files

Conformance is determined exclusively through observable
behavior defined by this specification.
