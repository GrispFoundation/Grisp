# GRISP Canonical IR Specification v0.29v2

## Status

Normative Specification

This document defines the Canonical Intermediate Representation (IR) for GRISP systems.

The Canonical IR is the sole executable representation consumed by conformant GRISP engines.

Source languages, DSLs, graphical editors, code generators, and manifest compilers SHALL compile to Canonical IR before execution.

The Canonical IR is a stable contract between:

* Parsers
* Compilers
* Validators
* Optimizers
* Execution Engines
* Test Harnesses

The Canonical IR is independent of source syntax.

---

# IR-001 Goals

The Canonical IR SHALL be:

* Deterministic
* Canonicalizable
* Serialization Stable
* Language Independent
* Fully Explicit
* Self Contained

The Canonical IR SHALL NOT depend upon:

* Source-language syntax
* Runtime reflection
* Host-language behavior
* External schema systems

---

# IR-002 Design Principles

All executable behavior SHALL be represented explicitly.

The IR SHALL contain:

* Type Definitions
* Function Definitions
* Rule Definitions
* Expressions
* Actions

The IR SHALL NOT contain:

* Comments
* Formatting directives
* Editor metadata
* Runtime implementation details

---

# IR-003 Top-Level Structure

A Canonical IR document SHALL contain:

```json
{
  "ir_version": "grisp-ir-v0.29v2",
  "manifest_id": "...",
  "manifest_version": "...",

  "types": [],
  "functions": [],
  "rules": [],

  "constants": {},
  "metadata": {}
}
```

Required fields:

* ir_version
* manifest_id
* manifest_version
* types
* functions
* rules

Unknown top-level fields SHALL be rejected.

The following fields are descriptive metadata only:

* manifest_id
* manifest_version
* metadata

These fields SHALL NOT affect execution semantics.

# IR-004 Type System

Supported primitive types:

```text
Boolean
Integer
String
Identifier
```

Supported compound types:

```text
List<T>
Map<String,T>
FixedPoint(scale)
```

Floating point types SHALL NOT exist.

Null SHALL NOT exist.

Undefined SHALL NOT exist.

---

# IR-005 Type Definitions

Node types SHALL be defined explicitly.

Example:

```json
{
  "kind": "node_type",
  "name": "Person",
  "fields": {
    "name": "String",
    "age": "Integer"
  }
}
```

All fields are mandatory.

Duplicate field names SHALL be rejected.

---

# IR-006 Edge Definitions

Example:

```json
{
  "kind": "edge_type",
  "name": "Friendship",
  "from": "Person",
  "to": "Person"
}
```

Edge endpoints SHALL reference valid node types.

---

# IR-007 Constants

Constants SHALL be immutable.

Example:

```json
{
  "MAX_LEVEL": {
    "type": "Integer",
    "value": 100
  }
}
```

Constants SHALL NOT depend on runtime state.

---

# IR-008 Functions

Functions SHALL be one of:

```text
pure
effect_deterministic
```

No other function categories exist.

Example:

```json
{
  "function_id": "CalculateTax",
  "kind": "pure",
  "parameters": [
    {
      "name": "income",
      "type": "Integer"
    }
  ],
  "return_type": "Integer"
}
```

---

# IR-009 Effect Functions

Effect-deterministic functions SHALL declare observable reads.

Example:

```json
{
  "function_id": "NearbyEnemies",
  "kind": "effect_deterministic",
  "declared_reads": [
    {
      "dependency": "Extent",
      "type": "Enemy"
    }
  ]
}
```

Missing required dependencies SHALL be rejected.

Under-declared dependencies SHALL be rejected.

---



```json

  "kind": "Literal",
```

Floating point literals SHALL be rejected.

Null literals SHALL be rejected.

# IR-017 Events

Events SHALL be deterministic.

Example:

```json
{
  "action": "EmitEvent",
  "event_type": "PersonAged",
  "payload": {
    "person": {
      "kind": "Variable",
      "name": "p"
    }
  }
}
```

Sampling SHALL NOT exist.

Probabilistic emission SHALL NOT exist.

Expressions appearing inside EmitEvent payloads SHALL participate in dependency extraction.

Dependencies SHALL be collected during discovery even if the transaction is later rejected.

EmitEvent payload expressions therefore contribute to observable reads.

---

# IR-018 Canonical Serialization

Canonical IR SHALL serialize as UTF-8 JSON.

Objects SHALL:

* Use lexicographically sorted keys
* Contain no duplicate keys

Arrays SHALL:

* Preserve declared ordering

Strings SHALL:

* Be encoded as UTF-8

Integers SHALL:

* Use canonical decimal representation
* Not contain leading zeros except for zero itself

Booleans SHALL be encoded as:

```json
true
false
```

Floating point values SHALL NOT appear.

Null values SHALL NOT appear.

Round-trip stability is required.

Parsing a valid Canonical IR document and immediately reserializing it SHALL produce an identical byte sequence.

Canonical serialization SHALL produce identical byte sequences across conformant implementations.

---

# IR-019 Validation Rules

A Canonical IR document SHALL be rejected if any of the following occur:

* Duplicate type names
* Duplicate rule identifiers
* Duplicate function identifiers
* Unknown type references
* Unknown field references
* Unknown expression kinds
* Unknown action kinds
* Unknown dependency kinds
* Invalid function signatures
* Invalid identifier syntax
* Cyclic type definitions
* Floating point values
* Null values
* Non-deterministic function declarations
* Under-declared effect function dependencies
* Ordering operations applied to non-orderable types
* Temporary handles used in UpdateField
* Temporary handles used in EmitEvent payloads

Validation SHALL occur before execution.

---

# IR-020 Conformance

A conformant compiler SHALL:

* Produce valid Canonical IR
* Produce deterministic output
* Produce canonical serialization

A conformant engine SHALL:

* Accept valid Canonical IR
* Reject invalid Canonical IR
* Execute according to the GRISP Deterministic Kernel Specification v0.29

Observable behavior SHALL be identical across conformant engines.

---

# IR-021 Identifier Rules

Grammar:

```text
Identifier ::= [A-Za-z_][A-Za-z0-9_]*
```

Identifiers SHALL be:

* Case-sensitive
* UTF-8 encoded
* Non-empty

The following identifiers SHALL be globally unique within a manifest:

* Type names
* Function identifiers
* Rule identifiers

Duplicate identifiers SHALL be rejected.

Identifiers beginning with:

```text
__grisp_
```

are reserved.

---

# IR-022 Type Grammar

Formal grammar:

```text
Type ::=
    Boolean
  | Integer
  | String
  | Identifier
  | FixedPoint(Integer)
  | List<Type>
  | Map<String,Type>
```

Restrictions:

```text
No Set<T>

No floating point types

No null type
```

FixedPoint scale SHALL be greater than or equal to zero.

FixedPoint arithmetic rules:

```text
Addition/Subtraction:
  scales must match

Multiplication:
  result_scale = left_scale + right_scale

Division:
  result_scale = dividend_scale
```

Examples:

```text
FixedPoint(2) + FixedPoint(2)  valid

FixedPoint(2) + FixedPoint(3)  invalid
```

---

# IR-023 Function Signature Rules

Every function SHALL define:

* function_id
* kind
* parameters
* return_type

Function parameter names SHALL be unique.

Function kinds SHALL be:

```text
pure
effect_deterministic
```

Functions SHALL NOT:

* Access system time
* Generate random values
* Access implementation-specific state

Effect-deterministic functions SHALL declare required observable reads.

# IR-026 Action Semantics

Supported actions:

```text
CreateNode
CreateEdge
UpdateField
DeleteNode
DeleteEdge
EmitEvent
Let
If
ForEach
```

Action definitions express logical intent.

Commit ordering SHALL be governed by the Kernel Specification.

Commit order SHALL be:

```text
1. CreateNode
2. CreateEdge
3. UpdateField
4. DeleteEdge
5. DeleteNode
```

IR action ordering SHALL NOT alter commit semantics.

DeleteNode implicitly removes all incident edges.

ForEach SHALL be deterministic.

Iteration rules:

```text
Node collections:
  ascending node_id

Edge collections:
  ascending edge_id

Lists:
  declared order

Maps:
  ascending key order
```

Operations depending upon ordering SHALL declare the appropriate ordering dependency.

# IR-027 Complete Dependency Catalog

## NodeExistence

Represents observation of node presence.

```json
{
  "dependency": "NodeExistence",
  "type": "Person"
}
```

## EdgeExistence

Represents observation of edge presence.

```json
{
  "dependency": "EdgeExistence",
  "type": "Friendship"
}
```

## Field

Represents observation of field values.

```json
{
  "dependency": "Field",
  "type": "Person",
  "field": "age"
}
```

## Predicate

Represents observation of a filtered subset.

## Extent

Represents observation of all instances of a type.

## Ordering

Represents observation of node ordering by field.

Required for:

```text
sort
min
max
order by
```

## EdgePredicate

Represents observation of an edge field predicate.

```json
{
  "dependency": "EdgePredicate",
  "edge_type": "Friendship",
  "field": "strength"
}
```

## EdgeOrdering

Represents observation of edge ordering.

```json
{
  "dependency": "EdgeOrdering",
  "edge_type": "Friendship",
  "field": "strength"
}
```

## EdgeType

Represents observation of the membership extent of an edge type.

```json
{
  "dependency": "EdgeType",
  "edge_type": "Friendship"
}
```

## Adjacency

Represents graph connectivity.

```json
{
  "dependency": "Adjacency",
  "node_type": "Person",
  "edge_type": "Friendship",
  "direction": "outgoing"
}
```

Allowed directions:

```text
incoming
outgoing
```

Dependency definitions SHALL conform to the GRISP Deterministic Kernel Specification v0.29.

---

# IR-028 IR Invariants

The following invariants SHALL hold.

## Determinism

Identical IR and identical input state SHALL produce identical observable behavior.

## Explicitness

All executable behavior SHALL be represented explicitly.

## Canonicality

Equivalent IR documents SHALL serialize identically.

## Type Safety

All field references SHALL resolve to declared fields.

## Dependency Completeness

All observable reads SHALL be represented through the dependency model.

## Stable Identity

Type identifiers, function identifiers, and rule identifiers SHALL remain stable across canonical serialization.

Violation of any invariant SHALL render the IR invalid.
