================================================================================
GRISP SPECIFICATION DEVELOPMENT AGENT
Specification v2.0
================================================================================

Identifier:  GSDA/2.0
Status:      Proposed normative specification
Supersedes:  GSDA/1.0 (uploaded draft)
             SpecAgent v0.1 (implementation note)
Purpose:     Cooperative development, analysis, repair, refinement, scoring,
             and publication of technical specifications using multiple
             untrusted LLM peers, under a deterministic kernel.
Domain:      Specification reasoning only. No compilation, no execution, no
             runtime, no OS, no tools, no filesystem effects on target
             systems.
Default:     fail-closed.
Plain text:  This document is intentionally plain text. It contains no
             markdown and no code fences inside itself so that it can be
             embedded in any tool without escaping.

Every normative statement in this document carries an identifier of the form
REQ-GSDA-<SUBSYS>-<NNN>. Every requirement is either TESTABLE or explicitly
UNTESTABLE with a reason. This is the same discipline the agent imposes on
the specifications it develops.

================================================================================
0. PRIORITY ORDER
================================================================================

  INTENT PRESERVATION
  > CONSISTENCY
  > COMPLETENESS
  > PRECISION
  > TRACEABILITY
  > TESTABILITY
  > CLARITY
  > CONCISENESS
  > STYLE

A lower-priority property must never override a higher-priority property.

  REQ-GSDA-META-001
  The system MUST resolve conflicts between properties in favour of the
  higher-priority property listed above.

================================================================================
1. PURPOSE
================================================================================

  REQ-GSDA-META-010
  GSDA/2.0 defines a system whose purpose is to help humans produce better
  technical specifications.

  REQ-GSDA-META-011
  The system MUST accept as input: rough notes, requirements lists, existing
  specifications, partial specifications, competing proposals, design
  discussions, and change requests.

  REQ-GSDA-META-012
  The system MUST produce as output a specification package containing at
  minimum: a human-readable specification, a machine-readable requirement
  matrix, a glossary, a list of open questions, a traceability map, a
  review record, and a provenance record.

  REQ-GSDA-META-013
  The system MUST NOT compile, execute, debug, sandbox, inspect runtime
  state, access external development tools, or determine whether an
  implementation works. Its domain is exclusively specification reasoning
  and specification improvement.

  REQ-GSDA-META-014
  The system MUST remain usable without any external compiler, runtime,
  debugger, LSP, tree-sitter, static analyzer, or network-facing AI tool.

================================================================================
2. SCOPE
================================================================================

In scope:

  - specification creation
  - specification refinement
  - requirements extraction
  - requirements formalization
  - alternative formulation
  - contradiction detection
  - ambiguity detection
  - missing-requirement detection
  - assumption detection
  - terminology management
  - traceability
  - testability analysis
  - consistency analysis
  - cross-repair
  - scoring
  - reliability estimation
  - revision management
  - convergence detection
  - human review
  - publication

Out of scope:

  - compilation
  - execution
  - debugging
  - runtime testing
  - LSP
  - tree-sitter
  - static analyzers
  - source code compilation
  - OS capabilities
  - filesystem execution
  - network execution
  - sandboxing
  - GRISP execution
  - tool execution

The absence of these mechanisms is intentional and is itself a requirement.

  REQ-GSDA-SCOPE-001
  The system MUST NOT introduce out-of-scope mechanisms unless this
  specification is revised.

================================================================================
3. DESIGN PRINCIPLES
================================================================================

  REQ-GSDA-DSGN-001
  Many imperfect reasoning systems cooperating MUST be preferred over one
  unreviewed reasoning system.

  REQ-GSDA-DSGN-002
  The system MUST NOT accept the pattern: one LLM produces a specification
  and that same LLM declares it correct.

  REQ-GSDA-DSGN-003
  Peer output MUST be treated as untrusted reasoning material.

  REQ-GSDA-DSGN-004
  The coordinator MUST be deterministic. It MUST NOT delegate bookkeeping,
  aggregation, state transitions, revision identity, or publication to an
  LLM.

  REQ-GSDA-DSGN-005
  Scoring MUST be used in place of simple majority voting.

  REQ-GSDA-DSGN-006
  Reliability MUST influence ranking but MUST NOT establish truth.

  REQ-GSDA-DSGN-007
  Uncertainty MUST be preserved, never manufactured into certainty.

  REQ-GSDA-DSGN-008
  A minority finding MUST NOT be discarded solely because it is a minority
  finding.

  REQ-GSDA-DSGN-009
  The user's original intent MUST be traceable through every revision.

5. TERMINOLOGY
================================================================================

The following terms have precise meanings inside GSDA/2.0. Every domain
term used in a GSDA specification MUST appear in the glossary with a
definition.

  TASK
  A unit of specification work submitted by a user.

  PEER
  An independent LLM reasoning participant. Peers are untrusted.

  ROLE
  A logical function assigned to a peer for a phase. A peer may hold
  multiple roles.

  CANDIDATE
  An independently generated specification proposal.

  CRITIQUE
  A peer's analysis of another peer's candidate or repair.

  REPAIR
  A new artifact produced by a peer that modifies a parent artifact.

  CROSS-REPAIR
  A repair in which the repairing peer differs from the author of the
  parent artifact.

  SCORE
  A peer's multi-dimensional quality judgement about a candidate or
  repair, together with a separate confidence value.

  RELIABILITY
  A coordinator-maintained estimate of how useful a peer has historically
  been for a given activity.

  LINEAGE
  The directed acyclic graph of artifact derivation relationships.

  PROVENANCE
  The record of which peer, role, and input produced each artifact.

  REQUIREMENT
  A normative statement identified by REQ-<SUBSYS>-<NNN>.

  OPEN QUESTION
  A question the specification cannot currently resolve.

  ASSUMPTION
  A statement treated as true for the purpose of the specification, but
  not asserted as a requirement.

  REVISION
  An immutable specification artifact with a stable cryptographic
  identity.

  KERNEL
  The deterministic part of the coordinator that performs requirement
  extraction, cross-reference checks, contradiction scans, coverage
  checks, glossary checks, testability checks, open-question checks,
  score aggregation, reliability updates, and revision identity.

  FINDING
  A structured observation produced by the kernel or by a peer.

  BLOCKING FINDING
  A finding that prevents a revision from being marked publication-ready.

6. SYSTEM MODEL
================================================================================

  REQ-GSDA-SYS-001
  The system consists of: a deterministic coordinator, a set of LLM peers,
  and a specification artifact store.

  REQ-GSDA-SYS-002
  All intelligence MUST come from the LLM peer network.

  REQ-GSDA-SYS-003
  All orchestration, bookkeeping, aggregation, and state transitions MUST
  be performed by the coordinator.

  REQ-GSDA-SYS-004
  The coordinator MUST NOT be an LLM.

  REQ-GSDA-SYS-005
  The coordinator MUST remain deterministic: given identical inputs and
  identical peer messages, it MUST produce identical outputs.

7. PEER MODEL
================================================================================

  REQ-GSDA-PEER-001
  A peer is an independent reasoning participant.

  REQ-GSDA-PEER-002
  A peer MUST NOT be considered authoritative merely because it is more
  capable, has a higher score, has higher reliability, generated the
  original proposal, or is the coordinator's preferred model.

  REQ-GSDA-PEER-003
  Each peer MUST have a stable identity of the form peer_id.

  REQ-GSDA-PEER-004
  A peer MAY be assigned one or more roles for a given phase.

  REQ-GSDA-PEER-005
  The coordinator MUST record, for every peer message, the peer_id, role,
  task_id, round_id, and artifact_id (if any) that the message concerns.

================================================================================
8. PEER ROLES
================================================================================

The following roles are defined. Each role is a prompt template plus a
response contract. A peer may hold several roles at once.

  8.1  GENERATOR
       REQ-GSDA-ROLE-001
       Produces independent specification candidates.

  8.2  FORMALIZER
       REQ-GSDA-ROLE-002
       Converts informal ideas into explicit normative requirements using
       MUST, MUST NOT, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY.

  8.3  CRITIC
       REQ-GSDA-ROLE-003
       Finds contradictions, omissions, ambiguity, vague language,
       undefined terminology, conflicting requirements, incomplete edge
       cases, hidden assumptions, unnecessary constraints, and accidental
       requirements.

  8.4  CONTRADICTION ANALYST
       REQ-GSDA-ROLE-004
       Specializes in conflicts between requirements and MUST distinguish
       direct contradiction, potential contradiction, contextual tension,
       different scope, and compatible-but-similar.

  8.5  COMPLETENESS ANALYST
       REQ-GSDA-ROLE-005
       Identifies what the specification has failed to say.

  8.6  TERMINOLOGY ANALYST
       REQ-GSDA-ROLE-006
       Maintains consistent definitions of domain terms.

  8.7  TESTABILITY ANALYST
       REQ-GSDA-ROLE-007
       Determines whether each requirement is sufficiently precise to
       permit an objective future test. Does not execute tests.

  8.8  CROSS-REPAIRER
       REQ-GSDA-ROLE-008
       Repairs another peer's specification. Cross-repair MUST be allowed
       to modify another peer's work.

  8.9  SCORER
       REQ-GSDA-ROLE-009
       Scores proposed specifications and repairs using explicit criteria.

  8.10 ADVERSARIAL REVIEWER
       REQ-GSDA-ROLE-010
       Attempts to construct interpretations under which the
       specification fails, becomes ambiguous, becomes contradictory,
       becomes incomplete, or becomes exploitable.

  8.11 CONSOLIDATOR
       REQ-GSDA-ROLE-011
       Produces an integrated specification from multiple compatible
       contributions. MUST preserve provenance.

  REQ-GSDA-ROLE-012
  The coordinator MAY assign additional role specializations such as
  Delphi specialist, protocol specialist, security specialist, or
  formal-methods specialist.

17. RELIABILITY MODEL
================================================================================

Reliability is per-peer, per-activity, and estimated only from evidence
observed inside GSDA. There is no compiler or runtime feedback.

  PeerReliability
  {
    peer_id             : string
    per_activity        : map<Activity, Reliability>
  }

  Reliability
  {
    mean                : 0..1
    sample_count        : integer
    lower_bound         : 0..1
    upper_bound         : 0..1
  }

  Activity ::= GENERATION | CRITIQUE | REPAIR | SCORING
             | TERMINOLOGY | CONTRADICTION | COMPLETENESS
             | TESTABILITY

  REQ-GSDA-REL-001
  Reliability MUST be tracked per activity.

  REQ-GSDA-REL-002
  New peers MUST start with an uncertain prior, not maximum trust.

  REQ-GSDA-REL-003
  Reliability MUST be updated only from evidence observed inside GSDA.

  REQ-GSDA-REL-004
  A peer's activity-level reliability MUST NOT be silently generalised to
  other activities.

  REQ-GSDA-REL-005
  Reliability MUST NOT be interpreted as truth. It only influences the
  weight assigned to a peer's judgement.

  REQ-GSDA-REL-006
  When a peer has no samples for an activity, its contribution weight for
  that activity MUST default to a value specified by configuration, and
  the default MUST be recorded in provenance.

  REQ-GSDA-REL-007
  The default update rule SHOULD be a Beta posterior update of the form
  Beta(alpha + successes, beta + failures) over a bounded outcome metric.
  Implementations MAY substitute another rule provided the substitution
  is recorded and deterministic.

  REQ-GSDA-REL-008
  Score inflation, score compression, excessive confidence, systematic
  disagreement, and systematic agreement MUST be detectable as anomalies.

  REQ-GSDA-REL-009
  Anomaly detection MAY reduce the weight of a peer's judgement but MUST
  NOT silently ban a peer.

  REQ-GSDA-REL-010
  Lineage-aware attribution MUST be applied when updating reliability for
  mixed artifacts.

19. AGGREGATION
================================================================================

For a target artifact r and criterion k, let:

  S(i,r,k)  = peer i's score value for criterion k on artifact r
  C(i,r,k)  = peer i's confidence for that score
  R(i,k)    = peer i's reliability for criterion k
  W(i,k)    = optional criterion or role weight (default 1)

Overall criterion-level aggregate:

              sum_i [ R(i,k) * W(i,k) * C(i,r,k) * S(i,r,k) ]
  A(r,k) =   -------------------------------------------------
                    sum_i [ R(i,k) * W(i,k) * C(i,r,k) ]

Overall artifact aggregate:

  A(r) = weighted_sum_k [ w(k) * A(r,k) ] / weighted_sum_k [ w(k) ]

  REQ-GSDA-AGG-001
  If the denominator of A(r,k) is zero because no scoring peer is
  available for criterion k, A(r,k) MUST be recorded as UNDEFINED and
  MUST NOT be silently replaced by 0 or 1.

  REQ-GSDA-AGG-002
  If w(k) is zero for all k, A(r) MUST be recorded as UNDEFINED.

  REQ-GSDA-AGG-003
  The coordinator MUST record the aggregate at both criterion level and
  artifact level.

  REQ-GSDA-AGG-004
  Score variance per criterion MUST be recorded.

  REQ-GSDA-AGG-005
  A minority finding with high severity and a credible rationale MUST
  trigger a targeted analysis round.

  REQ-GSDA-AGG-006
  A high-variance criterion MUST be flagged in the review record.

20. COORDINATOR
================================================================================

  REQ-GSDA-COR-001
  The coordinator is deterministic.

  REQ-GSDA-COR-002
  The coordinator owns: task identity, peer identity, round identity,
  artifact identity, lineage, message validation, score aggregation,
  reliability calculation, state transitions, revision creation, package
  generation, and publication.

  REQ-GSDA-COR-003
  The coordinator MUST validate every peer message against the peer
  message schema in section 21 before accepting it.

  REQ-GSDA-COR-004
  A malformed peer message MUST be rejected. The coordinator MUST NOT
  silently infer missing information.

  REQ-GSDA-COR-005
  The coordinator MUST NOT silently choose between materially different
  alternatives. Every substantive decision MUST produce a Decision
  artifact with a basis.

  Decision
  {
    decision_id         : string
    task_id             : string
    kind                : string
    basis               : string
    affected_artifacts  : string[]
    created_at          : timestamp
  }

  REQ-GSDA-COR-006
  Every substantive coordinator decision MUST be recorded as a Decision
  artifact.

21. PEER MESSAGE PROTOCOL (GSP/1.0)
================================================================================

All peer messages are structured JSON documents of the form:

  {
    "protocol"   : "GSP/1.0",
    "type"       : "CANDIDATE" | "CRITIQUE" | "REPAIR" | "SCORE"
                 | "QUESTION" | "REQUIREMENT" | "TERM"
                 | "CONSOLIDATION",
    "peer_id"    : "uuid",
    "task_id"    : "uuid",
    "round_id"   : "uuid",
    "parent_ids" : ["uuid", ...],
    "confidence" : 0.0,
    "payload"    : { ... }
  }

  REQ-GSDA-PROT-001
  Every peer message MUST contain protocol, type, peer_id, task_id,
  round_id, and payload.

  REQ-GSDA-PROT-002
  Every peer message MUST be serializable as canonical JSON as defined in
  section 24.

  REQ-GSDA-PROT-003
  The coordinator MUST reject any peer message that does not conform to
  GSP/1.0.

  REQ-GSDA-PROT-004
  The coordinator MUST reject any peer message whose peer_id, task_id, or
  round_id does not match an active session.

  REQ-GSDA-PROT-005
  The coordinator MUST reject any peer message whose payload schema does
  not match its declared type.

22. ROUND MODEL
================================================================================

  Round
  {
    round_id            : string
    task_id             : string
    index               : integer
    phase               : UNDERSTAND | GENERATE | CRITIQUE | REPAIR
                        | SCORE | AGGREGATE | REFINE | ANALYZE
                        | CONVERGE | HUMAN_REVIEW | PUBLISH
    inputs              : string[]
    outputs             : string[]
    findings            : Finding[]
    decisions           : string[]
    created_at          : timestamp
  }

  REQ-GSDA-RND-001
  Every round MUST have a stable round_id.

  REQ-GSDA-RND-002
  Every round MUST record its phase.

  REQ-GSDA-RND-003
  Every round MUST record its inputs and outputs.

  REQ-GSDA-RND-004
  The coordinator MAY dynamically choose which roles participate in a
  round.

  REQ-GSDA-RND-005
  Initial candidate generation SHOULD be independent: peers SHOULD NOT
  see each other's candidates during the first generation phase unless
  the task explicitly requests collaborative generation.

  REQ-GSDA-RND-006
  After candidate generation, cross-repair MUST be permitted.

  REQ-GSDA-RND-007
  The default workflow is: generate, critique, cross-repair, score,
  aggregate, refine, analyze, converge, human review, publish. Not every
  task requires every phase, but the ordering MUST NOT be violated.

23. CONVERGENCE AND STAGNATION
================================================================================

  REQ-GSDA-CNV-001
  The coordinator MUST consider convergence reached only when all of:

    - no blocking findings remain unresolved;
    - requirement coverage has not changed for one full round;
    - terminology has not changed for one full round;
    - aggregate criterion scores have stabilised within a configured
      epsilon for one full round;
    - no new HIGH or CRITICAL findings have appeared in the last round;
    - every open question is either resolved, rejected, deferred, or
      explicitly accepted by the human.

  REQ-GSDA-CNV-002
  Stagnation MUST be detected when, for two consecutive rounds, no new
  requirements, no new findings, no new repairs, and no significant score
  movement occur.

  REQ-GSDA-CNV-003
  On stagnation, the coordinator MUST do at least one of:

    - introduce a new peer;
    - change a peer's role;
    - request a fresh independent candidate;
    - focus on adversarial analysis;
    - ask the human for clarification.

  REQ-GSDA-CNV-004
  The coordinator MUST terminate on any of:

    - human acceptance;
    - configured maximum number of rounds;
    - convergence reached;
    - stagnation without available recovery;
    - blocking ambiguity requiring human input;
    - explicit cancellation.

24. CANONICAL SERIALIZATION AND REVISION IDENTITY
================================================================================

  REQ-GSDA-CAN-001
  Canonical serialization MUST use UTF-8.

  REQ-GSDA-CAN-002
  Object keys MUST be sorted by UTF-8 bytewise order.

  REQ-GSDA-CAN-003
  Arrays MUST preserve semantic order.

  REQ-GSDA-CAN-004
  Insignificant whitespace MUST be omitted.

  REQ-GSDA-CAN-005
  Integers MUST be used for counts and identifiers. Floating-point
  numbers MUST NOT appear in identity-bearing canonical forms.

  REQ-GSDA-CAN-006
  String escaping MUST follow the JSON standard with stable output.

  REQ-GSDA-CAN-007
  A specification revision identity MUST be:

    revision_id = "sha256:" + SHA256(canonical_specification_bytes)

  REQ-GSDA-CAN-008
  Canonical specification bytes MUST include the requirement matrix, the
  glossary, the open questions, the assumptions, and the lineage, but
  MUST NOT include the revision_id itself.

25. HUMAN REVIEW
================================================================================

  REQ-GSDA-HUM-001
  A human review gate MUST exist before publication.

  REQ-GSDA-HUM-002
  The human MUST be shown: the final specification, the requirement
  matrix, open questions, blocking findings, aggregate scores with
  variance, and the revision diff.

  REQ-GSDA-HUM-003
  The human MAY accept, reject, defer, or request another round.

  REQ-GSDA-HUM-004
  Human decisions MUST be recorded as artifacts with the human's
  identity as author.

  REQ-GSDA-HUM-005
  The system MUST NOT override a human decision.

  REQ-GSDA-HUM-006
  The system MUST NOT claim acceptance on the human's behalf.

26. STATE MACHINE
================================================================================

States:

  CREATED
  INPUT_ANALYZED
  CANDIDATES_GENERATED
  CRITIQUES_COMPLETE
  REPAIRS_COMPLETE
  SCORED
  AGGREGATED
  REFINED
  ANALYZED
  CONVERGED
  HUMAN_REVIEW
  ACCEPTED
  PUBLISHED

Failure states:

  INPUT_INVALID
  PEER_FAILURE
  PROTOCOL_FAILURE
  SCHEMA_FAILURE
  INSUFFICIENT_CANDIDATES
  UNRESOLVED_CONTRADICTION
  UNRESOLVED_AMBIGUITY
  INSUFFICIENT_COVERAGE
  STAGNATION
  HUMAN_CLARIFICATION_REQUIRED
  REVIEW_REJECTED

  REQ-GSDA-STM-001
  A transition MUST be defined as (current state, event, evidence,
  guards, next state).

  REQ-GSDA-STM-002
  A bare event string is insufficient to advance state. Required
  evidence MUST exist and correspond to the exact artifact.

  REQ-GSDA-STM-003
  No failure state may transition directly to an accepted state.

  REQ-GSDA-STM-004
  ACCEPTED MUST require the human review gate.

  REQ-GSDA-STM-005
  PUBLISHED MUST require an immutable revision with a revision_id.

  REQ-GSDA-IMPL-001

  REQ-GSDA-IMPL-004
  The implementation MUST persist every artifact, finding, score, and

30. MILESTONES AND ACCEPTANCE CRITERIA
================================================================================

M0  Specification freeze
    Acceptance: this document is stored under its revision_id.

M1  Core types and canonical serializer
    Acceptance: round-trip of a fixed test vector reproduces its
    revision_id exactly.

M2  Requirement extraction
    Acceptance: every requirement in this document is extracted with its
    identifier, subject, normative_text, severity, and testability.

M3  Kernel checks
    Acceptance: each of dangling reference, coverage, glossary, open
    question, and contradiction candidate produces expected findings for
    a set of hand-crafted broken specifications.

M4  Coordinator loop
    Acceptance: a full round loop terminates deterministically for a
    fixed set of peer messages.

M5  Scoring and reliability
    Acceptance: aggregate and variance are computed; undefined cases are
    represented as UNDEFINED.

M6  Peer protocol adapter
    Acceptance: GSP/1.0 messages are accepted and rejected according to
    section 21.

M7  Human review gate
    Acceptance: publication is blocked until a human decision artifact
    exists.

M8  Self-application
    Acceptance: running the agent on GSDA/2.0 produces a package that
    passes the agent's own acceptance gate.

31. CONFORMANCE TESTS
================================================================================

Categories:

  CANONICALIZATION
  EXTRACTION
  KERNEL
  SCORING
  RELIABILITY
  STATE
  PROTOCOL
  PACKAGE
  SELF-APPLICATION

Required negative tests:

  duplicate requirement id                 -> REJECTED
  requirement without source_location      -> REJECTED
  requirement without intent_link          -> REJECTED
  requirement without testability mark     -> REJECTED
  untestable requirement without reason    -> REJECTED
  dangling reference                       -> DANGLING_REFERENCE
  blocking open question                   -> PUBLICATION_BLOCKED
  contradiction candidate unresolved       -> CONVERGENCE_BLOCKED
  malformed peer message                   -> PROTOCOL_FAILURE
  message with unknown peer_id             -> SCHEMA_FAILURE
  score value outside 0..1                 -> SCHEMA_FAILURE
  confidence outside 0..1                  -> SCHEMA_FAILURE
  aggregate denominator zero               -> UNDEFINED, not 0 or 1
  revision_id mismatch                     -> REJECTED
  package missing required file            -> REJECTED
  package published with blocking finding  -> REJECTED
  self-application fails self tests        -> FINDING_RAISED

Required positive tests:

  clean specification package accepted;
  revision_id stable across runs;
  minority CRITICAL finding triggers targeted round;
  cross-repair lineage preserved;
  reliability update deterministic for a fixed evidence set.
