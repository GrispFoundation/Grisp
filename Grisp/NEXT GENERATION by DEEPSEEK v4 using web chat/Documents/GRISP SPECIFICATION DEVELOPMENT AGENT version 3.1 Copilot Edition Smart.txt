---------------------------------------------
FOUNDATIONS, ARCHITECTURE, NORMATIVITY,
PRIORITY ORDER, SCOPE, TRUST MODEL
---------------------------------------------

INTRODUCTION
------------
The GRISP Specification Development Agent (GSDA) is a deterministic,
multi‑peer system for developing, refining, critiquing, repairing,
scoring, and publishing technical specifications. GSDA/3.1 strengthens
earlier versions by tightening identity rules, canonicalization,
provenance, and publication guarantees.

GSDA operates through a strict pipeline of trust zones, ensuring that
no peer, no model, and no consensus is ever treated as authoritative.
Only the deterministic kernel defines valid state transitions.

The system is designed for environments requiring high assurance,
auditability, reproducibility, and strict separation of semantic and
execution metadata.


---------------------------------------------
SECTION 1 — ARCHITECTURE OVERVIEW
---------------------------------------------

GSDA processes information through seven trust zones:

    T0  External Input
    T1  LLM Provider
    T2  Peer Adapter
    T3  Validated Input Store
    T4  Deterministic Kernel
    T5  Authoritative State
    T6  Human Governance
    T7  Published Revision

The normal flow is:

    T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7

No peer is trusted. No peer score is truth. No peer reliability is truth.
The kernel is the only source of deterministic identity, validation,
arithmetic, and publication predicates.


---------------------------------------------
SECTION 2 — NORMATIVITY MODEL
---------------------------------------------

GSDA distinguishes three categories of specification text:

1. Informative Prose
   - Explains concepts.
   - Does not impose mandatory behavior.
   - Must begin with “[Informative]” when containing normative keywords.

2. Normative Requirements
   - Machine-readable requirement records.
   - Each has a stable requirement_id.
   - All mandatory behavior must be expressed through these records.

3. Structured Data
   - JSON-schema-governed records representing state, identity,
     provenance, evidence, configuration, etc.

Normative keywords are strictly controlled. The allowed set is:

    MUST
    MUST NOT
    SHALL
    SHALL NOT
    SHOULD
    SHOULD NOT
    MAY
    REQUIRED
    RECOMMENDED
    NOT RECOMMENDED
    OPTIONAL

Normative keywords outside requirement blocks must appear only in:
- keyword-definition paragraphs, or
- paragraphs beginning with “[Informative]”.

Unmarked normative keywords block publication.


---------------------------------------------
SECTION 3 — PRIORITY ORDER
---------------------------------------------

GSDA resolves conflicts using a strict priority hierarchy:

1. USER_INTENT_PRESERVATION
2. CONSISTENCY
3. COMPLETENESS
4. PRECISION
5. TRACEABILITY
6. TESTABILITY
7. CLARITY
8. CONCISENESS
9. STYLE

Rules:
- When two changes conflict, the higher priority wins.
- Lower-priority improvements must not weaken higher-priority properties.
- Human governance may override priorities only with explicit rationale.


---------------------------------------------
SECTION 4 — SCOPE
---------------------------------------------

GSDA is a pure specification-development system.

IN SCOPE:
- Deterministic kernel operations
- Conformance tests
- Multi-peer reasoning
- Specification refinement and publication

OUT OF SCOPE:
- Compilation
- Execution of target programs
- Debugging
- OS-level operations
- Arbitrary network access
- Runtime inspection
- Tree-sitter or static analysis of target languages

The kernel cannot spawn processes or perform OS-boundary exports.
Only the package exporter may produce final artifacts.


---------------------------------------------
SECTION 5 — TRUST BOUNDARY MODEL
---------------------------------------------

GSDA defines strict trust zones:

    T0 External world
    T1 LLM provider
    T2 Peer adapter
    T3 Validated input store
    T4 Deterministic kernel
    T5 Authoritative state
    T6 Human acceptance
    T7 Published revision

Rules:
- Normal flow: T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7
- T1 output is always untrusted until validated.
- Only kernel operations may modify authoritative state.
- Human decisions must be validated before state changes.
- Every trust-boundary crossing must be recorded in provenance.


---------------------------------------------
SECTION 6 — PSEUDO-CODE AND DELPHI EXAMPLES
---------------------------------------------

EXAMPLE 1 — Trust-Boundary Enforcement
--------------------------------------

Pseudo-code:

function process_input(payload):
    if payload.origin != T1:
        raise ProtocolFailure("Invalid origin")

    sanitized = adapter_sanitize(payload)
    validated = kernel_validate(sanitized)
    store_to_T3(validated)


Delphi:

procedure ProcessInput(const Payload: TPayload);
begin
  if Payload.Origin <> TOrigin.T1 then
    raise EProtocolFailure.Create('Invalid origin');

  var Sanitized := Adapter.Sanitize(Payload);
  var Validated := Kernel.Validate(Sanitized);

  T3Store.Add(Validated);
end;


EXAMPLE 2 — Priority Conflict Resolution
----------------------------------------

Pseudo-code:

function resolve_conflict(changeA, changeB):
    if priority(changeA) > priority(changeB):
        return changeA
    else if priority(changeB) > priority(changeA):
        return changeB
    else
        return tie_break(changeA, changeB)


Delphi:

function ResolveConflict(const A, B: TChange): TChange;
begin
  if A.Priority > B.Priority then
    Result := A
  else if B.Priority > A.Priority then
    Result := B
  else
    Result := TieBreak(A, B);
end;

IDENTITY CLASSES, CANONICALIZATION,
SEMANTIC PROJECTION, IDENTITY ALGORITHMS
---------------------------------------------

INTRODUCTION
------------
This part defines the identity system used throughout GSDA. Identity
is central to determinism: every record, message, artifact, and
decision must be uniquely and reproducibly identifiable across runs,
peers, transports, and environments.

GSDA/3.1 enforces strict separation between semantic identity
(derived only from content) and execution identity (derived from
context such as run_id, peer_id, or round_id). Canonicalization
ensures that identity inputs are stable, ordered, and free of
implementation-defined behavior.


---------------------------------------------
SECTION 1 — IDENTITY CLASSES
---------------------------------------------

GSDA defines four identity classes:

1. SEMANTIC_DETERMINISTIC
   - Depends only on declared semantic fields.
   - Independent of run_id, peer_id, timestamps, transport, or history.

2. EXECUTION_DETERMINISTIC
   - Depends on declared execution context fields.
   - Includes run_id, peer_id, round_id, logical_sequence.

3. COORDINATOR_ASSIGNED
   - Assigned by the deterministic kernel.
   - Includes run_id and peer_id.

4. DERIVED_EXECUTION
   - Derived deterministically from execution context.
   - Includes round_id and logical_sequence.

Rules:
- Semantic identities must not depend on execution metadata.
- Execution identities must list all input fields explicitly.
- No identity may depend on implementation-defined ordering.
- Wall-clock time must never influence semantic identity.


---------------------------------------------
SECTION 2 — GLOBAL CANONICALIZATION
---------------------------------------------

GSDA uses a canonical JSON profile based on RFC 8785, with additional
constraints:

1. Object keys are ordered by UTF‑8 bytewise lexicographic order.
2. Duplicate keys are rejected.
3. NaN and Infinity are rejected.
4. Negative zero normalizes to zero.
5. Identity-bearing records must use integer JSON numbers only.
6. Floating-point values in identity-bearing records cause failure.
7. Adapter rounding (when allowed) must use round-half-to-even.
8. Timestamps use the format: YYYY-MM-DDTHH:MM:SS.sssZ
9. Sorted arrays use bytewise ordering unless otherwise specified.
10. Locale-sensitive ordering is forbidden.
11. Case folding is forbidden except where explicitly declared.
12. NFC normalization applies only where specified.

Canonicalization functions:

- canonical_record_jcs(X)
- canonical_identity_object(X)
- canonical_file_json(X)

All identity algorithms use canonical_identity_object.


---------------------------------------------
SECTION 3 — SEMANTIC PROJECTION
---------------------------------------------

Semantic projection ensures that only meaningful content contributes
to semantic identity. Operational metadata, provenance, timestamps,
and execution context must not influence content_id.

Rules:
- Every content-addressed schema must declare a semantic projection.
- Only fields listed in the projection influence content_id.
- Provenance and authentication fields are excluded unless declared.
- logical_sequence and created_at never participate.
- Two records with identical semantic projections must produce
  identical content_id.


---------------------------------------------
SECTION 4 — IDENTITY ALGORITHMS
---------------------------------------------

This section rewrites all GSDA identity algorithms in improved form.
Each identity is defined as:

    prefix + sha256_hex(canonical_identity_object({...}))

All fields must be canonicalized before hashing.

Below are rewritten definitions with pseudo-code and Delphi examples.

function ComputeTaskID(const Task: TTask): string;

  Result := 'task:' + SHA256Hex(CanonicalIdentityObject(Obj));

TASK MODEL, INTENT EXTRACTION,
SOURCE REFERENCES, PEER MODEL,
ADAPTER RULES
---------------------------------------------

INTRODUCTION
------------
This part defines how GSDA interprets user intent, structures task
records, resolves provenance, and manages peer behavior. It also
defines the adapter layer, which is responsible for sanitizing and
canonicalizing provider output before kernel validation.

GSDA enforces strict separation between:
- user intent,
- peer interpretation,
- provenance,
- adapter sanitization,
- kernel validation.

This ensures that user intent remains authoritative, peer output
remains untrusted, and all transformations are deterministic.


---------------------------------------------
SECTION 1 — TASK MODEL
---------------------------------------------

A task record describes the user’s request and the context in which
GSDA must operate. It contains:

- schema
- task_id
- target_context_id
- user_prompt
- user_intent
- intent_elements
- domain
- namespace
- target_language
- target_audience
- constraints
- requested_outputs
- priority_profile
- created_at
- metadata

Rules:
- user_intent must remain separate from peer-generated interpretations.
- The coordinator must not replace user_intent with peer inference.
- Intent extraction must be deterministic.
- Every intent element must include byte_start and byte_end offsets.


---------------------------------------------
SECTION 2 — INTENT ELEMENTS
---------------------------------------------

IntentElement fields:

- schema
- intent_id
- text
- occurrence
- occurrence_weight
- source_refs
- byte_start
- byte_end

Intent elements represent fragments of the user’s intent, extracted
deterministically from the user_prompt and user_intent fields.

Rules:
- Identical input and identical policy must produce identical elements.
- Intent extraction must not call an LLM.
- Overlapping segments must be resolved deterministically.
- Discarded segments must produce evidence.
- Unrepresentable fragments must produce intent-loss evidence.


---------------------------------------------
SECTION 3 — INTENT EXTRACTION PROCESS
---------------------------------------------

GSDA uses HYBRID segmentation:

1. Explicit marker boundaries
2. Sentence boundaries
3. RFC 2119 keyword boundaries
4. Minimum-fragment merging
5. Deterministic overlap resolution
6. Intent-loss reporting

Overlap resolution uses:
- earliest byte_start
- longest segment
- bytewise-smallest text


---------------------------------------------
SECTION 4 — SOURCE REFERENCES
---------------------------------------------

SourceRef fields:

- schema
- source_kind
- source_id
- location
- derivation_chain

Source kinds map to identity types:

USER_PROMPT       → task_id  
INPUT_DOCUMENT    → input content_id  
PEER_INFERENCE    → evidence_id  
PEER_PROPOSAL     → artifact_id  
HUMAN_DECISION    → decision_id  
DERIVED           → evidence_id  

Rules:
- Unresolved source_id causes failure.
- PEER_INFERENCE and DERIVED must include non-empty derivation chains.
- Derivation chains must be acyclic.
- Chains may not exceed 256 steps unless configured lower.
- Historical references must resolve against immutable historical state.
- Superseded artifacts remain valid provenance targets.
- Deletion of referenced objects is prohibited.


---------------------------------------------
SECTION 5 — PEER MODEL
---------------------------------------------

A peer record contains:

- schema
- peer_id
- provider
- model
- model_version
- adapter_id
- transport
- role_profile
- prompt_profile_id
- slot_index
- profile_id

Peer roles include:

- GENERATOR
- FORMALIZER
- CRITIC
- CONTRADICTION_ANALYST
- COMPLETENESS_ANALYST
- TERMINOLOGY_ANALYST
- TESTABILITY_ANALYST
- CROSS_REPAIRER
- SCORER
- ADVERSARIAL_REVIEWER
- CONSOLIDATOR

Rules:
- Every peer must have a configured peer_id.
- slot_index is assigned by bytewise sorting peer_id.
- slot_index remains stable within a run.
- Provider outages are not reasoning failures.
- Reliability is maintained per (peer_id, activity).


---------------------------------------------
SECTION 6 — ADAPTER RULES
---------------------------------------------

The adapter is the only component allowed to sanitize provider output.

Adapter pipeline:

    RAW PRESERVE
    → OPTIONAL SANITIZE
    → PARSE
    → CANONICALIZE
    → content_id
    → message_id
    → ENVELOPE
    → KERNEL VALIDATION

Rules:
- Raw response must be preserved before sanitization.
- Raw response must be retrievable via content_id.
- Adapter must not mutate envelope identity fields.
- Envelope mutation causes protocol failure.
- Adapter must not inject omitted schema defaults.
- Structural salvage is limited to:
  * leading/trailing whitespace removal
  * UTF‑8 BOM removal (when declared)
- Adapter must not:
  * auto-close brackets
  * remove trailing JSON values
  * change identifiers
  * change numeric values
  * reorder arrays
  * invent missing fields
- Malformed structure outside salvage rules causes protocol failure.
- Sanitization must emit evidence.
- BOM removal must be distinguishable.
- Floating-point rounding is allowed only when:
  * target field is integer
  * adapter contract explicitly permits conversion
- Rounding uses round-half-to-even.
- Rounding emits FLOAT_ROUNDED evidence.
- Adapter-side floating-point data must never enter authoritative records.


---------------------------------------------
SECTION 7 — PSEUDO-CODE AND DELPHI EXAMPLES
---------------------------------------------

EXAMPLE 1 — Intent Extraction (Simplified)
------------------------------------------

Pseudo-code:

function extract_intents(text):
    segments = segment(text)
    merged = merge_minimum_fragments(segments)
    resolved = resolve_overlaps(merged)
    return resolved


Delphi:

function ExtractIntents(const Text: string): TIntentList;
var
  Segments, Merged, Resolved: TIntentList;
begin
  Segments := SegmentText(Text);
  Merged := MergeMinimumFragments(Segments);
  Resolved := ResolveOverlaps(Merged);
  Result := Resolved;
end;


EXAMPLE 2 — Source Reference Resolution
----------------------------------------

Pseudo-code:

function resolve_source(ref):
    case ref.kind of
        USER_PROMPT: return task_id
        INPUT_DOCUMENT: return content_id(ref.location)
        PEER_INFERENCE: return evidence_id(ref.location)
        PEER_PROPOSAL: return artifact_id(ref.location)
        HUMAN_DECISION: return decision_id(ref.location)
        DERIVED: return evidence_id(ref.location)
    end


Delphi:

function ResolveSource(const Ref: TSourceRef): string;
begin
  case Ref.Kind of
    skUserPrompt: Result := TaskID;
    skInputDocument: Result := ContentIDFromLocation(Ref.Location);
    skPeerInference: Result := EvidenceIDFromLocation(Ref.Location);
    skPeerProposal: Result := ArtifactIDFromLocation(Ref.Location);
    skHumanDecision: Result := DecisionIDFromLocation(Ref.Location);
    skDerived: Result := EvidenceIDFromLocation(Ref.Location);
  end;
end;


EXAMPLE 3 — Adapter Sanitization
---------------------------------

Pseudo-code:

function sanitize(raw):
    cleaned = trim_whitespace(raw)
    if has_bom(cleaned):
        cleaned = remove_bom(cleaned)
        emit_evidence("BOM_REMOVED")
    return cleaned


Delphi:

function AdapterSanitize(const Raw: string): string;
var
  S: string;
begin
  S := Trim(Raw);
  if HasBOM(S) then
  begin
    S := RemoveBOM(S);
    EmitEvidence('BOM_REMOVED');
  end;
  Result := S;
end;

---------------------------------------------
MESSAGE PROTOCOL, RELIABILITY MODEL,
REPAIR MODEL, SCORING MODEL
---------------------------------------------

INTRODUCTION
------------
This part defines how peers communicate, how reliability is computed,
how repairs are generated and applied, and how scoring works. These
mechanisms ensure that GSDA can coordinate multiple untrusted peers
while maintaining deterministic behavior and traceable outcomes.

The deterministic kernel enforces strict rules for message structure,
confidence values, reliability decay, repair ordering, and scoring
aggregation. No peer is ever treated as authoritative; reliability
is always contextual, evidence-based, and bounded.


---------------------------------------------
SECTION 1 — PEER MESSAGE PROTOCOL
---------------------------------------------

Every peer message consists of an envelope and a payload.

Envelope fields:
- schema = "gsp/3.1"
- message_id
- type
- peer_id
- run_id
- task_id
- round_id
- parent_ids
- confidence
- payload

Message types:
- CANDIDATE
- CRITIQUE
- REPAIR
- SCORE
- REQUIREMENT
- TERM
- QUESTION
- CONSOLIDATION

Rules:
- Every message must contain all envelope fields.
- confidence must be an integer in the range 1..1000.
- confidence = 0 is forbidden.
- Abstention is represented by omission, not zero.
- Envelope confidence and payload confidence must match.
- Transport authentication binds the message to peer_id.
- Transport token uses HMAC-SHA256(secret, peer_id | fingerprint | round_id).
- Transport fingerprint uses sha256_hex(transport_name | adapter_id | endpoint).
- Transport name comparison is case-sensitive.
- Token verification must not affect semantic state.
- Peer_id mismatch produces impersonation evidence.
- Partially parseable but schema-invalid messages are rejected.
- ReliabilityOutcome is never a peer-authored message type.


---------------------------------------------
SECTION 2 — RELIABILITY MODEL
---------------------------------------------

Reliability is maintained per (peer_id, activity). Activities include:
- GENERATION
- CRITIQUE
- REPAIR
- SCORING
- CONSOLIDATION
- ANALYSIS roles

Reliability modes:
1. FLAT
2. DECAYING

Reliability record fields:
- schema
- reliability_id
- run_id
- peer_id
- activity
- alpha
- beta
- mode
- history
- evidence

alpha and beta are integer counters representing:
- alpha = successful outcomes
- beta = unsuccessful outcomes

Reliability score = alpha / (alpha + beta), except in DECAYING mode.


---------------------------------------------
SECTION 3 — RELIABILITY DECAYING MODE
---------------------------------------------

DECAYING mode applies a weighted decay to historical outcomes.

Let:
- α = alpha
- β = beta
- w = decay_weight (0 < w ≤ 1)

Scaled values:
- α_scaled = floor(α * w)
- β_scaled = floor(β * w)

New outcome:
- If success: α_new = α_scaled + 1, β_new = β_scaled
- If failure: α_new = α_scaled, β_new = β_scaled + 1

Rules:
- α_new and β_new must remain non-negative.
- Overflow must be prevented by floor division.
- Reliability must remain within [0, 1].
- ReliabilityOutcome records must be emitted by the kernel only.


---------------------------------------------
SECTION 4 — RELIABILITY EXAMPLES
---------------------------------------------

EXAMPLE 1 — Flat Mode
---------------------

Initial:
    alpha = 3
    beta = 1

Score:
    3 / (3 + 1) = 0.75


EXAMPLE 2 — Decaying Mode
-------------------------

Initial:
    alpha = 10
    beta = 6
    w = 0.5

Scaled:
    alpha_scaled = floor(10 * 0.5) = 5
    beta_scaled  = floor(6 * 0.5)  = 3

New failure:
    alpha_new = 5
    beta_new  = 3 + 1 = 4

Score:
    5 / (5 + 4) = 0.555...


---------------------------------------------
SECTION 5 — REPAIR MODEL
---------------------------------------------

Repairs are peer-generated proposals to fix issues in candidate
specification text. Repairs are not authoritative; they must be
validated by the kernel and may be rejected.

Repair record fields:
- schema
- repair_id
- run_id
- peer_id
- round_id
- target_artifact_id
- changes
- rationale
- confidence

Rules:
- Repairs must not introduce schema violations.
- Repairs must not weaken higher-priority properties.
- Repairs must be deterministic and reproducible.
- Repairs must reference the artifacts they modify.
- Repairs must not modify authoritative state directly.
- Kernel applies repairs only after validation.


---------------------------------------------
SECTION 6 — REPAIR ORDERING
---------------------------------------------

Repairs are ordered by:

1. priority_tipping (if present)
2. earliest logical_sequence
3. highest confidence
4. bytewise-smallest repair_id

This ensures deterministic ordering even when multiple peers propose
conflicting repairs.

Pseudo-code:

function order_repairs(list):
    sort list by:
        priority_tipping desc,
        logical_sequence asc,
        confidence desc,
        repair_id bytewise asc
    return list


Delphi:

function OrderRepairs(const L: TRepairList): TRepairList;
begin
  Result := SortByCriteria(L,
    ['priority_tipping desc',
     'logical_sequence asc',
     'confidence desc',
     'repair_id asc']);
end;


---------------------------------------------
SECTION 7 — SCORING MODEL
---------------------------------------------

Scores evaluate candidate artifacts. A score record contains:

- schema
- score_id
- run_id
- peer_id
- round_id
- target_artifact_id
- score_value (integer 1..1000)
- rationale
- confidence

Rules:
- score_value must be 1..1000.
- score_value = 0 is forbidden.
- Abstention is omission.
- Scores must be deterministic.
- Scores must not depend on transport ordering.
- Scores must not depend on timestamps.


---------------------------------------------
SECTION 8 — SCORE AGGREGATION
---------------------------------------------

Aggregation uses weighted averaging based on peer reliability.

Let:
- s_i = score from peer i
- r_i = reliability of peer i
- w_i = weight = r_i

Aggregate score:
    S = (Σ w_i * s_i) / (Σ w_i)

Rules:
- Peers with zero reliability contribute zero weight.
- Aggregation must be deterministic.
- Aggregation must not depend on peer ordering.


---------------------------------------------
SECTION 9 — SCORING EXAMPLES
---------------------------------------------

EXAMPLE 1 — Simple Weighted Average
-----------------------------------

Peer scores:
    Peer A: score = 800, reliability = 0.9
    Peer B: score = 600, reliability = 0.5

Aggregate:
    S = (0.9*800 + 0.5*600) / (0.9 + 0.5)
      = (720 + 300) / 1.4
      = 1020 / 1.4
      = 728.57


EXAMPLE 2 — Delphi Implementation
----------------------------------

function AggregateScores(const Scores: TScores): Double;
var
  SumWeighted, SumWeights: Double;
  S: TScore;
begin
  SumWeighted := 0;
  SumWeights := 0;

  for S in Scores do
  begin
    SumWeighted := SumWeighted + (S.Value * S.Reliability);
    SumWeights := SumWeights + S.Reliability;
  end;

  if SumWeights = 0 then
    Result := 0
  else
    Result := SumWeighted / SumWeights;
end;

INTRODUCTION
------------
This final part defines how GSDA evaluates coverage of user intent,
how publication is authorized, how registries are structured, and how
packages are assembled. These mechanisms ensure that specifications
are complete, traceable, testable, and reproducible.

GSDA enforces strict rules for:
- intent coverage,
- publication gating,
- registry uniqueness,
- glossary term normalization,
- package structure and hashing.

This ensures that published specifications are deterministic,
auditable, and free of accidental omissions.


---------------------------------------------
SECTION 1 — COVERAGE MODEL
---------------------------------------------

Coverage measures how well the candidate specification addresses the
user’s intent. Coverage is computed over intent elements extracted
from user_prompt and user_intent.

Coverage record fields:
- schema
- coverage_id
- run_id
- task_id
- round_id
- total_intent_elements
- linked_intent_elements
- critical_intent_elements
- critical_coverage
- uncovered_offsets
- evidence

Definitions:
- total_intent_elements: number of extracted intent fragments.
- linked_intent_elements: fragments linked to artifacts or requirements.
- critical_intent_elements: fragments marked critical by policy.
- critical_coverage = linked_critical / total_critical.

Rules:
- Coverage must be deterministic.
- Coverage must not depend on peer ordering.
- Coverage must include byte offsets for uncovered fragments.
- Critical coverage below 1.0 blocks publication unless overridden.
- Overrides must name affected intent_ids and include rationale.

SECTION 3 — PUBLICATION PIPELINE
---------------------------------------------

Publication is a multi-stage deterministic process:

1. Freeze candidate package
2. Compute spec_content_id
3. Validate publication predicates
4. Apply human acceptance
5. Commit revision atomically
6. Produce published revision

Publication predicates include:
- schema validity
- identity consistency
- coverage thresholds
- traceability completeness
- glossary normalization
- registry uniqueness
- absence of normative keyword leaks
- absence of unresolved references
- absence of protocol failures
- absence of adapter failures
- absence of critical findings
- valid human acceptance signature

Rules:
- Predicates must be evaluated independently.
- Predicate evaluation must be deterministic.
- Publication must not modify authoritative state except through
  validated kernel operations.
- Publication must commit the frozen package atomically.
- Revision lineage must be updated deterministically.


---------------------------------------------
SECTION 4 — PUBLICATION PSEUDO-CODE
---------------------------------------------

Pseudo-code:

function publish(package):
    frozen = freeze(package)
    spec_id = compute_spec_content_id(frozen)

    if not validate_predicates(frozen):
        raise PublicationFailure

    if not human_accepts(frozen):
        raise HumanRejection

    revision = commit_revision(frozen, spec_id)
    return revision


Delphi:

function Publish(const Package: TPackage): TRevision;
var
  Frozen: TPackage;
  SpecID: string;
begin
  Frozen := FreezePackage(Package);
  SpecID := ComputeSpecContentID(Frozen);

  if not ValidatePredicates(Frozen) then
    raise EPublicationFailure.Create('Predicate failure');

  if not HumanAccepts(Frozen) then
    raise EHumanRejection.Create('Human rejection');

  Result := CommitRevision(Frozen, SpecID);
end;
