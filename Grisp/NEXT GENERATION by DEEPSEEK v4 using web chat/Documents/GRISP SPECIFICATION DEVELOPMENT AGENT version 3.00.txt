=====================================
GRISP SPECIFICATION DEVELOPMENT AGENT
GSDA/3.0
=====================================

Identifier:  GSDA/3.0
Status:      Proposed normative specification
Supersedes:  GSDA/2.13 and all earlier GSDA revisions
Purpose:     Cooperative development, analysis, critique, repair, refinement,
scoring, convergence, publication, and deterministic replay of
technical specifications using multiple untrusted LLM reasoning
peers under a deterministic kernel.
Domain:      Pure specification development.
Non-domain:  Compilation, execution, debugging, runtime inspection, LSP,
tree-sitter, static analysis of target programs, OS execution,
GRISP execution, arbitrary external software-development tools,
arbitrary network access.
Default:     Fail-closed for structural, identity, integrity, governance,
resource, and publication errors.

GSDA/3.0 is a major hardening and formalization release.

The architecture remains:

UNTRUSTED LLM PEERS
|
v
ADAPTERS
|
v
VALIDATED INPUTS
|
v
DETERMINISTIC KERNEL
|
v
AUTHORITATIVE STATE
|
v
HUMAN GOVERNANCE
|
v
PUBLISHED

3.0 resolves contradictions in 2.13 and adds explicit executable
contracts for identity domains, logical ordering, package staging,
bootstrap trust, content projections, resource limits, evidence,
reference semantics, and publication predicates.

===============================================
0. NORMATIVITY, KEYWORDS, AND META-REQUIREMENTS
===============================================

[Informative] GSDA distinguishes:

NORMATIVE REQUIREMENT
A machine-readable Requirement record with a stable requirement_id.

INFORMATIVE TEXT
Explanatory prose. Normative keywords appearing in such prose are
non-normative only when the paragraph begins with [Informative].

DATA
Structured values representing state, evidence, provenance,
identifiers, measurements, or other values.

[Informative] Normative keywords are interpreted according to RFC 2119 and
RFC 8174.

REQ-GSDA-META-001
Every mandatory GSDA behaviour MUST be represented as a Requirement
record, except the META-00xx bootstrap family defined by
meta_requirement/1.0.

REQ-GSDA-META-002
Every structured GSDA record MUST declare its schema identifier.

REQ-GSDA-META-003
A record with an unknown schema identifier or unsupported schema version
MUST be rejected with SCHEMA_FAILURE.

REQ-GSDA-META-004
Every structured record type MUST have an entry in the authoritative
schema registry.

REQ-GSDA-META-005
The schema language MUST be JSON Schema Draft 2020-12.

REQ-GSDA-META-006
A schema MUST declare additionalProperties = false unless it explicitly
declares a single extension object named x_gsda_ext and the registry
marks that schema as extensible.

REQ-GSDA-META-007
An unrecognized property MUST cause SCHEMA_FAILURE unless the property
is contained within an explicitly permitted x_gsda_ext object.

REQ-GSDA-META-008
The rendered specification MUST be derived from spec.requirements.json.
The rendered specification MUST NOT introduce mandatory behaviour absent
from the requirement set.

REQ-GSDA-META-009
The META-00xx bootstrap family MUST be validated in bootstrap pass zero
using the kernel-trusted meta_requirement/1.0 schema.

REQ-GSDA-META-010
After bootstrap pass zero, all Requirement records including META-00xx
MUST be validated by the ordinary schema-validation path.

REQ-GSDA-META-011
A requirement_id MUST be globally unique within a specification.
Duplicate requirement_id values MUST cause SCHEMA_FAILURE.

REQ-GSDA-META-012
The package MUST contain a normative-keyword linter named
RunNormativeKeywordLinter.

REQ-GSDA-META-013
RunNormativeKeywordLinter MUST scan every prose file included in the
publishable package.

REQ-GSDA-META-014
The linter MUST recognize exactly this normative keyword set:

MUST
MUST NOT
SHALL
SHALL NOT
SHOULD
SHOULD NOT
MAY
REQUIRED
RECOMMENDED
NOT RECOMMENDED
OPTIONAL

REQ-GSDA-META-015
A normative keyword appearing outside a Requirement record MUST either:

(a) be in an exempt keyword-definition paragraph, or
(b) be in a paragraph beginning with [Informative].

REQ-GSDA-META-016
A linter occurrence not satisfying REQ-GSDA-META-015 MUST produce
NORMATIVE_KEYWORD_LEAK and MUST block publication.

REQ-GSDA-META-017
Requirement boundaries for linter purposes MUST be established solely
from the requirement_id values in spec.requirements.json.

REQ-GSDA-META-018
A rendered block is a Requirement block only when its first token is a
requirement_id present in spec.requirements.json.

REQ-GSDA-META-019
The linter MUST NOT perform semantic classification of prose.

REQ-GSDA-META-020
The package MUST ship a machine-readable registry containing error codes,
named failures, evidence kinds, identity classes, and publication
predicates.

====================
1. DESIGN PRINCIPLES
====================

[Informative] GSDA is based on the separation:

PEER REASONING
produces proposals, findings, scores, evidence, and analysis.

KERNEL REASONING
produces deterministic facts, validates structure, computes
identities, performs aggregation, and controls state transitions.

HUMAN GOVERNANCE
resolves epistemic uncertainty and accepts or rejects publication.

REQ-GSDA-PRI-001
When two candidate changes conflict regarding specification quality, the
coordinator MUST prefer the higher-priority property.

REQ-GSDA-PRI-002
The quality priority order is:

1. USER_INTENT_PRESERVATION
2. CONSISTENCY
3. COMPLETENESS
4. PRECISION
5. TRACEABILITY
6. TESTABILITY
7. CLARITY
8. CONCISENESS
9. STYLE

REQ-GSDA-PRI-003
A lower-priority preference MUST NOT silently weaken a higher-priority
property.

REQ-GSDA-PRI-004
The quality priority order MUST NOT determine round ordering, peer
scheduling, or unrelated resource allocation.

REQ-GSDA-PRI-005
An operation-specific tie-break MUST be applied only after the priority
order fails to distinguish the alternatives.

REQ-GSDA-PRI-006
A coordinator Decision resolving a quality conflict MUST record the
priority_tipping value.

REQ-GSDA-PRI-007
Only an authorized HumanDecision MAY explicitly override the priority
order.

REQ-GSDA-PRI-008
A priority override MUST identify the affected priorities and provide
a non-empty rationale.

========
2. SCOPE
========

REQ-GSDA-SCOPE-001
GSDA MUST remain a specification-development system.

REQ-GSDA-SCOPE-002
GSDA MUST NOT require a compiler, target runtime, debugger, language
server, tree-sitter, target-program static analyzer, or arbitrary
external software-development tool for GSDA conformance.

REQ-GSDA-SCOPE-003
Execution of GSDA's own deterministic conformance suite is in scope.

REQ-GSDA-SCOPE-004
Execution of any target program or implementation artifact being
specified is out of scope.

REQ-GSDA-SCOPE-005
Only explicitly configured LLM peer providers MAY be contacted over a
network.

REQ-GSDA-SCOPE-006
The deterministic kernel MUST NOT invoke arbitrary network endpoints.

REQ-GSDA-SCOPE-007
The deterministic kernel MUST NOT spawn processes or open sockets.

REQ-GSDA-SCOPE-008
Package export MAY perform OS-boundary operations only through the
package exporter component.

REQ-GSDA-SCOPE-009
The package exporter MUST NOT mutate authoritative coordinator state.

=======================
3. TRUST BOUNDARY MODEL
=======================

Trust zones:

T0  External world
T1  LLM provider
T2  Peer adapter
T3  Validated input store
T4  Deterministic kernel
T5  Authoritative state
T6  Human acceptance
T7  Published revision

REQ-GSDA-TRUST-001
The normal data flow MUST be:

T0 -> T1 -> T2 -> T3 -> T4 -> T5 -> T6 -> T7

REQ-GSDA-TRUST-002
T5 MAY be read by T4 through defined kernel read operations.

REQ-GSDA-TRUST-003
T1 MUST NOT directly communicate with T4.

REQ-GSDA-TRUST-004
T1 MUST NOT directly write T5.

REQ-GSDA-TRUST-005
T2 MUST NOT write T5.

REQ-GSDA-TRUST-006
A peer adapter MAY write only to T3.

REQ-GSDA-TRUST-007
Every transition across a trust boundary MUST be represented in
provenance.

REQ-GSDA-TRUST-008
The kernel MUST treat every payload originating at T1 as untrusted until
validated.

REQ-GSDA-TRUST-009
No T1 payload may directly become authoritative state.

REQ-GSDA-TRUST-010
Authoritative state MUST be produced only by a kernel operation acting on
validated T3 inputs.

REQ-GSDA-TRUST-011
A kernel input lacking validated T3 provenance MUST be rejected with
PROTOCOL_FAILURE.

===================================
4. TERMINOLOGY AND IDENTITY CLASSES
===================================

[Informative] 3.0 distinguishes semantic identity from execution identity.
This removes the 2.13 contradiction between deterministic identity and
run-scoped identifiers.

Identity classes:

SEMANTIC_DETERMINISTIC
Reproducible from semantic content only.

EXECUTION_DETERMINISTIC
Reproducible from an identical recorded execution context.

COORDINATOR_ASSIGNED
Assigned by the coordinator.

DERIVED_EXECUTION
Deterministically derived from execution identity.

REQ-GSDA-IDC-001
SEMANTIC_DETERMINISTIC identities MUST NOT depend on run_id, peer_id,
round_id, wall-clock time, random values, transport state, or mutable
history.

REQ-GSDA-IDC-002
The following identities MUST be SEMANTIC_DETERMINISTIC:

task_id
content_id
spec_content_id
term_record_id
file_content_id

REQ-GSDA-IDC-003
The following identities MUST be EXECUTION_DETERMINISTIC:

message_id
artifact_id
evidence_id
decision_id
finding_id
assumption_id
question_id
reliability_outcome_id

REQ-GSDA-IDC-004
run_id and peer_id MUST be COORDINATOR_ASSIGNED.

REQ-GSDA-IDC-005
round_id MUST be DERIVED_EXECUTION.

REQ-GSDA-IDC-006
A deterministic identity formula MUST enumerate its complete input set.

REQ-GSDA-IDC-007
An undeclared identity input MUST NOT influence the identity.

REQ-GSDA-IDC-008
A deterministic identity MUST NOT depend on an implementation-defined
value.

REQ-GSDA-IDC-009
A deterministic identity MUST NOT depend on a wall-clock timestamp.

6. CANONICALIZATION
===================

REQ-GSDA-NORM-001
GSDA canonical JSON MUST be based on RFC 8785 with these GSDA rules:

* duplicate keys rejected before canonicalization;
* NaN rejected;
* Infinity rejected;
* negative zero normalized to zero;
* integer JSON values represented without exponent notation;
* floating-point values forbidden in identity-bearing records;
* object keys ordered by UTF-8 bytewise lexicographic order.

REQ-GSDA-NORM-002
The GSDA UTF-8 bytewise object-key order MUST supersede RFC 8785
UTF-16 code-unit key ordering.

REQ-GSDA-NORM-003
A GSDA implementation MUST NOT use an RFC 8785 library unchanged when
that library does not implement GSDA's UTF-8 bytewise ordering.

REQ-GSDA-NORM-004
canonical_record_jcs(X) MUST canonicalize a persisted GSDA record
including its schema property.

REQ-GSDA-NORM-005
canonical_identity_object(X) MUST canonicalize a transient identity
preimage using the same numeric, key-order, duplicate-key, and Unicode
rules as canonical_record_jcs.

REQ-GSDA-NORM-006
canonical_identity_object MUST NOT require X to be a registered
persisted record.

REQ-GSDA-NORM-007
canonical_file_json(X) MUST canonicalize parsed JSON without schema
injection.

REQ-GSDA-NORM-008
A GSDA record containing an identity-bearing floating-point number MUST
be rejected with SCHEMA_FAILURE.

REQ-GSDA-NORM-009
A non-identity-bearing float MAY occur only in a schema explicitly
declaring float_tolerant = true.

REQ-GSDA-NORM-010
No schema in GSDA/3.0 MAY declare float_tolerant = true unless the
schema registry explicitly permits it.

REQ-GSDA-NORM-011
Unicode NFC normalization MUST be used for configured term comparison.

REQ-GSDA-NORM-012
NFC normalization for term comparison MUST NOT modify the stored term
text.

REQ-GSDA-NORM-013
Term normalization MUST be:

NFC
-> trim
-> Unicode casefold
-> collapse internal whitespace runs to "-"
-> replace remaining non [a-z0-9-] with "-"
-> collapse consecutive "-"
-> strip leading and trailing "-"
-> lowercase

REQ-GSDA-NORM-014
An empty normalized term_id MUST cause SCHEMA_FAILURE.

REQ-GSDA-NORM-015
All identity-bearing integer divisions MUST be floor divisions.

REQ-GSDA-NORM-016
All timestamps MUST use:

YYYY-MM-DDTHH:MM:SS.sssZ

REQ-GSDA-NORM-017
A timestamp MUST NOT participate in a SEMANTIC_DETERMINISTIC identity.

REQ-GSDA-NORM-018
A timestamp MUST NOT be used as an authoritative ordering key.

REQ-GSDA-NORM-019
For textual UTF-8 package files, canonical file bytes MUST be:

strip leading UTF-8 BOM
normalize CRLF and CR to LF
apply Unicode NFC
encode UTF-8

REQ-GSDA-NORM-020
For binary package files, canonical file bytes MUST be the original
bytes without Unicode decoding, NFC normalization, BOM removal, or
line-ending conversion.

REQ-GSDA-NORM-021
The package manifest MUST record whether each file is canonicalized as
JSON, UTF-8 text, or binary.

REQ-GSDA-NORM-022
A media-type declaration incompatible with the selected canonicalization
mode MUST cause SCHEMA_FAILURE.

REQ-GSDA-NORM-023
file_content_id MUST use the file_content/1.0 identity formula.

===================================
8. LOGICAL ORDERING AND DETERMINISM
===================================

REQ-GSDA-ORD-001
Wall-clock timestamps MUST NOT determine authoritative ordering.

REQ-GSDA-ORD-002
The coordinator MUST maintain a monotonically increasing
logical_sequence within each run.

REQ-GSDA-ORD-003
logical_sequence MUST be assigned only by the coordinator.

REQ-GSDA-ORD-004
logical_sequence MUST be persisted as authoritative provenance for
events whose order affects deterministic decisions.

REQ-GSDA-ORD-005
A fresh execution MAY have different timestamp values from another

status

status:

UNDEFINED

For criterion k and artifact r:

Participating(i,r,k) iff
score exists
AND confidence >= 1
AND peer is not excluded by self-score rule.

N(r,k) =
sum R(i,k) * C(i,r,k) * W(k) * S(i,r,k)

D(r,k) =
sum R(i,k) * C(i,r,k) * W(k)

If D(r,k) > 0:

denom(r,k) = D(r,k)

A_rem(r,k) = sum(S) mod n
denom(r,k) = n
status = DEFINED
emit LOW_RELIABILITY_AGGREGATE

A(r,k) = 0
A_rem(r,k) = 0
denom(r,k) = 0
status = UNDEFINED

Overall:

K = defined criteria

If K is empty:

status = UNDEFINED

Else:

N(r) =
sum w(k) * (A(r,k) * denom(r,k) + A_rem(r,k))

D(r) =
sum w(k) * denom(r,k)

A(r) = N(r) div D(r)
A_rem(r) = N(r) mod D(r)
denom(r) = D(r)
status = DEFINED

===========================================
59. INFORMATIVE: WHAT GSDA DOES NOT PROMISE
===========================================

[Informative] GSDA does not promise objective truth in arbitrary domains.

[Informative] GSDA does not promise deterministic LLM generation.

[Informative] GSDA does not guarantee complete specification coverage.

[Informative] GSDA does not treat consensus as proof.

[Informative] GSDA does not treat reliability as truth.

[Informative] GSDA does not claim real-world independence between model
responses.

[Informative] GSDA does not eliminate the need for human judgment.

[Informative] GSDA does provide deterministic coordinator semantics,
immutable provenance, explicit uncertainty, reproducible identities,
bounded resource usage, deterministic replay, governed publication,
and machine-checkable conformance.

====================================
60. INFORMATIVE: CENTRAL ABSTRACTION
====================================

[Informative] The central abstraction is:

LLMs produce evidence.
Adapters normalize transport.
The kernel produces deterministic facts.
The coordinator produces authoritative state.
Reliability weights qualifying evidence.
Humans resolve epistemic uncertainty.
The revision is the governed specification.

[Informative] No single peer is the specification.

[Informative] No single peer is the reviewer.

[Informative] No score is truth.

[Informative] No consensus is proof.

[Informative] No reliability value is authority.

[Informative] The process is:

PROPOSE
-> CRITICIZE
-> SCORE
-> AGGREGATE
-> REPAIR
-> RESCORE
-> ANALYZE
-> REFINE
-> REPEAT
-> HUMAN REVIEW
-> STAGE
-> FREEZE
-> PUBLISH

===================
61. FINAL PRINCIPLE
===================

[Informative] GSDA is a deterministic governance shell around
non-deterministic reasoning workers.

[Informative] The quality objective is not to discover a mythical
perfect LLM.

[Informative] The quality objective is to construct a process in which
multiple imperfect reasoning systems can expose errors, preserve useful
disagreement, improve candidate specifications, and converge toward a
human-governed revision without allowing any individual model to become
the authority.

[Informative] Determinism belongs to the kernel.

[Informative] Reasoning belongs to the peers.

[Informative] Authority belongs to the governance process.

[Informative] Publication belongs to the package commitment and human
acceptance gate.
