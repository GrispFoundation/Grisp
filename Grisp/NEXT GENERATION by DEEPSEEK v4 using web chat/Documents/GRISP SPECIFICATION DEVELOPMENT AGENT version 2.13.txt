0. NORMATIVITY, KEYWORD SEMANTICS, AND META-REQUIREMENTS
================================================================================

[Informative] GSDA distinguishes three classes of text:

  NORMATIVE REQUIREMENT
    A machine-readable Requirement record with a stable requirement_id.

  INFORMATIVE TEXT
    Explanatory prose that does not itself impose mandatory behaviour.
    Any normative keyword that appears inside informative text MUST be
    preceded by the marker [Informative] as the first token of its
    paragraph per REQ-GSDA-NORM-013.

  DATA
    Structured values such as scores, terminology, provenance, revision
    metadata.

Only NORMATIVE REQUIREMENT records are mandatory.

[Informative] Keyword semantics (RFC 2119 + RFC 8174):

  MUST, SHALL, REQUIRED
      Required for conformance.

  MUST NOT, SHALL NOT
      Forbidden for conformance.

  SHOULD, RECOMMENDED
      Recommended. Deviation requires recorded rationale.

  SHOULD NOT, NOT RECOMMENDED
      Recommended prohibition.

  MAY, OPTIONAL
      Optional. No conformance penalty.

REQ-GSDA-META-0001
Every mandatory GSDA behaviour MUST be represented as a Requirement
record, except the META-00xx family itself, which uses schema
meta_requirement/1.0 as axiomatic bootstrap per REQ-GSDA-META-0011.

REQ-GSDA-META-0002
Every structured record MUST declare its schema version.

REQ-GSDA-META-0003
A record whose schema version does not match a known schema MUST be
rejected with SCHEMA_FAILURE.

REQ-GSDA-META-0004
A GSDA-conformant published specification MUST ship with every path
listed in REQUIRED_PACKAGE_PATHS defined by REQ-GSDA-PKG-000.

REQ-GSDA-META-0005
Every structured record type MUST have an entry in the schema
registry.

REQ-GSDA-META-0006
The schema language is JSON Schema Draft 2020-12. Future draft
additions require a major version bump and a migration record per
REQ-GSDA-MIG-001.

REQ-GSDA-META-0007
Every schema MUST declare additionalProperties = false unless the
schema explicitly provides an extension object named x_gsda_ext.

REQ-GSDA-META-0008
An unrecognized additional property MUST cause SCHEMA_FAILURE.

REQ-GSDA-META-0009
Any normative keyword appearing outside a Requirement record MUST be
backed by a Requirement record and MUST be marked [Informative] as
the first token of its paragraph in the rendered document.

REQ-GSDA-META-0010
The published specification MUST be derived from
spec.requirements.json. The prose form is a rendering and MUST NOT
introduce normative content not present in the requirement set.

REQ-GSDA-META-0011
The META-00xx family uses schema meta_requirement/1.0, which is
pre-validated by ValidateBootstrapMeta (see REQ-GSDA-KER-015) and
exempt from full-validation during bootstrap pass 0. After pass 0,
META records MUST be validated by the same JSON Schema validator as
other Requirement records. The bootstrap set is limited to META-00xx
only.

REQ-GSDA-META-0012
requirement_id MUST be unique across the entire requirement set of a
specification. A duplicated requirement_id MUST cause SCHEMA_FAILURE.

REQ-GSDA-META-0013
The specification MUST ship a linter, CheckNormativeKeywords, whose
behaviour is defined as follows:

  - It scans every prose file shipped in the package.
  - It MUST detect every occurrence of the keywords MUST, MUST NOT,
    SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, REQUIRED, RECOMMENDED,
    NOT RECOMMENDED, OPTIONAL.
  - Every detected occurrence MUST either:
      (a) appear inside a Requirement record, or
      (b) be preceded by an explicit [Informative] marker as the first
          token of its paragraph per REQ-GSDA-NORM-013.
  - The keyword definitions paragraph in Section 0 and every
    [Informative] marker MUST be exempt from detection.
  - Any occurrence that is neither MUST cause a linter failure with
    code NORMATIVE_KEYWORD_LEAK and MUST prevent publication.

REQ-GSDA-META-0014
The linter CheckNormativeKeywords MUST be executed as part of the
publication gate per Section 39.

REQ-GSDA-META-0015
The specification identifier GSDA and the family name GRISP MUST both
appear in the glossary. GRISP MUST be defined as the family; GSDA
MUST be defined as the concrete specification-development instance
within that family.

REQ-GSDA-META-0016
The keyword definitions in Section 0 are the authoritative keyword
set for the linter in REQ-GSDA-META-0013. Any keyword not listed
there MUST NOT be treated as normative for conformance purposes.

REQ-GSDA-META-0017
Bootstrap pass 0 consists solely of validating the META-00xx family
against schema meta_requirement/1.0 using kernel operation
ValidateBootstrapMeta. Pass 0 ends when no META record remains
unvalidated. Pass 1 begins with full requirement set validation.

REQ-GSDA-META-0018
The prose form of GSDA MUST NOT contain an unmarked normative keyword
outside a Requirement record. Prose that describes mandatory
behaviour MUST be rendered as either a Requirement record or an
[Informative] paragraph with a cross-reference to the backing
Requirement record.

REQ-GSDA-META-0019
CheckNormativeKeywords MUST determine requirement boundaries as
follows:

  - The linter MUST consume spec.requirements.json as the authoritative
    list of requirement_id values.
  - A rendered paragraph is treated as a Requirement record only when
    its first token is a requirement_id present in that list.
  - A rendered block whose first token is a requirement_id present in
    the list is exempt from keyword detection for the entire block,
    up to the next blank line followed by a non-indented token.
  - The linter MUST NOT attempt semantic classification of prose.

1. PRIORITY ORDER
================================================================================

  1. USER INTENT PRESERVATION
  2. CONSISTENCY
  3. COMPLETENESS
  4. PRECISION
  5. TRACEABILITY
  6. TESTABILITY
  7. CLARITY
  8. CONCISENESS
  9. STYLE

REQ-GSDA-PRI-001
When two candidate changes conflict with respect to specification
quality, the coordinator MUST prefer the higher-priority property
unless the human explicitly decides otherwise.

REQ-GSDA-PRI-002
A lower-priority improvement MUST NOT silently weaken a higher-
priority property.

REQ-GSDA-PRI-003
Where the priority order does not distinguish two alternatives, the
coordinator MUST use the operation's separately defined deterministic
tie-breaking rule.

REQ-GSDA-PRI-004
The priority order MUST NOT be applied outside genuine quality
conflicts. It does not determine round ordering or peer scheduling.

REQ-GSDA-PRI-005
When two operations are in scope for a quality conflict, the priority
order MUST be evaluated before any operation-specific tie-breaking
rule. The tie-breaking rule is invoked only when the priority order
leaves the alternatives equal.

REQ-GSDA-PRI-006
An operation-specific tie-breaking rule that would contradict the
priority order MUST NOT be applied.

REQ-GSDA-PRI-007
When a coordinator Decision resolves a quality conflict, the Decision
record MUST set priority_tipping to the Section 1 priority value that
tipped the choice. priority_tipping MUST be one of the enumerated
values. The value MUST belong to the same priority tier or higher
than every property being weakened; a priority_tipping that would
weaken a higher-tier property is invalid and MUST cause
GOVERNANCE_FAILURE.

REQ-GSDA-PRI-008
The priority order MUST NOT be silently overridden by a peer score,
a reliability value, or a repairer preference. Only a HumanDecision
MAY override the order, and the override MUST be recorded with the
affected priority values.

================================================================================
2. SCOPE
================================================================================

[Informative] In scope: specification creation, refinement, requirements
extraction, requirements formalization, alternative formulation,
contradiction detection, ambiguity detection, completeness analysis,
terminology management, traceability, testability analysis, consistency
analysis, cross-repair, scoring, reliability estimation, revision
management, convergence detection, human review, publication,
deterministic replay, execution of GSDA's own deterministic conformance
tests.

[Informative] Out of scope: compilation, execution, debugging, or
runtime testing of any target program or implementation artifact being
specified; LSP; tree-sitter; static analysis of target programs; OS
access; sandboxing of target programs; GRISP execution; arbitrary
network access.

[Informative] Permitted network use: GSDA MAY communicate with
explicitly configured LLM peer providers. GSDA MUST NOT invoke
arbitrary external implementation or execution tools. The backing
requirements are REQ-GSDA-SCOPE-004 and REQ-GSDA-SCOPE-005.

[Informative] Package export (see Section 40) is an OS-boundary
operation performed by a package exporter component outside the
deterministic kernel.

REQ-GSDA-SCOPE-001
GSDA MUST remain a pure specification-development system.

REQ-GSDA-SCOPE-002
GSDA MUST NOT require a compiler, runtime, debugger, language server,
tree-sitter, static analyzer, OS execution environment, or external
software-development tool to determine GSDA conformance.

REQ-GSDA-SCOPE-003
Execution of GSDA's own deterministic conformance tests is in scope.
Execution of any target program or implementation artifact being
specified is out of scope.

REQ-GSDA-SCOPE-004
GSDA MUST NOT invoke arbitrary external implementation or execution
tools. Only explicitly configured LLM peer providers MAY be contacted
over the network.

REQ-GSDA-SCOPE-005
Package export MUST be performed by a package exporter component.
The deterministic kernel MUST NOT perform OS-level file I/O outside
its own stores.

3. ERROR, EVIDENCE, AND FAILURE TAXONOMY
================================================================================

3.1 Error Record

  schema                "error/1.0"
  code                  one of the enumerated codes in 3.2
  category              one of SCHEMA | PROTOCOL | IDENTITY | RESOURCE
                        | GOVERNANCE | LIVENESS | PUBLICATION
  message_template      deterministic string, no peer-supplied content
  failing_id            optional identifier
  created_at            timestamp

3.2 Enumerated Error Codes and Category Mapping

  SCHEMA_FAILURE              category: SCHEMA
      schema version mismatch, additionalProperties violation, float
      or duplicate-key rejection, empty term_id after normalization,
      duplicate requirement_id, meta_requirement validation failure,
      config sub-schema missing, config value out of bounds.

  PROTOCOL_FAILURE            category: PROTOCOL
      malformed peer envelope, out-of-range confidence, missing
      required fields, duplicate conflicting message_id, partially
      parseable schema-invalid message, adapter envelope mutation.

  IMPERSONATION_ATTEMPT       category: IDENTITY
      transport-bound peer_id does not match the envelope peer_id.

  IDENTITY_MISMATCH           category: IDENTITY
      declared artifact_id does not match recomputed artifact_id.

  CONTENT_IDENTITY_MISMATCH   category: IDENTITY
      declared content_id does not match recomputed content_id.

  SOURCE_REFERENCE_UNRESOLVED category: IDENTITY
      a SourceRef.source_id does not resolve per REQ-GSDA-SRC-001, or
      a derivation_chain contains a non-resolving step_id or a cycle,
      or exceeds SRC-004 max length.

  SCOPE_VIOLATION             category: RESOURCE
      a kernel operation attempted to access a resource outside its
      permitted stores per REQ-GSDA-KER-005.

  INPUT_BOUNDS_EXCEEDED       category: RESOURCE
      a score, confidence, or weight exceeds the configured
      aggregation_bounds.

  AGGREGATION_BOUNDS_EXCEEDED category: RESOURCE
      an intermediate value N(r,k), D(r,k), N(r), D(r), a variance
      sum-of-squares term, or a cross-multiplication product exceeds
      the signed 128-bit range.

  RELIABILITY_BOUNDS_EXCEEDED category: RESOURCE
      after decay, alpha' or beta' would be negative, or
      alpha' + beta' would exceed maximum_reliability_evidence, or
      s + f would exceed maximum_reliability_evidence.

  GOVERNANCE_FAILURE          category: GOVERNANCE
      missing or invalid human acceptance; mutation of a PUBLISHED
      revision; unauthorized capability use; acceptance with
      unresolved blocking findings; undefined state transition;
      required rubric absent; quorum unmet; invalid priority_tipping;
      override that does not name a current blocking condition.

  LIVENESS_FAILURE            category: LIVENESS
      the scheduler cannot make progress for
      liveness_policy.max_stagnant_rounds consecutive rounds.

  PUBLICATION_FAILURE         category: PUBLICATION
      the publication gate refuses to release a revision.

  NORMATIVE_KEYWORD_LEAK      category: PUBLICATION
      the linter per REQ-GSDA-META-0013 detects a normative keyword
      outside a Requirement record without an [Informative] marker.

  CROSS_REFERENCE_UNRESOLVED  category: PUBLICATION
      the cross-reference linter detects a requirement_id cited
      anywhere in the package that does not resolve.

  CONFIG_INCOMPLETE           category: PUBLICATION
      the config completeness linter detects an unresolved
      "configured X" reference.

  TERM_COLLISION              category: SCHEMA
      two Term records differ only by Unicode normalization applied
      to their term field.

  LINEAGE_FAILURE             category: IDENTITY
      the lineage graph contains a cycle, references a missing
      parent, or an ancestor_chain_hash mismatch is detected.

3.3 Named Failures

Named failures are identifiers used in decision records, round
records, and evidence to describe a state. They are a distinct
namespace from error codes and MUST be prefixed with F_ when emitted.

  F_INPUT_INVALID
  F_PEER_FAILURE
  F_PROTOCOL_DEGRADED
  F_INSUFFICIENT_CANDIDATES
  F_INSUFFICIENT_PEERS
  F_UNRESOLVED_CONTRADICTION
  F_UNRESOLVED_AMBIGUITY
  F_INSUFFICIENT_COVERAGE
  F_STAGNATION
  F_HUMAN_CLARIFICATION_REQUIRED
  F_REVIEW_REJECTED
  F_PUBLICATION_BLOCKED
  F_DUPLICATE_MESSAGE_CONFLICT
  F_NO_VIABLE_ARTIFACT

3.4 Evidence Kinds

Evidence kinds are values of the evidence_kind field of an evidence
record. They are a third namespace.

  LOW_RELIABILITY_AGGREGATE
  LIVENESS_PROMOTION
  RELIABILITY_SATURATION
  FLOAT_ROUNDED
  OVERLAP_DISCARDED
  INTENT_LOSS_DETECTED
  ADAPTER_SANITIZED
  STRUCTURAL_SALVAGE
  DERIVATION_CHAIN_VERIFIED
  ALTERNATE_VIABLE_PROMOTION
  REPAIR_QUOTA_APPLIED
  COVERAGE_REPORT
  SNAPSHOT_ROUND_CONTEXT
  LOW_PRECISION_COMPARISON
  INVARIANT_VIOLATION
  COMPLIANCE_LEVEL_DECLARED

3.5 Requirements

REQ-GSDA-ERR-001
All failures MUST be emitted as an Error record conforming to
error/1.0 with one of the enumerated codes in Section 3.2 and one
category from the same section. Error codes, named failures, and
evidence kinds are three disjoint namespaces.

REQ-GSDA-ERR-002
SCHEMA_FAILURE MUST be used only for the schema and canonicalization
conditions listed in Section 3.2.

REQ-GSDA-ERR-003
PROTOCOL_FAILURE MUST be used only for the protocol conditions
listed in Section 3.2.

REQ-GSDA-ERR-004
IMPERSONATION_ATTEMPT MUST be used when transport-bound peer_id does
not match the peer_id declared inside the message envelope.

REQ-GSDA-ERR-005
GOVERNANCE_FAILURE MUST be used only for the governance conditions
listed in Section 3.2.

REQ-GSDA-ERR-006
LIVENESS_FAILURE MUST be used when the scheduler cannot make
progress for liveness_policy.max_stagnant_rounds consecutive rounds.

REQ-GSDA-ERR-007
PUBLICATION_FAILURE MUST be used when any publication gate condition
in Section 39 is unmet.

REQ-GSDA-ERR-008
message_template MUST contain no embedded peer content. Peer-supplied
detail MUST be attached as separate evidence, never inside the
template.

REQ-GSDA-ERR-009
Named failures in Section 3.3 MUST NOT be emitted as Error codes.
Error codes in Section 3.2 MUST NOT be emitted as named failures or
evidence kinds. The three namespaces are disjoint.

REQ-GSDA-ERR-010
Evidence kinds in Section 3.4 MUST NOT be emitted as Error codes.

REQ-GSDA-ERR-011
The error code registry, named failure registry, and evidence kind
registry MUST be shipped under spec.schemas/registries/1.0.json.
That single file is authoritative. Any other registry file named in
the package MUST be a derived copy and MUST be marked derived in its
content.

REQ-GSDA-ERR-012
Every error code in Section 3.2 MUST be mapped to exactly one
category in Section 3.2. The mapping MUST be machine-readable in
spec.schemas/registries/1.0.json.

REQ-GSDA-ERR-013
SCOPE_VIOLATION MUST be emitted when a kernel operation attempts to
access a resource outside its permitted stores per REQ-GSDA-KER-005.

REQ-GSDA-ERR-014
INPUT_BOUNDS_EXCEEDED, AGGREGATION_BOUNDS_EXCEEDED, and
RELIABILITY_BOUNDS_EXCEEDED are distinct codes. An implementation
MUST NOT emit one in place of another.

================================================================================
4. NORMALIZATION REGISTRY
================================================================================

REQ-GSDA-NORM-001
Canonical JSON serialization MUST follow a GSDA profile derived from
RFC 8785 with these extensions:

  - NaN, Infinity, and -Infinity MUST be rejected.
  - Duplicate object keys MUST be rejected before canonicalization.
  - Integers MUST use decimal representation without exponent and
    without leading zeros, except zero itself.
  - Negative zero MUST be normalized to zero.
  - Floating-point numbers MUST NOT appear in any identity-bearing
    record.
  - Object keys MUST be sorted by UTF-8 bytewise lexicographic order.

The GSDA profile deliberately overrides RFC 8785's UTF-16 code-unit
ordering for object keys; all keys are strings and UTF-8 bytewise
ordering is the canonical rule. Implementations MUST NOT rely on
off-the-shelf RFC 8785 libraries unless they are configured for
UTF-8 bytewise key ordering.

REQ-GSDA-NORM-001A
Identity-bearing records MUST NOT contain any floating-point JSON
number, NaN, or Infinity, and MUST NOT be produced from a source
document that contained a floating-point JSON number in any field
that participates in identity.

REQ-GSDA-NORM-001B
RFC 3339 timestamps are JSON strings and are not subject to the
float ban.

REQ-GSDA-NORM-002
term_id MUST be derived as:

  NFC(normalize) -> trim -> casefold (Unicode) ->
  collapse internal whitespace runs to single '-'
  -> replace remaining non [a-z0-9-] with '-'
  -> collapse consecutive '-' to one
  -> strip leading and trailing '-'
  -> lowercase

An empty term_id after normalization MUST cause SCHEMA_FAILURE.
Comparison MUST be on term_id only. Display labels are informative.

REQ-GSDA-NORM-003
requirement_id format is defined in REQ-GSDA-REQ-002 and
REQ-GSDA-REQ-012.

REQ-GSDA-NORM-004
canonical_record_jcs(X) = the GSDA canonical JSON serialization of X
per REQ-GSDA-NORM-001, with the schema field of X included as a
member. This is the canonicalization used for all GSDA records whose
schema is registered in spec.schemas/registries/1.0.json.

REQ-GSDA-NORM-004A
canonical_file_json(X) = the GSDA canonical JSON serialization of X
per REQ-GSDA-NORM-001, with no schema injection. This is the
canonicalization used for package files whose top-level object does
not carry a GSDA schema field (for example, JSON Schema files using
$schema).

REQ-GSDA-NORM-005
A JSON document containing a float, NaN, Infinity, duplicate key, or
negative zero MUST be rejected with SCHEMA_FAILURE unless it is
expressly a non-identity-bearing document and the schema declares
that the field is float-tolerant. No v2.13 schema declares float
tolerance.

REQ-GSDA-NORM-006
NFC normalization MUST be applied during term comparison only. It
MUST NOT alter the stored string or its identity-bearing canonical
representation.

REQ-GSDA-NORM-009
requirement_id for target-domain specifications is defined in
REQ-GSDA-REQ-012.

REQ-GSDA-NORM-010
Every timestamp field MUST be serialized as:

  YYYY-MM-DDTHH:MM:SS.sssZ

An RFC 3339 UTC instant with millisecond precision. No other timezone
offset is permitted in identity-bearing or provenance data. The
timestamp of a peer message is provenance only and MUST NOT be
included in message_id.

REQ-GSDA-NORM-011
canonical_record_jcs(X) MUST include the schema field of X. The
schema field value MUST be the canonical schema identifier, not the
full schema document. canonical_record_jcs MUST NOT be applied to
JSON documents whose top level is not a GSDA record.

REQ-GSDA-NORM-012
For the purpose of computing a PackageEntry sha256_hex value, the
canonical bytes of a file are:

  - For files whose name ends in ".json": UTF-8 encoding of
    canonical_file_json of the parsed JSON value.
  - For all other files: UTF-8 encoding after stripping a leading
    UTF-8 BOM if present, normalizing line endings to LF, and
    applying Unicode NFC.

No other transformation is permitted. Filename normalization is NOT
performed; filenames are compared as raw byte sequences.

REQ-GSDA-NORM-013
For linter purposes, a paragraph is a maximal sequence of consecutive
non-blank lines separated by at least one blank line. A blank line
matches ^\s*$. The [Informative] marker MUST appear as the first
token of the paragraph to exempt every normative keyword in that
paragraph.

REQ-GSDA-NORM-014
Every integer division operation in this specification MUST be
defined as floor division (truncation toward negative infinity).
Languages whose native division truncates toward zero MUST adjust
the result to floor before use. This applies to N(r,k) div D(r,k),
reliability decay, quorum threshold computation, and every other
division. All operands in this specification are non-negative;
implementations MAY use unsigned arithmetic for these operands and
MUST document any such substitution.

REQ-GSDA-NORM-015
A raw_response record is defined by schema "raw_response/1.0" with
fields:

  schema        "raw_response/1.0"
  media_type    string
  received_b64  Base64 string (may be empty)
  byte_length   integer >= 0

The content_id of a raw_response record MUST be computed as:

  "content:" + sha256_hex(
      canonical_record_jcs({
          "schema":       "raw_response_identity/1.0",
          "media_type":   <media_type>,
          "decoded_bytes_sha256":
              sha256_hex(decoded_bytes)
      }))

where decoded_bytes is the Base64-decoded value of received_b64. This
provides a well-defined identity for provider output that is not JSON
and is independent of the Base64 encoding.

REQ-GSDA-NORM-015A
A file_content record is defined by schema "file_content/1.0" with
fields:

  schema        "file_content/1.0"
  media_type    string
  byte_length   integer >= 0
  sha256_hex    string

The content_id of a file_content record MUST be:

  "content:" + sha256_hex(
      canonical_record_jcs({
          "schema":     "file_content_identity/1.0",
          "media_type": <media_type>,
          "sha256_hex": <sha256_hex>
      }))

file_content is used for package files whose bytes do not parse as a
GSDA record (for example, prose files, changelog files, binary test
vectors).

5. IDENTITY MODEL
================================================================================

[Informative] GSDA uses three identity classes; the classes, their
members, and their non-conflation rules are normative in
REQ-GSDA-ID-000 through REQ-GSDA-ID-115.

  DETERMINISTIC IDENTITY
      task_id, message_id, content_id, artifact_id, evidence_id,
      decision_id, config_id, spec_content_id, revision_id,
      intent_id, finding_id, finding_subject_id, assumption_id,
      question_id, reliability_outcome_id, term_record_id,
      file_content_id.

  COORDINATOR-ASSIGNED IDENTITY
      run_id, peer_id.

  DERIVED EXECUTION IDENTITY
      round_id.

REQ-GSDA-ID-000
A deterministic identity MUST be reproducible from its declared
inputs.

REQ-GSDA-ID-001
A coordinator-assigned identity MUST be stable for the life of the
entity it identifies and MUST NOT be used to derive any deterministic
identity, except that round_id MAY derive from run_id because
round_id is classified as DERIVED EXECUTION IDENTITY per Section 5.

REQ-GSDA-ID-002
Random or time-based values MUST NOT influence deterministic
identity.

--- 5.1 task_id ---

REQ-GSDA-ID-010
task_id MUST be:

  "task:" + sha256_hex(canonical_record_jcs({
      "schema":            "task_identity/1.0",
      "user_prompt":       <string>,
      "user_intent":       <string>,
      "domain":            <string>,
      "target_audience":   <sorted string[]>,
      "constraints":       <sorted string[]>,
      "requested_outputs": <sorted string[]>,
      "priority_profile":  <string>
  }))

namespace and target_language MUST NOT appear in task_id.

--- 5.2 run_id ---

REQ-GSDA-ID-020
run_id MUST identify a particular execution run.

REQ-GSDA-ID-021
run_id MUST be globally unique within the coordinator's identity
domain.

REQ-GSDA-ID-022
Default format: "run:" + UUID_v4.

REQ-GSDA-ID-023
run_id MUST NOT be used to derive content_id, spec_content_id, or
revision_id.

REQ-GSDA-ID-024
run_id MUST be preserved in replay packages.

--- 5.3 peer_id ---

REQ-GSDA-ID-030
peer_id MUST identify a configured peer slot.

REQ-GSDA-ID-031
peer_id MUST be stable across model upgrades, prompt-profile changes,
and provider-side updates, unless the human explicitly retires the
slot.

REQ-GSDA-ID-032
Default format: "peer:<slot>", where <slot> is a stable configured
identifier.

REQ-GSDA-ID-033
Provider, model, and model_version MUST be recorded as peer metadata,
NOT used to derive peer_id.

REQ-GSDA-ID-034
A change of provider or model for a peer slot MUST be recorded as a
peer-profile change and MUST NOT be treated as a new peer.

REQ-GSDA-ID-035
peer_id MUST NOT be used to derive any deterministic identity.

--- 5.4 round_id ---

REQ-GSDA-ID-016
round_id MUST NOT depend on any wall-clock value.

REQ-GSDA-ID-040
round_id = "round:" + run_id + ":" + decimal(round_index). Index
begins at zero and increases by one per round within the run.

--- 5.5 message_id ---

REQ-GSDA-ID-050
message_id MUST be:

  "msg:" + sha256_hex(canonical_record_jcs({
      "schema":          "message_identity/1.0",
      "run_id":          <run_id>,
      "peer_id":         <peer_id>,
      "payload_schema":  <payload schema identifier>,
      "content_id":      <content_id of sanitized payload>
  }))

REQ-GSDA-ID-051
Transport ordering MUST NOT determine message identity. Timestamp
MUST NOT be included in message_id. message_id MUST be derived from
the sanitized payload only per REQ-GSDA-ADP-009.

REQ-GSDA-ID-052
A repeated message_id with identical content MUST be idempotent.

REQ-GSDA-ID-053
A repeated message_id with conflicting content MUST produce
PROTOCOL_FAILURE and MUST be rejected.

--- 5.6 content_id ---

REQ-GSDA-ID-060
content_id MUST identify semantic payload content.

REQ-GSDA-ID-061
content_id MUST be:

  "content:" + sha256_hex(canonical_record_jcs({
      "schema":         <payload schema identifier>,
      "payload":        <payload value>
  }))

REQ-GSDA-ID-062
content_id MUST NOT depend on provenance, author, or transport.

--- 5.7 artifact_id ---

REQ-GSDA-ID-070
artifact_id MUST identify an immutable recorded instance.

REQ-GSDA-ID-071
artifact_id MUST be:

  "art:" + sha256_hex(canonical_record_jcs({
      "schema":              "artifact_identity/1.0",
      "task_id":             <task_id>,
      "run_id":              <run_id>,
      "artifact_kind":       <kind>,
      "content_id":          <content_id>,
      "author_peer_id":      <peer_id>,
      "author_role":         <role>,
      "round_id":            <round_id>,
      "parent_artifact_ids": <sorted artifact_id[]>,
      "contribution_index":  <integer>
  }))

REQ-GSDA-ID-072
artifact_id MUST NOT depend on wall-clock time.

REQ-GSDA-ID-073
Two artifacts MAY have the same content_id while having different
artifact_id values.

REQ-GSDA-ID-074
contribution_index is derived from the artifact's own preimage only.
It MUST NOT depend on the set of sibling artifacts recorded later in
the same tuple. The index is computed as:

  contribution_index = number of leading 0-bits in
      sha256(canonical_record_jcs({
          "schema":        "contribution_preimage/1.0",
          "run_id":        <run_id>,
          "round_id":      <round_id>,
          "artifact_kind": <kind>,
          "author_peer_id":<peer_id>,
          "content_id":    <content_id>,
          "message_id":    <message_id>
      }))

When two artifacts sharing a tuple would collide on contribution_index
because they have the same content_id and the same message_id (which
is only possible if the entire preimage is identical), they MUST be
recorded as a single artifact. Distinct preimages MUST NOT collide.

--- 5.12 working state alias ---

REQ-GSDA-ID-111
There is no separate working_state_id. The current proposed

7. PEER ADAPTER LAYER
================================================================================

REQ-GSDA-ADP-001
The peer adapter layer is the only GSDA component permitted to
sanitize raw provider output before kernel validation. Sanitization
MAY include stripping provider UI, mapping floats to integer score
fields, normalizing line endings, decoding HTML entities, and
structural salvage under ADP-010.

REQ-GSDA-ADP-002
Sanitization MUST be recorded in evidence. The original raw response
MUST be preserved by content_id (see REQ-GSDA-NORM-015) and MUST be
retrievable.

REQ-GSDA-ADP-003
The peer adapter MUST NOT modify any identity-bearing field of a
peer message after the message envelope is constructed. It may
modify only payload content and only to the extent permitted by the
message schema for the declared payload type.

REQ-GSDA-ADP-003A
Any modification of an envelope field by the adapter MUST cause
PROTOCOL_FAILURE.

REQ-GSDA-ADP-004
If sanitization cannot produce a schema-valid payload, the adapter
MUST reject the message with PROTOCOL_FAILURE.

REQ-GSDA-ADP-005
For non-identity-bearing numeric fields, the adapter MAY round a
floating-point value to the nearest integer using round-half-to-even
and MUST record a FLOAT_ROUNDED evidence record. The adapter MUST
reject with PROTOCOL_FAILURE when the value is NaN or Infinity or
its absolute value exceeds 10^6.

REQ-GSDA-ADP-006
When a peer message contains a floating-point value in an
identity-bearing field, the adapter MUST reject with SCHEMA_FAILURE
and MUST NOT round.

REQ-GSDA-ADP-007
Every adapter sanitization MUST be recorded as an evidence record of
kind ADAPTER_SANITIZED.

REQ-GSDA-ADP-008
The adapter MUST NOT inject default values into omitted fields.

REQ-GSDA-ADP-009
The adapter pipeline MUST be:

  RAW -> STRUCTURAL_SALVAGE (optional) -> SANITIZE -> CANONICALIZE
      -> content_id -> message_id -> ENVELOPE -> KERNEL VALIDATION

REQ-GSDA-ADP-010
Structural salvage is a pure function of raw bytes. It MAY perform
only the following transformations:

  - strip trailing bytes after a well-formed JSON value
  - remove a trailing comma before a closing bracket or brace
  - close at most one layer of unbalanced opening brackets or
    braces when the repair is unambiguous
  - unescape one double-escaped string layer when the result parses

It MUST NOT alter any numeric field value, any identifier, any string
that participates in identity, invent missing fields, or reorder
arrays whose schema declares them ORDERED. It MUST be idempotent: for
any bytes B on which salvage succeeds, salvage(salvage(B)) = salvage(B).

REQ-GSDA-ADP-011
When salvage is applied, the adapter MUST emit a STRUCTURAL_SALVAGE
evidence record containing the raw response content_id and a
deterministic description of the repair. If salvage fails, the
adapter MUST reject with PROTOCOL_FAILURE.

REQ-GSDA-ADP-012
Structural salvage MUST NOT use an LLM.

REQ-GSDA-CFG-001
Every value that affects deterministic coordinator behaviour MUST
exist in the configuration record.

REQ-GSDA-CFG-002
config_id MUST be computed per REQ-GSDA-ID-095.

REQ-GSDA-CFG-003
Configuration MUST be scoped per round. Each round records its
active config_id.

REQ-GSDA-CFG-004
A mid-run configuration change MUST start a new round with a new
config_id. The change and its reason MUST be recorded as a Decision.

REQ-GSDA-CFG-005
A replay using the same task, messages, kernel version, and
per-round config_ids MUST reproduce the same coordinator decisions.

REQ-GSDA-CFG-006
maximum_peers, maximum_candidates, maximum_scores_per_round,
maximum_cross_repairs, maximum_findings, and maximum_criteria MUST
be set such that every intermediate aggregation value remains
strictly below 2^127 - 1 per REQ-GSDA-KER-019.

REQ-GSDA-CFG-007
For the default configuration, maximum_peers MUST be at most 100 and
maximum_scores_per_round MUST be at most
maximum_peers * maximum_criteria.

REQ-GSDA-CFG-008
The effective cross-repair budget MUST be:

  B_effective = min(
      configured_cross_repair_budget,
      maximum_cross_repairs,
      N * C
  )

where N is the number of active peers and C the number of
candidates.

REQ-GSDA-CFG-009
The default configured_cross_repair_budget MUST be 2 * max(N, C).

REQ-GSDA-CFG-010
intent_segmentation_policy MUST conform to the schema above.

REQ-GSDA-CFG-011
If intent_segmentation_policy.mode is HYBRID, the kernel MUST apply
the algorithm in REQ-GSDA-KER-006.

REQ-GSDA-CFG-012
The configuration record MUST contain the fields defined in the
schema above.

REQ-GSDA-CFG-013
Every value that has a default in this Section MUST be recorded in
the config record even when the default is used.

REQ-GSDA-CFG-014
namespace MUST NOT be used to derive task_id. It is used only to
generate requirement_ids per REQ-GSDA-REQ-012.

REQ-GSDA-CFG-015
max_stagnant_rounds MUST be defined ONLY in
liveness_policy.max_stagnant_rounds.

REQ-GSDA-CFG-016
configured_max_peers used for fairness_key MUST be >= 1.

REQ-GSDA-CFG-017
maximum_criteria MUST be >= 10.

REQ-GSDA-CFG-018
convergence_policy, stagnation_policy, liveness_policy,
reliability_policy, aggregation_bounds, intent_segmentation_policy,
intent_criticality_policy, role_assignments, prompt_profiles,
criterion_rubrics, outcome_weights, cross_repair_quota_policy,
token_rotation_policy MUST each validate against a versioned
sub-schema stored in spec.schemas/.

REQ-GSDA-CFG-019
intent_criticality_policy.critical_weight_threshold MUST be the
single source of truth for critical coverage per CVG-002. When
absent, SCHEMA_FAILURE.

REQ-GSDA-CFG-020
aggregation_bounds MUST contain every field defined in the
aggregation_bounds/1.0 schema.

REQ-GSDA-CFG-021
intent_segmentation_policy.marker_prefixes MUST be a non-empty
string[] when mode includes MARKER. The array MUST be prefix-free:
no element may be a prefix of another element. Elements MUST be
sorted by length descending, and marker matching MUST use
longest-match-first. An empty or non-prefix-free array when mode
includes MARKER MUST cause SCHEMA_FAILURE.

REQ-GSDA-CFG-022
liveness_policy.bound_saturation_threshold MUST default to
max(1, maximum_peers div 2).

REQ-GSDA-CFG-023
reliability_profile MUST be one of FLAT or DECAYING. When FLAT,
REQ-GSDA-REL-017 decay MUST NOT be applied and
RELIABILITY_BOUNDS_EXCEEDED MUST be emitted on any update that
would exceed maximum_reliability_evidence. When DECAYING, decay is
applied per REL-017.

REQ-GSDA-CFG-024
cross_repair_quota_policy.group_weights MUST be present.
sum(group_weights) MUST be > 0, otherwise SCHEMA_FAILURE. When the
implementation does not wish to use partitioning, it MUST set every
weight to zero except one designated catch-all group; the coordinator
MUST still apply the reallocation_order.

REQ-GSDA-CFG-025
token_rotation_policy.max_age_seconds MUST be > 0 and <= 86400.

REQ-GSDA-CFG-026
compliance_level MUST be declared in the config record. The
coordinator MUST reject a run whose compliance_level is LEVEL_1 with
GOVERNANCE_FAILURE if any Level 2 publication feature is invoked.

22. CROSS-REPAIR SCHEDULING
================================================================================

REQ-GSDA-REP-010
The coordinator MUST bound the number of cross-repairs per round
using B_effective per REQ-GSDA-CFG-008.

REQ-GSDA-REP-011
Repair candidates MUST be generated as triples:

  (target_artifact_id, addressed_finding_id, repairer_peer_id)

REQ-GSDA-REP-012
The following MUST be pure functions of a round-start snapshot
recorded by SnapshotRoundContext per REQ-GSDA-KER-021:

  blocking_finding_count(t)
  unaddressed_finding_count(t)
  target_critical_count(t)
  target_high_count(t)
  target_aggregate(t)         (UNDEFINED sorts last)
  repairer_reliability(p)
  repairer_independent_count(p)

REQ-GSDA-REP-013
The reliability and independent_observation_count values used for
ordering MUST be obtained from SnapshotRoundContext. Mid-round
updates MUST NOT affect ordering.

REQ-GSDA-REP-014
Candidate triples MUST be ordered by a comparator that MUST NOT use
arithmetic negation and MUST NOT use IEEE infinity as a sentinel:

  1. blocking_finding_count(t)      descending
  2. unaddressed_finding_count(t)   descending
  3. target_critical_count(t)       descending
  4. target_high_count(t)           descending
  5. target_aggregate(t)            ascending with UNDEFINED last
  6. repairer_reliability(p)        descending
  7. repairer_independent_count(p)  descending
  8. fairness_key(p, round)         ascending
  9. target_artifact_id             ascending UTF-8 bytewise
 10. addressed_finding_id           ascending UTF-8 bytewise

REQ-GSDA-REP-015
fairness_key(p, round) = (round_index + slot_index(p))
                          mod max(1, round_config.maximum_peers)

where round_config is the config record with the config_id of the
current round, slot_index is defined in REQ-GSDA-PEER-005, and the
value of round_config.maximum_peers used MUST be recorded in the
round's provenance.

REQ-GSDA-REP-016
The first B_effective triples in the total order MUST be performed.

REQ-GSDA-REP-017
The exact ordered list of triples, the budget decision, the
snapshotted reliability values, the snapshotted
independent_observation_count values, the round_config.maximum_peers
used, and the fairness_key computed for each peer MUST be recorded
in provenance.

REQ-GSDA-REP-018
A repair triple whose addressed_finding_id is empty is permitted and
represents a whole-artifact repair.

REQ-GSDA-REP-019
If a finding with severity CRITICAL has remained OPEN for at least
liveness_policy.critical_promotion_rounds consecutive rounds without
being selected as an addressed_finding_id, the coordinator MUST
promote it to the top of the schedule. Promotion MUST be recorded
as a LIVENESS_PROMOTION evidence record.

REQ-GSDA-REP-020
liveness_policy.critical_promotion_rounds MUST default to 3 and
MUST be at least 2. Up to min(liveness_policy.alternate_promotion_cap,
B_effective) LIVENESS_PROMOTION records MAY be scheduled per round.
When multiple findings qualify, candidates MUST be selected by
created_at ascending, then by finding_id bytewise ascending. When
more findings qualify than the cap, the coordinator MUST emit
ALTERNATE_VIABLE_PROMOTION evidence listing all eligible findings
that were not promoted.

REQ-GSDA-REP-021
The exact set of triples performed MUST be recorded in provenance,
including the addressed_finding_id for each triple.

REQ-GSDA-REP-022
cross_repair_quota_policy.group_weights MUST be applied to partition
B_effective into sub-budgets by finding category group as declared
in the config. Each eligible finding MUST be assigned to exactly one
group by precedence A > B > C > D. The four named groups are:

  Group A: findings with blocking = true
  Group B: findings with severity CRITICAL or HIGH (and not Group A)
  Group C: findings with category OMISSION, TERM_CANDIDATE,
           MISSING_TERM, or NORMALIZED_TERM_COLLISION (and not A or B)
  Group D: all other findings (and not A, B, or C)

The sub-budget for each group MUST be:

  floor(B_effective * weight / sum_of_all_weights)

Remainders MUST be distributed in the order A, B, C, D. When
multiple remainders are equal, the group earlier in the
reallocation_order takes precedence. If a group has no eligible
triples, its sub-budget MUST be reallocated to groups in
reallocation_order, recording REPAIR_QUOTA_APPLIED evidence. A
partitioned policy MUST NOT cause more than B_effective triples to
be performed.

REQ-GSDA-REP-023
ALTERNATE_VIABLE_PROMOTION evidence records MUST NOT exceed
liveness_policy.alternate_evidence_max_records per run. When the cap
is reached, the coordinator MUST retain only the most recent records
and MUST record the pruning as a Decision.

REQ-GSDA-REP-024
REPAIR_QUOTA_APPLIED evidence MUST record, for each reallocation, the
source group, the destination group, the amount reallocated, and the
index in the reallocation_order at which the amount was moved.

TESTABILITY: TESTABLE

Confidence MUST be an integer in 1..1000.

REQ-GSDA-SCR-003
Confidence measures the peer's confidence in the submitted
judgement. It MUST NOT be interpreted as probability of truth.

REQ-GSDA-SCR-004
A peer MAY abstain from scoring a criterion by omitting it.

REQ-GSDA-SCR-005
A criterion value of 0 means "unacceptable" and MUST NOT be used to
express abstention.

REQ-GSDA-SCR-006
The peer MUST NOT submit an authoritative overall score.

REQ-GSDA-SCR-007
overall_hint MUST NOT be used in aggregation. The kernel MUST ignore
it for all aggregate and comparison purposes.

REQ-GSDA-SCR-008
For authoritative aggregation, the selected score for a
(scorer_peer_id, target_artifact_id, criterion) tuple is determined
by the following total order, applied to all recorded scores for
that tuple:

  1. greatest round_index                 (latest round wins)
  2. greatest created_at                  (latest submission wins)
  3. smallest message_id bytewise         (stable neutral tie-break)

If two scores remain tied after all three keys, they MUST be
identical records; otherwise the situation MUST cause
GOVERNANCE_FAILURE. message_id is content-derived, so the smallest
message_id is a neutral deterministic tie-break, not a claim about
recency.

REQ-GSDA-SCR-009
All earlier scores MUST remain immutable historical evidence.

REQ-GSDA-SCR-010
Each criterion MUST have a configured rubric with integer anchors at
0, 250, 500, 750, 1000 recorded in config.criterion_rubrics.

REQ-GSDA-SCR-011
Rubric anchors MUST be strictly increasing.

REQ-GSDA-SCR-012
When maximum_scores_per_round is exceeded for a target, the
coordinator MUST keep the latest score per (scorer_peer_id,
target_artifact_id, criterion) per REQ-GSDA-SCR-008 and MUST record
the discarded entries as a Decision.

REQ-GSDA-SCR-013
A missing criterion value MUST NOT be normalized to 0.

REQ-GSDA-SCR-014
If a required criterion lacks a configured rubric, the coordinator
MUST fail closed with GOVERNANCE_FAILURE.

REQ-GSDA-SCR-015
A peer's score on an artifact it authored MUST be recorded but MUST
NOT contribute to the authoritative aggregate for that artifact.

24. AGGREGATION
================================================================================

Rational aggregate record:

  schema                "rational_aggregate/1.0"
  A                     integer
  A_rem                 integer
  denom                 integer (>=0; 0 only when status is UNDEFINED)
  status                DEFINED | UNDEFINED

Participation rule:
  Peer i participates for criterion k on target r if and only if
  S(i,r,k) exists AND C(i,r,k) >= 1 AND peer i is not excluded by
  REQ-GSDA-SCR-015.

  N(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k) * S(i,r,k)

  D(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k)

  If D(r,k) > 0:
    A(r,k) = N(r,k) div D(r,k)
    A_rem(r,k) = N(r,k) mod D(r,k)
    denom(r,k) = D(r,k)
    status = DEFINED
  Else if any participating peer exists:
    A(r,k) = ( sum S ) div n
    A_rem(r,k) = ( sum S ) mod n
    denom(r,k) = n
    status = DEFINED
    Emit LOW_RELIABILITY_AGGREGATE evidence.
  Else:
    A(r,k) = 0; A_rem(r,k) = 0; denom(r,k) = 0; status = UNDEFINED

Overall artifact aggregate:

  Let K be the set of criteria with status(r,k) = DEFINED.
  Let w(k) be config.criterion_weights[k].

  If K is empty:
    A(r) = 0; A_rem(r) = 0; denom(r) = 0; status(r) = UNDEFINED
  Else:
    N(r) = sum over k in K of
             w(k) * ( A(r,k) * denom(r,k) + A_rem(r,k) )
    D(r) = sum over K of w(k) * denom(r,k)
    A(r) = N(r) div D(r)
    A_rem(r) = N(r) mod D(r)
    denom(r) = D(r)
    status(r) = DEFINED

REQ-GSDA-AGG-001
Undefined criteria MUST NOT be silently treated as zero.

REQ-GSDA-AGG-002
Undefined criteria MUST be explicitly recorded.

REQ-GSDA-AGG-003
If all criteria are undefined, the overall artifact aggregate MUST
be UNDEFINED.

REQ-GSDA-AGG-004
The exact configured criterion weights MUST be recorded in
provenance.

REQ-GSDA-AGG-005
Aggregate calculation MUST use signed 128-bit integers for all
intermediate products and sums. The implementation MUST fail closed
with AGGREGATION_BOUNDS_EXCEEDED if any intermediate value would
exceed the signed 128-bit range.

REQ-GSDA-AGG-006
Aggregation MUST fail closed with INPUT_BOUNDS_EXCEEDED when a score,
confidence, or weight exceeds the bound declared in
config.aggregation_bounds.

REQ-GSDA-AGG-007
A(r,k), A_rem(r,k), denom(r,k), A(r), A_rem(r), denom(r), and
status MUST all be stored in the authoritative aggregate record.

REQ-GSDA-AGG-008
Artifact selection MUST compare the aggregate triple (A, A_rem,
denom) as the exact rational:

  A + A_rem / denom

where denom > 0 and 0 <= A_rem < denom.

Comparison MUST proceed as follows:

  1. Compare A1 and A2. If unequal, the larger A wins.
  2. If A1 == A2, compare the remainders by cross-multiplying:
       product_left  = A_rem1 * denom2
       product_right = A_rem2 * denom1
  3. Cross multiplication MUST use signed 128-bit arithmetic with
     overflow detection.
  4. If either cross product would overflow the signed 128-bit
     range, the implementation MUST:
       a. reduce both fractions by the greatest common divisor of
          the numerator and denominator, and
       b. retry the cross multiplication once.
  5. If the cross multiplication still overflows after reduction,
     the implementation MUST fail closed with
     AGGREGATION_BOUNDS_EXCEEDED. It MUST NOT fall back to comparing
     A alone as a silent approximation.

Implementations MUST NOT construct A * denom + A_rem solely for
comparison. Precondition: status(r) = DEFINED for both artifacts
under comparison. UNDEFINED aggregates MUST be filtered per AGG-009
before comparison.

REQ-GSDA-AGG-009
An artifact whose overall status is UNDEFINED MUST be disqualified
from selection and MUST be marked NON_VIABLE.

REQ-GSDA-AGG-010
Artifact selection MUST use a deterministic total order over viable
artifacts only:

  1.   higher aggregate score per REQ-GSDA-AGG-008
  2.   higher minimum defined criterion score
  2.5  higher artifact_independent_observation_count as defined in
       Section 24.1
  3.   lower overall disagreement spread
  4.   greater number of independent scoring peers
  5.   artifact_id bytewise ascending

Overall disagreement spread is defined as the maximum criterion
spread across all criteria with at least two participating peers,
computed per Section 25. When no criterion has at least two
participating peers, overall disagreement spread MUST be 0.

24.1 artifact_independent_observation_count

The artifact_independent_observation_count for artifact r is defined
as the number of distinct independent_observation records
(Section 26.1) whose subject_ids contain r and whose
provider_profile_id or model_profile_id differ pairwise. It is not
the sum of any peer's cumulative reliability field.

REQ-GSDA-AGG-011
When no artifact is viable, no artifact is eligible for automatic
selection. The round MUST route the decision to human review with a
LOW_RELIABILITY_AGGREGATE evidence. This is a normal outcome for a
first round with cold-start peers.

REQ-GSDA-AGG-012
Signed 128-bit arithmetic MAY be implemented via native types,
two-word Int64 arithmetic, or an arbitrary-precision library,
provided the implementation fails closed on overflow.

REQ-GSDA-AGG-013
When a criterion's aggregate is UNDEFINED and any participating peer
exists, the aggregate MUST record LOW_RELIABILITY_AGGREGATE
evidence.

REQ-GSDA-AGG-014
When denom(r,k) == 0 and n_participants > 0, the
LOW_RELIABILITY_AGGREGATE fallback MUST NOT contribute to
reliability updates for the SCORING activity unless adjudicated by
a human.

REQ-GSDA-AGG-015
The set of participating peers for each criterion MUST be recorded
in the aggregate provenance.

25. DISAGREEMENT
================================================================================

For criterion k and artifact r, over participating peers:

  values          sorted list of S(i,r,k)
  n               number of participating peers
  sum             sum(values)
  sum_sq          sum over v of v * v
  minimum         values[0]                    if n > 0
  maximum         values[n-1]                  if n > 0
  mean_num        sum                          if n > 0
  mean_denom      n                            if n > 0
  spread          maximum - minimum            if n > 0
  variance_num    n * sum_sq - sum * sum       if n > 0
  variance_denom  n * n                        if n > 0
  variance_x1000  ( variance_num * 1000 ) div variance_denom

The mean is represented exactly as the rational mean_num / mean_denom.
Implementations MUST NOT truncate the mean before computing variance.
variance_num and variance_denom MUST be reduced by their greatest
common divisor before storage; the reduced pair is authoritative.
variance_x1000 is a presentation convenience and MUST be computed
from the unreduced or reduced pair with floor division, preserving
the exact rational whenever possible.

REQ-GSDA-VAR-001
Variance MUST be reported per criterion.

REQ-GSDA-VAR-002
Abstentions MUST NOT contribute to disagreement.

REQ-GSDA-VAR-003
A criterion whose spread exceeds config.disagreement_threshold MUST
be flagged HIGH_DISAGREEMENT.

REQ-GSDA-VAR-004
A HIGH_DISAGREEMENT criterion MUST be eligible to trigger another
analysis round.

REQ-GSDA-VAR-005
The complete participating score distribution MUST be preserved.

REQ-GSDA-VAR-006
The sum-of-squares term in variance MUST be bounds-checked per
REQ-GSDA-KER-019. If it would overflow the signed 128-bit range,
the implementation MUST fail closed with
AGGREGATION_BOUNDS_EXCEEDED.

REQ-GSDA-VAR-007
When reporting variance, implementations MUST record variance_num
and variance_denom. When only a single integer is required by a
consumer, variance_x1000 MUST be computed by floor division of
variance_num * 1000 by variance_denom, and the fact that a floor
was applied MUST be recorded if the remainder was non-zero.

26. RELIABILITY
================================================================================

[Informative] Reliability is an estimate of usefulness for a specific
activity. It is not truth, authority, reputation, or popularity.

Activities: GENERATION, CRITIQUE, REPAIR, SCORING, COMPLETENESS,
CONTRADICTION, TERMINOLOGY, TESTABILITY, PROTOCOL.

Reliability record:

  schema                "reliability/1.0"
  peer_id               string
  activity              string
  alpha                 integer >= 0
  beta                  integer >= 0
  sample_count          integer >= 0
  independent_observation_count integer >= 0
  mean                  integer 0..1000

ReliabilityOutcome record:

  schema                "reliability_outcome/1.0"
  outcome_id            string
  activity              string
  subject_ids           string[]
  attribution_peer_ids  string[]
  result                SUCCESS | FAILURE | NEUTRAL | CORROBORATED
  evidence_class        HUMAN_ADJUDICATION | KERNEL_STRUCTURAL
                        | INDEPENDENT_CORROBORATION
  evidence_ids          string[]
  created_at            timestamp

26.1 independent_observation record

  schema                "independent_observation/1.0"
  observation_id        string
  activity              string
  subject_ids           string[]
  finding_subject_id    string
  peer_id               string
  provider_profile_id   string
  model_profile_id      string
  evidence_id           string
  created_at            timestamp

An independent_observation record is emitted when a
ReliabilityOutcome with evidence_class = INDEPENDENT_CORROBORATION is
recorded. It is artifact/subject-scoped, not peer-scoped.

REQ-GSDA-REL-001
Reliability MUST be maintained per (peer, activity).

REQ-GSDA-REL-002
A peer with no historical evidence MUST have cold_start_alpha and
cold_start_beta from config.

REQ-GSDA-REL-003
Reliability MUST NOT be derived from artifact selection or survival.

REQ-GSDA-REL-004
A semantic reliability update MUST require an explicit
ReliabilityOutcome record, emitted by the coordinator.

REQ-GSDA-REL-005
A timeout MUST produce no reliability update.

REQ-GSDA-REL-006
A protocol violation MUST affect PROTOCOL activity only.

REQ-GSDA-REL-007
Every SUCCESS or FAILURE outcome MUST identify at least one
evidence_id.

REQ-GSDA-REL-008
KERNEL_STRUCTURAL outcomes MUST only affect activities for which the
kernel can establish objective structural validity.

REQ-GSDA-REL-009
INDEPENDENT_CORROBORATION means two or more peers classified as
KERNEL_SEPARATED per REQ-GSDA-REL-009A independently produced
findings with the same finding_subject_id and from distinct provider
or model profiles. Real-world independence is unknowable and MUST
NOT be claimed.

REQ-GSDA-REL-009A
A peer is KERNEL_SEPARATED for a finding subject when the
coordinator can establish from recorded inputs that the peer's
prompt did not contain any other peer's analysis, finding, score,
or aggregate for that subject before the peer produced its finding.
KERNEL_SEPARATED is the only independence class accepted for
automatic corroboration.

REQ-GSDA-REL-010
An INDEPENDENT_CORROBORATION outcome MUST have result =
CORROBORATED. CORROBORATED outcomes MUST NOT increment alpha or beta.
They MUST increment independent_observation_count on the reliability
records of every attribution_peer_id, and MUST emit exactly one
independent_observation record per distinct provider/model pair
among the attributions.

REQ-GSDA-REL-011
INDEPENDENT_CORROBORATION MUST only be used for CONTRADICTION,
COMPLETENESS, and TERMINOLOGY activities.

REQ-GSDA-REL-012
A mixed repair MUST NOT automatically attribute reliability to
upstream parent contributors.

REQ-GSDA-REL-013
Human adjudication MAY explicitly attribute credit or blame.

REQ-GSDA-REL-014
Without a qualifying outcome, reliability MUST remain unchanged.

REQ-GSDA-REL-015
Reliability updates MUST be deterministic for a fixed evidence set.

REQ-GSDA-REL-016
When the reliability means of two candidates differ by no more than
reliability_policy.mean_epsilon, the coordinator MUST prefer the
peer with higher sample_count. When sample_count is also equal, the
coordinator MUST apply REQ-GSDA-REL-022.

REQ-GSDA-REL-017
The reliability update is defined as follows. Let:

  total = alpha + beta
  M     = maximum_reliability_evidence
  w     = s + f

If w > M, the update MUST fail with RELIABILITY_BOUNDS_EXCEEDED.

If config.reliability_profile = FLAT:
  If total + w > M, the update MUST fail with
  RELIABILITY_BOUNDS_EXCEEDED.
  Else alpha' = alpha + s; beta' = beta + f.

If config.reliability_profile = DECAYING:
  If total + w <= M:
    alpha' = alpha + s
    beta'  = beta  + f
  Else:
    keep = M - w
    If keep < 0:
      alpha' = s
      beta'  = f
    Else if total == 0:
      alpha' = cold_start_alpha
      beta'  = cold_start_beta
      If alpha' + beta' == 0:
        fail with RELIABILITY_BOUNDS_EXCEEDED.
    Else:
      alpha_scaled = (alpha * keep) div total
      beta_scaled  = (beta  * keep) div total
      remainder    = keep - alpha_scaled - beta_scaled
      If alpha >= beta:
        alpha' = alpha_scaled + remainder + s
        beta'  = beta_scaled + f
      Else:
        alpha' = alpha_scaled + s
        beta'  = beta_scaled + remainder + f

REQ-GSDA-REL-017A
Before applying DECAYING proportional scaling, the reliability record
MUST satisfy alpha + beta > 0. If alpha + beta = 0, the coordinator
MUST materialize cold-start values per REQ-GSDA-REL-002 before
applying the update. If the resulting cold-start total remains zero,
the update MUST fail closed with RELIABILITY_BOUNDS_EXCEEDED.

REQ-GSDA-REL-018
sample_count' = sample_count + s + f.

REQ-GSDA-REL-019
For purposes of this requirement, a peer has "reached maximum
reliability evidence" for an activity when, after an update, its
alpha + beta is equal to maximum_reliability_evidence. When the
number of such peers exceeds
liveness_policy.bound_saturation_threshold, the coordinator MUST
emit RELIABILITY_SATURATION evidence and MUST break further ties by
fairness rotation per REQ-GSDA-REP-015.

REQ-GSDA-REL-020
REQ-GSDA-REL-020 is reserved and MUST NOT be assigned.

REQ-GSDA-REL-021
independent_observation_count MUST be used as a secondary ranking
signal per REQ-GSDA-AGG-010 step 2.5 and per REQ-GSDA-REL-022.

REQ-GSDA-REL-022
When two peers have equal reliability means for an activity, the
coordinator MUST prefer the peer with the higher
independent_observation_count. When those are also equal, the
coordinator MUST apply the fairness rotation per REQ-GSDA-REP-015.

REQ-GSDA-REL-023
After any update, alpha' and beta' MUST both be >= 0. A computation
that would produce a negative value MUST instead fail with
RELIABILITY_BOUNDS_EXCEEDED.

REQ-GSDA-REL-024
Reliability MUST NOT be claimed to preserve the mean across an
update that adds new evidence. The Bayesian update is allowed to
shift the mean toward s / (s + f). The only guarantee in DECAYING
mode is that decay of the prior is proportional and that no
intermediate value exceeds M or falls below 0.

REQ-GSDA-REL-025
If s + f > maximum_reliability_evidence, the update MUST fail with
RELIABILITY_BOUNDS_EXCEEDED.

REQ-GSDA-REL-026
decay_mean_tolerance applies only in DECAYING mode when a decay
scaling step is performed. If |mean' - mean| > decay_mean_tolerance
where mean' is the post-decay mean before new evidence is added,
the coordinator MUST emit RELIABILITY_SATURATION evidence recording
the drift. The update itself MUST NOT be rejected on this ground;
the evidence exists for auditability.

TESTABILITY: TESTABLE

27. RELIABILITY UPDATE
================================================================================

For an activity with prior (alpha, beta) and observed (s, f):

  total = alpha + beta
  M     = maximum_reliability_evidence

The update follows REQ-GSDA-REL-017 and REQ-GSDA-REL-017A.

mean = (1000 * alpha') div (alpha' + beta')

where s and f are weighted integer counts derived from the outcome
class, using outcome_weights from config:

  HUMAN_ADJUDICATION:        default weight 100
  KERNEL_STRUCTURAL:         default weight 50
  INDEPENDENT_CORROBORATION: contributes to independent_observation_count
                             only.

A single SUCCESS outcome with weight w increments s by w.
A single FAILURE outcome with weight w increments f by w.
A NEUTRAL outcome does not change s or f.
A CORROBORATED outcome increments independent_observation_count by 1
per attribution_peer_id, and emits independent_observation records.

REQ-GSDA-REL-100
The implementation MUST declare cold_start_alpha, cold_start_beta,
maximum_reliability_evidence, and outcome_weights.

REQ-GSDA-REL-101
Reliability calculation MUST use integer arithmetic.

REQ-GSDA-REL-102
A future reliability profile MAY define conservative lower bounds.
Such a profile requires a new specification revision.

32. REVISION DIFF
================================================================================

Requirement matching is by requirement_id.
Term matching is by term_id.
Assumption matching is by assumption_id.
Question matching is by question_id.

Diff categories: ADDED_REQUIREMENT, REMOVED_REQUIREMENT,
MODIFIED_REQUIREMENT, REWORDED_REQUIREMENT, ADDED_TERM, REMOVED_TERM,
MODIFIED_TERM, ADDED_QUESTION, RESOLVED_QUESTION,
CHANGED_ASSUMPTION, CHANGED_STATUS.

Normalization for comparison is field-specific:

  normative_text       line endings LF; ASCII whitespace runs
                       collapsed to single space; leading and trailing
                       ASCII whitespace trimmed.

  definition           same as normative_text, then NFC for comparison
                       only.

  statement            same as normative_text.

  question             same as normative_text.

  structured fields    exact after canonical_record_jcs.

RFC 2119 keyword changes MUST be treated as MODIFIED, not REWORDED.

REQ-GSDA-DIFF-001
A field changed in one of the compared records MUST produce a
recorded change.

REQ-GSDA-DIFF-002
A requirement whose normative_text changes only by the permitted
whitespace normalization MUST be classified REWORDED.

REQ-GSDA-DIFF-003
Changes to severity, status, intent_links, related_requirements,
related_terms, related_tests, testability, or untestable_reason MUST
be recorded even if normative_text is unchanged.

REQ-GSDA-DIFF-004
Status transitions MUST be recorded separately as CHANGED_STATUS.

REQ-GSDA-DIFF-005
The diff algorithm MUST be deterministic for a fixed pair of
revisions.

REQ-GSDA-DIFF-006
Diff comparison of definitions and terminology-stability checks MUST
use the same normalization rule.

REQ-GSDA-DIFF-007
Case MUST remain significant for every field. No case folding MUST
be applied during diff comparison, except the NFC normalization
explicitly permitted for definition comparison by REQ-GSDA-DIFF-006.

REQ-GSDA-CSM-001
The coordinator transition function MUST be:

  next_state = T(current_state, round_outcome, SnapshotRoundContext)

where T is evaluated as the following ordered decision table. The
first row whose source matches the current state and whose guard
evaluates to true is selected.

  1. INIT                  -> VALIDATING_BOOTSTRAP  guard: true
  2. VALIDATING_BOOTSTRAP  -> EXTRACTING            guard: pass0_ok
  3. VALIDATING_BOOTSTRAP  -> FAILED_CLOSED         guard: !pass0_ok
  4. EXTRACTING            -> FORMALIZING           guard: true
  5. FORMALIZING           -> SCORING               guard: true
  6. SCORING               -> AGGREGATING           guard: scores_complete
                                                          AND !rescore_phase
  7. SCORING               -> ANALYZING             guard: scores_complete
                                                          AND rescore_phase
  8. AGGREGATING           -> SCHEDULING_REPAIR     guard: true
  9. SCHEDULING_REPAIR     -> REPAIRING             guard: triples_remaining
 10. SCHEDULING_REPAIR     -> SCORING               guard: !triples_remaining
 11. REPAIRING             -> SCORING               guard: true
 12. ANALYZING             -> SCORING               guard: refine_required
 13. ANALYZING             -> AWAITING_HUMAN        guard: !refine_required
 14. AWAITING_HUMAN        -> PUBLISHING            guard: human_accept
 15. AWAITING_HUMAN        -> SCORING               guard: human_reject
 16. PUBLISHING            -> PUBLISHED             guard: gate_pass
 17. PUBLISHING            -> FAILED_CLOSED         guard: !gate_pass
 18. any except PUBLISHED  -> FAILED_CLOSED         guard: unrecoverable

Guard definitions:

  pass0_ok                ValidateBootstrapMeta returned no errors.
  scores_complete         every required score for every scored target
                          has been collected or explicitly recorded
                          as unavailable.
  rescore_phase           the current round is a rescore round that
                          follows a REPAIR phase.
  triples_remaining       at least one scheduled repair triple has not
                          yet been performed.
  refine_required         at least one REFINE reason per PROC-004
                          exists.
  human_accept            a valid HumanDecision with action=ACCEPT
                          satisfying REQ-GSDA-REV-001 exists.
  human_reject            a valid HumanDecision with action=REJECT
                          exists.
  gate_pass               ValidatePublicationGate returned a clean
                          result, or a valid override per HUM-116
                          applies.
  unrecoverable           a LINEAGE_FAILURE, IDENTITY_MISMATCH,
                          CONTENT_IDENTITY_MISMATCH, or similar
                          non-recoverable invariant fault occurred.

REQ-GSDA-CSM-002
An undefined transition MUST cause FAILED_CLOSED and MUST emit

REQ-GSDA-CSM-003
Deterministic replay MUST replay state transitions using stored

REQ-GSDA-CSM-004

REQ-GSDA-CSM-005

REQ-GSDA-CSM-006

GOVERNANCE_FAILURE.

REQ-GSDA-CSM-007

37. CONVERGENCE AND STAGNATION
================================================================================

Convergence criteria: no blocking open questions; no unresolved
ESTABLISHED contradictions; no blocking findings; all critical
intent elements traced; all related_requirements references resolve;
all related_terms references resolve; no newly introduced CRITICAL
findings; requirement coverage stable; terminology stable; score
movement below convergence_policy.score_stability_threshold across
convergence_policy.stable_rounds; no HIGH_DISAGREEMENT criterion
above threshold.

Definitions:

  requirement coverage stable
      the set of requirement_ids is identical across the last
      convergence_policy.stable_rounds rounds.

  terminology stable
      the set of term_ids and their canonical_record_jcs-serialized
      definitions are identical across the last
      convergence_policy.stable_rounds rounds, using the same
      whitespace-insensitive normalization as REQ-GSDA-DIFF-002.

  score movement
      max over all defined A(r,k) of |A(r,k)_current -
      A(r,k)_previous|. Below threshold when this max is strictly
      less than convergence_policy.score_stability_threshold.

  meaningful repair
      a repair whose diff per Section 32 is non-empty.

  meaningful revision
      a revision whose diff per Section 32 is non-empty.

REQ-GSDA-CNV-001
Score stability alone MUST NOT be sufficient for convergence.

REQ-GSDA-CNV-002
The number of consecutive stable rounds required for convergence
MUST be convergence_policy.stable_rounds.

REQ-GSDA-CNV-003
The exact convergence thresholds MUST be recorded in provenance.

REQ-GSDA-CNV-004
Stagnation MUST be evaluated over stagnation_policy.window_rounds
rounds.

REQ-GSDA-CNV-005
Stagnation means that within the configured window there is no new
requirement, resolved requirement, new finding, resolved finding,
meaningful repair, meaningful revision, or score movement above
stagnation_policy.score_threshold.

REQ-GSDA-CNV-006
On stagnation the coordinator MUST change at least one of: peer
composition, role assignment, prompt strategy, candidate-generation
strategy, analysis focus.

REQ-GSDA-CNV-007
If stagnation persists beyond liveness_policy.max_stagnant_rounds,
the coordinator MUST terminate with LIVENESS_FAILURE.

REQ-GSDA-CNV-008
The coordinator MUST terminate on any of: human acceptance,
configured maximum rounds, convergence reached, stagnation without
recovery, blocking ambiguity requiring human input, explicit
cancellation.

41. INTENT COVERAGE
================================================================================

REQ-GSDA-CVG-001
Intent coverage is defined as:

  if |intent_elements| == 0:
    coverage = 0
    Emit INTENT_LOSS_DETECTED evidence.
    Emit COVERAGE_REPORT evidence with total = 0.
    The coordinator MUST mark the task F_INSUFFICIENT_COVERAGE.
  else:
    coverage = |intent_elements linked to at least one ACTIVE
               requirement| / |intent_elements|

An intent_element is linked when at least one ACTIVE requirement has
that intent_id in its intent_links.

REQ-GSDA-CVG-002
Critical coverage is defined over the subset of intent_elements
whose occurrence_weight meets or exceeds
config.intent_criticality_policy.critical_weight_threshold. If the
subset is empty, critical coverage is defined as 1 (vacuous truth).
Otherwise critical coverage equals the fraction of elements in the
subset that are linked.

REQ-GSDA-CVG-003
PUB-001 condition CriticalIntentCoverageComplete is satisfied when
critical coverage equals 1.

REQ-GSDA-CVG-004
A COVERAGE_REPORT evidence record MUST be emitted at the close of
every round. Its content MUST match the CoverageReport in
REQ-GSDA-HUM-101. The report MUST list uncovered intent_ids,
uncovered critical intent_ids, and the byte offsets of their source
fragments.

REQ-GSDA-CVG-005
Critical coverage less than 1 MUST block publication unless a human
Decision per REQ-GSDA-HUM-116 explicitly overrides the
F_INSUFFICIENT_COVERAGE condition and names the uncovered
intent_ids in override_conditions and rationale.

ExtractIntentElements MUST produce a deterministic set of

  1. Split text at sentence boundaries: period, question mark, or
     exclamation mark followed by whitespace and an uppercase letter
     or digit; a single newline; or an explicit marker matching
     startsWith any entry in
     intent_segmentation_policy.marker_prefixes, applied
     longest-match-first per REQ-GSDA-CFG-021.

     sentence immediately before the keyword.

  3. If a fragment is shorter than
     intent_segmentation_policy.min_fragment_length, merge it with
     the following fragment. If none follows, merge with the
     preceding fragment.

     the longest segment at each source position. On partial overlap,
     the segment starting earlier in source order takes precedence.
     When two segments have equal length and equal start position,
     the segment with the bytewise-smallest text is kept. Discarded
     segments MUST be recorded as OVERLAP_DISCARDED evidence with
     their byte offsets.

     finding and record INTENT_LOSS_DETECTED evidence with the byte
     offsets.

46. STATE TRANSITIONS
================================================================================

  CREATED --[task valid]--> ACTIVE
  ACTIVE --[convergence criteria met]--> CONVERGED
  ACTIVE --[human review requested]--> AWAITING_HUMAN
  CONVERGED --[human review requested]--> AWAITING_HUMAN

REQ-GSDA-STM-005

REQ-GSDA-STM-006

51. TRUST BOUNDARY MODEL
================================================================================

[Informative] GSDA treats every input from an LLM peer as untrusted.
The trust boundary model is normative in TRUST-001 through TRUST-005.

Trust zones:

  T0  External world (humans, documents, upstream systems)
  T1  LLM provider
  T2  Peer adapter
  T3  Coordinator input store
  T4  Deterministic kernel
  T5  Authoritative state
  T6  Human acceptance
  T7  Published revision

REQ-GSDA-TRUST-001
Data flow MUST be directed:

  T0 -> T1 -> T2 -> T3 -> T4 -> T5 -> T6 -> T7

T5 -> T4 is permitted for read-only kernel operations.
T5 -> T2 is forbidden except through explicitly defined request data.
T1 -> T4 is forbidden.
T2 -> T5 is forbidden.
T1 -> T5 is forbidden.

REQ-GSDA-TRUST-002
A peer adapter MUST NOT write to T5. It MAY write only to T3.

REQ-GSDA-TRUST-003
The deterministic kernel MUST reject any input that does not carry a
validated T3 provenance.

REQ-GSDA-TRUST-004
A trust-boundary crossing MUST be recorded as provenance. Every
artifact MUST carry provenance identifying the zone transitions
that produced it.

REQ-GSDA-TRUST-005
The kernel MUST treat every payload originating in T1 as an
untrusted proposal. No payload from T1 may directly become
authoritative state. Authoritative state MUST be produced by a
kernel operation acting on validated T3 inputs.

invariant in this section. Failure MUST be reported through the
error taxonomy in Section 3 and MUST NOT be silently ignored.

54. ALGORITHM CONTRACTS
================================================================================

[Informative] This section defines executable contracts for the most
subtle kernel operations. Each contract lists inputs, preconditions,
the algorithm, postconditions, forbidden dependencies, arithmetic
domain, failure codes, and required vectors. These contracts are
normative.

REQ-GSDA-ALG-001
CompareRationalAggregate

  Inputs:
    (A1, R1, D1)  rational aggregate triple
    (A2, R2, D2)  rational aggregate triple

  Preconditions:
    D1 > 0
    D2 > 0
    0 <= R1 < D1
    0 <= R2 < D2
    status1 = DEFINED
    status2 = DEFINED

  Output:
    -1 | 0 | +1

  Algorithm:
    1. If A1 != A2: return sign(A1 - A2).
    2. Compute L = R1 * D2 with 128-bit overflow check.
    3. Compute R = R2 * D1 with 128-bit overflow check.
    4. If L and R are both representable:
         return sign(L - R).
    5. Else reduce both fractions by gcd(A*D+R, D):
         A1r, R1r, D1r = reduce(A1, R1, D1)
         A2r, R2r, D2r = reduce(A2, R2, D2)
       If A1r != A2r: return sign(A1r - A2r).
       Retry cross multiplication on (R1r, D2r) and (R2r, D1r).
    6. If still overflowing: fail with AGGREGATION_BOUNDS_EXCEEDED.

  Postconditions:
    Return is a total order consistent with exact rational
    comparison of A + R/D.

  Forbidden dependencies: none.

  Failure codes: AGGREGATION_BOUNDS_EXCEEDED.

  Required vectors: see Section 55.

REQ-GSDA-ALG-002
UpdateReliability

  Inputs:
    prior (alpha, beta, sample_count, independent_observation_count)
    observations (s, f, corroborations)
    config: reliability_profile, cold_start_alpha,
            cold_start_beta, maximum_reliability_evidence

  Preconditions:
    alpha >= 0, beta >= 0, s >= 0, f >= 0, corroborations >= 0
    maximum_reliability_evidence >= 1

  Algorithm:
    total = alpha + beta
    M = maximum_reliability_evidence
    w = s + f
    If w > M: fail RELIABILITY_BOUNDS_EXCEEDED.
    If reliability_profile = FLAT:
      If total + w > M: fail RELIABILITY_BOUNDS_EXCEEDED.
      alpha' = alpha + s; beta' = beta + f.
    If reliability_profile = DECAYING:
      If total + w <= M: alpha' = alpha + s; beta' = beta + f.
      Else:
        keep = M - w
        If keep < 0: fail RELIABILITY_BOUNDS_EXCEEDED.
        If total == 0:
          alpha' = cold_start_alpha; beta' = cold_start_beta
          If alpha' + beta' == 0: fail RELIABILITY_BOUNDS_EXCEEDED.
        Else:
          alpha_scaled = (alpha * keep) div total
          beta_scaled  = (beta  * keep) div total
          remainder = keep - alpha_scaled - beta_scaled
          If alpha >= beta:
            alpha' = alpha_scaled + remainder + s
            beta'  = beta_scaled + f
          Else:
            alpha' = alpha_scaled + s
            beta'  = beta_scaled + remainder + f
    If alpha' < 0 or beta' < 0: fail RELIABILITY_BOUNDS_EXCEEDED.
    If alpha' + beta' > M: fail RELIABILITY_BOUNDS_EXCEEDED.
    sample_count' = sample_count + w
    independent_observation_count' =
        independent_observation_count + corroborations

  Postconditions:
    alpha' >= 0, beta' >= 0, alpha' + beta' <= M.

  Failure codes: RELIABILITY_BOUNDS_EXCEEDED.

  Required vectors: see Section 55.

REQ-GSDA-ALG-003
ComputeVariance

  Inputs:
    values: non-empty list of integers in 0..1000

  Preconditions:
    n >= 1

  Algorithm:
    sum_v = sum(values)
    sum_sq = sum over v of v * v
    variance_num = n * sum_sq - sum_v * sum_v
    variance_denom = n * n
    Reduce (variance_num, variance_denom) by gcd.
    variance_x1000 = (variance_num * 1000) div variance_denom
    remainder = (variance_num * 1000) mod variance_denom

  Postconditions:
    variance_num >= 0
    variance_denom > 0
    variance_x1000 is a floor representation of the exact rational.

  Failure codes: AGGREGATION_BOUNDS_EXCEEDED.

REQ-GSDA-ALG-004
ComputeFairnessKey

  Inputs:
    round_index: non-negative integer
    slot_index: non-negative integer
    configured_max_peers: integer >= 1

  Algorithm:
    fairness_key = (round_index + slot_index)
                   mod configured_max_peers

  Postconditions:
    0 <= fairness_key < configured_max_peers.

REQ-GSDA-ALG-005
ValidateLineage

  Inputs:
    artifact_id
    parent_artifact_ids
    parent_anc_hashes
    lineage store
    maximum_lineage_depth

  Algorithm:
    1. Verify parent_anc_hashes sorted bytewise ascending.
    2. Verify each parent_anc_hash matches recomputed
       ancestor_chain_hash of the corresponding parent.
    3. Traverse parent closure from artifact_id, bounded by
       maximum_lineage_depth.
    4. If artifact_id appears in the closure: LINEAGE_FAILURE.
    5. If traversal exceeds maximum_lineage_depth: LINEAGE_FAILURE.
    6. Recompute ancestor_chain_hash of artifact_id and compare.
    7. If mismatch: LINEAGE_FAILURE.

  Postconditions:
    Either LINEAGE_FAILURE is raised, or the artifact's lineage is
    acyclic and hashes match.

ExtractIntentElements

  Postconditions:

REQ-GSDA-ALG-007
SelectLatestScore

    Return the first element.
    If two elements compare equal on all keys and are distinct
    records, fail with GOVERNANCE_FAILURE.

REQ-GSDA-ALG-008
PromoteLiveness

  Inputs:
    open CRITICAL findings
    current round_index
    critical_promotion_rounds
    alternate_promotion_cap
    B_effective

  Algorithm:
    1. Select findings with OPEN status, severity CRITICAL, and
       age >= critical_promotion_rounds.
    2. Sort by (created_at ASC, finding_id ASC).
    3. Take up to min(alternate_promotion_cap, B_effective) findings.
    4. If more qualify than the cap, emit ALTERNATE_VIABLE_PROMOTION
       evidence listing the remainder.

  Postconditions:
    At most min(alternate_promotion_cap, B_effective) LIVENESS_PROMOTION
    records emitted this round.

58. INFORMATIVE: WHAT GSDA DOES NOT PROMISE
================================================================================

[Informative] The following is informative only.

[Informative] GSDA does not promise: objective truth in arbitrary
domains; deterministic LLM generation; perfect specification
completeness; unanimous peer agreement; elimination of LLM
hallucination; automatic resolution of human decisions; score as
proof; consensus as truth; reliability as truth.

[Informative] GSDA does claim: deterministic coordinator behaviour;
deterministic replay of coordinator decisions; content identity
independent of provenance; artifact identity preserving provenance
and lineage; spec_content identity independent of history; global
revision identity preserving history; explicit uncertainty;
immutable provenance; preservation of disagreement; controlled
cross-repair; reproducible aggregation; explicit human governance.

[Informative] The central abstraction is: LLMs produce evidence. The
coordinator produces state. The kernel produces deterministic facts.
Reliability weights evidence. Humans resolve epistemic uncertainty.
The revision is the governed specification.

================================================================================
59. FINAL PRINCIPLE
================================================================================

[Informative] The purpose of GSDA is not to find a single perfect
LLM.

[Informative] The purpose is to construct a process in which
imperfect LLMs can repeatedly improve one another's work.

[Informative] The fundamental operation is:

  PROPOSE
  -> CRITICIZE
  -> SCORE
  -> AGGREGATE
  -> REPAIR
  -> RESCORE
  -> ANALYZE
  -> REFINE
  -> REPEAT
  -> HUMAN REVIEW
  -> PUBLISH

[Informative] The system is a cooperative specification workshop
implemented as a deterministic orchestration system, populated by
multiple untrusted LLM reasoning peers.

[Informative] No single peer is the specification. No single peer is
the reviewer. No score is truth. No consensus is proof.

[Informative] The quality of the specification emerges from repeated
independent reasoning, criticism, cross-repair, explicit scoring,
controlled reliability, preserved provenance, and human governance.
