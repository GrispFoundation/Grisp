================================================================================
0. PURPOSE
================================================================================

GRISP Agent v2.0 is a general-purpose AI software engineering agent that
produces VERIFIED ENGINEERING ARTIFACTS, not merely plausible text.

It combines:

  - a deterministic verification and execution kernel;
  - a multi-LLM cooperative reasoning layer;
  - optional debugging and test-program capabilities;
  - a browser-based AI transport layer;
  - a strict artifact / evidence / provenance model;
  - a fail-closed acceptance gate.

The fundamental invariant is:

  NO UNVERIFIED ARTIFACT MAY BECOME AN ACCEPTED GRISP RESULT.

================================================================================
1. PRIORITY ORDER
================================================================================

  CORRECTNESS
  > SAFETY
  > DETERMINISM
  > VERIFIABILITY
  > PROVENANCE
  > ROBUSTNESS
  > CLARITY
  > PERFORMANCE
  > COST
  > STYLE

A lower-priority property must never override a higher-priority one.

Examples:
  - a fast result cannot override a failed compiler;
  - a highly trusted LLM cannot override a failed test;
  - consensus between many LLMs cannot override a GRISP policy rejection;
  - a high subjective score cannot override missing evidence.

================================================================================
2. NON-NEGOTIABLE INVARIANTS
================================================================================

  I1  UNPARSED DATA CANNOT BECOME AN ARTIFACT.
  I2  FAILED OBJECTIVE VALIDATION CANNOT BECOME ACCEPTED.
  I3  AI OPINION CANNOT OVERRIDE OBJECTIVE FAILURE.
  I4  UNRECOGNIZED PLAN CANNOT EXECUTE.
  I5  FINAL COMMITTED BYTES MUST EQUAL FINAL VERIFIED BYTES.
  I6  EVERY ACCEPTED ARTIFACT MUST HAVE TRACEABLE EVIDENCE.
  I7  EVERY AI REQUEST MUST HAVE A UNIQUE REQUEST ID.
  I8  EVERY AI SESSION MUST HAVE A STABLE SESSION ID.
  I9  TAB INDEX IS NOT TAB IDENTITY.
  I10 TRANSPORT MUST NOT MODIFY SEMANTIC CONTENT.
  I11 PARSER MUST NEVER INVENT DATA.
  I12 POLICY IS FAIL-CLOSED.
  I13 STATE TRANSITIONS REQUIRE EVIDENCE.
  I14 CANONICAL IDENTITY IS DETERMINISTIC.
  I15 MULTI-LLM SCORING IS ADVISORY ONLY.
  I16 NO LLM MAY CERTIFY ITS OWN IMPLEMENTATION.
  I17 NO FORCE-ACCEPT PATH MAY EXIST.
  I18 OPTIONAL CAPABILITIES MAY NOT BE IMPLIED BY CONSENT.

================================================================================
3. ROLES
================================================================================

  - COORDINATOR
      Deterministic orchestrator. Runs the protocol, negotiates capabilities,
      aggregates evidence, updates reliability, calls GRISP, commits.

  - AI WORKERS (PEERS)
      Untrusted external reasoning engines. Generate candidates, critiques,
      repairs, test programs, capability requests, scores, adversarial
      reviews. Never establish correctness.

  - GRISP KERNEL
      Deterministic verification and execution layer. Parses, canonicalizes,
      hashes, validates policy, compiles, runs, tests, verifies, commits.

  - TOOL ENGINE
      Real compilers, runtimes, test runners, debuggers, LSPs, tree-sitters,
      static analyzers, crash-log readers. Executed only through GRISP.

  - GARP GATEWAY (Firefox)
      Browser AI transport. Stateful sessions, stable tab identity, request
      correlation, streaming events, cancellation.

  - EVIDENCE / ARTIFACT STORE
      Immutable records. Artifacts, files, evidence, decisions, provenance.

  - FINAL VERIFIER
      Hard acceptance gate. Operates on the exact bytes to be committed.

  - EXPLAINER
      Human-readable summary. Never authoritative.

================================================================================
7. CANONICALIZATION
================================================================================

Canonical JSON rules:

  - UTF-8 encoding;
  - no insignificant whitespace;
  - no line breaks outside strings;
  - object keys sorted by UTF-8 bytewise order;
  - arrays preserve semantic order;
  - integers only (no floats in core identity semantics);
  - stable string escaping;
  - stable integer formatting.

File ordering for canonicalization:

  1. filename UTF-8 bytewise lexicographic;
  2. content_sha256 UTF-8 bytewise lexicographic.

Ordering must NOT depend on:
  - locale;
  - case-insensitive comparison;
  - Windows filesystem sort order;
  - incidental JSON-library object ordering.

Invalid metadata is a hard error. It must never be silently replaced with {}.

No implicit normalization is permitted before hashing:
  - no CRLF to LF conversion;
  - no Unicode NFC normalization on artifact bytes;
  - no whitespace trimming;
  - no encoding conversion.

If a transformation changes bytes, it creates a new artifact.

================================================================================
8. PARSER CONTRACT
================================================================================

Preferred path:

  GAI/1.0 structured response
      -> schema validation
      -> artifact extraction
      -> hash validation
      -> ArtifactBundle

Markdown is compatibility-only.

Parser results:

  PARSED
  PARSE_ERROR
  PARSE_AMBIGUOUS
  SCHEMA_ERROR
  HASH_MISMATCH

The parser must reject:

  - missing required filename;
  - multiple valid interpretations;
  - task_id mismatch between response and caller;
  - absolute path;
  - drive-qualified path;
  - UNC path;
  - path traversal;
  - embedded NUL;
  - unsupported encoding;
  - unknown language;
  - truncated fence;
  - unterminated fence;
  - duplicate filename;
  - conflicting filename declarations.

No heuristic cleanup is allowed. Tokens such as "CopyDownload",
"Delphiprogram", or "Pascalprogram" become PARSE_ERROR, not silent repair.

Filename inference is prohibited unless the task explicitly supplies an
expected filename. The parser must never invent a filename.

Markdown extraction must explicitly specify whether the newline adjacent to
the closing fence belongs to the artifact. Parser transformations must never
silently change artifact bytes.

================================================================================

States:

  CREATED
  PARSED
  NORMALIZED
  STATIC_VALID
  COMPILE_PENDING
  COMPILED
  RUNTIME_PENDING
  RUNTIME_VERIFIED
  TEST_PENDING
  TEST_VERIFIED
  POLICY_VERIFIED

  FINAL_VERIFIED

Failure states:

  PARSE_FAILED
  STATIC_FAILED
  POLICY_REJECTED
  COMPILE_FAILED
  RUNTIME_FAILED
  TEST_FAILED
  TIMEOUT
  CANCELLED
  CRASHED
  VERIFICATION_FAILED
  COMMIT_FAILED

A transition is defined by:

  current state
  + event
  + required evidence
  + guards
  = next state

A string event such as "compile_ok" is not sufficient. Valid compilation
evidence must exist and must be bound to the exact artifact.

No failure state may transition directly to an accepted state.

No implicit transition from failure to accepted may exist.

================================================================================
11. ACCEPTANCE PREDICATE
================================================================================

Acceptable(Task, Candidate) =

    ArtifactValid
AND StaticValid
AND PolicyValid
AND RequiredBuildValid
AND RequiredRuntimeValid
AND RequiredTestsValid
AND ProvenanceComplete
AND FinalVerificationValid

Missing evidence for a required check means FALSE, not unknown assumed true.

Applicability of compile / runtime / test is derived from artifact kind and
must be explicit. "Not applicable" is a contract value, not an inference from
a skipped step.

================================================================================
12. OBJECTIVE EVIDENCE RULE
================================================================================

Objective validation must never be inferred from:

  - LLM opinion;
  - worker score;
  - number of approving agents;
  - provider reputation;
  - previous successful run;
  - human confidence.

Only the applicable objective evidence can satisfy an objective gate.

  requested

  granted
  used

PolicyResult fields:

  policy_profile
  capabilities_requested[]
  capabilities_granted[]
  checks[]
  result
  reason

  policy_id
  result
  details

  PASS
  FAIL
  REQUIRES_HUMAN_APPROVAL

High-risk capabilities may require human approval after objective
verification, not instead of it.

================================================================================
14. CAPABILITIES
================================================================================

Capabilities are explicit, immutable security objects.

Example capability names:

  read
  write
  list
  delete
  compile
  run
  debug
  inspect_state
  stack_trace
  lsp_diagnostics
  ast_parse
  test_execute
  read_logs
  browser_ai
  network
  process_spawn

A capability has:

  name
  root
  allowed operations
  allowed MIME types
  maximum size

A capability request does not grant the capability. The policy engine decides.

Optional capabilities include:

  - syntax check;
  - semantic check (LSP);
  - compile;
  - run;
  - debugger;
  - stack trace;
  - tree-sitter AST;
  - test-program execution.

Peers may request capabilities when they judge the task complex, risky,
uncertain, or previously crashy. Peers should not request capabilities for
trivial or obviously correct code.

Baseline lightweight checks (syntax parse, quick compile, single quick run,
short stack trace on crash) may be enabled automatically for artifacts that
touch execution. Heavy debugging and full test programs remain optional.

15. MULTI-LLM REASONING LAYER
================================================================================

Roles:

  Generator
  Analyst
  Critic
  Repairer
  Test Designer
  Adversarial Reviewer
  Verifier
  Documentation Agent
  Specialist (Delphi, Windows, security, performance, compiler, database,
              network)

Peer outputs are always classified as:

  SUBJECTIVE_AI_EVIDENCE

They may contribute to:

  quality_score
  reviewer_confidence
  repair priority
  provider selection

They cannot satisfy:

  compile gate
  runtime gate
  test gate
  policy gate
  artifact integrity
  final verification

Consensus does not mean acceptance. Consensus means confidence increase only.

Worker reliability is capability-specific. At minimum:

  generation
  critique
  repair
  test_design
  scoring
  protocol

Reliability updates should be evidence-weighted, ideally Bayesian, rather
than a single fixed increment.

================================================================================
16. OPTIONAL DEBUGGING AND TEST PROGRAMS
================================================================================

Debugging and test programs are optional capabilities, not mandatory steps.

Peer may emit a capability request such as:

  capability_request:
    target: some_peer
    capabilities:
      - syntax_check
      - compile
      - runtime
      - stack_trace
      - test_execute
    reason: "Repair introduces pointer arithmetic"

The coordinator merges requests, applies policy, and activates only approved
capabilities. If no peer requests debugging or tests, those phases are skipped.

Test programs must target the actual artifact. A test that recreates the
implementation, invents APIs, or cannot execute against the real artifact is
marked TEST_INVALID and cannot produce acceptance evidence.

Test descriptor fields:

  test_id
  test_target
  test_type
  oracle
  coverage_intent

Test types:

  black_box
  unit
  integration
  property

================================================================================
17. SCORING AND AGGREGATION
================================================================================

Scoring is advisory. It ranks eligible candidates only.

Eligible set:

  parsed
  AND policy_ok
  AND required_build_ok
  AND required_runtime_ok
  AND required_tests_ok

Subjective scoring may use:

  score_value
  confidence
  external debug/test feedback
  peer reliability

External correctness may include:

  syntax
  semantic
  compile
  runtime
  test pass
  crash count
  timeout count
  breakpoint violations

Weights are configurable.

A candidate with compile=false is ineligible regardless of subjective score.

Tie-breaking should prefer:

  1. higher median external correctness;
  2. lower variance across subjective scores;
  3. higher sum of reliability among supporters.

================================================================================
21. COMMIT
================================================================================

Commit is transactional:

  FINAL_VERIFIED
      -> prepare
      -> stage exact bytes
      -> write
      -> read back
      -> verify hashes
      -> atomic publish / rename
      -> re-read committed bytes
      -> verify identity
      -> record commit evidence
      -> COMMITTED

If committed bytes differ from verified bytes: COMMIT_FAILED.

A partial write must never be reported as committed.

There must be no force-accept path. Draft output may be exported outside the
accepted artifact namespace (for example /workspace/draft/), but only the
accepted namespace (for example /workspace/final/) contains accepted artifacts.

25. IMPLEMENTATION METHODOLOGY
================================================================================

GRISP itself must be built using a multi-LLM review mesh:

  Specification
      -> Requirement extraction
      -> Specification audit
      -> Implementation contract
      -> Test generation
      -> Architecture design
      -> Independent implementation
      -> Deterministic build
      -> Static validation
      -> Independent code review
      -> Adversarial review
      -> Conformance testing
      -> Repair cycle
      -> Full verification
      -> Acceptance decision
      -> Immutable commit

Minimum logical roles:

  1. Requirements Analyst
  2. Specification Auditor
  3. Implementation Agent
  4. Independent Code Reviewer
  5. Adversarial Reviewer
  6. Test / Conformance Agent
  7. Deterministic Verification System

No LLM may declare its own implementation correct. Deterministic gates decide.

Trust levels:

  T0  Untrusted LLM output
  T1  Parsed candidate artifact
  T2  Deterministically validated artifact
  T3  Compiled artifact
  T4  Runtime-verified artifact
  T5  Test-verified artifact
  T6  Policy-verified artifact
  T7  Final-verified artifact
  T8  Accepted / committable artifact

An artifact must not skip trust levels.

================================================================================
28. ABSOLUTE IMPLEMENTATION RULE
================================================================================

DO NOT MAKE THE IMPLEMENTATION MORE PERMISSIVE THAN THE SPECIFICATION.

When implementation encounters ambiguity: reject.
When evidence is missing: fail the gate.
When identity is uncertain: fail verification.
When the browser state is unknown: report unknown or error.
When the AI response is malformed: PARSE_ERROR.
When committed bytes differ from verified bytes: COMMIT_FAILED.

The system's job is not to make questionable inputs look successful. Its job
is to make the boundary between UNVERIFIED and VERIFIED unmistakable.

Preserve this transformation:

  UNTRUSTED INPUT
        -> STRICT INTERPRETATION
        -> IMMUTABLE ARTIFACT
        -> OBJECTIVE MEASUREMENT
        -> IMMUTABLE EVIDENCE
        -> DETERMINISTIC GATE
        -> FINAL RE-VERIFICATION
        -> BYTE-IDENTICAL COMMIT

Never:

  UNTRUSTED INPUT
        -> HEURISTIC CLEANUP
