The Improved Edition (Parts 1–5) is a readability-oriented rewrite of the original GSDA/3.1. It preserves the core architecture (T0–T7 trust zones, deterministic kernel as sole authority, semantic vs. execution identity separation, strict adapter rules, exact identity formulas, coverage, publication gating, etc.) while adding pseudo-code and Delphi-style examples. It is still a high-assurance, fail-closed, content-addressed system.

The supplied Delphi code (CanonicalJson, Identity/Factory/Provenance, Coverage V1/V2, Traceability V1/V2, CoordinatorV2, Round/Task/System Orchestration V2, SpecContentIDV2, SpecDiffV2, EngineV2, Viz, etc.) is an exploratory prototype skeleton. It captures high-level structure and some identity/canonicalization intent but diverges substantially from the Improved Edition’s normative requirements.

### High-Level Alignment
**Strengths (what matches the spirit):**
- Clear separation of concerns: Kernel owns state, Coordinator/Orchestrators drive rounds, Identity factory distinguishes Semantic / Execution / Coordinator-Assigned / Derived.
- Canonicalization unit attempts UTF-8 bytewise key ordering, rejects NaN/Infinity, and normalizes negative zero — directionally correct.
- Multi-round peer-message flow, consolidation, simple convergence detection, coverage and traceability engines, and publication-bundle construction exist.
- Identity prefixes and hashing appear in several places; provenance zones are sketched.
- Coverage and traceability are treated as first-class (even if stubbed).

**Overall verdict:**  
This is a useful early prototype / proof-of-concept for a LEVEL_1-ish exploration in Delphi. It is **not** a conformant implementation of the Improved Edition (nor of the original GSDA/3.1). Most deterministic guarantees, exact algorithms, fail-closed rules, SemanticProjection discipline, package integrity, and self-conformance requirements are missing, approximated, or stubbed with dummy data.

### Section-by-Section Assessment

**Part 1 – Foundations, Architecture, Normativity, Priority, Scope, Trust**
- Trust zones and “kernel is the only authority” are conceptually present.
- No evidence of the full T0→T7 flow enforcement, provenance recording on every boundary crossing, or human-decision validation before state mutation.
- Priority order and USER_INTENT_PRESERVATION are not implemented as decision criteria.
- Scope restrictions (no process spawning, no arbitrary network, pure specification) are not enforced in code.

**Part 2 – Identity Classes, Canonicalization, Semantic Projection, Identity Algorithms**
- Identity class taxonomy is present and is one of the stronger parts.
- CanonicalJson is a partial implementation: key sorting is attempted, but string escaping is minimal, full RFC 8785 profile compliance is incomplete, and there is no clear separation of `canonical_record_jcs` / `canonical_identity_object` / `canonical_file_json`.
- **Critical gap:** SemanticProjection is essentially absent. Content identities frequently incorporate execution or operational fields.
- Exact identity formulas from the Improved Edition (specific schema strings such as `"task_identity/3.1"`, exact field lists, sorted arrays, exclusion of namespace/target_language from task_id, etc.) are not followed. Many identities are constructed ad-hoc or with simplified objects.
- `spec_content_id` and `revision_id` constructions do not match the required inputs or independence rules.

**Part 3 – Task Model, Intent Extraction, Source References, Peer Model, Adapter Rules**
- Task creation exists but is simplified; `user_intent` separation from peer interpretation is not rigorously enforced.
- Intent extraction is a naïve split-on-periods stub. It does not implement HYBRID segmentation, marker/RFC-2119 boundaries, deterministic overlap resolution, byte offsets as first-class, or intent-loss evidence.
- Source-reference resolution and derivation-chain acyclicity/boundedness are missing or stubbed.
- Adapter pipeline is not present in the strict form required (RAW PRESERVE → limited salvage only → parse → canonicalize → content_id → message_id → envelope → kernel validation). The Improved Edition’s hard limits on salvage (whitespace/BOM only; no auto-close, no inventing fields, no reordering, etc.) are not enforced.
- Peer slot_index assignment by bytewise peer_id sort and stability within a run are not visible.

**Part 4 – Message Protocol, Reliability, Repair, Scoring**
- GSP/3.1 envelope validation, confidence range 1..1000, abstention-by-omission, transport-token (HMAC) binding, and impersonation detection are largely absent.
- Reliability model is simplified or missing. The Improved Edition’s FLAT vs DECAYING modes, integer alpha/beta, bounds (M), independent-observation counting, and kernel-only ReliabilityOutcome emission are not implemented.
- Repair model and ordering are heavily simplified (a few keys). The multi-key deterministic ordering, SnapshotRoundContext freezing of reliability/fairness values, quota groups, and liveness promotion rules are missing.
- Scoring/aggregation is a simple floating-point weighted average. This diverges from both the original’s exact integer rational aggregation (with A, A_rem, denom, status, 128-bit intermediates) and even the Improved Edition’s still-deterministic requirements. Self-score exclusion, criterion rubrics, and authoritative selection order are absent.

**Part 5 – Coverage, Publication, Registry, Glossary, Package**
- Coverage engines exist (V1 intent-oriented, V2 graph-oriented) but rely on stubs and dummy links (“artifact:dummy”). Critical-coverage < 1.0 blocking, uncovered offsets, and human-override naming of every uncovered critical intent_id are not fully realized.
- Publication pipeline is skeletal. Freeze → predicate evaluation → human acceptance → atomic commit is not implemented with the required immutability and revalidation guarantees. Most publication predicates (schema validity, normative-keyword linter, cross-reference linter, package hash matching, tuple-list binding, etc.) are missing.
- Registry, glossary normalization (NFC + casefold + whitespace collapse rules), and term-collision-before-replacement are absent or incomplete.
- Package structure, per-file canonicalization modes, manifest, package_hash (manifest without self-hash), frozen tuple list, and atomic commit are not present in any robust form.
- Traceability is graph-based in V2 (good direction) but linking is simulated; completeness and deterministic content_id derivation for traceability are incomplete.

### Critical Gaps and Risks
1. **Determinism surface is incomplete.** Exact identity pre-images, SemanticProjection, integer-only aggregation, SnapshotRoundContext, and canonical ordering are not enforced. Different runs or peer arrival orders can produce divergent identities or aggregates.
2. **Fail-closed behavior is weak.** Many paths use stubs or silent defaults instead of SCHEMA_FAILURE, PROTOCOL_FAILURE, GOVERNANCE_FAILURE, RESOURCE_LIMIT_REJECTED, etc.
3. **Adapter and peer-message trust boundary is porous.** The strict sanitization and envelope-immutability rules are not present.
4. **Human governance and package integrity** (the final authority and publication binding) are essentially missing.
5. **Self-conformance and testability** — the Improved Edition (and original) require golden vectors, mechanical registry coverage, and differential testing. None of this infrastructure is visible.
6. **Floating-point usage** in aggregation and coverage ratios contradicts the spirit of integer/exact semantics emphasized throughout GSDA.

### Recommendations to Close the Gap
- Prioritize a faithful identity + canonicalization + SemanticProjection layer that exactly matches the formulas and field lists in Part 2. Make every content-addressed record declare and use its projection.
- Implement the adapter pipeline and GSP/3.1 envelope validation next; reject anything outside the allowed salvage rules.
- Replace floating-point aggregation with the exact integer (or at least deterministic rational) form.
- Make intent extraction, coverage, and traceability operate on real byte offsets and real links rather than dummies; emit the required evidence kinds.
- Add SnapshotRoundContext before any ordering that depends on reliability or fairness.
- Implement the publication gate with the full predicate list, freeze, tuple-list binding, and atomic commit semantics.
- Introduce a minimal registry of error codes / evidence kinds / predicates and mechanical checks that every TESTABLE requirement has coverage.
- Keep the Improved Edition’s pseudo-code/Delphi examples as executable specifications and drive unit tests from them.

**Summary judgment:**  
The code is a reasonable architectural sketch and a useful vehicle for exploring multi-round orchestration and identity ideas in Delphi. It is not yet an implementation of the Improved Edition. The distance to conformance is still large, primarily in the deterministic identity/canonicalization surface, adapter strictness, exact arithmetic, package integrity, and fail-closed governance. Closing those gaps would turn the prototype into a credible LEVEL_1 foundation and a platform on which LEVEL_2 features could later be added.



The Delphi GSDA/3.1 codebase (`GSDA_AllCombinedUTF8.txt`) partially implements the deterministic multi-peer architecture defined in the GSDA 3.1 specification (`GSDA SPECIFICATION DEVELOPMENT AGENT version 3.1`), achieving strong alignment in canonical JSON handling, identity graph traceability, and coverage metric tracking, but omitting key adapter sanitization rules, normativity checks, and exact identity algorithms.

**Key Architectural Strengths**

* **Deterministic Traceability**: `GSDAIdentityTraceGraph.pas` models requirement-to-artifact and artifact-to-evidence links as strongly typed graph nodes, fulfilling the provenance requirements of Part 5 Section 9.


* **Offset-Aware Coverage**: `GSDACoverage.pas` captures character range offsets (`ByteStart`/`ByteEnd`) and enforces the critical coverage gating rule specified in Part 5 Section 1.


* **Canonical Serialization**: `GSDACanonicalJson.pas` enforces UTF-8 byte ordering for object keys and normalizes negative zero floats as required by Part 2 Section 2.



**Implementation Gaps & Deviations**

* **Omitted Normativity Model**: The implementation does not parse RFC 2119 normative keywords (`MUST`, `SHALL`) or verify informative text tagging (`[Informative]`), which Part 1 Section 2 marks as mandatory publication gates.


* **Generic Identity Factories**: `GSDAIdentityFactory.pas` uses generic object wrappers instead of enforcing canonical schemas for all 20 specification identities (such as `art:`, `ev:`, `dec:`, `fnd:`, and `spec:`).


* **Bypassed Adapter Pipeline**: Messages move directly from T1 to the kernel in `GSDAKernel.pas`, violating the T0 → T1 → T2 → T3 → T4 trust boundary flow defined in Part 1 Section 1 and Part 3 Section 6.



I analyzed the supplied Part 1 + Part 2 implementation against the **GSDA/3.1 specification you supplied immediately before it**.

The overall result is quite clear:

> **This is not yet a conforming implementation of GSDA/3.1. It is primarily a scaffold/prototype containing several independent partial implementations, many placeholders, and a V2 architecture that diverges materially from the specification.**

There are also **hard compile-time defects**, so the current code cannot be treated as an executable implementation yet.

This is probably the biggest architectural problem before looking at individual functions.

# 4. Canonical JSON is not compliant

`GSDACanonicalJson.pas` looks promising at first, because it tries to implement UTF-8 bytewise sorting.

That part is directionally correct.

But several critical requirements fail.

## 4.1 Duplicate keys are not rejected

The specification requires duplicate-key rejection.

You do:

```pascal
for Pair in Obj do
  Keys.Add(Pair.JsonString.Value);
```

Then sort the keys.

A duplicated key can therefore occur twice in `Keys`.

This code:

```pascal
Pair := Obj.Get(Key);
```

does not establish that the source contained exactly one occurrence.

You need to detect duplicate keys during parsing/canonicalization.

---

## 4.2 String escaping is incomplete

You explicitly say:

```pascal
// Minimal: escape quotes and backslashes; you can extend to full JSON escaping.
```

That is not acceptable for an authoritative canonicalization function.

Control characters such as:

* CR
* LF
* TAB
* backspace
* form feed

must be handled correctly.

The current implementation can produce invalid JSON.

---

## 4.3 Number handling violates deterministic numeric semantics

You convert the JSON number to:

```pascal
V: Double;
V := N.AsDouble;
```

That immediately introduces IEEE floating-point semantics into an identity layer.

That can cause:

* precision loss
* large integer corruption
* exponent normalization differences
* platform/runtime differences

The GSDA/3.1 identity layer specifically requires identity-bearing integer values to remain exact.

This implementation does not provide that guarantee.

---

## 4.4 `N.ToString` isn't a formal canonical-number implementation

This:

```pascal
Result := N.ToString;
```

is not enough to establish a canonical numeric representation.

You need explicit numeric grammar and normalization rules.

---

## 4.5 `Canonicalize(nil)` returning `"null"`

This:

```pascal
if Obj = nil then
  Exit('null');
```

is dangerous for an identity canonicalizer.

A missing mandatory value and the actual JSON value `null` are semantically different in many GSDA schemas.

The canonicalizer should not silently turn an absent object into a valid authoritative `null`.

---

## 4.6 Fallback behavior is unacceptable

```pascal
else
  Result := Obj.ToString;
```

A canonical identity encoder cannot have an unspecified fallback.

Unknown JSON node types must fail closed.

---

# 5. The kernel's canonical identity function is explicitly a placeholder

This is even more serious.

`GSDAKernel.pas` says:

```pascal

```

and implements:

```pascal
Result := Obj.ToJSON;
```

while the comment says:

```text

```

Therefore the actual kernel identity calculation is **not canonical**.

This means:

```pascal

target_context_id
```

from this kernel cannot be considered deterministic according to GSDA/3.1.

# 6. Semantic projection is absent

The specification introduced an important concept:

> every content-addressed schema explicitly declares its semantic projection.

The implementation never actually implements this.

`TSemanticIdentity.FromJson` does:

```pascal
Canon := TGSDACanonicalJson.Canonicalize(Obj);
```

and hashes the entire object.

`MakeSemantic` wraps the entire `Content`:

```pascal
Obj.AddPair('content', Content.Clone as TJSONObject);
```

There is no schema-defined projection.

Consequently, metadata or fields that should not affect semantic identity can affect the hash.

That violates a fundamental part of the identity architecture.

# 7. V2 `task_id` is not GSDA/3.1 `task_id`

This deserves separate emphasis.

The required identity is essentially:

```text
task:
SHA256(
    canonical_identity_object(
        {
            schema,
            user_prompt,
            user_intent,
            domain,
            sorted target_audience,
            sorted constraints,
            sorted requested_outputs,
            priority_profile
        }
    )
)
```

V2 computes effectively:

```text
task:
SHA256(
    canonical("content": {prompt})
)
```

It therefore does not distinguish, for example:

```text
Task A:
prompt = "Create a specification"
domain = "security"

Task B:
prompt = "Create a specification"
domain = "music"
```

Those should have different semantic identities.

Your V2 implementation can give them the same task identity.

# 8. `target_context_id` is effectively lost in V2

The V1 kernel has:

```pascal

```

and computes it.

The V2 `TTask` only has:

```pascal

Prompt
```

and no target context.

Yet target context is explicitly part of the 3.1 architecture.

Thus the actual V2 execution path discards:

```text
namespace
target_language
```

and other context associated with target interpretation.

# 9. Run identity is wrong

The specification says:

```text
run_id = run:UUID_v4
```

The implementation tries:

```pascal
MakeExecution('run', Task.TaskID)
```

This is fundamentally the wrong identity class.

A run ID must not be derived from the semantic task identity in this manner.

Two independent executions of the same task must get different run IDs.

Your intended V2 design appears to confuse:

```text
execution-deterministic
```

with:

```text
coordinator-assigned
```

which was exactly one of the major identity errors that the revised specification was designed to prevent.

# 10. Round identity is wrong

Specification:

```text
round_id = round:run_id:round_index
```

V2:

```pascal
Result := TGSDAIdentityFactory.MakeDerived(
  'round',
  RunID,
  Index
).Value;
```

That creates a hash-derived identity rather than the specified round identifier.

This also creates a second problem here:

```pascal
Result.RoundIndex :=
  StrToIntDef(RoundID.Split([':'])[1], 0);
```

If the resulting ID is:

```text

```

then `Split(':')[1]` is a hash, not an integer.

Therefore `RoundIndex` will generally become `0`.

So even the internal round bookkeeping is inconsistent with the ID generator.

# 11. Logical sequence is missing

GSDA/3.1 explicitly introduced:


as a deterministic execution-order primitive.

There is no authoritative logical sequence counter in the V2 kernel.

`TRun` does not contain one.

Messages do not contain one.

Artifacts do not contain one.

# 51. The biggest architectural lesson

The implementation is currently doing this:

```text
LLM/message JSON
      ↓
some parsing
      ↓
heuristic scoring
      ↓
dummy traceability
      ↓
hash whatever state happens to exist
      ↓
publication
```

The specification requires something much closer to:

```text
T0 external input
      ↓
T1 untrusted provider
      ↓
T2 authenticated adapter
      ↓
canonical + schema + identity validation
      ↓
T3 validated immutable input
      ↓
T4 deterministic kernel
      ↓
authoritative semantic/execution records
      ↓
evidence / provenance / traceability
      ↓
deterministic aggregation
      ↓
frozen candidate
      ↓
publication predicates
      ↓
authenticated human decision
      ↓
atomic package commit
      ↓
immutable revision lineage
```

The current implementation has fragments of both architectures, but the second one is not actually in control.

# 52. Priority order for fixing it

I would **not** continue patching all these units individually.

That risks producing another increasingly complicated collection of semi-compatible V1/V2 components.

The better approach is to establish one authoritative implementation core.

### P0 — make the system structurally coherent

First eliminate:

```text
GSDAKernel vs GSDAKernelV2
V1 publication vs V2 publication
V1 traceability vs V2 traceability
two lineage stores
two identity implementations
```

Choose one authoritative set of types and services.

```text
IdentityValidation vs Identity classes
```

```text
escaped strings
control characters
integers
large integers
negative zero
NaN
Infinity
unsupported numeric forms
arrays
nested objects
```

Nothing should calculate an identity using `Obj.ToJSON`.

Build one authoritative identity service supporting:

# 53. My assessment of the current implementation

The code should **not yet be used as the implementation baseline for GSDA/3.1**.

It is better characterized as:

> **a prototype exploration of the architecture, not a partially completed deterministic governance implementation.**

The most important thing is that the problems are not primarily "bugs in a few methods." Several central algorithms have been replaced by simplified substitutes:

```text
canonicalization       → normal JSON
semantic identity      → hash whole object
run identity           → attempted execution hash
reliability            → Double
scoring                → heuristic multiplication
coverage               → dummy/synthetic links
traceability           → dummy/synthetic graph
SpecContentID          → runtime snapshot hash
revision diff          → current vs current
human approval         → True
publication predicates  → True
package                → JSON blob
```

Those substitutions are what make the implementation non-conforming.

## Bottom line

**Do not "fix the TODOs" one by one.**

The implementation needs a **controlled rewrite around a single authoritative GSDA/3.1 kernel**, retaining useful low-level ideas such as the identity registry and trace graph but replacing the placeholder semantics.

The strongest next step is to take this exact implementation and produce a **GSDA/3.1 Implementation Gap Matrix**, mapping every normative requirement to:

```text
REQ-ID
→ implementation unit
→ implementation symbol
→ current behavior
→ required behavior
→ severity
→ exact code change
→ conformance test
```

That would turn this from a broad architectural critique into a precise implementation plan.

# Highest-priority implementation sequence

The matrix contains many rows, but they are **not independent tasks**. The dependency order matters.

## Phase 0 — stop the architectural drift

These need to happen first:


The project must have **one kernel, one identity service, one traceability engine, one coverage engine, one publication gate, and one lineage store**.

Without that, every later fix risks being implemented twice.

## Bottom-line gap classification

The implementation currently has **useful structural scaffolding**, but the core deterministic governance properties are still absent.

The most important finding from the matrix is that the gaps cluster around six foundations:

**canonicalization → identity → authoritative state → provenance → deterministic evaluation → atomic publication**

Until those six are implemented correctly, adding more peer roles, smarter consolidation, more sophisticated prompts, or more scoring logic will mostly make the prototype larger without making it conformant.

The implementation should therefore be treated as a **prototype to be refactored/rebuilt against this matrix**, rather than as a near-complete GSDA/3.1 implementation requiring incremental bug fixes.




GSDA Implementation vs Alter Spec (Copilot Edition Smart) — Deep Analysis

Implementation: GSDA_AllCombined.txt — 31 Delphi units, ~5,158 LOC
Alter Spec: GRISP_SPECIFICATION_DEVELOPMENT_AGENT_version_3.1_Copilot_Edition_Smart.txt — 5 parts, 42KB
Original Normative: GRISP_SPECIFICATION_DEVELOPMENT_AGENT_version_3.1.txt — 721 REQs
Date: 2026-09-12
0. Executive Summary

The implementation is an honest attempt at a V2 engine that partially understands GSDA ideas (trust zones, canonicalization, identity registry, trace graph), but it fails both the alter spec and the original normative spec.

    It implements UTF-8 bytewise key ordering correctly in GSDACanonicalJson.pas — that's the best part.
    It violates its own alter spec in 9 critical places: package hashing, reliability decay formula, repair ordering, scoring aggregation, coverage calculation, publication predicates, trust zone authentication, human acceptance, and registry uniqueness.
    It violates original GSDA/3.1 LEVEL_2 in 14 places, most severely: floating-point in kernel, wall-clock timestamps, locale-sensitive formatting, placeholder spec_content_id, TODO predicates always true, no resource limits, no SnapshotRoundContext, no HMAC transport token, no atomic commit.

Verdict: Current code is LEVEL_0 / demo — useful as scaffold, not publishable. Needs 3-week hardening to reach LEVEL_1, 6-week to reach LEVEL_2.
1. Alter Spec Overview — What Copilot Edition Actually Says

Copilot Edition is not an improvement, it's a simplification with examples:

Good simplifications:

    Keeps T0->T7 flow
    Keeps adapter pipeline RAW->SANITIZE->PARSE->CANONICALIZE->content_id->message_id->ENVELOPE->KERNEL VALIDATION
    Keeps confidence 1..1000 integer, abstention by omission
    Keeps derivation chain max 256, acyclicity
    Keeps glossary normalization steps (NFC, trim, casefold, whitespace->"-", etc.)

Dangerous divergences from normative 3.1:

    Package hashing: normative = pkg: + sha256(canonical_record_jcs(manifest_without_package_hash)) where manifest_without_package_hash = parse + delete key. Copilot = file_content_id = file: + sha256(canonical_file_json(bytes)) and package_hash = sha256(concatenate(file_content_ids)). Concatenation is order-dependent, not canonical, allows reordering attack, no manifest binding.
    Reliability decay: normative = FLAT and DECAYING with integer alpha/beta, keep=M-w, floor division, remainder distribution, saturation detection. Copilot = alpha_scaled = floor(alpha * w), beta_scaled = floor(beta * w), w float 0..1, no keep, no remainder, float score.
    Repair ordering: normative = 11-key ordering (blocking count DESC, unaddressed DESC, critical DESC, high DESC, aggregate ASC UNDEFINED last, reliability DESC, independent observation DESC, fairness_key ASC, target_id ASC, finding_id ASC, repairer_id ASC) with SnapshotRoundContext. Copilot = 4-key (priority_tipping DESC, logical_sequence ASC, confidence DESC, repair_id bytewise ASC) — loses criticality.
    Scoring aggregation: normative = exact integer N(r,k)=sum R*C*W*S, D(r,k)=sum R*C*W, store A,A_rem,denom,status, rational comparison with gcd reduction, 128-bit checked. Copilot = weighted average float S = sum(w_i*s_i)/sum(w_i) with Double — breaks determinism, replay.
    Coverage: normative = linked_intent_elements/total, critical coverage, byte offsets, zero-intent block. Copilot = same idea but float ratios, no zero-intent protection.

Implementation must be judged against Copilot Edition's own rules, not just normative.

3. Conformance vs Alter Spec — Section by Section
3.1 Trust Boundary Model (Alter Part 1 Sec 5, Part 3 Sec 6)

Alter says: Normal flow T0->T7, T1 output untrusted until validated, only kernel may modify authoritative state, every crossing in provenance, adapter only whitespace+BOM salvage.

Implementation:

    GSDAKernelV2.ProcessIncomingFromT1 directly parses JSON and adds to RoundMsgs without going through adapter sanitization or validated input store T3. Violates.
    GSDAPeerAdapterV2.DetermineTrustZone uses PeerID.StartsWith('t1:') — not HMAC per Alter Part 4 Sec 1 HMAC-SHA256(secret, peer_id|fingerprint|round_id). Impersonation possible. Should be PROTOCOL_FAILURE.
    No provenance recording for trust-boundary crossing.

Fix: Kernel must not have ProcessIncomingFromT1. Adapter must be sole entry, must emit ADAPTER_SANITIZED evidence, must validate HMAC, must write to T3, kernel validates T3.
3.2 Canonicalization (Alter Part 5 Sec 8, normative NORM-001..022)

Alter says: canonical_file_json, UTF-8 bytewise ordering.

Implementation GSDACanonicalJson.pas:

    ✅ CompareUtf8Bytewise via TEncoding.UTF8.GetBytes correct, matches NORM-002/003.
    ✅ SortObjectKeys with custom comparer correct.
    ❌ CanonicalizeString only escapes \ and " — misses \b \f \n \r \t and control chars U+0000..001F must be \u00XX. RFC8785 requires full escaping. Will produce invalid canonical JSON.
    ❌ CanonicalizeNumber uses TJSONNumber.AsDouble then N.ToString — introduces float. Should reject NaN/Infinity (does) but also must normalize -0 to 0 (does) and must reject floats for identity-bearing records. Using Double loses precision for large integers > 2^53.
    ❌ CanonicalizeObject checks Pair = nil for duplicate, but TJSONObject in Delphi already overwrites duplicate keys silently — duplicate detection must happen before parsing.

Fix: Implement integer-only check: if JSON number contains . or e/E then SCHEMA_FAILURE for identity records. Implement full string escaping per RFC8785 §3.2.2.
3.3 Identity Model (Alter Part 2)

Alter says: semantic deterministic, execution deterministic, coordinator assigned, derived execution. task_id = task: + sha256(canonical_identity_object({schema, user_prompt, user_intent, ...})), target_context_id includes task_id+namespace+target_language, message_id includes run_id+peer_id+payload_schema+content_id, etc.

Implementation:

    GSDAIdentityFactory.CanonicalHash does Schema + ':' + hash(Canon) where Canon = canonicalize(Obj) where Obj contains schema and content — not per spec's explicit field list. Spec requires fields user_prompt, user_intent, domain, target_audience sorted, constraints sorted, requested_outputs sorted, priority_profile — implementation just hashes Prompt string.
    GSDAKernelV2.CreateTask calls MakeSemantic('task', Prompt) where Prompt is string, not JSONObject — type mismatch, would not compile in strict mode, but in this bundle it passes string as content via implicit conversion? Actually factory expects Content: TJSONObject, but called with Prompt string — bug.
    MakeExecution adds extra field containing payload_schema and content_id from payload — spec says payload_schema + sanitized payload content_id, but should be sanitized content_id computed after canonicalization, not from payload field.

Fix: Implement exact formulas per Section 7 of normative spec, with sorted arrays using bytewise ordering.
3.4 Peer Model & Adapter (Alter Part 3 Sec 5-6)

Alter says: peer_id required, slot_index = bytewise sort peer_id, stable within run, reliability per (peer_id, activity), adapter pipeline RAW PRESERVE->SANITIZE->PARSE->CANONICALIZE->content_id->message_id->ENVELOPE->KERNEL VALIDATION, salvage limited to whitespace+BOM, no auto-close, no identifier changes, emit evidence.

Implementation:

    GSDAPeerAdapterV2 does parse, schema check starts with gsp/, confidence 1..1000, message type range check — good.
    Missing: raw response preservation, raw retrievable via content_id, envelope identity fields mutation check, BOM removal distinguishable evidence, float rounding with round-half-to-even and FLOAT_ROUNDED evidence.
    No adapter contract for float conversion.

Fix: Add raw storage, emit evidence objects.
3.5 Message Protocol (Alter Part 4 Sec 1)

Alter says: envelope fields all required, confidence 1..1000, 0 forbidden, envelope and payload confidence equal, transport token HMAC, fingerprint = sha256(transport_name|adapter_id|endpoint), case-sensitive, token verification must not affect semantic state, peer_id mismatch -> impersonation evidence, ReliabilityOutcome never peer-authored.

Implementation: No transport token verification at all. No parent_ids, no envelope vs payload confidence equality check. No impersonation evidence emission.

Fix: Implement VerifyTransportToken kernel op per KER list.
3.6 Reliability Model (Alter Part 4 Sec 2-4)

Alter says: per (peer_id, activity), FLAT and DECAYING, alpha=successes, beta=failures, decay w=0..1 float, scaled = floor(alpha*w), etc.

Implementation GSDAPeerScoringV2:

    Uses Double for reliability, trust zone weight, message type weight, provenance weight, final score = Confidence * R * TZ * MT * PV — float multiplication, violates integer exact semantics.
    GetPeerReliability returns 0.5 default — should be cold-start alpha/beta per config, not hardcoded.
    No alpha/beta integer counters, no history, no evidence, no saturation detection, no RELIABILITY_SATURATION evidence.
    ComputeProvenanceWeight uses provenance trust zone to weight — not in spec, invents weight.

Fix: Replace Double with integer alpha/beta, implement UpdateReliability with exact integer arithmetic, keep=M-w per normative, not w float. Store sample_count, independent_observation_count.
3.7 Repair Model & Ordering (Alter Part 4 Sec 5-6)

Alter says: repair record fields, must not introduce schema violations, must not weaken higher-priority, deterministic ordering by priority_tipping DESC, logical_sequence ASC, confidence DESC, repair_id bytewise ASC.

Implementation: No repair record type, no repair validation, GSDAPeerConsolidationV2 merges repairs via MergeRepairs and ApplyCritiques — not validated, no schema check, no priority_tipping. Ordering not implemented.
3.8 Scoring Model & Aggregation (Alter Part 4 Sec 7-9)

Alter says: score_value 1..1000, 0 forbidden, abstention omission, deterministic, aggregation S = sum(w_i*s_i)/sum(w_i), peers zero reliability weight zero.

Implementation: Uses float weighted average example from alter spec, but also multiplies by extra weights (trust zone, message type) not in alter spec. No abstention handling, no self-score exclusion per SCR-014, no score selection by round_index DESC, logical_sequence DESC, message_id ASC.

Normative requires: Exact integer aggregation with A,A_rem,denom,status, rational comparison with gcd. Implementation fails both.

Fix: Implement AggregateScores with integer arithmetic, checked 128-bit, store participating peer set, emit LOW_RELIABILITY_AGGREGATE when fallback.
3.9 Coverage Model (Alter Part 5 Sec 1-2)

Alter says: total_intent_elements, linked, critical, critical_coverage = linked_critical/total_critical, byte offsets for uncovered, critical <1.0 blocks publication unless overridden naming intent_ids.

Implementation GSDACoverageV2:

    Counts requirements covered by artifacts if outgoing>0, artifacts with evidence, decisions linked — not intent elements. Wrong model.
    Uses Double ratios RequirementCoverageRatio etc, not intent coverage.
    No byte offsets, no critical intent handling, no zero-intent block.
    GSDACoverage.pas (V1) does use intent elements but with Double CriticalCoverage.

Fix: Implement intent extraction per INTENT-001..009 deterministic hybrid segmentation, then coverage per CVG-001..011.
3.10 Publication Pipeline (Alter Part 5 Sec 3-4)

Alter says: freeze, compute spec_content_id, validate predicates (schema validity, identity consistency, coverage thresholds, traceability completeness, glossary normalization, registry uniqueness, no keyword leaks, no unresolved references, no protocol failures, no adapter failures, no critical findings, valid human acceptance signature), predicates independent deterministic, commit atomically, update lineage.

4. Critical Security & Determinism Bugs

    Float in kernel: Double used for scores, reliability, coverage ratios — violates NORM-007/008/012 and AGG-005. Must be integer 0..1000 with exact rational.
    Wall-clock: Now in GSDARevisionLineageV2, DateTimeToStr locale-sensitive — violates ID-182, KER-010 no locale. Must use stored created_at from replay package, excluded from semantic identities.
    Locale-sensitive sort: TList<string>.Sort default uses locale — must use UTF-8 bytewise per NORM-002.
    Human acceptance bypass: HumanAccepts returns True — violates HUM-001..018, SEC-002.

    Convergence via float epsilon: Abs(Prev.WinningScore - Curr.WinningScore) < 0.0001 — violates exact integer comparison per CNV-006.

    Resource limits: No checks for maximum_array_items, maximum_object_properties, maximum_json_depth, etc — violates RES-001..006.
