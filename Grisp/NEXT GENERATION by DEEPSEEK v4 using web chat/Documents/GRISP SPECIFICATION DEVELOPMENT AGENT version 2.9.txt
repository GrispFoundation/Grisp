GRISP SPECIFICATION DEVELOPMENT AGENT
Specification v2.9
================================================================================

Identifier:  GSDA/2.9
Status:      Proposed normative specification (closure revision)
Supersedes:  GSDA/2.8, GSDA/2.7, GSDA/2.6, GSDA/2.5, GSDA/2.4, GSDA/2.3,
             GSDA/2.2, GSDA/2.1, GSDA/1.0
Purpose:     Cooperative development, analysis, critique, repair, refinement,
             scoring, convergence, and publication of technical specifications
             using multiple untrusted LLM reasoning peers under a
             deterministic kernel.
Domain:      Pure specification development.
Non-domain:  Compilation, execution, debugging, runtime inspection, LSP,
             tree-sitter, static analysis, execution of any target program,
             OS access, external implementation tools, GRISP execution,
             arbitrary network access.
Default:     Fail-closed for structural and governance errors.

This is a closure revision of GSDA/2.8. No new architectural concepts are
introduced.

CHANGE LOG vs 2.8:
  - Failure taxonomy unified: error codes and named failures in disjoint
    namespaces (F_ prefix for named failures).
  - META bootstrap uses distinct schema meta_requirement/1.0.
  - config_id definition added to identity model.
  - Normative keyword set extended (SHALL, REQUIRED, RECOMMENDED,
    NOT RECOMMENDED, OPTIONAL) and linter aligned.
  - MIG-005 deleted (duplicate of MIG-003).
  - Package hash: manifest_without_package_hash precisely defined.
  - contribution_index: sorted by message_id bytewise.
  - Config: policy sub-schemas versioned; max_stagnant_rounds single source.
  - Aggregation: denominator stored; cross-product overflow checked.
  - Reliability bounds: proportional decay replaces hard failure.
  - Cross-repair fairness: active_peers with fallback.
  - Package export separated from kernel (exporter component).
  - Liveness promotion limited to one per round.
  - AGG-011 (all-undefined) reworded to be reachable.
  - Round phases mapped to coordinator states.
  - rev identity "lineage" precisely defined.
  - Timestamp RFC3339 strings exempt from float ban.
  - Scoring abstention vs zero enforced by SCR-013.
  - Round-less decisions allowed empty round_id.
  - Compliance levels (MVK vs FULL) introduced.
  - Self-conformance corpus extended and completed.

0. NORMATIVITY, KEYWORD SEMANTICS, AND META-REQUIREMENTS
================================================================================

GSDA distinguishes three classes of text:

  NORMATIVE REQUIREMENT
    A machine-readable Requirement record with a stable requirement_id.

  INFORMATIVE TEXT
    Explanatory prose that does not itself impose mandatory behaviour.
    Any normative keyword that appears inside informative text MUST be
    preceded by the marker [Informative] on the same paragraph.

  DATA
    Structured values such as scores, terminology, provenance, revision
    metadata.

Only NORMATIVE REQUIREMENT records are mandatory.

Keyword semantics (RFC 2119 + RFC 8174):

  MUST, SHALL, REQUIRED
      Required for conformance. Violation is a critical non-conformance.

  MUST NOT, SHALL NOT
      Forbidden for conformance. Violation is a critical non-conformance.

  SHOULD, RECOMMENDED
      Recommended. Deviation requires recorded rationale in the
      conformance file.

  SHOULD NOT, NOT RECOMMENDED
      Recommended prohibition. Deviation requires recorded rationale.

  MAY, OPTIONAL
      Optional. No conformance penalty either way.

REQ-GSDA-META-0001
Every mandatory GSDA behaviour MUST be represented as a Requirement record,
except the META-00xx family itself, which uses schema meta_requirement/1.0
as axiomatic bootstrap per REQ-GSDA-META-0011.

REQ-GSDA-META-0002
Every structured record MUST declare its schema version.

REQ-GSDA-META-0003
A record whose schema version does not match a known schema MUST be
rejected with SCHEMA_FAILURE per Section 3.

REQ-GSDA-META-0004
A GSDA-conformant published specification MUST ship with every path
listed in REQUIRED_PACKAGE_PATHS defined by REQ-GSDA-PKG-000.

REQ-GSDA-META-0005
Every structured record type MUST have an entry in the schema registry.

REQ-GSDA-META-0006
The schema language is JSON Schema Draft 2020-12. Future draft additions
require a major version bump and a migration record per REQ-GSDA-MIG-001.

REQ-GSDA-META-0007
Every schema MUST declare additionalProperties = false unless the schema
explicitly provides an extension object named x_gsda_ext.

REQ-GSDA-META-0008
An unrecognized additional property MUST cause SCHEMA_FAILURE.

REQ-GSDA-META-0009
Any normative keyword appearing outside a Requirement record MUST be
backed by a Requirement record and MUST be marked [Informative] in the
rendered document.

REQ-GSDA-META-0010
The published specification MUST be derived from
spec.requirements.json. The prose form is a rendering and MUST NOT
introduce normative content not present in the requirement set.

REQ-GSDA-META-0011
The META-00xx family uses schema "meta_requirement/1.0", which is
pre-validated and exempt from self-reference checks during bootstrap
pass 0. After pass 0, META records MUST be validated by the same JSON
Schema validator as other Requirement records. The bootstrap set is
limited to META-00xx only.

REQ-GSDA-META-0012
requirement_id MUST be unique across the entire requirement set of a
specification. A duplicated requirement_id MUST cause SCHEMA_FAILURE and
MUST prevent the specification from being accepted as a working state.

REQ-GSDA-META-0013
The specification MUST ship a linter, CheckNormativeKeywords, whose
behaviour is defined as follows:

  - It scans every prose file shipped in the package.
  - It MUST detect every occurrence of the keywords MUST, MUST NOT,
    SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, REQUIRED, RECOMMENDED,
    NOT RECOMMENDED, OPTIONAL.
  - Every detected occurrence MUST either:
      (a) appear inside a Requirement record, or
      (b) be preceded by an explicit [Informative] marker on the same
          paragraph.
  - Any occurrence that is neither MUST cause a linter failure with code
    NORMATIVE_KEYWORD_LEAK and MUST prevent publication.

REQ-GSDA-META-0014
The linter CheckNormativeKeywords MUST be executed as part of the
publication gate per Section 39.

REQ-GSDA-META-0015
The specification identifier GSDA and the family name GRISP MUST both
appear in the glossary. GRISP MUST be defined as the family; GSDA MUST
be defined as the concrete specification-development instance within
that family.

REQ-GSDA-META-0016
The keyword definitions in this Section are the authoritative keyword
set for the linter in REQ-GSDA-META-0013. Any keyword not listed in this
Section MUST NOT be treated as normative for conformance purposes.

1. PRIORITY ORDER
================================================================================

  1. USER INTENT PRESERVATION
  2. CONSISTENCY
  3. COMPLETENESS
  4. PRECISION
  5. TRACEABILITY
  6. TESTABILITY
  7. CLARITY
  8. CONCISENESS
  9. STYLE

REQ-GSDA-PRI-001
When two candidate changes conflict with respect to specification
quality, the coordinator MUST prefer the higher-priority property unless
the human explicitly decides otherwise.

REQ-GSDA-PRI-002
A lower-priority improvement MUST NOT silently weaken a higher-priority
property.

REQ-GSDA-PRI-003
Where the priority order does not distinguish two alternatives, the
coordinator MUST use the operation's separately defined deterministic
tie-breaking rule.

REQ-GSDA-PRI-004
The priority order MUST NOT be applied outside genuine quality conflicts.
It does not determine round ordering or peer scheduling.

REQ-GSDA-PRI-005
When two operations are in scope for a quality conflict, the priority
order MUST be evaluated before any operation-specific tie-breaking rule.
The tie-breaking rule is invoked only when the priority order leaves the
alternatives equal.

REQ-GSDA-PRI-006
An operation-specific tie-breaking rule that would contradict the
priority order MUST NOT be applied.

REQ-GSDA-PRI-007
Priority order MUST be documented in every Decision that resolves a
quality conflict, citing which priority tipped the choice.

================================================================================
2. SCOPE
================================================================================

In scope:
  specification creation, refinement, requirements extraction,
  requirements formalization, alternative formulation, contradiction
  detection, ambiguity detection, completeness analysis, terminology
  management, traceability, testability analysis, consistency analysis,
  cross-repair, scoring, reliability estimation, revision management,
  convergence detection, human review, publication, deterministic replay,
  and execution of GSDA's own deterministic conformance tests.

Out of scope:
  compilation, execution, debugging, or runtime testing of any target
  program or implementation artifact being specified; LSP; tree-sitter;
  static analysis of target programs; OS access; sandboxing of target
  programs; GRISP execution; arbitrary network access.

Permitted network use:
  GSDA MAY communicate with explicitly configured LLM peer providers.
  GSDA MUST NOT invoke arbitrary external implementation or execution
  tools.

Package export (see Section 40) is an OS-boundary operation and is
performed by a package exporter component outside the deterministic
kernel.

REQ-GSDA-SCOPE-001
GSDA MUST remain a pure specification-development system.

REQ-GSDA-SCOPE-002
GSDA MUST NOT require a compiler, runtime, debugger, language server,
tree-sitter, static analyzer, OS execution environment, or external
software-development tool to determine GSDA conformance.

REQ-GSDA-SCOPE-003
Execution of GSDA's own deterministic conformance tests is in scope.
Execution of any target program or implementation artifact being
specified is out of scope.

REQ-GSDA-SCOPE-004
GSDA MUST NOT invoke arbitrary external implementation or execution
tools. Only explicitly configured LLM peer providers MAY be contacted
over the network.

REQ-GSDA-SCOPE-005
Package export MUST be performed by a package exporter component. The
deterministic kernel MUST NOT perform OS-level file I/O outside its own
stores.

================================================================================
3. ERROR, EVIDENCE, AND FAILURE TAXONOMY
================================================================================

3.1 Error Record

  schema                "error/1.0"
  code                  one of the enumerated codes in 3.2
  category              SCHEMA | PROTOCOL | IDENTITY | RESOURCE
                        | GOVERNANCE | LIVENESS | PUBLICATION
  message_template      deterministic string, no peer-supplied content
  failing_id            optional identifier
  created_at            timestamp

3.2 Enumerated Error Codes

  SCHEMA_FAILURE
      schema version mismatch, additionalProperties violation, float or
      duplicate-key rejection, empty term_id after normalization,
      duplicate requirement_id, meta_requirement validation failure.

  PROTOCOL_FAILURE
      malformed peer envelope, out-of-range confidence, missing required
      fields, duplicate conflicting message_id, partially parseable
      schema-invalid message, adapter envelope mutation.

  IMPERSONATION_ATTEMPT
      transport-bound peer_id does not match the envelope peer_id.

  IDENTITY_MISMATCH
      declared artifact_id does not match recomputed artifact_id.

  CONTENT_IDENTITY_MISMATCH
      declared content_id does not match recomputed content_id.

  SOURCE_REFERENCE_UNRESOLVED
      a SourceRef.source_id does not resolve per REQ-GSDA-SRC-001, or a
      derivation_chain contains a non-resolving step_id or a cycle.

  INPUT_BOUNDS_EXCEEDED
      a value used in aggregation exceeds the configured bounds.

  RELIABILITY_BOUNDS_EXCEEDED
      an attempted reliability update is inconsistent with the decay rule
      in REQ-GSDA-REL-017.

  GOVERNANCE_FAILURE
      missing or invalid human acceptance; mutation of a PUBLISHED
      revision; unauthorized capability use; acceptance with unresolved
      blocking findings; undefined state transition.

  LIVENESS_FAILURE
      the scheduler cannot make progress for
      liveness_policy.max_stagnant_rounds consecutive rounds.

  PUBLICATION_FAILURE
      the publication gate refuses to release a revision.

  NORMATIVE_KEYWORD_LEAK
      the linter per REQ-GSDA-META-0013 detects a normative keyword
      outside a Requirement record without an [Informative] marker.

  TERM_COLLISION
      two Term records differ only by Unicode normalization applied to
      their term field.

  LINEAGE_FAILURE
      the lineage graph contains a cycle or references a missing parent.

3.3 Named Failures

Named failures are identifiers used in decision records, round records,
and evidence to describe a state. They are a distinct namespace from
error codes and MUST be prefixed with F_ when emitted.

  F_INPUT_INVALID
  F_PEER_FAILURE
  F_PROTOCOL_DEGRADED
  F_INSUFFICIENT_CANDIDATES
  F_INSUFFICIENT_PEERS
  F_UNRESOLVED_CONTRADICTION
  F_UNRESOLVED_AMBIGUITY
  F_INSUFFICIENT_COVERAGE
  F_STAGNATION
  F_HUMAN_CLARIFICATION_REQUIRED
  F_REVIEW_REJECTED
  F_PUBLICATION_BLOCKED
  F_DUPLICATE_MESSAGE_CONFLICT
  F_NO_VIABLE_ARTIFACT

3.4 Evidence Kinds

Evidence kinds are values of the evidence_kind field of an evidence
record. They are a third namespace.

  LOW_RELIABILITY_AGGREGATE
  LIVENESS_PROMOTION
  RELIABILITY_SATURATION
  FLOAT_ROUNDED
  OVERLAP_DISCARDED
  INTENT_LOSS_DETECTED
  ADAPTER_SANITIZED
  DERIVATION_CHAIN_VERIFIED

3.5 Requirements

REQ-GSDA-ERR-001
All failures MUST be emitted as an Error record conforming to error/1.0
with one of the enumerated codes in Section 3.2 and one category from
the same section. Error codes, named failures, and evidence kinds are
three disjoint namespaces.

REQ-GSDA-ERR-002
SCHEMA_FAILURE MUST be used only for the schema and canonicalization
conditions listed in Section 3.2.

REQ-GSDA-ERR-003
PROTOCOL_FAILURE MUST be used only for the protocol conditions listed in
Section 3.2.

REQ-GSDA-ERR-004
IMPERSONATION_ATTEMPT MUST be used when transport-bound peer_id does not
match the peer_id declared inside the message envelope.

REQ-GSDA-ERR-005
GOVERNANCE_FAILURE MUST be used only for the governance conditions listed
in Section 3.2.

REQ-GSDA-ERR-006
LIVENESS_FAILURE MUST be used when the scheduler cannot make progress for
liveness_policy.max_stagnant_rounds consecutive rounds.

REQ-GSDA-ERR-007
PUBLICATION_FAILURE MUST be used when any publication gate condition in
Section 39 is unmet.

REQ-GSDA-ERR-008
message_template MUST contain no embedded peer content. Peer-supplied
detail MUST be attached as separate evidence, never inside the template.

REQ-GSDA-ERR-009
Named failures in Section 3.3 MUST NOT be emitted as Error codes. Error
codes in Section 3.2 MUST NOT be emitted as named failures or evidence
kinds. The three namespaces are disjoint.

REQ-GSDA-ERR-010
Evidence kinds in Section 3.4 MUST NOT be emitted as Error codes.

REQ-GSDA-ERR-011
The error code registry, named failure registry, and evidence kind
registry MUST be versioned and shipped under
spec.schemas/registries/1.0.json.

================================================================================
4. NORMALIZATION REGISTRY
================================================================================

REQ-GSDA-NORM-001
Canonical JSON serialization MUST follow RFC 8785 (JSON Canonicalization
Scheme) with these GSDA extensions:

  - NaN, Infinity, and -Infinity MUST be rejected.
  - Duplicate object keys MUST be rejected before canonicalization.
  - Integers MUST use decimal representation without exponent and
    without leading zeros, except zero itself.
  - Negative zero MUST be normalized to zero.
  - Floating-point numbers MUST NOT appear in any identity-bearing
    record.
  - Object keys MUST be sorted by UTF-8 bytewise lexicographic order.

REQ-GSDA-NORM-001A
The following records are identity-bearing and MUST NOT contain any
floating-point JSON number, NaN, or Infinity, and MUST NOT be produced
from a source document that contained a floating-point JSON number in
any field that participates in identity:

  - content_id payload
  - artifact_id input
  - evidence_id input
  - decision_id input
  - config_id input
  - spec_content_id input
  - revision_id input
  - any record listed in a schema whose canonical form is used to
    derive one of the above

A violation MUST cause SCHEMA_FAILURE. Sanitization by the adapter MUST
NOT rescue a violation in these fields. The adapter MUST reject the
record instead.

REQ-GSDA-NORM-001B
RFC 3339 timestamps are serialized as JSON strings and are NOT JSON
numbers. A timestamp string containing a period (".") is exempt from the
float ban in NORM-001A. Identity-bearing records containing timestamp
strings MUST still be validated against NORM-010.

REQ-GSDA-NORM-002
term_id MUST be derived as:

  NFC(normalize) -> trim -> casefold (Unicode) ->
  collapse internal whitespace runs to single '-'
  -> replace remaining non [a-z0-9-] with '-'
  -> collapse consecutive '-' to one
  -> strip leading and trailing '-'
  -> lowercase

An empty term_id after normalization MUST cause SCHEMA_FAILURE.
Comparison of terms MUST be performed on term_id only. Display labels
are informative.

REQ-GSDA-NORM-003
requirement_id format is defined in REQ-GSDA-REQ-002 for GSDA itself and
in REQ-GSDA-REQ-012 for target-domain specifications.

REQ-GSDA-NORM-004
All identity-bearing canonical serialization MUST use
canonical_jcs(X) = RFC 8785 serialization of X, with the schema field of
X included as a member.

REQ-GSDA-NORM-005
A JSON document containing a float, NaN, Infinity, duplicate key, or
negative zero MUST be rejected with SCHEMA_FAILURE unless it is
expressly a non-identity-bearing document and the schema declares that
the field is float-tolerant. No v2.9 schema declares float tolerance.

REQ-GSDA-NORM-006
NFC normalization MUST be applied during term comparison only. It MUST
NOT alter the stored string or its identity-bearing canonical
representation.

REQ-GSDA-NORM-009
requirement_id for target-domain specifications is defined in
REQ-GSDA-REQ-012.

REQ-GSDA-NORM-010
Every timestamp field MUST be serialized as an RFC 3339 UTC instant with
millisecond precision and the literal suffix "Z":

  YYYY-MM-DDTHH:MM:SS.sssZ

No timezone offset other than "Z" is permitted in identity-bearing or
provenance data. The timestamp of a peer message is provenance only and
MUST NOT be included in message_id.

REQ-GSDA-NORM-011
canonical_jcs(X) MUST include the schema field of X. The schema field
value MUST be the canonical schema identifier, not the full schema
document.

================================================================================
5. IDENTITY MODEL
================================================================================

GSDA uses three identity classes. They MUST NOT be conflated.

  DETERMINISTIC IDENTITY
    Derived by a defined algorithm from declared inputs.

      task_id
      message_id
      content_id
      artifact_id
      evidence_id
      decision_id
      config_id
      spec_content_id
      revision_id

  COORDINATOR-ASSIGNED IDENTITY
    Assigned by the coordinator at runtime.

      run_id
      peer_id

  DERIVED EXECUTION IDENTITY
    Derived deterministically from coordinator-assigned identity.

      round_id

REQ-GSDA-ID-000
A deterministic identity MUST be reproducible from its declared inputs.

REQ-GSDA-ID-001
A coordinator-assigned identity MUST be stable for the life of the entity
it identifies and MUST NOT be used to derive any deterministic identity.

REQ-GSDA-ID-002
Random or time-based values MUST NOT influence deterministic identity.

--- 5.1 task_id ---

REQ-GSDA-ID-010
task_id MUST be:

  "task:" + sha256_hex(canonical_jcs({
      "schema":            "task_identity/1.0",
      "user_prompt":       <string>,
      "user_intent":       <string>,
      "domain":            <string>,
      "target_audience":   <sorted string[]>,
      "constraints":       <sorted string[]>,
      "requested_outputs": <sorted string[]>,
      "priority_profile":  <string>
  }))

namespace and target_language MUST NOT appear in task_id. namespace is
carried in the configuration record per REQ-GSDA-CFG-012.

--- 5.2 run_id ---

REQ-GSDA-ID-020
run_id MUST identify a particular execution run.

REQ-GSDA-ID-021
run_id MUST be globally unique within the coordinator's identity domain.

REQ-GSDA-ID-022
The default format is:

  run_id = "run:" + UUID_v4

REQ-GSDA-ID-023
run_id MUST NOT be used to derive content_id, spec_content_id, or
revision_id.

REQ-GSDA-ID-024
run_id MUST be preserved in replay packages.

--- 5.3 peer_id ---

REQ-GSDA-ID-030
peer_id MUST identify a configured peer slot.

REQ-GSDA-ID-031
peer_id MUST be stable across model upgrades, prompt-profile changes,
and provider-side updates, unless the human explicitly retires the slot.

REQ-GSDA-ID-032
The default format is:

  peer_id = "peer:<slot>"

where <slot> is a stable configured identifier.

REQ-GSDA-ID-033
Provider, model, and model_version MUST be recorded as peer metadata,
NOT used to derive peer_id.

REQ-GSDA-ID-034
A change of provider or model for a peer slot MUST be recorded as a
peer-profile change and MUST NOT be treated as a new peer.

REQ-GSDA-ID-035
peer_id MUST NOT be used to derive any deterministic identity.

--- 5.4 round_id ---

REQ-GSDA-ID-040
round_id MUST be derived deterministically:

  round_id = "round:" + run_id + ":" + decimal(round_index)

where round_index begins at zero and increases by one per round within
the run.

REQ-GSDA-ID-016
round_id MUST NOT depend on any wall-clock value. It is derived solely
from run_id and round_index.

--- 5.5 message_id ---

REQ-GSDA-ID-050
message_id MUST be:

  "msg:" + sha256_hex(canonical_jcs({
      "schema":          "message_identity/1.0",
      "run_id":          <run_id>,
      "peer_id":         <peer_id>,
      "payload_schema":  <payload schema identifier>,
      "content_id":      <content_id of payload>
  }))

REQ-GSDA-ID-051
Transport ordering MUST NOT determine message identity. Timestamp MUST
NOT be included in message_id.

REQ-GSDA-ID-052
A repeated message_id with identical content MUST be idempotent.

REQ-GSDA-ID-053
A repeated message_id with conflicting content MUST produce
PROTOCOL_FAILURE and MUST be rejected.

--- 5.6 content_id ---

REQ-GSDA-ID-060
content_id MUST identify semantic payload content.

REQ-GSDA-ID-061
content_id MUST be:

  "content:" + sha256_hex(canonical_jcs({
      "schema":         <payload schema identifier>,
      "payload":        <payload value>
  }))

REQ-GSDA-ID-062
content_id MUST NOT depend on provenance, author, or transport.

--- 5.7 artifact_id ---

REQ-GSDA-ID-070
artifact_id MUST identify an immutable recorded instance.

REQ-GSDA-ID-071
artifact_id MUST be:

  "art:" + sha256_hex(canonical_jcs({
      "schema":              "artifact_identity/1.0",
      "task_id":             <task_id>,
      "run_id":              <run_id>,
      "artifact_kind":       <kind>,
      "content_id":          <content_id>,
      "author_peer_id":      <peer_id>,
      "author_role":         <role>,
      "round_id":            <round_id>,
      "parent_artifact_ids": <sorted artifact_id[]>,
      "contribution_index":  <integer>
  }))

REQ-GSDA-ID-072
artifact_id MUST NOT depend on wall-clock time.

REQ-GSDA-ID-073
Two artifacts MAY have the same content_id while having different
artifact_id values.

REQ-GSDA-ID-074
contribution_index MUST be assigned as follows:

  1. Identify every artifact that shares the tuple
     (run_id, round_id, artifact_kind, author_peer_id,
      parent_artifact_ids).
  2. Sort that set by content_id in UTF-8 bytewise ascending order,
     then by message_id in UTF-8 bytewise ascending order.
  3. Assign contribution_index = 0 to the first element, 1 to the
     second, and so on.

The second sort key (message_id) ensures the assignment is reproducible
from declared inputs regardless of transport order, per REQ-GSDA-ID-051.

When only one artifact exists for the tuple, contribution_index MUST be
zero.

--- 5.8 evidence_id ---

REQ-GSDA-ID-080
evidence_id MUST be:

  "ev:" + sha256_hex(canonical_jcs({
      "schema":        "evidence_identity/1.0",
      "run_id":        <run_id>,
      "evidence_kind": <kind>,
      "subject_ids":   <sorted identifier[]>,
      "content_id":    <content_id of evidence payload>,
      "produced_by":   <peer_id or "coordinator" or "human">
  }))

--- 5.9 decision_id ---

REQ-GSDA-ID-090
decision_id MUST be:

  "dec:" + sha256_hex(canonical_jcs({
      "schema":        "decision_identity/1.0",
      "run_id":        <run_id>,
      "actor_type":    HUMAN | COORDINATOR | SYSTEM,
      "actor_id":      <identifier>,
      "round_id":      <round_id or empty when outside a round>,
      "subject_ids":   <sorted affected identifiers>,
      "content_id":    <content_id of decision payload>
  }))

A decision made outside any round (for example, an ACCEPT decision in
AWAITING_HUMAN state) MUST use the empty string for round_id.

--- 5.10 config_id ---

REQ-GSDA-ID-095
config_id MUST be:

  "cfg:" + sha256_hex(canonical_jcs({
      "schema":                 "config_identity/1.0",
      "canonical_config_object": <materialized config>
  }))

The canonical_config_object MUST include every field with default
materialized per REQ-GSDA-CFG-013, and MUST include the quorum record
content_id when a quorum is configured.

--- 5.11 spec_content_id ---

REQ-GSDA-ID-100
spec_content_id MUST identify semantic specification content, whether
proposed or accepted.

REQ-GSDA-ID-101
spec_content_id MUST be:

  "spec:" + sha256_hex(canonical_jcs({
      "schema":                      "spec_content_identity/1.0",
      "requirements_content_id":     <content_id>,
      "glossary_content_id":         <content_id>,
      "assumptions_content_id":      <content_id>,
      "open_questions_content_id":   <content_id>,
      "traceability_content_id":     <content_id>
  }))

REQ-GSDA-ID-102
spec_content_id MUST NOT include lineage, artifact_id values, peer
identity, revision history, timestamps, changelog text, review records,
or decisions.

REQ-GSDA-ID-103
Two specifications with identical requirements, glossary, assumptions,
open questions, and traceability MUST share spec_content_id even if
their histories differ.

--- 5.12 revision_id ---

REQ-GSDA-ID-110
revision_id MUST identify a revision history node.

REQ-GSDA-ID-111
revision_id MUST be GLOBAL, not run-scoped.

REQ-GSDA-ID-112
revision_id MUST be:

  "rev:" + sha256_hex(canonical_jcs({
      "schema":              "revision_identity/1.0",
      "parent_revision_ids": <sorted revision_id[]>,
      "spec_content_id":     <spec_content_id>,
      "lineage":             <revision lineage>
  }))

REQ-GSDA-ID-112A
"revision lineage" in REQ-GSDA-ID-112 is defined as the ordered list of
ancestor revision_id values reachable from the parent_revision_ids,
sorted by revision_id bytewise ascending. It is a redundant check of the
parent chain, not a copy of the artifact lineage graph.

REQ-GSDA-ID-113
Two revisions MAY share spec_content_id while having different
revision_id values.

REQ-GSDA-ID-114
revision_id MUST NOT include run_id, changelog text, timestamps, or
package_hash.

REQ-GSDA-ID-115
A run MUST reference revisions; a revision MUST NOT reference a run for
identity purposes.

7. PEER ADAPTER LAYER
================================================================================

The peer adapter layer is the only GSDA component that may perform
provider-specific parsing, sanitization, or transport handling. It is
the trust boundary between raw provider output and the kernel.

REQ-GSDA-ADP-001
The peer adapter layer MUST be authorized to sanitize raw provider
output before kernel validation. Sanitization MAY include:

  - stripping provider-added UI decorations
  - rejecting or mapping floats to integer score fields
  - normalizing line endings to LF
  - decoding HTML entities inside JSON strings

REQ-GSDA-ADP-002
Sanitization MUST be recorded in evidence. The original raw response
MUST be preserved by content_id and MUST be retrievable.

REQ-GSDA-ADP-003
The peer adapter MUST NOT modify any identity-bearing field of a peer
message after the message envelope is constructed. It may modify only
the payload content and only to the extent permitted by the message
schema for the declared payload type.

REQ-GSDA-ADP-003A
Any modification of an identity-bearing field by the adapter MUST cause
PROTOCOL_FAILURE per REQ-GSDA-ERR-001.

REQ-GSDA-ADP-004
If sanitization cannot produce a schema-valid payload, the adapter
MUST reject the message with PROTOCOL_FAILURE and MUST NOT forward
a partially sanitized message to the kernel.

REQ-GSDA-ADP-005
For non-identity-bearing numeric fields only (for example criterion
values in the range 0..1000, confidence values in the range 1..1000),
the peer adapter MAY round a floating-point value to the nearest integer
using round-half-to-even. The adapter MUST record the original value and
the rounded value as a FLOAT_ROUNDED evidence record.

The adapter MUST reject the message with PROTOCOL_FAILURE when:

  - the value is NaN or Infinity;
  - the absolute value exceeds 10^6;
  - the target field is declared identity-bearing in
    REQ-GSDA-NORM-001A.

REQ-GSDA-ADP-006
When a peer message contains a floating-point value in a field declared
identity-bearing by REQ-GSDA-NORM-001A, the adapter MUST reject the
message with SCHEMA_FAILURE and MUST NOT round the value.

REQ-GSDA-ADP-007
Every adapter sanitization MUST be recorded as an evidence record of
kind ADAPTER_SANITIZED whose content_id identifies the raw response and
whose payload identifies the sanitized fields.

REQ-GSDA-ADP-008
The adapter MUST NOT inject default values into omitted fields. A field
that is not supplied by the peer MUST remain absent in the sanitized
payload.

REQ-GSDA-CFG-003
Configuration MUST be scoped per round. Each round records its active

REQ-GSDA-CFG-004
A mid-run configuration change MUST start a new round with a new

REQ-GSDA-CFG-005

maximum_scores_per_round MUST be at most
maximum_peers * maximum_criteria.

REQ-GSDA-CFG-008

  B_effective = min(
      configured_cross_repair_budget,
      maximum_cross_repairs,
      N * C
  )

where N is the number of active peers and C the number of candidates.

REQ-GSDA-CFG-009
The default configured_cross_repair_budget MUST be 2 * max(N, C).

REQ-GSDA-CFG-010

REQ-GSDA-CFG-011

algorithm in REQ-GSDA-KER-006.

REQ-GSDA-CFG-012
The configuration record MUST contain the fields defined in the schema
above.

REQ-GSDA-CFG-013
Every value that has a default in this Section MUST be recorded in the
config record even when the default is used. The default value MUST
appear in config_id.

REQ-GSDA-CFG-014
namespace MUST NOT be used to derive task_id. It is used only to
generate requirement_ids per REQ-GSDA-REQ-012.

REQ-GSDA-CFG-015
max_stagnant_rounds MUST be defined ONLY in
liveness_policy.max_stagnant_rounds. A top-level alias MUST equal the
liveness_policy value if present; otherwise SCHEMA_FAILURE.

REQ-GSDA-CFG-016
configured_max_peers used for fairness_key MUST be >= 1. If
config.maximum_peers is 0, SCHEMA_FAILURE.

REQ-GSDA-CFG-017
maximum_criteria MUST be >= 10. When maximum_criteria < 10, SCHEMA_FAILURE.

REQ-GSDA-CFG-018
convergence_policy, stagnation_policy, liveness_policy,
reliability_policy, intent_segmentation_policy, role_assignments,
prompt_profiles, criterion_rubrics, and outcome_weights MUST each
validate against a versioned sub-schema stored in spec.schemas/.

20. CONTRADICTIONS
================================================================================

Contradiction levels:

  CANDIDATE
    Produced by the deterministic kernel or a peer.

  PROBABLE
    Independently supported by two or more peers who did not exchange
    their analyses before producing their findings.

  ESTABLISHED
    Confirmed by one of the following:

      (a) explicit human adjudication; or
      (b) a structural conflict pattern declared in the kernel pattern
          registry and matched exactly; or
      (c) identical scope (identical subject and target) with opposite
          RFC 2119 modality on the same normative predicate.

Peer agreement alone MUST NOT establish truth.

REQ-GSDA-CON-001
Heuristic contradiction detection MUST produce
CONTRADICTION_CANDIDATE.

REQ-GSDA-CON-002
An ESTABLISHED contradiction MUST block publication until resolved or
explicitly overridden by an authorized human decision.

REQ-GSDA-CON-003
The analysis supporting a contradiction finding MUST be preserved.

REQ-GSDA-CON-004
The kernel pattern registry MUST be versioned with the specification.
A pattern MUST be a pure function of the requirements under
consideration and MUST NOT depend on peer-supplied natural language.

REQ-GSDA-CON-005
When the kernel promotes a contradiction to ESTABLISHED, it MUST record
the exact pattern that matched.

22. CROSS-REPAIR SCHEDULING
================================================================================

REQ-GSDA-REP-010
The coordinator MUST bound the number of cross-repairs per round using
B_effective per REQ-GSDA-CFG-008.

REQ-GSDA-REP-011
Repair candidates MUST be generated as triples:

  (target_artifact_id, addressed_finding_id, repairer_peer_id)

REQ-GSDA-REP-012
The following MUST be pure functions of data fixed at round start:

  blocking_finding_count(t)     =
      count of findings with status OPEN and blocking = true on target t

  unaddressed_finding_count(t)  =
      count of findings on target t whose finding_id is not listed in
      any addressed_finding_ids in repairs already scheduled this round

  target_critical_count(t)      =
      count of OPEN findings on target t with severity = CRITICAL

  target_high_count(t)          =
      count of OPEN findings on target t with severity = HIGH

  target_aggregate(t)           =
      A(t) from Section 24; if A(t) is UNDEFINED, target_aggregate(t)
      is treated as the sentinel value UNDEFINED_AGGREGATE, which
      sorts last regardless of direction

  repairer_reliability(p)       =
      reliability of p in activity CROSS_REPAIRER, snapshotted at round
      start

  repairer_independent_count(p) =
      independent_observation_count of p in activity CROSS_REPAIRER,
      snapshotted at round start

REQ-GSDA-REP-013
The reliability and independent_observation_count values used for
ordering MUST be snapshotted at the start of the round and recorded in
provenance. Mid-round updates MUST NOT affect ordering.

REQ-GSDA-REP-014
Candidate triples MUST be ordered by a comparator that MUST NOT use
arithmetic negation and MUST NOT use IEEE infinity as a sentinel:

  1. blocking_finding_count(t)      descending
  2. unaddressed_finding_count(t)   descending
  3. target_critical_count(t)       descending
  4. target_high_count(t)           descending
  5. target_aggregate(t)            ascending with UNDEFINED_AGGREGATE
                                    sorting after every defined value
  6. repairer_reliability(p)        descending
  7. repairer_independent_count(p)  descending
  8. fairness_key(p, round)         ascending
  9. target_artifact_id             ascending UTF-8 bytewise
 10. addressed_finding_id           ascending UTF-8 bytewise

REQ-GSDA-REP-015
fairness_key(p, round) MUST be computed as:

  fairness_key(p, round) =
      (round_index + slot_index(p)) mod max(1, configured_max_peers)

where:

  configured_max_peers = config.maximum_peers, stable for the run
  slot_index(p)        = stable integer assigned per REQ-GSDA-PEER-005

The rotation MUST use configured_max_peers and MUST NOT use
active_peer_count. When active_peers < configured_max_peers, rotation
still covers the configured range; the active set is filtered after
rotation.

REQ-GSDA-REP-016
The first B_effective triples in the total order MUST be performed.

REQ-GSDA-REP-017
The exact ordered list of triples and the budget decision MUST be
recorded in provenance, including the snapshotted reliability values,
the snapshotted independent_observation_count values, and the
fairness_key computed for each peer in the round.

REQ-GSDA-REP-018
A repair triple whose addressed_finding_id is empty is permitted and
represents a repair targeting the whole artifact rather than a specific
finding.

REQ-GSDA-REP-019
If a finding with severity CRITICAL has remained OPEN for at least
liveness_policy.critical_promotion_rounds consecutive rounds without
being selected as an addressed_finding_id, the coordinator MUST promote
it to the top of the schedule for the next round regardless of aggregate
score. Promotion MUST be recorded as a LIVENESS_PROMOTION evidence
record. liveness_policy.critical_promotion_rounds defaults to 3.

REQ-GSDA-REP-020
liveness_policy.critical_promotion_rounds MUST default to 3 and MUST
be at least 2. At most one LIVENESS_PROMOTION MAY be recorded per round.
When multiple findings qualify, the oldest by created_at ascending, then
by finding_id bytewise ascending, MUST be promoted.

REQ-GSDA-REP-021
The exact set of triples that were performed MUST be recorded in
provenance, including the addressed_finding_id for each triple.

24. AGGREGATION
================================================================================

Rational aggregate record:

  schema                "rational_aggregate/1.0"
  A                     integer
  A_rem                 integer
  denom                 integer (>=0; 0 only when status is UNDEFINED)
  status                DEFINED | UNDEFINED

For criterion k, target artifact r, and peer i:

  S(i,r,k)   score value             integer 0..1000
  C(i,r,k)   confidence              integer 1..1000
  R(i,k)     reliability             integer 0..1000
  W(i,k)     participation weight    integer 1..100, default 100

Participation rule:
  Peer i participates for criterion k on target r if and only if
  S(i,r,k) exists per Section 23 AND C(i,r,k) >= 1.

Weighted aggregate for criterion k:

  N(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k) * S(i,r,k)

  D(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k)

  If D(r,k) > 0:
    A(r,k) = N(r,k) div D(r,k)
    A_rem(r,k) = N(r,k) mod D(r,k)
    denom(r,k) = D(r,k)
    status = DEFINED
  Else if any participating peer exists:
    A(r,k) = ( sum S ) div n
    A_rem(r,k) = ( sum S ) mod n
    denom(r,k) = n
    status = DEFINED
    and emit LOW_RELIABILITY_AGGREGATE evidence
  Else:
    A(r,k) = 0
    A_rem(r,k) = 0
    denom(r,k) = 0
    status = UNDEFINED

Overall artifact aggregate is computed as a weighted mean over defined
criteria using the same rational representation.

REQ-GSDA-AGG-001
Undefined criteria MUST NOT be silently treated as zero.

REQ-GSDA-AGG-002
Undefined criteria MUST be explicitly recorded.

REQ-GSDA-AGG-003
If all criteria are undefined, the overall artifact aggregate MUST be
UNDEFINED.

REQ-GSDA-AGG-004
The exact configured criterion weights MUST be recorded in provenance.

REQ-GSDA-AGG-005
Aggregate calculation MUST use signed 128-bit integers for all
intermediate products and sums. The implementation MUST fail closed with
INPUT_BOUNDS_EXCEEDED if any intermediate value would exceed the signed
128-bit range. N(r,k), D(r,k), and the cross-product used for rational
comparison MUST each be bounds-checked.

REQ-GSDA-AGG-006
If any intermediate value exceeds the configured input bounds, the
aggregate MUST fail closed with INPUT_BOUNDS_EXCEEDED.

REQ-GSDA-AGG-007
A(r,k), A_rem(r,k), denom(r,k), A(r), A_rem(r), denom(r), and status
MUST all be stored in the authoritative aggregate record, not only in
provenance.

REQ-GSDA-AGG-008
Artifact selection MUST compare the pair (A(r), A_rem(r), denom(r)) as a
rational using signed 128-bit cross multiplication:

  compare( A1 + A_rem1/denom1 , A2 + A_rem2/denom2 )
      as compare( (A1*denom1 + A_rem1) * denom2
              vs  (A2*denom2 + A_rem2) * denom1 )

Both sides MUST be computed in 128-bit arithmetic. Implementations MUST
NOT compare only A(r) when A_rem(r) differs.

REQ-GSDA-AGG-009
An artifact whose overall status is UNDEFINED MUST be disqualified from
selection and MUST be marked NON_VIABLE.

REQ-GSDA-AGG-010
Artifact selection MUST use a deterministic total order over viable
artifacts only:

  1.   higher aggregate score per REQ-GSDA-AGG-008
  2.   higher minimum defined criterion score
  2.5  higher sum of independent_observation_count across DISTINCT
       scoring peers for that artifact
  3.   lower disagreement spread
  4.   greater number of independent scoring peers
  5.   artifact_id bytewise ascending

REQ-GSDA-AGG-011
When no artifact is viable (every artifact has an UNDEFINED overall
aggregate), no artifact is eligible for automatic selection. The round
MUST route the decision to human review with a LOW_RELIABILITY_AGGREGATE
evidence.

REQ-GSDA-AGG-012
Signed 128-bit arithmetic MAY be implemented via native types, via
two-word Int64 arithmetic, or via an arbitrary-precision library,
provided the implementation fails closed on overflow with
INPUT_BOUNDS_EXCEEDED and never silently truncates.

REQ-GSDA-AGG-013
When a criterion's aggregate is UNDEFINED and any participating peer
exists, the aggregate MUST record LOW_RELIABILITY_AGGREGATE evidence.

REQ-GSDA-AGG-014
When denom(r,k) == 0 and n_participants > 0, the LOW_RELIABILITY_AGGREGATE
fallback MUST NOT contribute to reliability updates for the SCORING
activity unless adjudicated by a human.

  scale = maximum_reliability_evidence div (alpha + beta + s + f)
  alpha' = (alpha * scale) + s
  beta'  = (beta  * scale) + f

A RELIABILITY_SATURATION evidence record MUST be emitted with the
before and after values. Decay MUST preserve the mean to within ±1
point when possible. If even scaled values exceed the bound, the update
MUST fail with RELIABILITY_BOUNDS_EXCEEDED.

REQ-GSDA-REL-018
sample_count MUST be updated as:

  sample_count' = sample_count + s + f

where s and f are the weighted success and failure counts.

REQ-GSDA-REL-019

maximum_reliability_evidence exceeds
liveness_policy.bound_saturation_threshold, the coordinator MUST emit
a RELIABILITY_SATURATION evidence and MUST break further ties by
fairness rotation per REQ-GSDA-REP-015.

REQ-GSDA-REL-020
REL-020 is reserved.

REQ-GSDA-REL-021
independent_observation_count MUST be used as a secondary ranking
signal per REQ-GSDA-AGG-010 step 2.5 and per REQ-GSDA-REL-022.

REQ-GSDA-REL-022
When two peers have equal reliability means for an activity, the
coordinator MUST prefer the peer with the higher
independent_observation_count. When those are also equal, the
coordinator MUST apply the fairness rotation per REQ-GSDA-REP-015.

REQ-GSDA-REL-023
When the count of peers that have reached maximum_reliability_evidence
exceeds config.bound_saturation_threshold, the coordinator MUST emit a
RELIABILITY_SATURATION evidence record and MUST apply the fairness
rotation per REQ-GSDA-REP-015 to break all subsequent ties.

27. RELIABILITY UPDATE
================================================================================

For an activity with prior (alpha0, beta0) and observed (s, f):

  alpha' = alpha0 + s
  beta'  = beta0  + f
  mean   = (1000 * alpha') div (alpha' + beta')

where s and f are weighted integer counts derived from the outcome
class, using outcome_weights from config:

  HUMAN_ADJUDICATION:        default weight 100
  KERNEL_STRUCTURAL:         default weight  50
  INDEPENDENT_CORROBORATION: contributes to independent_observation_count
                             only.

A single SUCCESS outcome with weight w increments s by w.
A single FAILURE outcome with weight w increments f by w.
A NEUTRAL outcome does not change s or f.
A CORROBORATED outcome increments independent_observation_count by 1.

If (alpha + beta + s + f) exceeds maximum_reliability_evidence, the
decay rule in REQ-GSDA-REL-017 MUST be applied before committing.

REQ-GSDA-REL-100
The implementation MUST declare cold_start_alpha, cold_start_beta,
maximum_reliability_evidence, and outcome_weights.

REQ-GSDA-REL-101
Reliability calculation MUST use integer arithmetic.

REQ-GSDA-REL-102
A future reliability profile MAY define conservative lower bounds.
Such a profile requires a new specification revision.

32. REVISION DIFF
================================================================================

Requirement matching is by requirement_id.
Term matching is by term_id.
Assumption matching is by assumption_id.
Question matching is by question_id.

Diff categories:

  ADDED_REQUIREMENT
  REMOVED_REQUIREMENT
  MODIFIED_REQUIREMENT
  REWORDED_REQUIREMENT
  ADDED_TERM
  REMOVED_TERM
  MODIFIED_TERM
  ADDED_QUESTION
  RESOLVED_QUESTION
  CHANGED_ASSUMPTION
  CHANGED_STATUS

Normalization for comparison is field-specific and declared by each
schema field:

  normative_text
      whitespace-insensitive: line endings normalized to LF, ASCII
      whitespace runs collapsed to a single space, leading and trailing
      ASCII whitespace trimmed.

  definition
      whitespace-insensitive, otherwise exact.

  statement
      whitespace-insensitive, otherwise exact.

  question
      whitespace-insensitive, otherwise exact.

  structured fields
      exact comparison after canonical_jcs serialization.

Case MUST remain significant for every field.

RFC 2119 keyword changes MUST be treated as MODIFIED, not REWORDED,
even if only case differs.

REQ-GSDA-DIFF-001
A field changed in one of the compared records MUST produce a recorded
change.

REQ-GSDA-DIFF-002
A requirement whose normative_text changes only by the permitted
whitespace normalization MUST be classified REWORDED. Any other
character change MUST be classified MODIFIED.

REQ-GSDA-DIFF-003
Changes to severity, status, intent_links, related_requirements,
related_terms, related_tests, testability, or untestable_reason MUST be
recorded even if normative_text is unchanged.

REQ-GSDA-DIFF-004
Status transitions MUST be recorded separately as CHANGED_STATUS.

REQ-GSDA-DIFF-005
The diff algorithm MUST be deterministic for a fixed pair of revisions.

  ACTIVE
  CONVERGED
  AWAITING_HUMAN
  ACCEPTED
  PUBLISHED
  TERMINATED

Round phases:

  UNDERSTAND
  GENERATE
  CRITIQUE
  SCORE
  AGGREGATE
  REPAIR
  ANALYZE
  REFINE
  CONVERGE

Mapping (round phase -> coordinator state):

  UNDERSTAND          -> EXTRACTING
  GENERATE            -> FORMALIZING
  CRITIQUE            -> FORMALIZING
  SCORE               -> SCORING
  AGGREGATE           -> AGGREGATING
  REPAIR              -> SCHEDULING_REPAIR then REPAIRING
  ANALYZE             -> ANALYZING
  REFINE              -> SCORING (loop)
  CONVERGE            -> AWAITING_HUMAN

Round record:

  schema                "round/1.0"
  round_id              string
  run_id                string
  index                 integer
  phase                 <one of the phases above>
  config_id             string
  inputs                string[]
  outputs               string[]
  findings              string[]
  decisions             string[]
  absent_peers          string[]
  created_at            timestamp

REQ-GSDA-CSM-001
Coordinator transitions MUST only follow declared edges:

  INIT                 -> EXTRACTING
  EXTRACTING           -> FORMALIZING
  FORMALIZING          -> SCORING
  SCORING              -> AGGREGATING
  AGGREGATING          -> SCHEDULING_REPAIR
  SCHEDULING_REPAIR    -> REPAIRING
  REPAIRING            -> ANALYZING
  ANALYZING            -> SCORING  (repeat round)
  ANALYZING            -> AWAITING_HUMAN (convergence)
  AWAITING_HUMAN       -> PUBLISHING (human ACCEPT)
  AWAITING_HUMAN       -> SCORING  (human REJECT)
  PUBLISHING           -> FAILED_CLOSED (gate fails)
  any                  -> FAILED_CLOSED (unrecoverable)

REQ-GSDA-CSM-002
An undefined transition MUST cause FAILED_CLOSED and MUST emit
GOVERNANCE_FAILURE.

REQ-GSDA-CSM-003
Deterministic replay MUST replay state transitions using stored decision
records and snapshotted reliability, not live peer scores.

REQ-GSDA-CSM-004
Run state MUST be authoritative. Round phase MUST NOT be used to infer
run state.

REQ-GSDA-CSM-005
The transition from AWAITING_HUMAN to PUBLISHING MUST be triggered by
a HUMAN Decision per Section 31, not by a round.

REQ-GSDA-CSM-006
The mapping from round phase to coordinator state MUST be as defined
above. A round whose phase does not match the current coordinator state
MUST cause GOVERNANCE_FAILURE.

37. CONVERGENCE AND STAGNATION
================================================================================

Convergence criteria:

  no blocking open questions
  no unresolved ESTABLISHED contradictions
  no blocking findings
  all critical intent elements traced
  all related_requirements references resolve
  all related_terms references resolve
  no newly introduced CRITICAL findings
  requirement coverage stable
  terminology stable
  no HIGH_DISAGREEMENT criterion above threshold

Definitions:

  requirement coverage stable
      the set of requirement_ids is identical across the last
      convergence_policy.stable_rounds rounds.

  terminology stable
      the set of term_ids and their canonical_jcs-serialized
      definitions are identical across the last
      convergence_policy.stable_rounds rounds.

  score movement
      max over all defined A(r,k) of |A(r,k)_current - A(r,k)_previous|.
      Score movement is below threshold when this maximum is strictly
      less than convergence_policy.score_stability_threshold.

  meaningful repair
      a repair whose diff per Section 32 is non-empty.

  meaningful revision
      a revision whose diff per Section 32 is non-empty.

REQ-GSDA-CNV-001
Score stability alone MUST NOT be sufficient for convergence.

REQ-GSDA-CNV-002
The number of consecutive stable rounds required for convergence MUST
be convergence_policy.stable_rounds in config.

REQ-GSDA-CNV-003
The exact convergence thresholds MUST be recorded in provenance.

REQ-GSDA-CNV-004
Stagnation MUST be evaluated over
stagnation_policy.window_rounds rounds.

REQ-GSDA-CNV-005
Stagnation means that within the configured window there is no:

  new requirement
  resolved requirement
  new finding
  resolved finding
  meaningful repair
  meaningful revision
  score movement above stagnation_policy.score_threshold

REQ-GSDA-CNV-006
On stagnation the coordinator MUST change at least one of:

  peer composition
  role assignment
  prompt strategy
  candidate-generation strategy
  analysis focus

REQ-GSDA-CNV-007
If stagnation persists beyond liveness_policy.max_stagnant_rounds, the
coordinator MUST terminate with LIVENESS_FAILURE.

REQ-GSDA-CNV-008
The coordinator MUST terminate on any of:

  human acceptance
  configured maximum rounds (config.maximum_rounds)
  convergence reached
  stagnation without available recovery
  blocking ambiguity requiring human input
  explicit cancellation

REQ-GSDA-KER-006
ExtractIntentElements MUST produce a deterministic set of IntentElements
from user_prompt and user_intent using config.intent_segmentation_policy.

Default policy for mode = HYBRID:

  1. Split text at sentence boundaries. A sentence boundary is:
     - a period, question mark, or exclamation mark followed by
       whitespace and an uppercase letter or a digit; or
     - a single newline; or
     - an explicit marker in the segment marker prefix set.

  2. Within each sentence, if an RFC 2119 keyword appears (MUST,
     MUST NOT, SHALL, SHALL NOT, SHOULD, SHOULD NOT, MAY, REQUIRED,
     RECOMMENDED), split the sentence immediately before the keyword.

  3. If the resulting fragment is shorter than
     intent_segmentation_policy.min_fragment_length, merge it with the
     following fragment in source order. If no following fragment
     exists, merge with the preceding fragment.

  4. Overlapping or nested segments MUST be deduplicated by keeping
     the longest segment at each source position. When segments overlap
     partially, the segment that starts earlier in source order takes
     precedence. Discarded segments MUST be recorded as
     OVERLAP_DISCARDED evidence with their source byte offsets.

  5. If a source fragment cannot be segmented, emit an INTENT_LOSS
     finding for that fragment and record its byte offsets as evidence
     of kind INTENT_LOSS_DETECTED.

REQ-GSDA-KER-006A
ExtractIntentElements MUST produce identical output for identical input
and identical intent_segmentation_policy. The boundary detector is a
versioned pure function recorded in the config.

REQ-GSDA-KER-007

REQ-GSDA-KER-008

================================================================================

  CREATED --[task valid]--> ACTIVE

  ACTIVE --[human review requested]--> AWAITING_HUMAN

  any --[unrecoverable failure]--> FAILED_CLOSED

REQ-GSDA-STM-005
No failure state may transition directly to ACCEPTED.

53. INFORMATIVE: WHAT GSDA DOES NOT PROMISE
================================================================================

[Informative] The following is informative. It does not affect
conformance.

[Informative] GSDA does not promise:

  objective truth in arbitrary domains
  deterministic LLM generation
  perfect specification completeness
  unanimous peer agreement
  elimination of LLM hallucination
  automatic resolution of human decisions
  score as proof
  consensus as truth
  reliability as truth

[Informative] GSDA does claim:

  deterministic coordinator behaviour
  deterministic replay of coordinator decisions
  content identity independent of provenance
  artifact identity preserving provenance and lineage
  spec_content identity independent of history
  global revision identity preserving history
  explicit uncertainty
  immutable provenance
  preservation of disagreement
  controlled cross-repair
  reproducible aggregation
  explicit human governance

[Informative] The central abstraction is:

  LLMs produce evidence.
  The coordinator produces state.
  The kernel produces deterministic facts.
  Reliability weights evidence.
  Humans resolve epistemic uncertainty.
  The revision is the governed specification.

================================================================================
54. FINAL PRINCIPLE
================================================================================

[Informative] The purpose of GSDA is not to find a single perfect LLM.

[Informative] The purpose is to construct a process in which imperfect
LLMs can repeatedly improve one another's work.

[Informative] The fundamental operation is:

  PROPOSE
  -> CRITICIZE
  -> SCORE
  -> AGGREGATE
  -> REPAIR
  -> RESCORE
  -> ANALYZE
  -> REFINE
  -> REPEAT
  -> HUMAN REVIEW
  -> PUBLISH

[Informative] The system is a cooperative specification workshop
implemented as a deterministic orchestration system, populated by
multiple untrusted LLM reasoning peers.

[Informative] No single peer is the specification.
[Informative] No single peer is the reviewer.
[Informative] No score is truth.
[Informative] No consensus is proof.

[Informative] The quality of the specification emerges from repeated
independent reasoning, criticism, cross-repair, explicit scoring,
controlled reliability, preserved provenance, and human governance.
