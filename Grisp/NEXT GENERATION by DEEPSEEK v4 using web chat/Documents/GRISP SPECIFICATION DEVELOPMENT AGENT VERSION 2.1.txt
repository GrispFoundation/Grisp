================================================================================
GRISP SPECIFICATION DEVELOPMENT AGENT
Specification v2.2
================================================================================

Identifier:  GSDA/2.2
Status:      Proposed normative specification
Supersedes:  GSDA/2.1

Purpose:
  Cooperative development, analysis, critique, repair, refinement, scoring,
  convergence, and publication of technical specifications using multiple
  untrusted LLM reasoning peers.

Domain:
  Pure specification development.

Explicit non-domain:
  Compilation, execution, debugging, runtime inspection, LSP, tree-sitter,
  static analysis, program execution, OS access, external implementation
  tools, GRISP execution.

Primary principle:
  MANY IMPERFECT REASONING SYSTEMS
  + STRUCTURED COOPERATION
  + DETERMINISTIC COORDINATION
  = PROGRESSIVELY BETTER SPECIFICATIONS

Default:
  Fail closed for structural and governance errors.

================================================================================
0. NORMATIVITY AND SCHEMA VERSIONING
================================================================================

GSDA distinguishes three classes of specification text:

  NORMATIVE REQUIREMENT
    A machine-readable Requirement record with a stable requirement_id.
  INFORMATIVE TEXT
    Explanatory prose that does not itself impose mandatory behaviour.
  DATA
    Structured values such as scores, terminology, provenance, and
    revision metadata.

Only NORMATIVE REQUIREMENT records are mandatory.

Every structured record type carries a schema version string:

  Requirement        "requirement/1.0"
  Finding            "finding/1.0"
  Score              "score/1.0"
  Candidate          "candidate/1.0"
  Critique           "critique/1.0"
  Repair             "repair/1.0"
  Term               "term/1.0"
  Assumption         "assumption/1.0"
  OpenQuestion       "open_question/1.0"
  Artifact           "artifact/1.0"
  PeerMessage        "gsp/1.0"
  Revision           "revision/1.0"
  Package            "package/1.0"

REQ-GSDA-META-0001
Every mandatory GSDA behaviour MUST be represented as a Requirement
record.

REQ-GSDA-META-0002
Every structured record MUST contain its schema version.

REQ-GSDA-META-0003
A record whose schema version does not match a known schema MUST be
rejected.

5. IDENTITY MODEL
================================================================================

This section resolves a determinism defect in prior revisions.

Five distinct identities exist. They MUST NOT be conflated.

  task_id
    Coordinator-assigned, stable for the life of a task.
    Format: "task:" + UUID.

  peer_id
    Coordinator-assigned, stable for a peer instance.
    Format: "peer:" + UUID.

  round_id
    Coordinator-assigned, one per round.
    Format: "round:" + UUID.

  artifact_id
    Content-addressed. Derived from the artifact's canonical content.
    Format: "art:" + sha256_hex(canonical_bytes).

  revision_id
    Content-addressed. Derived from the published revision's canonical
    content.
    Format: "rev:" + sha256_hex(canonical_bytes).

REQ-GSDA-ID-001
artifact_id MUST be computed as:

  artifact_id = "art:" + sha256_hex(
      canonical_utf8({
          "schema":            "artifact/1.0",
          "artifact_kind":     <kind>,
          "author_peer_id":    <peer_id>,
          "author_role":       <role>,
          "parent_artifact_ids": [<sorted list of artifact_id>],
          "content":           <canonical content of the artifact>
      })
  )

REQ-GSDA-ID-002
The artifact's created_at timestamp MUST NOT be included in the bytes
hashed to derive artifact_id.

REQ-GSDA-ID-003
Two artifacts with identical kind, author, parents, and content MUST
share an artifact_id.

REQ-GSDA-ID-004
revision_id MUST be computed per Section 27.

REQ-GSDA-ID-005
Random or time-based values MUST NOT appear inside any bytes used to
derive artifact_id or revision_id.

16. CROSS-REPAIR BUDGET
================================================================================

For N peers and C candidates, the unconstrained cross-repair matrix is
N*C repairs.

REQ-GSDA-REP-010
The coordinator MUST bound the number of cross-repairs per round using a
configured budget B.

REQ-GSDA-REP-011
The default budget is B = min(N*C, 2*max(N, C)).

REQ-GSDA-REP-012
When B < N*C, the coordinator MUST select the repairs to perform using
a deterministic rule that is recorded in provenance.

REQ-GSDA-REP-013
The deterministic rule SHOULD prioritise:

  1. repairing the current leader,
  2. repairing by the highest-reliability CROSS_REPAIRER for the current
     subject,
  3. coverage of currently un-critiqued findings.

  SCORING
  COMPLETENESS

  activity              string
  mean                  integer 0..1000
  sample_count          integer
  lower_bound           integer 0..1000
  upper_bound           integer 0..1000

REQ-GSDA-REL-001
Reliability MUST be maintained per activity.

REQ-GSDA-REL-002
A peer with no historical evidence MUST have a configured cold-start

REQ-GSDA-REL-003
Reliability MUST NOT be derived solely from popularity or selection

REQ-GSDA-REL-004
Reliability updates MUST use recorded outcomes from at least one of:

  - an explicit human decision about a specific artifact;
  - an explicit peer retraction of a specific finding;

  - the outcome of a structural kernel check on an artifact the peer

REQ-GSDA-REL-005

REQ-GSDA-REL-006
Reliability updates MUST be deterministic for a fixed evidence set.

REQ-GSDA-REL-007

REQ-GSDA-REL-008
If no objective signal is available, reliability MUST remain at its
current value. It MUST NOT drift.

REQ-GSDA-REL-009
A peer that fails a protocol check (malformed message, impersonation,
schema violation) MUST receive a small negative update to the PROTOCOL
activity only.

REQ-GSDA-REL-010
A peer that times out or is unavailable MUST receive no reliability
update for that round.

19. RELIABILITY UPDATE MODEL
================================================================================

GSDA uses a Beta posterior over a bounded success metric.

For an activity with prior (alpha0, beta0) and observed (s, f) successes
and failures:

  alpha' = alpha0 + s
  beta'  = beta0  + f
  mean   = floor(1000 * alpha' / (alpha' + beta'))
  lower_bound = the value L in 0..1000 such that
                P(Beta(alpha', beta') < L/1000) <= p_low
  upper_bound = the value U in 0..1000 such that
                P(Beta(alpha', beta') > U/1000) <= p_high

where p_low and p_high are configured thresholds, recorded in
provenance.

REQ-GSDA-REL-100
The implementation MUST declare its p_low and p_high thresholds.

REQ-GSDA-REL-101
The implementation MUST declare its prior (alpha0, beta0).

REQ-GSDA-REL-102
For activity selection purposes, the coordinator SHOULD use lower_bound
rather than mean, to prefer conservatively reliable peers.

REQ-GSDA-REL-103
The implementation MUST NOT round in a way that allows two peers with
identical evidence to receive different means.

TESTABILITY: TESTABLE

20. AGGREGATION
================================================================================

For criterion k and artifact r, and peer i:

  S(i,r,k)   score value             integer 0..1000
  C(i,r,k)   confidence              integer 1..1000
  R(i,k)     reliability (lower_bound for activity k)  integer 0..1000
  W(i,k)     participation weight    integer 1..100, default 100

Participation rule:

  Peer i participates in criterion k for artifact r if and only if
  peer i provided a score S(i,r,k) for criterion k and its confidence
  C(i,r,k) >= 1.

  If peer i did not provide S(i,r,k), or if S is explicitly marked
  absent, peer i does NOT participate in criterion k for artifact r.

  A missing confidence MUST be treated as abstention, not as zero.

Aggregate for criterion k:

  N(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k) * S(i,r,k)

  D(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k)

  If D(r,k) > 0:
    A(r,k) = N(r,k) div D(r,k)
  Otherwise:
    A(r,k) = UNDEFINED

Overall artifact aggregate:

  Let K be the set of criteria with A(r,k) != UNDEFINED.
  If K is empty:
    A(r) = UNDEFINED
  Otherwise:
    A(r) = floor(
      sum over k in K of (w(k) * A(r,k))
      /
      sum over k in K of (w(k))
    )

where w(k) is the configured criterion weight, an integer 1..100.

REQ-GSDA-AGG-001
Undefined criteria MUST NOT be silently treated as zero.

REQ-GSDA-AGG-002
Undefined criteria MUST be explicitly recorded.

REQ-GSDA-AGG-003
If all criteria are undefined, the overall artifact score MUST be
UNDEFINED.

REQ-GSDA-AGG-004
The exact configured criterion weights MUST be recorded in the
provenance of the aggregate.

REQ-GSDA-AGG-005
Aggregate score calculation MUST use integer arithmetic only.

REQ-GSDA-AGG-006
The participation rule MUST be applied identically for every criterion
and every artifact.

TESTABILITY: TESTABLE

21. VARIANCE
================================================================================

For criterion k and artifact r, the coordinator computes:

  values          sorted list of S(i,r,k) for participating peers i
  n               number of participating peers
  minimum         values[0]                      if n > 0
  maximum         values[n-1]                    if n > 0
  mean            floor(sum(values) / n)         if n > 0
  spread          maximum - minimum              if n > 0
  variance_x1000  floor( sum over v of (v - mean)^2 * 1000 / n )
                                                 if n > 0

REQ-GSDA-VAR-001
Variance MUST be reported per criterion.

REQ-GSDA-VAR-002
Abstentions MUST be counted separately and MUST NOT contribute to the
variance.

REQ-GSDA-VAR-003
A criterion whose spread exceeds a configured threshold MUST be flagged
as HIGH_DISAGREEMENT.

REQ-GSDA-VAR-004
A HIGH_DISAGREEMENT criterion MUST be eligible to trigger another
analysis round.

REQ-GSDA-VAR-005
A high-variance result MUST NOT be silently collapsed into a single
number without recording the distribution.

TESTABILITY: TESTABLE

24. CONTRADICTION ANALYSIS
================================================================================

Contradiction levels:

  CANDIDATE
    Produced by the deterministic kernel or a heuristic peer.
  PROBABLE
    Supported by peer analysis of scope and semantics.
  ESTABLISHED
    Confirmed by two or more independent peers and a human, or by an
    unambiguous definitional conflict.

REQ-GSDA-CON-001
Heuristic contradiction detection MUST produce CONTRADICTION_CANDIDATE.

REQ-GSDA-CON-002
An ESTABLISHED contradiction MUST prevent convergence.

REQ-GSDA-CON-003
The system MUST preserve the analysis supporting a contradiction
finding.

27. REVISION IDENTITY
================================================================================

The revision identity is computed over the following canonical content:

  {
    "schema":          "revision_content/1.0",
    "requirements":    [<sorted Requirement records>],
    "glossary":        [<sorted Term records>],
    "assumptions":     [<sorted Assumption records>],
    "open_questions":  [<sorted OpenQuestion records>],
    "traceability":    <trace map>,
    "lineage":         <lineage graph of artifact_ids>
  }

Sorting is by UTF-8 bytewise order of the record's identifier.

REQ-GSDA-RID-001
revision_id MUST be:

  "rev:" + sha256_hex(canonical_utf8(revision_content))

REQ-GSDA-RID-002
The revision_id field MUST NOT be included in the bytes being hashed.

REQ-GSDA-RID-003
Two revisions with different identity-bearing canonical content MUST
produce different revision_ids except in the cryptographic event of a
SHA-256 collision.

REQ-GSDA-RID-004
Timestamps, changelog text, and package_hash MUST NOT be included in
the bytes being hashed. They are metadata of the revision, not part of
its identity.

38. REVISION DIFF
================================================================================

A revision diff compares two revisions and produces:

  ADDED_REQUIREMENT
  REMOVED_REQUIREMENT
  MODIFIED_REQUIREMENT
  REWORDED_REQUIREMENT
  ADDED_TERM
  REMOVED_TERM
  MODIFIED_TERM
  ADDED_QUESTION
  RESOLVED_QUESTION
  CHANGED_ASSUMPTION

The diff algorithm compares revisions by matching requirement_id, then
term_id, then assumption_id, then question_id. For each matched pair,
the record content is compared:

  if normative_text identical: no change
  if normative_text differs only in whitespace or case: REWORDED
  otherwise: MODIFIED

REQ-GSDA-DIFF-001
A revision diff MUST preserve old and new values for every changed
normative element.

REQ-GSDA-DIFF-002
The diff algorithm MUST be deterministic for a fixed pair of revisions.

48. WHAT GSDA DOES NOT PROMISE
================================================================================

GSDA does not promise:

  objective truth in arbitrary domains
  perfect specification completeness
  unanimous peer agreement
  elimination of LLM hallucination
  automatic resolution of human decisions
  deterministic LLM outputs
  score as proof
  consensus as truth

GSDA instead promises structured cooperation, explicit uncertainty,
traceability, reproducible coordination, and preservation of
disagreement.

================================================================================
49. FINAL PRINCIPLE
================================================================================

The purpose of GSDA is not to find a single perfect LLM.

The purpose is to construct a process in which imperfect LLMs can
repeatedly improve one another's work.

The fundamental operation is:

  PROPOSE
  -> CRITICIZE
  -> REPAIR
  -> SCORE
  -> ANALYZE
  -> REFINE
  -> REPEAT

The system is a cooperative specification workshop implemented as a
deterministic orchestration system, populated by multiple untrusted LLM
reasoning peers.

No single peer is the specification.
No single peer is the reviewer.
No score is truth.
No consensus is proof.

The quality of the specification emerges from repeated independent
reasoning, criticism, cross-repair, explicit scoring, controlled
reliability, preserved provenance, and human governance.
