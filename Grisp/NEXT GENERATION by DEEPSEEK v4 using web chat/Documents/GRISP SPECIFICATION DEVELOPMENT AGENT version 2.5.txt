GRISP SPECIFICATION DEVELOPMENT AGENT
Specification v2.5
================================================================================

Identifier:  GSDA/2.5
Status:      Proposed normative specification
Supersedes:  GSDA/2.4, GSDA/2.3, GSDA/2.2, GSDA/2.1, GSDA/1.0
Purpose:     Cooperative development, analysis, critique, repair, refinement,
             scoring, convergence, and publication of technical specifications
             using multiple untrusted LLM reasoning peers under a
             deterministic kernel.
Domain:      Pure specification development.
Non-domain:  Compilation, execution, debugging, runtime inspection, LSP,
             tree-sitter, static analysis, program execution, OS access,
             external implementation tools, GRISP execution, arbitrary
             network access.
Default:     Fail-closed for structural and governance errors.

This is a closure revision. It fixes the remaining semantic contracts in
2.4 and does not introduce new features.

================================================================================
0. NORMATIVITY AND KEYWORD SEMANTICS
================================================================================

GSDA distinguishes three classes of text:

  NORMATIVE REQUIREMENT
    A machine-readable Requirement record with a stable requirement_id.

  INFORMATIVE TEXT
    Explanatory prose that does not itself impose mandatory behaviour.

  DATA
    Structured values such as scores, terminology, provenance, revision
    metadata.

Only NORMATIVE REQUIREMENT records are mandatory.

Keyword semantics:

  MUST
      Required for conformance. Violation is a critical non-conformance.

  MUST NOT
      Forbidden for conformance. Violation is a critical non-conformance.

  SHOULD
      Recommended. A conformant implementation may deviate only if it
      records the deviation and its rationale in its conformance file.

  SHOULD NOT
      Recommended prohibition. Deviation requires recorded rationale.

  MAY
      Optional. No conformance penalty either way.

REQ-GSDA-META-0001
Every mandatory GSDA behaviour MUST be represented as a Requirement record.

REQ-GSDA-META-0002
Every structured record MUST declare its schema version.

REQ-GSDA-META-0003
A record whose schema version does not match a known schema MUST be
rejected with SCHEMA_FAILURE.

REQ-GSDA-META-0004
A GSDA-conformant published specification MUST ship with its own
spec.requirements.json, spec.tests.json, spec.glossary.json, spec.trace.json,
and spec.conformance.json.

REQ-GSDA-META-0005
Every structured record type MUST have an entry in the schema registry.

REQ-GSDA-META-0006
The schema language is JSON Schema Draft 2020-12.

REQ-GSDA-META-0007
Every schema MUST declare additionalProperties = false unless the schema
explicitly provides an extension object.

REQ-GSDA-META-0008
An unrecognized additional property MUST cause SCHEMA_FAILURE.

================================================================================
2. SCOPE
================================================================================

In scope:
  specification creation, refinement, requirements extraction,
  requirements formalization, alternative formulation, contradiction
  detection, ambiguity detection, completeness analysis, terminology
  management, traceability, testability analysis, consistency analysis,
  cross-repair, scoring, reliability estimation, revision management,
  convergence detection, human review, publication, deterministic replay.

Out of scope:
  compilation, execution, debugging, runtime testing, LSP, tree-sitter,
  static analysis, OS access, sandboxing, tool execution, GRISP execution,
  arbitrary network access.

Permitted network use:
  GSDA MAY communicate with explicitly configured LLM peer providers.
  GSDA MUST NOT invoke arbitrary external implementation or execution tools.

REQ-GSDA-SCOPE-001
GSDA MUST remain a pure specification-development system.

REQ-GSDA-SCOPE-002
GSDA MUST NOT require a compiler, runtime, debugger, language server,
tree-sitter, static analyzer, OS execution environment, or external
software-development tool to determine GSDA conformance.

REQ-GSDA-SCOPE-003
Introducing an out-of-scope mechanism MUST require a specification revision.

GSDA MUST support multiple independent LLM peers.

REQ-GSDA-DSN-002

REQ-GSDA-DSN-004

REQ-GSDA-DSN-005

REQ-GSDA-DSN-006

REQ-GSDA-DSN-007

REQ-GSDA-DSN-008

REQ-GSDA-DSN-009

REQ-GSDA-DSN-010

REQ-GSDA-DSN-011

insufficient.

REQ-GSDA-DSN-012
GSDA MUST be deterministic for a fixed set of inputs, peer messages,
and configuration.

REQ-GSDA-DSN-013
Provenance MUST NOT contaminate semantic identity.

REQ-GSDA-DSN-014
Popularity MUST NOT be a reliability signal.

REQ-GSDA-DSN-015
Agreement MUST NOT be treated as success.

5. IDENTITY MODEL
================================================================================

GSDA distinguishes twelve identities. They MUST NOT be conflated.

  5.1  task_id           Identity of the described task.
  5.2  run_id            Identity of a particular execution run.
  5.3  peer_id           Identity of a configured peer slot.
  5.4  round_id          Identity of a round.
  5.5  message_id        Identity of a peer message.
  5.6  content_id        Identity of semantic payload content.
  5.7  artifact_id       Identity of an immutable recorded instance.
  5.8  evidence_id       Identity of an observation.
  5.9  decision_id       Identity of a governance decision.
  5.10 spec_content_id   Identity of semantic specification content.
  5.11 working_state_id  Identity of the current proposed specification.
  5.12 revision_id       Identity of a revision history node.

Two classes of identity exist:

  SEMANTIC IDENTITY (deterministic from declared inputs)
    task_id, content_id, spec_content_id, revision_id, working_state_id

  EXECUTION IDENTITY (coordinator-assigned; must be internally consistent)
    run_id, peer_id, round_id, message_id, artifact_id, evidence_id,
    decision_id

REQ-GSDA-ID-000
Random or time-based values MUST NOT influence semantic identity.

REQ-GSDA-ID-001
Execution identity values MUST be assigned by the coordinator and MUST be
stable for the life of the entity they identify.

--- 5.1 task_id ---

REQ-GSDA-ID-010
task_id MUST be content-derived:

  task_id = "task:" + sha256_hex(canonical_utf8({
      "schema":            "task_identity/1.0",
      "user_prompt":       <string>,
      "user_intent":       <string>,
      "domain":            <string>,
      "target_audience":   <sorted string[]>,
      "constraints":       <sorted string[]>,
      "requested_outputs": <sorted string[]>,
      "priority_profile":  <string>
  }))

--- 5.2 run_id ---

REQ-GSDA-ID-020
run_id MUST identify a particular execution run.

REQ-GSDA-ID-021
run_id MUST be globally unique within the coordinator's identity domain.

REQ-GSDA-ID-022
The default format is:

  run_id = "run:" + UUID_v4

REQ-GSDA-ID-023
run_id MUST NOT be used to derive content_id or spec_content_id.

REQ-GSDA-ID-024
run_id MUST NOT be used to derive revision_id.

--- 5.3 peer_id ---

REQ-GSDA-ID-030
peer_id MUST identify a configured peer slot.

REQ-GSDA-ID-031
peer_id MUST be stable across model upgrades, prompt-profile changes,
and provider-side updates, unless the human explicitly retires the slot.

REQ-GSDA-ID-032
The default format is:

  peer_id = "peer:<slot>"

where <slot> is a stable configured identifier.

REQ-GSDA-ID-033
Provider, model, and model_version MUST be recorded as peer metadata,
NOT used to derive peer_id.

REQ-GSDA-ID-034
A change of provider or model for a peer slot MUST be recorded as a
peer-profile change and MUST NOT be treated as a new peer.

--- 5.4 round_id ---

REQ-GSDA-ID-040
round_id MUST be:

  "round:" + run_id + ":" + decimal(round_index)

where round_index begins at zero and increases by one.

--- 5.5 message_id ---

REQ-GSDA-ID-050
message_id MUST be content-derived from the complete message envelope
excluding message_id itself.

REQ-GSDA-ID-051
Transport ordering MUST NOT determine message identity.

REQ-GSDA-ID-052
A repeated message_id with identical content MUST be idempotent.

REQ-GSDA-ID-053
A repeated message_id with conflicting content MUST produce
DUPLICATE_MESSAGE_CONFLICT and MUST be rejected.

--- 5.6 content_id ---

REQ-GSDA-ID-060
content_id MUST identify semantic payload content.

REQ-GSDA-ID-061
content_id MUST be:

  "content:" + sha256_hex(canonical_utf8({
      "payload_schema": <payload schema identifier>,
      "payload":        <payload value>
  }))

REQ-GSDA-ID-062
content_id MUST NOT depend on provenance, author, or transport.

--- 5.7 artifact_id ---

REQ-GSDA-ID-070
artifact_id MUST identify an immutable recorded instance.

REQ-GSDA-ID-071
artifact_id MUST be:

  "art:" + sha256_hex(canonical_utf8({
      "schema":              "artifact_identity/1.0",
      "task_id":             <task_id>,
      "run_id":              <run_id>,
      "artifact_kind":       <kind>,
      "content_id":          <content_id>,
      "author_peer_id":      <peer_id>,
      "author_role":         <role>,
      "round_id":            <round_id>,
      "parent_artifact_ids": <sorted artifact_id[]>,
      "contribution_index":  <integer>
  }))

REQ-GSDA-ID-072
artifact_id MUST NOT depend on wall-clock time.

REQ-GSDA-ID-073
Two artifacts MAY have the same content_id while having different
artifact_id values.

--- 5.8 evidence_id ---

REQ-GSDA-ID-080
evidence_id MUST be:

  "ev:" + sha256_hex(canonical_utf8({
      "schema":        "evidence_identity/1.0",
      "run_id":        <run_id>,
      "evidence_kind": <kind>,
      "subject_ids":   <sorted identifier[]>,
      "content_id":    <content_id of evidence payload>,
      "produced_by":   <peer_id or "coordinator" or "human">
  }))

--- 5.9 decision_id ---

REQ-GSDA-ID-090
decision_id MUST be:

  "dec:" + sha256_hex(canonical_utf8({
      "schema":        "decision_identity/1.0",
      "run_id":        <run_id>,
      "actor_type":    HUMAN | COORDINATOR | SYSTEM,
      "actor_id":      <identifier>,
      "round_id":      <round_id>,
      "subject_ids":   <sorted affected identifiers>,
      "content_id":    <content_id of decision payload>
  }))

--- 5.10 spec_content_id ---

REQ-GSDA-ID-100
spec_content_id MUST identify semantic specification content ONLY.

REQ-GSDA-ID-101
spec_content_id MUST be computed ONLY from the current accepted working
state, not from intermediate artifact collections.

REQ-GSDA-ID-102
spec_content_id MUST be:

  "spec:" + sha256_hex(canonical_utf8({
      "schema":         "spec_content_identity/1.0",
      "requirements":   <sorted Requirement records>,
      "glossary":       <sorted Term records>,
      "assumptions":    <sorted Assumption records>,
      "open_questions": <sorted OpenQuestion records>,
      "traceability":   <trace map>
  }))

REQ-GSDA-ID-103
spec_content_id MUST NOT include lineage, artifact_id values, peer
identity, revision history, timestamps, changelog text, review records,
or decisions.

REQ-GSDA-ID-104
Two specifications with identical requirements, glossary, assumptions,
open questions, and traceability MUST share spec_content_id even if
their histories differ.

--- 5.11 working_state_id ---

REQ-GSDA-ID-110
working_state_id MUST identify the current proposed specification.

REQ-GSDA-ID-111
working_state_id MUST be computed from the same fields as spec_content_id
and MUST equal spec_content_id for the same semantic state.

REQ-GSDA-ID-112
The coordinator MUST present the working state identified by
working_state_id at the human review gate.

--- 5.12 revision_id ---

REQ-GSDA-ID-120
revision_id MUST identify a revision history node.

REQ-GSDA-ID-121
revision_id MUST be GLOBAL, not run-scoped.

REQ-GSDA-ID-122
revision_id MUST be:

  "rev:" + sha256_hex(canonical_utf8({
      "schema":              "revision_identity/1.0",
      "parent_revision_ids": <sorted revision_id[]>,
      "spec_content_id":     <spec_content_id>,
      "lineage":             <lineage graph>
  }))

REQ-GSDA-ID-123
Two revisions MAY share spec_content_id while having different
revision_id values.

REQ-GSDA-ID-124
revision_id MUST NOT include run_id, changelog text, timestamps, or
package_hash.

REQ-GSDA-ID-125
A run MUST reference revisions; a revision MUST NOT reference a run
for identity purposes.

8. CANONICALIZATION
================================================================================

REQ-GSDA-CAN-001
Identity-bearing canonical serialization MUST be UTF-8 without BOM.

REQ-GSDA-CAN-002
Object keys MUST be ordered by raw UTF-8 bytewise lexicographic order.

REQ-GSDA-CAN-003
Insignificant whitespace MUST be omitted.

REQ-GSDA-CAN-004
Strings MUST preserve their exact Unicode code points. Unicode
normalization MUST NOT be performed implicitly.

REQ-GSDA-CAN-005
Integers MUST use decimal representation without leading zeroes, except
zero itself.

REQ-GSDA-CAN-006
Floating-point numbers MUST NOT occur in identity-bearing canonical data
under any circumstances.

REQ-GSDA-CAN-007
Control characters MUST use lowercase hexadecimal JSON escapes
(\u0000 .. \u001f). Quotation mark and backslash MUST be escaped.
Slash MUST NOT be escaped.

REQ-GSDA-CAN-008
Every array field MUST be declared by its schema as either ORDERED or SET.
SET arrays MUST be sorted by canonical serialization of their elements.
ORDERED arrays MUST preserve their declared semantic order.

REQ-GSDA-CAN-009
The canonicalization profile MUST be versioned.

REQ-GSDA-CAN-010
A JSON document used for identity-bearing purposes MUST NOT contain
floating-point numbers, NaN, Infinity, or duplicate keys. Any such
document MUST be rejected with SCHEMA_FAILURE.

REQ-GSDA-CAN-011
The canonical form of a record MUST be independent of the order of the
record's own fields beyond key sorting.

13. PEER MESSAGE PROTOCOL (GSP/2.0)
================================================================================

  schema                "gsp/2.0"
  message_id            content-derived
  type                  CANDIDATE | CRITIQUE | REPAIR | SCORE
                        | REQUIREMENT | TERM | QUESTION
                        | CONSOLIDATION | RELIABILITY_OUTCOME
  peer_id               string
  run_id                string
  task_id               string
  round_id              string
  parent_ids            string[]
  confidence            integer 1..1000
  payload               object (type-specific)

REQ-GSDA-PROT-001

REQ-GSDA-PROT-002
message_id MUST be computed from the envelope excluding message_id itself.

REQ-GSDA-PROT-003
The coordinator MUST reject malformed peer messages.

REQ-GSDA-PROT-004
Missing optional fields MUST be represented according to schema, not
inferred from prose.

REQ-GSDA-PROT-005
A peer MUST NOT be able to masquerade as another peer.

REQ-GSDA-PROT-006
A peer message whose peer_id does not match the transport-bound peer MUST
be rejected with IMPERSONATION_ATTEMPT.

REQ-GSDA-PROT-007
A peer message whose confidence is outside 1..1000 MUST be rejected with
PROTOCOL_FAILURE.

REQ-GSDA-PROT-008
Transport identity MUST be bound to peer_id via a coordinator-issued
token.

14. PEER DEGRADATION
================================================================================

REQ-GSDA-PER-001
A peer that fails to respond within peer_timeout_ms MUST be marked ABSENT
for the round.

REQ-GSDA-PER-002
An ABSENT peer MUST receive no reliability update for the round.

REQ-GSDA-PER-003
A malformed response MUST produce PROTOCOL_FAILURE for that peer in that
round.

REQ-GSDA-PER-004
A PROTOCOL_FAILURE affects PROTOCOL reliability only.

REQ-GSDA-PER-005
The round proceeds with remaining valid peers unless minimum_peers is
violated.

REQ-GSDA-PER-006
If minimum_peers is violated, the round MUST terminate with
INSUFFICIENT_PEERS.

REQ-GSDA-PER-007
A provider outage MUST NOT be classified as a reasoning failure.

25. AGGREGATION
================================================================================

For criterion k, target artifact r, and peer i:

  S(i,r,k)   score value             integer 0..1000
  C(i,r,k)   confidence              integer 1..1000
  R(i,k)     reliability (integer 0..1000)
  W(i,k)     participation weight    integer 1..100, default 100

Participation rule:
  Peer i participates for criterion k on target r if and only if
  S(i,r,k) exists (per Section 24) AND C(i,r,k) >= 1.

  Missing S or missing C means abstention.

  R(i,k) = 0 contributes zero weight but remains a valid participation.

Aggregate for criterion k:

  N(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k) * S(i,r,k)

  D(r,k) = sum over participating i of
             R(i,k) * C(i,r,k) * W(i,k)

  If D(r,k) > 0:
    A(r,k) = N(r,k) div D(r,k)
  Otherwise:
    A(r,k) = UNDEFINED

Overall artifact aggregate:

  Let K be the set of criteria with A(r,k) != UNDEFINED.
  If K is empty:
    A(r) = UNDEFINED
  Otherwise:
    A(r) = ( sum over k in K of w(k) * A(r,k) ) div ( sum over k in K of w(k) )

Bounded inputs (enforced by config):
  score                 <= 1000
  confidence            <= 1000
  reliability           <= 1000
  weight                <= 100
  peers                 <= maximum_peers
  scores per round      <= maximum_scores_per_round

Under these bounds the largest possible intermediate value in Int64
arithmetic is well below overflow.

REQ-GSDA-AGG-001
Undefined criteria MUST NOT be silently treated as zero.

REQ-GSDA-AGG-002
Undefined criteria MUST be explicitly recorded.

REQ-GSDA-AGG-003
If all criteria are undefined, the overall artifact aggregate MUST be
UNDEFINED.

REQ-GSDA-AGG-004
The exact configured criterion weights MUST be recorded in provenance.

REQ-GSDA-AGG-005
Aggregate calculation MUST use signed 64-bit integer arithmetic.

REQ-GSDA-AGG-006
If any intermediate value exceeds the configured input bounds, the
aggregate MUST fail closed with INPUT_BOUNDS_EXCEEDED.

REQ-GSDA-AGG-007
The remainder of each integer division MUST be recorded in provenance
for audit.

REQ-GSDA-AGG-008
Artifact selection MUST use a deterministic total order:

  1. higher aggregate score
  2. higher minimum defined criterion score
  3. lower disagreement spread
  4. greater number of independent scoring peers
  5. artifact_id bytewise ascending

28. RELIABILITY UPDATE
================================================================================

For an activity with prior (alpha0, beta0) and observed (s, f):

  alpha' = alpha0 + s
  beta'  = beta0  + f
  mean   = (1000 * alpha') div (alpha' + beta')

where s and f are weighted integer counts derived from the outcome
class, using outcome_weights from config:

  HUMAN_ADJUDICATION:        default weight 100
  KERNEL_STRUCTURAL:         default weight  50
  INDEPENDENT_CORROBORATION: default weight  20

A single SUCCESS outcome with weight w increments s by w.
A single FAILURE outcome with weight w increments f by w.
A NEUTRAL outcome does not change s or f.

REQ-GSDA-REL-100
The implementation MUST declare cold_start_alpha, cold_start_beta, and
outcome_weights.

REQ-GSDA-REL-101
Reliability calculation MUST use integer arithmetic.

REQ-GSDA-REL-102
A future reliability profile MAY define conservative lower bounds.
Such a profile requires a new specification revision.

36. DEFAULT COOPERATIVE PROCESS

  -> SCORE

  missing traceability
  human request

37. CONVERGENCE AND STAGNATION
================================================================================

Convergence criteria:

  no blocking open questions
  no unresolved ESTABLISHED contradictions
  no blocking findings
  all critical intent elements traced
  all related_requirements references resolve
  all related_terms references resolve
  no newly introduced CRITICAL findings
  requirement coverage stable
  terminology stable
  no HIGH_DISAGREEMENT criterion above threshold

REQ-GSDA-CNV-001
Score stability MAY be supporting evidence but MUST NOT be sufficient for
convergence.

REQ-GSDA-CNV-002
The number of consecutive stable rounds required for convergence MUST be
explicit configuration.

REQ-GSDA-CNV-003
The exact convergence thresholds MUST be recorded in provenance.

REQ-GSDA-CNV-004
Stagnation MUST be evaluated over a configured window of rounds.

REQ-GSDA-CNV-005
Stagnation means that within the configured window there is no:

  new requirement
  resolved requirement
  new finding
  resolved finding
  meaningful repair
  meaningful revision
  score movement above threshold

REQ-GSDA-CNV-006
On stagnation the coordinator MUST change at least one of:

  peer composition
  role assignment
  prompt strategy
  candidate-generation strategy
  analysis focus

REQ-GSDA-CNV-007
If stagnation persists, the coordinator MUST request human intervention
or terminate with STAGNATION.

REQ-GSDA-CNV-008
The coordinator MUST terminate on any of:

  human acceptance
  configured maximum rounds
  convergence reached
  stagnation without available recovery
  blocking ambiguity requiring human input
  explicit cancellation

51. WHAT GSDA DOES NOT PROMISE
================================================================================

GSDA does not promise:

  objective truth in arbitrary domains
  deterministic LLM generation
  perfect specification completeness
  unanimous peer agreement
  elimination of LLM hallucination
  automatic resolution of human decisions
  score as proof
  consensus as truth
  reliability as truth

GSDA DOES claim:

  deterministic coordinator behaviour
  deterministic replay of coordinator decisions
  content identity independent of provenance
  artifact identity preserving provenance and lineage
  spec_content identity independent of history
  working_state identity for the current proposal
  global revision identity preserving history
  explicit uncertainty
  immutable provenance
  preservation of disagreement
  controlled cross-repair
  reproducible aggregation
  explicit human governance

The central abstraction is:

  LLMs produce evidence.
  The coordinator produces state.
  The kernel produces deterministic facts.
  Reliability weights evidence.
  Humans resolve epistemic uncertainty.
  The working state is the current proposal.
  The revision is the governed specification.

================================================================================
52. FINAL PRINCIPLE
================================================================================

The purpose of GSDA is not to find a single perfect LLM.

The purpose is to construct a process in which imperfect LLMs can
repeatedly improve one another's work.

The fundamental operation is:

  PROPOSE
  -> CRITICIZE
  -> SCORE
  -> AGGREGATE
  -> REPAIR
  -> RESCORE
  -> ANALYZE
  -> REFINE
  -> REPEAT
  -> HUMAN REVIEW
  -> PUBLISH

The system is a cooperative specification workshop implemented as a
deterministic orchestration system, populated by multiple untrusted LLM
reasoning peers.

No single peer is the specification.
No single peer is the reviewer.
No score is truth.
No consensus is proof.

The quality of the specification emerges from repeated independent
reasoning, criticism, cross-repair, explicit scoring, controlled
reliability, preserved provenance, and human governance.
