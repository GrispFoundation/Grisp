**Short takeaway:**  
The **GRISP sandbox security model** is a *mathematically enforced isolation system* built from **capabilities**, **graph‑sealed regions**, and **deterministic rewrite rules**.  
It ensures that an AI agent **cannot escape**, **cannot escalate**, **cannot reinterpret paths**, and **cannot perform any operation outside its explicitly granted capability envelope**.

It is the exact opposite of DeepSeek Harness’s permissive, OS‑exposed sandbox.

---

# 🛡️ GRISP Sandbox Security Model  
The GRISP sandbox is built on three pillars:

- **Capability envelopes**  
- **Virtual filesystem graph regions**  
- **Deterministic rewrite rule enforcement**  

Together, these form a *provable* security boundary.

---

## 🧩 1. Sandbox = Sealed Graph Region  
In GRISP, the sandbox is not a directory.  
It is a **sealed region of the graph**.

Example regions:

- `/workspace`  
- `/sandbox`  
- `/tmp`  

Each region is a **G‑Block** with edges defining:

- allowed operations  
- allowed child nodes  
- allowed rewrite rules  
- allowed capabilities  

The agent cannot:

- create new regions  
- escape a region  
- traverse edges outside the region  
- reinterpret region boundaries  

This prevents:

- POSIX vs Windows path confusion  
- drive‑letter injection  
- `..` traversal  
- absolute path escapes  

Exactly the problems you saw in DeepSeek Harness.

---

## 🔐 2. Capabilities Define the Sandbox Boundary  
Capabilities are **immutable graph nodes** that define:

- allowed operations  
- allowed MIME types  
- allowed size limits  
- allowed path roots  
- allowed rewrite rules  

Example:

```
(capability
  (allows write)
  (root /workspace)
  (max-size 64kb)
  (mime text)
)
```

Capabilities cannot be:

- escalated  
- modified  
- invented  
- reinterpreted  

This prevents:

- `danger-full-access` escalation  
- `workspace-write` escalation  
- hallucinated tool calls  
- unauthorized writes  

---

## 📁 3. Canonical Path Normalization  
GRISP normalizes all paths into canonical form:

- no drive letters  
- no UNC paths  
- no backslashes  
- no mixed separators  
- no symbolic links  
- no `..`  
- no absolute roots  

Example:

User gives:  
`G:\workspace\test.txt`

Model gives:  
`/workspace/test.txt`

GRISP normalizes both to:  
`/workspace/test.txt`

If normalization escapes the capability root → **reject**.

This prevents the exact Harness bug where:

- `/sandbox/helloworld.pas` → `G:\sandbox\helloworld.pas`  
- `/workspace/test.txt` → `G:\workspace\test.txt`

GRISP simply **does not expose the OS**.

---

## 🧠 4. Rewrite Rules Enforce Security  
Rewrite rules define how operations behave.

Example:

```
(rule
  (match (write file x))
  (rewrite (update-block x)))
```

Rewrite rules enforce:

- deterministic behavior  
- capability validation  
- region isolation  
- MIME restrictions  
- size limits  
- path normalization  

If a rewrite violates any constraint → **reject**.

This prevents:

- inconsistent behavior  
- nondeterministic tool calls  
- hallucinated operations  
- sandbox bypass  

---

## 🧱 5. No OS Exposure  
DeepSeek Harness exposes:

- real filesystem  
- real drive letters  
- real permissions  
- real escalation paths  

GRISP exposes **none** of these.

The agent sees only:

- graph nodes  
- rewrite rules  
- capability envelopes  
- virtual paths  

This prevents:

- real disk writes  
- real permission escalation  
- real OS interaction  
- real path confusion  

---

## 🧪 6. Deterministic Execution  
The GRISP interpreter is deterministic:

- same input → same rewrite sequence  
- same rewrite sequence → same result  
- no race conditions  
- no nondeterministic branching  

This prevents:

- inconsistent tool behavior  
- unpredictable writes  
- random sandbox escapes  

---

## 🧨 7. Non‑obvious insight  
The GRISP sandbox is not a “security layer.”  
It is a **mathematical structure** that *cannot be escaped* because escape is not representable in the graph.

This is why GRISP is fundamentally more secure than DeepSeek Harness.
