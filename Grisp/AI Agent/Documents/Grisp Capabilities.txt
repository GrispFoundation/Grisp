**Short takeaway:**  
The **GRISP capability model** is a *mathematically strict permission system* that controls **everything an AI agent is allowed to do**.  
It replaces the messy, error‑prone permission system you saw in DeepSeek Harness with a **deterministic, graph‑verified, non‑escalatable capability envelope**.

It is the single most important part of GRISP’s security architecture.

---

# 🧱 GRISP Capability Model  
The GRISP capability model answers one question:

> **“What is the agent allowed to do, and under what exact conditions?”**

Capabilities are **first‑class G‑Blocks** in the GRISP graph.  
They are immutable, non‑escalatable, and validated by rewrite rules.

---

# 🧩 1. Capabilities are Graph Nodes (G‑Blocks)
A capability is not a permission flag.  
It is a **graph node** with edges describing allowed actions.

Example capability block:

```
(capability
  (allows write)
  (root /workspace)
  (max-size 64kb)
  (mime text)
)
```

Capabilities have:

- **type** (read, write, execute, list, delete)
- **scope** (workspace, sandbox, tmp)
- **constraints** (size, MIME, count)
- **rewrite rules** (how the capability behaves)
- **edges** (what blocks it applies to)

This makes capabilities **composable**, **inspectable**, and **provable**.

---

# 🔐 2. Capabilities are Immutable  
DeepSeek Harness fails because the model can request:

- `workspace-write`
- `danger-full-access`
- `fs_write` outside workspace

GRISP solves this by making capabilities **immutable**.

The agent cannot:

- request new capabilities  
- escalate capabilities  
- modify capabilities  
- reinterpret capabilities  
- invent capabilities  

Capabilities are created **only by the host**, never by the model.

---

# 📁 3. Capabilities Define Allowed Paths  
A capability contains a **root path**:

```
(root /workspace)
```

GRISP normalizes all paths and checks:

- Does the path stay inside `/workspace`?  
- Does normalization escape the root?  
- Does the capability allow this operation?  

If not → **reject**.

This prevents:

- POSIX vs Windows confusion  
- drive‑letter injection  
- `..` traversal  
- sandbox bypass  
- absolute path escapes  

Exactly the problems you saw in DeepSeek Harness.

---

# 🧠 4. Capabilities Define Allowed Operations  
Capabilities explicitly list allowed operations:

```
(allows write)
(allows read)
(allows list)
```

If the agent tries:

```
delete("/workspace/test.txt")
```

GRISP checks:

- Does the capability allow delete? → No  
- Reject. No escalation.

If the agent tries:

```
write("/workspace/secret.bin")
```

GRISP checks:

- Does the capability allow write? → Yes  
- Does it allow binary MIME? → No  
- Reject.

This prevents:

- hallucinated tool calls  
- unintended writes  
- unintended deletes  
- unintended reads  

---

# 🧪 5. Capabilities Define Allowed MIME Types  
Capabilities can restrict content types:

```
(mime text)
```

This prevents:

- writing binary executables  
- writing DLLs  
- writing scripts  
- writing malware  
- writing arbitrary blobs  

The model cannot bypass MIME restrictions.

---

# 📦 6. Capabilities Define Size Limits  
Capabilities can restrict file size:

```
(max-size 64kb)
```

This prevents:

- large data dumps  
- memory abuse  
- resource exhaustion  
- runaway writes  

If the model tries to write 1 MB → reject.

---

# 🧨 7. Capabilities Define Rewrite Rules  
Capabilities are enforced by rewrite rules:

```
(rule
  (match (write file x))
  (rewrite (update-block x)))
```

Rewrite rules ensure:

- deterministic behavior  
- no hallucinated operations  
- no implicit escalation  
- no ambiguous interpretation  
- no OS‑dependent behavior  

This is the mathematical backbone of GRISP security.

---

# 🧭 8. Capabilities Are Passed Explicitly  
The agent must **explicitly declare** which capability it is using:

```
(use capability write-workspace)
(write "/workspace/test.txt" "Hello")
```

If the agent tries to write without declaring a capability → reject.

If the agent declares a capability it does not have → reject.

This prevents:

- accidental writes  
- hallucinated writes  
- implicit writes  
- tool‑use confusion

This is why they cannot be bypassed.
