Below is the proposed **GRISP Implementation Methodology v1.0**, designed to sit alongside the GRISP v1.0 specification and govern how GRISP itself is implemented, reviewed, tested, repaired, and accepted.

# GRISP Implementation Methodology v1.0

**Status:** Proposed
**Version:** 1.0
**Scope:** Implementation, verification, review, repair, and acceptance of GRISP software and protocol components
**Primary Principle:** LLMs are untrusted reasoning workers. Deterministic machinery is the authority for correctness.

---

## 1. Purpose

The GRISP Implementation Methodology defines how a GRISP specification is transformed into a trustworthy implementation.

The methodology exists because implementation of a strict deterministic protocol by a single AI agent is insufficient as a correctness strategy.

An implementation agent may:

* misunderstand a requirement;
* silently infer missing information;
* simplify a required rule;
* implement only the obvious execution path;
* introduce permissive behavior;
* accidentally weaken security;
* confuse descriptive behavior with normative behavior;
* declare its own implementation correct without adequate evidence.

GRISP therefore separates:

**reasoning, implementation, review, testing, verification, and acceptance.**

No individual LLM, implementation process, code review, or subjective score is sufficient to establish correctness.

Correctness must ultimately be demonstrated through deterministic, reproducible evidence.

---

# 2. Core Principles

## 2.1 Specification is the source of truth

The implementation MUST be derived from the normative GRISP specification.

Existing code MUST NOT silently become the specification.

Where the specification and implementation disagree, the disagreement MUST be explicitly recorded and resolved.

An implementation agent MUST NOT redefine a requirement merely because an alternative implementation appears easier.

---

## 2.2 Existing implementations are evidence, not authority

An existing GRISP implementation may contain:

* useful code;
* useful architectural ideas;
* useful tests;
* historical decisions;
* bugs;
* omissions;
* unintended permissiveness.

Existing code MUST therefore be treated as an implementation candidate under review.

It MUST NOT be assumed correct merely because it compiles, passes basic tests, or was previously generated or reviewed by an LLM.

---

## 2.3 LLMs are untrusted reasoning workers

LLMs may:

* analyze specifications;
* extract requirements;
* propose architectures;
* write code;
* generate tests;
* inspect code;
* identify defects;
* suggest repairs;
* produce adversarial cases;
* explain failures.

LLMs MUST NOT be the final authority for:

* protocol validity;
* artifact identity;
* evidence validity;
* policy authorization;
* state-transition validity;
* test success;
* compilation success;
* final artifact correctness;
* commit eligibility.

An LLM may recommend:

**ACCEPT**

but only deterministic acceptance machinery may authorize acceptance.

---

## 2.4 Multiple LLMs increase coverage, not truth

Independent LLM workers SHOULD be used when practical.

They MUST NOT be treated as a voting system.

Three LLMs agreeing on an incorrect implementation does not make it correct.

Disagreement is useful because it exposes uncertainty and review surface.

Agreement is useful only as additional evidence.

The ultimate authority remains deterministic verification.

---

## 2.5 Determinism is the final authority

Whenever correctness can be determined mechanically, it MUST be determined mechanically.

Examples include:

* parsing;
* canonicalization;
* hashing;
* schema validation;
* path validation;
* state transitions;
* capability checks;
* compilation;
* execution results;
* test results;
* evidence relationships;
* artifact identity;
* final verification.

Subjective LLM judgments MAY be used for ranking, diagnosis, prioritization, or review.

They MUST NOT override objective failure.

---

## 2.6 Fail closed

When a required fact cannot be established, the implementation MUST fail closed.

Examples:

* missing required field;
* missing evidence;
* unknown capability;
* unverifiable hash;
* ambiguous artifact;
* invalid transition;
* incomplete compilation evidence;
* stale verification;
* malformed response.

The system MUST NOT repair such omissions by inference unless the GRISP specification explicitly authorizes inference.

---

## 2.7 No self-certification

An agent MUST NOT certify its own implementation solely from its own reasoning.

The implementation agent MAY run tools and tests.

The implementation agent MAY report results.

Acceptance MUST be independently determined.

---

# 3. Methodology Lifecycle

Every significant GRISP implementation SHOULD follow this lifecycle:

```text
GRISP Specification
        |
        v
Requirement Extraction
        |
        v
Specification Audit
        |
        v
Implementation Contract
        |
        v
Test Generation
        |
        v
Architecture Design
        |
        v
Independent Implementation
        |
        v
Deterministic Build
        |
        v
Static Validation
        |
        v
Independent Code Review
        |
        v
Adversarial Review
        |
        v
Conformance Testing
        |
        v
Repair Cycle
        |
        v
Full Verification
        |
        v
Acceptance Decision
        |
        v
Immutable Release / Commit
```

A failed stage MUST NOT be silently skipped.

A later successful stage MUST NOT erase evidence of an earlier failure.

---

# 4. Phase 0 — Specification Freeze

Before implementation begins, the target specification revision MUST be identified.

The implementation process MUST record:

* specification name;
* specification version;
* specification revision or content hash;
* implementation methodology version;
* implementation target;
* supported platform;
* toolchain version.

The specification MUST be treated as immutable for the duration of an implementation run.

If the specification changes, the implementation run MUST be associated with the new specification revision.

---

# 5. Phase 1 — Requirement Extraction

A requirement extractor converts the normative specification into machine-trackable requirements.

Each requirement SHOULD receive a stable identifier.

Example:

```text
REQ-PARSER-007
Requirement:
  A parser MUST reject an artifact when filename information
  required by the schema is absent.

Severity:
  CRITICAL

Failure:
  PARSE_ERROR
```

Requirements SHOULD include at least:

```text
RequirementId
Subsystem
NormativeText
Severity
Preconditions
ExpectedBehavior
FailureBehavior
SecurityImpact
Testability
RelatedTests
RelatedImplementation
```

A requirement MUST NOT disappear merely because it is difficult to implement.

Difficult requirements are precisely the requirements that require stronger tracking.

---

# 6. Phase 2 — Specification Audit

An independent specification auditor examines the requirements before implementation.

The auditor searches for:

* ambiguity;
* contradictory requirements;
* undefined behavior;
* missing failure behavior;
* hidden assumptions;
* inconsistent terminology;
* unspecified canonical ordering;
* unspecified defaults;
* unspecified security behavior;
* requirements that cannot be deterministically tested.

The auditor MUST distinguish:

```text
SPECIFICATION DEFECT
IMPLEMENTATION DEFECT
TEST DEFECT
TOOLING DEFECT
```

These categories MUST NOT be conflated.

A defect in the specification MUST NOT be “fixed” by silently changing the implementation.

---

# 7. Phase 3 — Implementation Contract

The extracted requirements and specification audit are transformed into an implementation contract.

The contract MUST define, where applicable:

* input schema;
* output schema;
* legal states;
* legal transitions;
* deterministic ordering;
* canonical representation;
* identity/hash rules;
* failure conditions;
* policy rules;
* evidence requirements;
* security invariants;
* transaction/commit rules.

The contract SHOULD be simpler to execute and test than the complete human-readable specification.

---

# 8. Phase 4 — Test-First Construction

Critical requirements SHOULD have tests before implementation.

Every critical requirement SHOULD have at least:

```text
positive case
negative case
boundary case
adversarial case
```

For security-sensitive requirements, adversarial testing SHOULD be mandatory.

Examples:

```text
missing required field
unexpected field
duplicate field
incorrect hash
tampered content
ambiguous response
unauthorized capability
stale evidence
invalid state transition
malformed LLM response
partial output
duplicate evidence
incorrect final identity
```

Tests MUST verify rejection behavior, not merely successful behavior.

---

# 9. Phase 5 — Architecture Review

Before substantial coding begins, an architecture agent reviews the intended implementation.

The architecture review MUST evaluate:

* separation of concerns;
* trust boundaries;
* deterministic behavior;
* error handling;
* state management;
* evidence flow;
* canonicalization;
* security boundaries;
* commit semantics;
* testability;
* reproducibility.

The architecture agent SHOULD explicitly identify places where the implementation could accidentally become more permissive than the specification.

---

# 10. Phase 6 — Independent Implementation

The implementation agent implements the contract.

The implementation agent SHOULD receive:

* normative specification;
* implementation contract;
* requirement matrix;
* test suite;
* project constraints;
* existing implementation only when historical comparison is useful.

The implementation agent SHOULD NOT be instructed to “make the existing code work” as its primary objective.

The preferred objective is:

> Implement the contract.

The implementation MUST avoid:

* silent inference;
* undocumented defaults;
* automatic authorization;
* hidden state transitions;
* fake success evidence;
* placeholder implementations;
* TODO behavior in normative paths;
* compatibility behavior that weakens the specification.

---

# 11. Phase 7 — Deterministic Build

The implementation MUST be built using a controlled toolchain.

The build process MUST produce objective evidence of:

```text
source identity
toolchain identity
build result
compiler diagnostics
binary identity
```

A source that merely appears correct to an LLM MUST NOT be treated as compiled.

A claimed compiler result without actual compiler evidence MUST NOT establish COMPILED status.

---

# 12. Phase 8 — Static Validation

Static validation MUST verify all deterministic properties that can be established before execution.

Examples include:

* schema correctness;
* type correctness;
* identifier validity;
* path safety;
* canonical structure;
* dependency validity;
* illegal combinations;
* forbidden fields;
* duplicate operations;
* policy requirements.

Static validation MUST be deterministic.

---

# 13. Phase 9 — Independent Code Review

At least one independent review agent SHOULD inspect the implementation without relying on the implementation agent's explanation as authoritative.

The reviewer SHOULD receive:

* specification;
* requirement matrix;
* implementation;
* tests;
* build evidence.

The reviewer SHOULD search for:

* missing requirements;
* incorrectly implemented requirements;
* permissive behavior;
* hidden assumptions;
* incorrect error handling;
* security weaknesses;
* nondeterministic behavior;
* incorrect canonicalization;
* state-machine bypasses;
* evidence fabrication or weakening.

The reviewer MUST report concrete findings tied to requirement identifiers where possible.

---

# 14. Phase 10 — Adversarial Review

A separate adversarial agent SHOULD attempt to break the implementation.

Its objective is not to explain why the code looks reasonable.

Its objective is to find inputs or execution paths that cause the implementation to violate the contract.

Adversarial testing SHOULD specifically target:

```text
LLM hallucination
omitted fields
invented fields
malformed JSON
partial artifacts
incorrect hashes
hash substitution
identity mismatch
path traversal
duplicate operations
state bypass
stale evidence
forged evidence
unauthorized capability
TOCTOU conditions
partial commit
concurrent execution
crash recovery
timeout handling
unexpected tool output
```

The adversarial agent SHOULD assume that all upstream LLM output is hostile or mistaken.

---

# 15. Phase 11 — Specialist Review

Critical components SHOULD receive specialist review.

Recommended specialists include:

```text
Protocol Specialist
Security Specialist
Canonicalization Specialist
State-Machine Specialist
Delphi Specialist
Compiler/Toolchain Specialist
Testing Specialist
Filesystem Specialist
```

Specialists MUST review according to explicit contracts.

A specialist opinion is evidence, not final authorization.

---

# 16. Phase 12 — Conformance Testing

The implementation MUST be tested against the requirement-derived conformance suite.

The result SHOULD be represented as a requirement coverage matrix.

Example:

```text
Requirement       Code                  Test              Result
-----------------------------------------------------------------------
REQ-PARSER-001    Grisp.ArtifactParser  Parser_001        PASS
REQ-PARSER-002    Grisp.ArtifactParser  Parser_002        PASS
REQ-PARSER-003    Grisp.ArtifactParser  Parser_003        FAIL
REQ-POLICY-001    Grisp.Policy          Policy_001        PASS
REQ-COMMIT-001    Grisp.Commit          Commit_001        FAIL
```

A requirement MUST NOT be marked PASS merely because an LLM believes that the code implements it.

PASS requires objective evidence.

---

# 17. Phase 13 — Evidence Integrity

Every significant verification step SHOULD produce evidence.

Evidence SHOULD identify:

```text
EvidenceId
TaskId
ArtifactId
Operation
Tool
Status
ExitCode
Diagnostics
InputHash
OutputHash
EnvironmentId
CreatedAt
Metadata
```

Evidence MUST be bound to the artifact and operation it describes.

Evidence MUST NOT be accepted merely because its textual contents claim success.

Where practical, evidence SHOULD be independently reproducible.

---

# 18. Phase 14 — Repair

When defects are found, the implementation enters a repair cycle.

A repair MUST identify:

```text
defect
requirement
root cause
affected implementation
affected tests
repair
new verification
```

A repair agent MUST NOT simply modify code until a test happens to pass.

Repairs MUST preserve unrelated requirements.

After repair:

```text
build
static validation
conformance tests
adversarial tests
```

MUST be rerun as required by the affected scope.

Critical changes SHOULD trigger the complete verification pipeline.

---

# 19. Phase 15 — Regression Protection

Every discovered defect SHOULD become a permanent regression test.

The intended sequence is:

```text
defect found
    |
    v
reproduction test
    |
    v
repair
    |
    v
test passes
    |
    v
test retained permanently
```

A previously discovered bug MUST NOT be allowed to silently return.

---

# 20. Phase 16 — Final Verification

Before acceptance, the implementation MUST undergo final verification.

Final verification MUST establish, as applicable:

```text
correct specification revision
correct source identity
successful build
successful static validation
successful runtime verification
successful tests
successful policy verification
valid evidence
correct artifact identity
absence of blocking diagnostics
final artifact hash match
```

Verification MUST apply to the exact artifact that is going to be accepted.

A verification result for artifact A MUST NOT authorize artifact B.

---

# 21. Phase 17 — Acceptance Gate

Acceptance is a deterministic gate.

Conceptually:

```text
ACCEPT =
    valid artifact identity
    AND valid specification revision
    AND required policy passed
    AND required objective evidence exists
    AND no blocking diagnostics exist
    AND required compile evidence exists
    AND required runtime evidence exists
    AND required test evidence exists
    AND final artifact identity matches
    AND final verification succeeded
```

Failure of any mandatory condition MUST produce rejection.

Subjective scores MUST NOT override a failed hard gate.

---

# 22. Subjective LLM Scores

LLM scoring MAY be used for:

* quality ranking;
* maintainability;
* clarity;
* architecture preference;
* review prioritization;
* identifying likely weak areas;
* selecting between independently valid implementations.

LLM scores MUST NOT override:

```text
parse failure
schema failure
compile failure
test failure
policy failure
identity mismatch
missing mandatory evidence
security failure
invalid state transition
```

The methodology therefore distinguishes:

```text
CORRECTNESS
QUALITY
PREFERENCE
```

Correctness is objective where possible.

Quality is evaluative.

Preference is subjective.

These categories MUST NOT be confused.

---

# 23. Implementation Candidates

Multiple implementations MAY be generated independently.

For example:

```text
Candidate A
Candidate B
Candidate C
```

Each candidate SHOULD be independently evaluated.

The preferred candidate is the one that satisfies the deterministic acceptance gate and provides the strongest engineering properties.

A candidate MUST NOT pass solely because it received the highest LLM score.

This allows multiple LLM implementations to compete without allowing LLMs to become the authority.

---

# 24. Existing Implementation Audit

When an existing implementation is available, the methodology SHOULD run two parallel tracks.

### Track A — Fresh implementation

```text
Specification
    |
Requirements
    |
Tests
    |
Fresh implementation
    |
Verification
```

### Track B — Existing implementation audit

```text
Existing implementation
    |
Requirement mapping
    |
Independent review
    |
Adversarial testing
    |
Defect report
```

The results SHOULD be compared.

This prevents the new implementation from inheriting accidental behavior from the old implementation.

The existing implementation MAY still provide useful algorithms, data structures, compatibility information, and performance optimizations after they have been independently validated.

---

# 25. Trust Boundaries

The implementation methodology defines explicit trust levels.

```text
T0 — Untrusted LLM output
T1 — Parsed candidate artifact
T2 — Deterministically validated artifact
T3 — Compiled artifact
T4 — Runtime-verified artifact
T5 — Test-verified artifact
T6 — Policy-verified artifact
T7 — Final-verified artifact
T8 — Accepted/committable artifact
```

An artifact MUST NOT skip trust levels without satisfying the requirements represented by those levels.

In particular:

```text
LLM response != valid artifact
valid artifact != compiled artifact
compiled artifact != tested artifact
tested artifact != policy-approved artifact
policy-approved artifact != finally verified artifact
finally verified artifact != committed artifact
```

---

# 26. State-Machine Integrity

State transitions MUST be justified by validated evidence.

An event string alone SHOULD NOT be sufficient to establish a success state when the specification requires objective evidence.

For example:

```text
compile_ok
```

MUST NOT by itself establish:

```text
COMPILED
```

unless valid compilation evidence exists.

Likewise:

```text
test_ok
```

MUST NOT establish:

```text
TEST_VERIFIED
```

unless the required test evidence exists and corresponds to the exact artifact.

State transitions SHOULD therefore be modeled as:

```text
current state
+
event
+
required evidence
+
guards
=
next state
```

rather than merely:

```text
current state
+
event
=
next state
```

---

# 27. Policy Integrity

Policy MUST be authoritative and fail closed.

A requested capability is not an authorization.

The fact that an agent names a capability MUST NOT itself grant that capability.

Conceptually:

```text
requested capability
        |
        v
authorization policy
        |
   +----+----+
   |         |
 GRANTED   REJECTED
```

Policy implementation MUST therefore distinguish:

```text
requested
authorized
granted
used
```

These states MUST NOT be collapsed into a single value.

---

# 28. Parser Strictness

Protocol parsers MUST reject malformed or insufficient input according to the specification.

A parser MUST NOT silently transform an incomplete artifact into a valid artifact by invention.

Examples of forbidden implicit behavior, unless explicitly specified:

```text
missing task_id -> inferred value
missing filename -> inferred filename
missing artifact kind -> hard-coded default
missing language -> hard-coded default
missing hash -> ignored
unknown field -> silently ignored
invalid value -> substituted with default
```

Strictness is a security and correctness mechanism, not merely a formatting preference.

---

# 29. Canonicalization and Identity

Canonicalization MUST be independently specified and deterministically implemented.

The implementation MUST NOT depend on:

* incidental JSON object ordering;
* platform-specific serialization;
* locale-dependent ordering;
* undefined map iteration order;
* filesystem enumeration order;
* implementation-specific floating-point behavior.

Artifact identity MUST derive from the exact canonical domain defined by the GRISP specification.

The implementation MUST provide tests showing that:

```text
same semantic artifact
    =>
same canonical representation
    =>
same identity
```

and:

```text
different identity-relevant content
    =>
different canonical representation
    =>
different identity
```

---

# 30. Commit Integrity

Commit MUST be treated as a privileged operation.

An implementation MUST NOT commit an artifact merely because earlier stages once succeeded.

The commit process SHOULD ensure:

```text
final verification
      |
      v
prepare/stage
      |
      v
commit
      |
      v
post-commit verification
```

Where atomic multi-file commit is required, temporary or staging locations SHOULD be used to prevent partially committed artifacts.

The final committed bytes MUST correspond exactly to the verified artifact identity.

---

# 31. Concurrency and Time-of-Check Issues

Verification results can become stale.

An implementation MUST account for the possibility that:

```text
verify
  |
  | artifact changes
  v
commit
```

occurs.

Where necessary, the system MUST bind final verification to the exact artifact and transaction being committed.

Security-sensitive operations MUST NOT rely on a stale earlier observation.

---

# 32. Failure Classification

Failures SHOULD be classified explicitly.

Recommended categories:

```text
SPECIFICATION_ERROR
PARSE_ERROR
SCHEMA_ERROR
CANONICALIZATION_ERROR
STATIC_VALIDATION_ERROR
POLICY_ERROR
COMPILE_ERROR
RUNTIME_ERROR
TEST_ERROR
EVIDENCE_ERROR
STATE_ERROR
SECURITY_ERROR
COMMIT_ERROR
ENVIRONMENT_ERROR
TOOL_ERROR
```

A system SHOULD NOT collapse all failures into a generic success/failure value when the distinction affects recovery or acceptance.

---

# 33. Reproducibility

A successful implementation SHOULD be reproducible from its recorded inputs.

The methodology SHOULD record:

```text
specification identity
source identity
test identity
toolchain identity
environment identity
configuration identity
dependency identity
result identity
```

The objective is:

```text
same inputs
+
same specified environment
=
same result
```

When true reproducibility is impossible, the source of nondeterminism MUST be explicitly documented.

---

# 34. Review Independence

A review is considered independent only when the reviewer can reach its conclusion without relying exclusively on the implementation agent's own claims.

At least one review path SHOULD be conducted from:

```text
specification -> code
```

rather than:

```text
implementation agent explanation -> reviewer agreement
```

The reviewer MUST have sufficient access to the normative requirements and objective evidence.

---

# 35. Minimum Multi-Agent Configuration

A minimum serious GRISP implementation SHOULD use at least these logical roles:

```text
1. Requirements Analyst
2. Specification Auditor
3. Implementation Agent
4. Independent Code Reviewer
5. Adversarial Reviewer
6. Test/Conformance Agent
7. Deterministic Verification System
```

These roles MAY be implemented by different models or by the same model in separate isolated stages.

However, stronger independence is preferable.

For high-risk changes, specialized reviewers SHOULD be added.

---

The preferred implementation environment is:

```text
                    GRISP SPECIFICATION
                             |
                             v
                  REQUIREMENT EXTRACTION
                             |
              +--------------+--------------+
              |                             |
              v                             v
       SPECIFICATION AUDIT            TEST GENERATION
              |                             |
              +--------------+--------------+
                             |
                             v
                    IMPLEMENTATION AGENT
                             |
                             v
                    DETERMINISTIC BUILD
                             |
                             v
                  INDEPENDENT REVIEWERS
                 /      |       |       \
                /       |       |        \
         Security   Protocol  Delphi   Adversarial
                \       |       |        /
                 \      |       |       /

                  CONFORMANCE ENGINE

                         |
```

The deterministic verifier sits outside the authority of the LLM agents.

---

# 37. Repair Loop

The implementation process SHOULD behave as a controlled loop:

```text
IMPLEMENT
    |
BUILD
    |
TEST
    |
REVIEW
    |
VERIFY
    |
    +---- PASS ----> ACCEPT
    |
    +---- FAIL ----> DIAGNOSE
                         |
                         v
                       REPAIR
                         |
                         +----> BUILD
```

A repair MUST NOT directly change the acceptance decision.

It changes the artifact, which causes verification to be performed again.

---

# 38. Prohibited Methodology Patterns

The following patterns MUST NOT be considered sufficient for GRISP implementation acceptance:

### 38.1 Single-agent self-approval

```text
LLM writes code
LLM says code is correct
ACCEPT
```

### 38.2 Compile-only acceptance

```text
code compiles
therefore protocol is correct
```

### 38.3 Test-only acceptance

```text
existing tests pass
therefore implementation is complete
```

### 38.4 Majority-vote correctness

```text
LLM A: correct
LLM B: correct
LLM C: correct

therefore correct
```

### 38.5 Permissive compatibility

```text
specification requires X
implementation receives missing X
implementation silently invents X
```

### 38.6 Self-generated evidence

```text
LLM says compile succeeded
therefore COMPILED evidence exists
```

### 38.7 Partial-path acceptance

```text
parser works
therefore complete protocol works
```

### 38.8 Existing-code anchoring

```text
old implementation exists
therefore new implementation should be based on old assumptions
```

# 39. Implementation Quality Metrics

The methodology SHOULD track at least:

```text
Requirement Coverage
Conformance Pass Rate
Critical Requirement Pass Rate
Adversarial Failure Rate
Regression Count
Open Critical Defects
Evidence Completeness
Build Reproducibility
Review Findings
Repair Cycles
```

A high subjective code-quality score MUST NOT compensate for missing critical requirements.

---

# 40. Acceptance Classes

Implementations SHOULD be classified explicitly.

```text
UNVERIFIED
    No sufficient evidence.

PARTIALLY VERIFIED
    Some requirements verified.

CONFORMANT
    All mandatory requirements pass.

HARDENED
    Conformant plus adversarial/security review passes.

RELEASE CANDIDATE
    Hardened plus complete final verification.

ACCEPTED
    Release candidate satisfies the complete GRISP acceptance gate.

REJECTED
    One or more mandatory acceptance conditions failed.
```

The implementation state MUST be machine-readable.

---

# 41. Change Impact Analysis

Every implementation change SHOULD be classified by impact.

Example:

```text
LOW
documentation
nonfunctional refactor

MEDIUM
parser behavior
serialization
evidence handling

HIGH
canonicalization
identity calculation
policy
state machine
commit
security boundary
```

High-impact changes SHOULD trigger complete verification.

No change MUST be classified as low impact merely because the code diff is small.

---

# 42. Golden Tests

GRISP SHOULD maintain a collection of immutable golden cases.

Golden cases SHOULD include:

```text
valid minimal artifact
valid complex artifact
malformed artifact
ambiguous artifact
hash mismatch
artifact identity mismatch
policy rejection
compile failure
runtime failure
test failure
missing evidence
stale evidence
commit failure
malicious path
duplicate operation
invalid state transition
```

Golden cases MUST remain stable across implementation revisions unless the GRISP specification itself changes them.

---

# 43. Mutation and Adversarial Testing

For critical components, the conformance system SHOULD deliberately mutate valid artifacts.

Examples:

```text
remove required field
change one byte
change one character
change filename
change language
change hash
change artifact identity
reorder content
insert unknown field
duplicate operation
alter evidence
alter state
```

The implementation SHOULD reject every mutation that is invalid according to the specification.

This is particularly valuable for detecting implementations that appear strict but actually ignore important differences.

---

# 44. Cross-Implementation Testing

When practical, GRISP SHOULD have more than one implementation or independent reference model for critical deterministic rules.

For example:

```text
Delphi implementation
        vs
independent reference implementation
```

Their outputs MAY be compared for:

* canonical representation;
* hashes;
* parser decisions;
* state transitions;
* policy decisions;
* validation results.

This provides a powerful defense against implementation-specific mistakes.

---

# 45. Reference Model

Critical semantics SHOULD have a compact reference model.

The reference model SHOULD prioritize:

```text
simplicity
clarity
determinism
auditability
```

over production optimization.

Production implementations can then be tested against the reference model.

The reference model itself remains subject to independent review.

---

# 46. Final Artifact Rule

The artifact being committed MUST be the artifact being verified.

Conceptually:

```text
source S
   |
   v
artifact A
   |
   v
verification(A)
   |
   v
commit(A)
```

The following MUST NOT be accepted:

```text
verify(A)
modify(A)
commit(A)
```

without revalidation appropriate to the modification.

Likewise:

```text
verify(A)
build(B)
commit(B)
```

MUST NOT be considered valid unless B is proven to be exactly the verified artifact under the applicable identity rules.

---

# 47. Methodology Invariants

The following invariants SHOULD be treated as foundational GRISP implementation rules.

```text
M-001
No LLM may be the sole authority for correctness.

M-002
No artifact may be accepted without objective evidence
required by the specification.

M-003
Missing mandatory information must fail closed.

M-004
An implementation may not silently redefine the specification.

M-005
An implementation may not self-certify correctness.

M-006
Objective verification outranks subjective scoring.

M-007
Every critical defect should become a regression test.

M-008
The exact artifact verified must be the artifact accepted.

M-009
Existing implementation behavior must not be assumed normative.

M-010
Every accepted implementation must be traceable to the
specification revision and evidence that established acceptance.
```

---

# 48. Recommended GRISP Development Workflow

For normal development, the practical workflow is:

```text
1. Freeze specification revision.

2. Extract every normative requirement.

3. Audit the specification independently.

4. Build the requirement/test matrix.

5. Create negative and adversarial tests.

6. Design the implementation architecture.

7. Implement independently from the old implementation.

8. Build with the real toolchain.

9. Run deterministic validation.

10. Perform independent code review.

11. Perform adversarial review.

12. Run complete conformance tests.

13. Convert every discovered defect into a regression test.

14. Repair.

15. Repeat verification.

16. Perform final artifact verification.

17. Evaluate hard acceptance criteria.

18. Commit only after acceptance.
```

---

# 49. Recommended First Application to GRISP v1.0

The methodology SHOULD first be applied to the existing GRISP implementation before extending its feature set.

The existing implementation SHOULD be audited against the complete v1.0 contract.

Known classes of behavior requiring particular attention include:

```text
strict artifact parsing
required-field enforcement
artifact identity
canonicalization
policy authorization
state-transition guards
evidence validity
compile/run/test evidence
final verification
atomic commit
concurrency/TOCTOU protection
conformance coverage
GARP/provider completeness
```

The goal is not to preserve the existing implementation.

The goal is to determine objectively which parts are conformant and which are not.

```text
valid HelloWorld accepted
```

This vertical slice provides an empirical test of both:

# 51. Success Criterion

The methodology is successful when an implementation generated or repaired through the process can withstand:

```text
specification review
+
independent implementation review
+
adversarial review
+
deterministic conformance testing
+
regression testing
+
final verification
```

while producing reproducible acceptance evidence.

The methodology is not successful merely because:

```text
the code compiles
the code looks good
an LLM approves it
multiple LLMs agree
basic tests pass
```

---

# 52. Final Principle

GRISP is intended to provide a deterministic execution substrate for reasoning systems.

Its implementation process MUST therefore apply the same principle to the development of GRISP itself:

> **Reasoning may propose.
> Testing may challenge.
> Review may criticize.
> Repair may modify.
> Evidence may establish.
> Deterministic verification decides.**

No AI agent is trusted merely because it is capable.

No implementation is trusted merely because it is plausible.

No artifact is accepted merely because an agent says it is correct.

**GRISP correctness is earned through independently reproducible evidence.**

## 53. Versioning

This document is:

```text
GRISP Implementation Methodology v1.0
```

Changes to this methodology SHOULD themselves be managed under the same methodology.

A future methodology revision MUST identify:

* changed rules;
* compatibility impact;
* affected implementation processes;
* affected conformance tests;
* affected acceptance logic.

The methodology is therefore subject to the same engineering discipline that it imposes on GRISP implementations.

This gives us the methodological layer that the current implementation process was missing. The next logical step is to turn this into a **machine-readable GRISP Implementation Contract + requirement/test matrix**, then use that to audit the current Delphi implementation rather than continuing to patch it.
