G-Blocks: A Universal Typed Graph Expression Format
Specification Version 1.0
==================================================

1. Introduction
---------------

G-Blocks are a typed, declarative, graph-structured representation format
designed for expressing data, computation, and relationships in a way that is:

- crystal clear
- strongly typed
- unambiguous
- scalable
- universal
- LLM-friendly
- implementation-friendly (e.g. Delphi, C, Go)
- GRISP-native (graph rewrite information symbolic processor)

G-Blocks unify the readability of block-structured languages with the expressive
power of graph-based computation.

They are suitable for:

- tool interfaces
- symbolic computation
- configuration
- data modeling
- protocol definitions
- AI-model interaction
- graph rewriting systems
- GRISP-style information processing


2. Core Concepts
----------------

2.1 Nodes
---------

A node is the fundamental unit of structure.

Syntax:

  node <NodeName> {
      ...
  }

A node represents:

- an entity
- a concept
- a tool
- a value container
- a graph vertex

Node names are identifiers using standard programming-language conventions
(e.g. letters, digits, underscore, starting with a letter or underscore).


2.2 Edges
---------

Inside a node block, each line defines an edge:

  <EdgeName>: <Type> = <Value>

An edge is a typed, labeled connection from the node to a value or another node.

Edges are:

- explicit
- strongly typed
- unambiguous


2.3 Types
---------

G-Blocks support a minimal but extensible type system:

- number
- string
- boolean
- identifier
- array<T>
- node (nested block)

Examples:

  a: number
  name: string
  flag: boolean
  tool: identifier
  items: array<number>
  metadata: node

Future extensions may include (but are not limited to):

- map<K,V>
- tuple<T1,T2,...>
- optional<T>
- union<T1|T2>
- range<T>
- set<T>


2.4 Values
----------

Values must match their declared type.

Examples:

  a: number = 5
  b: string = "Hello"
  flag: boolean = true
  tool: identifier = tool.math.add
  items: array<number> = [1,2,3,4]

Nested nodes are allowed:

  metadata: node = {
      timestamp: string = "2026-05-15T22:35:00"
      user: string = "Skybuck"
  }

This allows hierarchical and graph-like structures to be expressed clearly.


3. Graph Semantics
------------------

G-Blocks represent typed labeled graphs.

- Each "node" block is a graph vertex.
- Each "<EdgeName>" is a labeled edge.
- Each "<Value>" is either a literal, an identifier, an array, or another node.
- Arrays represent multi-edges or ordered collections.
- Identifiers represent references to other nodes or symbolic names.

This aligns with GRISP's graph rewrite model:

- Programs are graphs.
- Data is graphs.
- Execution is graph rewriting.


4. Tool Interface Definition
----------------------------

Tools are defined as nodes that describe their parameters and return types.

Example: math.add

  node tool.math.add {
      a: number
      b: number
      returns: number
  }

This defines:

- the tool name: tool.math.add
- the parameter names: a, b
- the parameter types: number, number
- the return type: number

Example: string.concat

  node tool.string.concat {
      a: string
      b: string
      returns: string
  }

Example: sort.asc

  node tool.sort.asc {
      items: array<number>
      returns: array<number>
  }


5. Tool Call Representation
---------------------------

A tool call is represented as a node that specifies:

- which tool is being called
- the arguments and their values

Example: call math.add with a = 5, b = 7

  node call {
      tool: identifier = tool.math.add
      a: number = 5
      b: number = 7
  }

Example: call string.concat with "Hello" and "World"

  node call {
      tool: identifier = tool.string.concat
      a: string = "Hello"
      b: string = "World"
  }

Example: call sort.asc with [5,3,9,1]

  node call {
      tool: identifier = tool.sort.asc
      items: array<number> = [5,3,9,1]
  }


6. Tool Response Representation
-------------------------------

A tool response is also represented as a node.

Example: result of math.add

  node result {
      value: number = 12
  }

Example: result of string.concat

  node result {
      value: string = "HelloWorld"
  }

Example: result of sort.asc

  node result {
      value: array<number> = [1,3,5,9]
  }


7. Design Goals
---------------

G-Blocks were designed to satisfy the following goals:

7.1 Clarity
-----------

Every construct has exactly one meaning. The syntax is simple and regular:

  EdgeName: Type = Value

No hidden rules, no implicit typing, no ambiguous nesting.


7.2 Strong Typing
-----------------

Types are explicit and enforced. This enables:

- static validation
- safer transformations
- clearer contracts between components
- easier integration with strongly typed languages (e.g. Delphi, Rust, Go)


7.3 Graph-Native
----------------

Nodes and edges map directly to graph structures:

- node -> vertex
- edge -> labeled edge
- value -> literal or reference

This makes G-Blocks a natural fit for:

- graph rewriting systems
- GRISP-style computation
- knowledge graphs
- symbolic reasoning


7.4 LLM-Friendly
----------------

G-Blocks avoid common pitfalls for language models:

- no commas to forget
- no braces to mismatch
- no quotes to escape
- no indentation rules
- no deeply nested JSON

The structure is block-based and line-based, which models handle well.


7.5 Implementation-Friendly
---------------------------

G-Blocks are easy to parse and validate in languages like Delphi, C, C++, Go,
Rust, etc. A simple line-based parser can:

- detect node boundaries
- parse edges
- enforce types
- build an in-memory graph representation


7.6 Universal and Scalable
--------------------------

G-Blocks can represent:

- simple tool calls
- complex nested configurations
- large graphs
- protocols
- schemas
- symbolic expressions

The type system and syntax are extensible without breaking existing documents.


8. Comparison to Other Formats
------------------------------

JSON:
- Strengths: ubiquitous, supported everywhere.
- Weaknesses: punctuation-heavy, weak typing, easy to break, hard for LLMs.

XML:
- Strengths: structured, extensible.
- Weaknesses: verbose, noisy, angle-bracket heavy.

YAML:
- Strengths: human-readable.
- Weaknesses: indentation-sensitive, ambiguous, fragile.

S-expressions:
- Strengths: simple, uniform.
- Weaknesses: tree-only, no explicit types, positional arguments.

Protobuf (text/binary):
- Strengths: efficient, typed.
- Weaknesses: not naturally human-readable (binary), schema-dependent.

G-Blocks:
- Strengths: typed, clear, graph-native, human-readable, LLM-friendly.
- Weaknesses: new format (requires tooling and adoption).


9. Formal Grammar (EBNF-style)
------------------------------

This is a simplified EBNF-style grammar for G-Blocks:

  GBlock      = "node", Identifier, "{", { Edge }, "}" ;
  Edge        = Identifier, ":", Type, [ "=", Value ], Newline ;
  Type        = Identifier | ArrayType ;
  ArrayType   = "array", "<", Type, ">" ;
  Value       = Literal | Identifier | Array | NodeBlock ;
  NodeBlock   = "{", { Edge }, "}" ;
  Array       = "[", [ Value, { ",", Value } ], "]" ;
  Literal     = Number | String | Boolean ;

Notes:

- Identifier: a sequence of letters, digits, and underscores, not starting with a digit.
- Number: integer or floating-point literal.
- String: double-quoted text, with standard escaping rules.
- Boolean: "true" or "false".
- Newline: end-of-line marker.
