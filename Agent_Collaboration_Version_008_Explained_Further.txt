# GRISP - Agent Collaboration Protocol Version 0.08
# Planning and execution unified into a single graph lifecycle
# (Date: 9 june 2026 by Skybuck Flying + ChatGPT + CoPilot)
# ============================================================

Overview
This release tightens the model into a single, coherent graph-first runtime. The planner now writes native GRISP nodes and edges directly; planning, optimization, activation, assignment, execution, and synthesis are all expressed as graph rewrites operating on the same node types. Provenance for planning runs is explicit so plans remain auditable and reversible.

Key improvements in Version 0.08
- **Single lifecycle field**: Goals and Tasks use one lifecycle attribute (planned → pending → assigned → in_progress → waiting_tool → completed | failed). No separate phase/status pairs; invalid state combinations are eliminated.
- **Planner emits native graph**: Planners create ordinary `Goal` and `Task` nodes and native edges (`subgoal_of`, `belongs_to_goal`, `depends_on`) with `lifecycle = "planned"`. No separate Planned* types or special planned_* edges.
- **Provenance for plans**: Every planner run is a `PlanningRequest` node; created nodes link back via `created_by_plan` edges for auditing, pruning, and rollbacks.
- **Declarative plan optimization**: Validation, deduplication, cycle detection, and balancing are ordinary GRISP rules (e.g., `MergeDuplicateTasks`, `DetectCycle`) that operate on planned nodes before activation.
- **Activation separated from assignment**: Activation flips `lifecycle` from `planned` → `pending`; assignment is a separate rule that flips `pending` → `assigned`. This cleanly separates “is executable” from “who executes it.”
- **Tool and planning runtimes remain side-effect boundaries**: `ToolRequest`/`ToolResult` and `PlanningRequest`/`PlanningResult` are explicit runtime interactions; the graph engine treats them as external events to be integrated.
- **Capability and capacity flexible**: Capability matching is rule-driven (`CanExecute`), and capacity is modeled but left extensible (graph-based load nodes are supported later).
- **Planner-as-agent supported**: Planning can be implemented as an ordinary task assigned to a Planner agent, making planning itself a first-class, auditable workflow.
- **Engine-friendly strategy**: The strategy pipeline (PlanOptimization → Activation → Assignment → Execution → Integration → Synthesis) is explicit and ready to map to the runtime scheduler.
